"Knowledge-Based Pull Requests" is a paper by Xinyu Zhang and Weiwei Sun of Fudan University proposing a change to what crosses a trust boundary when an outside contributor submits work to a project. Its premise is that AI coding agents have moved the bottleneck: "code is increasingly cheap, while understanding intent, negotiating scope, and governing long-term project responsibility remain costly." Its proposal, [[DefinedTerm/knowledge-based-pull-requests]], is that the artifact crossing the boundary should be a human-confirmed knowledge package rather than a patch, with mergeable code regenerated inside the receiving project.

## Key Findings

The paper's framing contrast is three-way. In an issue-based flow, sparse knowledge and no code cross the boundary. In a traditional pull request, external code crosses and becomes the merge candidate. In the proposed workflow, external code is only one source within a knowledge package, and the code that can enter the codebase is generated by a project-owned inner trusted coding agent under repository and security policy. The authors state the resulting governance benefit as separating two decisions that traditional pull requests collapse into one: whether the knowledge should enter the project, and whether a particular implementation should be merged.

A point the paper argues at some length is that the answer is neither raw traces nor raw code. Attaching the collaborator's agent transcript is called insufficient, because raw traces "can contain stale conclusions, irrelevant trial-and-error, copied documents, secrets, private environment details, and untrusted instructions", and can be too long to read — which would merely move the bandwidth problem from code review to trace review. What is needed instead is described as "a reviewable and transformable knowledge object: compact enough for project-side reviewers, structured enough for agents, explicit about uncertainty, and backed by provenance when a claim needs inspection."

The authors are careful about what they are claiming. They state that knowledge extraction, specification writing, provenance tracking and agentic code generation are not individually new capabilities, and that the contribution is "a workflow-level recombination for software collaboration across trust boundaries". They also anticipate the sharpest objection themselves — that the proposal is spec-driven development for untrusted contributors — and grant that it intentionally borrows the idea that structured intent can guide agentic implementation while adding a governance layer around source, evidence and authority.

The cost model is stated as a condition rather than a benefit. The workflow adds stages — knowledge extraction, view generation, human confirmation, knowledge review, project-side regeneration, fidelity checking, and ordinary code review — so the authors write that it "is useful only when agents can absorb routine, auditable transformation work and when that absorbed work is cheaper than asking project-side developers to reverse-engineer external code, repair architecture mismatches, and rediscover constraints late in review", and that for small mechanical fixes the path is likely too heavy. They call this a hypothesis to evaluate rather than a property of the workflow.

Two governance details are worked out in more depth than the rest. **Implementation authority** is named as the central governance claim: external code can be valuable evidence that a problem is real, a behaviour feasible, or an edge case relevant, but it is not the default artifact to merge, because the inner trusted agent can operate with the project's tests, style rules, architecture, dependency policy and security rules, and can be instrumented, sandboxed and audited. The authors add that this "does not make the inner trusted agent infallible. It makes control over implementation explicit." **Contributor credit** is flagged as a problem the workflow creates: the external collaborator does additional knowledge work and may not become the author of the merged code, which "can turn KPR into a worse deal for contributors than an ordinary PR" without explicit credit, so the paper argues contribution credit should be recorded separately from code authorship.

## Context

The empirical component is deliberately small and the authors label it as such. They built a controlled simulation pilot over seven merged public pull requests, stating explicitly that it "is not an end-to-end validation of KPR and does not involve project maintainers" and tests only whether real PR material can be converted into packages and evaluated under controlled information loss and synthetic poisoning. Artifacts were scored by the authors themselves on a 0–2 rubric, which they say should be read "as an instrumentation check rather than as a claim about maintainer productivity".

Three limited observations came out of it. Ordinary summaries and knowledge packages both preserved visible intent across all seven cases, which the authors partly attribute to descriptive PR titles and small changes. Packages made evidence traceability explicit when patch signals were available, where normal summaries did not separate claims, evidence, provenance and safety. And compact external-code signals proved useful: with the PR description withheld, packages still preserved enough implementation knowledge in six of seven cases, while with the diff withheld only five of seven reached implementation sufficiency — the clearest failure being an automated plugin-list update, where a compact summary does not contain enough information to regenerate an exact list.

The synthetic poisoning result is hedged more sharply still. All seven poisoned packages rejected the inserted hunk, but the authors state this holds "because the harness marks it as non-legitimate external code", showing only that the artifact can represent untrusted-code distinctions and be stress-tested, "not that KPR is secure against real adversarial prompt injection or malicious code". The pilot also exposed a weakness the authors report against themselves: constraint specificity stayed low across all conditions, with packages capturing generic constraints but not rich project-specific non-goals.
