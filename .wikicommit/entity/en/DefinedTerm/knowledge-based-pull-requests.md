Knowledge-Based Pull Requests (KPR) is the workflow proposed in [[ScholarlyArticle/knowledge-based-pull-requests]] for software collaboration across a trust boundary — the paper names open source, enterprise, vendor, contractor and customer-driven settings. Its defining move is what it demotes: an external collaborator's local code, tests and cleaned agent interaction trace are treated as knowledge sources rather than as the default merge candidate, and the code that can actually enter the codebase is generated by a project-owned inner trusted coding agent operating under the receiving project's repository context, engineering conventions, tests and security policy.

## Usage

The workflow has seven stages. An external collaborator works locally with a coding agent to explore, implement and test a change. An extraction agent cleans the local trace, diff, tests, logs and human corrections and distils them into a KPR package. A transformation agent renders that package into whichever reviewer-facing form the project prefers — a concise reviewer brief, design memo, risk checklist, test plan, or implementation brief. The collaborator reviews and confirms the package before it is submitted. Project-side reviewers then gate knowledge acceptance and code integration as two separate decisions, with the inner trusted agent regenerating the candidate implementation in between.

Four agent roles are distinguished by the kind of work they do: a **local exploration agent** helping the collaborator discover the need, try implementations, run tests and identify edge cases; an **extraction agent** turning messy local traces, diffs and test evidence into a structured package with provenance; a **transformation agent** converting the package into the reviewer-facing views above; and the **inner trusted coding agent** operating inside the project boundary. The stated division of labour is that agents carry the routine translation, summarization and regeneration work while the decisions themselves remain human-governed.

The paper is specific about what the workflow is not. It is not a replacement for code review, and not a demand that reviewers accept an external collaborator's original implementation — the point is the opposite, that a project can accept, reject or modify the underlying idea without accepting the external patch as authoritative. It does not claim a design document is sufficient for merge, and does not claim project-side regeneration eliminates license or security obligations. Nor does it ask every pull request to become a knowledge package: small bug fixes, compatibility patches and low-risk mechanical changes are said to remain more efficiently handled as ordinary code pull requests. The intended scope is changes where reconstructing intent from code is expensive.

Its authors name project-side regeneration as the most fragile part of the design, noting that the inner trusted agent may fail to reconstruct a faithful implementation from an accepted package, especially for cross-module behaviour changes, and that more project context is not automatically better because repository-level instruction files can raise inference cost. They also identify a bargain the workflow changes for the contributor, who does extra knowledge work yet may not author the merged code, and argue that credit must therefore be recorded separately from code authorship — a project distinguishing "knowledge package by" from "implementation generated by" and "reviewed by".

## Related Terms

The workflow borrows from [[DefinedTerm/spec-driven-development]] the idea that structured intent can guide agentic implementation, and its authors treat "KPR is spec-driven development for untrusted contributors" as the strongest equivalence critique of their proposal, answering it by pointing to the governance layer around source, evidence and authority that they add on top.
