Ralph — also referred to as the Ralph Wiggum technique, after the *Simpsons* character — is a technique for running a coding agent unattended, named by [[Person/geoffrey-huntley]] in [[BlogPosting/ralph-wiggum-as-a-software-engineer]]. In its purest form it is a Bash loop that pipes a fixed prompt file to an agent over and over (`while :; do cat PROMPT.md | claude-code ; done`), doing one task per iteration and starting each iteration with a fresh context window. Huntley's characterisation of why it works is that "the technique is deterministically bad in an undeterministic world": every loop will fail in identifiable ways, and those failures are answered by adding instructions to the prompt rather than by changing tools. He describes it as workable with any tool that does not cap tool calls and usage.

## Usage

Huntley's account gives several operating rules for it.

**One item per loop.** The agent is asked to do one thing per iteration and trusted to choose which thing is most important — which he acknowledges reads as full hands-off vibe coding that "will test the bounds of what you consider responsible engineering." The restriction may be relaxed as a project stabilises, and should be narrowed back when results go off the rails.

**Deterministic stack allocation.** Each loop should place the same things into context — the plan file (`fix_plan.md`) and the specifications — even though re-spending that allocation every loop is wasteful, on the grounds that a fuller context window produces worse outcomes.

**The primary context window as a scheduler.** Rather than allocating to the main window, the loop should dispatch [[DefinedTerm/subagents]] for expensive work such as searching the filesystem or summarising a test run. Huntley notes that fanning out to hundreds of subagents for builds and tests produces "bad form back pressure," so his prompts permit many parallel subagents for search and file writing but only one for building and testing.

**Two phases.** Generation is cheap and steered by specifications and a project-specific standard library; the hard part is rejecting output that is wrong, which is the job of [[DefinedTerm/backpressure]].

**Tuning by adding signs.** The recurring metaphor is putting up a sign next to the slide so Ralph looks before jumping. Two failure modes Huntley singles out are the agent running `ripgrep`, concluding something is unimplemented, and building it again — answered with an instruction not to assume — and the model's bias toward placeholder and minimal implementations, answered with an escalating instruction demanding full implementations. He notes the models chase their reward function, and that the reward function is compiling code.

**Capturing reasoning for future loops.** Because each iteration starts fresh, the agent is instructed to document why a test and its backing implementation matter. Huntley describes this as leaving notes for future iterations that will not have the reasoning in their context window, and reports it helps the model decide whether a failing test should be fixed, changed, or deleted.

**A TODO list treated as disposable.** The loop maintains a prioritised plan file, regenerated by a separate planning loop when it goes stale; Huntley says he has deleted it many times and watches it "like a hawk."

### A second account of the same loop

[[BlogPosting/the-code-agent-orchestra]] describes the pattern under the name **the Ralph Loop**, which it says was popularised by [[Person/geoffrey-huntley]] and Ryan Carson — a claim about who spread the technique, not about who first built it. Its own framing of the core idea is "stateless-but-iterative": the agent resets each iteration so it never accumulates confusion, while continuity is carried outside the context window.

The cycle it states has five steps — pick the next task from a `tasks.json` file, implement the change, validate by running tests, types and lint, commit if the checks pass and update task status, then clear the context and start fresh. It names four channels through which memory survives a reset: git commit history, a progress log, the task state file itself, and [[DefinedTerm/agents-md]] as long-term semantic memory. Its stated safeguards are feeding errors back for auto-retry but killing and reassigning after three or more stuck iterations, always working on feature branches, hard limits on iterations, time and tokens, and a pull request the developer reviews before merge. Its stated adoption path is one loop overnight, graduating to ten loops on ten branches.

The same account records two implementations built on the pattern: Ryan Carson's standalone `ralph` tool (snarktank/ralph), which implements the core loop, and his Antfarm project, which layers multi-agent orchestration on top of OpenClaw using the same pattern. The post's claim is that the core idea generalises across tools, which sits alongside rather than replaces Huntley's own narrower scope statement above.

### Where the loop ended up

[[BlogPosting/survey-of-development-workflows-in-the-coding-agent-era]] places the Ralph Loop among long-session design patterns, all of which it says share one principle: keep the context window stateless and use the filesystem and git as persistent storage. Its account of the mechanism matches the original — a goal spec in `PROMPT.md`, one iteration of work per pass, exit when the context fills or the work finishes, and the loop restarting with a fresh context — and adds the structural claim that context rot is avoided because every iteration starts at 0% fill. It dates the pattern to June 2025 and records that Anthropic integrated it as an official `ralph-wiggum` plugin in December 2025.

Two extensions are named. `ralph-orchestrator`, a Rust implementation, adds a backpressure gate that blocks advancing until tests, lint and typecheck pass, plus warnings at 70k tokens and forced rotation at 80k. `oh-my-claudecode`'s Ralph mode offers 32 specialised agents, parallel execution of five or more concurrent tasks, and compaction-proof persistent memory in a notepad file.

The survey also sets the loop within a complexity spectrum for session design, running from the one-line bash loop through an official loop command, [[DefinedTerm/frequent-intentional-compaction]] as a method, a two-agent arrangement, and a 19-agent framework — in order of increasing sophistication rather than increasing merit.

### The loop as the base of an agent-team harness

[[BlogPosting/building-a-c-compiler-with-parallel-claudes]] uses the same shape as its starting point, and says so — its author notes that if you have seen the Ralph loop, the harness "should look familiar." The implementation is a bash `while true` loop that starts a fresh Claude Code session as soon as the previous one exits, logging each run against the current commit, with the prompt instructing the agent to break the problem into small pieces, track what it is working on, decide what to do next, and keep going until it is perfect. The author notes the agent has no choice about the last part, since the loop runs forever — and records one occasion where Claude accidentally killed its own shell and ended the loop.

What that project adds to the pattern is parallelism: the same generation loop spawns each new session in a fresh container, with several such loops running at once and coordination handled by lock files in the shared repository rather than by any agent-to-agent protocol.

## Related Terms

Ralph is one concrete implementation of [[DefinedTerm/agentic-coding]] and sits at the autonomous end of it, close to [[DefinedTerm/vibe-coding]] in its willingness to let the agent decide — Huntley applies that phrase to it himself — while relying on [[DefinedTerm/backpressure]] and specifications for the discipline that [[DefinedTerm/vibe-engineering]] and [[DefinedTerm/spec-driven-development]] locate in human review. It differs deliberately from [[DefinedTerm/multi-agent-orchestration]]: Huntley argues that agent-to-agent coordination was not needed at the time and compares non-deterministic agents-as-microservices unfavourably to a single monolithic process.

Its stated scope is narrow. Huntley presents it as a technique for bootstrapping greenfield projects, with the expectation of getting roughly 90% of the way, and says outright that he would not use it in an existing codebase.
