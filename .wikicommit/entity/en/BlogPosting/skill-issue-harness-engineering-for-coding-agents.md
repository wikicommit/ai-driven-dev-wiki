"Skill Issue: Harness Engineering for Coding Agents" is a post published on the HumanLayer blog on 12 March 2026 by an author identified only as Kyle. Its premise comes from the team's own experience: after a year of watching coding agents fail "in every conceivable way: ignoring instructions, executing dangerous commands un-prompted, and going in circles on the simplest of tasks," and across dozens of projects and hundreds of sessions, they concluded that "it's not a model problem. It's a **configuration problem**."

The post is explicit that this is not a claim that models will stop improving. Its argument is that unexpected failure modes are fundamental to non-deterministic systems, so as models get smarter they will be given bigger and harder problems and will continue to fail in unexpected ways — which makes the useful question how to get the most out of today's models rather than which future model will fix things. The title is the punchline: "The model is probably fine. It's just a skill issue."

Structurally it is a tour of configuration surfaces, each with the team's own findings about what worked and what did not. It reads as one practitioner team's account of its own workflow rather than as measurement, and says so — the closing section is a candid list of things they tried and abandoned. The framing concept it develops is [[DefinedTerm/harness-engineering]].

## Key Points

- **Context files first, and short.** The post argues [[DefinedTerm/context-files]] are usually worth customising before anything else, since they are deterministically injected into the system prompt. Its response to the ETH Zurich study it summarises — testing 138 agentfiles across various repos, finding that LLM-generated ones actively hurt performance while costing over 20% more, that human-written ones helped only about 4%, that agents spent 14–22% more reasoning tokens processing context-file instructions and took more steps without improving resolution rates, and that codebase overviews and directory listings did not help because agents discover structure on their own — is that the study confirms its own earlier advice rather than refuting it: avoid auto-generating the file, include as few instructions as reasonably possible, use progressive disclosure, and keep contents concise and universally applicable. It reports its own file is under 60 lines.
- **MCP servers are for tools, and fewer of them.** The post states that in practice [[DefinedTerm/model-context-protocol]] is used for plugging in tools, since the spec's resources, prompts, and elicitations "are generally not well-supported by MCP clients and coding agent harnesses." It flags two consequences of tool descriptions being injected into the system prompt: a prompt-injection risk, so never connect to a server you do not trust (and note that STDIO servers and others running client-side via `npx` or `uvx` can execute code on your host regardless); and context cost, since too many tools fill the window with descriptions. It cites Anthropic's experimental MCP tool search as evidence the failure mode is common enough to warrant a product response, and advises turning off unused servers that expose many tools.
- **Prefer a CLI to an MCP server where one exists.** The team's finding is that when an MCP server duplicates functionality already available as a CLI well-represented in training data — GitHub, Docker, most databases — prompting the agent to use the CLI works better, because the model already knows the tool and the output composes with `grep` and `jq`. Their worked example is replacing the Linear MCP server with a small CLI wrapping the Linear API, documented as six example invocations in their context file, which they report saved thousands of tokens of tool definitions plus more from verbose MCP responses.
- **Skills are for reusable knowledge, loaded on demand.** The post's account of [[DefinedTerm/agent-skills]] is a [[DefinedTerm/progressive-disclosure]] argument from its own failure: stuffing every instruction and tool into the system prompt made the agent worse, blowing the instruction budget before work began. It describes activation concretely — `SKILL.md` is loaded into the context window as a user message and the agent is told which directory it came from, so the skill file can point at other bundled files and say when to read them. It notes the packaging limitation that MCP servers and custom tools cannot be bundled into a skill directly; they must be shipped as an executable, CLI, or package. It also warns that skill registries have already been found distributing hundreds of malicious skills, and that skills should be treated like `npm install random-package` because registries can execute arbitrary code on the machine.
- **Sub-agents are for context control, not personas.** The post reports that role-based sub-agents — "frontend engineer," "backend engineer," "data analyst" — did not work, and that what does work is using [[DefinedTerm/subagents]] as a **context firewall**: the dispatching agent sees only the prompt it wrote and the final result, with none of the intermediate tool calls or results entering its window. It names good uses as locating definitions, identifying codebase patterns, tracing information flow across service boundaries, and general research — tasks with a simple answer but many intermediate calls. Its convention is that sub-agents return condensed answers that themselves follow progressive disclosure, citing sources as `filepath:line` or URLs so the parent can fetch detail only if needed. Sub-agents also serve cost control on their account: an expensive model for the parent's planning and orchestration, a cheaper and faster one for each sub-agent.
- **Bigger context windows are not the fix.** The post is skeptical of extended-context models on the grounds that an extended-context release is usually the same model with sequence-extension math rather than a larger instruction budget: "A bigger context window doesn't make the model better at finding the needle — it just makes the haystack bigger." Its alternative is structural context isolation, with each sub-agent getting a fresh small high-relevance window and only condensed results flowing back, letting many context windows be stitched together for one problem. Where a harness has no native sub-agent support, it describes writing an MCP server that launches a new agent session and returns its final message — with the warning that combining this with native sub-agents lets them dispatch further sub-agents through MCP, and that harness MCP tool-call timeouts may need raising.
- **Hooks are for control flow.** The post describes [[DefinedTerm/agent-hooks]] as conceptually similar to git hooks and lists four uses the team relies on: notifications when an agent finishes or an approval has been pending too long; approvals expressed as rules more expressive than the default permissions model, its example being automatically denying any `Bash()` call that tries to run migrations with an instruction to ask the user instead; integrations such as sending a Slack message, opening a GitHub PR, or setting up a preview environment; and verification, running a typecheck or build every time the agent stops when it completes in a few seconds. Its worked example is a Stop hook running a formatter and TypeScript typecheck: silent on success, and on failure surfacing only the errors with exit code `2`, which tells the harness to re-engage the agent until they are resolved.
- **Back-pressure is the highest-leverage investment, and must be context-efficient.** The post states that the likelihood of solving a problem with a coding agent is strongly correlated with the agent's ability to verify its own work, and calls building [[DefinedTerm/backpressure]] into the repository one of the highest-leverage things the team has spent time on. Its mechanisms are typechecks and builds, unit and integration tests, code coverage reporting with a Stop hook prompting the agent when coverage drops, and UI interaction testing. The efficiency constraint comes from a specific failure: running the full test suite after every change flooded the window with 4,000 lines of passing tests, after which the agent lost track of the task and began hallucinating about test files it had just read. Their fix was to swallow output and surface only errors, for builds as well as tests — success silent, failure verbose.

## Context

The post situates itself against two neighbours it names directly. It treats harness engineering as a subset of context engineering, crediting the latter to the author's cofounder Dex Horthy and pointing to Viv's two posts as the complementary framing — one deriving four customization levers, the other working backwards from what models cannot do natively. It also reads OpenAI's post on the topic as taking a narrower view centred on back-pressure and verification, while flagging its own uncertainty about that reading.

Its empirical citations are secondhand summaries rather than the studies themselves: the ETH Zurich agentfiles study, and Chroma's context rot research, which it reports as testing 18 models on needle-in-a-haystack tasks and finding that performance degrades as context length increases, with steeper degradation when semantic similarity between the question and the relevant information is low. The post is candid that needle-in-a-haystack work "is admittedly quite different from agentic coding," and offers the finding as matching its experience rather than as proof of it.
