"Effective harnesses for long-running agents" は [[Organization/anthropic]] が2025年11月26日に公開した Justin Young によるエンジニアリング投稿である。多数のコンテキストウィンドウにまたがるタスクにおいて Claude Agent SDK に一貫した前進をさせるための社内の実験を報告するものであり、コード例つきの公開クイックスタートを伴っている。

投稿は中核の問題を、能力ではなく不連続性として述べる。エージェントは離散的なセッションのなかで働かねばならず、新しいセッションはそれ以前に何があったかの記憶をまったく持たずに始まる。喩えとして挙げられるのは、交代制で働くエンジニアが担当するソフトウェアプロジェクトであり、新しく来るエンジニアは前の交代の記憶を持たない。掲げられている立場は、[[DefinedTerm/compaction]] だけではこの隔たりは埋まらない、というものである。投稿が Opus 4.5 と名指す最前線のコーディングモデルでさえ、Agent SDK 上で複数のコンテキストウィンドウにわたるループで動かしても、「高水準のプロンプトだけを与えられたのでは、本番品質の Web アプリを構築するには至らない」——走っている例は「claude.ai のクローンを構築する」である。

処方箋は2部構成のハーネスである。**初期化エージェント（initializer agent）**——その特化したプロンプトが、まさに最初のセッションで環境を整える——と、**コーディングエージェント（coding agent）**——それ以降のすべてのセッションで走り、漸進的に前進し、構造化された更新を残す——である。脚注がこの分割に但し書きを付ける。この2つが別々のエージェントと呼ばれるのは、初期のユーザープロンプトが異なるからにすぎない。システムプロンプト、ツールの集合、ハーネス全体はそれ以外は同一である。投稿はこれを、更新された Claude 4 のプロンプティングガイドが勧める「まさに最初のコンテキストウィンドウには別のプロンプトを」という推奨に結びつけている。

## 主要な実践

投稿は、初期化エージェントが構築する環境を3つの構成要素に整理し、それぞれを観測された特定の失敗への対処として導入する。

- **JSON による機能リスト。** エージェントがアプリを一発で作り上げようとしたり、プロジェクトを早々に完成したと宣言したりするのを止めるため、初期化エージェントはユーザーのプロンプトを敷衍した包括的な機能要件のファイルを書く——claude.ai クローンの例では200を超える機能があり、それぞれが「ユーザーは新しいチャットを開き、クエリを打ち込み、Enter を押し、AI の応答を目にすることができる」といった端から端までの記述であり、構造化された `steps` と `passes` フィールドを持つ。すべてが初期状態では失敗と印されるため、後のエージェントは完全な機能とは何を意味するかの明確な輪郭を得る。コーディングエージェントは、このファイルを `passes` の状態を変えることによってのみ編集するよう促され、「テストを取り除いたり編集したりすることは受け入れられない。機能の欠落やバグにつながりうるからだ」といった強い言い回しの指示で補強される。投稿はこのファイル形式について具体的な理由を挙げている。実験の末に JSON に落ち着いたのは、「Markdown ファイルと比べて、モデルが JSON ファイルを不適切に変更したり上書きしたりする可能性が低い」からである。
- **漸進的な前進、一度に1機能。** コーディングエージェントは1セッションにつき1つの機能にだけ取り組むよう求められる。投稿はこれを、一度に多くをやりすぎるエージェントの傾向に対処するうえで決定的だと述べている。
- **すべてのセッションの終わりに、きれいな状態を。** 投稿は「きれいな状態」を具体的に、main ブランチへマージするのにふさわしい類のコードと定義する——重大なバグがなく、整然としてよく文書化されており、開発者が無関係な散らかりを片付けずに新しい機能に取りかかれる状態である。最も効果的だとわかった機構は、モデルに記述的なコミットメッセージで git へコミットさせ、進捗のファイルへ進捗の要約を書かせることであり、これはモデルが悪い変更を取り消して動く状態へ復帰することも可能にする。
- **ブラウザ自動化を通じた端から端までのテスト。** 投稿は、Claude が適切なテストなしに機能を完了と印すことを報告している。コードを変更し、ユニットテストを走らせたり開発サーバへ `curl` を実行したりさえするのに、その機能が端から端までは動いていないことを認識し損ねるのである。ブラウザ自動化のツールを使い、人間のユーザーがするようにテストせよと明示的に促すことで、これは大幅に改善した。投稿は、エージェントがコードだけからは明らかでないバグを見つけられるようになったことで、それらのツールが性能を劇的に高めたと評価している。述べられている限界も記録されている。Claude は Puppeteer MCP サーバ経由ではブラウザネイティブのアラートモーダルを見ることができず、それらのモーダルに依拠する機能は結果としてバグを含みやすかった。

コーディングの各セッションは、他の何かをする前に固定された状況把握の手順を走らせるよう促される。作業ディレクトリを見るために `pwd` を走らせ、直近の作業に追いつくために git のログと進捗のファイルを読み、まだ完了していない最優先の機能を選ぶために機能リストを読む。初期化エージェントはさらに、開発サーバを起動する `init.sh` スクリプトを書くため、各セッションは新しいものを実装する前に基本的な端から端までのテストを走らせられる——クローンの例では、サーバを起動し、Puppeteer MCP を使ってチャットを開き、メッセージを送り、応答を受け取ることである。これについての投稿の論拠は、壊れたアプリの上に新しい機能の実装を始めるエージェントは問題を悪化させるだけだ、というものである。

投稿はこの部分を、観測された4つの失敗モードと、それぞれに対処する初期化エージェントおよびコーディングエージェントの振る舞いを対応づける表で締めくくる。早すぎる勝利宣言、バグを抱えたまま、あるいは文書化されないまま残される環境、機能を早まって完了と印すこと、そしてアプリの動かし方を突き止めるのに時間を費やすことである。

## 範囲と留保

投稿は自らを「ありうる解の一組」として提示し、自身の未解決の問いを名指す。単一の汎用のコーディングエージェントが文脈をまたいで最良に振る舞うのか、それともマルチエージェントのアーキテクチャのほうが良いのかは依然として不明であると述べ、特化したテスト、品質保証、あるいはコードの整理のエージェントを、もっともらしい改善として示唆している。またこのデモがフルスタックの Web アプリ開発に最適化されていることを指摘し、知見を科学研究や金融モデリングといった分野へ一般化することを今後の課題として挙げている。

証拠は、Anthropic が自社の SDK とモデルを用いて行った社内実験であり、質的に報告されている——投稿が示すのは観測された振る舞いと、それを変えたプロンプトであって、ハーネスの設計どうしを測定して比較したものではない。
