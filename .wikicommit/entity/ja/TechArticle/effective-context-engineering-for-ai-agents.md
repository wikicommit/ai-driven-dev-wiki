「Effective context engineering for AI agents」は [[Organization/anthropic]] が2025年9月29日に公開したエンジニアリング記事であり、同社の Applied AI チームによるものである。言語モデルを用いた構築が、プロンプトに適した言葉を見つけることから、より広い問い——「われわれのモデルに望ましい振る舞いを生ませる可能性が最も高いのは、どのようなコンテキストの構成か」——に答えることへ移ったと論じ、その構成の各要素についてのメンタルモデルと具体的な技法の集合を提示する。

その指導原理は一文で述べられ結論でも繰り返される。良いコンテキストエンジニアリングとは、望ましい結果の可能性を最大化する、シグナルの高いトークンの可能な限り小さな集合を見つけることである。記事はこれをトークンの上限についてではなくモデルの振る舞いについての主張に根拠づけている。コンテキストは限界収穫逓減を伴う有限の資源として扱うべきである。モデルには「注意の予算」があり、トークンが1つ増えるたびにそれが消耗されるからだ。

これは Anthropic が自社製品で適用している実践についての同社自身の記述であり、いくつかの例は Claude Code がそれらをどう実装しているかを記述している。ここでの推奨は同社のものであって、この分野の概観ではない。

## 主な実践

- **適切な高度のシステムプロンプト。** 記事は2つの失敗モードを名指す。正確な振る舞いを引き出すために複雑で脆い if-else のロジックをハードコードすること、そして共有された文脈を前提とした漠然とした高レベルの指針を与えることである。最適な高度は、振る舞いを導くのに十分具体的でありながら、モデルに強力なヒューリスティクスを残すだけの柔軟さを持つものだと記述される。プロンプトを区切られた節へ整理することを推奨しつつ、モデルが良くなるにつれて厳密な書式の重要性は下がると指摘し、最良のモデル上で最小限のプロンプトから始め、観測された失敗に対処するために指示を加えていくことを勧めている。
- **トークン効率がよく曖昧でないツール。** ツールは自己完結的で、エラーに堅牢で、意図された用途が明確であるべきである。記事は肥大化したツールの集合を最もよくある失敗モードの一つとして名指し、ある状況でどのツールが当てはまるかを人間のエンジニアが断定できないなら、エージェントがそれ以上にうまくやることはない、という判定基準を示している。
- **網羅ではなく厳選された例。** few-shot のプロンプトは強く推奨されるが、記事はエッジケースの羅列をプロンプトへ詰め込むことに反対し、期待される振る舞いを描き出す多様で典型的な例の集合を好むとしている。
- **ジャストインタイムのコンテキスト取得。** 関連するデータをすべてあらかじめ前処理するのではなく、エージェントは軽量な識別子——ファイルパス、保存されたクエリ、ウェブのリンク——を保持し、実行時にツールを通じてデータを読み込む。記事は、Claude Code が的を絞ったクエリを書き、`head` と `tail` を使って大きなデータを読み込まずに分析することを例として挙げ、それらの参照のメタデータ自体がシグナルを担っていると論じる。`tests/` にある `test_utils.py` という名のファイルは、`src/core_logic/` にある同じ名前のファイルとは異なるものを含意する。記事は、実行時の探索が事前計算されたデータの取得より遅いというトレードオフを指摘し、ハイブリッドな戦略——一部のデータはあらかじめ、それ以上の探索はエージェントの裁量で——を Claude Code が実際に行っていることとして記述している。`CLAUDE.md` はあらかじめコンテキストへ投入され、glob と grep がファイルをオンデマンドで取得する。
- **長期にわたるタスクのための3つの技法。** [[DefinedTerm/compaction]]——コンテキストの上限に近づいた会話を要約し、その要約から再開する。構造化されたノートテイキング——エージェントがコンテキストウィンドウの外にノートを永続化し、リセット後にそれを読み戻す（[[DefinedTerm/agentic-memory]] を参照）。そしてサブエージェントアーキテクチャ——専門特化したサブエージェントがきれいなコンテキストウィンドウで広く探索し、およそ 1,000〜2,000 トークンに凝縮した要約を返す（[[DefinedTerm/multi-agent-orchestration]] を参照）。記事はそれぞれをタスクの形へ対応づけている。広範なやり取りを要する作業にはコンパクション、明確なマイルストーンを伴う反復的な開発にはノートテイキング、並行的な探索が報われる調査と分析にはマルチエージェントである。

## 適用範囲と留保

記事の中心的な実証上の主張は [[DefinedTerm/context-rot]]——コンテキストウィンドウ内のトークンが増えるにつれ、モデルがそのコンテキストから情報を正確に想起する能力が下がる——であり、これを needle-in-a-haystack のベンチマークに関する研究に帰し、トランスフォーマーのアーキテクチャにおける n² のトークン対関係と、短い系列がより一般的である訓練分布によって説明している。その結果を、明確な断崖ではなく性能の勾配として特徴づけている。

推奨のうち2つには明示的な留保が付されている。コンパクションについては、過度に強いコンパクションは、その重要性が後になって初めて明らかになる微妙な文脈を失わせると警告し、複雑なエージェントのトレース上でコンパクションのプロンプトを調律する際は、まず再現率を最大化してから適合率を改善することを勧めている。全体の流れの方向については、より賢いモデルほど規定的なエンジニアリングを必要としなくなるだろうと予測し、「うまくいく最も単純なことをせよ」が最良の助言であり続けるだろうと述べている。つまりここでの個別の技法は、耐久性のあるアーキテクチャとしてではなく現時点の実践として提示されている。
