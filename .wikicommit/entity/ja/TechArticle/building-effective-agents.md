この投稿は、Anthropic が業界を横断して LLM エージェントを構築する数十のチームと働くなかで学んだことを凝縮したものであり、その見出しとなる知見は否定的である。「最も成功した実装は、複雑なフレームワークや特化したライブラリを使っていなかった。むしろ、単純で組み合わせ可能なパターンで構築していた。」

[[DefinedTerm/agentic-system]] のもとで記述されるその構成上の区別は、**ワークフロー**——LLM とツールが事前に定義されたコードの経路を通じてオーケストレーションされるもの——を、**エージェント**——LLM が自らのプロセスとツールの使用を動的に方向づけるもの——から分ける。投稿は5つのワークフローパターンと1つのエージェントのパターンを、複雑さの昇順で目録化し、*拡張された LLM*——検索、ツール、メモリで強化されたモデルであり、投稿はこれをユースケースに合わせて仕立て、容易でよく文書化されたインターフェースを与えることを勧める——から始める。

このページには、記述されているツールの情勢の多くが2024年12月以降に変化したという注記があり、現在のアプローチについては [[TechArticle/scaling-managed-agents|Managed Agents]] の仕事を読者に指し示している。

## 主要な実践

**うまくいくもののうち最も複雑でないものを選ぶ。** 推奨は、可能な限り単純な解を見つけ、必要なときにだけ複雑さを増すことである——それは「そもそもエージェンティックなシステムを構築しないことを意味するかもしれない」。エージェンティックなシステムは、タスクの性能と引き換えに待ち時間とコストを差し出すからだ。多くのアプリケーションでは、検索と文脈内の例を伴う単一の LLM 呼び出しを最適化すれば十分である。より高い複雑さが正当化される場合、ワークフローは明確に定義されたタスクに対して予測可能性と一貫性を提供し、エージェントは大規模な柔軟性とモデル駆動の意思決定に適する。

**フレームワークには用心せよ。** それらは LLM の呼び出し、ツールの定義と解析、呼び出しの連鎖といった低水準のタスクを単純化するが、「しばしば余分な抽象の層を作り出し、それが背後のプロンプトと応答を覆い隠してデバッグを難しくする」うえ、もっと単純な構成で足りるところに複雑さを加えたくさせる。助言は、多くのパターンが数行のコードで済むのだから LLM の API を直接使うことから始めること、そしてフレームワークを使うなら背後のコードを理解することである。内部で何が起きているかについての誤った仮定は、顧客のエラーのありふれた源として名指されている。

**5つのワークフローパターン。**

- **プロンプトチェイニング（Prompt chaining）**はタスクを固定された系列へ分解し、各呼び出しが前の出力を処理する。中間ステップにはプログラム的なゲートを任意で置ける。各呼び出しをより易しいタスクにすることで、待ち時間と引き換えに正確さを得る。固定されたサブタスクへきれいに分解できるタスクに適する。
- **ルーティング（Routing）**は入力を分類し、特化した後続処理へ振り向け、関心の分離とより特化したプロンプトを可能にする。個別に扱ったほうがよい明確なカテゴリがあり、かつ分類を正確に行える場合に適する。
- **並列化（Parallelization）**には2つの変種がある。*区分け（sectioning）*はタスクを独立したサブタスクへ分けて並行に走らせるものであり、*投票（voting）*は同じタスクを複数回走らせて多様な出力を得るものである。掲げられている根拠は、複数の考慮事項を伴う複雑なタスクでは、各考慮事項がそれぞれの呼び出しを得たときにモデルは概してよりよく振る舞う、というものである。
- **オーケストレータ・ワーカー（Orchestrator-workers）**では、中央の LLM が動的にタスクを分解し、ワーカーへ委譲し、結果を総合する。投稿はこれを並列化と明示的に区別する。地形としては似ているが、サブタスクは事前に定義されていない——それらは個別の入力からオーケストレータが決めるのであり、だからこそサブタスクを事前に予測できない複数ファイルにわたるコード変更のような作業に適する。
- **評価者・最適化者（Evaluator-optimizer）**では、一方の呼び出しが応答を生成し、もう一方がそれをループの中で評価する。適合のよい兆候として述べられている2つは、人間がフィードバックを言語化したときに応答が目に見えて改善すること、そしてモデル自身がそうしたフィードバックを提供できることである。

**エージェントは、よく設計されたツールを伴う単純なループである。** 投稿はエージェントを「典型的には、環境からのフィードバックに基づいてループの中でツールを使うだけの LLM」と記述する。人間との命令や議論から始まり、その後は独立して計画し動作しつつ、各ステップで環境からグラウンドトゥルースを得て、チェックポイントや行き詰まりで人間のフィードバックのために一時停止する。実装が素直であるがゆえに、てこはツールセットの設計と文書化にある——[[DefinedTerm/agent-computer-interface]] を参照。

**3つの中核的な原則**が投稿を締めくくる。エージェントの設計において単純さを保つこと。エージェントの計画のステップを明示的に見せることで透明性を優先すること。そして徹底したツールの文書化とテストを通じてエージェント・コンピュータ・インターフェースを丹念に作り込むこと。

## 範囲と留保

投稿は自律性のコストを率直に述べている。エージェントはより高いコストと、誤りが累積する可能性を意味する。したがって適切なガードレールを備えたサンドボックス環境での広範なテストと、統制を保つための最大反復回数のような停止条件を勧める。エージェントは、ステップ数を予測できず固定された経路をハードコードできない、開けた問題に適する——そしてモデルの意思決定への「ある程度の信頼」を必要とする。だからこそ投稿はその自律性を、*信頼できる環境において*タスクを規模化するのに理想的だと枠づける。

エージェントが割に合う領域についての付録は2つの領域——カスタマーサポートとコーディング——を挙げ、それらが共有するものを特定する。会話と行動の双方を要するタスク、明確な成功基準、フィードバックループ、そして意味のある人間の監督である。コーディングについては特に、解が自動テストを通じて検証可能であり、品質が客観的に測定できることを指摘しつつ、「解がより広いシステムの要求と整合していることを確かめるうえで、人間のレビューは依然として決定的である」と付け加えている。

これらのパターンは明示的に規範ではない。それらは「開発者が形を与え組み合わせられる、ありふれたパターン」であり、成功の鍵として述べられているのは測定と反復であり、複雑さは結果を目に見えて改善するときにのみ加えられるべきものである。
