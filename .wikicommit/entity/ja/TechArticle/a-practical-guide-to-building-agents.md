*A practical guide to building agents*（エージェント構築の実践ガイド）は、初めてのエージェントの構築方法を模索しているプロダクトチームとエンジニアリングチームに向けて OpenAI が公開したガイドである。
このガイドは、数多くの顧客への導入事例から得た知見を、実践的で実行可能なベストプラクティスへと凝縮したものだと自らを位置づけている。
有望なユースケースを見極めるための枠組み、エージェントのロジックとオーケストレーションを設計するためのパターン、
そしてエージェントを安全かつ予測可能に動かし続けるためのプラクティスを扱っている。

ガイドが示す範囲は意図的に基礎的なものである。ガイドによれば、読み終えた読者は最初のエージェントを構築し始めるのに必要な知識を身につけているはずだという。
構成は、エージェントとは何か、いつ構築すべきか、エージェント設計の基盤、ガードレール、結論の 5 部からなり、
各設計上のポイントを [[SoftwareApplication/openai-agents-sdk]] を使って書かれた短い Python の例で示している。
ただし、同じ概念は好みのライブラリを使っても、ゼロからでも実装できるとも述べている。

## 詳細

ガイドはエージェントを、ユーザーに代わって独立してタスクを達成するシステムと定義し、その境界線をワークフローの制御に引いている。
LLM を組み込んではいるものの、それをワークフローの実行の制御に使っていないアプリケーション、たとえば単純なチャットボット、
シングルターンの LLM、感情分類器などはエージェントではない。ガイドはエージェントに 2 つの中核的な特徴を与えている。
一つは、LLM を使ってワークフローの実行を管理し、ワークフローがいつ完了したかを判断すること、そして失敗した場合には自らの行動を修正するか、
処理を止めてユーザーに制御を返すことである。もう一つは、外部システムとやり取りするためのツールにアクセスでき、
それらの中から動的に選択すること、しかも常に定められたガードレールの範囲内でそうすることである。

エージェントをいつ構築すべきかについて、ガイドは、従来の自動化では対処しきれなかったワークフローにエージェントが適していると論じ、3 つを挙げている。
微妙な判断や例外を伴う複雑なワークフロー、大規模で入り組んだルールセットのせいで保守が難しくなったシステム、
そして非構造化データに大きく依存するワークフローである。具体的な対比として挙げられているのは支払い詐欺の分析で、
従来のルールエンジンがチェックリストのように機能するのに対し、LLM エージェントは文脈や微妙なパターンを評価する。
ユースケースがこれらの基準を明確に満たさない場合には、決定論的な解決策で十分かもしれないとガイドは述べている。

設計の基盤は 3 つの構成要素からなる。推論を担うモデル、エージェントが呼び出せるツール、そしてエージェントの振る舞いを定める指示である。
ガイドは、ベースラインを確立するためにまずすべてのタスクで最も高性能なモデルを使ってプロトタイプを作り、
そのうえでより小さなモデルに置き換えて、どこならそれで十分かを見極めることを推奨している。ツールはデータ、アクション、
オーケストレーションの 3 種類に分類され、最後のものは他のエージェントにツールとして公開されたエージェントである。
指示については、既存の業務手順書やポリシー文書からルーチンを導き出すこと、情報量の多い資料をより小さなステップに分解すること、
すべてのステップを特定のアクションまたは出力に対応させること、そして条件分岐によってエッジケースを想定しておくことを推奨している。

オーケストレーションは、ツールを備えた 1 つのモデルが終了条件に達するまでループで動くシングルエージェントシステムと、
マルチエージェントシステムとの選択として示されている。ガイドの一般的な推奨は、まずシングルエージェントの能力を最大限に引き出し、
ツールを段階的に追加していくことであり、プロンプトに多くの条件分岐が積み重なったときや、ツール同士の重なりが大きく
選択を混乱させるようになったときに複数のエージェントに移行すべきだとしている。その際、問題なのはツールの数ではなく
ツールの類似性であり、15 を超える別個のツールをうまく扱えている実装もあれば、重なり合う 10 未満のツールで苦戦している実装もあると指摘している。
複数のエージェントが妥当な場合について、ガイドは広く適用できる 2 つのカテゴリとして
[[DefinedTerm/manager-pattern]] と [[DefinedTerm/decentralized-pattern]] を挙げている。

最後の節では、[[DefinedTerm/guardrails]] を単一の制御ではなく多層的な防御として扱い、
LLM ベースの分類器、正規表現やブロックリストのようなルールベースの保護、そしてモデレーション API を組み合わせている。
関連性分類器、安全性分類器、PII フィルター、モデレーション、ツールのセーフガード、ルールベースの保護、出力の検証という 7 つの種類を挙げ、
それらを構築するための 3 段階のヒューリスティックを示している。まずデータのプライバシーとコンテンツの安全性に注力し、
現実のエッジケースや失敗が現れるにつれてガードレールを追加し、エージェントの進化に合わせてセキュリティとユーザー体験の両面から調整する、というものである。
ガイドは最後に、[[DefinedTerm/human-in-the-loop]] による介入を、特に導入初期における重要なセーフガードとして扱っている。
この介入は、失敗のしきい値を超えたときや、リスクの高いアクションが行われるときに発動される。
