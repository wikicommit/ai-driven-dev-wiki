「Code execution with MCP: Building more efficient agents」は2025年11月4日に Anthropic の「Engineering at Anthropic」の名のもとで公開されたエンジニアリング記事であり、Adam Jones と Conor Kelly によるものである。その主張はリード文そのものに述べられている。直接のツール呼び出しは定義ごと・結果ごとにコンテキストを消費するのだから、エージェントは代わりにツールを呼ぶコードを書く方がうまくスケールする、というものだ。これは実践についての論争ではなく設計の手引きである。2つの具体的なコストのパターンを名指し、[[DefinedTerm/model-context-protocol]] サーバのための具体的なファイルツリーの実装を提案し、そこから導かれる性質を列挙し、それを採用する運用上のコストを述べている。

記事はまず MCP が何のためのものか——ツールとエージェントの組み合わせごとのカスタム統合に代わる1つの普遍的なプロトコル——を述べ直し、2024年11月の公開以来コミュニティが数千のサーバを作ったこと、主要なプログラミング言語すべてに SDK が存在すること、そして業界がエージェントをツールとデータへ接続する事実上の標準として MCP を採用したことを報告する。次いで取り上げる問題は、その成功の帰結である。開発者は日常的に、数十のサーバにまたがる数百から数千のツールへアクセスできるエージェントを作っている。

## 主な実践

- **2つのトークンの吸い込み口を別々に診断する。** あらかじめ読み込まれるツールの定義は、リクエストが読まれる前からコンテキストを占める——数千のツールともなれば数十万トークンである。中間結果が第2の吸い込み口である。あらゆる結果がモデルを通過するため、記事の Google Drive から Salesforce への例では会議の全文文字起こしがコンテキストを2度流れることになり、2時間の会議なら追加で 50,000 トークンに相当するとされ、より大きな文書ではウィンドウをまるごと超えることもありうる。また、大きな文書や複雑なデータ構造を扱うとき、モデルはツール呼び出しのあいだでデータをコピーする際に誤りを犯しやすくなるかもしれないとも指摘している。
- **サーバを生成されたファイルツリーとして提示する。** 示された実装はサーバごとに `servers/` ディレクトリを用い、ツールごとに1つの TypeScript ファイルを置く。各ファイルは `callMCPTool` へ転送する型付きの関数をエクスポートする。例のワークフローは、こうして通常のインポートと関数呼び出しのコードになる。
- **エージェントにファイルシステムを探索させてツールを発見させる。** servers ディレクトリを一覧し、必要なツールのファイルだけを読む——例を 150,000 トークンから 2,000 トークンへ、98.7% の削減にしたと報告されている。代替として、詳細度のパラメータ（名前のみ、名前と説明、完全なスキーマ）を持つ `search_tools` ツールも提案されている。
- **実行環境の中で結果をフィルタし変換してから返す。** そうすれば 10,000 行のシートを扱うエージェントは、そのすべてではなく5行だけをログに出す。
- **制御フローをコードとして書く。** ループ、条件分岐、エラーハンドリングは、連鎖したツール呼び出しではなく見慣れたコードになる。これは if 文の評価からモデルの往復を取り除きもするため、最初のトークンまでのレイテンシも縮む。
- **機微なデータをデフォルトでコンテキストの外に保つ。** 中間結果は、ログに出さない限り実行環境にとどまる。機微なワークロードについて記事は、クライアントがモデルの目に触れる前に PII を捕捉してトークン化し（`[EMAIL_1]`、`[PHONE_1]`）、出ていくときに復元することを記述している。これにより実際の値はコンテキストへ入ることなく2つのサービスのあいだを移動する。また、これによってデータがどこへ流れうるかについての決定論的な規則も可能になると指摘している。
- **状態とコードを永続化する。** ファイルシステムへのアクセスにより、エージェントは中間結果をファイルへ書いて再開でき、自ら書いた作業コードを再利用可能な関数として保存できる。そうした関数に `SKILL.md` を加えればそれは構造化されたスキルになる。記事はこれを [[DefinedTerm/agent-skills]] に結びつけ、エージェントが時間とともに自らのスキャフォールディングを進化させることだと記述している。

## 適用範囲と留保

記事は、このパターンが無償ではないことを明示している。エージェントが生成したコードを実行するには、サンドボックス化、リソース制限、監視を備えた安全な実行環境が必要であり、そうしたインフラ要件は、直接のツール呼び出しなら避けられる運用上のオーバーヘッドとセキュリティ上の考慮を加える。トークンコストの削減、レイテンシの低下、ツールの合成性の改善といった便益は、それらの実装コストと比較検討すべきだと述べている。

またこの考えを Anthropic だけのものだとも主張していない。Cloudflare が同様の知見を「Code Mode」として MCP を用いたコード実行に言及しつつ公開したことに触れ、中核の洞察は同じだと述べている。結論としての枠づけは、ここに関わる問題——コンテキストの管理、ツールの合成、状態の永続化——は目新しく感じられるが、ソフトウェアエンジニアリングには既知の解があり、このアプローチはその確立されたパターンをエージェントへ適用するものだ、というものである。全編を通じての例は、稼働中のシステムからの測定ではなく仮想の Google Drive と Salesforce のサーバであり、98.7% という数字はその1つの例示的なワークフローについて示されたものである。
