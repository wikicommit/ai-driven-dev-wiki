"Equipping agents for the real world with Agent Skills" は [[DefinedTerm/agent-skills]] を導入した [[Organization/anthropic]] のエンジニアリング投稿であり、2025年10月16日に公開され、Barry Zhang、Keith Lazuka、Mahesh Murag によって書かれた。2025年12月18日付の更新が付されており、Agent Skills がその後、プラットフォームをまたぐ移植性のためのオープン標準として公開されたことを述べている。

投稿が掲げる動機は、能力とコンテキストの不一致である。モデルが良くなるにつれて、汎用のエージェントは本格的な計算環境と関わることができるようになる——[[SoftwareApplication/claude-code]] がその例であり、ローカルなコード実行とファイルシステムを通じて複雑なタスクを成し遂げる——が、「実際の仕事は手続き的な知識と組織的な文脈を必要とする」のであり、エージェントにドメイン固有の専門性を装備させるには、ユースケースごとにカスタムのエージェントを作るよりも、組み合わせやすく、規模化でき、移植性のある機構が要る。スキルを1つ書くことの喩えとして挙げられるのは、新しく入る人のためのオンボーディングガイドをまとめることである。

そこで定義される機構は意図的に平明である。スキルとは `SKILL.md` ファイルを含むディレクトリであり、その YAML フロントマターは必須の2つのフィールド `name` と `description` を担い、あわせて任意の同梱された指示、スクリプト、リソースを持つ。投稿はその単純さこそが要点だとして締めくくる——「スキルは単純な概念であり、それに見合って単純な形式を持つ」。これこそが、組織、開発者、エンドユーザーがカスタマイズされたエージェントを作るのを容易にしているのだ、と論じる。

## 主要な実践

- **3つのレベルにわたる段階的開示。** 投稿はこれを「Agent Skills を柔軟かつ規模化可能にしている中核の設計原則」と名指し、目次と章と詳細な付録を備えたよく整理されたマニュアルを喩えとする。**第1のレベル**は `name` と `description` のメタデータであり、エージェントは起動時に、インストールされたすべてのスキルについてこれを自身のシステムプロンプトへ事前読み込みする——スキルを読み込まずに、それがいつ当てはまるかを知るには十分である。**第2のレベル**は `SKILL.md` の本体であり、エージェントがそのスキルを関連ありと判断した場合にのみコンテキストへ読み込まれる。**第3のレベル以降**はスキルのディレクトリに同梱され `SKILL.md` から名前で参照される追加のファイルであり、エージェントは必要になったときにだけそこを辿り発見する。述べられている帰結は、ファイルシステムとコード実行のツールを持つエージェントはスキル全体をコンテキストに入れる必要が決してないため、「スキルへ同梱できるコンテキストの量は事実上無際限である」ということである。
- **各レベルが何をもたらすかを示す実例。** 投稿は Claude の文書編集能力の背後にある PDF スキルを辿る。Claude はすでに PDF を理解しているが、フォームへの記入のようにそれを操作することには限りがある。そのスキルの `SKILL.md` はさらに2つのファイル `reference.md` と `forms.md` を参照する。フォーム記入の指示を `forms.md` へ移すことで、スキルの中核は無駄なく保たれる——実際にフォームへ記入するときにだけ Claude がそれを読むだろう、という著者の信頼のうえで。投稿はその結果生じるコンテキストの系列を辿る。システムプロンプトと、すべてのスキルのメタデータと、ユーザーのメッセージ。Claude が Bash を呼び出して `pdf/SKILL.md` を読む。Claude が `forms.md` を読むことを選ぶ。それからタスクへ進む。
- **コードはスキルの第一級の一部である。** スキルは、エージェントが自らの裁量で実行するコードを同梱できる。投稿の論拠は経済的でもあり信頼性についてでもある。「トークン生成によってリストをソートすることは、単にソートのアルゴリズムを走らせるよりはるかに高くつく」のであり、多くのアプリケーションはコードだけが与える決定的な信頼性を必要とする。PDF の例では、あらかじめ書かれた Python スクリプトがすべてのフォームフィールドを抽出し、投稿は Claude がそのスクリプトも PDF もコンテキストに読み込むことなくそれを実行できると注記している。
- **執筆の4つの指針。** *評価から始める*——代表的なタスクでエージェントを走らせ、どこでつまずくかを観察して具体的な能力の欠落を見つけ、そのうえでその欠落に対してスキルを漸進的に作る。*規模に向けて構造化する*——手に負えなくなった `SKILL.md` を参照されるファイルへ分割し、互いに排他的な、あるいはめったに同時に現れない経路は分けたままにしてトークンの使用量を減らし、Claude がスクリプトを実行すべきなのか参照として読むべきなのかを明確にする。コードは双方の役割を果たすからである。*Claude の視点から考える*——Claude が実際にそのスキルをどう使うかを観察し、予想外の軌跡や特定の文脈への過度な依存を探す。とりわけ `name` と `description` に注意を払う。それらがそもそもスキルが起動するかどうかを決めるからである。*Claude とともに反復する*——作業しながら Claude に、うまくいったアプローチとよくある間違いをスキルへ書き留めさせ、道を外れたときには自己省察させる。投稿はこれが、著者が予期したことではなく Claude が実際に必要としていることを表面化させると論じる。

## 範囲と留保

投稿はセキュリティの機構ではなくセキュリティ上の立場を述べている。スキルが指示とコードの双方を供給するため、悪意あるスキルは、それが使われる環境に脆弱性を持ち込んだり、Claude にデータを外部へ持ち出させ意図しない行動を取らせたりしうると警告する。推奨は、信頼できる出所からのみスキルをインストールすること、そして出所の信頼度が低い場合はまずスキルを徹底して監査すること——同梱されたファイルを読み、コードの依存関係と、画像やスクリプトのような同梱されたリソースにとりわけ注意を払い、Claude を信頼できない可能性のある外部のネットワーク上の出所へ接続させる指示やコードに目を光らせること——である。

利用可能性については、投稿は執筆時点で Skills が Claude.ai、Claude Code、Claude Agent SDK、Claude Developer Platform にわたって対応されていたと述べている。近い将来の計画として述べられていたのは、Skills の作成、編集、発見、共有、利用という全ライフサイクルを覆う機能と、外部ツールを伴うより複雑なワークフローをエージェントに教えることで Skills が [[DefinedTerm/model-context-protocol]] のサーバをどう補完しうるかの探究である。さらに先を見据えて、エージェント自身が Skills を作り、編集し、評価できるようにし、自らの振る舞いのパターンを再利用可能な能力へ成文化させたいという希望が述べられている。

これはベンダーによる自社の機構の紹介であり、指針は、スキルが実際にどう振る舞うかについての独立した知見ではなく、Anthropic の設計上の意図である。
