この投稿は [[SoftwareApplication/claude-managed-agents]] の背後にあるアーキテクチャと、それを生んだ推論を説明する。その前提は、ハーネスがモデル単独ではできないことについての仮定を符号化しており、それらの仮定はモデルが良くなるにつれて古びていく、というものである。したがって持続する設計上の問題は、「まだ思いつかれてもいないプログラム」に向けてどう構築するかである。

古びについての具体的な例が示される。以前の仕事において、Claude Sonnet 4.5 はコンテキストの限界が近づいているのを感じ取ると、タスクを早々に切り上げてしまった。投稿がこれを**コンテキスト不安（context anxiety）**と呼ぶ振る舞いであり、その対処はハーネスへコンテキストのリセットを加えることだった。同じハーネスを Claude Opus 4.5 上で走らせると、その振る舞いは消えており、リセットは死重となっていた。

そこから組み立てられる喩えはオペレーティングシステムである。OS はハードウェアを、まだ存在していないプログラムにとっても十分に一般的な抽象——プロセス、ファイル——へ仮想化することで数十年もったのであり、だからこそ `read()` は、それが1970年代のディスクパックに届いているのか現代の SSD に届いているのかに無関心でいられる。Managed Agents は同じしかたでエージェントを仮想化する。**セッション**（起きたことすべての追記専用のログ）、**ハーネス**（Claude を呼び出しそのツール呼び出しを振り分けるループ）、そして**サンドボックス**（コードを実行しファイルを編集するための実行環境）へ——それぞれが互いを乱すことなく差し替え可能である。

## 主要な実践

**ペットを飼うな。** 最初の設計はセッション、ハーネス、サンドボックスを1つのコンテナに置いた。それはファイルの編集を直接のシステムコールにし、サービスの境界を取り除いたが、名前を持ち手ずから世話され、失うことのできないサーバを生んだ。コンテナが落ちればセッションが失われ、応答しなくなればそれを看病して健康に戻さねばならなかった。デバッグは障害そのものより悪かった——内部を覗く唯一の窓が WebSocket のイベントストリームであり、それはハーネスのバグとパケットの欠落とオフラインのコンテナとを区別できず、内部のシェルを得るには、しばしばユーザーのデータも抱えているコンテナへ入ることを意味した。

**コンテナを家畜にせよ。** ハーネスがコンテナの外にあれば、それは他のあらゆるツールを呼ぶのと同じしかたでサンドボックスを呼ぶ。`execute(name, input) → string` である。死んだコンテナはツール呼び出しのエラーとして現れて Claude へ返され、Claude が再試行すれば `provision({resources})` を通じて新しいものが初期化される。

**ハーネスも家畜にせよ。** セッションのログがハーネスの外にあるため、ハーネスの中にクラッシュを生き延びる必要のあるものは何もない。代替は `wake(sessionId)` で起動され、`getSession(id)` を通じてイベントログを取得し、最後のイベントから再開する。ループの途中では、ハーネスは `emitEvent(id, event)` によって記録を耐久的に保つ。

**認証情報をサンドボックスの手の届かないところへ。** 結合された設計では、Claude が生成した信頼できないコードが認証情報と同じコンテナで走っていたため、[[DefinedTerm/indirect-prompt-injection]] は Claude に自身の環境を読ませるよう説得するだけでよかった——その後、攻撃者は制限のない新しいセッションを立ち上げ、そこへ作業を委譲できた。投稿は、狭いスコープ設定を第一の答えとすることを退ける。それは限られたトークンで Claude に何ができないかについての仮定を符号化するものであり、その一方で Claude は賢くなり続けるからである。構造的な対処は、トークンがサンドボックスから決して到達できないようにすることである。Git については、リポジトリのアクセストークンがサンドボックスの初期化時にリポジトリをクローンし、ローカルのリモートへ組み込まれるため、エージェントがそれを一度も扱うことなく `push` と `pull` が機能する。カスタムツールについては、OAuth トークンは安全な保管庫に置かれ、Claude は、セッションに紐づくトークンを実際の認証情報と交換する専用のプロキシを通じて MCP のツールを呼ぶ。ハーネスがいかなる認証情報も知らされることはない。

**セッションをコンテキストウィンドウではなくコンテキストオブジェクトとして扱え。** コンパクションも切り詰めも、何を残すかについて不可逆な判断を下すが、どのトークンを後のターンが必要とするかを知るのは難しい。ここではセッションのログは、エージェントが問い質せる耐久的なストレージである。`getEvents()` はイベントストリームの位置指定のスライスを選び取るため、ハーネスは読むのをやめたところから再開したり、ある時点の数イベント前まで巻き戻して経緯を見たり、特定の行動の前にコンテキストを読み直したりできる。取得されたイベントはその後ハーネスの中で変換できる——プロンプトキャッシュのヒット率のためでも、将来のモデルが必要とする任意のコンテキストエンジニアリングのためでもよい。これらの関心事を分ける理由として述べられているのは、将来のモデルが要求する具体的なコンテキストエンジニアリングは予測できない、ということである。だからセッションが保証するのは耐久性と問い質せることだけである。

## 範囲と留保

報告された性能上の結果は、脳が起点となるツール呼び出しを通じてコンテナを遅延プロビジョニングすることに由来する。だからコンテナをすぐには必要としないセッションはそれを待たずに済み、保留中のイベントが取り出され次第、推論を始められる。そのアーキテクチャのもとで最初のトークンまでの時間は p50 でおよそ 60%、p95 で 90% 超低下した。これらは Anthropic の自社サービスについての自社の数値である。

「多数の手」という方向は、長く計画されていたものではなく、新たに実現可能になったものとして提示されている。単一のコンテナがそもそも選ばれたのは、以前のモデルが多数の実行環境について推論し、どこへ作業を送るかを決める能力を持たなかったからである。知能が規模を増すにつれて、単一のコンテナのほうが制約となった。その障害が、脳が手を伸ばしていたすべての手の状態を失わせるからである。手は `execute(name, input) → string` にすぎないため、ハーネスはサンドボックスがコンテナなのか、電話なのか、ポケモンのエミュレータなのかを知らないし、手は脳から脳へ渡せる。

投稿はこの成果を [[DefinedTerm/meta-harness]] として位置づける——Claude がどの具体的なハーネスを必要とするかについては意図的に意見を持たず、その周囲のインターフェースについては意見を持つのである。
