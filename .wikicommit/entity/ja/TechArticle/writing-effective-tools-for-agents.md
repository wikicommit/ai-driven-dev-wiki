"Writing effective tools for agents — with agents" は Ken Aizawa による2025年9月11日の Engineering at Anthropic の投稿である。その論証は、ツールが新しい種類のソフトウェア——「決定的なシステムと非決定的なエージェントのあいだの契約」——であり、それゆえツールを書くことは、別の開発者に向けて関数や API を書くのと同じしかたでは扱えない、というものである。実践的な提案は、エージェント自身がこれから使うツールを、そのエージェントを用いて改善する、評価駆動のループである。

## 要点

投稿の枠づけとなる区別は、`getWeather("NYC")` が常に同一に振る舞う従来のソフトウェアと、「今日は傘を持っていくべき？」と問われたときに天気のツールを呼ぶかもしれないし、一般的な知識から答えるかもしれないし、明確化のために問い返すかもしれないし、そもそもツールを掴み損ねるかもしれないエージェントとのあいだにある。掲げられた目標はエージェントが有効でありうる面積を広げることであり、経験上、エージェントにとって最も「人間工学的」なツールは、人間にとっても驚くほど直観的である、と観察されている。

記述されるワークフローは3つの段階からなる。**試作（Prototype）**——ツールを作り、手で試す。ローカルの MCP サーバや Desktop の拡張でくるんで Claude Code や Claude Desktop アプリで動かせるようにし、Claude にツールを書かせるときは関連するライブラリ、API、SDK のドキュメントを与える。**評価（Evaluate）**——実世界の利用に根ざした多数のタスクを、それぞれ検証可能な帰結と対にして生成する。投稿は具体的である。弱いタスクは単一ステップの検索（「支払いログを `purchase_complete` と `customer_id=9182` で検索せよ」）であり、強いタスクは数十回のツール呼び出しを要しうる（「顧客 ID 9182 が、1回の購入試行に対して3回課金されたと報告した。関連するログのエントリをすべて見つけ、同じ問題の影響を受けた他の顧客がいるかを判定せよ」）。**協働（Collaborate）**——評価に用いたエージェントの記録を連結して Claude Code へ貼り付け、結果を分析しツールをリファクタリングする。

分析について、ツール設計を超えて一般化する指摘がなされている。エージェントがフィードバックから*省いた*ものは、しばしば含めたものより重要である。LLM は「常に意図したとおりを言うわけではない」からであり、生の記録は、エージェントが述べた理由づけと並べて読まねばならない。この方法で見つかった欠陥の実例は、Claude がローンチ時に Web 検索ツールの `query` パラメータへ不必要に `2025` を付け足しており、それが結果に偏りを与えていたというものである。これはツールの説明を改善することで是正された。

抽出された5つの原則は次のとおりである。

- **適切なツールを選ぶ。** ツールが多いほど良い結果になるとは限らず、投稿が観察したと報告するありふれた誤りは、エージェントに適しているかどうかにかかわらず既存のソフトウェアの機能や API のエンドポイントを単にくるんだだけのツールである。コンピュータのメモリが安価であるのに対しエージェントのコンテキストは限られているため、すべての連絡先を返すツールは総当たりの読み込みを強いる。投稿は `list_contacts` よりも `search_contacts` や `message_contact` を勧め、連鎖する操作を1回の呼び出しへ集約することを勧める——`list_users`/`list_events`/`create_event` の代わりに `schedule_event`、`read_logs` の代わりに `search_logs`、3つの別々の顧客の検索の代わりに `get_customer_context` である。
- **名前空間を切る。** 関連するツールを、サービス別（`asana_search`、`jira_search`）およびリソース別（`asana_projects_search`、`asana_users_search`）に共通の接頭辞のもとへまとめることは、潜在的に数百に及ぶツールのなかから、エージェントが適切なときに適切なツールを選ぶ助けになりうる。投稿は、接頭辞ベースと接尾辞ベースの名前空間の切り方が、自社のツール利用の評価に対して無視できない、そしてモデルに依存する影響を持つと報告している。
- **意味のあるコンテキストを返す。** ツールは信号の強い情報を返すべきであり、`uuid`、`256px_image_url`、`mime_type` のような低水準の識別子を避けて、`name`、`image_url`、`file_type` を選ぶべきである。投稿は、任意の英数字の UUID を意味的に有意味な言語へ、あるいは 0 始まりの ID 体系へ解決することが、幻覚を減らすことで検索タスクにおける Claude の精度を有意に改善すると報告している。双方の形式が必要な場合には、エージェントが `"concise"` か `"detailed"` の応答を要求できる `response_format` の列挙を提案し、自社の Slack の例で簡潔な形式がおよそ3分の1のトークンで済んだと報告している。
- **トークン効率に向けて最適化する。** 大量のコンテキストを消費しうる応答には、ページング、範囲の選択、フィルタリング、そして妥当な既定値を伴う切り詰めが勧められる。投稿は、Claude Code が既定でツールの応答を 25,000 トークンに制限していると述べている。切り詰めとエラーメッセージそれ自体もプロンプトとして扱われる。エラーは不透明なコードやトレースバックではなく、具体的で行動につながる改善を伝えるべきである。
- **説明をプロンプトエンジニアリングする。** 投稿はこれを、手に入るなかで最も効果的な手法の1つと呼び、新しく入る人に説明するようにツールを記述すること——特殊なクエリの形式やニッチな用語といった暗黙の文脈を明示すること——と、パラメータに曖昧さなく名前を付けること（`user` ではなく `user_id`）を助言する。挙げられている証拠は自社のものである。Claude Sonnet 3.5 が、ツールの説明への精密な改良の後に [[Dataset/swe-bench]] Verified で最先端の性能を達成した、というものである。

## 背景

投稿はその助言を、理論化されたものではなく導き出されたものとして提示する。その大半が Anthropic の社内のツール実装を Claude Code で繰り返し最適化するなかから生まれたこと、評価が自社の社内ワークスペースの上に構築されたこと、そして取り置いたテストセットが、自社の研究者あるいは Claude が書いた「エキスパート」の実装をさらに上回る利得を示したことを述べている。結びの立場は、エージェント向けのツールを構築することがソフトウェア開発の実践を決定的なパターンから非決定的なパターンへ向け直すことを要求するというものであり、効果的なツールは「意図的かつ明確に定義され、エージェントのコンテキストを賢明に使い、多様なワークフローのなかで組み合わせられ、エージェントが実世界のタスクを直観的に解けるようにする」ものだとされる。

自社のツールとモデルの性能についての主張は Anthropic 自身のものであり、自社製品について公表されたものであって、独立した検証はない。全体を通じた論証がエージェントの限られたコンテキストをうまく使うことについてのものであるため、これは同社の [[DefinedTerm/context-engineering]] についての他の文章とは別物ではなく、その隣に位置する。そして [[DefinedTerm/model-context-protocol]] を、その規模——潜在的に数百のツール——がここで扱われる問題を作り出す配送の機構として扱っている。
