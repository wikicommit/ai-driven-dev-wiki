"Spec Kit Agents: Context-Grounded Agentic Workflows" は Pardis Taghavi と Santosh Bhavani による論文であり、[[DefinedTerm/spec-driven-development]] における信頼性の問題は構造の欠如ではなく証拠の欠如であると提案する。その論証は、[[SoftwareApplication/spec-kit]] のような段階的なワークフローはそれ自体では [[DefinedTerm/context-blindness]]——内部的には整合しているが、実際に存在するリポジトリとは両立しない中間成果物——を防がないのであり、したがって接地（grounding）は生成するエージェントの振る舞いに委ねるのではなく、明示的なワークフローの操作にすべきだ、というものである。

## 主要な知見

記述されるシステムは、既存の Specify → Plan → Tasks → Implement の各段階のまわりに**コンテキスト接地の層**を加える。この層は意図的に開発者エージェントの主プロンプトの外側に置かれる。各フェーズの前に、**発見フック（discovery hooks）**が読み取り専用のプローバを走らせ、グロブ、grep、git の履歴といった検査ツールを用いてリポジトリの証拠を集め、プロジェクト固有の規約、既存の API、関連するモジュールを表面化させる。各フェーズの後に、**検証フック（validation hooks）**が生成された成果物を検査する。前段の成果物についてはこれは構造的・参照的な制約を意味する——PLAN.md に挙げられたファイルパスが存在するか、必要なライブラリが存在するか、タスクリストが実行可能で正しく順序づけられているか——そして実装の後にはユニットテストやリンタといったリポジトリのチェックを実行することを意味する。著者らは設計の意図を、幻覚されたパス、欠けている依存関係、実行不能な計画が、コード生成によって増幅される前に捕捉されるよう、エラーの検出を前倒しすることだと述べている。

論文は、これが先行研究と*いつ*・*何を*検証するかにおいて異なることを明示している。検証を実装の後に集中させるのではなく、コード生成の前に中間成果物を検証し、実装後の実行可能なチェックは最終のゲートとして保持する。ツールに基づく検証を、単一の終段のフィルタではなく、フェーズごとに繰り返されるフックとして扱うのである。またこの配置を最小権限のものとして枠づける——プロダクトマネージャエージェントはリポジトリの分析とバージョン管理の検査に制限され、発見フックは読み取り専用であり、検証フックだけがプロジェクトのチェックのための実行権限でそれらの権限を拡張する。

**測定された効果は小さいが一貫している。** 5つのリポジトリ（FastAPI、Airflow、Dexter、Plausible Analytics、Strapi）の32の機能タスクを覆う128回の実行にわたり、完全にコンテキスト接地された構成は、1〜5 の複合 LLM-as-judge スコアを 3.51 から 3.66 へ改善した——0.15 の利得であり、著者らは完了したタスクの対応づけられた部分集合において統計的に有意（Wilcoxon の符号順位検定、p < 0.05）と報告している——一方でリポジトリレベルのテスト互換性は 99.7〜100% を保った。著者らはこれをどう読むべきかについて慎重である。「主たる便益は平均スコアの劇的な跳ね上がりではなく、多段階のエージェンティックなワークフローにおいて累積するコンテキストのエラーを、より早く検出し防ぐことにある。」

2種類のフックを分離するアブレーションでは、いずれも Full のベースライン 3.51 を上回り、検証のみ（3.57）が発見のみ（3.53）を上回り、両者を組み合わせた設計が 3.66 で最も強かった。著者らはこれを2つの構成要素が相補的であることの証拠と読む。6つの対応づけられたタスクに対する盲検の人間の選好調査では60票が投じられ、Full に19、引き分け33、Full-Augmented に8という内訳であった。

**コストは実行時間である。** 待ち時間は予算のファミリー内でのみ比較されている——Baseline と Augmented は40分の予算で、Full と Full-Augmented は90分で実行された——追加のフェーズによってファミリーをまたぐ比較が無意味になるためである。40分のファミリー内ではフックは平均 1.1 分を加えた（15組で 14.4 から 15.5 へ）。90分のファミリー内では 13.2 分を加えた（16組で 24.0 から 37.2 へ）。著者らはこれを品質と実行時間のトレードオフとして提示し、このアプローチが「よりリスクの高い、あるいは複雑度の高いタスクに最も適している」と結論づけている。

論文が実世界のソフトウェアエンジニアリングの Issue 300 件からなる標準的なベンチマークと記述する SWE-bench Lite では、システムはベースライン構成で 56.5% の Pass@1 に達し、コンテキスト接地フックを有効にすると 58.2% に達した。論文は、実験のすべてがベースモデルとして MiniMax-M2.5 を用いていると注記しつつ、オーケストレーションの枠組みそれ自体はモデル非依存であると論じている。

## 背景

評価の設計は生成と採点を分離している。エージェンティックなワークフローは、MiniMax-M2.5 を背後に持つ Anthropic 互換のエンドポイントへルーティングされた Claude Code CLI を通じて実行され、一方で品質は Claude Opus 4.6 によって、完全性・正しさ・スタイル・保守性にわたる 1〜5 の尺度で独立に判定され、複合スコアはそれらの平均である。著者らは、この分離が採点をエージェントのプロンプトとツールアクセスから隔離することで自己評価のバイアスを減らすことを意図していると述べ、同じルーブリックを用いた出力の部分集合に対する小規模な盲検の人間レビューでそれを補完したと報告している。実行が成功と数えられるのは、少なくとも1つのファイル変更を含むプルリクエストを生成し、致命的な実行エラーなく完了した場合のみであり、人間による計画レビューのチェックポイントは実験のために自動承認された。

結果は控えめなものであり、見出しの数値としてではなく設計の原則として提示されている。その一般性は、テストされたもの——5つのリポジトリ、32のタスク、1つのベースモデル、そして著者ら自身が単独で依拠せず人間のレビューで補完している LLM-as-judge の指標——によって画されている。
