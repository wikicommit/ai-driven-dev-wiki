ハルビン工業大学の研究者らが主導するこのサーベイは、単一の正しい呼び出しがもはや興味深い問いではなくなった地点から[[DefinedTerm/agentic-tool-use|エージェント型ツール利用]]を概観する。[[DefinedTerm/react-prompting|ReAct]] を含む初期のツール学習研究は、モデルに意図を認識させ API リクエストを整形させることを教えた。著者らは、実用的なエージェントは今や、長い軌跡にわたって多数のツールを協調させ、中間状態を保持し、失敗から回復し、レイテンシ・コスト・安全性の制約のもとで動作しなければならず、そのため中核的な難しさはアクセスではなくオーケストレーションになったと論じる。著者らはこれを意思決定空間の質的な変化として捉えている。すなわち、ツールを 1 つ選ぶことから、ツールのサブセット選択、ツール間の依存関係、逐次的および並列的なスケジューリング、失敗からの回復、再プランニングにまたがる、相互に結びついた一連の意思決定への変化である。

このサーベイの動機は、著者らが文献に見いだす 2 つのギャップにある。1 つは概念的なもので、ツール利用、ツール呼び出し、ツールリトリーバル、ワークフロー実行、オーケストレーションといった用語は、異なる能力レベルを指すにもかかわらず曖昧に使われている。もう 1 つは構造的なもので、プランニング、学習、安全性、効率、ベンチマーク、オープン環境への適応は通常別々に研究されているが、実際にデプロイされたエージェントシステムはそれらの相互作用に依存している。そこで本サーベイはまず、マルチツールオーケストレーションの統一的な定式化を与える。これは、対話履歴とメモリからツール呼び出しまたは終了を選択する方策であり、タスクの成功と、呼び出し回数・レイテンシ・料金・リスクとをトレードオフするコストを考慮した目的関数のもとで定義される。そのうえで、6 つの相互に関連する次元に沿って分野を整理している。

## 要点

- 6 つの次元とは、推論時のプランニングと実行、学習と軌跡の構築、安全性と制御、リソース制約下での効率、オープン環境における能力の完全性、ベンチマークの設計と評価である。
- 推論について著者らは、線形で ReAct 型の逐次的なトレースから、グラフや階層的分解に基づくトポロジーを意識したプランニングへの移行、そして「一度生成して実行する」から「探索し、検証し、それから確定する」への移行を説明している。長期的なオーケストレーションはさらに、コンポーネント間の分業、大規模なツールエコシステムにまたがるルーティング、実行履歴を圧縮または外部化するメモリに依存する。
- チューニング手法は、計算量とデータへの依存度の昇順に並べられている。すなわち、学習不要の手法（ツールリトリーバル、プロンプティング、ノンパラメトリックメモリ）、マルチツール軌跡の合成、教師ありファインチューニング、強化学習である。著者らは、合成データにとって決定的な尺度は、今や量ではなく、ロングテールかつ多段階のエラーパターンをどれだけカバーしているかであると論じている。
- 著者らはマルチツールの安全性リスクを 2 つの次元に分けている。1 つは並列実行で、同時の書き込み操作が競合状態や不整合な状態を招くおそれがある。もう 1 つは長期にわたるツールチェーンで、悪意あるコンテンツや上流の小さなエラーがステップをまたいで伝播・増幅する。防御策は、実行前の制約からトランザクション型の分離とロールバックを経て、実行後の検証へと移行していると説明されている。
- 効率に関する研究は、レイテンシの削減（並列実行、プランニングと行動の非同期な分離、投機的実行）とコストの削減（すべてのツール説明をプロンプトに入れる代わりの動的なツールリトリーバル、適応的なモデルルーティング、キャッシュとメモリ）に分類されている。
- 能力の完全性は、能力の境界を知覚すること（ツールをハルシネーションする代わりに確認を求めるか終了する）、自律的な[[DefinedTerm/tool-creation|ツール作成]]、そして再利用可能な経験とスキルメモリによるオープン環境への適応、というループとして説明されている。
- ベンチマークは、単一時点での呼び出しの正しさから、長期的な能力の 4 つの次元、すなわちツール依存関係のトポロジー的な複雑さ、時間的なスケール、動的な環境、自己修正を伴う状態の永続性へと変遷してきたとたどられている。著者らは、長期的な評価は最終的な成功だけに頼るべきではないと論じている。
- 応用について著者らは、ドメイン間の違いは主にオーケストレーションのトポロジーではなく運用上のボトルネックに由来すると論じている。ソフトウェアエンジニアリングでは、決定論的なテストに基づく成功とテスト検証のコストが、エンタープライズワークフローでは、トランザクションの一貫性、監査、権限の境界がそれにあたる。

## 補足

このサーベイは、ツール利用一般やエージェントシステム全般ではなくマルチツールオーケストレーションを分析単位とし、しばしば混同されると著者らが考える概念、すなわちツール呼び出し、ツールリトリーバル、オーケストレーション、ツールセットの拡張の間に境界線を引くことで、ツール学習や LLM エージェントに関する先行サーベイとの違いを打ち出している。結びの研究課題では、状態を持つオーケストレーションのためのより良い抽象化、動的かつ長期的な設定のためのより強力な評価プロトコル、そしてモデルレベルの推論とシステムレベルの保証とのより緊密な統合を求めている。応用については、インターフェースの変化に対する適応的な回帰テスト、プロセスレベルの検証可能性と再生可能な監査、コスト・レイテンシ・品質の同時最適化、そして組み合わせ可能で敵対的にも頑健な失敗からの回復を挙げている。
