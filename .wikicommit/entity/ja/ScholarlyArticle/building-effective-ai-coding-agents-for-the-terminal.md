本技術レポートは、オープンソースのコマンドライン・コーディングエージェント [[SoftwareApplication/opendev]] と、その背後にあるアーキテクチャ上の決定を記録している。その枠づけは、AI によるコーディング支援の情勢が複雑な IDE プラグインから、開発者がソース管理を行い、ビルドを実行し、環境をデプロイするまさにその場所で直接動作する、多用途でターミナルネイティブなエージェントへと移りつつあるというものである。

著者は、本論文の目的が新規のアルゴリズム的ブレークスルーを提示することではなく、本番投入可能なエージェント的コーディングシステムを作るなかで得られた設計上の決定、トレードオフ、教訓を共有すること——クローズドソースの産業実践とオープンな学術的言説のあいだにあると彼が述べるギャップを橋渡しすること——だと明言している。彼はこれを、知る限りオープンソースでターミナルネイティブな対話型コーディングエージェントについての最初の包括的な技術レポートだと位置づけ、既存のシステムは2つのカテゴリのいずれかに入ると論じる。論文を公開しているがインタラクティブな日常利用ではなく自動評価に向けて設計されたベンチマーク志向の枠組みと、設計上の決定を記録した公開の技術レポートを欠く CLI ネイティブなエージェントである。

3つのエンジニアリング上の課題がこの仕事を組織立てている。モデルのトークン予算を日常的に超えるセッションにわたって有限のコンテキストウィンドウを管理すること。エージェントが任意のシェルコマンドを実行できるときに破壊的な操作を防ぐこと。そしてエージェントのプロンプト予算を圧迫せずに能力を拡張することである。

## 主な貢献

**別個のフェーズとしてのスキャフォールディングとハーネス。** レポートはアーキテクチャ上の応答を2つのフェーズを軸に枠づけている。最初のプロンプトより前にエージェントを組み立てる [[DefinedTerm/agent-scaffolding]]——システムプロンプト、ツールスキーマ、サブエージェントのレジストリ——と、実行時にツールのディスパッチ、コンテキスト管理、安全性の強制をオーケストレーションする [[DefinedTerm/agent-harness]] である。

**複合 AI システムにおけるワークフローごとの LLM 束縛。** 単一のモノリシックなモデルではなく、各認知ワークフローがユーザー設定を通じて独立にモデルを選ぶ構造化されたアンサンブルとして記述されている。5つのモデルの役割——action、thinking、critique、vision、compaction——が定義され、それぞれにフォールバックの連鎖がある。レポートは、これによってシステムが構成上モデル非依存になり、プロバイダの切り替えやコストの最適化が設定変更だけで済むと論じている。

**拡張された ReAct 実行ループ。** 標準的な Reason-Act のサイクルは、ツールへのアクセスなしで走る明示的な thinking フェーズと、任意の自己批評フェーズによって拡張されている。レポートが述べる根拠は、ツールが利用可能なときモデルは深く考えるよりも素早く行動する傾向があるということ、そしてモデルの振る舞いを変えるのはツールを使うなという指示ではなく、API 呼び出しからツールスキーマが存在しないことそのものだ、というものである。ループにはドゥームループの検知も含まれる。各ツール呼び出しをツール名と引数のハッシュとして指紋化し、同じ指紋が再発したときに、注入された警告から承認ベースの一時停止へと段階を上げる。

**第一級の関心事としてのコンテキストエンジニアリング。** レポートは [[DefinedTerm/adaptive-context-compaction]]、注意の減衰に対抗するための [[DefinedTerm/system-reminders]]、エピソード的な要約と直近メッセージの逐語を分離する二重メモリのアーキテクチャ、大きな出力をスクラッチファイルへ退避させるツール種別ごとの実行結果の要約、そしてプロジェクト固有の知識をスコア付きの箇条書きのプレイブックとして蓄積する経験駆動のメモリパイプラインを提示している。

**トークン効率のよい拡張性と多層防御の安全性。** 外部ツールは、すべてのスキーマをあらかじめ読み込むのではなく、Model Context Protocol サーバに対するキーワード検索を通じて遅延的に発見される。レポートは、これにより起動時のコンテキストコストが 40% から 5% 未満へ下がったと述べている。安全性は独立した5つの層で強制される。プロンプトレベルのガードレール、二重エージェントの分離によるスキーマレベルのツールゲーティング、永続的な権限を持つ実行時の承認システム、ツールレベルの検証、そしてユーザー定義のライフサイクルフックである。

## 注記

レポートの考察の節は、横断的な5つの設計上の緊張を、このシステムを超えて持ち運べると著者が提示する教訓へと抽出している。コンテキストをバッファではなく予算として扱い、段階的な削減のステージを設計すること。行動を促すリマインダーを冒頭ではなく判断の時点で注入し、システムロールではなくユーザーロールを用い、リマインダーの種類ごとに頻度に上限を設けること。安全でないツールはブロックするのではなく見えなくすること。モデルは存在を知らない能力について推論できないからである。ツールは厳密な正しさを要求するのではなく LLM の不正確さを吸収するよう設計すること。そしてセッションの長さとともに増大するあらゆるリソースに上限を設けること。さらに測定に関する教訓もある。レポートは、プロバイダが報告するトークン数を真値として扱わなければならないと論じる。プロバイダは目に見えないコンテンツを注入するため、ローカルでのトークン計数は実際の使用量を系統的に過小評価するからである。

著者はレポートの主たる限界を明示している。アーキテクチャ上の決定と設計の根拠は記録しているが、体系的な定量評価を欠いており、[[Dataset/swe-bench]] やターミナル対話型のベンチマークに対するベンチマーキングを、確立されたベースラインに照らしてこのアーキテクチャを検証する今後の課題として挙げている。
