「Context Engineering for AI Agents in Open-Source Software」は、Seyedmoein Mohsenimofidi、Matthias Galster、Christoph Treude、Sebastian Baltes による予備的な実証研究であり、第23回国際ソフトウェアリポジトリマイニング会議（MSR '26）向けに公表された。その主題は新種のソフトウェア成果物としての [[DefinedTerm/context-files]] であり、それを研究する論拠は方法論的である。プロンプトは内容が生成された後に保存されることがめったにないため、バージョン管理されたコンテキストファイルは、現実世界の [[DefinedTerm/context-engineering]] を直接観察する稀な機会を与えてくれる、というのである。著者たちはこれを、オープンソースプロジェクトでさまざまな AI エージェントを導くために用いられるコンテキストファイルを分析した、初の全体的な実証研究と説明している。

## 主な知見

**導入は初期段階にある。** フォークではなく、ライセンスを持ち、活発に保守されている GitHub リポジトリ 228,890 件という出発集団を 48,795 件へ絞り、さらに人気と成熟度のバランスを取って 1 万件の標本へ順位づけて落としたところ、この研究が走査した4つのコンテキストファイル形式（Copilot instructions、CLAUDE.md、AGENTS.md、GEMINI.md）のうち少なくとも1つを採用していたのは 466 件——5%——にすぎなかった。著者たちはこれを導入の初期段階と読み、4つのツールに焦点を絞ったことを限界として注記している。その 466 件のうち、言語の分布はおおむね標本全体の構成をなぞっており、Go がやや過剰に表れていた。TypeScript が 135 リポジトリで首位、続いて Go と Python がそれぞれ 58、C# が 56、Java 36、JavaScript 34、C++ 32、Rust 29、PHP 19、C 9 である。特定の形式は言語ごとに集まっており——C# のリポジトリは強く Copilot に集中し、Claude Code は TypeScript で非常に人気があった——最も多く共起した組み合わせは AGENTS.md と CLAUDE.md で、25 リポジトリにおいてであった。

**ファイルの長さのばらつきが最も大きいのは AGENTS.md である。** Copilot の instruction ファイルが平均で最も長く（M = 310 行、SD = 127）、続いて CLAUDE.md（M = 287、SD = 112）、GEMINI.md が最も短かった（M = 106、SD = 65）。AGENTS.md は平均 142 行だが標準偏差は 231 であり——4つのなかで最も変動が大きい——著者たちはこれが、開発者がどれだけの情報を与えることを選ぶかを反映しているのかもしれないと示唆している。

**確立された内容構造は存在しない。** 標本中の 155 件の AGENTS.md ファイルから節の見出しを分析し、著者たちは意味的に類似した見出しをカテゴリへまとめるコーディングガイドを構築した。最も頻繁だったのは規約（レベル1およびレベル2の見出しで 50）、貢献ガイドライン（48）、アーキテクチャないし構造（47）、ビルドコマンド（40）、次いで目標と目的およびテスト実行（それぞれ 32）、メタデータ（29）、テスト戦略（24）であった。トラブルシューティング（8）、パターンと例（8）、セキュリティ（6）は比較的まれであった。

**書き方は5つに分かれる。** 規約とラベル付けされた 50 の節すべてを検討し、この研究は書き方を5つの文体的次元に沿って特徴づけ、それぞれをコーパスから例示している。*記述的*——指示を与えずに既存の実践を文書化する（「本プロジェクトは Linux カーネルのスタイルガイドラインを用いる」）。*規範的*——直接の命令形（「既存のコードスタイルと規約に従うこと」）。*禁止的*——してはならないことを述べる（「main ブランチへ直接コミットしてはならない」）。*説明的*——規則の後に理由を加える（「CI 環境でのタイミングの問題を防ぐため、ハードコードされた待機を避けること」）。そして*条件的*——状況に応じた論理を符号化する（「リフレクションを使う必要がある場合は ReflectionUtils の API を使うこと」）。著者たちはこの幅を、プロジェクトがエージェントに期待をどう伝えるのが最善かをまだ試行錯誤していることの証拠と読んでいる。

**大半のファイルは一度も改訂されない。** 155 件の AGENTS.md ファイルのうち、77 件（50%）はまったく変更されておらず、36 件（23%）は一度変更され、32 件（21%）は2回から7回変更されていた。著者たちは、コミットが10件以上ある 10 ファイル（6%）から 169 件のコミットに注釈を付け、変更カテゴリの主流が指示の追加（78 件）と指示の修正（59 件）であり、節の追加（26）、指示の削除（23）、見出しの修正（23）を大きく引き離していることを見出した。節の削除と参照の更新はそれぞれ2件であった。大半のコミット（111 件、66%）は単一の変更カテゴリを表していた。検討したすべてのファイルにおいて、指示の追加ないし修正がその履歴における第1ないし第2の変更であり、著者たちはこれを、変更が主として指示を微調整し整えるために行われていることの証拠と捉えている。変更のテンポは大きくばらついており——あるプロジェクトは19日間に49回の変更を行い、別のプロジェクトは148日間に11回であった——著者たちは、変更がいつどれだけの頻度で起きるかに明確なパターンは特定できなかったと述べている。

## 背景

同論文の枠づけとなる区別は、プロンプトエンジニアリングがタスクをモデルに*どう*記述するかにかかわるのに対し、コンテキストエンジニアリングはモデルが*どのような*タスク関連情報にアクセスできるかにかかわる——ガイドライン、設定ファイル、文書、模範的なコード片——というものであり、後者を「タスクに関連する情報を設計し、構造化し、LLM へ提供する意図的なプロセス」と定義している。同論文は、エージェントベースのツールが対話型のものに対して優位を持つのはまさにこの点であり、永続的で構造化されたタスク固有のコンテキストを、より細かい粒度で与えられるからだと論じている。

その結論は、開発者が何をしているかの変化として述べられている。人間向けの README に加えて、「ソフトウェア開発者はいまや機械のための文書を書き、保守している」のであり、これらのファイルは他のあらゆる成果物と同じくバージョン管理され、レビューされ、品質保証され、テストされる。著者たちはオープンソースのリポジトリを、開発者がエージェントベースのツールへの語りかけをどう試行錯誤しているかを研究するための「自然の実験室」として位置づけ、今後の作業に向けた未解決の問い——標準スキーマが相互運用性を改善しうるか、リポジトリはコンテキストファイルを1つ保つべきか複数保つべきか、複数のエージェントに向けた指示をどう調整するか——を示している。

この研究は明示的に予備的かつ探索的であり、著者たちは研究設問により全体的に答えるべくこれを拡張すると述べている。彼らはまた、行わなかったことも明記している。変更の背後にある意図をラベル付けしていないこと、カテゴリごとの変更数を定量化していないこと、そしてコミットが10件未満のファイルを詳細に分析していないことである。
