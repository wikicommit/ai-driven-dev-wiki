Intuit AI Research によるこのプレプリントは、[[DefinedTerm/agentic-tool-use]] のインターフェース側を
対象としている。出発点となる主張は、ツールを使うエージェントを改善する取り組みの多くはエージェントの側
── より大きなモデル、より良いプロンプティングやファインチューニング ── を変えるものである一方、
エージェントが読むツール記述は通常、人間の開発者向けに書かれているというものである。そうした記述は
曖昧さを許容し、制約を暗黙のままにし、エージェントには獲得できない背景知識を前提としており、これらの
欠陥は候補となるツールの数が増えるにつれて積み重なっていく。ツール記述を改善する既存の手法は、新しい
API ごとにクエリ合成・軌跡収集・アノテーションというツール単位のパイプラインを再実行するか、各ツールを
独立に書き換えるかのいずれかであり、未知のツールに転移するパターンを学習することができない。

著者らの仮説は、効果的なツール記述は有限で再利用可能なインターフェースパターンの集合に従っており、
したがって記述の書き換えは転移可能な能力として学習できる、というものである。彼らの手法 Trace-Free+ は、
小規模なオープンウェイトモデル（Qwen3-4B-Instruct）をファインチューニングし、ツールの元のインターフェース
から改善された記述を生成させる。学習はカリキュラムに従う。最初は実行トレースの要約を含む例の割合を高く
し、次第にトレースのない例へと移行させることで、新しいツールがスキーマだけを伴って届くというデプロイ時の
条件に合わせる。学習ターゲットは、ToolBench から取った実世界の RESTful API に対する 3 段階のパイプライン
から得られる。すなわち、エージェント型のプローバーで動作するツールにアノテーションを付け、呼び出し間の
依存関係を持つ複数ステップのクエリを合成し、まず一般的なドキュメントのガイドラインで、次に失敗した軌跡
から抽出したルールで記述を洗練する。

評価では、すべてのテスト用ツールを学習から除外している。主要なベンチマークは StableToolBench で、
ドメインをまたぐ転移は RestBench（TMDB と Spotify）と [[Dataset/berkeley-function-calling-leaderboard]]
v2 で検証し、主なツール利用エージェントとして GPT-4.1 を用いている。

## 主なポイント

- 論文は、効果的な記述が共有するインターフェースパターンを 5 つのカテゴリに特定している。ツール選択の
  範囲（いつツールを使い、いつ使わないか）、ツール間の依存関係、出力の説明、パラメータの制約、パラメータ
  間の依存関係である。元の記述は、どのカテゴリでも分析対象ツールの 12% 未満しかカバーしていなかった
  のに対し、Trace-Free+ はツール選択の範囲で 97.2%、パラメータの制約で 94.2% に達した。
- StableToolBench の複数ステップのクエリでは、Trace-Free+ はクエリ単位の成功率 44.6% を達成し、元の
  記述の 33.5%、一般的なガイドラインで書き換えた記述の 41.5% を上回った。単一ステップのクエリでは、
  ガイドラインに基づく書き換えを上回らなかった（60.7% 対 61.6%）。
- エージェントに 150 個以上の候補ツールを提示するスケーリング実験では、Trace-Free+ は元の記述で生じる
  精度低下を 29.23% 抑え、クエリ単位の成功率を平均 60.89% 改善した。これは評価の中で最大の改善であり、
  著者らはこれを、ツールカタログが大きいときにこそインターフェースの最適化が最も重要になることを示す
  ものと解釈している。
- 書き換えた記述は RestBench に転移し、TMDB では元の記述に比べてクエリ単位の成功率が最大 51.3% 相対的に
  改善した。また BFCL v2 では、GPT-4.1、Claude Sonnet 4.5、Gemini-3-pro-preview のいずれも、エージェント
  自体には一切手を加えずに改善した。
- 記述の書き換えとエージェントのファインチューニングは相補的だった。RestBench 上の Qwen3-4B-Instruct
  エージェントでは、ファインチューニングのみでクエリ単位の成功率が 54.1% から 55.0% に、Trace-Free+
  のみで 62.1% に、両者を組み合わせると 62.9% になった。
- 著者らのデプロイに関する助言は、単純なクエリや小さなカタログにはガイドラインに基づく書き換えで十分
  であり、Trace-Free+ は複数ステップのワークフローを伴う大規模なツールカタログに適している、というもの
  である。

## 補足

評価ではステップ単位の教師強制（teacher forcing）を導入している。これは、エージェントの選択にかかわらず
各ステップで正解のツールを実行するもので、失敗をそれ以前の誤りではなく、エージェントが現在のツールの
記述をどう読んだかに帰属させられるようにする。一方、スケーリング実験ではエージェント自身の選択を実行
している。著者らはまた、StableToolBench のパラメータスキーマのうちサーバーが要求するものと一致しない
一部を修正し、すべての手法を修正後のスキーマで評価したため、彼らの絶対値は元のスキーマを用いた研究とは
直接比較できない。

著者らが述べる限界には、上記の単一ステップでの差 ── 合成した学習クエリが平均 3 つのツールを使うことに
起因すると彼らは考えている ──、記述生成器として小規模なベースモデル 1 つだけを用いたこと、そして推論
された制約の精度を測ることの難しさがある。後者については、なじみのない API に対して、モデルがときに
制約（サーバーが強制していない値の範囲など）をハルシネーションする可能性がある。この論文は査読中の
プレプリントとされており、ここで抽出したバージョンは arXiv:2602.20426v2 である。
