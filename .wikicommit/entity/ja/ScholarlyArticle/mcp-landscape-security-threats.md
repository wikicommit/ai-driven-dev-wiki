華中科技大学の Xinyi Hou、Yanjie Zhao、Shenao Wang、Haoyu Wang（責任著者は Haoyu Wang）による本論文は、著者らが [[DefinedTerm/model-context-protocol]] の情勢、その立ち上がりつつあるエコシステム、そしてそのセキュリティリスクについての最初の分析だと述べるものを提示している。その動機として掲げられているのは論争ではなくギャップである。MCP は「業界で急速に採用が進んだ」が「学術的にはいまだほとんど探究されていない」というのである。

その手法はアーキテクチャが先、セキュリティが後である。著者らはサーバの視点から MCP サーバの完全なライフサイクルを定義し——公式のプロトコル文書と、実際の MCP の運用ワークフローの体系的な分析から導いたと述べている——、そのライフサイクルの上に脅威の分類体系を構築する。ライフサイクルは4つの逐次的なフェーズからなる。**作成**——開発者がメタデータを定義し、能力を宣言し、サーバを実装する。**デプロイ**——開発者が公開プラットフォームへリリースし、ユーザーがホストへ配備し、クライアントが接続する。**運用**——ユーザーが能動的に対話する実行時の期間。そして**保守**——バージョンの反復、設定の更新、継続的な最適化である。

## 主な貢献

- **ライフサイクルに根ざした脅威の分類体系。** 16の脅威シナリオが4種類の攻撃者へ対応づけられている。*悪意ある開発者*——名前空間のタイポスクワッティング、ツール名の衝突、選好の操作、ツールポイズニング、ラグプル、サーバ間シャドーイング、コマンドインジェクション。*外部の攻撃者*——インストーラのなりすまし、間接プロンプトインジェクション。*悪意あるユーザー*——認証情報の窃取、サンドボックスからの脱出、ツール連鎖の悪用、認可されていないアクセス。*セキュリティ上の欠陥*——脆弱なバージョン、権限の残存、設定のドリフトである。
- **フェーズではなく起点に基づく分類。** 著者らは、各リスクを単一のライフサイクルのフェーズへ割り当てることに明示的に反対している。「ツールポイズニングやラグプルのような攻撃は作成の段階で持ち込まれるが、運用時に発火する」からである。代わりに起点を分析することが、源流での緩和を支えると彼らは述べる。
- **概念実証による検証。** 著者らは、特定された各リスク種別について隔離された環境で PoC の MCP サーバを構築し、それらに接続するための公式 SDK 上のカスタム MCP ホストも作った。彼らはその限界を明示している。目的は実行可能性を示すことであり、攻撃の成功率やベースとなる LLM ごとの挙動の違いを測ることではなく、それらは今後の課題としている。
- **MCP が従来のアプローチと異なる点。** 本論文は、MCP が「アクセス制御、能力ネゴシエーション、スキーマの発見をプロトコルのプリミティブとして組み込んでおり、この点が従来の関数呼び出しの仕組みと異なる」と論じ、手作業による API の結線、プラグインのインターフェース、エージェント枠組みの限界に対処しているとする。
- **エコシステムのスナップショット。** 採用状況はカテゴリ別に表にまとめられ、2025年9月時点まで更新されている。最初期の MCP 支持者の公式文書を手作業で調べて編纂し、コミュニティの議論とリポジトリのマイニングによって拡張したものである。著者らは、これが検証可能な統合を持つ成熟した製品に偏っており網羅的ではないことを認め、このデータセットを公開リポジトリとして維持すると述べている。公式 SDK は TypeScript、Python、Java、Kotlin、C# について記録され、コミュニティの枠組みとサーバ生成プラットフォームも併記されている。
- **役割ごとのライフサイクル別推奨。** 開発者には、来歴の検証を実装すること、バージョン管理されたリリースを用いること、サーバの登録前に静的解析またはデジタル署名を適用することを勧める。ユーザーには、信頼できる MCP のコレクションを優先すること、インストール時にデジタル署名を検証すること、サンドボックス化されたホストに依拠することを勧める。エコシステムのメンテナには、自動的なバージョンチェック、完全性の監査、必須の設定検証をレジストリとコレクションへ統合することを勧める。

## 注記

エコシステムがなぜ危険にさらされているのかについての本論文の診断は、技術的というより構造的である。**集中的なセキュリティ監督の不在**を指摘する。サーバが独立した開発者によって管理されるため、ベースラインを監査したり順守を強制したりする中央の権威が存在せず、パッチ適用は不揃いで脆弱性の管理も不定期になり、公式のパッケージ管理の仕組みがないことがバージョンの不整合と検証されていない更新をもたらす。また**認証と認可のギャップ**も指摘し、MCP は「現在、クライアントとサーバにまたがる認証と認可の標準化された枠組みを欠いている」と述べている。

名指された脅威のうち2つは、本 wiki が他所で記録している記述を拡張するものである。本論文は [[DefinedTerm/tool-poisoning]] を、悪意ある開発者による能力の宣言のもとに置き、あわせて**ラグプル**——サーバの宣言された能力が、ユーザーがそれを信頼するようになった後で変わる——と**サーバ間シャドーイング**——悪意ある機能が別のサーバの存在の陰に隠される——を挙げている。**名前空間のタイポスクワッティング**の扱いでは、タイポスクワッティング自体はパッケージマネージャ、プラグインシステム、クラウドの枠組みでおなじみのものであるが、MCP のもとでは異なる現れ方をすると指摘する。デプロイ時のユーザーも実行時のホストも、明示的な手動の選択ではなく主として名前と説明のテキストに基づいてサーバを選ぶからである。
