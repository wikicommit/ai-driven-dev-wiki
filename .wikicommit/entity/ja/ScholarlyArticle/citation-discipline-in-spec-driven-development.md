「Citation Discipline in Spec-Driven Development」は Subham Panda による2026年6月付の論文であり、コーディングエージェントに、書くコードの一行ごとに要件を引用させることが、正しさ、決定性、ハルシネーションの検出可能性を実質的に改善するのかを問うている。その枠づけとなる問題は説明責任にかかわる。人間の開発者と違って LLM には後から自らの判断を説明させることができず、その出力は「微妙な逸脱を持ち込んでいるときでさえもっともらしく見える」——スコープ外の機能、訓練データからの先行事例の混入、過剰な作り込み——のであり、同論文によればそれらは典型的にはすべての自動テストを通過しながら、承認されていない機能を持ち込む。

## 主な知見

比較の対象は、トレーサビリティへの3つのアプローチである。**traceSDD** は、コードの一行ごとにインラインの引用を義務づけ、それぞれを階層的な `REQ-XXX.Y.Z` 識別子を持つ第3層の要件点に結びつけ、検証可能な主張として扱う。コード中に引用されていながら仕様に存在しない REQ ID は、自動的に検出可能な孤児となる。**Spec Kit**（[[SoftwareApplication/spec-kit]]）は spec-plan-tasks の連鎖を通じて成果物レベルの一貫性を強制するが、同論文の見立てでは、引用の連鎖は実装が始まった時点で途切れる。**OpenSpec** は、YAML のサイドカーファイルに置かれた事後的な外部トレースマップを用い、ソースコードに注釈を付けることなく、行の範囲を後から仕様の ID へ結びつける。

同論文の見出しの結果は、アーキテクチャの異なる2つのモデルにまたがって再現したと報告するトレードオフである。**引用は決定性を下げる**。引用なしの条件は、独立したセッションにまたがる語彙上の類似度が、引用ありの条件より有意に高かった（Claude d = −0.76, p = 0.003; GLM d = −0.72, p < 0.001）。**自動的なハルシネーション検出を可能にするのは引用ありの条件だけである**。トレーサビリティ検出率（TDR）は Claude で 86.4%、GLM で 88.0% であり、他の3つはいずれも 0% であった。偽陽性率はどちらの研究でも 0% である。著者は引用なしの条件が何を確立するかを強調している。すなわちそれは同一の REQ 形式の仕様を用いながら何も検出しなかったのであり、同論文はこれを、検出には単に構造化された仕様があるだけでは足りず、コード中の注釈が必要であることの証明と読んでいる。

他の2つのフレームワークに対する traceSDD の決定性上の優位は部分的であった。Spec Kit よりは有意に良かった（Claude d = 0.47, p = 0.049; GLM d = 0.42, p = 0.003）が、OpenSpec とは有意差がなかった（Claude d = 0.18, p = 0.44; GLM d = 0.14, p = 0.32）。第4の知見は仕様の形式そのものにかかわる。引用なしの REQ 形式の条件は、外部の2つのベースラインをいずれも有意に上回った（Spec Kit に対し平均 d = 1.02、OpenSpec に対し平均 d = 0.91）。同論文はこれを、構造化された REQ 形式の仕様が、いかなる引用の注釈とも独立に決定性の錨を与えることの証拠と捉えている。

決定性のペナルティについて同論文が提示する説明は、引用の配置のばらつきである。独立した各セッションにおいて、モデルはどのコードを書くかだけでなく、各引用をどこに置くかも決めなければならない——関数のシグネチャは自らが実装するすべての要件を引用するのか、主たるものだけなのか、複数行の条件分岐は一度引用するのか各行で引用するのか——のであり、著者が正解はないと注記するこれらの判断が、体系的な語彙上の乖離を持ち込む。サブグループ分析では、このペナルティは易しく小さなタスクで最も顕著であった。

## 背景

推奨は場面ごとに階層化されている。規制のある、あるいはリスクの高い領域の本番システムについては、偽陽性率 0% での 86〜88% の検出が、語彙的類似度にしておよそ 0.13〜0.21 ポイントという同論文が中程度と呼ぶ決定性のコストを正当化するという理屈で、引用の義務づけを勧めている。素早いプロトタイピングについては、REQ 形式の仕様を用いた引用なしのアプローチを勧め、引用のオーバーヘッドなしに構造上の錨を保つことを勧めている。Spec Kit と OpenSpec を比較検討しているチームについては、Spec Kit のほうが決定性が低く自動検出をまったく欠くため、測定された次元では劣る選択であると述べつつ、「その開発者体験と自然なワークフローが実務上は埋め合わせになりうる」ことを明示的に認めている。

同論文は自らの限界について異例なほど率直である。すべての実装は中程度の複雑さ（50〜1,000行）の Python であるため、本番規模のタスクでは振る舞いが異なりうる。2つのモデルは1つより強い証拠ではあるが、それでも全体の一部である。最も重要なこととして、ハルシネーションは既知の偽 REQ-099 識別子を用いて*注入*されたものであり、著者は自然発生的なハルシネーションはより微妙でありうると注記している。とりわけ、ハルシネーションされたコードについて引用を完全に省くモデルは、孤児 REQ のチェックをまるごと迂回してしまうのであり、Claude のデータではハルシネーション事例のおよそ 12% でそれが起きていた。そこから、孤児 REQ のチェックを引用なしの行のチェックで補うべきだという推奨が導かれている。決定性の指標は語彙的類似度を測るものであり、著者は正規化の後でさえ内容と書式を混同していることを認めている。また N=20 の Claude の研究は、一部の比較については検出力が不足していた。

同論文が述べていないことが1つある。著者と、最も強いと結論づけられたフレームワークとの間に何らかの関係があるかどうかである。traceSDD についてのその推奨を吟味する読者に与えられているのは、報告された方法と事前登録された分析だけである。
