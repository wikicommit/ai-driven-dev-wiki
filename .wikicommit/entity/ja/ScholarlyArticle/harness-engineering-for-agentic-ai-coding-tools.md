本論文は、エージェント型 AI コーディングツールがどのような設定メカニズムを提供しているか、そして開発者がオープンソースリポジトリで実際にそれらをどう使っているかを問う。この問いは階層的な語彙によって枠づけられている。*コンテキスト*は 1 回のモデル呼び出しへの入力の全体であり、*エージェントハーネス*はモデルを取り巻くソフトウェアで、エージェントループを駆動し、呼び出しごとにそのコンテキストを組み立て、ツールスキーマを公開し、ターンごとの状態を管理する。[[DefinedTerm/context-engineering]] はハーネスが実行時に組み立てるコンテキストを設計する実践であり、コンテキストだけでなくハーネスそのものをプロジェクトに合わせてカスタマイズすることを、著者らは [[DefinedTerm/harness-engineering]] と呼ぶ。*設定メカニズム*とは、開発者がツールやエージェントの振る舞いをプロジェクトやワークフローに合わせて調整するためのあらゆる手段であり、*設定アーティファクト*とは、`CLAUDE.md` ファイルやスキルディレクトリのような、リポジトリでバージョン管理されるその具体的なインスタンスである。

著者らはまず、[[SoftwareApplication/claude-code]]、[[SoftwareApplication/github-copilot]]、[[SoftwareApplication/cursor]]（CLI）、[[SoftwareApplication/gemini-cli]]、[[SoftwareApplication/openai-codex]] CLI のドキュメントを調べ、ファイル名とディレクトリ名から検出ヒューリスティクスを導き出した。次に、GitHub 上のエンジニアリングされたオープンソースプロジェクト ── フォークではなく、ライセンスを持ち、複数のコントリビューターがいて、2024 年より前に作成され、2025 年 6 月以降も活動しているリポジトリで、明確なソフトウェアエンジニアリングの実践を示すプロジェクトだけを残すために LLM で README ファイルを分類したもの ── をサンプリングし、これらのツールを 1 つ以上使っている 2,853 のリポジトリを見つけた。全体的な採用状況に加えて、3 つのメカニズムを詳細に分析している。コンテキストファイルと Skills はすべてのツールがサポートしているため、Subagents は Skills と同じ形式を共有しているためである。

主な結論は、開発者は静的なコンテキストのメカニズムを広く採用している一方、実行可能なメカニズムや外部のメカニズムはめったに採用しておらず、「したがって、今日のオープンソースにおけるハーネスエンジニアリングは、ほとんどがコンテキストエンジニアリングである」というものである。著者らは結果を、まだ定着しつつある慣行についての実証的なベースラインであり、ある時点（2026 年 2 月）のスナップショットであると位置づけている。

## 主なポイント

- 本論文は 8 つのリポジトリレベルの設定メカニズムを整理している。Context Files、Skills、Subagents、Commands、Rules、Settings、Hooks、MCP サーバーである。Context Files と Skills は調査した 5 つのツールすべてがサポートしており、8 つすべてを実装しているツールは 1 つもない。
- コンテキストファイルは最も頻繁に採用されたメカニズムで、ツールごとにリポジトリの 61.5% から 100% で使われていた。Claude Code、Copilot、Cursor、Gemini では、他のメカニズムで採用率が 20% を超えたものはなかったが、例外として Cursor のリポジトリの 72.8% が Rules を採用し、Gemini のリポジトリの 62.3% が Settings を使っていた。Codex（4 リポジトリ）は数が少なすぎて特徴づけられなかった。
- リポジトリの 70.6% は単一のツールだけを設定しており、さらに 493（17.3%）はツール固有の設定アーティファクトを持たずに [[DefinedTerm/agents-md]] を使っている。
- Claude Code のリポジトリは最も幅広いメカニズムを使っており、Cursor のプロジェクトは Rules と Commands に重点を置き、Copilot のリポジトリがコンテキストファイル以外に広がることはまれである。
- 2,586 のリポジトリ（サンプルの 90.6%）で見つかった 4,768 のコンテキストファイルのうち、最も多かったのは `CLAUDE.md`（34.4%）で、`AGENTS.md`（31.6%）、`copilot-instructions.md`（29.2%）がそれに続いた。
- 複数の種類のコンテキストファイルを持つリポジトリでは、通常 `CLAUDE.md` が最初に作成され、`AGENTS.md` が後から追加されていた。`CLAUDE.md` が参照する先として最も多いのは `AGENTS.md`（301 件）であり、`AGENTS.md` は 353 件の被参照を受けていて、他のどの種類のファイルよりもはるかに多い。著者らはこれを、ベンダーの指示ではなく開発者の実践によって推進される、ツール非依存の標準としての `AGENTS.md` へのボトムアップの収束と読み取っている。
- 著者らは、Claude Code がサンプル中で最も人気のあるツールであるにもかかわらず、研究時点では `AGENTS.md` をネイティブにサポートしていなかったことを指摘し、これを開発者の実践とツールの機能との間のギャップだと述べている。
- 研究では 158 のリポジトリで 601 の [[DefinedTerm/agent-skills]] が見つかった（リポジトリあたりの中央値は 2）。85.5% は追加のリソースを含んでおらず、Skills は実行可能なスクリプトとしてよりも主に構造化されたテキストとして機能しており、仕様が推奨する 500 行を超えるものは 4.8% にすぎない。
- 131 のリポジトリで 450 の Subagents が見つかり（リポジトリあたりの中央値は 2）、Claude Code の Subagents で利用できる永続メモリ機能を使っているリポジトリは 1 つもなかった。

## 補足

著者らの実践的な推奨はこれらの知見から導かれている。`AGENTS.md` はエージェント型ツールを設定するための最も簡単な入り口である。複数のツールを使う開発者は、それを共有のコア設定として維持すべきであり、場合によっては複数のコンテキストファイルを階層的に構成し、ツール固有のファイルをそれを参照するアダプターとして機能させるとよい。Skills は繰り返し行うワークフローのためにスクリプトや構造化されたリソースを束ねる手段を提供するが、ほとんどの Skills はそうしていない。そして Rules や Commands のようなツール固有のメカニズムは、ワークフローを 1 つのツールに縛りつける。また、1 つのリポジトリに複数のコンテキストファイルを重ねると、冗長な指示や矛盾する指示が生じるリスクがあることも指摘しており、より豊かな設定がコンテキストファイルだけの場合と比べてエージェントの成果を測定可能な形で改善するかどうかについて、縦断的研究や統制された研究を求めている。

著者らが述べている限界には次のものがある。ヒューリスティクスは実際のツール利用ではなく設定アーティファクトの存在を検出していること（コミット履歴をスキャンしたところ、設定アーティファクトを 1 つ以上持つリポジトリの 72.1% で AI が作成したコミットが見つかり、著者らはこれを下限として扱っている）、Copilot、Cursor、Gemini については検出されたファイルの一部が非エージェント型のモードにも適用されること、「エンジニアリングされたプロジェクト」の分類が 1 つの LLM による 1 回のラベリングに依拠していること、そしてサンプルがオープンソースの GitHub リポジトリのみを対象としていることである。

本論文は、AIware '26（モントリオール、2026 年 7 月 6〜7 日）で発表された "Configuring Agentic AI Coding Tools: An Exploratory Study" の拡張版である。著者らの所属は、バンベルク大学、ハイデルベルク大学、シンガポール経営大学である。
