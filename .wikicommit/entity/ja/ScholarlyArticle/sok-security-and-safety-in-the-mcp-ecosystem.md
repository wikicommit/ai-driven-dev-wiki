この知識体系化（SoK）論文——Tribhuvan University、University of North Dakota、Youngstown State University、University of Missouri、University of Toledo に所属する Shiva Gaire、Srijan Gyawali、Saroj Mishra、Suman Niroula、Dilip Thakur、Umesh Yadav によるもので、著者全員が等しく貢献したと述べられている——は、[[DefinedTerm/model-context-protocol]] を「大規模言語モデル（LLM）を外部のデータおよびツールへ接続する事実上の標準であり、実質的に『エージェンティック AI のための USB-C』として機能するもの」として捉える。その中心的な主張は、MCP にバグがあるということではなく、セキュリティエンジニアリングが通常依拠している区別を MCP が崩してしまうということである。

その主張は、問題についての本論文自身の枠づけである。従来のソフトウェアにおいて、「セキュリティは悪意ある敵対者（たとえば SQL インジェクション）から守り、セーフティは意図しないシステムの振る舞い（たとえば競合状態）から守る。MCP においては、この区別がぼやける」。示される具体例は双方向に働く。セキュリティ侵害——攻撃者が企業のナレッジベースへ悪意ある文書を注入すること——が、モデルが「誠実に、しかし誤って、データベースを削除する権限があると信じ込む」というセーフティの失敗を引き起こす。逆に、ツールの引数を幻覚するといったセーフティの失敗が、機微なデータが公開ログへ流出するというセキュリティ侵害を生みうる。著者らは、現在の防御はこの二重性に対して備えが不十分だと論じる。「従来のファイアウォールは JSON-RPC メッセージの意味的な意図を検査できず、LLM のセーフティフィルタはツール実行の下流の帰結を見ることができない」からである。そして MCP をセキュアにするには「コンテキストの可用性と実行権限を切り離しがたく結びついた変数として扱う統合的な脅威モデルが必要である」と結論づける。

## 主な貢献

本論文は4つの貢献を挙げている。

- **統合された脆弱性の分類体系**。*敵対的なセキュリティ上の脅威*——例として挙げられるのはツールのなりすましとコンテキストポイズニング——を、*認識に関わるセーフティ上のハザード*——分散したツール委譲におけるアラインメントの失敗など——から区別する。
- **MCP のプリミティブの構造的分析**。「コンテキスト」（Resources）を「アクション」（Tools）から切り離すことが新しい脆弱性の類型を生むと論じる。読み取り専用のアクセスが書き込みアクションを引き起こすために武器化される**プリミティブ横断のエスカレーション**を含む。
- **立ち上がりつつある防御のサーベイ**。プロンプトエンジニアリングを超えてアーキテクチャ的な解へ進み、暗号学的な来歴のための Enhanced Tool Definition Interface（ETDI）とカーネルレベルのセッション隔離を挙げている。
- **フォレンジックなケーススタディ**。Supabase のデータ漏洩を含む実世界のインシデントを再構成し、企業導入のための教訓を導いている。

そのスコープは、MCP のエコシステム自体が持ち込むリスクへ意図的に絞られている。すなわちプロトコルのプリミティブ、オープンなツールレジストリにおけるサプライチェーンリスクを含む分散した Host–Client–Server の相互作用から生じるトポロジのリスク、そしてそれらの交差である。重み汚染のような一般的な LLM への敵対的攻撃は、プロトコルの完全性や実行フローに直接影響しない限り明示的に除外されている。

セーフティの分類体系は4つの部分に整理され、それぞれが主たるプリミティブとリスク種別へ対応づけられている。**認識的完全性**（Resources——断片化された、あるいは忠実度の低い検索に由来する接地の失敗または幻覚）。**敵対的耐性**（Resources と Prompts——外部データに埋め込まれた隠れた指示やプロンプトインジェクション）。**アラインメントの一貫性**（Host のモデルとツールのポリシー——有害な委譲につながるポリシーの衝突や目標追求のミスアラインメント）。そして**システム的ガバナンス**（人間の監督と規制——ヒューマンインザループの失敗、説明責任のギャップ、デュアルユースの悪用）である。セキュリティ側のカテゴリには、セッション間の汚染、サプライチェーンおよびモデル切り替えの攻撃（ラグプル、サーバのなりすまし、認可されていないツールの改変）、プロトコルの悪用と名前の衝突（コマンドの重複、混乱した代理人によるアクセス）、そしてサービス妨害とリソース枯渇が含まれる。

## 注記

MCP が*なぜ*これらのリスクを増幅するのかについての本論文の説明は、偶発的というより構造的である。MCP が責務を、それぞれ異なる信頼領域で動作する3つのプリミティブへ分離しており、かつそれらのプリミティブが独立した Host、Client、Server にまたがって相互作用するため、「従来の『単一のセーフティ境界』が溶解する」。したがって、あるプリミティブにおける失敗——たとえば忠実度の低い文脈の検索——が、別のプリミティブによって実行される有害な行動へとエスカレートしうる。著者らは検索拡張生成との明示的な類比を引き、そこでは「上流の検索における認識的な誤りが下流の推論へ頻繁に伝播する」と述べたうえで、MCP のもとではプロトコルが実世界の行動を実行できるため伝播が増幅され、コンテキストの誤りが運用上の害になると論じる。

現状についての診断は、「MCP の採用は急速である一方、ガバナンスと標準化は後れを取っている」というものである。多くのクライアントは完全なツール仕様を提示せず、権限を透明に要求せず、コンテキストと実行のあいだの厳格な境界を強制していない。そこへサードパーティのインストーラ、共有されたコンテキスト、認証の不在、検証されていないツールの更新が加わって露出を拡大させている。本論文が求める防御策の組み合わせは、認証、サンドボックス化、来歴の確認、ツールの検証、セッションの隔離、継続的な監視、そして最小権限の強制である。

結論は、単にどう守るかにとどまらず、このプロトコルをどう理解すべきかについての主張である。MCP は「単なる API としても、単なる LLM としても」扱えない。コンテキストとアクションの結合が「意味的な攻撃面」を作り出し、そこでは間接プロンプトインジェクションが実世界の運用上の被害へとエスカレートし、幻覚がセキュリティ侵害を招きうるからである。著者らは、既存の防御は「必要ではあるが十分ではない」と述べ、必要なのは暗号学的な来歴、実行時の意図の検証、そして厳格なケイパビリティベースの隔離であるとする。その責任は、「ID と検証をコア仕様に焼き込まなければならない」プロトコル設計者、「モデルへの入力を信頼できないユーザーデータとして扱わなければならない」ツール開発者、そしてエージェント的な振る舞いを継続的に監視しなければならない組織のあいだで分担される。

これはプレプリント（2025年12月、バージョン2）であり、著者らはこれを「Model Context Protocol のリスクを体系化した最初の学術的サーベイ」だと位置づけている。[[ScholarlyArticle/mcp-landscape-security-threats]]、[[Report/model-context-protocol-security]]、[[DefinedTerm/tool-poisoning]]、[[DefinedTerm/indirect-prompt-injection]] も参照。
