「Knowledge-Based Pull Requests」は復旦大学の Xinyu Zhang と Weiwei Sun による論文であり、外部の貢献者がプロジェクトへ作業を提出するとき、何が信頼境界を越えるのかについての変更を提案している。その前提は、AI コーディングエージェントがボトルネックを移動させたというものである。「コードはますます安価になる一方、意図の理解、スコープの交渉、プロジェクトの長期的責任の統治は依然として高くつく。」その提案である [[DefinedTerm/knowledge-based-pull-requests]] は、境界を越える成果物はパッチではなく人間が確認した知識パッケージであるべきであり、マージ可能なコードは受け入れ側のプロジェクトの内部で再生成される、というものである。

## 主な知見

同論文の枠づけとなる対比は3通りである。イシューに基づくフローでは、疎な知識が境界を越え、コードは越えない。従来のプルリクエストでは、外部のコードが越えてマージ候補になる。提案されたワークフローでは、外部のコードは知識パッケージのなかの1つの情報源にすぎず、コードベースに入りうるコードは、リポジトリとセキュリティのポリシーのもとでプロジェクトが所有する内部の信頼されたコーディングエージェントによって生成される。著者たちは、そこから得られるガバナンス上の便益を、従来のプルリクエストが1つに潰してしまう2つの判断を切り分けることとして述べている。すなわち、その知識がプロジェクトに入るべきかどうかと、特定の実装がマージされるべきかどうかである。

同論文がやや長めに論じている点は、答えが生のトレースでも生のコードでもないということである。協働者のエージェントのトランスクリプトを添付することは不十分と呼ばれる。生のトレースは「古びた結論、無関係な試行錯誤、複写された文書、秘密情報、私的な環境の詳細、信頼できない指示を含みうる」からであり、読むには長すぎることもあるからである——それでは帯域の問題をコードレビューからトレースレビューへ移すだけになる。代わりに必要とされるものは「レビュー可能かつ変換可能な知識オブジェクト。プロジェクト側のレビュアーにとって十分にコンパクトで、エージェントにとって十分に構造化されており、不確かさについて明示的で、主張を検分する必要があるときには来歴に裏づけられたもの」と説明されている。

著者たちは自らが何を主張しているのかについて注意深い。知識の抽出、仕様の記述、来歴の追跡、エージェンティックなコード生成は個々には新しい能力ではないと述べ、貢献は「信頼境界をまたぐソフトウェア協働のための、ワークフローレベルの再結合」であるとしている。彼らはまた最も鋭い反論——この提案は信頼できない貢献者向けの仕様駆動開発ではないか——を自ら予期し、構造化された意図がエージェンティックな実装を導きうるという考えを意図的に借りていることを認めつつ、その周りに情報源、証拠、権限にかかわるガバナンスの層を加えていると述べている。

コストのモデルは、便益としてではなく条件として述べられている。このワークフローは段階を追加する——知識の抽出、ビューの生成、人間による確認、知識のレビュー、プロジェクト側での再生成、忠実度の検査、そして通常のコードレビューである。ゆえに著者たちは、それが「エージェントが定型的で監査可能な変換作業を吸収でき、かつその吸収された作業が、プロジェクト側の開発者に外部コードをリバースエンジニアリングさせ、アーキテクチャの不整合を直させ、レビューの終盤で制約を再発見させるより安く済むときにのみ有用である」と書き、小さな機械的な修正にはこの経路はおそらく重すぎるとしている。彼らはこれを、ワークフローの性質ではなく評価されるべき仮説と呼んでいる。

2つのガバナンス上の細部が、他より深く詰められている。**実装の権限**は中心的なガバナンスの主張として名指されている。外部のコードは、問題が実在すること、ある振る舞いが実現可能であること、あるエッジケースが関連することの、価値ある証拠でありうるが、それはマージすべき既定の成果物ではない。内部の信頼されたエージェントは、プロジェクトのテスト、スタイル規則、アーキテクチャ、依存関係のポリシー、セキュリティ規則とともに動作でき、計装され、サンドボックス化され、監査されうるからである。著者たちは、これが「内部の信頼されたエージェントを無謬にするわけではない。実装に対する統制を明示的にするのである」と付け加えている。**貢献者のクレジット**は、このワークフローが生み出す問題として指摘されている。外部の協働者は追加の知識労働を行いながら、マージされたコードの著者にならないかもしれず、それは明示的なクレジットがなければ「KPR を、貢献者にとって通常の PR より悪い取引に変えてしまいうる」。ゆえに同論文は、貢献のクレジットはコードの著者性とは別に記録されるべきだと論じている。

## 背景

実証部分は意図的に小さく、著者たちもそう明記している。彼らはマージ済みの公開プルリクエスト7件にわたる統制されたシミュレーションのパイロットを構築し、それが「KPR の端から端までの検証ではなく、プロジェクトのメンテナは関与していない」こと、そして実際の PR の素材をパッケージへ変換でき、統制された情報損失と合成的な汚染のもとで評価できるかだけを試すものであることを明示している。成果物は著者たち自身によって 0〜2 のルーブリックで採点されており、これは「メンテナの生産性についての主張としてではなく、計装のチェックとして」読まれるべきだと彼らは述べている。

そこから3つの限定的な観察が得られた。通常の要約と知識パッケージは、7件すべてで可視的な意図を保存した。著者たちはこれを部分的に、記述的な PR のタイトルと変更の小ささに帰している。パッチの信号が利用できる場合、パッケージは証拠のトレーサビリティを明示したが、通常の要約は主張、証拠、来歴、安全性を切り分けていなかった。そしてコンパクトな外部コードの信号は有用であることが示された。PR の説明を伏せた場合でも、パッケージは7件中6件で実装知識を十分に保存したのに対し、差分を伏せた場合には7件中5件しか実装上の十分性に達しなかった——最も明瞭な失敗は自動化されたプラグイン一覧の更新であり、そこではコンパクトな要約は正確な一覧を再生成するのに十分な情報を含んでいない。

合成的な汚染の結果は、さらに強く留保されている。汚染された7件のパッケージはすべて挿入されたハンクを拒絶したが、著者たちはこれが「ハーネスがそれを正当でない外部コードとして印づけるがゆえに」成り立つと述べており、示されているのはこの成果物が信頼できないコードの区別を表現でき、ストレステストにかけられるということだけであって、「KPR が現実の敵対的なプロンプトインジェクションや悪意あるコードに対して安全であることではない」。このパイロットはまた、著者たちが自らに不利な形で報告する弱点も露わにした。制約の具体性はすべての条件で低いままにとどまり、パッケージは一般的な制約は捉えたものの、プロジェクト固有の豊かな非目標は捉えられなかった。
