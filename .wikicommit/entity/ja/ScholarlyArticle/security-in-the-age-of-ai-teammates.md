"Security in the Age of AI Teammates" はノートルダム大学の5名の著者による実証研究であり、2026年1月1日に arXiv へ投稿された。その主題は、自律的なコーディングエージェントが実際のリポジトリに対してプルリクエストを著すとき、セキュリティについて実際に何をしているのか、そして人間のメンテナがどう応答するのか、である。

論文が特定する空白は、エージェントが著したプルリクエストに関する先行の実証研究が生産性と受理率に集中しており、「ソフトウェアセキュリティにおける自律エージェントの役割と、人間によるレビューの動態がほとんど未探索のまま残されている」ことである。データは、広くデプロイされている5つの自律コーディングエージェントが著した、キュレーション済みのプルリクエスト 33,596 件からなる AIDev データセットであり、そこからセキュリティに関わる PR がルールベースのフィルタリングによって特定され、そのうえで人手で確認されている。

## 主要な貢献

- **出現率と、その不均等な分布。** 確認されたセキュリティ関連のエージェンティックなプルリクエストは 1,293 件、データセット内のエージェント活動全体の 3.85% である。その割合はエージェントごとに大きく異なる。[[SoftwareApplication/claude-code]] が最も高い比率を示し、459 件、自身の活動の 14.6% である。次いで Copilot が 4,970 件（10%）、Devin が 4,827 件（7.6%）——絶対数ははるかに大きいが比率は低い。OpenAI Codex は対極にあり、人手による検証の後にセキュリティ関連と確認された PR は自身の 1.3% にすぎない。
- **セキュリティ作業は脆弱性の修正ではなく堅牢化が主である。** 論文の分類はセキュリティ関連の PR を互いに排他的な4つのカテゴリ——依存関係の更新、脆弱性の修正、セキュリティ機能、設定／コンプライアンス——に分け、その知見は「エージェントは狭い脆弱性の修正のみに焦点を当てるのではなく、テスト、ドキュメント、設定、エラー処理の改善を含む、補助的なセキュリティ堅牢化の活動を最も頻繁に行う」というものである。PR のタイトルと説明の質的分析はさらに、セキュリティ作業がそれ自体としてのセキュリティ作業として着手されるのではなく、より広い開発上の目標——最も多いのはコードのリファクタリングと機能の改善——のなかに埋め込まれていることが多いと付け加える。
- **受理はエージェントごと、言語ごとに大きく異なる。** セキュリティ関連のエージェンティックな PR のマージ率は、Copilot の 49.60% から OpenAI Codex の 86.59% までの幅がある。エコシステム別では、Rust のセキュリティ PR が 51.16% で最も低い受理率を示す。
- **セキュリティ PR は著しく重い人間の精査を受ける。** レビュー待ち時間の中央値は**セキュリティ PR で 3.92 時間、そうでないもので 0.11 時間**——中央値でおよそ36倍の差である。論文はこの比較においてセキュリティ PR 1,130 件に対し非セキュリティ 30,154 件を報告しており、この隔たりはセキュリティ側のマージ率がより低いことと併存している。
- **却下を予測するのはセキュリティの内容ではない。** PR レベルの早期の信号の分析は、「知覚されるリスクは、明示的なセキュリティの用語よりも、複雑さと冗長さ（たとえばタイトルの長さ）とより強く結びついている」ことを見出す。結論はその含意を直截に引き出す。「エージェントが著したコードのセキュリティレビューは、脆弱性の内容だけにとどまらず、文脈的・認知的な要因によって形づくられる。」

## 覚え書き

レビュー待ち時間の対比は、実践にとって最も広い含意を持つ結果である。というのも、これは他では逸話的にしか語られないことを定量化しているからだ。人間のレビューのボトルネックは、エージェントの出力に対して一様ではない。セキュリティでないエージェンティックな PR の中央値 0.11 時間——7分未満——は、事実上おざなりなレビューを表しており、他方で同じメンテナが中央値のセキュリティ PR には3時間半以上を費やしている。このパターンは [[DefinedTerm/verification-bottleneck]] に記録されたレビューコストの知見と整合し、それをより鋭くする。レビュアーは一様にレビューしているのではなくトリアージしているように見えるのであり、それは彼らがセキュリティ関連として印を付け*損ねた*カテゴリが7分の扱いを受けることを意味する。

却下の信号についての知見は、この論文で最も居心地の悪いものである。レビューの決定が、PR がどれだけリスキーかではなく、どれだけ作業量が多そうに見えるかを追っていることを示唆するからだ。前の点と併せて読めば、レビューのプロセスが表層的な手がかりに応答している像が浮かぶ。

2つの境界が当てはまる。測定されているのはセキュリティ上の帰結ではなくプルリクエストの帰結とレビューのタイミングである——ここには、マージされたセキュリティ PR が正しかったのか、却下されたものがマージされるべきだったのかを立証するものは何もない。そして「セキュリティ関連」の特定は、PR の内容とデータセットのタグに対するルールベースのフィルタリングと人手の確認に依拠しているため、出現率の数値はセキュリティに関わる変更一般の尺度ではなく、セキュリティ関連と読める作業の下限である。
