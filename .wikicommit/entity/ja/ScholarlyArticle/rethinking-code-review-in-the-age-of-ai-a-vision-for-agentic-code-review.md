このビジョン論文は、アンカラ大学、Microsoft、ビルケント大学の著者らによるもので、AI コーディングアシスタントがコードの生産を加速させる一方で、そのコードが通過しなければならないレビューのパイプラインはほとんど変わっていない、という観察から出発する。こうした状況では、コードレビューはもはや生産性のボトルネックであるだけでなく、AI が生み出したコードの品質と説明責任を担う主要な制御面（control surface）であると論じる。また、個々のレビューステージを改善してきた先行研究は、ステージがツールの境界をまたぐコンテキストに依存しているため、それだけでは効果的なレビューへと組み合わさらないと主張している。

論文はまず、実践によって定義される 5 つの時代を通してコードレビューの歴史をたどる。アドホックなレビュー（1940 年代〜1960 年代）、形式的なインスペクション（1970 年代〜1990 年代）、軽量なピアレビュー（1990 年代〜2000 年代）、統合型コードレビュー（2000 年代〜2010 年代）、自動化支援型レビュー（2010 年代〜2020 年代）である。次に、従来のプルリクエストのワークフローをモデル化し、その課題を 4 つの領域に分類する。PR 作成（コンテキストの欠如、ドキュメントの欠如、イシューへのリンクの欠如）、レビュアーの割り当て、コードレビューそのもの（変更の理解、変更の影響、[[DefinedTerm/pr-issue-alignment]]、大きな差分、時間的なプレッシャー）、コメントの提供（有用性、感情、有害性）であり、そのうちいくつかを [[DefinedTerm/lgtm-smell]] と結びつけている。

論文が提案するのは、5 つのステージからなる AI 駆動のコードレビューフレームワークで、各ステージは LLM エージェントや従来のツールと、明示的なヒューマン・イン・ザ・ループの品質ゲートを組み合わせている。その後に、リスクと、実務者および研究者への示唆についての議論が続く。

## 要点

- 論文が挙げる 3 つの貢献は、AI によって加速されたコード生産は PR ベースのレビューの欠点を緩和するのではなく増幅すること、ステージ単位の改善だけではライフサイクル全体にわたる効果的なレビューを生み出せないこと、そしてレビューの有効性をライフサイクルの成果として扱うことを具体化する 5 ステージのフレームワークである。
- PR 作成：エージェントが PR のタイトルと説明文を生成し、イシューをリンクまたは作成し、自動化された一次レビューを実行して修正を提案する。作成者は提出前にドラフトを対話的に修正する。これは必須の人間による検証ステップである。
- PR 拡充：4 つの分析エージェント ── アラインメント分析、バグの起こりやすさの分析、サンドボックスでのランタイム分析、変更影響分析 ── が並行して動作し、要約エージェントがそれらの構造化された所見を、証拠への参照と確信度の指標を伴う主張へと統合する。矛盾は暗黙のうちに解消するのではなく、表面化させる。
- レビュアー選定では、LLM ではなく従来のレビュアー推薦手法を用いる。著者らはその理由を、計算効率とトークンコストのバランスに求めている。
- AI 支援コードレビューの中心は、レビュアーが自然言語で問いかける PR Review Agent と、関数やクラスといった論理的な単位を軸に変更を整理し、各単位をそれに関する分析レポートに結びつける「diff-map」である。このステージには、説明、自動レビュー、修正提案、有害性の測定、有用性の測定の各エージェントも含まれる。
- PR 振り返りは、人間向けと、後で機械が検索・取得するための両方を意図したレビューの要約を生成し、継続的なプロセス改善のためのレビュー指標を算出する。
- 提案されたワークフローでは、最終的なマージの権限は人間のレビュアーに残る。著者らは、レビュアーが手作業の検査者からエージェントを監督する運用者へと移行すると述べている。
- 議論では、ハルシネーションとコンテキストの劣化、プロジェクトをまたいだ汎化の限界、エージェント間での誤りの蓄積、評価の難しさ、透明性、説明責任、プライバシー、[[DefinedTerm/automation-bias]]、知識共有と暗黙的なメンタリングの劣化、そしてエージェントの誤りの連鎖による隠れた経済的コストといったリスクが挙げられ、後者に対しては確信度に基づくサーキットブレーカーが提案されている。

## 補足

このフレームワークは提案であって、実装や評価が行われたシステムではない。論文は結果ではなく研究課題を提示している。実務者に対しては、すべてのエージェントを一度に導入するのではなく、モジュール単位で段階的に導入すること、そしてフレームワークを社内プラットフォームとして扱うことを推奨している。また、将来の拡張の可能性として、動的なリスクベースのレビュールーティング（「ファストレーン」と「ハイリスクレーン」）を提示しつつ、誤分類がその主な危険であると警告している。研究者に対しては、人間と AI が混在する環境に向けたレビュー品質の再定義、レビューコメントの種類で層別化した評価、AI 支援レビューのインターフェース設計の研究、コンテキストの拡充、そして速度ではなくレビューの深さを捉える評価指標を求めている。論文のタイトルは、このレビューのビジョンを表すのに [[DefinedTerm/agentic-code-review]] という用語を用いている。
