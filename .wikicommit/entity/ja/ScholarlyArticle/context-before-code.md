この EASE 2026 の経験報告は、明示的なアーキテクチャ上の制約のもとで本番運用を想定した 2 つの AI
システムを構築する際に、対話的な「バイブコーディング」がどのように振る舞うかを検討している。1 つは
構造化されたメモリと厳格なテナント分離を備えたマルチプロジェクトのエージェント学習プラットフォーム、
もう 1 つは引用の追跡とロールベースのアクセス制御を備えた、ファイルを扱える学術向けの検索拡張生成
（RAG）システムである。どちらのシステムも Tampere University の小規模なフルスタックチームによって
開発され、テナント分離、非同期実行、制御された検索を含む要件は実装開始前に定義され、実装後には
構造化された手動テスト、コードインスペクション、実行時ログの分析によって検証された。

両システムを通じて、バイブコーディングは足場づくりと機能実装 — API ルート、シリアライズ用ユーティリ
ティ、インターフェースコンポーネント — を加速させたが、生成されたコードはプロンプトで明示されて
いないアーキテクチャ上の特性を一貫して十分に規定していなかった。初期のルートはデータベースクエリに
おけるプロジェクト単位のフィルタリングを欠いており（プロジェクトをまたいだデータアクセスの危険が
あった）、メモリ更新と埋め込みの処理は非同期という要件があったにもかかわらず当初は同期的に実行されて
おり、いずれも手作業での修正を要した。論文は、その結果としてエンジニアリングの労力がボイラープレートの
実装から、制約の規定、分離の監査、強制の検証へと移ったと報告し、対話的なコード生成が本番の信頼性に
とって不十分なままであった繰り返し現れるアーキテクチャ上の領域 — 論文はこれを「委任不可領域
（non-delegation zones）」と呼ぶ — を特定している。

## 要点
- バイブコーディングは両システムで定型的な足場づくり（API ルート、データベースモデル、UI コンポー
  ネント）を確実に加速させたが、アーキテクチャ上の特性 — テナント分離、アクセス制御、非同期処理 — は、
  それらの制約がプロンプトで明示されない限りほとんど保たれなかったと報告している
- エンジニアリングの労力に繰り返し見られる変化を特定している。ボイラープレートの記述、CRUD の足場
  づくり、基本的なルーティング、UI テンプレートへの労力は減り、アーキテクチャ設計、分離の監査、
  ポリシーの規定、検証・監視への労力は増えた
- アーキテクチャ上の「委任不可領域」という概念を提案している。これは、意図的な手作業によるアーキ
  テクチャ設計と検証なしには対話的なコード生成が確実に扱えないと著者らが見出した、繰り返し現れる
  領域（マルチテナンシー、アクセス制御、メモリポリシー、非同期処理）である
- バックグラウンドタスクのキューイングのようなインフラ上の決定は安全に先送りできなかったと報告して
  いる。推論と埋め込みを同期的に実行していた初期のプロトタイプは、繰り返し使用するうちに不安定に
  なり、バックグラウンドワーカーへ移さなければならなかった
- これら 2 つの事例に基づき、AI 支援開発はシステムレベルの設計を置き換えるものとしてではなく、明確に
  規定されたアーキテクチャ上の境界の内側で迅速に実装するためのツールとして最も効果的だと論じている

## 補足
- これは、フルスタックとインフラの経験を持つ小規模チームによる、2 事例の回顧的な経験報告である。
  著者らは、知見は広く一般化できる結論ではなく経験に基づく洞察であると述べ、自分たちが両システムの
  構築に関与していることを潜在的なバイアスの源として挙げている。著者らは、記憶ではなく観察可能な
  成果物（コミット履歴、実行時ログ、記録されたプロンプト）に分析を根拠づけることで、これを軽減しよう
  とした
- 統制された実験や、生産性・コード品質・欠陥率の定量的な測定は行われていない
