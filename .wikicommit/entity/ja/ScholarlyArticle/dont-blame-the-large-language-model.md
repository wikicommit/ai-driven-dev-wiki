「Don't Blame the Large Language Model」は、カナダのクイーンズ大学の4人の著者による実証ソフトウェアエンジニアリングの論文であり、2026年7月20日に arXiv へ投稿され、*ACM Transactions on Software Engineering and Methodology* へ投稿された。その主題は、*進化するソフトウェアシステム*としての [[DefinedTerm/agent-harness]] である——「開発者と大規模言語モデルの間に位置し、システムプロンプト、ツールの実行、コンテキスト管理、反復的な推論ループをオーケストレートするミドルウェア層」。

その方法論上の貢献は、通常の実験設定の反転である。先行研究がハーネスを固定してモデルを変化させるのに対し、この研究はモデルを固定してハーネスだけを変化させる。これによって品質の変化を、モデルの更新と混同することなくハーネスに帰属させられる。著者たちはこれを、ハーネスの寄与を切り分けた初の対照縦断研究であると述べ、特定の実践者の振る舞いからその動機づけを行っている。すなわち、ユーザーはハーネスの更新後に品質のリグレッションを日常的に報告するが、「一貫してそれをハーネス自体ではなく背後のモデルのせいにする」のである。

設計は2つの部分からなる。ランドスケープ分析は5つの主要なオープンソースのハーネス——Codex、Qwen Code、Gemini CLI、OpenCode、OpenHands——を扱い、リリース速度、開発活動、保守負担を、VS Code と GitHub CLI をベースラインとして測定する。次いで対照的な深掘りが、背後の LLM を一定に保ったまま、Qwen Code CLI の35の連続リリースを SWE-bench Verified（[[Dataset/swe-bench]] を参照）から層化抽出した50のタスクに対して評価する。このハーネスが選ばれたのは、カスタムのローカル LLM エンドポイントをネイティブにサポートしているからである。

## 主な貢献

- **ハイパーチャーン——ハーネスは通常のソフトウェアよりはるかに速く進化する。** 5つのハーネスは平均して週あたり 1.5〜18 リリース、1日あたり 2.8〜34 コミットであり、プルリクエストのレビュー時間の中央値は4時間未満である。同時期の VS Code と GitHub CLI は週あたり 0.6〜0.8 リリースであり——最も活発なハーネスはリリース集約度で 13〜28 倍ということになる。同論文はこのパターンを**ハイパーチャーン（hyper-churn）**と名づけている。同論文が特定する機構は、生のコミット量ではなく変換率である。エージェントハーネスは1リリースあたり平均でわずか 7〜14 コミットしか必要としないのに対し、VS Code は 421.4、GitHub CLI は 52.2 である。VS Code のほうが1日あたり 47.9 とコミット率は高いにもかかわらず、である。著者たちは、ほぼ即時のレビュー時間は「これらのプロジェクト自体がエージェントハーネスであることを考えれば、コードレビューにエージェンティック AI を使っていることを部分的に反映しているのかもしれない」と注記している。
- **イシューのバックログはクローズされるより増えていく。** Gemini CLI は 224 日間に 9,951 件のイシューを、OpenCode は 278 日間に 8,621 件を、Codex は 293 日間に 5,574 件を積み上げた。同論文が引く比較は、量ではなくクローズ率についてである。VS Code は12か月で 40,074 件のイシューを受けたが、月あたり平均 68 名の活発な貢献者からなる専任チームによってその 89.3% をクローズしており、GitHub CLI は 1,118 件を受けてクローズ率 82.1% であった。バグ修正のコミットは、これらのハーネス全体で開発工数のおよそ 30% を占める。
- **中心的な否定的結果。** モデルを固定した Qwen Code の35のリリースにわたって、**タスク解決率に統計的に有意な改善はない**——そして初期のバージョンが、より洗練された後継を上回ることさえある。その一方でトークン使用量とツール呼び出し数は、場合によっては倍以上になりながら、それに見合う向上を伴わない。著者たちはこれを「開発活動とエージェントの有効性との間の根本的な断絶」と呼んでいる。彼らはまた、失敗したタスクは成功したタスクより多くの資源を消費することも報告し、トークンの膨張を、より大きなシステムプロンプトがより多くの会話ターンと複合することに帰している。
- **どのリリースのパターンが品質を動かすか。** 機能中心のリリースは高い解決率と有意に相関する（ρ = 0.438）が、トークン消費とツール呼び出しの増加という代償を伴う。修正中心のリリースは解決率を改善せずにトークン消費を上げる。プルリクエストの平均サイズが大きいリリースは*低い*トークン消費と相関しており、著者たちはこれを、変更をまとまりのある PR へ統合するほうが、多数の小さな PR よりオーバーヘッドが少なくて済むためと読んでいる。そしてコード削除量が多いことは低いトークン消費と関連づけられる。リファクタリングのチャーン比率とリリース頻度には品質上の便益は見られない。
- **どの構成要素に触れるのが危険か。** すべてのコミットを参照用のハーネスアーキテクチャへ写像し、同論文は **LLM プロバイダ層**と**コンテキスト管理**を、その変更が品質劣化と最も頻繁に関連づけられる高リスク領域として特定している。著者たちの説明は、これらが情報のモデルへの出入りを直接に統べているからだというものである。**拡張性**と**セキュリティ**の構成要素への変更は、一貫して安全ないし中立な結果と関連づけられる。とくにコンテキスト管理の拡張は、低いトークン効率と関連づけられる。
- **欠けているとされる実践。** 同論文は以上のすべてを、**エージェンティックな品質保証**の不在に帰している。すなわち、生成されたパッチの正しさを検証するだけでなく、エージェントの実際の非機能品質——トークン消費、ツール呼び出しのオーバーヘッド——を評価する自動的な品質リグレッションテストである。その裏づけとなる証拠は、これらのプロジェクトの CI/CD パイプラインを検査したところ、「われわれが記録した品質劣化の具体例はすべて、既存の自動チェックをすべて通過していた」ことである。その推奨は、開発者はリリースにわたって解決率、トークン消費、ツール呼び出しのオーバーヘッドを監視すべきであり、研究者は「背後の LLM と並んでエージェントハーネスのバージョンを報告し統制すべきである」というものである。

## 注記

この実践がまだ存在しない理由として同論文自身が述べているのはコストである。活発に開発されているプロジェクトのコミットの頻度で代表的な評価を回すのは高くつく。これはまた、同論文が記録するリグレッションが従来の単体テストや結合テストには見えない理由でもある。それらは「エージェントハーネスと LLM の相互作用から創発する振る舞い上の効果」だからである。

否定的結果を読むにあたって、2つの境界を視野に入れておく価値がある。対照的な深掘りは、1つのハーネス（Qwen Code CLI）を1つのモデルファミリーと50の層化された SWE-bench Verified のタスクで扱っているため、改善なしという知見はその構成について確立されたのであって、ハーネス横断的にではない。5つのハーネスを扱うランドスケープ分析が確立するのは開発集約度の像だけであり、品質の像ではない。そしてバグ修正のベンチマークにおける解決率は、品質の狭い定義である——[[Dataset/swe-bench]] に記録された、テスト通過をマージ可能性の代理指標とすることについての注意はここにも当てはまる。

それでもこの知見は、[[DefinedTerm/harness-engineering]] の背後にある前提——エージェントの振る舞いの大きな部分が決まるのはモデルではなくハーネスにおいてである——への、利用可能な最も鋭い実証的裏づけであり、同時に新しいハーネスのほうが良いという想定を切り崩すものである。
