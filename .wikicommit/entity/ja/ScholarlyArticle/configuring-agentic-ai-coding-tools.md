開発者がバージョン管理されたリポジトリレベルの成果物を通じてエージェンティック AI コーディングツールをどう設定しているかについての探索的研究。著者らは [[SoftwareApplication/claude-code]]、[[SoftwareApplication/github-copilot]]、[[SoftwareApplication/cursor]]、[[SoftwareApplication/codex-cli]]、[[SoftwareApplication/gemini-cli]] にまたがる8つの設定メカニズムを体系的に記録し、次いでそれらのメカニズムが 2,926 の GitHub リポジトリにおいて採用されているか、またどのように採用されているかを検討している。

本論文は*設定メカニズム*を、開発者がツールとエージェントの振る舞いをプロジェクトやワークフローに合わせて調整する手段として定義し、*設定成果物*をそのメカニズムの具体的な仕様——実際の Markdown または JSON ファイル——として定義する。著者らはこれを、これらのメカニズムとその採用パターンについての初のツール横断・エージェント横断の対応づけとして提示している。先行する実証研究は、単一の成果物の種類を切り離して、最も多くはリポジトリレベルのコンテキストファイルに焦点を当てていたと彼らは指摘する。

## 主な貢献

- **8つの設定メカニズムのカタログ**。5つのツールのドキュメントから特定されたものである。[[DefinedTerm/context-files]]、[[DefinedTerm/agent-skills]]、[[DefinedTerm/subagents]]、Commands、Rules、Settings、Hooks、そして MCP サーバ。5つのツールすべてで利用できるものもあれば、ツール固有のものもある。
- **2,926 リポジトリにわたる採用分析。** コンテキストファイルが支配的であり、しばしばそこにある唯一の設定メカニズムである。Rules、Settings、Commands、Skills、Subagents はいずれも 20% 未満のリポジトリにしか現れない。Claude Code のリポジトリが最も広い設定のフットプリントを示す一方、Cursor のプロジェクトは Rules と Commands を重視し、Copilot と Codex のリポジトリはコンテキストファイルを超えることがまれである。
- **3つのツール横断メカニズムの詳細な検討。** コンテキストファイルのなかでは [[DefinedTerm/agents-md]] が相互運用可能な標準として立ち現れており、最も強く観測されたパターンは CLAUDE.md が AGENTS.md を指し示すというものである。Skills と Subagents の採用は浅い。中央値のリポジトリはいずれも2つを定義しており、見つかった 601 の Skills のうち 83.3% は追加のリソースを含んでいなかった。リソースがある場合も、実行可能なスクリプトより静的なドキュメントの方が一般的であった。
- **これらの知見から導かれた実践者への指針。** コンテキストファイル、とりわけ AGENTS.md が最も摩擦の少ない入口である。複数のツールを使うチームは AGENTS.md を共有の設定ベースラインと見なし、ツール固有のファイルはそれを参照するアダプタとして機能させることを検討すべきである。そして実行可能な Skills は、期待される便益が追加のセットアップの手間を正当化する場合にのみ、意図的に採用すべきである。

## 注記

本研究のサンプリングのパイプラインは、SEART に基づく選定——フォークでなく、コントリビュータが2人以上、ライセンスがあり、2024年1月1日より前に作成され、2025年6月1日以降のコミットがある GitHub リポジトリを、言語と活動度でフィルタしたもの——から始まり、37,249 のリポジトリが得られた。利用できないリポジトリ、README のないもの、そして README が英語でない 994 件を除外したのち、GPT-5.2 に基づく分類パイプラインが残りのうち 32,564 を「エンジニアリングされた」ソフトウェアプロジェクトとしてラベル付けし、次いでファイルパスのヒューリスティクスによって5つのツールのいずれかを使う 2,926 件が特定された。

著者らはいくつかの限界を率直に述べている。彼らのヒューリスティクスが検知するのは設定成果物の存在であって、対応するツールが実際に使われているかどうかではないため、成果物の存在は採用の代理指標にとどまる。GitHub Copilot、Cursor、Gemini については、検知されたファイルが会話モードとエージェントモードの双方に適用されるため、エージェント的な利用だけを切り分けることはできない。リポジトリの分類はモデル間の一致を取らない単一のラベリング実行によるものであり、「判定不能」の 2,204 件は除外された。本研究は OSS の GitHub リポジトリのみを対象としており、その知見は2026年2月時点のスナップショット——確定した知見ではなく初期の実証的なシグナル——として記述されている。
