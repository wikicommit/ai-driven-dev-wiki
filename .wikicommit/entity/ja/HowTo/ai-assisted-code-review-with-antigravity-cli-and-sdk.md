Google Codelabs のチュートリアルに基づくこの手順は、エージェントが書いたコードのレビュアーとして Antigravity を使う 2 つの方法を構築する。1 つは [[SoftwareApplication/antigravity-cli]] によるフィーチャーブランチの対話的なレビュー、もう 1 つは [[SoftwareApplication/antigravity-sdk]] で構築し CI で実行するエージェントによる、すべてのプルリクエストの自動レビューである。このチュートリアルの前提は、[[DefinedTerm/vibe-coding]] では開発者がコードを書くのではなく承認するため、動作するコードが十分なセキュリティレビューを経ずにマージされうる、というものである。しかも、すべての行を読むことにすれば、そもそもバイブコーディングを行う動機であったスピードを手放すことになる。

## 前提条件

- Google Cloud アカウントと GitHub アカウント。ターミナル、バージョン管理、CI/CD についての基本的な知識。
- レビュー対象のリポジトリ。チュートリアルでは、デモ用の CRM アプリのフォークを使う。このアプリには、意図的に脆弱性を含む 2 つのフィーチャーブランチがある。脆弱性とは、文字列連結で組み立てられた SQL、入力検証の欠如、ハードコードされた管理者の認証情報、認証のない管理用エンドポイント、そしてパストラバーサルのリスクである。
- インストールと認証を済ませた Antigravity CLI（`agy`）。チュートリアルでは、プリインストールされている Cloud Shell を使う。
- SDK エージェント用の Gemini API キー。

## 手順

### CLI による対話的なレビュー

1. レビュー対象のフィーチャーブランチをチェックアウトする。
2. `npx skills add addyosmani/agent-skills --skill code-review-and-quality -y` で、コードレビュー用のエージェントスキル（[[DefinedTerm/agent-skills]] を参照）をワークスペースにインストールする。スキルは `.agents/skills/` に配置されるため、リポジトリと一緒にコミットし、CI を含め、そのリポジトリで作業する全員で共有できる。
3. CLI を起動し、`/skills` でスキルが一覧に表示されることを確認する。チュートリアルは時間を節約するために `--dangerously-skip-permissions` を付けて起動しているが、このフラグはあらゆる操作を許可してしまうと警告している。
4. `main` と現在のブランチとの差分をレビューし、指摘事項と修正計画を `code_review.md` に書き出すよう、ただしまだ修正は適用しないようエージェントに依頼する。エージェントは該当するスキルを自ら選び出して使う。
5. 指摘事項と計画を読み、提案された修正を適用するようエージェントに依頼する。
6. アプリを実行して引き続き動作することを確認し、動作しなければエージェントと反復してから、コミットする。

### SDK による自動レビュー

1. レビュー対象のブランチをチェックアウトし、`uv` でレビューエージェント用の Python プロジェクトを作成して、`google-antigravity` パッケージを追加する。
2. 同じレビュー用スキルをインストールし、エージェントのプロジェクトにコピーする。これにより、SDK が `skills_paths` 設定を通じてスキルを読み込めるようになる。
3. レビューエージェントを書く。チュートリアルのエージェントは、デフォルトですべてのツールを拒否し、ファイル読み取り用のツール、`run_command`、`finish` だけを許可する。さらに、ツール呼び出し前のフックが `git` で始まらないコマンドをすべてブロックし、ツール呼び出し後のフックが監査のために各ツールの結果をログに記録する。システム指示ではファイルを決して変更しないと定め、レスポンススキーマによって構造化された指摘事項（ファイル、行、重大度、カテゴリ、説明、修正案）を返させる。エージェントはそれを Markdown として `code_review.md` に書き出す。
4. API キーを環境変数に設定した状態で、ブランチに対してエージェントをローカルで実行し、出力を確認する。
5. プルリクエストが作成または更新されたときに実行される GitHub Actions のワークフローを追加する。このワークフローは、エージェントが `git diff main...HEAD` を実行できるよう全履歴をチェックアウトし、エージェントを実行して、`code_review.md` をプルリクエストのコメントとして投稿する。
6. API キーを `GEMINI_API_KEY` という名前のリポジトリシークレットとして保存し、ブランチをプッシュして、自分のフォークに対してプルリクエストを作成する。ワークフローがレビューをコメントとして投稿する。

## 補足

- チュートリアルは、エージェントスキルを、インストールするとスラッシュコマンドになる宣言的な Markdown ファイルであり、エージェント間で移植でき、Git を通じて共有できるものと説明している。Antigravity CLI のワークスペーススキルは `.agents/skills/` に、グローバルスキルは `~/.gemini/config/skills/` に置かれる。チュートリアルでインストールするスキルは、正しさ、可読性、アーキテクチャ、セキュリティ、パフォーマンスの 5 つの軸でレビューを行い、指摘事項に重大度のラベルを付ける。チュートリアルはこれを一例として挙げており、唯一の選択肢とはしていない。
- そもそもスキルを使う理由として挙げられているのは再現性である。スキルがなくても CLI はレビューを行えるが、その場合は一般的な学習知識に頼ることになり、セッションごとに一貫しない基準を適用するおそれがある。
- SDK エージェントにおける強制は 2 つの層にある。フレームワークレベルのポリシーと、2 つ目のチェックとしてのフックである。また、チュートリアルはレビューの範囲をコードベース全体ではなくブランチの差分に限定している。
- ワークフローのトリガーは、たとえば特定のパスに絞り込むことも、オンデマンドでレビューするために `/review` のようなコメントコマンドに切り替えることもできる。
- 後片付けの際、2 つ目のフィーチャーブランチのプルリクエストは、修正されていない脆弱なコードがまだ含まれているため、マージしないようチュートリアルは警告している。
