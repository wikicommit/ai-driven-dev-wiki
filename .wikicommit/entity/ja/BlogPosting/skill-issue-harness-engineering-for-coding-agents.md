「Skill Issue: Harness Engineering for Coding Agents」は、2026年3月12日に HumanLayer のブログで公開された記事であり、著者は Kyle とのみ記されている。その前提はチーム自身の経験に由来する。コーディングエージェントが「考えうるあらゆる形で——指示を無視し、頼まれてもいない危険なコマンドを実行し、ごく単純なタスクで堂々巡りをして——」失敗するのを1年にわたり眺め、数十のプロジェクトと数百のセッションを経て、彼らはこう結論した。「これはモデルの問題ではない。**設定の問題**である」。

本記事は、これがモデルの改善が止まるという主張ではないことを明言している。その論旨は、予期せぬ失敗モードは非決定的なシステムにとって本質的なものであり、モデルが賢くなるほどより大きく難しい問題が与えられ、予期せぬ形で失敗し続けるだろう、というものだ。だからこそ有用な問いは、どの未来のモデルが解決してくれるかではなく、今日のモデルからどう最大限を引き出すかになる。タイトルがそのオチである。「モデルはおそらく問題ない。ただのスキルイシューだ」。

構成としては設定面をめぐる巡回であり、それぞれについて何がうまくいき何がうまくいかなかったかというチーム自身の知見が添えられる。測定ではなく一実践者チームによる自らのワークフローの報告として読めるものであり、本記事自身もそう述べている。末尾の節は、試して手放したものの率直な一覧である。本記事が展開する枠組みの概念が [[DefinedTerm/harness-engineering]] である。

## 要点

- **まずコンテキストファイル、しかも短く。** 本記事は、[[DefinedTerm/context-files]] はたいてい何よりも先にカスタマイズする価値があると論じる。決定的にシステムプロンプトへ注入されるからだ。本記事が要約するチューリッヒ工科大学の研究——さまざまなリポジトリにわたる138のエージェントファイルを検証し、LLM が生成したものは20%以上のコスト増を伴いながら性能を積極的に損なうこと、人間が書いたものでも改善は約4%にとどまること、エージェントはコンテキストファイルの指示を処理するのに14〜22%多くの推論トークンを費やし、解決率を改善しないままステップ数を増やすこと、そしてコードベースの概観やディレクトリ一覧は、エージェントが自力で構造を発見するため役に立たなかったこと——への応答は、この研究は自分たちの以前の助言を反駁するのではなく裏づけている、というものだ。すなわち、ファイルの自動生成を避けよ、指示は合理的に可能な限り少なくせよ、プログレッシブディスクロージャーを使え、内容は簡潔かつ普遍的に適用可能なものに保て。自分たちのファイルは60行未満だと報告している。
- **MCP サーバーはツールのためのものであり、数は少なく。** 本記事は、実務において [[DefinedTerm/model-context-protocol]] はツールを差し込むために使われていると述べる。仕様にあるリソース、プロンプト、エリシテーションは「MCP クライアントやコーディングエージェントのハーネスに概してあまりよくサポートされていない」からだ。ツールの説明文がシステムプロンプトに注入されることの帰結を2つ指摘している。プロンプトインジェクションのリスクである——信頼していないサーバーには決して接続してはならない（加えて、STDIO サーバーや `npx`・`uvx` 経由でクライアント側で動くものは、いずれにせよホスト上でコードを実行しうる点にも注意）。そしてコンテキストのコストである——ツールが多すぎるとウィンドウが説明文で埋まる。本記事は Anthropic の実験的な MCP ツール検索を、この失敗モードが製品としての対応に値するほど一般的であることの証拠として引き、多数のツールを露出する未使用のサーバーはオフにするよう助言する。
- **CLI があるなら MCP サーバーより CLI を選べ。** チームの知見は、MCP サーバーが、訓練データによく表れている CLI としてすでに利用可能な機能——GitHub、Docker、たいていのデータベース——を重複させている場合、CLI を使うようエージェントにプロンプトするほうがうまくいく、というものだ。モデルはすでにそのツールを知っており、出力は `grep` や `jq` と組み合わせられるからである。彼らの実例は、Linear の MCP サーバーを Linear API をラップする小さな CLI に置き換え、コンテキストファイルに6つの実行例として記述したことであり、これによってツール定義の数千トークンに加え、冗長な MCP のレスポンス分もさらに節約できたと報告している。
- **スキルは再利用可能な知識のためのものであり、オンデマンドで読み込まれる。** [[DefinedTerm/agent-skills]] についての本記事の説明は、自らの失敗から出発した [[DefinedTerm/progressive-disclosure]] の議論である。あらゆる指示とツールをシステムプロンプトに詰め込んだ結果、エージェントは悪化し、作業が始まる前に指示の予算を使い果たしてしまった。起動の仕組みは具体的に述べられている。`SKILL.md` はユーザーメッセージとしてコンテキストウィンドウに読み込まれ、それがどのディレクトリ由来かがエージェントに伝えられる。そのためスキルファイルは同梱の他のファイルを指し示し、いつそれを読むべきかを述べることができる。また、MCP サーバーやカスタムツールをスキルに直接同梱できないというパッケージング上の制約にも触れており、それらは実行ファイル、CLI、あるいはパッケージとして配布しなければならない。さらに、スキルのレジストリがすでに数百もの悪意あるスキルを配布していた事例が見つかっていること、そしてレジストリはマシン上で任意のコードを実行しうるため、スキルは `npm install random-package` と同じように扱うべきだと警告している。
- **サブエージェントはペルソナではなくコンテキスト制御のためのものである。** 本記事は、役割ベースのサブエージェント——「フロントエンドエンジニア」「バックエンドエンジニア」「データアナリスト」——はうまくいかなかったと報告し、うまくいくのは [[DefinedTerm/subagents]] を**コンテキストのファイアウォール**として使うことだと述べる。呼び出し元のエージェントが見るのは自分が書いたプロンプトと最終結果だけであり、途中のツール呼び出しやその結果は一切そのウィンドウに入らない。良い用途として挙げられるのは、定義の場所を特定すること、コードベースのパターンを同定すること、サービス境界をまたぐ情報の流れを追跡すること、そして一般的な調査であり——いずれも答えは単純だが途中の呼び出しが多いタスクである。彼らの流儀では、サブエージェントは自らもプログレッシブディスクロージャーに従った凝縮された答えを返し、出典を `filepath:line` や URL として引用することで、親が必要なときにだけ詳細を取りに行けるようにする。サブエージェントは彼らにとってコスト管理の役割も果たす。親の計画とオーケストレーションには高価なモデルを、各サブエージェントにはより安価で高速なモデルを使う。
- **コンテキストウィンドウを広げることは解決策ではない。** 本記事は拡張コンテキストのモデルに懐疑的である。拡張コンテキスト版のリリースはたいてい、指示の予算が増えたわけではなく、系列長を伸ばす数学的処理を施した同じモデルだからだ。「コンテキストウィンドウが大きくなっても、モデルが針を見つけるのがうまくなるわけではない。干し草の山が大きくなるだけだ」。その代替として示されるのが構造的なコンテキストの隔離である。各サブエージェントが新鮮で小さく関連度の高いウィンドウを得て、凝縮された結果だけが戻ってくる。こうして多数のコンテキストウィンドウを一つの問題のために縫い合わせられる。ハーネスにサブエージェントのネイティブサポートがない場合については、新しいエージェントのセッションを起動して最終メッセージを返す MCP サーバーを書くことが説明されている——ただし、これをネイティブのサブエージェントと組み合わせると、サブエージェントが MCP を通じてさらにサブエージェントを呼び出せてしまうこと、そしてハーネスの MCP ツール呼び出しのタイムアウトを引き上げる必要があるかもしれないことが警告されている。
- **フックは制御フローのためのものである。** 本記事は [[DefinedTerm/agent-hooks]] を概念的に git のフックに近いものと説明し、チームが頼りにしている4つの用途を挙げる。エージェントが完了したとき、あるいは承認が長く保留されすぎているときの通知。デフォルトのパーミッションモデルよりも表現力のあるルールとして表される承認——その例として、マイグレーションを実行しようとする `Bash()` の呼び出しを自動的に拒否し、代わりにユーザーに尋ねるよう指示することが挙げられる。Slack へのメッセージ送信、GitHub の PR 作成、プレビュー環境の用意といった統合。そして検証——数秒で完了するなら、エージェントが停止するたびに型チェックやビルドを実行する。その実例は、フォーマッタと TypeScript の型チェックを実行する Stop フックである。成功時は沈黙し、失敗時はエラーのみを終了コード `2` とともに表面化させる。これはハーネスに対して、エラーが解消されるまでエージェントを再度動かすよう伝えるものだ。
- **バックプレッシャーは最もレバレッジの高い投資であり、コンテキスト効率が良くなければならない。** 本記事は、コーディングエージェントで問題を解決できる見込みは、エージェントが自らの作業を検証できる能力と強く相関すると述べ、リポジトリに [[DefinedTerm/backpressure]] を組み込むことをチームが時間を費やしたなかで最もレバレッジの高いことの一つに挙げる。その仕組みは、型チェックとビルド、ユニットテストと結合テスト、カバレッジが下がったときにエージェントを促す Stop フックを伴うコードカバレッジのレポート、そして UI の操作テストである。効率という制約は、ある具体的な失敗から来ている。変更のたびにテストスイート全体を実行したところ、成功したテストの4,000行がウィンドウを埋め尽くし、その後エージェントはタスクを見失い、たった今読んだばかりのテストファイルについて幻覚を起こし始めた。彼らの対処は、出力を飲み込んでエラーのみを表面化させることであり、テストだけでなくビルドについても同様にした——成功は沈黙、失敗は饒舌に。

## 背景

本記事は、直接名指しした2つの隣接概念に対して自らを位置づけている。ハーネスエンジニアリングをコンテキストエンジニアリングの部分集合として扱い、後者を著者の共同創業者である Dex Horthy に帰し、補完的な枠づけとして Viv の2本の記事を挙げる——一方は4つのカスタマイズのレバーを導き、他方はモデルがネイティブにはできないことから逆算するものである。また、このテーマについての OpenAI の記事を、バックプレッシャーと検証を中心に据えたより狭い見方を取るものとして読んでいるが、その読み方自体への自らの不確かさも表明している。

実証的な引用は、研究そのものではなく二次的な要約である。チューリッヒ工科大学のエージェントファイル研究と、Chroma のコンテキストロットの研究であり、後者については18のモデルを needle-in-a-haystack（干し草の山から針を探す）タスクで検証し、コンテキスト長が増えるにつれて性能が劣化すること、そして質問と関連情報の意味的類似度が低いときに劣化がより急峻になることを見出したと報告している。本記事は、needle-in-a-haystack の研究が「エージェンティックコーディングとはかなり異なることは認める」と率直に述べ、この知見を証明としてではなく自らの経験と符合するものとして提示している。
