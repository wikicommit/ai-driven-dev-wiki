「Context Engineering」は、LangChain チームが 2025年7月2日に公開した記事である。その整理上の貢献は、[[DefinedTerm/context-engineering]] の戦略を4つに分類する枠組み——**書く（write）、選ぶ（select）、圧縮する（compress）、分離する（isolate）**——にあり、これは著名なエージェント製品と論文のレビューから組み立てられている。記事の後半は、この各分類を [[SoftwareApplication/langgraph]] の機能に対応づけることに充てられている。

冒頭では Andrej Karpathy に帰される比喩が示される。LLM は新しい種類のオペレーティングシステムのようなもので、モデルが CPU、コンテキストウィンドウが RAM にあたる、というものだ。そして彼によるコンテキストエンジニアリングの説明、「次のステップにちょうど適した情報でコンテキストウィンドウを満たす、繊細な技芸であり科学」が引用される。記事は管理すべきコンテキストを、指示（プロンプト、メモリ、少数事例（few-shot）、ツールの説明）、知識（事実とメモリ）、ツール（ツール呼び出しからのフィードバック）に分けている。

これはベンダーによる記事である。分類は実践者が実際に行っていることの調査として提示されるが、後半は LangGraph の設計が各分類を支えているという論証になっている。

## 要点

- **なぜ重要か。** 長時間にわたるタスクと蓄積されていくツールのフィードバックによって、エージェントは大量のトークンを使う。これはコンテキストウィンドウを超過させたり、コストとレイテンシを膨らませたり、性能を劣化させたりしうる。記事は Drew Breunig の文章から4つの名前付き失敗モードを伝えている。コンテキスト汚染（context poisoning、ハルシネーションがコンテキストに入り込む）、コンテキスト散漫（context distraction、コンテキストが学習内容を圧倒する）、コンテキスト混乱（context confusion、余計なコンテキストが応答に影響する）、コンテキスト衝突（context clash、コンテキストの各部分が食い違う）である。[[DefinedTerm/context-rot]] を参照。
- **書く（Write）:** コンテキストウィンドウの外にコンテキストを保存すること。スクラッチパッドはタスクの実行中に情報を保持し、ファイルに書き出すツールとして、あるいは実行時状態オブジェクトのフィールドとして実装される。メモリはセッションをまたいで持続する。記事は、エージェントの各ターンの後に振り返り、自ら生成したメモリを再利用するという Reflexion の考え方と、過去のフィードバックからメモリを定期的に統合する Generative Agents を引き、ChatGPT、Cursor、Windsurf がいずれも長期メモリを自動生成していることに触れている。[[DefinedTerm/agentic-memory]] を参照。
- **選ぶ（Select）:** コンテキストをウィンドウに引き込むこと。エピソード記憶（少数事例）、手続き記憶（指示）、意味記憶（事実）というメモリの型を区別し、多くのコードエージェントが、常に絞り込まれた一群のファイルを読み込むことで選択の問題を回避していると指摘する——Claude Code の `CLAUDE.md`、Cursor と Windsurf のルールファイルが名指しされている。また、あまりに多くのツールでエージェントを過負荷にしないためのツール説明に対する RAG も扱い、Windsurf の Varun による、コードのインデックス作成はコンテキスト検索と同じではなく、コードベースが大きくなるにつれ埋め込み検索は当てにならなくなるという発言を伝えている。
- **圧縮する（Compress）:** 必要なトークンだけを残すこと。エージェントの軌跡全体にわたる要約——記事は身近な例として Claude Code の自動コンパクト動作を挙げる——に加えて、トークンを多く消費するツール呼び出しの後や、エージェント間の境界といった特定の地点で適用される要約がある。トリミングは、モデルによってではなくヒューリスティックによってフィルタや刈り込みを行うものとして、要約と区別されている。[[DefinedTerm/compaction]] を参照。
- **分離する（Isolate）:** コンテキストを分割すること。それぞれが自分のツール、指示、コンテキストウィンドウを持つサブエージェントへの分割が、最も広く用いられているアプローチとして説明される。記事は、隔離されたコンテキストを持つ多数のエージェントが単一のエージェントを上回ったという Anthropic の報告を、その代償——チャットの最大15倍のトークン、サブエージェントの作業を計画するための入念なプロンプトエンジニアリング、そして調整のオーバーヘッド——とあわせて伝えている。さらに、サンドボックス内で動作する HuggingFace の CodeAgent を例に、実行環境にコンテキストを分離すること、そして実行時状態オブジェクトのフィールドに分離することも扱っている。[[DefinedTerm/multi-agent-orchestration]] を参照。
- **まず計測せよ。** これらを適用する前に、自分のデータを見てトークン使用量を追跡する手段と、コンテキストエンジニアリング上の変更が効いているのか害になっているのかを検証する手段を持つべきだ、と記事は助言する。

## 背景

本記事は、このテーマについて広く読まれた2025年の2つの論考のうちの一方であり、両者は両立するが整理の仕方が異なる説明にたどり着いている。[[TechArticle/effective-context-engineering-for-ai-agents]] は同じ問題を有限の「アテンション予算」を軸に枠づけ、長い時間軸に向けた技法をコンパクション、構造化されたノートテイキング、マルチエージェントアーキテクチャとして分類する。あちらがモデルの挙動から論じるのに対し、こちらは実際に出荷されているエージェントが何をしているかの調査から論じており、その4つの分類は、モデルの仕組みについての主張としてではなく、既存の実践を整理するためのカテゴリとして提示されている。

記事の中で最も強い主張のいくつかは他所から伝えられたものである——コンテキストエンジニアリングは「AI エージェントを構築するエンジニアにとって事実上第一の仕事だ」という Cognition の断言、Anthropic のマルチエージェントの結果、Breunig の失敗モード、そしてスクラッチパッドとメモリの背後にある諸論文——。記事はそれぞれ自ら立証するのではなく、リンクを張っている。
