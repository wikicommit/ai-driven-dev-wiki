「Improving agent with semantic search」は、[[Organization/anysphere]] のブログの *research* カテゴリに掲載された、2025年11月6日付で Stefan Heule、Emily Jia、Naman Jain によって書かれた記事である。その主張は、[[DefinedTerm/semantic-search]] は字句検索を置き換えるのではなく、それと並んでコーディングエージェントのツールセットの中に位置を占めるに値する、というものであり、同社自身のオフライン評価とオンライン A/B テストによってその点を論じている。

## 要点

- 前提の枠組み。コーディングエージェントがプロンプトを受け取ったとき、うまく答えるにはファイルを読み検索することでコードベースの理解を組み立てる必要がある。セマンティック検索は、grep のようなツールによる正規表現ベースの検索に加えて、自然言語のクエリに合致するコード断片を取得する——挙げられている例は「認証はどこで扱っているか？」である。
- Cursor は自社の埋め込みモデルを学習させ、高速な検索のためのインデックス作成パイプラインを構築したと報告している。
- セマンティック検索を追加したことによる主要な主張は次のとおり。質問への回答の正確性が平均 12.5% 向上（モデル別では 6.5%〜23.5% の幅）、コード変更がコードベースに残される割合の上昇、ユーザーが正しい解に到達するまでの反復回数の減少、そしてテストしたすべてのモデル——フロンティアのコーディングモデルすべてを含む——で正確性が改善したこと。
- オフライン評価は [[Dataset/cursor-context-bench]] 上で実施された。これは、正解が既知のコードベース内情報検索のために同社が維持している評価用データセットであり、自社の Composer を含む Cursor で最もよく使われているモデル全体にわたって行われた。比較はモデルを固定し、利用可能なツールにセマンティック検索が含まれるかどうかだけを変えるもので、Cursor はすべての構成においてセマンティック検索が結果を有意に改善したと述べている。
- オンライン A/B テストでは両グループに同じモデルを与え、片方のグループのエージェントだけがセマンティック検索を使えるようにした。報告された効果はより小さく、コードの残存率は 0.3% 上昇（1,000 ファイル以上のコードベースでは 2.6% まで上昇）、セマンティック検索がない場合に不満を示すユーザーの追加リクエストが 2.2% 増加した。記事はこの効果の小ささを、テストが検索を要するクエリだけでなくエージェントへの全クエリを対象にしていたためだとしている。
- 独自の検索モデルは、汎用的なコード類似度ではなくエージェントのセッションから学習されている。エージェントは正しいコードにたどり着くまでに複数回の検索を行い、いくつものファイルを開くため、そのトレースは事後的に、もっと早い段階で何を取得すべきだったかを明らかにする。各ステップでどの内容が最も役に立ったはずかを LLM がランク付けし、埋め込みモデルはその類似度スコアをこのランキングに整合させるよう学習される。

## 背景

記事の結論は、二方向に意図的に留保が付けられている。セマンティック検索は「特に大規模なコードベースにおいて、最良の結果を得るために現時点では必要である」——これは恒久的なものではなく現在についての主張である——と述べ、また Cursor のエージェントは「セマンティック検索と同様に grep も多用しており、この2つの組み合わせが最良の結果をもたらす」としており、字句検索が時代遅れだと論じてはいない。締めくくりでは、モデルの改善に伴い、エージェントハーネスに与えるすべてのツールを引き続きテストし評価していくと述べている。

ここに示された数値はすべて Cursor 自身のものであり、Cursor 自身のベンチマークとユーザーベースで、Cursor が販売している機能について測定されたものである。この情報源の中では、そのいずれも独立に再現されてはいない。外部的により意味を持つのは A/B テストの結果のほうであり、そしてそれは同時に、より小さいほうの結果でもある。
