GitHub のブログに掲載された 2026 年 6 月 9 日付の記事で、[[SoftwareApplication/github-copilot-cli]]から使う[[DefinedTerm/github-copilot-custom-agents]]を紹介している。出発点は、ターミナルで積み重なっていく摩擦——同じコマンドを何度も実行し直すこと、コンテキストを何度も説明し直すこと、ログをチームが対処できる形に翻訳すること——であり、記事の提案は、チームのコンテキストを Markdown のエージェントプロファイルに一度だけ書き込んでおくことで、繰り返し行うタスクを単発のプロンプトから始めるのではなく、毎回同じやり方で実行できるようにすることである。

記事の大部分は 4 つのエージェントプロファイルの例で占められている。いずれも、エージェントの名前、説明、使用してよいコマンドラインツールの一覧を記した YAML フロントマターと、それに続く指示からなる Markdown ファイルであり、セキュリティ監査エージェント、Infrastructure as Code のコンプライアンスエージェント、リリースノートエージェント、インシデント対応エージェントの 4 つである。記事は、パートナー製のエージェントを使うべき場合と自分で書くべき場合についての指針で締めくくられている。

## 要点

- カスタムエージェントとは、どのように動作するか、どのツールを使えるか、どの基準に従うか、どのような出力を生成するかを記述した Markdown のエージェントプロファイルによって定義される Copilot エージェントであり、どこで実行されてもその振る舞いが一貫する。
- Copilot CLI では、カスタムエージェントは、`.agent.md` で終わり YAML フロントマターを持つ Markdown ファイルであるエージェントプロファイルを、対象リポジトリの `.github/agents` ディレクトリに追加することで作成され、`/agent` スラッシュコマンドで呼び出される。
- プロファイルはリポジトリ内のファイルなので、レビュー、バージョン管理、共有ができる。記事によれば、それによって同じ期待が CLI から IDE へ、さらに GitHub 上のプルリクエストへと作業に付いていく。
- 記事は、Copilot CLI はすでにスクリプトを実行し、API を呼び出し、リポジトリを直接扱うため、エージェント駆動の作業に適しており、実行中心のワークフローを一度エンコードしてターミナルから呼び出せるとしている。
- 例として示されたプロファイルには共通のパターンがある。明示された目標、動作ルール、実行するチェックやコマンド、そして固定された出力形式である——たとえば、セキュリティ監査では重大度ごとにまとめたプルリクエストにそのまま使えるチェックリスト、Infrastructure as Code のレビューではリスク評価付きの承認に使える要約である。
- いくつかの例では、ツールが見つからない場合やデータが利用できない場合には結果をでっち上げるのではなく欠落として報告すること、また出力からシークレットや認証情報を伏せることをエージェントに指示している。
- GitHub は JFrog、Dynatrace、Octopus Deploy、Arm などのパートナーと共同で構築した既製のエージェントを提供している。記事は、スピードとツール固有のベストプラクティスを求めるならそれらを、チームが自らの規約や社内ツールについて精度、継続性、コントロールを必要とするならカスタムエージェントを勧めている。
- 始め方についての助言は、チームがすでに毎週繰り返しているタスクを 1 つ選び、同じツールで同じチェックを実行して同じレビュー可能な出力を生成するエージェントにすることである。
