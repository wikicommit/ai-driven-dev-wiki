「Agentic Coding in 2026: A Practical Guide for Big Code」は、2026年5月21日に [[Organization/sourcegraph]] のブログで Matt Tanner が公開したガイドである。想定読者として明示されているのは、エージェンティックコーディングを現実のスケールで機能させようとしているシニアエンジニアとプラットフォームリーダーであり、その構成上の出発点となる観察は、「サイドプロジェクトでうまくいく手法は、12年分の意思決定が積み重なった2,000リポジトリのモノレポに向けた瞬間に崩れ落ちる」というものである。

本ガイドの実質的な貢献は [[DefinedTerm/eighty-percent-problem]]——エージェントがタスクの目に見える部分を完了し、コンテキストウィンドウの外にあるものを黙って取りこぼす、というパターンに対する本ガイドの命名——と、それがモデルの限界ではなくコンテキストのインフラストラクチャの問題であるという主張である。その主張は発行元自身の製品へとつながっており、本記事はベンダーによるガイドである。末尾の各節は Sourcegraph の提供面の一覧とデモの申し込みになっている。

とはいえ、自らの主張の境界については慎重である。「正直な但し書き」の節は、小規模な単一リポジトリのプロジェクトではこのコードベース全体にわたるコンテキストは必要ないと述べ、本ガイドが論じる価値は「リポジトリ数が1を超えた瞬間に現れ、100へ向かうにつれて加速する」としている。

## 要点

- **自律的なツール利用を軸に引かれた定義。** 本ガイドはエージェンティックコーディングを、自律的なエージェントがシェル、テストランナー、コード検索、バージョン管理を用いて、人間の介入を限定的に抑えつつコードの計画・記述・テスト・反復を行うソフトウェア開発として定義する。その境界の例示となるのが、「失敗しているビルドを直して」と言われたときに各カテゴリのツールが何をするかである。オートコンプリートは何もしない——こちらがタイプし始めるのを必要とするからだ。チャットは貼り付けられたエラーを読み、手作業で適用する修正を提案する。エージェントはターミナルを開き、失敗しているテストを実行し、スタックトレースを読み、壊れた関数を grep し、ファイルを編集し、テストを再実行し、グリーンになったら報告する。本ガイドが指摘する振る舞い上の飛躍は、「エージェントは、いま自分が観測したものに基づいて次に何をするかを決める」という点にある。
- **姿勢としてのバイブコーディング、アーキテクチャとしてのエージェンティックコーディング。** 本記事は「バイブコーディング」の造語を、2025年2月の Andrej Karpathy のツイート——「完全にバイブに身を委ね、指数関数を受け入れ、コードが存在することさえ忘れる」「新しい種類のコーディング」を述べたもの——に帰し、Karpathy が自分は使い捨ての週末プロジェクトについて語っているのだと明言していたことにも触れる。本記事自身の区別は、「バイブコーディングは姿勢である——モデルを信じ、差分を読まず、動くまでプロンプトを投げ続ける」のに対し、「エージェンティックコーディングはアーキテクチャである——モデルはツールに結線され、ループの中で動き、人間が完了の定義に照らしてレビューするコードを生み出す」というものだ。これを本記事は一つの問い——「違いは、正しさを誰が所有するかにある」——と、一つのルールに還元する。「バイブコーディングは、間違えるコストがゼロのときに機能する。エージェンティックコーディングは、間違えるコストが顧客の障害であるときに機能しなければならない」。
- **7つのステップからなるループ。** プロンプト、コンテキスト収集、計画、実行、テスト、リファイン、出力。エージェント同士を分けるものについての本記事の主張は、「あるエージェントが別のエージェントより優れている理由がモデルであることはめったにない」というもので、多くのツールが同じフロンティアモデルのファミリーを利用しているからである。差別化要因はモデルを取り巻くシステム——検索、ツール利用、計画、サンドボックス化、レビュー——であり、とりわけステップ2の質だとされる。
- **80%問題。** エージェントはタスクの目に見える80%を確実にこなし、コンテキストウィンドウの外にある見えない20%を取りこぼす。しかもその取りこぼしには予測可能なカテゴリがある——認証ミドルウェア、別レイヤーの API DTO、監査ログ、兄弟リポジトリの結合テスト、バックエンドの権限を鏡写しにするフロントエンドのガード、そしてマイグレーションスクリプトである。本記事はその解決を推論ではなく検索の問題として枠づけ——「エージェントが賢くなったのではない。目が増えたのだ」——近似的な検索（埋め込み、ベクトル類似度）と決定的な検索（正確なシンボル参照、すべての呼び出し箇所、すべての実装）を区別する。
- **6ステップのチームワークフロー。** タスクのスコープを定める（シニアエンジニアがプロンプトを書き、その変更がローカルなものか横断的なものかを判断する）。エージェントにコンテキストを装備させる。ループを走らせ、きれいに終了するか行き詰まっていないかを見張る。差分を人間のプルリクエストと同じようにレビューし、ローカルで実際に動かすことも含める。CI でゲートをかけ、人間のコミットが受けるのと同じチェックを通らないエージェントのコミットは入れない。そして事後に監査し、エージェント別・プロンプト別・コード変更別に活動を追跡する。その枠づけは、「エージェントをコミット権限を持つ業務委託先のように扱う」というものだ。さらに安価なチェックが一つ加えられている。エージェントが完了したと言ったら、それが触れたシンボルの他の使用箇所を検索せよ。エージェントが一度も開いていない何かが出てきたなら、そのタスクは完了していない。
- **3層のスタック。** ループを回すコーディングエージェント。IDE 統合とチャットアシスタント——短い時間軸のタスクには有用だが、ループという意味では自律的ではない。そしてコンテキストとインフラストラクチャの層——インデクシング、コード検索、コードインテリジェンス、リポジトリ全体にわたる知識である。この3つに対する本記事のメンタルモデルは、「エージェントはエンジン、MCP は配線、コードベースのコンテキストは燃料である。素晴らしいエンジンも悪い燃料ではエンストする」というものだ。
- **エージェント運用のコストモデル。** 本ガイドはコストを3つの項目——モデルの推論、検索とインデクシングのインフラストラクチャ、そして人間のレビュー時間——に分解し、推論を最も変動が大きいものとして名指す。「エージェントはリファインのループの中でタスクごとに何度も呼び出しを行うからだ」。チームが報告するばらつきの要因として挙げられているのはコンテキストの質である。「適切なコンテキストがあれば、エージェントはリトライが減り、より速く終わる」。これによってコンテキストへの取り組みは、品質だけでなくコストのレバーにもなる。

## 背景

本記事は、エージェントの出力が落ち着くのではなく積み上がっていくという主張について、発行元自身のデータを引いている。AI 導入後、大規模エンタープライズアカウントの84%でコード行数が着実に増加し、開発者はそれに応じて検索を減らすのではなく増やしたと報告している。この数字は Sourcegraph 自身のもので、自社のアカウントから得られたものである。

他者に帰されている2つの言及は、本記事自身の主張とは分けて捉えておく価値がある。本記事は [[Person/simon-willison]] のエージェンティックエンジニアリングに関する文章を、この実践を「プロのエンジニアがコーディングエージェントを使って既存の専門性を増幅するのであって、人間の判断をバイブで置き換えるのではない」と枠づけるものとして読んでいる——一次的な説明は [[DefinedTerm/vibe-engineering]] と比較されたい。また、変化した開発者の役割について Steve Yegge の「brute squad（力任せの部隊）」という枠づけを引いている。コードをタイプすることは減り、同時並行で走る多数の実行を操縦し検証することが増える、というものだ。さらに Sourcegraph のホームページから Stripe の Alistair Gray の言葉を引用し、社内ドキュメント、チケットの詳細、ビルドの状態、コードインテリジェンスを集めるために MCP に接続された Stripe 社内のエージェント労働力「Minions」について述べている。
