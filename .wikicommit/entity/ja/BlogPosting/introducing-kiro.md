「Introducing Kiro」は、2025年7月14日付の [[SoftwareApplication/kiro]] の発表記事であり、Nikhil Swaminathan（Product Lead）と Deepak Singh（VP DevEx & Agents）によって書かれている。冒頭はプロンプト駆動の開発についての問題提起から始まる。プロンプトを繰り返して作られたアプリケーションは動作し、「魔法のように感じられる」が、モデルが置いた前提は文書化されず、要件は曖昧なままで、システムの設計を後から再構成するのは難しい。

記事の論旨は、Kiro は [[DefinedTerm/vibe-coding]] が得意だが、狙いはその先にある、というものだ。その強みとして掲げられるのはプロトタイプを本番システムへ載せることであり、それを担うのが記事が中心に据える2つの機能、**spec** と **hook** である。記事は、例として用意した EC アプリケーションに商品レビュー機能を追加する流れをたどりながら、その両方を説明していく。

これはベンダーによる発表であり、実際そのように読める。このワークフローが何を解消するのかについての主張は製品チーム自身のものであり、記事はウェイトリストへのリンクと、プレビュー期間中は一定の制限のもとで Kiro が無料であるという注記で締めくくられている。

## 要点

- **spec は一つのプロンプトを要件へと展開する。** 記事は、*「Add a review system for products」* と入力すると、Kiro がレビューの閲覧、作成、絞り込み、評価についてのユーザーストーリーを生成し、それぞれに EARS（Easy Approach to Requirements Syntax）記法の受け入れ基準を付ける様子を説明している。その目的は、プロンプトが置いている前提を明示することだとされる。
- **承認された要件から設計文書が導かれる。** Kiro はコードベースと承認済みの要件を分析し、データフロー図、TypeScript のインターフェース、データベーススキーマ、API エンドポイントを生成すると説明されている。
- **タスクが生成され、順序づけられ、要件へ結びつけられる。** 各タスクには単体テスト、統合テスト、ローディング状態、モバイル対応、アクセシビリティ要件といった詳細が伴うとされる。タスクは進捗表示とともに一つずつ実行され、完了した作業はコードの差分とエージェントの実行履歴から監査できる。
- **spec はコードベースと同期し続ける。** 記事はこれを、実装の途中で開発者が元の成果物を更新しなくなり、コードと合致しないドキュメントが残るというよくある失敗への対処として提示している。
- **hook はイベント駆動のエージェント自動化である。** ファイルの保存、作成、削除、あるいは手動で起動する。挙げられている例は、React コンポーネントの保存時にテストファイルを更新すること、API エンドポイントの変更時に README を更新すること、そしてコミット前に漏洩した資格情報を走査することである。hook をいったん Git にコミットすれば、その基準はチーム全体に適用される、と記事は述べている。
- **残りは一般的な AI エディタである。** Model Context Protocol のサポート、ステアリングルール、ファイル・URL・ドキュメントをコンテキストプロバイダとするエージェンティックチャット。Code OSS 上に構築されているため、VS Code の設定と Open VSX のプラグインをそのまま引き継げる。

## 背景

記事は spec を「バイブコーディングの流れ」と「spec の明快さ」をつなぐ結合組織として枠づけており、その点で、プロンプト駆動のプロトタイピングには本番に至る前により構造化された対の存在が必要だとする 2025年の他の議論と並ぶ。この立場は [[DefinedTerm/spec-driven-development]] がより一般的に扱っているものであり、他のツールもそれぞれ異なる具体的なワークフローで実装している。

記事が掲げるビジョンはローンチそのものより広い。チームをまたいだ設計の合意形成、矛盾する要件の解消、技術的負債の解消、コードレビューへの厳密さの導入、そしてシニアエンジニアが去るときの組織知の保全である。これらは、ローンチされた製品が実際に行うこととしてではなく、チームが取り組もうとしている課題として提示されている。
