本記事は、エージェントに [[DefinedTerm/dotagents]] 規約を自ら適用させるために著者が作った [[DefinedTerm/agent-skills|Agent Skill]] である `dotagents-standard` を紹介する。冒頭に置かれているのは、この規約が防ごうとしている失敗モードである。プロジェクトのコンテキストファイルは小さく始まり——いくつかのビルド上の落とし穴、ガードレール一つ、本当の中身がどこにあるかへのポインタ——そして膨らんでいく。追加のひとつひとつが、書かれた当日にはその場所を得るに値するものだったからだ。「その失敗モードは累積的である」。やがてエージェントは CSS を編集しながらデータベーススキーマを読み、恒常的な振る舞いの規則が8か月前の一回限りの決定の3段落上に置かれ、行動する前にファイルを端から端まで読む者は誰もいなくなる。

著者は、名前をつけないままこれに近いことをすでに実践していたと述べる。エージェントが3種類の読み手向けの内容を一度に渡されることのないよう、いくつかのプロジェクトでドキュメントを三分割していたのだ——ただしプロジェクトごとに一貫性なく適用していた。欠けていたのは、この一般的なパターンの名前と、エージェント自身にそれを適用させる方法だった。

## 要点

- **難しいのは規約ではなく分類のステップである。** 本記事が述べる観察は、dotagents の README を読むのは5分の作業だが、既存の散らかったコンテキストファイルにそれを適用するのはそうではない、というものだ。「この標準が教えてくれるのは、コンテキストが種類ごとに分割されるべきだという*こと*であって、ある段落が*どの種類なのか*ではない」。7行のタクソノミー表が、各種のコンテンツを行き先のディレクトリに対応づける。
- **2つの混同がとくに名指しされている。** *規則とメモリ*——規則は常に従う恒常的な指示、メモリは経緯を説明し変わりうる事実や決定であり、両者を混ぜることは「この標準全体が防ぐために存在する原罪。『こうしなければならない』と『我々はかつてこう決めた』を区別できなくなってしまう」と呼ばれる。*コンテキストと仕様*——コンテキストは持続的で、多数のタスクにわたって読み取り専用であるのに対し、仕様はいま作っているものであり、そのタスクが出荷された瞬間に用済みになる。
- **このスキルは自らの原則を自分自身に適用している**——著者が最も誇りに思っていると述べる細部である。`SKILL.md` は1画面分にとどめられ、メンタルモデル、タクソノミー表、2つのワークフロー（既存のセットアップを活用する／新規に導入する）、そしてルーターパターンを収める。より深い素材は `references/` ディレクトリに置かれ、タスクがその深さを必要とするときにのみ読まれる。そこにはコピー＆ペースト用のテンプレートと、架空の課金 API を題材とした完全に記入済みのレイアウト例が含まれる。
- **良いルーターの規則は、トリガーを名指しし、行動を表す動詞を伴う。** 本記事の例示する規則は、条件を `READ`、`CHECK`、`CONSULT`、`ADOPT` と対にする。こうすることでエージェントは、あるファイルが存在するというだけでなく、そのポインタで何を*する*のかを知る。その警告はこうだ。「これを省くと、無条件に『常にすべてを読め』というルーターは、モノリスをディレクトリ一段深いところで作り直すだけになる」。
- **メモリは読み書き両方である。** エージェントがタスクの途中で持続的な決定を下したり、長く効く選好を学んだりしたときは、それを書き戻して、次のセッションが導出し直すのではなく継承できるようにせよ、というのが指示である。そしてタスクがルーターの指し示していないコンテキストを必要とした場合、それは行き止まりではなくルーターのバグとして扱われる——そのファイルを読み、タスクを終え、それから欠けていたルーティング規則を追加する。
- **わざわざこれをやる理由として述べられているのは**、エージェントがより多くを担うにつれてコンテキストの肥大化が悪化するということである。自律性が増せばセッションも増え、蓄積される決定も増え、もう1段落追加したくなる誘惑も増す。「よく分解されたルーターが1つあれば、エージェントがスタイルシートを直すのにスキーマファイルを*読まなかった*最初のセッションで、それは元を取る」。

## 背景

これは自作のツールについての実践者による報告であり、その基礎となる規約を擁護する議論は測定ではなく著者自身の推論である。コンテキストの節約量や品質向上の数値は示されていない。著者は、自分が作ったものと自分が土台にしたものを慎重に区別している。規約はその考案者に帰され、また本記事は同じディレクトリ名を共有するより広範なプロトコルとこの規約とを明示的に切り離している。「この2つは混同されやすい」という理由からである。
