この記事は、AI エージェントについて支配的な「ループを内蔵したチャットウィンドウ」という捉え方には限界があると論じる。モデルは忘れ、作業を早々に「完了」と宣言し、やり取り全体が一度の着席を前提に組み立てられているからである。記事はその先にあるもの、すなわち、多数のセッションとサンドボックスにまたがり、場合によっては数日から数週間にわたって目標に向けて前進し続け、しかも次のセッションが前回の続きから取りかかれるようワークスペースを十分きれいに保つエージェントを描き出し、Anthropic、Cursor、Google がそれぞれそのために何を構築してきたかを概観している。

記事は「長時間稼働」という言葉が指す 3 つの意味、すなわち長期的な推論、長時間の実行、持続的なエージェンシーを区別し（[[DefinedTerm/long-running-agent]] を参照）、本番環境の長時間稼働エージェントの設計は、繰り返し現れる 3 つの障害への対処が大半を占めると論じる。その障害とは、サイズにかかわらずいずれは埋まってしまうコンテキストウィンドウ、白紙の状態で始まる新しいセッションまで生き残る状態がないこと、そして本当に完了したかどうかについてのモデルの自己申告が当てにならないことである。

## 要点

- [[DefinedTerm/ralph-loop]] は、未完了のタスクを選び、エージェントにプロンプトを与え、チェックを実行し、ディスク上のファイルに状態を追記するという、bash スクリプト程度に単純なループであり、より大規模なシステムがどれも土台としている同じ発想を、実践者レベルで表したものとして示されている。状態はエージェントのコンテキストの外にあるため、新たな反復のたびにファイルシステムから十分な情報を読み取って作業を続けられるのである。
- Anthropic のハーネスに関する 2 つの記事は、自律的なフルスタック開発のためのイニシャライザーエージェントとコーディングエージェントの分割を説明し、続いて [[SoftwareApplication/claude-managed-agents]] の背後にある [[DefinedTerm/brain-hands-session-split]] アーキテクチャを説明している。そこでは、モデルとハーネスのループ、サンドボックス化された実行環境、追記専用のセッションイベントログがそれぞれ独立して置き換え可能になっている。Anthropic は、これらを切り離したことで、最初のトークンが出るまでの時間が p50 でおよそ 60%、p95 で 90% 超短縮されたと報告している。
- Anthropic の科学計算に関する別の記事は、同じパターンを、生きた計画としての `CLAUDE.md`、持ち運びできる実験ノートとしての `CHANGELOG.md`、そしてエージェントが完了を主張するたびにエージェントをコンテキストに引き戻す Ralph Loop 式の `for` ループにまで単純化している。その事例研究は、Claude Opus 4.6 が数日かけて構築したボルツマンソルバーで、参照実装と 1% 未満の差で一致するに至った。
- 長時間稼働するコーディングエージェントのスケーリングについての Cursor 自身の説明は、3 つの協調設計を順に試したことを述べている。フラットなファイルロック、次に楽観的並行性制御、そして Planner、Worker、Judge の階層である（[[DefinedTerm/planner-worker-model]] を参照）。また、Opus は早く止まってしまう傾向があったため、長時間の自律的な作業に限っては GPT のモデルのほうが Opus を上回ったと報告している。つまり、同じタスクでも役割が異なれば別のモデルが求められうるということである。
- Google は Cloud Next '26 で Vertex AI を [[SoftwareApplication/gemini-enterprise-agent-platform]] に統合し、同じ brain/hands/session の形を、名前の付いたサービス群（Agent Runtime、Agent Sessions、Agent Memory Bank、Agent Sandbox など）として製品化し、アイデンティティと監査証跡の機能を同梱した。
- Osmani と Shubham Saboo が別途公開した「長時間稼働エージェントの 5 つのパターン」は、[[DefinedTerm/checkpoint-and-resume]]、委任された承認（[[DefinedTerm/human-in-the-loop]] を参照）、階層化されたメモリによるコンテキスト、アンビエントな処理、フリートのオーケストレーションを、実際に機能する長時間稼働エージェントとデモとを分けるパターンとして挙げている。
- 記事の実践的な推奨事項は次のとおりである。エージェントが始める前に完了条件を外部ファイルに書き出すこと、モデルに自分の仕事を採点させるのではなく評価者を生成者から切り離すこと、プロンプトだけでなくセッションログに投資すること、そしてコンパクションやコンテキストの完全なリセットを後回しにせず第一級のものとして扱うこと。
- 記事は、執筆時点で未解決の問題を 5 つ挙げている。コスト（予算を定めずに 24 時間実行すると 1 週間分の API 費用を使い果たしうる）、セキュリティ（API キー、クラウドへのアクセス、シェル実行による攻撃対象領域の拡大）、アラインメントのドリフト（多数のコンテキストウィンドウにわたる再要約で元の目標への忠実さが失われること）、検証（1 日分の自律的な活動を監査するのは人間の時間という現実のコストである）、そして人間の役割である。人間の役割について記事は、コードを書くことから、自律的な実行者が 1 日動き続けられるほど正確な仕様を書くことへと移りつつあると位置づけている。

## 背景

記事は、Google、Anthropic、Cursor が同じ根底の形、つまりモデルのループを実行サンドボックスから、さらに永続的なセッションログから切り離し、計画を生成から、さらに評価から分けるという形に収束しつつも、その表面的な範囲では異なっていると位置づけている。Google のプラットフォームはエンタープライズ規模でアイデンティティと監査証跡を同梱し、Claude Managed Agents は「ホストされた Anthropic のハーネス」であり、Cursor のバックグラウンドエージェントは長時間稼働のコーディングを IDE の外、クラウドへと移している。Osmani はこの記事を、ハーネスのプリミティブ（[[BlogPosting/agent-harness-engineering]]）と Ralph Loop（[[BlogPosting/self-improving-agents]]）に関する自身の以前の記事の続編として提示しており、各ベンダーの具体的な主張と事例研究は、自身の検証ではなく、それぞれのベンダーが公開した記事によるものとしている。
