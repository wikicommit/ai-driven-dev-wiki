本記事はポッドキャストでの対話のハイライトをまとめたもので、著者が落ち着かない気づきと呼ぶもの——[[DefinedTerm/vibe-coding]] と [[DefinedTerm/agentic-engineering]] が自身の仕事において収束し始めたこと——を中心に据えている。彼は両者の間にはっきりとした区別を打ち立てていた。バイブコーディングはコードをまったく見ないモードであり、エージェンティックエンジニアリングは同じツールを自分の能力の限りを尽くして使うプロフェッショナルな実践である、と。そして本記事は、自分の働く場ではその線がもはや保たれていないという告白である。

## 要点

- **もとの区別、改めて。** バイブコーディングとは、何かを頼み、何かを受け取り、動けばそれでよし、というものだ——コードの品質にも追加の制約にも注意を払わない。それについての彼の見解は、境界を伴いつつ肯定的なままである。バグが自分だけを傷つける個人用ツールには素晴らしいが、他人のために作るソフトウェアには「甚だしく無責任」だ。他人があなたのバグに傷つけられるからである。
- **何が変わったか。** コーディングエージェントの信頼性が上がるにつれ、彼はすべての行をレビューすることをやめた。「本番レベルのものについてさえ」である。彼が挙げる例は、SQL クエリを実行する JSON API エンドポイントであり、これは Claude Code がテストとドキュメントを添えて素直に正しく書き上げてくれるものであって、彼はその結果を読まない。
- **それと折り合いをつけるために彼が使う類比**は、社内の依存関係の話である。エンジニアリングマネージャーとして、たとえば画像リサイズのサービスについて他チームが書いたコードのすべての行を読むことはしないだろう。彼らのドキュメントを読み、それを使い、自分の機能を出荷し、問題が出て初めて彼らのリポジトリに踏み込む。エージェントも同じように、必要になるまで覗かない半ブラックボックスとして扱っている。
- **なぜその類比が居心地悪いのか。** 「Claude Code には職業上の評判がない！」。人間のチームは評判を築くことができ、自らの行いに説明責任を負う。エージェントは説明責任を引き受けられない。彼が代わりに持っているのは、素直なものを彼の好むスタイルで正しく量産してきたというモデルの実績である。
- **名指しされているリスク**は逸脱の常態化である。監視なしにモデルが正しいコードを書いていたと判明するたびに、後日、誤ったタイミングでそれを信頼して痛い目に遭うリスクが生まれる。
- **ソフトウェアの評価は難しくなった。** 100 のコミット、良い readme、網羅的なテストを備えたリポジトリは、かつては丁寧さと注意深さのシグナルだった。今の彼なら、見た目が同一のものを30分で作れる。彼の代替のシグナルは利用実績である。誰かが2週間毎日使ってきたバイブコーディング製のものは、吐き出されただけでほとんど動かされていないものより彼にとって価値がある。同じ規則のエンタープライズ版はこうだ。他の大企業2社が半年間問題なく運用していないような CRM は使いたくない。
- **ライフサイクルはもっと遅い速度に合わせて作られていた。** 1日200行から2,000行になることは、下流だけでなく上流も壊す。彼はあるデザインリーダーの主張を伝える。重厚なデザインプロセスが存在するのは、デザインを誤ると3か月分のエンジニアリングを失っていたからであり、作ることがもはや3か月かからないのなら、デザインプロセスはもっとリスクを取ってよい、というものだ。
- **なぜ彼が自分のキャリアを恐れていないのか。** これらのツールは既存の経験の増幅器であり、彼とエージェントの会話はたいていの人には「月の言葉」であり、そしてソフトウェアを作ることはツールがどうであれ猛烈に難しいままだからである。彼はある論者の言葉を引く。自分でバイブコーディングするより、プロとして運営されるソフトウェア企業が AI を使ってより良い製品を作ってくれるほうがいい、というものであり、これを YouTube を十分に見るより配管工を呼ぶほうを選ぶことになぞらえている。

## 背景

これはポッドキャストでの発言から組み立てられた個人的な省察であり、その枠づけは明示されている。著者は、ポッドキャストが自分をこれまで言葉にしていなかった考えが浮かび上がるような形で声に出して考えさせることがある、と注記している。その価値は、他人がどう働くべきかについての一般的な主張としてではなく、境界を引いた本人による、実践の中で境界が浸食されていく一次的な記録としてある。
