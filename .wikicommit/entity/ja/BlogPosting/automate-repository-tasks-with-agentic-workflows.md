[[SoftwareApplication/github-agentic-workflows]] をテクニカルプレビューとして公開したことを告げる GitHub の発表であり、GitHub Next の研究者と Microsoft Research のエンジニアが執筆している。記事は、自らが目指す成果の描写から始まる。リポジトリを開くと、イシューはトリアージされてラベルが付けられ、CI の失敗は調査されて修正案が提示され、ドキュメントは最近のコード変更に合わせて更新され、新しいプルリクエストがレビューを待っている。そしてそのすべてが「目に見え、検査可能で、あなたが定めた境界の内側で動作している」という状態である。

記事の中身は 2 つに分かれる。1 つ目は仕組みである。望む成果を平易な Markdown で記述し、それをワークフローとしてリポジトリに追加すると、コーディングエージェントが GitHub Actions の中でそれを実行する。2 つ目は、記事が譲れないものとして扱うガードレールのアーキテクチャであり、これこそがエージェントを継続的に動かすことを実験的な試みではなく実用的なものにしているとされる。すなわち、デフォルトは読み取り専用であり、書き込みは事前に承認された [[DefinedTerm/safe-outputs]] に限定される。

## 要点

- 著者らは、GitHub Next が出発点とした問いを述べている。AI コーディングエージェントの時代に、強力なガードレールを備えたリポジトリ自動化とはどのようなものか、という問いである。出発点に GitHub Actions が選ばれたのは、スケーラブルなリポジトリ自動化がすでにそこに存在しているからだという。
- ワークフローファイルは 2 つの部分からなる。トリガー、パーミッション、ツール、許可する出力を指定する YAML フロントマターと、ジョブを自然言語で記述する Markdown の指示である。記事の言い方では、Markdown が意図であり、境界は前もって明示される。
- 各 Markdown ワークフローは、`gh-aw` CLI 拡張と `gh aw compile` によって、GitHub Actions が実行する `.lock.yml` ファイルにコンパイルされる。記事によれば、ワークフローの作成には通常 AI の支援が使われ、対話型のコーディングエージェントを使うのが最も簡単な方法だが、手作業での作成手順も示されている。
- ワークフローを実行するエンジンは設定可能であり、記事は Copilot CLI、Claude Code、OpenAI Codex を挙げている。
- セキュリティアーキテクチャは、意図しない振る舞いとプロンプトインジェクション攻撃に対する多層防御として説明されている。デフォルトで読み取り専用のパーミッション、事前に承認されたレビュー可能な GitHub 操作に対応する Safe Outputs を通じてのみ行われる書き込み、そしてサンドボックス化された実行、ツールの許可リスト、ネットワーク分離である。
- 記事は、これが、標準的な Actions の YAML ワークフローの中でコーディングエージェントの CLI を直接実行するという代替手段よりも厳格だと主張している。後者は、タスクに必要な以上のパーミッションをエージェントに与えてしまうことが多いという。
- 新たに実用的になったものとして 6 つのカテゴリが挙げられている。継続的なトリアージ、ドキュメント、コードの簡素化、テストの改善、品質の衛生管理、レポーティングである。著者らはこれらを [[DefinedTerm/continuous-ai]] という括りにまとめている。これは、CI/CD の実践と同様のかたちで自動化と協働を強化する、SDLC への AI の統合を指す彼らの用語である。
- 著者らは、これが CI/CD を置き換えるのではなく補完するものだと明言している。エージェント型ワークフローはビルド、テスト、リリースのパイプラインを置き換えるものではなく、そのユースケースは決定論的な CI/CD ワークフローとはほとんど重ならないとされる。
- 実践的な指針は次のとおりである。プルリクエストの作成を有効にする前に、コメント、ドラフト、レポートといった低リスクの出力から始めること。機能開発ではなく、目標志向のコード改善から始めること。レポートについては「良い」とは何かを具体的に示すこと。より大きなループには人間を置き続けること（記事の捉え方では、エージェントだけのサブループが自律的でいられるのは、エージェントが定められた条件のもとで行動する*からこそ*である）。そして、ワークフローの Markdown をコードとして扱うことである。
- 記事は、プルリクエストが自動でマージされることは決してなく、常に人間がレビューして承認しなければならないと述べている。
- ワークフローの実行は実行時にコーディングエージェントを使うため、課金コストが発生する。記事は、これを管理するために使用するモデルを設定できると指摘している。

## 背景

これは GitHub 自身のブログに掲載された、GitHub が構築したシステムを説明する当事者によるテクニカルプレビューの発表であり、記事は GitHub、Microsoft Research、Azure Core Upstream の協働によるものだと述べている。価値を示す根拠は、GitHub Next における著者ら自身の経験と、他組織の名前の挙がった利用者の推薦の言葉の引用であり、評価や測定は報告されていない。

ガードレールをめぐる議論、すなわち広範なパーミッションを与えるのではなく、エージェントの書き込みを事前承認済みでレビュー可能な少数の操作に限定するという考え方は、[[DefinedTerm/guardrails]] や [[DefinedTerm/deny-first-permission-evaluation]] で論じられているものと同じ手法である。また、人間が監督する外側のループの中に自律的なエージェントのサブループを置くという捉え方は、[[DefinedTerm/outer-loop]] や [[DefinedTerm/human-in-the-loop]] につながる。
