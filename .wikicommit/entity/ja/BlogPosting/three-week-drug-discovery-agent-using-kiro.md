2026年2月18日付、6人の著者による AWS Industries ブログのこの記事は、製品ではなくプロジェクトについて報告している。AWS のチームが創薬のための本番投入可能な標的同定エージェントを「わずか3週間、3人の開発者で」構築したというもので、記事はその方法論、アーキテクチャ上の決定、そして得られた教訓を共有している。本 wiki に収録しているのは、方法論——[[SoftwareApplication/kiro]] を用いて端から端まで実践された [[DefinedTerm/spec-driven-development]] の、具体的かつ日付の明らかな記録——のためであり、本 wiki の主題領域の外にあるライフサイエンスのユースケースのためではない。

なぜ仕様駆動開発が選ばれたのかについての記事の枠づけは、明示的な対比になっている。記事は [[DefinedTerm/vibe-coding]] を「開発者が直観と当面の必要に基づいて直接コードを書き、試行錯誤を通じて洗練させていく、反復的で探索的なアプローチ」と記述し、これは「小さなプロトタイプには有効でありうるが、ソリューションをスケールさせ、生成されたコードの品質と一貫性を確保することが難しくなる」と述べる。そのうえで仕様駆動開発を対置し、それは「対照的に、計画を実行から分離する」ものであり、コードが一行でも書かれる前に詳細な仕様が作られる、としている。

## 要点

- **機能ごとに3つの仕様ドキュメント**。最初のプロンプトから順に作成され、それぞれ次に進む前にレビューされる。`requirements.md` は何を作るのかを扱い、機能要件、受け入れ基準、成功指標を含む——ステークホルダーが検証できる言葉での「なぜ」と「何を」である。`design.md` は技術アーキテクチャ、実装アプローチ、統合ポイントを扱い、フレームワーク、API、データフローに関する決定を文書化する。`tasks.md` は設計を実行可能な実装ステップへ分解し、各ステップは「より広い機能についての文脈を保ちつつ、自律的な実行に足るだけの粒度」を持つ。
- **その構造の4つの利点**として述べられているもの。開発者がレビューと検証を行う一方でツールが自律的に機能を実装できるだけの文脈を作り出すこと。仕様を読めば新しいチームメンバーが何がなぜ作られたのかを学べるため、オンボーディングが容易になること。チームが「前回の実装と同じ技術スタックに基づいて新しい機能を開発せよ」と言えるようになること。そして——記事が最も重要だと呼ぶもの——人間による監督を*計画段階に*とどめることで、誤解がコードではなくドキュメントの段階で正され、それによって高コストな手戻りが防がれるとしている。
- **プロジェクト全体の一貫性のための3つのステアリングドキュメント**。目的と主要な能力を定義する `product` ドキュメント、ツールの抽象化パターンやエラーハンドリングの標準といった組織的原則を強制する `structure` ドキュメント、スタックと開発ガイドラインを定める `tech` ドキュメントである。記事はこれらを仕様とスコープによって区別し——ステアリングドキュメントはプロジェクト全体を、仕様は特定の機能を扱う——、これらは自動的に文脈として追加されると指摘する。
- **定型作業のためのエージェントフック**。フックはファイルシステムのイベントを監視し、あらかじめ定義されたプロンプトをバックグラウンドで実行した。この事例ではコードの変更に合わせて `README.md` のドキュメントを最新に保つのに用いられ、記事はさらにテスト生成、パフォーマンス最適化、コーディング標準の維持も委譲されたタスクとして挙げている。フックはリポジトリレベルで保存されるため、チェックアウトすればチーム全体がこの自動化を得られる。
- **3週間の内訳**。1〜3日目は要件収集とステークホルダーとの合意形成。4〜6日目は技術設計とアーキテクチャの決定。7〜14日目は仕様の作成とフルスタックのウェブアプリの実装。14〜21日目はテスト、フィードバック、そしてプロンプトエンジニアリングと機能要望に関する反復である。
- **報告された成果**（いずれもチーム自身の数字）。ツールが「ビジネスロジックのコードの 95% 超を生成し、80時間超の開発時間を節約した」。ツールが書いた README のドキュメントは推定8時間を節約した。そしてステアリングドキュメントによりチームメンバー全員が同じコーディング標準とフレームワークに従った。
- **5つの教訓**。仕様に先行投資すること。包括的なステアリングドキュメントから始めること。生成の精度を高めるために [[DefinedTerm/model-context-protocol]] の知識ソースへ接続すること。自分のデータを信頼し、それ以外のすべてにラベルを付けること——本番システムの中にシミュレートされたものがあってはならず、開発中に使ったテストデータはデータ側と出力側の双方で明示的に印を付けなければならない。ラベルのないテストデータは、もっともらしく見えるがゆえに本物の応答と区別しがたくなるからである。そして初日から可観測性を作り込むこと。

## 背景

仕事の進め方が何を変えたのかについての記事のまとめは、その領域の外へ最も持ち出しやすい一文である。「Kiro における仕様駆動のアプローチは、われわれの開発を、一行一行のコードを書くことから、人間の監督のもとで AI エージェントにタスクを導き委譲することへと移行させた」。チーム編成についての記述もそこから導かれる。3人のソリューションアーキテクトがそれぞれ独立に自分のツールと統合に取り組み、共有された仕様によって整合性が保たれる一方、反復的なコーディングはツールが担った、というものである。

ここに挙がる数字と利点の主張はすべて AWS 自身のものであり、コーディングツールと使用されたクラウドサービスの双方のベンダーによって公開された記事に由来する。独立した評価は存在せず、チームはこのアプローチが機能することを示すという目的も部分的に持って着手したプロジェクトについて書いている。記事はまた第三者の数字も伝えている——見積もりで52週分の作業を3週間で完了し、効率が 90% 向上したという顧客の事例——が、これは一段隔てて報告されたものであり、そのように読むべきである。

記事は、このプロジェクトではまだ使っていない2つの今後の方向性で締めくくられている。ひとつは **Kiro Powers** で、記事が「従来の MCP サーバのコンテキスト過負荷問題」と呼ぶものを解決するために文脈とツールをオンデマンドで読み込む専門特化された専門性モジュールとして記述され、MCP ツール、ステアリングファイル、フックを組み込みのベストプラクティスとともに束ね、関連する場合にのみ有効化されるという。もうひとつは **Kiro Autonomous Agent** で、非同期のチームメイトとしてソフトウェア開発の仕事を担うことを意図したフロンティアエージェントとして記述され、IDE 内ですでに構築されたエージェントから学び、同じパターンを適用して、絶えざる人間の導きなしにさらに多くを構築できるとされている。
