記事の議論は、コーディングエージェントについての特定の見方から出発する。すなわち、コーディングの問題の解決策を見つけるための力任せのツールとしての見方である。この見方に立てば、明確なゴールと、それに向かって繰り返し試行するツールの集合に還元できる問題は、エージェントが力ずくで突破できることが多い問題である。そして磨く価値のあるスキル、記事が **エージェント的ループの設計**（designing agentic loops）と名付けるスキルとは、そうしたツールとそのループを注意深く設計することである。記事はこの捉え方を、[[DefinedTerm/ai-agent]]（AI エージェント）とはゴールを達成するためにループの中でツールを実行するものである、という著者自身が好む定義に基づかせている。

記事の分量の大半は、この捉え方がぶつかる障害に割かれている。力任せのアプローチには、エージェントが各ステップで承認を待って止まることなく動き続けることが必要である。著者は、エージェントがデフォルトで行うコマンドごとの承認プロンプトは、より安全ではあるものの、この方法で問題を解決するエージェントの有効性を劇的に下げると論じる。それを取り除くこと、記事が YOLO モードと呼ぶものは、本当に危険であると同時に、最も生産的な結果を得るための鍵でもあると示され、記事はこの緊張と付き合うための 3 つの方法、すなわちサンドボックス、他人のコンピュータ、そしてリスクの受け入れを順に検討する。

残りは実践的な内容である。ツールについて記事は、この目的にはたいてい [[DefinedTerm/model-context-protocol]] よりもシェルコマンドのほうが優れていること、そして [[DefinedTerm/agents-md]] のようなファイルに短い実例を 1 つ書いておけば、たいていエージェントはそこから一般化できることを論じる。認証情報については、テスト環境やステージング環境と、厳格な予算上限を推奨する。記事は最後に、この扱いに値する問題を、成功基準が明確で、よい解決策を見つけるには退屈な試行錯誤が必要な問題として特徴づけ、自動テストをその例に共通する要素として挙げている。

## 要点

- コーディングエージェントは、コーディングの問題の解決策を見つけるための力任せのツールと考えることができる。明確なゴールと繰り返し試行するツールに還元できる問題は、力ずくで解決に持ち込めることが多い。
- エージェント的ループの設計は、重要な新しいスキルとして提案されており、記事は、明確な名前があれば議論しやすくなることを期待してこのスキルに名前を付けているのだと明言している。
- エージェントについての著者の作業上の定義、すなわちゴールを達成するためにループの中でツールを実行するものという定義こそが、ツールとループの設計をスキルが発揮される場にしている。
- コマンドごとの承認プロンプトはエージェントの危険性に対するデフォルトの対策であり、それは力任せの問題解決におけるエージェントの有効性を劇的に下げる。
- 無人で動かす YOLO モードには 3 つのリスクが挙げられている。悪いシェルコマンドが大切なものを壊すこと、エージェントから見えるファイルや秘密情報が持ち出されること、そして自分のマシンが別の標的を攻撃するためのプロキシとして使われることである。
- 3 つの対応が示されている。安全なサンドボックスで実行する、他人のコンピュータを使う、あるいはリスクを取り、エージェントを悪意のある指示にさらさないよう努める、というものであり、著者はほとんどの人が 3 つ目を選ぶと述べている。
- 他人のコンピュータで実行することは著者自身のお気に入りであり、その好みの具体例として GitHub Codespaces が挙げられている。著者はそこでの最悪のケースを、チェックアウトされたコードが持ち出されるか、接続されたリポジトリに悪いコードがプッシュされることに限定されるとしている。
- Docker や Apple のコンテナツールは、コンテナエスケープが存在するにもかかわらず、ほとんどの人にとって妥当なリスクだと判断されている。これはセキュリティ上の保証ではなく、著者自身のリスク判断として述べられている。
- コーディングエージェントは独自のサンドボックス化を実装しているが、著者は信頼できるほど説得力のあるそのドキュメントを見たことがないと報告している。これは検証された知見ではなく著者自身の評価である。
- 記事は「Safe YOLO mode」についての Anthropic 自身の Claude Code ドキュメントを引用している。それはインターネットアクセスのないコンテナで `--dangerously-skip-permissions` を実行することを推奨している。この推奨はベンダーのものがここで伝えられているのであり、記事自身の知見ではない。
- エージェントのインターネットアクセスを信頼できるホストのリストに制限することは、持ち出し攻撃によってプライベートなソースコードが盗まれるのを防ぐよい方法として示されている。
- エージェントのツールについては、MCP よりもシェルコマンドとして考えるほうがたいてい生産的である。コーディングエージェントはシェルコマンドの実行が得意だからである。
- `AGENTS.md` のようなファイルに実例を 1 つ書いておくだけで、エージェントが一般化するには十分なことが多い。著者の例は 1 つのスクリーンショットのコマンドであり、エージェントはそこから URL とファイル名を変える方法を推測した。
- よく知られたツールの名前を挙げること（「playwright python を使え」「ffmpeg を使え」）でたいてい十分である。ループの中で動くエージェントは、初期の自分の誤りから立ち直れるからである。
- 認証情報は、損害が封じ込められるテスト環境やステージング環境にスコープを限定すべきであり、お金を使える認証情報には厳しい予算上限を設けるべきである。
- 著者によるスコープを限定した認証情報の例は、1 回のコールドスタートの調査のために作成した、予算 5 ドルの専用の Fly.io 組織と、それに限定された API キーである。著者は、その調査の結果は述べるほど有用ではなかったと報告している。
- このパターンは、成功基準が明確で、よい解決策を得るには退屈な試行錯誤が必要な問題に適している。示されている目安は、多くのバリエーションを試さなければならないだろうと考えている自分に気づくことである。
- 4 つの問題の形が例として挙げられている。失敗しているテストのデバッグ、インデックスのベンチマークのようなパフォーマンス最適化、依存関係のアップグレード、そしてコンテナイメージの縮小である。
- よく整備されていてきれいに通るテストスイートが、それらすべての例にわたってコーディングエージェントの価値を増幅する共通の要素として挙げられている。
