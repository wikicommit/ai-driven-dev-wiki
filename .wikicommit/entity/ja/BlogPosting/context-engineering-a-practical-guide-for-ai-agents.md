「Context Engineering: A Practical Guide for AI Agents (2026)」は、2026年5月28日に [[Organization/sourcegraph]] のブログで Matt Tanner が公開したガイドであり、同じ著者による [[BlogPosting/agentic-coding-in-2026-a-practical-guide-for-big-code]] の1週間後にあたる。想定読者として明示されているのは、「チャットボットのデモ段階を過ぎた」エンジニアで、エージェントを本番環境で持ちこたえさせたい人々である。

その枠づけの前提は、2025年半ばまでにプロンプトの言い回しが主要なボトルネックではなくなり、代わって繰り返し現れる問題は、「コンテキストウィンドウが自らの重みで崩壊しないようにしつつ」、毎ターン適切なファイル、ツール定義、会話の断片、検索された事実をエージェントに与えることになった、というものである。チャットボットとエージェントの区別が、その賭け金を具体的にする。エージェントは「ステップ1から46までの残滓がまだモデルのコンテキストウィンドウに残った状態で、ステップ47で判断を下そうとする」のであり、コンテキストの失敗の大半は、冒頭の悪いプロンプトからではなく、有限の予算がどう費やされたかから生じる。

姉妹記事と同様、これはベンダーのガイドであり、その論旨は発行元自身の製品に到達する。4つの柱という整理と失敗モードのカタログはそれとは独立に成立するが、ベンチマークの数値は発行元による自社ツールの自社測定である。

## 要点

- **4つの柱。** 本ガイドは「著者によってこの領域の切り分け方は少しずつ異なる」ことを認め——Prompting Guide は階層的なレイヤーを列挙し、Phil Schmid は7つの構成要素を挙げ、Anthropic はシステムプロンプト、ツール、例示、メッセージ履歴を列挙せずに順に説明していると注記する——実践的な整理として4つを提示する。**指示**は、最初のユーザーメッセージ以前にモデルが保持する役割・制約・出力形式であり、ここでの失敗として挙げられるのは長さではなく「モデルの訓練とのミスマッチ」である。モデル既定のツール利用ヒューリスティックに反する詳細な指示は、毎ターン混乱した振る舞いを生む。**検索**は、外部データがウィンドウに入ってくる経路であり、ベクトルデータベース上の RAG、構造化クエリ、ファイル読み取り、そして軽量な識別子を用いたジャストインタイムの検索にわたる。**メモリ**は、短期の会話履歴と長期のセッション横断状態に分かれ、通常はコンパクションのステップを伴う。**ツール**は、この規律が「最も容赦なくなる」場所だと説明される。各定義と各結果がトークンを消費し、曖昧なツール群はモデルにほぼ重複したもの同士の選択でターンを浪費させるからである。
- **プロンプトエンジニアリングとは対立ではなく階層の関係。** 本ガイドは両者が「スタックの異なる層に位置する」と論じ、いま自分がどちらをやっているかを判別するテストを提示する。「名詞や形容詞を差し替えているなら、まだプロンプトエンジニアリングである。エージェントがどのデータをどの順序で、どんな再ランキングを伴って取得し、コンテキストウィンドウが埋まったときに何を追い出すかを変えているなら、それはコンテキストエンジニアリングである」。本ガイドはこの規律を4つの問いに還元する。何を取ってくるか、いつ取ってくるか、どう圧縮するか、そしていつ捨てるか。
- **事前フィルタリングとしてのトークン予算管理。** その定義は「シグナルの低いコンテンツを、コンテキストウィンドウに入った*後*ではなく*前*に切り落とす規律」である——ツール出力の切り詰め、古い会話の逐次的な要約へのコンパクション、関連度のしきい値を下回る検索結果チャンクの破棄、そして各検索呼び出しが寄与する候補数の上限設定である。再ランキングは、素朴な RAG パイプラインが「機能し始めるか、機能しなくなるかが決まる」ステップとして提示され、高い再現率で50件の候補を取得し、その50件すべてをプロンプトに投げ込むのではなく精度の高い上位5件に再ランキングするパイプラインが例示される。
- **失敗モードのカタログ。** コンテキストの過負荷——同じタスクにおいて、10万トークンのコードベース要約を与えたエージェントのほうが、5千トークンの的を絞った検索を与えた場合よりも成績が悪かったという観察が報告されている。**コンテキストの散漫化**では、無関係な素材が重要なコンテキストを押しのける。**コンテキストの混乱**では、矛盾するシグナルがモデルを別々の方向に引っ張る。**陳腐化した／無関係な検索**では、更新されていない埋め込みによって、エージェントが古い README で見つけた非推奨 API を自信をもって呼び出してしまう。そして **lost in the middle（中間での見落とし）** については、Liu ら の論文の知見が引用される。性能は「関連情報が入力コンテキストの冒頭または末尾にあるときに最も高くなることが多く、長いコンテキストの中間にある関連情報にモデルがアクセスしなければならないときには著しく劣化する。これは明示的に長コンテキスト対応とされるモデルでも同様である」。最後の点についての実践的な読みは、組み立ての順序が重要だということだ——最もシグナルの高い素材は先頭か末尾に置き、中ほどに埋もれさせない。
- **構造があるところでは、構造は類似度に勝る。** とりわけコーディングエージェントについて、本ガイドはコードには構造——コールグラフ、型情報、リポジトリ横断の参照——があり、テキスト検索はそれを捨ててしまうと論じる。だからこそ構造的な参照は、「そのシンボルに言及している50個のファイルがあります」を「定義されている1つのファイルと、3か所の呼び出し箇所がここにあります」に変える。ただしこれが条件付きであることは明示されている。実世界でのカバレッジはインデクシング、言語サポート、権限に依存する。
- **ウィンドウを広げても問題は消えない。** 示されている立場は、コンテキストウィンドウの拡大は一部の圧力を減らすがすべてではない、というものである。サイズとともにレイテンシとコストが増大し、lost in the middle と散漫化のパターンは依然として当てはまるからだ。「200万トークンあっても、LLM に見せたいのは今のタスクに有用なものだけである」。
- **ターンごとの組み立てパイプライン。** 本ガイドはその順序を具体的に述べる。ユーザー入力とクエリから始め、1つ以上の検索ステップを並列に実行し——ベクトル検索、キーワード検索、構造化された参照、コードグラフのクエリ——その結果を現在のタスク向けの候補集合にマージし、その上でメモリ、システム指示、ツール定義を重ねてからモデルを呼び出す。マルチエージェントシステムでは、各サブエージェントがより狭いスコープに対して同じパイプラインを実行してから報告を返すことがある。これが4つの柱を、4つの別個の関心事ではなく一つの流れに束ねるものである。
- **トークン予算が、再現率だけでなく機構として重要な理由。** モデルが注意を向ける対象の劣化に加えて、本ガイドはコストの議論を示す。「標準的な密なアテンションでは、コストは系列長に対して二次的にスケールする。スパースアテンションや flash attention の最適化を用いても、コンテキストウィンドウの拡大は依然としてレイテンシ、支出、検索の難度を増大させる」。
- **本ガイドが処方する計装。** 「追加の検索一つ、追加のツール呼び出し一つ、再ランキングの一巡ごとに、それは p95 レイテンシとタスクあたりコストに現れる」ため、タスクごとのトークン使用量とツール呼び出し回数を追跡し、予算を設定し、あるエージェントのクラスがそれを恒常的に超えたらアラートを出すことを推奨している。

## 背景

本ガイドは、2025年半ばにこの語を広めるのに寄与した人物として Phil Schmid の名を挙げ、その枠づけ——適切な情報とツールを、適切な形式で、適切なタイミングでモデルに与える動的なシステムを設計すること——を引用している。また [[Organization/anthropic]] によるこの規律の定義と、ツール群についての観察も引用する。「人間のエンジニアが、ある状況でどのツールを使うべきかを断定できないのなら、AI エージェントにそれ以上を期待することはできない」。いずれも本ガイド自身の定式化ではなく他者の見解の引用としてここに現れており、一次的な説明は [[DefinedTerm/context-engineering]] に記録されている。

定量的な内容は一次情報である。発行元自身の [[Dataset/codescalebench]] の結果は、本記事が2026年3月のものとしており、370 件のエンタープライズ規模のタスクにわたって同一のエージェントを2つの構成で走らせたものとして報告されている。また本記事は、2026年2月の Sourcegraph 7.0 リリースが同社のコードインテリジェンスプラットフォームを「開発者と AI エージェントの双方にとっての共有インテリジェンス層」と位置づけたとも述べている。読者は、測定された差分をベンダーによる自社検索層の評価として扱うべきである。
