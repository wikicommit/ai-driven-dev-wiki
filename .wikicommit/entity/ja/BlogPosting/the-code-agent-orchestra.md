「The Code Agent Orchestra - what makes multi-agent coding work」は、[[Person/addy-osmani]] が2026年3月26日に O'Reilly AI CodeCon で行った講演の文章版である。その構成上の主張は、生産的な開発者の働き方にすでに転換が起きたということだ。1人の開発者が単一のエージェントを同期的に導き、コンテキストウィンドウが厳然たる天井となる*指揮者*モデルから、複数のエージェントがそれぞれ独自のコンテキストウィンドウとファイルのスコープを持って非同期に走り、開発者は上から計画し様子を確認する*オーケストレーター*モデルへ、である。

本記事は段階的に高度化する3つのパターン——[[DefinedTerm/subagents]]、Claude Code の [[DefinedTerm/agent-teams]] 機能、そして専用のオーケストレーションツール——として構成され、その後に、この仕組み全体を信頼できるものにすると著者が論じる品質ゲートが続く。これらの推奨とともに、本記事は一つの警告を携えている。人間というボトルネックは「バグではなく機能だった」というものだ。人間のペースであれば誤りは早い段階で感じ取られるが、オーケストレートされた艦隊は、開発者が捕捉できるよりも速く小さな誤りを積み上げてしまう。本記事自身は、まず着手すべき5つのパターンで締めくくられ、その先頭がサブエージェントである。

## 要点

- **単一エージェントの天井を決めるのは3つの制約である。** コンテキストの過負荷、専門特化の不在、協調の不在。本記事の主張は、サブエージェントが前の2つを解決し、Agent Teams が3つすべてを解決するというものだ。
- **マルチエージェントへ進む、互いに積み上がる4つの理由。** 並列性（本記事はフロントエンド・バックエンド・テストに3体のエージェントを充てて「3倍のスループット」を挙げる）、狭いファイル所有権を通じた専門特化、git worktree による隔離、そして [[DefinedTerm/agents-md]] ファイルに蓄積される複利的な学習である。
- **広いファンアウトよりも階層的な委譲。** 1つのオーケストレーターが6体のサブエージェントを起動して自らのコンテキストを断片化させるのではなく、2体の機能リードを起動し、それぞれが自分のブリーフを分解する。Osmani はこれをエンジニアリング組織におけるテックリードの層になぞらえる。
- **2026年のツールの3層俯瞰。** ティア1はインプロセスのサブエージェントと Agent Teams。ティア2は隔離された worktree をダッシュボードと差分レビューとともに走らせるローカルのオーケストレーター（3〜10体のエージェントに最適）。ティア3はプルリクエストを返すクラウドの非同期エージェント。彼は大半の開発者が3つすべてを使うようになると見ている。
- **3〜5人のチームメイトがスイートスポットだと述べられており**、トークンコストはチームの規模に比例して増える。
- **3つの品質ゲート。** 実装前の計画の承認、ライフサイクルイベントで自動チェックを走らせるフック（`TaskCompleted` フックでリントとテストを実行し、`TeammateIdle` フックでテストが通ることを確認する）、そして複利的な学習の器としての `AGENTS.md` である。
- **ボトルネックは生成ではなく検証である**——[[DefinedTerm/verification-bottleneck]] を参照。本記事の具体的な主張は、テストが通ってもリグレッションのカバレッジが保証されるわけではないこと、エージェントは妥当ではあるが肝心なところを外したテストを書くこと、そして1人の開発者なら煩わしい程度で済ませるフレーキーな環境が、40体のエージェントが同時にぶつかると系全体の障害物になること、である。
- **委譲するのはタスクであって判断ではない。** エージェントが適しているのは評価関数のきつい作業——ボイラープレート、マイグレーション、テストのスキャフォールディング——であり、アーキテクチャ、何を作らないかの決定、そしてシステム全体のコンテキストを踏まえたレビューは開発者の手元に残る。
- **レバレッジは仕様にある。** 50体のエージェントが並列に走る状況では、曖昧な要件は何十もの実行に伝播し、そのそれぞれが別々の形で誤る。これが、優れたエンジニアほどこれらのツールから*より多くの*レバレッジを得る（より少なくではなく）理由についての本記事の説明である。

## 背景

本記事は研究成果ではなく講演の記事化であり、その主張の大半は著者自身の実践と観察として提示されている。外部の証拠に依拠する箇所ではそう明示している。Osmani は、LLM が生成した `AGENTS.md` ファイルには利点がなく、推論コストを20%以上増やしながら成功率をわずかに（平均でおよそ3%）低下させうるのに対し、開発者が書いたコンテキストファイルは約4%というささやかな改善をもたらすという主張について、チューリッヒ工科大学の Gloaguen らの研究を引いている。これが、リードがすべての行を承認しなければならず、エージェントが `AGENTS.md` に直接書き込んではならないという彼のルールの根拠である。

また、Steve Yegge の AI 支援コーディングの8つのレベルを、この講演が位置づけられている梯子として枠づけ、レベル5から8を扱っているが、個々のレベルの内容を改めて説明することはしていない。本記事のいくつかの節は、著者が別途公開したより長い記事の要約である。このページは、本記事自身が述べていることのみを記録する。
