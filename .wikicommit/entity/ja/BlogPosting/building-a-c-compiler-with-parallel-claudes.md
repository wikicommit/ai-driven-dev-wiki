本記事は、16 個のエージェントに Linux カーネルをコンパイルできる Rust ベースの C コンパイラをゼロから書くという課題を与え、その後はおおむね放任した実験を報告している。2,000 回近い Claude Code のセッションと2万ドル弱の API コストを費やして、チームは x86・ARM・RISC-V 上で Linux 6.9 をビルドできる10万行のコンパイラを生み出した。

著者は、コンパイラのほうが副産物であることを明言している。本記事が焦点を当てるのは、長時間動作する自律エージェントチームのためのハーネス設計についてこのプロジェクトが教えたこと——人間の監督なしにエージェントを軌道に乗せ続けるテストをどう書くか、複数のエージェントが並行して前進できるよう作業をどう構造化するか、そしてこのアプローチがどこで天井にぶつかるか——である。プロジェクトは能力ベンチマークとして枠づけられ、Claude 4 モデルシリーズ全体で実行された。その目的として明示されているのは、モデルが今日「かろうじて」できることに負荷をかけて試すことで、後に確実にできるようになることを先取りすることである。

## 要点

- **ループは意図的に最小限である。** 既存のエージェントスキャフォールドは操作者がオンラインにいることを前提としており、長い問題を与えられたモデルはいずれ停止して入力を待つ。ここでのハーネスは bash の `while true` ループで、前のセッションが終わるやいなや新しい Claude Code のセッションを開始する。プロンプトは、問題を小さな断片に分解し、いま何に取り組んでいるかを記録し、進み続けるよう指示するものである。本記事は [[DefinedTerm/ralph]] ループとの類似に触れ、実機ではなくコンテナで走らせるよう警告している。
- **並列性はオーケストレーターではなく git によって調停される。** 各エージェントには bare リポジトリをマウントした Docker コンテナが与えられ、ワークスペースにクローンし、終わったらプッシュして返す。タスクの衝突は `current_tasks/` ディレクトリに書き込まれるロックファイルで防がれる。2 つのエージェントが同じタスクを主張した場合、git 自身の同期によって後者は別のタスクを選ばざるを得なくなる。オーケストレーションエージェントも、エージェント間のメッセージングも、上位の目標を管理するための強制されたプロセスも存在しない。各エージェントが何をするかを自分で決め、たいていは「次に最も明白な」問題を選ぶ。著者はこれをごく初期の研究プロトタイプだと呼んでいる。
- **テストの質が拘束条件になる。** エージェントは与えられた問題が何であれ自律的に解いてしまうため、「タスクの検証器がほぼ完璧であることが重要だ。さもなければ Claude は間違った問題を解いてしまう」。新機能を加えるたびにエージェントが既存の機能を壊し始めたときの答えは、新しいコミットが既存のコードを壊せないよう、より厳格に強制する CI パイプラインだった。
- **ハーネスは著者にではなくモデルに向けて書かれる**——ここから導かれた具体的な設計ルールについては [[DefinedTerm/agent-harness]] を参照。
- **単一の巨大タスクという天井と、それを破ったオラクル。** 何百もの独立した失敗テストがある状況では並列化は自明である。各エージェントが別々のテストを取ればよい。だが Linux カーネルのコンパイルは一つの巨大なタスクであり、すべてのエージェントが同じバグにぶつかり、それを直し、互いの変更を上書きし合った——16 個のエージェントは役に立たなかった。解決策は、GCC を既知の正しいコンパイラのオラクルとして使うことだった。ハーネスはカーネルの大部分を GCC でコンパイルし、残りのファイルだけを Claude のコンパイラでコンパイルする。こうすると失敗によってバグがその部分集合に局在化され、各エージェントが別々のファイルに取り組めるようになる。その後も、組み合わせると失敗するが個別には動作するファイルの対を見つけるために、デルタデバッグが必要だった。
- **専門特化は、単なるスループット向上とは別の並列性の使い方である。** 問題を解くエージェント群のほかに、重複コードを統合する役目を与えられたエージェントが1つ置かれ（本記事は、LLM が書くコードは既存の機能を再実装しがちだと注記する）、コンパイラ自身の性能を担当するもの、生成されるコードの効率を担当するもの、Rust 開発者の視点からプロジェクトの設計を批評しそれに応じて再構成するもの、そしてドキュメントを担当するものが置かれた。

## 背景

評価の節は、限界について異例なほど率直である。この実行は2週間で20億の入力トークンを消費し、1億4,000万の出力トークンを生成した。このコンパイラは開発中インターネットにアクセスしないクリーンルーム実装であり、依存するのは Rust の標準ライブラリのみである。QEMU、FFmpeg、SQLite、postgres、redis をコンパイルでき、ほとんどのコンパイラテストスイートで99%の合格率に達し、Doom をコンパイルして実行できる。しかし 16 ビット x86 コンパイラを持たず、Linux をリアルモードから起動するには GCC を呼び出す。独自のアセンブラもリンカも持たない。多くのプロジェクトをビルドできるがすべてではない。生成されるコードは、最適化をすべて無効にした GCC のものよりも効率が悪い。そして Rust コードの品質は、まずまずではあるが熟練の Rust プログラマが書くものにははるかに及ばない、と説明されている。著者は、これらのいくつかを直そうと懸命に試みたが完全には成功しなかったと述べ、新機能とバグ修正が既存の機能を頻繁に壊したとしている。

本記事は勝利ではなく居心地の悪さで締めくくられる。示されている懸念は、自律的なシステムでは「テストが通るのを見て仕事が終わったと思い込みやすいが、実際にそうであることはめったにない」ということであり——[[DefinedTerm/verification-bottleneck]] を参照——著者は自身のペネトレーションテストの経歴を踏まえて、プログラマが自ら一度も検証していないソフトウェアをデプロイするという見通しを現実の懸念として名指している。彼のまとめは、この実験は自分を興奮させると同時に落ち着かなくもさせるというものであり、モデルとスキャフォールドの急速な進歩は「膨大な量の新しいコードを書く扉を開く」が、それを安全に切り抜けるには新しい戦略が必要になる、というものである。
