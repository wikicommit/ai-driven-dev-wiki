本記事は、コーディングエージェント時代に開発が実際どのように進められているかを調査し、2026年3月時点のこの分野の状況を3つの層——プロジェクトの回し方、エージェントとコーディングするための技法、その双方を支えるインフラストラクチャ——に整理し、最後に著者自身のワークフローで締めくくる。ハーネスエンジニアリングについての先行記事の続編として位置づけられており、その先行記事は本記事が引いて眺めるための実装上の土台として扱われている。

その枠組みの概念が [[DefinedTerm/agentic-engineering]] である。本記事は、Karpathy が2025年2月にバイブコーディングを提唱したこと、それが続く1年のうちに構造化されたエンジニアリング手法へと成熟したこと、そして2026年2月に Karpathy がそれをエージェンティックエンジニアリングと改名したことを報告する——自分でコードを書くことはなく、時間の99%はコードを書くエージェントのオーケストレーションと監督に充てられる、という定義とともに。

## 要点

**4つのプロジェクトワークフロー**が、互いに排他的なものではなく組み合わせ可能なものとして提示される。

- **Brainstorm → Plan → Execute（Harper Reed 方式）**——*一度に一つずつ質問して*とプロンプトされた会話型 LLM が `spec.md` を生み出し、推論モデルがそれを `prompt_plan.md` と `todo.md` に変え、プロンプトを順にエージェントへ投入する。グリーンフィールドの個人プロジェクトに最も適しており、本記事は Harper 自身がそれを認めているとする。その重要性は、いきなりコードへ飛びつかないという原則を確立した点にある。
- **[[DefinedTerm/spec-driven-development]] ／ AI-DLC**——2025年から2026年にかけて最も速く広まったワークフローで、バイブコーディングの対極として位置づけられ、基本の流れは要件 → 設計 → タスク → 実装である。本記事は SDD を spec-first、spec-anchored、spec-as-source の3レベルに分類する見方と、Technology Radar の Assess 評価を引く。AWS の AI-DLC はこれを Inception、Construction、Operations のフェーズにわたるチーム・組織規模へ拡張し、ビジネス上の意図を詳細な要件へ変換する4時間の同期型 Mob Elaboration セッションと、タスクの複雑さに応じて9段階のメニューから段階を選ぶ Adaptive Workflow を備える。その利点として述べられているのは、実装中のマイクロな承認をフェーズゲートのレビューに置き換えて承認疲れを解消することであり、問題として述べられているのは、コードからの仕様の乖離——「マークダウンの海に溺れる」——小さなバグ修正には過剰であること、そして重厚な事前仕様＋ビッグバンリリースへ退行するリスクである。
- **[[DefinedTerm/research-plan-implement]]**——3フェーズのワークフローで、その中核の規則は、詳細な計画が文書として書かれ、レビューされ、承認されるまでエージェントはコードを書かない、というものである。
- **[[SoftwareApplication/superpowers]]**——SDD と TDD を単一の7段階パイプラインに符号化し、その手法をエージェントに強制するスキルフレームワーク。

選択の指針は、グリーンフィールドの単独作業なら Harper Reed 方式、仕様管理を必要とするチームなら SDD、既存コードベースへの大きな変更なら RPI、ワークフロー全体の自動化なら Superpowers、というものだ。

**セッション内の品質技法。** [[DefinedTerm/context-engineering]] がモデル選択よりも上位の、最も重要な単一のレバーとして名指される。技法としては、コンテキストのパッキング、[[DefinedTerm/progressive-disclosure]]、ファイルシステムを外部メモリとして使うこと、コンテキストの末尾に再注入される `todo.md` によって注意を管理すること、そしてエージェントが同じ失敗を繰り返さないよう失敗の状態を意図的に消*さない*ことが挙げられる。2つのアンチパターンが名指しされている。few-shot の例を多数含むコンテキストファイルを読み込ませること——エージェントが考える代わりにパターンを模倣するようになる——と、作業が始まる前にコンテキストウィンドウを埋めてしまうことである。以降の節は [[DefinedTerm/context-rot]]、コーディングエージェントによる TDD、[[DefinedTerm/multi-agent-orchestration]]、[[DefinedTerm/best-of-n]] 並列戦略、AI による AI のレビュー、失敗モード、そしてエージェントネイティブなコード設計を扱う。

**失敗モードの表**は、6つの症状と緩和策を対にしている。ハルシネーション（最新のドキュメントを注入し、テストで捕捉する）、無限ループ（溝にはまった状態の検出、トークン上限による打ち切り）、過剰生成（スコープを明示的に限定し、禁止事項をコンテキストファイルに書く）、偽の完了（PostToolUse フックでテストを自動実行する）、エージェントのドリフト（リンターと型チェッカーで機械的に是正する）、そして確率的なカスケード——1ステップ95%の成功率が5ステップで77%になる——であり、これは小さなタスクに分けて個別に検証することで緩和される。

**エージェントネイティブなコード設計**は、技法に先立つものとして提示される。名前付きエクスポートと一貫したエラー型による grep しやすい命名、一貫した命名規約のもとに併置されたテスト（`ls` 一発でその存在が確認できる）、水平方向ではなく機能単位のモジュール化、実装が正しいかどうかをエージェントに伝える報酬信号としてテストを扱うこと、そして並列のマルチエージェント作業の前提条件として事前に合意されるインターフェース契約である。

**インフラストラクチャ。** 各節は、コンテキストファイルの設計、[[DefinedTerm/agent-skills]] とプラグインのエコシステム、決定的な層としてのフックとリンター、並列性の物理的な土台としての git worktree、MCP 対 CLI＋スキルという問い、ワークフロー定義型・エージェント管理型・プロセスマルチプレクサ型・役割ベース型に分類されたオーケストレーションツールの俯瞰、長時間セッションの設計、[[SoftwareApplication/github-agentic-workflows]]、セキュリティ、そして [[SoftwareApplication/symphony]] を扱う。

**著者自身の実践**は、一つを採用するのではなくパターンを混ぜ合わせている。*アイデア駆動型*のフローは、アイデア → エージェントによる仕様のドラフト → ユーザーのレビュー → エージェントの実装 → ユーザーの受け入れ、という流れで進み、Patrol Agent が定期的に停滞しているセッションを確認し、通知をまとめることで、ユーザーが継続的に中断されるのではなくまとめて処理できるようにする。実験的な*自動化*フローは、網羅的な開発ドキュメントを用意し、ハーネスとフィードバックループを構築し、タスクを `tasks.jsonl` に書き出し、タスクごとにプランモード → 自動承認 → 実装をエージェントに走らせ、コミット時のフックで自動レビューを行う。本記事は、この構成で8時間の自動実行が完走したと報告している。

## 背景

これは研究ではなく実践者によるサーベイである。その数値の大半——スター数、ベンチマークのスコア、報告された高速化——は著者による測定ではなくリンク先の出典から中継されたものであり、本記事はそれぞれを引用することでそう明示している。本記事自身の貢献は、3つの層への整理と、ワークフロー間の選択の指針にある。

まとめとして述べられているのは、2026年においてエージェンティックエンジニアリングは定着したということ、開発はプロジェクトのワークフロー・実装の技法・インフラストラクチャにまたがって設計されるということ、そして本当に重要なのはフィードバックループを決定的に閉じること、構造化された地点に人間を挿入すること、そしてセッションを短く保つことである。
