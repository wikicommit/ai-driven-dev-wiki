Kiro は2025年7月に発表された AI IDE であり、構想から本番までを AI エージェントとともに進める手立てとして提示されている。その発表 [[BlogPosting/introducing-kiro]] は、これを [[DefinedTerm/vibe-coding]] が得意でありながらその先を狙うものとして位置づけている。強みとして掲げられているのはプロトタイプを本番システムへ乗せることであり、そのために中心と名指された2つの機能が **spec** と **hooks** である。

発表が提示する問題の枠組みは、プロンプト駆動の開発が置き去りにするものである。プロンプトを繰り返して作られたアプリケーションは動作するが、モデルが置いた前提は文書化されず、要件は曖昧なままで、システムの設計は再構成しがたい。そのためアプリケーションが要件を満たしているのか、設計が性能や環境にどう影響するのかを判断するのが難しくなる。

## 概要

発表は Kiro の spec のワークフローを3ステップの流れとして記述している。*「商品にレビュー機能を追加して」*のような1つのプロンプトから、Kiro は関連するケースを網羅するユーザーストーリーを生成し、それぞれに EARS（Easy Approach to Requirements Syntax）記法で書かれた受け入れ基準を付す。プロンプトの前提を明示化するためだ、というのが述べられた根拠である。次いで発表によれば、コードベースと承認済みの要件を併せて分析し、設計ドキュメント——データフロー図、TypeScript のインターフェース、データベーススキーマ、API エンドポイント——を作る。最後にタスクとサブタスクを生成し、依存関係によって順序づけ、それぞれを要件へ紐づける。ユニットテスト、統合テスト、ローディング状態、モバイル対応、アクセシビリティ属性といった細部は個々のタスクに付される。

発表はさらに、タスクが進捗表示とともに1つずつ起動されること、完了した作業がコードの差分とエージェントの実行履歴を通じて監査できること、そして spec が進化するコードベースと同期し続けることを述べている。開発者はコードを書いてから Kiro に spec の更新を頼むことも、spec を手で編集してタスクを再生成することもできる。実装の途中で当初の成果物が更新されなくなるというよくあるパターンへの処方として提示されている。これらはいずれも製品チーム自身の主張であり、出典に独立した検証は存在しない。

## 機能

- **Specs**——プロンプトから生成され、コードベースと同期し続ける要件、設計、タスクの成果物。[[DefinedTerm/spec-driven-development]] を参照。
- **Hooks**——ファイルの保存、作成、削除、あるいは手動の起動でバックグラウンドのエージェントを発火させるイベント駆動の自動化。Kiro は平易な言葉のプロンプトを受け取り、そこから最適化されたシステムプロンプトを生成し、監視するリポジトリのフォルダを選ぶ。発表は、いったんフックが Git にコミットされれば、その標準がチーム全体に強制されると述べている。[[DefinedTerm/agent-hooks]] を参照。
- 専門特化したツールを接続するための **Model Context Protocol のサポート**。
- プロジェクト全体で AI の振る舞いを導く **Steering rules**。
- ファイル、URL、ドキュメントのコンテキストプロバイダを備えた、その場のタスクのための **エージェンティックチャット**。
- **Code OSS の上に構築**されており、既存の VS Code の設定と Open VSX 互換のプラグインをそのまま引き継げる。

### これを用いた報告事例

[[BlogPosting/three-week-drug-discovery-agent-using-kiro]] は、AWS のチームが Kiro で本番エージェントを構築した日付の明らかな記録であり、発表が記述する成果物をより具体的な言葉で名指している。各機能の仕様は順に作られ、それぞれ次に進む前にレビューされる3つのファイルである。機能要件、受け入れ基準、成功指標のための `requirements.md`。技術アーキテクチャ、実装アプローチ、統合ポイントのための `design.md`。そして設計を「より広い機能についての文脈を保ちつつ、自律的な実行に足るだけの粒度」のステップへ分解する `tasks.md` である。同記事はまた Kiro を「仕様駆動（spec-driven）開発を軸に構築された最初の AI コーディングツール」とも呼んでいるが、これはベンダーとしての主張である。

Steering はそこでは、チームが書いたプロジェクト全体の3つのドキュメントとして記述されている。目的と主要な能力を定義する `product` ドキュメント、ツールの抽象化パターンやエラーハンドリングの標準といった組織的原則を強制する `structure` ドキュメント、そしてスタックと開発ガイドラインを定める `tech` ドキュメントであり、文脈として自動的に追加され、スコープによって仕様と区別される。steering はプロジェクト全体を、仕様は1つの機能を扱う。フックは原理としてではなく使われ方として記述されている。ファイルシステムのイベントを監視し、コードの変更に合わせて `README.md` を最新に保つためにあらかじめ定義されたプロンプトをバックグラウンドで実行した。フックはリポジトリレベルに置かれるため、チェックアウトすればチーム全体がこの自動化を得られる。

同じ記事は2つの能力を、そのプロジェクトで使われたものとしてではなく今後の方向性として挙げている。**Kiro Powers** は、文脈とツールをオンデマンドで読み込む専門特化された専門性モジュールとして記述され、MCP ツール、ステアリングファイル、フックを領域のベストプラクティスとともに束ね、関連する場合にのみ有効化することで、記事が「従来の MCP サーバのコンテキスト過負荷問題」と呼ぶものに対処する。MCP の設定の代わりにワンクリックでインストールできるという。**Kiro Autonomous Agent** は、非同期のチームメイトとしてソフトウェア開発の仕事を担うことを意図したフロンティアエージェントとして記述され、Kiro IDE 内ですでに構築されたエージェントから学び、絶えざる人間の導きなしにそれらのパターンを再利用できるとされている。

## 沿革

Kiro は2025年7月14日に Nikhil Swaminathan（プロダクトリード）と Deepak Singh（VP DevEx & Agents）によって発表された。発表時点ではプレビュー期間中は一定の制限つきで無償であり、待機リストによるゲートがかけられ、Mac、Windows、Linux と主要なプログラミング言語の多くをサポートしていた。発表は、チーム間の設計の整合、相反する要件の解消、技術的負債の解消、コードレビューにおける厳密さ、そしてシニアエンジニアが去るときの組織知の保全といったより広いロードマップを、出荷済みの能力としてではなくチームが目指している方向として記述している。
