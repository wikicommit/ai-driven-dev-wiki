GitHub Copilot コードレビューは [[SoftwareApplication/github-copilot]] の機能であり、Copilot がプルリクエストをレビューし、問題を特定し、数回のクリックで適用できる修正を提案する。GitHub のドキュメントによれば、あらゆる言語で書かれたコードをレビューし、変更を複数の観点から検討する。これは、調整されたモデル、プロンプト、システム挙動の組み合わせを用いる専用製品として説明されており、モデルの切り替えは意図的にサポートされていない。ドキュメントが挙げる理由は、モデルを変更すると信頼性、ユーザー体験、レビューコメントの品質が損なわれる可能性が高いというものである。

ドキュメントは、この機能を利用できる環境として GitHub.com、GitHub CLI、GitHub Mobile、VS Code、Visual Studio、Xcode、JetBrains IDE、そしてパブリックプレビューの Azure DevOps を挙げている。また、Copilot を組織から提供されている場合、GitHub.com と GitHub Mobile でレビューを行うには、その組織が Copilot コードレビューのポリシーを有効にする必要があると記している。Copilot Business と Copilot Enterprise のプランでは、管理者が 2 つのポリシーを有効にすることで、Copilot ライセンスを持たない組織メンバーにも GitHub.com でのアクセスを付与できる。この経路は IDE では利用できないとされている。

ドキュメントは、この機能が人間によるレビューの代わりにはならないことを明言している。Copilot はすべての問題を見つけることが保証されておらず、ときに誤りを犯すとされ、そのフィードバックは慎重に検証し、人間によるレビューで補うべきだとしている。

[[BlogPosting/60-million-copilot-code-reviews-and-counting]] における GitHub 自身の製品目標の説明によれば、2024 年に開発を始めた後、目標は網羅性から、プルリクエストを素早く前に進める助けとなるシグナルの高いフィードバックへと移り、正確性、シグナル、速度を指標とする継続的な評価ループを通じて調整されてきた。この説明では、この機能は言うべき価値のあることがないときには意図的に沈黙する。GitHub は、レビューの 71% で実行可能なフィードバックを提示し、残りでは何も言わないと報告している。また、より良い指摘のためにはレビューが遅くなることも受け入れるとし、肯定的なフィードバックを 6% 高める一方でレイテンシを 16% 増加させたあるモデル変更を例に挙げている。

## 機能

2026 年 3 月 5 日付の GitHub の changelog エントリは、Copilot コードレビューがエージェント型のツール呼び出しアーキテクチャ上で動作するようになり、必要に応じてより広いリポジトリコンテキスト（関連コード、ディレクトリ構造、参照）を収集することで、変更がより大きなアーキテクチャにどう適合するかをフィードバックに反映させること、そしてこれが一般提供されたことを告知した。同日の GitHub のブログ記事は、この再設計をより詳しく説明している。エージェントはリポジトリを探索してロジック、アーキテクチャ、不変条件を理解する。問題を最後にまとめて確定するのではなく読みながら記録する（GitHub によれば、前者のやり方では初期の発見を「忘れる」ことが多かった）。レビューをまたいでメモリを保持でき、コードベースのある部分で指摘されたパターンを後のレビューに生かせる。長く複雑なプルリクエストではレビュー戦略を事前に立てる。そして、リンクされた issue やプルリクエストを読み、単体では妥当に見えるがプロジェクトの要件に合わないコードを見つける。GitHub は、この転換によって肯定的なフィードバックが当初 8.1% 増加したとしている。同記事は、これと併せて行われた表示面の変更も説明している。コメントを単一行ではなく複数行のコード範囲に付けること、同じパターンのエラーの繰り返しを 1 つのコメントにクラスタ化すること、そして提案された修正の 1 クラス全体を一度に適用する一括自動修正である。

これとは別に、製品ドキュメントは基本的なレビューを拡張する 2 つのエージェント型機能を説明している。1 つ目はプロジェクト全体のコンテキスト収集で、リポジトリ全体を分析して変更のコンテキストをよりよく理解する。2 つ目は Copilot クラウドエージェントへ提案を引き渡す機能で、提案された修正を適用した新しいプルリクエストをそのブランチに対して作成する作業を自動化する（パブリックプレビューであり、変更される可能性があるとされている）。どちらも、この機能を含むすべてのプランで自動的に有効になる。これらは GitHub Actions 上で動作し、デフォルトでは標準の GitHub ホストランナーを使い、より大きな GitHub ホストランナーやセルフホストランナーも選択できる。これらが動作するために組織で GitHub Actions を有効にしておく必要はないが、GitHub ホストランナーが無効化されている場合はこれらの機能は利用できず、レビューはより限定的な形にフォールバックする。Actions が利用できない場合やワークフローが失敗した場合でも、レビュー自体はこれらの機能なしで生成される。

レビューの負荷レベルは 2 つ用意されている。デフォルトの Lite は、バグ、セキュリティ脆弱性、スタイルの不統一といった一般的な問題について、素早く的を絞ったフィードバックを返す標準的なレビューと説明されている。Balanced はプルリクエストをより推論能力の高いモデルに回し、複雑なロジック、セキュリティ上重要なコード、サービスをまたぐ変更をより時間をかけて分析する。その分 AI クレジットを多く消費し、Actions の実行時間もわずかに増える可能性がある。ドキュメントは、セキュリティ上重要なコード、複数サービスにまたがるプルリクエスト、厳格な品質基準を持つリポジトリには Balanced を、網羅的な分析よりも素早いフィードバックが重要な場合には Lite を推奨している。使用された負荷レベルは、各実行後にプルリクエストの概要コメントに表示される。

レビューは依頼によるだけでなく自動にもできる。デフォルトでは、Copilot はレビュアーとして割り当てられたときにのみプルリクエストをレビューする。Copilot Pro または Pro+ の個人ユーザーは自分のすべてのプルリクエストを自動レビューの対象にでき、リポジトリオーナーはリポジトリ単位で、組織オーナーは一部またはすべてのリポジトリでこれを有効にできる。トリガーは設定によって異なる。基本設定ではプルリクエストが作成されたときと、ドラフトが初めてオープンに切り替えられたときに発火し、さらに新しくプッシュされたコミットごとのレビューやドラフトのレビューのための設定もある。プッシュごとにレビューするよう設定しない限り、Copilot は 1 つのプルリクエストを 1 回だけレビューする。

すべてのレビューには、Copilot がそのプルリクエストを承認可能と判断したかどうかを示す承認判定が概要コメントに含まれ、デフォルトではこれは必須承認数には数えられない。Copilot による承認（パブリックプレビューとされている）はリポジトリ、組織、エンタープライズの設定で有効にでき、有効にすると Copilot はチームメイトの承認と同様に必須承認ルールを満たす承認レビューを提出できる。その後に新しいコミットがプッシュされると、この承認は取り消される。

一部のファイル種別はレビューの対象外である。`package.json` や `Gemfile.lock` などの依存関係管理ファイル、ログファイル、SVG ファイルがそれにあたる。

## 採用状況とエコシステム

ドキュメントは、レビューが参照できる 4 つのカスタマイズの仕組みを説明し、それらをスコープによって区別している。`.github/copilot-instructions.md` は Copilot 固有の、リポジトリ全体に常に適用されるルールを保持する。`.github/instructions/` 配下のパス固有の `*.instructions.md` ファイルは、特定のパスやファイル種別に限定して常に適用されるルールを保持する。リポジトリのルートにある [[DefinedTerm/agents-md]] は、AI ツールやエージェントのあいだで共有されることを意図した、常に適用されるルールを保持する。そして `.github/skills/` 配下のスキルは、オンデマンドで、あるいは関連する場合に自動的に実行されるタスク固有のワークフローを保持する。GitHub はこの違いを、「Copilot よ、このリポジトリについて常にこれを知っておけ」「どのエージェントも、常にこれを知っておけ」「必要なときにこれをせよ」という対比でまとめている。

リポジトリレベルの [[DefinedTerm/agent-skills]] と [[DefinedTerm/model-context-protocol]] サーバーは、いずれも関連する場合にはレビュー中に利用できる。ドキュメントによれば、Copilot はカスタム指示、エージェント指示、スキルをベースブランチではなくヘッドブランチから読み込むため、それらへの変更は、その変更を導入するのと同じプルリクエストの中でテストできる。また、スキルや MCP が使われやすくなる条件も説明している。レビューに焦点を当てたスキルのディレクトリ名、MCP のコンテキストに言及するカスタム指示、そして issue キーやインシデント ID などの識別子を含むプルリクエストの説明文である。GitHub MCP サーバーと Playwright MCP サーバーはデフォルトで有効になっており、リポジトリの MCP 設定はクラウドエージェントとコードレビューの両方に適用される。レビュー中の MCP ツールの使用を許可するリポジトリ設定はデフォルトでオンになっており、レビューについてのみ無効にすることもできる。Copilot Pro、Pro+、Max のプランでパブリックプレビューとして提供されている Copilot Memory により、Copilot はリポジトリについて学んだ詳細を保存し、レビュー時に利用できる。

GitHub は GitHub Code Quality を、代替ではなく補完するものとして位置づけている。コードレビューがプルリクエストの変更を見るのに対し、Code Quality はプルリクエストとデフォルトブランチに対するルールベースの CodeQL による分析、テストカバレッジの指標、クラウドエージェントへの委任を含むワンクリックの Copilot による修正、そしてルールセットによる任意のマージゲートを加える。

利用量は AI クレジットで計測され、ドキュメントはコストが 2 つの要素から成るとしている。モデルとのやり取りに対するクレジットと、エージェント型機能に対する Actions の実行時間である。レビュー 1 回あたりの固定価格は公表しておらず、代わりにモデルの進化に伴って変わる可能性があるとする推定範囲を示し、消費量は一般にプルリクエストの規模やリポジトリのカスタム指示に応じて増えると記している。利用量の帰属は依頼者に従う。自動レビューはプルリクエストの作成者に、手動で依頼されたレビューは依頼者に帰属し、クラウドエージェントが作成したプルリクエストについては、まず人間の共同作成者に、いなければ組織に帰属する。Copilot ライセンスを持たないユーザーにアクセスが付与されている場合、その消費は個人の予算ではなく、組織またはエンタープライズに直接請求される。Copilot Business と Copilot Enterprise では、ユーザーレベルの予算に達するか、エンタープライズまたはコストセンターの支出上限を使い切ると、他のクレジットを消費する機能とともにコードレビューもブロックされる。
