Agentic SDLC Spec Kit は、Tikal のエンジニアリングチームが保守する [[SoftwareApplication/github-spec-kit]] のフォークである。掲げられているビジョンは、Agentic SDLC 12 Factors の方法論と [[DefinedTerm/spec-driven-development]] を組み合わせることである。このフォークは 12 Factors を、戦術的な SDD プロセスの上に位置する戦略レイヤーとして提示し、AI コーディングエージェントでソフトウェアを構築するための哲学的・戦略的な原則であると説明している。その対象には戦略的マインドセット、コンテキストの足場づくり（context scaffolding）、デュアル実行ループ、チームの能力といった事柄が含まれ、一方で SDD は仕様化、計画、タスク分解、実装という具体的なフェーズを担う。

このフォークは、上流のリポジトリが仕様駆動開発の中核プロセスに焦点を当ててきたと述べ、自らをその基盤を AI ネイティブな開発のための完全かつ独自色の強いプラットフォームへと拡張するものと位置づけている。プロジェクト自身の言葉を借りれば、開発プロセスから組織的な方法論への転換である。MIT ライセンスで公開されており、フォーク自身のリポジトリから、`agentic-sdlc-v` という接頭辞を持つリリースタグの下で `agentic-sdlc-specify-cli` としてインストールする。これに合わせて、`specify self check` と `specify self upgrade` もフォークを指すように変更されている。前提条件は、Linux・macOS・Windows のいずれか、サポートされている AI コーディングエージェント、Python 3.11 以降、Git、そしてインストール用の `uv` または `pipx` である。

## 機能

このフォークは追加機能を、戦略レイヤー、CLI アドオン、同梱エクステンション、同梱プリセット、実行面の強化に分けて整理している。最初に来るのは戦略レイヤーである。12 Factors と並んで、ルール、ペルソナ、例、スキルからなる `team-ai-directives` ナレッジベースがバージョン管理され、プロジェクト間で同期される。これはプロジェクト作成時に `--team-ai-directives` フラグを通じて組み込まれ、このフラグはローカルディレクトリ、GitHub または GitLab のアーカイブ URL、あるいはアーカイブへの直接の URL を受け付ける。`levelup` コマンドは完了したセッションを再利用可能な Context Directive Records に変換し、それらがこのナレッジベースに還元される。プロジェクトはこれを、プロジェクト横断の学習ループを閉じるものと説明している。プライベートなナレッジベースには、ホストとトークンを保持する環境変数を指定するプロバイダー設定ファイルを通じてアクセスする。

次に、中核の SDD を超える同梱エクステンション群がある。アーキテクチャへの影響分析と意思決定記録のための `architect`、プロダクト思考とユーザーストーリーの洗練のための `product`、テスト駆動のワークフローのための `tdd`、評価駆動開発のための `evals`、ブランチまたはワークツリーの自動化のための `git`、セッションのナレッジ管理のための `levelup`、そして監督モードと安全のためのガードレールを備えた、ミッション駆動の SDLC 自動化のための `workflow` である。

続いて同梱プリセットがある。これは、ツールキットが何をできるかではなく、どう振る舞うかを積み重ね可能な形でカスタマイズするものである。`agentic-sdlc` は specify、plan、tasks、implement、converge という全ライフサイクルをカバーしてプリインストールされており、セッションベースのアドホックな実行のための `agentic-quick` も同様にプリインストールされている。軽量な変更提案ワークフローである `agentic-change` はオプトインである。プロジェクトが 2 つのカスタマイズの仕組みの間に引く区別は、エクステンションが新しい能力を追加するのに対し、プリセットはコアとエクステンションがすでに提供しているテンプレートとコマンドを上書きする、というものである。どちらも同じ優先順位のスタック — プロジェクトローカルの上書き、プリセット、エクステンション、コアのデフォルトの順 — で解決されるが、そのタイミングは異なる。テンプレートは実行時に解決され、スタックを上から順にたどって最初に一致したものが使われる。一方、エクステンションとプリセットのコマンドはインストール時に適用され、`specify extension add` または `specify preset add` によってエージェントのコマンドディレクトリに書き込まれる。このとき最も優先度の高いバージョンが採用され、削除時には次に優先度の高いものが自動的に復元される。
バンドルはその両者の上に位置し、厳選されバージョンが固定されたエクステンション、プリセット、ステップ、ワークフローの組をパッケージ化する。これにより、優先順位付けされたカタログのスタックから、チームのロール全体を 1 つのコマンドでプロビジョニングできる。

最後は実行面である。タスクのオーケストレーションは DAG を考慮しており、ウェーブ単位の並列または逐次実行のためのタスクグラフを生成する。デュアル実行ループは各タスクを、即時に処理する `[SYNC]` か、後回しにして処理する `[ASYNC]` に分類する。そして各フィーチャーを独自の Git ワークツリーに分離でき、上流の `git` エクステンションの上にタスクブランチのワークフローが重ねられている。

これらはコーディングエージェントに対して、いくつかのコマンド名前空間として提示される。`/spec.*` は中核のライフサイクルを実行する。すなわち、プロジェクトの原則の確立、任意のブレインストーミング、specify、clarify、plan、tasks、analyze、implement、converge である。`converge` は仕様、計画、タスクに照らしてコードベースを評価し、収束した後にはテストゲート、差分分析、4 本柱の品質評価を実行する。`/change.*` と `/quick.*` はより軽量な変更提案とセッションベースの経路であり、`/workflow.*` はミッションの評価、実行、再開、永続化を扱う。スキルモードをサポートするインテグレーションでは、同じコマンドがスラッシュコマンドのプロンプトファイルではなくエージェントスキルとしてインストールされる。このフォークは Claude Code、GitHub Copilot、Cursor、Gemini CLI、opencode、Qwen、Codex、Windsurf、Junie を含むさまざまなコーディングエージェントのサポートを挙げており、全体についてはインテグレーションのリファレンスを参照するよう案内している。

## 採用とエコシステム

このプロジェクトは Tikal のエンジニアリングチームによって保守され、独自のドキュメントサイトと issue トラッカーを備えて GitHub 上でオープンに開発されている。上流の問題は代わりに上流のリポジトリへ報告するよう案内されている。謝辞では、このプロジェクトが John Lam の仕事と研究、およびオリジナルの Spec Kit プロジェクトから強い影響を受け、それらに基づいていると述べられている。
