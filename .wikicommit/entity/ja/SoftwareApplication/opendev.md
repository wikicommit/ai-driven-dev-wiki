OpenDev はソフトウェアエンジニアリングのための、オープンソースでコマンドライン向けの AI コーディングエージェントであり、[[ScholarlyArticle/building-effective-ai-coding-agents-for-the-terminal]] に記録されている。そのアブストラクトは、Rust で書かれ、ターミナルネイティブなパラダイム——エージェントが IDE のプラグインとしてではなく、開発者がソース管理を行い、ビルドを実行し、環境をデプロイするまさにその場所で直接動作する——のために特別に設計されたものと記述している。

その中心的な設計原理は、これが*複合 AI システム*であるということだ。単一のモノリシックな LLM ではなく、それぞれがユーザー設定のモデルへ独立に束縛されたエージェントとワークフローの構造化されたアンサンブルである。レポートはこれをセッション、エージェント、ワークフロー、LLM という4階層として枠づけ、きめ細かいモデル選択によってコスト、レイテンシ、能力のトレードオフをワークフローごとに最適化できるとする。著者が強調する帰結は、構成上モデル非依存であることだ。プロバイダの切り替えやコストの最適化には、コードの変更ではなく設定の変更だけで足りる。

システムを導く3つの設計原則が述べられている。関心の分離——モデルの選択、コンテキストの管理、安全性の強制、ツールのディスパッチが独立に設定可能かつ置き換え可能であること。漸進的な劣化——トークンの予算、反復回数、ネットワーク接続が尽きても、システムが優雅に機能し続けること。そして魔法よりも透明性——ツールの呼び出し、安全性による拒否、コンテキストのコンパクション、メモリの更新といったシステムのあらゆる行動が、開発者から観察可能であり上書き可能であること。

## 概要

アーキテクチャは4つの層に組織されている。Entry と UI の層は2つのフロントエンド——ターミナル UI とウェブ UI——をサポートし、共通のコールバック契約を共有することで、エージェント層をインターフェース非依存に保つ。Agent の層は5つの専門特化したモデルの役割（action、thinking、critique、vision、compaction）を別々の LLM へ割り当て、拡張された ReAct ループを回す。Tool と Context の層はレジストリを通じてツール呼び出しをディスパッチし、モデルのコンテキストウィンドウを管理する。Persistence の層は設定、セッションのトランスクリプト、プロバイダのメタデータ、ロールバックのための操作ログを、外部のデータベースを必要とせずディスク上の通常のファイルとして保存する。

推論のループは標準的な ReAct のサイクルを、ツールへのアクセスなしで走る明示的な thinking フェーズと任意の自己批評フェーズによって拡張する。述べられた根拠は、ツールが利用可能なときモデルは深く考えるよりも素早く行動する傾向があること、そして振る舞いを変えるのはツールを使うなという指示ではなく、API 呼び出しからツールスキーマが存在しないことそのものだ、というものである。4段階の thinking の深さによって、ユーザーはタスクごとにレイテンシと熟慮の質を釣り合わせることができ、最も深い段階では自己批評が自動的に含まれる。

計画はモードの状態機械ではなく委譲によって扱われる。計画が必要なとき、主エージェントは Planner サブエージェントを生成する。そのスキーマには読み取り専用のツールしか含まれていないため、書き込み操作は実行時にブロックされるのではなく構造的に不可能である。Planner はコードベースを探索し、得られた知見を分析し、構造化された計画ファイルを書く。主エージェントはそれを実行に進む前にユーザーへ提示して承認を求める。

## 機能

**コンテキストエンジニアリング。** [[DefinedTerm/adaptive-context-compaction]] は、ハードな上限での単一の緊急コンパクションではなく、コンテキストの圧力が高まるにつれて5段階の漸進的に強い削減を適用する。ツールの実行結果はツール種別ごとの要約器を通り、サイズの閾値を超える出力は短いプレビューと参照パスとともにスクラッチファイルへ退避される。二重メモリのアーキテクチャは、直近メッセージの逐語とともに全履歴のエピソード的な要約を thinking のモデルへ供給し、会話の長さによらず thinking の予算を有界に保つ。

**振る舞いの舵取り。** [[DefinedTerm/system-reminders]] は、長いセッションにおける注意の減衰に対抗するために判断の時点で注入される、短く単一目的のメッセージである。それぞれがカウンタまたはワンショットのフラグによって統べられており、リマインダーが雑音へ堕することがない。

**安全性。** 5つの独立した層が、抽象度を段階的に下げながら危険な行為を差し止める。プロンプトレベルのガードレール、スキーマレベルのツール制限、3段階の自律性レベルとプロジェクトごとの永続的なルールを備えた実行時の承認システム、危険なパターンのブロックリストと古い読み取りの検知を含むツールレベルの検証、そしてツール呼び出しをハードにブロックできるユーザー定義のライフサイクルフックである。ファイルを変更するエージェントの各ステップで取られるシャドー git のスナップショットが、ステップ単位の取り消しを提供する。ユーザー自身の履歴とは何も共有しないベアリポジトリを用いる。

**ツール。** システムには組み込みのツールのカタログが同梱されている。ファイル操作、長時間走るサーバを自動的にバックグラウンドへ昇格させるシェル実行、ウェブとの対話、Language Server Protocol を介した多言語の意味的なコード解析、タスクの追跡、そしてサブエージェントへの委譲にまたがる。外部のツールは Model Context Protocol サーバに対するキーワード検索を通じて遅延的に発見される。レポートは、これにより MCP 統合の起動時のコンテキストコストが予算の 40% から 5% 未満へ下がったと述べている。`edit_file` ツールは、段階的に緩められる9つの照合パスの連鎖を実装しており、末尾の空白、インデントのずれ、エスケープシーケンスの違いといった惜しい編集対象が、エラーではなく成功した編集になる。

**サブエージェント。** 8種類のサブエージェントが定義され、それぞれがフィルタされたツールの集合に制限されている。Code-Explorer、Planner、PR-Reviewer、Security-Reviewer、Web-Clone、Web-Generator、Project-Init、Ask-User である。1つの応答のなかで複数の生成呼び出しを出すと、自動的な並列実行が起動される。

## 沿革

レポートはリリースの年表ではなくシステムの設計の変遷を記録しており、いくつかのアーキテクチャ上の転換を挙げている。エージェント種別の初期のクラス階層は、パラメータ化された単一のエージェントクラスへ置き換えられた。システムプロンプトの遅延構築は、初回呼び出しのレイテンシとツール発見との競合を取り除くために先行構築へ置き換えられた。4ツールからなる plan モードの状態機械は、エージェントが plan モードから抜けられないことがあったため Planner サブエージェントへの委譲に置き換えられた。サブエージェントは当初、主エージェントと同じツールを持っており、それがコンテキストの汚染と役割の混乱を招いた。そしてスキルは当初起動時に読み込まれていたが、のちにメタデータのインデックスとオンデマンドの読み込みへ分割された。
