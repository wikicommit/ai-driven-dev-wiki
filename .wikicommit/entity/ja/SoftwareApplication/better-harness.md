Better Harness は、AI コーディングエージェントを取り巻くワークフローを分析・改善するためのオープンソースツールであり、QoderAI が MIT ライセンスで公開している。README はその考え方を「Delegate coding to agents. Improve the loop around them」（コーディングはエージェントに委ね、エージェントを取り巻くループを改善せよ）と要約している。このツールは開発者がすでに使っているコーディングエージェントを通じて動作し、プロジェクトの証拠（およびサポートされているホストではセッションの証拠）を収集して、それを優先順位付けされた改善策と検証可能な次のステップに変換する。リポジトリ自身の説明では、コーディングエージェントのための [[DefinedTerm/harness-engineering]] プラットフォームとされている。

このツールが扱う問題は、最終的な差分をレビューするだけでは見えない問題として位置づけられている。README は、エージェントを取り巻くワークフローがうまくいかなくなる 5 つのパターンを挙げている。目標があいまいなためにエージェントが自信満々に間違った問題を解いてしまうこと、誰も再現できない場当たり的な手順、証拠のない「動きます」という主張、速度のためにレビューや納品時のチェックが省かれること、そして教訓が失われて次のタスクで同じ摩擦が再発することである。Better Harness は、こうしたシステムレベルの問題を代わりに分析するものとして位置づけられている。

## 機能

Better Harness は、その分析をフィードフォワードとフィードバックのループを軸に組み立てており、この枠組みについては Martin Fowler のサイトを引用している（[[DefinedTerm/guides-and-sensors]] を参照）。`AGENTS.md`、仕様、スキル、受け入れ基準といったフィードフォワードのガイドが、エージェントが行動する前にそれを方向づけ、リンター、テスト、フック、評価エージェントといったフィードバックのセンサーが結果を観測してエージェントの自己修正を助ける。このループ全体にわたって、Better Harness は **Agent Work Loop** と呼ぶ納品の 5 つの次元を評価する。

| 次元 | 問いかける内容 |
| --- | --- |
| Task Understanding | エージェントは目標と「完了」の意味を理解しているか |
| Controlled Execution | 作業はサポートされた、再現可能な経路の上で行われているか |
| Change Validation | 変更が実際に機能するという証拠はあるか |
| Reliable Delivery | AI の速度が品質チェックや受け入れを迂回していないか |
| Learning Capture | 次のタスクはこのタスクから恩恵を受けるか |

`/better-harness` ワークフローを実行すると、タスクの範囲に限定したベースラインが確立され、5 部構成の概要、優先順位付けされた指摘事項、検出されたエージェントアセット、証拠の要約を組み合わせたレポートが生成される。各指摘事項はその証拠に結びつけられ、影響、期待される出力、範囲を限定した修正、受け入れチェックを伴う。修正アクションは、レビュー用に範囲を限定した修正計画を下書きする。レポートはホストに応じて、ホストネイティブの Canvas（Qoder と Cursor）か、Markdown と対になった自己完結型の HTML ファイル（Claude Code、Codex、Qwen Code、GitHub Copilot、Kimi Code）になる。比較可能なレポートが時間の経過とともに蓄積されると、履歴ビューで 5 つの次元の推移を確認できる。ただしプロジェクトはこれを、改善の因果的な証明ではなく記録された傾向として提示している。これとは別に、対話型の Harness Inspector が、読み取り専用のワークスペースの中で、プロダクトの意図からエージェントの活動、セッション、ファイル、コミットまで納品の流れを追跡する。

プロジェクトは、欠けている証拠が明示されたままであることを強調している。観測されていない振る舞いは、根拠のないスコアに変えられるのではなく、観測されていないものとして報告される。README はその境界を次のように引いている。設定されたアセットはある仕組みが存在することを示せるが、それが使われたことや成果を改善したことを示せるのは、関連づけられたタスクの証拠だけである。内部では、3 つの独立した証拠エージェントがそれぞれ別の領域から収集を行い、単一のリードエージェントがその結果を統合する。

リポジトリが公開しているものは、相互に結びついた 3 つの層として説明されている。エンジニアリングプラクティスのガイダンス（セッションの証拠、プロジェクトのハーネス、エージェントのカスタマイズ、[[DefinedTerm/loop-engineering]] を扱う）、Agent Work Loop 評価モデル、そして実行可能な実装である。実装は、[[DefinedTerm/agent-skills]] のスキルとしてパッケージ化された正規の `/better-harness` ワークフローと、証拠コレクター、アナライザー、レンダラー、ホストごとの薄いアダプターからなる。スタンドアロンの CLI は、すべてのホストについてローカルのインストール状況の証拠を調べ、ホストごとのインストール、更新、削除の計画を、実行はせずに作成できる。

## 採用とエコシステム

Better Harness はホスト間で単一のエントリーポイントを使わず、コーディングエージェントごとに個別にインストールされる。多くの場合、各ホストのマーケットプレイスの仕組みを通じたプラグインとしてである。README は、[[SoftwareApplication/claude-code]]、Codex Desktop と Codex CLI（[[SoftwareApplication/openai-codex]]）、[[SoftwareApplication/qoder]]、[[SoftwareApplication/cursor]]、[[SoftwareApplication/github-copilot-cli]] についてはその場でセットアップ手順を示し、Qwen Code、Pi、Kimi Code、WorkBuddy、Grok についてはドキュメントを参照するよう案内している。Qoder デスクトップアプリには組み込まれており、インストールは不要で、Qoder の Quest ビューのサイドバー項目からもアクセスできる。デスクトップアプリと併せてインストールされた Qoder CLI も、これを認識する。Cursor プラグインはマーケットプレイスに公開されていないため、ツールは検証されていないコマンドを出力する代わりに、Cursor のインストール計画を利用不可と報告する。セッションの証拠は各ホストが何を記録しているかに依存する。たとえば GitHub Copilot については Copilot CLI のトランスクリプトを読み取るが、Copilot は応答ごとのトークン使用量を記録しないこと、そして VS Code の Copilot Chat にはサポートされた永続的なトランスクリプトがないことを注記している。
