Spec Kit は仕様駆動開発のツールキットである。そのドキュメントは [[DefinedTerm/spec-driven-development]]——仕様が実行可能となり、動く実装を直接生成するプロセス——を定義し、そのアプローチの中核的な哲学、開発のフェーズ、実験上の目標を提示している。

プロジェクト自身のサイトは、このツールを SDD だけよりも広く枠づけており、Spec Kit を「任意のコーディングエージェントをコードの先へ押し出し、あなたの SDLC や任意の業務プロセスにわたって導く、拡張可能で意図駆動のハーネス」と記述し、SDD をこのツールが支える唯一のプロセスとしてではなく、すぐに使える状態で同梱されているプロセスとして提示している。冒頭に掲げられるタグライン——「仕様駆動開発、あるいはあなた自身のプロセスを、ステップごとに、あるいは自動化されたワークフローとして」——も同じ切り分けを述べている。デフォルトのプロセス、自動化の層、そしてプロセスをまるごと差し替える選択肢である。

## 概要

Spec Kit に同梱される中核のプロセスは **Spec → Plan → Tasks → Implement** であり、サイトは各フェーズが次へ供給される Markdown の成果物を生み出すため、コーディングエージェントが場当たり的なプロンプトではなく構造化された文脈を受け取ると記述している。豊富なテンプレート、品質チェックリスト、成果物横断の分析が最初から備わっているとされる。

Spec Kit は、要件が変わった後にチームが `spec.md`、`plan.md`、`tasks.md` の各ファイルをどう保全あるいは変更するかを意図的に規定していない。そのドキュメントはこれを別個の主題として扱い、仕様の永続化モデルと、既存プロジェクトにおける仕様を進化させるワークフローのもとで扱っている。

このツールは `specify` という名の CLI を通じてインストールされ操作される。サイトは `uv tool install specify-cli` に続けて `specify init my-project --integration copilot` という2行のクイックスタートを示している。エージェントを選んで `specify init` を実行すると、対応するコマンドファイルとディレクトリ構造が自動的に用意される。

## 機能

ドキュメントは Spec Kit の取り組みを、4つの掲げられた目標を持つ研究と実験として枠づけている。技術からの独立——多様な技術スタックを用いてアプリケーションを作れること、そしてプロセスが特定の技術、プログラミング言語、フレームワークに縛られないこと。企業の制約——ミッションクリティカルなアプリケーション開発、クラウドプロバイダ・技術スタック・エンジニアリング実践といった組織的な制約、そして企業のデザインシステムとコンプライアンス要件を扱うこと。ユーザー中心の開発——異なるユーザー層と好みに向けて、[[DefinedTerm/vibe-coding]] から AI ネイティブな開発までのアプローチを支えること。そして創造的で反復的なプロセス——並行した実装の探索、反復的な機能開発のワークフロー、アップグレードと近代化のタスクを含む。

**エージェントの統合。** プロジェクトのサイトは35の統合を掲げ、そのなかに Copilot、Gemini、Codex、Kilo Code、Zed、Claude、Forge、Kiro を挙げ、ユーザーは単一のコマンドでエージェント間を自由に切り替えられ、ロックインはないと述べている。リストにないエージェントには、逃げ道として `generic` の統合が提供されている。

**拡張性の層。** 中核のプロセスの上に4つの名前の付いた構成要素が乗る。プリセットがそれを調律し、拡張がそれに加え、ワークフローがそれをオーケストレーションし、バンドルが結果を共有のためにパッケージ化する。サイトは70人を超える作者による138のコミュニティ拡張と25のプリセットを報告し、プロセスそのものがこれらの構成要素の中に宿るため、ユーザーは「SDD にも、ソフトウェアにさえ、決して縛られない」と明言している。この方法で作られた6つの代替プロセスが挙げられている。AI 駆動のエンジニアリングライフサイクルを7段階で扱う AIDE。spec-first、code-first、spec-drift を扱うベースライン駆動のワークフロー Canon。SDD をプロダクトマネジメント寄りに捉え直した Product Forge。7つのフェーズにわたる端から端までの .NET Framework 移行 FX→.NET。品質保証のゲートを備えたマルチエージェントのオーケストレーション MAQA。そしてストーリーバイブルから投稿までを扱う長編小説のための Fiction Book Writing である。コンプライアンスのゲートとガバナンスを追加するものとして名指されているコミュニティ拡張には CI Guard と Architecture Guard がある。

**ワークフロー。** ワークフローのエンジンは、同じプロセスのための自動化の層である。Spec Kit のリファレンスドキュメントは、ワークフローが、コマンド、プロンプト、シェルのステップ、人間のチェックポイントを連ねて反復可能な手順にすることで、多段階の仕様駆動開発のプロセスを自動化するものだと記述している。条件分岐、ループ、ファンアウト／ファンインをサポートし、中断したまさにその地点から一時停止と再開ができる。11のステップ種別が文書化されている。`command`（Spec Kit のコマンドを呼び出す）、`prompt`（任意のプロンプトをコーディングエージェントへ送る）、`shell`、`init`、`gate`（人間の承認のために一時停止する）、`if`、`switch`、`while`、`do-while`、`fan-out`、`fan-in` である。実行は `.specify/workflows/runs/<run_id>/` の下に `state.json`、`inputs.json`、`log.jsonl` として状態を永続化する。これが `specify workflow resume` によって、実行が一時停止あるいは失敗したまさにそのステップから継続できる理由である。文書化されている実行状態は `created`、`running`、`completed`、`paused`、`failed`、`aborted` である。

このツールに同梱される組み込みのワークフロー `speckit`（「Full SDD Cycle」）は、人間のチェックポイントを明示的にしている。`specify` を実行し、`review-spec` のゲートで一時停止し、`plan` を実行し、`review-plan` のゲートで一時停止し、それから `tasks` と `implement` を実行する。いずれかのゲートで却下されると実行は中止される。

**オーバーレイ。** インストール済みのワークフローを編集する代わりに、プロジェクトはそこへオーバーレイを重ねられる。ベースとなるワークフローのステップリストに対する編集操作（`insert_after`、`insert_before`、`replace`、`remove`）を宣言する YAML ファイルであり、優先度によって解決され、数値の小さい方が勝つ。文書化された目的は、更新をまたいでローカルのカスタマイズを安全に保つことである。オーバーレイはインストール済みのワークフローのディレクトリの外に存在し、再インストールしても残るからだ。ドキュメントは限界も率直に述べている。オーバーレイはステップリストにのみ作用し、ワークフローのメタデータや入力スキーマを変更できず、他のオーバーレイが追加したステップを対象にできず、ファンアウトのテンプレートをアンカーとして使えない。

**カタログと配布。** ワークフローは固定の順序で解決されるカタログを通じて発見される。すべてに優先する環境変数 `SPECKIT_WORKFLOW_CATALOG_URL`、次にプロジェクトの設定、次にユーザーの設定、そして組み込みの公式およびコミュニティのカタログである。組織は自前のカタログをホストして、自社の開発者が発見するものを取捨選択できる。サイトは、このツールがオフラインでも、ファイアウォールの背後でも、Windows・macOS・Linux 上でも動作すると述べている。

**述べられているセキュリティ上の姿勢。** ワークフローのリファレンスは、このエンジンが何を保証*しない*かについて異例なほど率直であり、その留保は能力と並べて記録する価値がある。`shell` のステップはユーザー自身の権限でローカルのコマンドを実行するのであって、ケイパビリティのサンドボックスは存在しない。`requires` のブロックは実行時のゲートではなく助言的な事前条件であり、`requires.permissions` のケイパビリティゲートは、存在しないサンドボックスを含意してしまうがゆえに検証で却下される。式は引用符付けもエスケープも加えない素の文字列置換によって解決されるため、`run` のフィールドへ到達した補間値はシェルの構文として解釈される。ドキュメントはこのリスクが、ワークフローを実行する者が与えるワークフローの入力と、直前の `prompt` ステップの出力について最も鋭いと指摘する。後者は AI エージェントが生み出したテキストであり、エージェントが読んだファイル、チケット、ウェブのコンテンツによって左右されうるため、信頼できないものとして扱うべきだという。推奨される対策は、`enum` の許可リストによって値を源で制約すること、制約されていない値を `run` のフィールドから完全に締め出すこと、そして引用符付けをセキュリティの境界と見なさないことである。また `gate` のステップはその後に続くコマンドを表示もサニタイズもせず、その `message` を逐語的に出力するため、信頼できない素材は代わりに `show_file`——その内容は制御文字と ANSI が除去される——を通じて示すべきだと警告している。同じ主題について FAQ は、ほとんどのワークフローがそれぞれの作者によって独立に作られ保守されていること、そして Spec Kit のメンテナがワークフローのコードをレビュー・監査・推奨・サポートしていないことを述べている。

### 提唱者が示す7ステップのライフサイクル

[[BlogPosting/spec-driven-development-a-spec-first-approach-to-ai-native-engineering]] は、このツールのエンジニアリングのライフサイクルを、上記の4フェーズの中核プロセスではなく7つのステップとして提示し、両端に広げている。**Constitution**（原則、標準、ガードレールを定める）、**Specify**（要求、シナリオ、受け入れ基準を捉える）、**Clarify**（曖昧さ、依存関係、エッジケースを解消する）、**Plan**（意図をアーキテクチャ、フロー、制約へ翻訳する）、**Tasks**（作業を実装可能な単位へ分解する）、**Implement**（AI を用いてコードとテストを生成し洗練する）、そして **Validate**（出力が仕様と一致することを検証する）である。そのかたちの要約は「意図を定め、曖昧さを取り除き、制約とともに計画し、AI とともに実装し、仕様に照らして検証する」である。

同投稿はまた、プロジェクト自身のサイトが述べていない出自の主張も述べている。Spec Kit を「Microsoft によって作られたオープンソースのツール」と記述し、このワークフローと相性のよい AI コーディングツールとして [[SoftwareApplication/github-copilot]] を挙げている。これは Microsoft のブログにおける Microsoft 自身の特徴づけであり、そのようなものとしてここに記録する。上に記述したプロジェクトのサイトは、このプロジェクトをコミュニティによって作られたものとして提示しており、作成した組織を名指してはいない。

## 研究での利用

Spec Kit の段階的なワークフローは、学術的な仕事が上に構築し、それに照らして測定するベースラインとして用いられてきた。[[ScholarlyArticle/spec-kit-agents]] は Specify → Plan → Tasks → Implement の系列を出発点とし、構造だけでは [[DefinedTerm/context-blindness]]——内部的には整合しているが対象のリポジトリとは両立しない中間成果物——を防がないと論じる。提案される追加は、既存の各段階を包むコンテキスト接地の層である。各フェーズの前にリポジトリを探る読み取り専用の発見フックと、その後で生じた成果物を検査する検証フックであり、いずれもエージェントの主プロンプトの外に保たれる。同論文自身の評価では、この追加が128回の実行にわたって 1〜5 の複合的な判定品質スコアを 3.51 から 3.66 へ引き上げ、その代償として、より長いワークフローのファミリーでは1回の実行あたりおよそ13分の追加の実行時間を要した——いずれも論文の著者らが自らのシステムについて報告した数値である。

第二の研究である [[ScholarlyArticle/citation-discipline-in-spec-driven-development]] は、Spec Kit を2つの競合するトレーサビリティの規律に照らして測定し、より芳しくない結論に達している。同論文は Spec Kit を、spec-plan-tasks の連鎖を通じて成果物レベルの一貫性を強制するもので、引用の連鎖は実装が始まると途切れると特徴づけ、これを一方では行ごとの要求の引用と、他方では事後的な外部のトレースマップと対比する。測定された2つの次元において Spec Kit は最下位だった。いずれの比較対象よりも低い出力の決定性（Claude Sonnet 4.6 で語彙的類似度の平均が OpenSpec の 0.487 に対して 0.460、GLM-5-turbo で 0.480 に対して 0.434）、そして自動化された幻覚の検出が皆無であること——同研究における検出は、要求の識別子がコードそのものに存在することに依拠していたからである。論文はこれが Spec Kit を「測定された次元において最も弱い選択肢」にすると述べつつ、「その開発者体験と自然なワークフローが実践では補いうる」ことも明示的に認めている。

### ガバナンスの具現化としての評価

[[ScholarlyArticle/productivity-reliability-paradox]] は Spec Kit を、自らの [[DefinedTerm/specification-governance-model]] の最も完成度の高い既存の具現化として評価し、機能のレベルで動作し、意図の捕捉から実装までのライフサイクルを統治するものと位置づける。ツール非依存の設計を、利便性ではなく経済上の要点として際立たせている。仕様がリポジトリへコミットされ、参加するいかなるエージェントも消費できるため、ガバナンスの構造は、エージェント固有のツールが生むようなロックインを作らないのである。

同論文によるこのツールの成熟度の評価は意図的に慎重である。2026年4月時点で Spec Kit をバージョン 0.8.x と記録し、小規模ながら成長しつつある採用者コミュニティを持ち、独立した学術的評価がなく、ソフトウェアチームの大多数が採用するどころか出会ってもいないと述べ、Spec Kit を「実証済みの解としてではなく、最も完成度の高い既存の具現化として」評価すると明言する。2つの限界を直截に名指す。仕様の品質が人間の執筆に依存すること、そしてこのツールが仕様の完全性の自動検証をまだ含んでいないことである。予備的であり独立には検証されていないとしつつ伝えている報告済みの帰結には、上流の成果物——PRD、設計、構造、技術仕様、テスト計画——の作成が、およそ12時間からおよそ15分の人間の操舵とエージェントの実行時間へ圧縮されたことが含まれる。

同論文における4か月のパイロット研究は、3つのフルスタック Web プロジェクトにおいて、中堅とシニアのエンジニア14名とともに、2か月のベースライン期間と2か月の介入期間を通じて Spec Kit を試した。各プロジェクトは、譲れないアーキテクチャとコーディングの原則を捉える `/speckit.constitution` を定義し、影響度が中および高の変更は `/speckit.specify`、`/speckit.plan`、`/speckit.tasks` を経由させた。著者は結果の数値を、統制されたものではなく指標的なものとして報告している——並行する対照群はなく、計測は遡及的だった。機能あたりのリードタイムの中央値は 8〜12 営業日から 6〜9 営業日へ、スプリントあたりの後工程でのホットフィックスは 3〜5 件から 1〜2 件へ、月あたりのロールバックは 2〜4 件から 0〜1 件へ、短期のコードチャーンは変更行の 12〜18% から 6〜10% へ動き、これに対して中規模の機能あたり 45〜90 分の仕様執筆のオーバーヘッドがあった。

### 比較しうるフレームワークのなかでの位置

[[ScholarlyArticle/from-prompt-to-process]] は Spec Kit を、6次元のプロセスのタクソノミーで比較される6つのフレームワークの一群に置く。そこでは仕様に 2、コンテキスト・役割・実行・検証にそれぞれ 1、移植性に 2 を記録し——12点満点中8点であり、10点の [[SoftwareApplication/bmad-method]] と9点の [[SoftwareApplication/spec-kitty]] に次ぐ。記録された支配的な強みは「真実の源としての仕様と移植性」であり、記録された支配的なリスクは「検証が弱ければ成果物と実装のあいだに乖離が生じること」である。これらの点数は独立した実証的な測定ではなく、公式ドキュメントに基づく著者の判断である。

同論文の特徴づけは、仕様が使い捨ての文書ではなく真実の源として扱われること、そして spec-plan-tasks-implement のサイクルが、レビュー可能な中間成果物を作ることで自然言語とエージェントの行動のあいだの距離を縮めることである。リポジトリのコマンドとして constitution、specification、plan、tasks、implementation と、任意の clarification、analysis、checklist のコマンドを挙げている。述べられている脆さは、エージェントが成果物をうまく解釈することへの依存である。明確な仕様は助けになるが、追加のチェックなしに実装、テスト、保守が整合し続けることを保証はしない。

同じ比較のなかで、Spec Kit と [[SoftwareApplication/openspec]] は競合する SDD のツールキットとして位置づけられており、OpenSpec のほうが軽量で、Spec Kit のほうがフェーズと移植性において完成度が高いとされる。

## 沿革

プロジェクトは自らをコミュニティによって作られたものとして提示している。サイトは240人を超えるコントリビュータ、121,000 を超える GitHub のスター、35の統合、138の拡張、25のプリセット、そして6つの「friends」プロジェクトを報告し、誰でも拡張、プリセット、ワークフローを作って公開できると述べている。サイトは自身の最終更新を2026年7月16日と記録している。
