GitHub Agentic Workflows は、開発者が Markdown で定義し GitHub Actions のワークフローとして実行する AI 駆動のリポジトリ自動化である。GitHub のドキュメントは従来の自動化との対比を率直に示している。「固定された if-then のルールによる従来の自動化とは異なり、エージェント的ワークフローはコーディングエージェントを用いて文脈を理解し、判断を下し、意味のある行動を取る——それらすべてを自然言語の指示から行う」。一方でトリガー、権限、safe outputs といったガードレールは依然としてフロントマターで明示的に宣言される。同じ考えについての発表記事のまとめは、「望む成果を平易な Markdown で記述し、それを自動化されたワークフローとしてリポジトリへ追加すると、GitHub Actions 内のコーディングエージェントを使って実行される」というものである。

この機能は GitHub Next で生まれ、同社は1つの問い——「AI コーディングエージェントの時代における、強力なガードレールを備えたリポジトリ自動化とはどのようなものか」——の探究として始めたと述べている。基盤として GitHub Actions が選ばれたのは、GitHub の説明によれば、そこにはすでに権限、ログ、監査、サンドボックス化された実行、そして豊富なリポジトリの文脈が備わっているからであり、また Actions の上に構築することで、いつどこでコーディングエージェントを使うかの判断をリポジトリの所有者に委ねたまま、数百万のリポジトリでそれらを利用可能にできるからである。

## 概要

各ワークフローは2つの部分からなる1つの Markdown ファイルである。`---` に挟まれた YAML フロントマターは、ワークフローがいつ実行されるか、どの権限を持つか、どの書き込み操作が許されるかを設定する。Markdown の本文は、エージェントが従う自然言語の指示を担う。発表記事はこの分担を「Markdown は意図であり、トリガー、権限、ツール、許される出力はあらかじめ明示される」と表現している。

このライフサイクルには、エージェントに直接プロンプトを与えるのとは異なるコンパイルの段階が加わる。作成者は `.md` ファイルを書き、それを堅牢化された `.lock.yml` の GitHub Actions ワークフローファイルへコンパイルし、双方をデフォルトブランチへコミットしてプッシュし、その後は他の Actions のワークフローと同様に——トリガーによって、GitHub のウェブインターフェースから、あるいは GitHub CLI から——実行する。コンパイルは `gh aw` の CLI 拡張（`gh extension install github/gh-aw` の後に `gh aw compile`）で行う。GitHub 自身の推奨は、ワークフローを手で書くのではなく対話型のコーディングエージェントに生成させ、その結果をレビューし検証してからリポジトリへ追加することである。

GitHub が挙げるタスクは、ビルドパイプラインの仕事ではなくリポジトリの雑務である。入ってくる Issue のトリアージとラベル付け、CI の失敗の調査と修正案の提示、日次または週次のステータスレポートの生成、コードの変更に合わせたドキュメントの整合、そしてテストカバレッジの改善である。発表記事は同じ素材を6つの「継続的」なカテゴリ——トリアージ、ドキュメント、コードの単純化、テストの改善、品質の衛生、レポーティング——にまとめ、そこから生まれる実践を [[DefinedTerm/continuous-ai]] と名づけている。

GitHub は、これが CI/CD の置き換えではないことを明示している。エージェント的ワークフローは「既存の CI/CD を置き換えるのではなく補うよう設計されて」おり、ビルド、テスト、リリースのパイプラインを置き換えるものではなく、そのユースケースは決定論的な CI/CD のワークフローとほとんど重ならない。

## 機能

ここでの出典はいずれも GitHub が自社製品を記述したものである。以下のガードレールは GitHub のドキュメントが述べるとおりであり、独立に検証されたものではない。

- **エンジンの選択。** 複数のコーディングエージェントがサポートされ、フロントマターの `engine` プロパティで指定される。それぞれに固有の認証シークレットが必要である。ドキュメントは GitHub Copilot、Anthropic Claude、OpenAI Codex、Google Gemini を挙げ、何も指定されない場合のデフォルトは [[SoftwareApplication/github-copilot]] であるとする。発表記事は例として Copilot CLI、Claude Code、OpenAI Codex を挙げている。
- **デフォルトで読み取り専用。** 明示的に追加が許可されない限り、ワークフローはリポジトリに対して読み取り専用の権限しか持たない。
- **Safe outputs。** 書き込み操作——Issue の作成、コメントの追加、プルリクエストのオープン——は、フロントマターで宣言され検証された `safe-outputs` を通じてのみ許される。これらはあらかじめ承認されレビュー可能な GitHub の操作へ対応づけられる。
- **脅威の検知。** 提案された出力は、書き込み行為が適用される前に、疑わしい変更や安全でない変更がないか走査される。
- **隔離。** エージェントはファイアウォールとサンドボックスを備えた GitHub Actions の環境で、ツールの許可リストとネットワークの隔離のもとで実行される。シークレットはエージェントのランタイムへ露出されるのではなく、隔離された下流のジョブに保たれる。
- **ロールベースのアクセス。** エージェント的ワークフローを起動または変更できる者を、ロールベースのアクセス制御によって制限できる。
- **コストの制御。** 推論は AI クレジットで従量計測され、`1 AIC = 0.01 米ドル`である。`gh aw logs` と `gh aw audit RUN-ID` が所要時間、トークンの使用量、AIC の見積もりを報告し、フロントマターの `max-ai-credits` が1回の実行に上限を設ける（デフォルトは 1,000 AIC）。GitHub は、AIC の値がベストエフォートの見積もりであり、プロバイダの請求書と一致しない場合があると注記している。総コストは2つの部分——GitHub Actions の分数と推論——からなり、Copilot エンジンの利用は Copilot の課金へ対応づけられ、サードパーティのエンジンはそのプロバイダによって課金される。

このアーキテクチャについて GitHub が述べる理由は、明白な代替案との比較である。標準的な Actions の YAML ワークフローの内側でコーディングエージェントの CLI を直接実行する方法は「多くの場合、特定のタスクに必要な以上の権限をこれらのエージェントに与えてしまう」のに対し、エージェント的ワークフローはデフォルトで読み取り専用のアクセスを与え、GitHub の操作を safe outputs を通じて経路づけることで「より厳しい制約、より明確なレビューの地点、そしてより強い全体的な制御」をもたらす。GitHub はこの設計全体を、意図しない振る舞いとプロンプトインジェクション攻撃に対する多層防御として記述している——[[DefinedTerm/indirect-prompt-injection]] を参照。

## 沿革

GitHub はこの機能を2026年2月13日の [[BlogPosting/automate-repository-tasks-with-github-agentic-workflows]] で発表し、テクニカルプレビューとして提供されること、そして「GitHub、Microsoft Research、Azure Core Upstream の協働」であることを述べた。ドキュメントの方はこれをパブリックプレビューであり変更されうるものと記述している。いずれも GitHub 自身による特徴づけであり、2つの文書は段階について異なる言葉を用いている。

その時点でのチーム向けの GitHub の指針は、技法というより力点の移動であった。ワークフローは「完璧なプロンプトよりも、目標と望ましい出力に焦点を当てたときに最もうまく働く」のであり、作成者は成功がどのようなものかについて明確さを提供し、それをどう達成するかの探索はワークフローに委ねる。ワークフローは非常に一般的なもの（「ソフトウェアを改善せよ」）から非常に具体的なものまで幅がありうると指摘し、経験則として「リポジトリにおける反復的な作業を言葉で記述できるなら、それはエージェント的ワークフローに向いているかもしれない」と示している。プレビュー時点の要件は、リポジトリで GitHub Actions が有効であること、AI エンジンのアカウントを持っていること、そして GitHub CLI がインストールされ認証済みであることであった。
