Qoder は、Alibaba が公開している [[DefinedTerm/ai-ide]] である。[[ScholarlyArticle/rule-taxonomy-and-evolution-in-ai-ides]] が調査対象として選んだ 5 つのツールの 1 つであり、選定の基準は、コード生成とチャットのやり取りの際に IDE が従わなければならない [[DefinedTerm/ai-ide-rules]] を開発者が明示的に定義できることであった。この研究は、ツールの公式変更履歴に基づき、リリース日を 2025 年 8 月 21 日と記録している。

## 機能

Qoder のルールファイルはプロジェクト内の `.qoder/rules/` 以下に置かれ、ルールは生成時とチャット時に遵守される。ツール横断で見たこの仕組みについては [[DefinedTerm/ai-ide-rules]] を参照。

## Alibaba Cloud が Qoder CN として文書化している製品

Alibaba Cloud は、`help.aliyun.com` の `/zh/lingma/` パス以下で、本文中で **Qoder CN** と呼ばれる製品のユーザーガイドを公開している。Qoder CN がこの製品の別名なのか、その地域版なのか、あるいはまったく別の製品なのかは、そのガイドも上記の研究も述べておらず、ここで保持している他の情報からも確定できない。このガイドをこのページに記録しているのは、名称が、いずれのソースが示すものの中で両者のつながりに最も近いものだからである。以下は、そのガイドが Qoder CN について述べている内容であり、Qoder について確定した事実として読むべきではない。

このガイドは **エージェントモード**（智能体模式）について説明しており、これは何をすべきかを自ら判断し、環境を把握し、ツールを使うことができ、プロジェクト検索、ファイル編集、ターミナルを用いてコーディングタスクを最初から最後までやり遂げるとしている。ガイドは 4 つの中核機能を挙げている。まず、エージェントはプロジェクトレベルの変更を行い、タスクを自ら分解してプロジェクト全体にわたる複数のファイルを編集し、ターンを重ねての反復とスナップショットによるロールバックも利用できるとしている。次に、エージェントはフレームワーク、技術スタック、タスクに必要なファイル、エラーメッセージといったプロジェクトの状況を自動的に把握するため、コンテキストを手作業で添付する必要がないとしている。さらに、エージェントは 10 種類以上の組み込みプログラミングツールを自らの判断で利用し、その中にはファイル検索、ファイルとディレクトリの読み取り、プロジェクト内のセマンティックなシンボル検索、ファイルの変更、エラーの取得、ターミナルでの実行が含まれ、開発者に確認や介入を求めることなくそれらを使うとしている。そして、エージェントはタスクの遂行の一環としてターミナルコマンドを決定し、記述し、実行するとしている。

同じガイドの別のページでは、それらのツールが用途別にグループ分けされ、名前が列挙されている。そこで示されている一覧は次のとおりである。

- **検索** — `search_codebase`（現在のプロジェクトに対するセマンティック検索）、`search_file`、`grep_code`、`search_symbol`、`list_dir`、`web_search`（API キー不要とされている）、`fetch_content`（URL の内容の取得）、`search_memory`、`fetch_rules`。
- **ファイル編集** — `edit_file`、`read_file`、`delete_file`、`create_file`。ガイドによれば、エージェントはこれらを使ってプロジェクト内の複数のファイルにまたがる変更を行う。
- **ターミナル実行** — `run_in_terminal` と `get_terminal_output`。コマンドは、タスクでそれまでに起きたことに基づいて記述される。
- **問題の取得** — `get_problems`。IDE の Problems ペインに表示されるコードの問題を読み取る。
- **メモリ** — `update_memory`。開発者が何かを覚えておくよう求めたとき、またはツールが何かを自動的に保持すべきだと判断したときに呼び出される。
- **To-do 計画** — `add_tasks` と `update_tasks`。ガイドはこれらを、エージェントが自ら計画を立てることと結びつけている。つまり、未完了の作業を To-do 項目に分解し、進めながら実行経路を修正していく。

そのページはまた、MCP サービスがサポートされており、開発者が自由に設定できると述べている。これは、後述するエージェントページの MCP ツールに関する説明と整合している。表には 2 つの小さな不整合があり、取り繕わずに指摘しておく価値がある。「终端执行」（ターミナル実行）という見出しが 2 回現れ、2 回目は To-do 計画の行の上に置かれていること、そして `update_tasks` の行では説明が名前の列に入っていることである。

確認については、ガイドは 2 つのゲートを説明している。ターミナルコマンドは、デフォルトでは実行のたびに確認のために提示され、「実行」を選ぶとコマンドが IDE のターミナルウィンドウに送られ、「キャンセル」を選ぶとそれをスキップしてエージェントに戻り、エージェントはそのフィードバックから次のステップを計画するという。バックグラウンドで実行するためのコマンドはその旨が示され、エージェントは他の作業を続けながら、必要なときにその出力を確認する。確認なしで実行してよいコマンドの許可リストは、プラグインのチャット設定の Auto-Run セクションで設定できると説明されている。MCP ツールが設定されている場合、ガイドによれば、エージェントはそれを呼び出すことが役立つかどうかを自ら判断し、呼び出しのたびに事前に確認を求め、その結果をコンテキストとしてフィードバックする。

ガイドは計画とタスク追跡についても説明している。複雑だと判断したタスクについては、エージェントは計画を作成し、実行開始前に開発者にレビューのために提示するとされ、`/plan` によって同じことを意図的に発動できる。また、要求から To-do リストを導き出し、要求が拡張されればそのリストも拡張し、各項目の状態をチャットウィンドウに表示するという。別のプロンプト最適化機能は、周囲のコンテキストと会話履歴を用いて大まかな指示をより詳細なものに書き直すと説明されており、開発者はそれを編集、送信、または取り消すことができる。

同じガイドのさらに別のページは、エージェントモードに組み込まれた **コードレビューエージェント**（Code Review agent）について説明しており、個別の設定は不要だとしている。開発者はチャットパネルをエージェントモードに切り替え、`/code-review` コマンドを使うか、望むレビューを自然言語で記述し、その範囲として、プロジェクト全体、特定のファイル、Git の差分、またはプルリクエストを指定する。エージェントはその範囲を、論理的欠陥、セキュリティ脆弱性（例として SQL インジェクションと XSS が挙げられている）、パフォーマンスのボトルネック、コードスタイルの問題といった複数の観点からレビューし、重大度別にエラー、警告、提案に分類した構造化レポートを作成するとされ、各項目にはコードの位置、問題の説明、修正案が示される。大規模な変更については、よりきめ細かなフィードバックを得るためにモジュールごとにレビューすることを勧めており、変更が特定のビジネスロジックに関わる場合は、その背景を要求の中で簡潔に説明することを勧めている。ツール横断で見たこのパターンについては [[DefinedTerm/code-review-agent]] を参照。そのページにはまた、Qoder CN シリーズの新しいドキュメントサイトが docs.qoder.cn で公開されたこと、そしてガイド自身のサイト上の内容は製品の最新の機能や変更を反映していない可能性があることを知らせる告知が掲載されている。

なお、このガイドは設定対象をプラグインとして説明しており、コマンドはホスト IDE のターミナルウィンドウに送られる。これは、上記の研究が Qoder について説明しているスタンドアロンの AI IDE とは異なる形態である。このことも、2 つの記述を 1 つの製品についてのものとして扱わないさらなる理由である。

## 3 つ目の記述：仕様駆動開発のサーベイにおいて

Jimmy Song のオンラインハンドブック『智能体构建指南』のある章は、[[DefinedTerm/spec-driven-development]] の代表的な実装を概観する中で **Qoder** を挙げ、仕様をコードとして扱うという考え方に基づいて構築された、SDD のシナリオ専用に設計された AI プログラミングアシスタントだと説明している。その記述によれば、構造化された Markdown で仕様を記述することをサポートし、そこからプロジェクト構造、コード、テストケースを生成し、何度かの会話を通じて開発者が仕様を洗練・発展させるのを支援するという。LLM、コード生成、テスト、デプロイの機能を統合しているとされ、チームでの協働や複雑なエンジニアリング作業に適しているとされている。

その章は、説明しているツールの URL、ベンダー、バージョンを示していないため、それが上記の AI IDE を指すのか、Alibaba Cloud が Qoder CN として文書化しているプラグインを指すのか、あるいはまた別のものを指すのかは、ここで保持しているどの情報からも確定できない。そのため、上記の 2 つのいずれかに統合するのではなく、同じ名前の下での 3 つ目の記述として記録している。

## 採用とエコシステム

その研究の数値のうち 2 つが採用状況に関わるが、両者は異なるものを測定している。リポジトリマイニングでは、最初の検索で Qoder の候補プロジェクトが 125 件見つかったが、キーワードとルールファイルによるフィルタリングと手作業による検査を経て、AI IDE で構築されたと明示している 83 件のプロジェクトからなる最終データセットに残ったのは 1 件であった。実務者サーベイでは、回答者 99 人のうち 16 人が現在 Qoder を開発に使っていると回答した。マイニングの数値は、ツールを使用しており、かつ README や説明文でその旨を述べている公開プロジェクトの数を反映しており、研究は、AI IDE を使いながらそれを明示していないプロジェクトが過小に数えられると指摘している。一方、サーベイの数値は、ルールファイルへの変更をコミットしたことのある開発者の自己申告による利用状況を反映している。
