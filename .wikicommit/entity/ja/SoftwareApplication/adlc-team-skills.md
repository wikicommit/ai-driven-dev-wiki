adlc-team-skills は、コーディングエージェントに毎セッションの開始時にチームのコンテキストを与え、「見知らぬ他人のように作業するのをやめさせる」ことを目指す [[DefinedTerm/agent-skills]] のコレクションである。GitHub の tikalk organization で MIT ライセンスのもとに公開されており、[[DefinedTerm/twelve-factor-agentic-sdlc]] を実装していると述べている。Agent Skills の標準をサポートするエージェントで動作し、[[SoftwareApplication/claude-code]]、Codex、[[SoftwareApplication/opencode]]、Cursor、Copilot の名前が挙げられている。

中心となる考え方は、チームのルールを、1 台のマシン上にあってドリフトしていく個人の `CLAUDE.md` ファイルではなく、プルリクエストを通じてレビューされチーム全体で共有される、独立したバージョン管理下の「team-ai-directives」リポジトリに置くというものである。セッション開始時には、セッション開始イベントのフックによって起動される `team-boot` スキルが、それらのルールの簡潔なインデックス ― 名前と 1 行の説明からなるおよそ 100 トークン ― だけを注入し、エージェントは現在のタスクがあるルールに合致したときにだけ、そのルールの全文を取得する。README は、この「注入ではなくインデックス」という設計の根拠として、完璧な検索ができる場合でも長いコンテキストはモデルの性能を低下させるという研究を挙げている。チームリポジトリの種類別のインデックスファイルも同様に、[[DefinedTerm/progressive-disclosure]] として説明されている。

## 機能

README は、4 つの部分からなる基本的なセッションのワークフローを説明している。`team-boot` はディレクティブのインデックスを注入する。`mission-brief` は、まず契約 ― 目標、制約、非目標、成功基準 ― を強制することでエージェントがいきなりコードに飛びつくのを止め、そのうえで、ゲート、サーキットブレーカー、再開、監査証跡を備えた specify → plan → implement ↔ converge のループを進める。セッション終了時には、`team-learn` が苦労して得た修正を Context Directive Records（CDR）として抽出し、確信度でスコア付けし、まとめてレビューしたうえで、受け入れられたものをチームリポジトリへのドラフトのプルリクエストとして公開する。ドラフトと利用データは orphan ブランチに保持され、後のセッションが実際の利用状況に基づいて CDR を順位付けできるようにしている。`team-repair --build-to-delete` は、あるルールを外した状態で評価を再実行し、それでもモデルが合格する場合はそのルールの削除を提案する。

さらに別のスキル群が次のものをカバーしている。評価（実行可能なグレーダーの構築 ― コードで検証できるところではどこでも二値のチェックを用い、静的なチェックで検証できないものにだけ LLM ジャッジを用いる ― で、ホールドアウト分割と真陽性率・真陰性率によって検証される）、`PRD.md` と `AD.md` を生成するプロダクトとアーキテクチャの決定記録、git 履歴の中のイシューに紐づいたコミットから掘り起こされる変更の決定記録、そして選択がアーキテクチャ決定記録として記録される前に Tikal Tech Radar の見解を注入する技術選定スキルである。`mission-brief` は、あわせてインストールされた他のコレクションのスキルにステップを引き渡すこともでき、それらの `SKILL.md` のフロントマターを読んでその中から選ぶ。README は、併用できるコレクションの 1 つとして [[SoftwareApplication/superpowers]] を挙げている。

このセッションループの周囲には、README が**ソフトウェアファクトリー**と呼ぶもの、すなわちエージェント型 SDLC のアウターループがある。`factory-init` は既存のリポジトリをブートストラップし、`factory-queue` は人間が承認する意図のゲートの後ろで入ってくる作業をトリアージし、`factory-mission` はそれを、テストエージェントと実装エージェントにテストファーストで分担させながら、分離されたワークツリーの中で仕様によるゲートを備えたミッションとして実行する。`factory-review` は結果として生じたプルリクエストをコードとして書かれたポリシーに照らして採点し、`factory-learn` は実行から得られた教訓をチームリポジトリへとフィードバックする。README は、自動化されたすべての段階は助言的なものであり、ゲートは人間が握っており、何も自動でマージされないと述べている。

## 採用状況とエコシステム

スキルは、プロジェクト独自の `adlc-cli` を通じてインストールされる。これは汎用のスキルインストーラーをラップしたもので、それに加えて 9 つのコーディングエージェント向けにスラッシュコマンドを生成し、セッション開始時のフックを配線する。あるいは、それらのフックなしに単なるスキルとしてインストールすることもできる。付属のドキュメントでは、同じ organization の [[SoftwareApplication/agentic-sdlc-spec-kit]] とあわせてインストールする方法を扱っている。プロジェクトが掲げる理念は、ルールは時間とともに増えるのではなく減っていくべきであり、コードでチェックできるものには二値のグレーダーを用意すべきであり、あらゆる種類の決定はバージョン管理されたリポジトリに置かれ、記録からドキュメント、コードへとたどれるようにすべきだというものである。

README にはセキュリティインシデントも記録されている。2026-07-27 に、サプライチェーンワームが盗まれたメンテナのトークンを使って、リポジトリの `.claude/` と `.vscode/` ディレクトリに悪意あるペイロードを数時間にわたって注入した。README によれば、このペイロードが実行されたのは、リポジトリをクローンして VS Code で開いたか、その中で Claude Code のセッションを開始した人に対してだけであり、スキルのインストール経路ではそれらのファイルは一度も配布されておらず、履歴の書き換え、シークレットのローテーション、ブランチ保護の強化が行われたという。あらゆるリポジトリに向けた教訓として README が述べているのは、クローン内の `.vscode/tasks.json` と `.claude/settings.json` を実行可能なコードとして扱うべきだということである。
