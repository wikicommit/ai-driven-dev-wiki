Claude Managed Agents は Claude Platform 上のホステッドサービスであり、顧客に代わって長期にわたるエージェントを実行する。[[TechArticle/scaling-managed-agents]] で示されるその設計上の前提は、ハーネスがモデル単独ではできないことについての仮定を符号化しており、モデルが良くなるにつれてそれらの仮定は古びていく、というものである。だからこそこのサービスは「今日われわれが運用しているものを含め、いかなる特定の実装よりも長く生き残ることを意図した」小さなインターフェース群を露出させている。

## 概要

このサービスはエージェントを、互いを乱すことなくそれぞれ差し替え可能な3つの構成要素へと仮想化する。**セッション**——起きたことすべての追記専用のログ。**ハーネス**——Claude を呼び出し、そのツール呼び出しをインフラへ振り分けるループ。そして**サンドボックス**——Claude がコードを実行しファイルを編集する実行環境である。掲げられている姿勢は、それらのインターフェースの形については意見を持ち、その背後で何が動くかについては持たない、というものである。

## 機能

その説明で名指されるインターフェースは、サンドボックスその他任意のツールを呼び出す `execute(name, input) → string`、新しいサンドボックスを立ち上げる `provision({resources})`、ハーネスを再起動する `wake(sessionId)`、イベントログを取得する `getSession(id)`、エージェントループの途中でそこへ追記する `emitEvent(id, event)`、そしてイベントストリームの位置指定のスライスを選び取る `getEvents()` である。

セッションのログがハーネスとサンドボックスの双方の外側にあるため、サンドボックスの障害は失われたセッションではなくツール呼び出しのエラーとして Claude に現れ、クラッシュしたハーネスは、同じセッションで目覚めて最後のイベントから再開する別のハーネスで置き換えられる。この同じ耐久性が、コンテキストウィンドウには与えられないものをエージェントに与える。自らの過去を問い質す能力——読むのをやめたところから再開すること、ある時点に至る経緯を見るために巻き戻すこと、特定の行動の前のコンテキストを読み直すこと——であり、不可逆な圧縮の判断だけに依拠せずに済む。

認証情報は設計上サンドボックスの外に保持される。リポジトリのアクセストークンはサンドボックスの初期化時にクローンのために使われ、ローカルの git リモートへ組み込まれるため、エージェントがそれを扱うことなく `push` と `pull` が機能する。カスタムツール向けの OAuth トークンは安全な保管庫に置かれ、セッションに紐づくトークンを実際の認証情報と交換する専用の MCP プロキシを通じて到達される。ハーネスがいかなる認証情報も知らされることはない。

## 沿革

このアーキテクチャは、セッション、ハーネス、サンドボックスを単一のコンテナに置いていた以前の設計を捨てた結果として記述されている。その設計はサーバを「ペット」にしてしまった——コンテナが落ちればセッションが失われ、応答しなくなればそれを看病して健康に戻さねばならず、デバッグにはしばしばユーザーのデータを抱えたコンテナへ入ることが必要だった。またその設計は、Claude が作業する対象がすべてその傍らにあると仮定していたため、自社の仮想プライベートクラウド内のリソースへ Claude を到達させたい顧客は、ネットワークをピアリングするか、自らハーネスを運用せねばならなかった。

疎結合化はその仮定を取り除き、さらにツール呼び出しが必要とするときにだけコンテナをプロビジョニングすることで、報告された待ち時間の改善をもたらした。最初のトークンまでの時間は p50 でおよそ 60%、p95 で 90% 超の低下であり、これは Anthropic が自社サービスについて自ら測定したものである。
