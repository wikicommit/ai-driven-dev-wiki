GitHub Copilot コーディングエージェントは、GitHub の非同期バックグラウンドコーディングエージェントである。Osmani はこれを、ドラフトのプルリクエストを作成し、バックグラウンドで作業し、その後レビューを依頼するバックグラウンドエージェントとして位置づけられたものと説明している。人間はそこにコメントし、エージェントに反復させることができる。

GitHub は 2025 年 5 月にこれを発表し（[[BlogPosting/github-copilot-meet-the-new-coding-agent]] を参照）、委任のインターフェースをその中心的な考え方とした。1 つ以上の GitHub の issue を、チームメンバーに割り当てるのと同じ方法で（github.com、GitHub Mobile、GitHub CLI から）Copilot に割り当てると、あとはエージェントが引き受ける。GitHub 上や VS Code 内の Copilot Chat から、プルリクエストを作成するよう依頼することもできる。

## 機能

- 開発者がリアルタイムでペアを組む必要はなく、バックグラウンドで非同期にタスクに取り組む。
- 出力の単位としてドラフトのプルリクエストを作成する。
- レビューを依頼し、人間のコメントに応じて反復する。
- issue を割り当てられると目の絵文字でリアクションし、その後仮想マシンを起動し、リポジトリをクローンし、環境を設定し、GitHub のコード検索を利用した検索拡張生成（RAG）でコードベースを分析する。変更は git のコミットとしてドラフトのプルリクエストにプッシュし、作業しながらそのプルリクエストの説明を更新する。
- 推論と検証のステップはセッションログで公開され、GitHub はこれを判断を追跡し問題を見つける手段として提示している。
- リポジトリの設定で構成された [[DefinedTerm/model-context-protocol]] サーバーにより、GitHub 外のデータや機能にアクセスできる。GitHub 自身の MCP サーバーもこれに含まれる。
- 割り当てられた issue に添付された画像を読み取るため、バグのスクリーンショットや機能のモックアップをタスクの一部にできる。
- 関連する issue やプルリクエストの議論からコンテキストを取り込み、リポジトリのカスタム指示に従う。
- GitHub のデベロッパーアドボケイトによる解説（[[BlogPosting/from-idea-to-pr]]）は、割り当て後の手順を次のように示している。ブランチを作成する。新しいセッションを開始する（リポジトリに `copilot-setup-steps.yml` があれば、まず開発環境を設定する）。タスクを確認し、コードベースを探索し、計画を立てる。カスタム指示があればコンテキストとして用いる（例ではコミット前に `npm run lint` と `npm run test` が通ることを求めている）。そしてレビューのためにドラフトのプルリクエストを作成する。プルリクエストのコメントとして投稿されたフィードバックは別のセッションを開始させ、エージェントはそこで依頼された変更に取り組む。
- 同じ解説は、これを Copilot のエージェントモードと対比している。エージェントモードはエディタ内で開発者と並んで同期的に作業するのに対し、コーディングエージェントは非同期にタスクに取り組む。
- AI エージェント型プログラミングに関するサーベイは、「GitHub Copilot Agent」を（どの Copilot 製品を指すかは明示せずに）複数ステップにわたって会話を保持し、以前の関数名を記憶し、エージェント間のやり取りの反復を通じて完全なモジュールを構築できるものとして説明している。サーベイでは、これはインタラクション間で状態を保持しない従来の [[SoftwareApplication/github-copilot]] のようなシングルターンのツールと対比されている。
- 同じサーベイは、「GitHub Copilot agent」がサポートするとするツールの一部を列挙しており、それはコンパイラ（gcc、clang）、デバッガ（gdb、pdb）、テストフレームワーク（pytest、Jest）、リンター（eslint、black）、バージョン管理（git）、ビルドシステム（make、npm）、パッケージマネージャ（pip、cargo）、言語サーバー（pyright、tsserver）にわたる。
- GitHub は、これがテストの整ったコードベースにおける低〜中程度の複雑さのタスク（機能追加、バグ修正、テストの拡充、リファクタリング、ドキュメント改善）で最も力を発揮すると述べている。これは GitHub 自身による適用範囲の主張であり、測定結果ではない。

- GitHub による後の入門記事（[[BlogPosting/github-copilot-coding-agent-101]]、2025 年 9 月、2026 年 1 月更新）は、作業を渡す方法をさらに 2 つ加えている。GitHub Pull Requests 拡張機能を通じた VS Code からの委任と、実行中のタスクも追跡する github.com のエージェントパネルである。また、IDE の Copilot Chat や、MCP をサポートする任意のツールから指示できるとしている。エージェントが作業している間、ドラフトのプルリクエストには `[WIP]` のタグが付けられ、その後エージェントがタイトルと説明を更新し、開発者にタグを付けてレビューを求める。さらなる変更は `@copilot` をタグ付けしたコメントで依頼する。
- 同じ記事によれば、Playwright と GitHub の MCP サーバーが組み込まれた状態で提供され、リポジトリ管理者はリポジトリ設定の JSON 構成を通じて他のサーバーを追加する。また、インターネットアクセスはファイアウォールによって制限されており、そのデフォルトルールは、GitHub とのやり取りや依存関係のダウンロードに使うホストを許可している。
- GitHub のデベロッパーアドボケイトによるセットアップガイド（[[BlogPosting/onboarding-your-ai-peer-programmer]]、2025 年 7 月）は、割り当て後の決まった手順を説明している。ブランチを作成し、作業を追跡するためのプルリクエストを作成し、GitHub Actions 内に隔離された環境を作成し、issue またはプロンプトを読み、プロジェクトを探索し、反復的に作業し、最後にプルリクエストを更新してレビューの準備ができたことをチームに通知する。環境は `.github/workflows/copilot-setup-steps.yml` のワークフローによって設定され、そのジョブは `copilot-setup-steps` という名前でなければならないこと、そしてエージェントが 2 種類のカスタム指示を読むことを説明している。リポジトリ全体に適用される `.github/copilot-instructions.md` と、`applyTo` の glob によって特定のファイルを対象とする `.github/instructions/` 配下の `<file-name>.instructions.md` ファイルである。
- 同じガイドによれば、リポジトリの Copilot コーディングエージェント設定で MCP サーバーを構成する代わりに、プロジェクト内の既存の `.vscode/mcp.json` をエージェントが MCP サーバーの特定に使うこともできる。また、プルリクエスト上の「View session」ボタンで、エージェントが行ったすべてのことを確認できる。

この解説は、issue 自体を Copilot で起草すること（自然言語のプロンプトを、タイトル、受け入れ基準、変更すべきファイルへの手がかりを備えた issue に変換すること）と組み合わせている。委任に関する助言は、issue のスコープを厳密に絞ること、エージェントが意図を理解していると仮定せずに受け入れ基準を示すこと、実行やマージの前に他のプルリクエストと同じように変更を慎重にレビューすること、そして一度で正しい結果が得られるとは考えずに反復を前提とすることである。これはデモに基づく一実践者の助言であり、測定結果ではない。

## セキュリティと制御

GitHub が掲げる設計目標は、チームにエージェントを加えることで、リポジトリの既存の制御を緩める必要が生じないようにすることであり、デフォルトで適用される 4 つのポリシーを説明している。エージェントは自分が作成したブランチにのみプッシュでき、デフォルトブランチや人間が作成したブランチには手を触れない。エージェントにプルリクエストの作成を依頼した開発者はそれを承認できないため、必須レビューのルールが守られる。エージェントのインターネットアクセスは、カスタマイズ可能な信頼済みの接続先リストに制限される。そして GitHub Actions のワークフローは人間の承認なしには実行されない。既存のリポジトリのルールセットや組織のポリシーも適用されるとされている。

計算基盤は GitHub Actions であり、GitHub はスケールを理由にこれを選んだ。GitHub は、2018 年に導入された Actions を世界最大の CI/CD エコシステムと説明しており、GitHub Marketplace には 25,000 を超えるアクションがあり、平日には毎日 4,000 万件以上のジョブが実行されているとしている。

入門記事はこれらの制御を改めて述べたうえで、さらに 2 つを加えている。エージェントはリポジトリ権限が制限されたサンドボックス環境で作業すること、そしてトレーサビリティのためにコミットが共同作成者付きで記録されることである。また、このエージェントを従来の IDE アシスタントと対比している。後者では依然として開発者がブランチを作成し、コミットメッセージを書き、プルリクエストを作成するのに対し、コーディングエージェントはそれらの手順をプルリクエストのワークフロー内で自動化し、各手順が記録されてチームから見えるようになっている。

セットアップガイドは、デフォルトのファイアウォールがエージェントのアクセスを npm や pip のパッケージホストといった中核的なサービスに制限するものだと説明し、データ流出のリスクを管理する手段として提示している。悪意ある指示が何らかの形でエージェントに届いた場合、そうでなければコードやその他の機密情報がリモートの場所に漏洩しうるためである。リモート MCP サーバーの追加やその他のインターネットアクセスには、リポジトリの Copilot コーディングエージェント設定でファイアウォールの許可リストを更新する必要がある。

## 採用状況とエコシステム

発表時点では Copilot Enterprise と Copilot Pro+ の顧客が利用でき、リポジトリ単位で有効化された。Copilot Enterprise のユーザーについては、管理者がポリシーを有効にする必要もあった。

Osmani はこれを、他のクラウドエージェント（Claude Web、Codex、Jules）とともに、コードを書き、コマンドを実行し、レビューのための変更を提案する、並列化可能でサンドボックス化されたタスク向けに明確に位置づけられたツールとして分類している。また、GitHub が「Agent HQ」をプレビューしたと報告している。これは複数のサードパーティ製コーディングエージェントを一か所で調整するためのコントロールプレーンであり、同じタスクでそれらを並列に実行して出力を比較することもできる。これは、1 つではなく複数のエージェントを管理するための「ミッションコントロール」ダッシュボードへ向かう、より広い動きの一部とされている。
