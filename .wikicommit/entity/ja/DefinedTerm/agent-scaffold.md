**エージェントスキャフォールド**とは、コーディングエージェントにおいて言語モデルを取り囲むスキャフォールディング（足場）のコード、すなわち制御ループ、ツール定義、状態管理、コンテキスト戦略である。[[ScholarlyArticle/inside-the-scaffold]] は、エージェントが研究用プロトタイプから本番用ツールへと移行するにつれて、このコードがエージェントの振る舞い、犯す誤り、トークン予算の使い道をますます左右するようになっていると論じる。それにもかかわらず、研究文献ではこのコードはほとんど理解されていないままだという。概念的なサーベイは、ある本番システムを別のシステムと区別する実装戦略ではなく、抽象的な能力によってエージェントを分類しているからである。

## 用法

この論文の分類体系は、13 のオープンソースエージェントのソースコード分析から導かれたもので、スキャフォールドの設計を 3 つの層に整理している。

**制御アーキテクチャ** — エージェントが次に何をするかをどう決めるか。ここには制御ループのトポロジーが含まれる。論文はこれを、フィードバックループのない固定パイプラインから、ユーザー駆動のループ、逐次的な ReAct ループ、フェーズ分けされたループを経て、深さ優先の木探索、そして完全なモンテカルロ木探索に至るスペクトラム上に位置づけている。さらに、ループの*駆動者*、つまり次に何が起こるかをユーザー、スキャフォールド、モデルのいずれが決めるのか、そしてループを実装するコードレベルの仕組み（命令型の while ループ、再帰、コンパイルされたステートマシン、例外ベースのシグナリングなど）も含まれる。

**ツールと環境のインターフェース** — エージェントがコードや実行環境とどのように相互作用するか。ここには、ツールセットとツールをモデルに伝える方法、編集およびパッチのフォーマット、ツールが起動時に静的に登録されるのか動的に発見されるのか、コンテキスト取得のパラダイム（モデル主導のツール呼び出し、事前計算されたインデックス、埋め込み検索、または静的なリポジトリマップ）、そしてエージェントとホストの間の信頼境界を記録する実行分離モデルが含まれる。

**リソース管理** — エージェントがコンテキスト、状態、モデルをどのように管理するか。ここには、状態管理の戦略（履歴を保持するデータ構造と、それが追記専用か変更可能か）、コンテキストのコンパクション手法、マルチモデルのルーティング、セッションをまたぐ永続メモリが含まれる。

同じ論文は、これらの次元を連続的なスペクトラムとして扱うのが最善であり、5 つの**ループプリミティブ**（ReAct、生成・テスト・修復、計画・実行、複数回の試行リトライ、木探索）が、エージェントが重ねたり入れ子にしたりする合成可能な構成要素として働くと論じる。そのため、可能なスキャフォールドの空間はカテゴリー的ではなく組み合わせ的なものになる。

11 の本番用コーディングエージェントを対象とした別のソースコード研究である [[ScholarlyArticle/harness-engineering-anatomy-architecture-and-evolution-of-coding-agents]] は、「スキャフォールド」と [[DefinedTerm/agent-harness]] の関係を取り上げ、両者を実務上はほぼ同義語だとしている。区別が有用な場合には、「スキャフォールド」を構造的なコード（ループとレジストリ）に、「ハーネス」をそれを組み込んで出荷されるランタイムの成果物に充てている。その例として、Mini-SWE-Agent のスキャフォールドは 100 行の Python であるのに対し、Claude Code のハーネスはターミナル UI、パーミッションシステム、プラグインエコシステムを備えたプロダクトである、と挙げている。この研究は Inside the Scaffold を方法論上最も近い先行研究と位置づけ、その論文の 12 の次元を自らの 7 つのハーネスサブシステムに対応づけており、自らの語彙よりも明確だと判断した箇所ではループプリミティブの語彙を採用している。また、本番のループの多くは 1 つのプリミティブを実装するのではなくプリミティブを合成しているという観察もこの論文から引いており、調査対象の 4 つのプロバイダーネイティブなエージェントが現在搭載しているプランモードを、ReAct に計画・実行を接ぎ木したものと読み解いている。

## 適用される場面

- モデルの外で行われるあらゆる設計判断に当てはまる。どのツールをどの粒度で公開するか、履歴をどう表現するか、いつそれを圧縮するか、コードをどこで実行するか、どのモデルがどのステップを担当するか、といった判断である。論文の枠組みでは、同じ基盤モデルでもこれらの選択によって振る舞いが異なるため、これらの選択はモデルの能力を単に支えるのではなく、媒介しているとされる。
- スキャフォールドとモデルを切り離して論じられることを前提とする。論文は、この前提が実際にはしばしば破られることを明言している。論文はコーパス内のエージェントのベンチマークを行っていないが、その理由として、ベンチマークのスコアはスキャフォールドのアーキテクチャを、モデルの能力、プロンプトエンジニアリング、さらには反復回数の上限やコスト上限といった付随的な設定と混同してしまうことを挙げている。
- 単一のラベルに還元されると、分析の枠組みとして機能しなくなる。論文の主張によれば、複数のプリミティブを重ねたシステムに 1 つの名前（「ReAct エージェント」「パイプラインエージェント」）を割り当てると、実際にそのシステムを差別化している判断が見えなくなる。そのようなラベルを比較する研究は、ループのトポロジー、ループの駆動者、ツールセットの設計、コンテキスト管理を 1 つの二値に押し込めてしまう。
- 一様に決着しているわけではない。論文は、外部の制約が支配的で実務者が共通の答えにたどり着いた、収束した次元と、支配的な解決策がまだ現れていないために分岐したままの次元とを区別しており、後者のグループとしてコンテキストのコンパクション、状態管理、マルチモデルのルーティングを挙げている。
- その根拠は、当初の 22 の候補から網羅的でない方法で選ばれた 13 のエージェントを対象とする、単一の研究者による定性的なケーススタディであり、すべての主張は固定されたコミットにおけるファイルパスと行番号に紐づけられている。その知見は、2026 年初頭時点で調査されたオープンソースのコーパスを記述するものであり、スキャフォールドのコードを調査できないプロプライエタリなエージェントは、その構成上除外されている。
