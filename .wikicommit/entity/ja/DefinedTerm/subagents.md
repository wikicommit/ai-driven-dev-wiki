サブエージェントとは、エージェンティックな AI コーディングツール、あるいは他のエージェントがタスクを委任できる、専門化された AI エージェントである。それを記述する出典に共通する定義的な性質はコンテキストの分離である。サブエージェントは呼び出し元のエージェントのコンテキストの内側で実行されるのではなく、自らのコンテキストウィンドウの内側で動作し、その結果を親エージェントへ返す。

[[ScholarlyArticle/configuring-agentic-ai-coding-tools]] の説明では、サブエージェントは技術的には [[DefinedTerm/agent-skills]] の定義と同じ YAML フロントマターの構造を共有する Markdown ファイルである。二つの機構の機能上の違いは作業がどこで起きるかにある。サブエージェントは自らのコンテキストウィンドウを得るのに対し、スキルはその指示を呼び出し元のエージェントのコンテキストの内側で実行する。

## 用法

**設定機構として。** サブエージェントへの対応はスキルへの対応ほど普遍的ではない。同研究が調査した五つのツールのうち、[[SoftwareApplication/claude-code]]（`.claude/agents/`）、[[SoftwareApplication/github-copilot]]（`.github/agents/`）、[[SoftwareApplication/cursor]]（`.cursor/agents/`）がこの機構を提供しており、[[SoftwareApplication/codex-cli]] と [[SoftwareApplication/gemini-cli]] は提供していない。

普及の様子はスキルのそれに近いパターンをたどる。同研究は131のリポジトリにわたって452のサブエージェントを見出しており、1リポジトリあたり平均3.45、中央値2（最小1、最大18）である。これを使うリポジトリは一般に3つ未満しか定義しない。サブエージェントはまた、設定、スキル、MCP を含む他のいくつかの設定機構と正の相関を示す。

同研究が探して使用が見つからなかった能力が一つある。永続的なメモリである。Claude Code のサブエージェントは自らのメモリ——エージェントとのやり取りを越えて残り、デバッグの知見のように時間をかけて知識を蓄積するのに使える永続的なディレクトリ——を持てるが、著者らはサンプル内でそうしたメモリファイルを保存しているリポジトリを見つけられなかった。

**アーキテクチャ上の機構として。** [[ScholarlyArticle/building-effective-ai-coding-agents-for-the-terminal]] は、[[SoftwareApplication/opendev]] の設計において、実装する側からサブエージェントのオーケストレーションを記録している。そこでは各サブエージェントの型がフィルタされたツールの集合に制限されている——同報告は Code-Explorer、Planner、PR-Reviewer、Security-Reviewer、Web-Clone、Web-Generator、Project-Init、Ask-User を挙げている——のであり、その制限は実行時の権限チェックではなくスキーマの水準で強制される。同報告はこれを安全性の議論として提示している。読み取り専用のサブエージェントのスキーマからは書き込みツールが単に存在しないため、エージェントはそれを呼び出そうとすることも、例外を主張することも、迂回の条件を探ることもできない。

同報告はサブエージェントの能力を制限する三つの理由を挙げている。タスク管理のツールを除外してメインのエージェントだけがタスク一覧を調整するようにし、競合状態を防ぐこと。コンテキストの大きさを減らし、各サブエージェントをその特定の役割に集中させること。そして誤りの爆発半径を限定し、探索のサブエージェントが誤ってファイルを変更できないようにすることである。

同報告はまた二つの運用上の性質も述べている。メインのエージェントが同じ応答のなかで複数の生成呼び出しを出すと、複数のサブエージェントが並行して走りうる。同報告はこれを、独立した操作についてスレッドのオーバーヘッドをレイテンシの削減と引き換えるものと枠づけている。そしてサブエージェントのプロンプトは、過剰な探索を防ぐために明示的な終了条件を担う——同報告は、明確な停止条件を欠いた初期のプロンプトが際限のない探索を招き、探索用のサブエージェントが同じファイルを繰り返し読んでいたこと、そして停止条件とループ防止の指示を加えることで解決したことを記録している。さらに記録されている教訓は、初期のバージョンがサブエージェントにメインのエージェントと同じツールを与えており、それがコンテキストの汚染、役割の混乱、そして両方のエージェントが同時にタスク一覧を更新しようとしたときの衝突を引き起こしたことである。

コンテキストの分離は、サブエージェントを検索に特に有用にしているものでもある。同報告は、サブエージェントが多段階の検索を行うとき、数千行のコードにおよびうる中間の結果はサブエージェントのウィンドウの内側に留まり、蒸留された要約だけがメインのエージェントへ返ると指摘している——検索の過程そのものが、メインのエージェントが推論と行動に必要とするコンテキスト予算を食い潰すのを防ぐのである。

両方の出典が示唆し、OpenDev の報告が明示している帰結は、サブエージェントの結果がユーザーには見えないということである。それゆえ親エージェントは、それが見られたと前提するのではなく、自らその発見を提示せねばならない。

**日々の実務として。** Anthropic の Claude Code のドキュメントは、サブエージェントをユーザーが使える最も強力なツールの一つとして提示している。コンテキストが根本的な制約であるという理由による。コードベースを調べることは多くのファイルを読むことを意味し、それらはすべてメインの会話のコンテキストを消費するが、サブエージェントは別のコンテキストウィンドウで走って要約を報告する。推奨される呼び出し方は明示的である——*「サブエージェントを使って X を調査して」*——のであり、特に二つの用途を挙げている。探索がメインのコンテキストを消費しないよう調査のスコープを定めること（「無限の探索」と呼ぶ失敗パターンへの対処として挙げられている）、そしてタスクを完了とみなす前に完了した作業を新しいコンテキストでレビューし、作業をしたエージェント自身がそれを採点しないようにすること（[[DefinedTerm/llm-as-judge]] を参照）である。

[[Person/geoffrey-huntley]] は [[BlogPosting/ralph-wiggum-as-a-software-engineer]] で同じコンテキストの議論をさらに進め、一次コンテキストウィンドウには何も割り当てるべきではなく、ファイルシステムの検索やテストスイートが通ったかの要約といった高価な割り当て型の作業にサブエージェントを派遣するスケジューラとして動作させるべきだと論じている。彼はまた限界も記録している。数百のサブエージェントへ扇形に展開してすべてにビルドとテストを走らせると「悪い形のバックプレッシャー」が生じるのであり、それゆえ彼のプロンプトは検索とファイル書き込みには多数の並列サブエージェントを許しつつ、ビルドとテストには1つしか許さない。彼の説明では、並列度を制御することは実装の細部ではなく、この機構を使うことの一部である。

同じベンダーの [[PresentationDigitalDocument/claude-code-advanced-patterns]] のスライドは、委任の前に確認すべき三つの条件としてこの選択を述べている。サブエージェントに、定義されたツールのアクセス水準と成功ないし完了の基準を伴う、明確で比較的専門化された役割を与えられること。その作業を検査したり作業に介入したりすることが優先事項ではなく、完了したタスクといくつかの結論が返ってくれば十分であること。そしてコンテキストの管理がこの分離によって果たされること。同スライドはサブエージェントを同じ軸上の二つの隣人のあいだに置いている——無関係なタスクのための別のターミナルと、協調するワークストリームへ分割された一つの大きなタスクのためのエージェントチームである——それゆえ、単一のメインセッションから焦点の絞られたサブタスクを委任することが、サブエージェントをそのいずれからも区別する。

### 分離が何を要するか——あるベンダーの実装において

Anthropic の Claude Code のサブエージェント専用のドキュメントは、サブエージェントが何を引き継ぎ何を引き継がないかについて具体的であり、それがコンテキストの分離の背後にあるトレードオフを可読にしている。各サブエージェントは自らのコンテキストウィンドウ、自らのシステムプロンプト、自らのツールへのアクセス、独立した権限を伴って走り、ドキュメントは使う理由を五つ挙げている。コンテキストを温存すること、ツールの制限を通じて制約を強制すること、プロジェクトをまたいで設定を再利用すること、焦点の絞られたシステムプロンプトで振る舞いを専門化すること、そしてより速く安価なモデルへ作業を振り分けてコストを制御することである。

コストの側は、新しいサブエージェントが本当にまっさらから始まることである。会話の履歴も、すでに呼び出されたスキルも、親がすでに読んだファイルも見ない。受け取るのは親が組み立てた委任のメッセージに加えて、自らのシステムプロンプトと付加された環境の詳細であって、親の完全なシステムプロンプトではない。ドキュメントはまた、境界をまったく越えない状態も名指ししている。セッションの出力スタイルはサブエージェントの応答を形作らず、メインの会話の自動メモリは読み込まれず、サブエージェントのコンテキストウィンドウの大きさは自らのモデルによって決まるため、より小さなモデルへ委任するとそのサブエージェントのウィンドウも小さくなる。そこから導かれる案内は、タスクが頻繁なやり取りを必要とするとき、複数のフェーズが多くのコンテキストを共有するとき、あるいはレイテンシが問題になるときには、メインの会話を選ぶべきだというものである。fork でないサブエージェントはまっさらから始まり、コンテキストを集めるのに時間を要しうるからである。

組み込みのサブエージェントのうち二つは、読み込まれるものをさらに意図的に狭めている。Explore と Plan はいずれも Write と Edit を拒否された読み取り専用のエージェントであり、調査を速く安価に保つために CLAUDE.md の階層と親セッションの git の状態を飛ばす。ドキュメントは、どのエージェントがそれらを飛ばすかを変える設定はないと指摘している。掲げられる緩和策は、いずれにせよメインの会話が完全な CLAUDE.md のコンテキストとともにそれらの結果を読むのだから、規則を委任のプロンプトで言い直す必要があるのは、それがサブエージェント自身にまで届かねばならないときだけだ、というものである——例として「`vendor/` ディレクトリを無視する」が挙げられている。

**fork** は、その分離からの文書化された逃げ道である。`/subtask` で開始され、それまでの会話全体——同じシステムプロンプト、ツール、モデル、メッセージの履歴——を引き継ぐ。ドキュメントはこれを、サブエージェントが通常提供する入力側の分離を意図的に捨てつつ、出力側の分離は保つものと説明している。fork 自身のツール呼び出しは親の会話の外に留まり、最終的な結果だけが返ってくる。他のどのサブエージェントでも有用であるには背景が多すぎるとき、あるいは同じ出発点から複数の手法を並行して試すときに fork を推奨している。

同じドキュメントは、この機構が規模において突き当たる運用上の限界も記録しており、これは実務者が語る並列性の懸念の具体的な形である。入れ子には上限がある——既定では、サブエージェントはメインの会話から3層下まで自らのサブエージェントを立ち上げられ、それを超えると委任のツールが与えられず、サブエージェント自身が作業して一つの要約を返さねばならない。同時実行数には別の上限がある。既定では、21体目の実行中サブエージェントを立ち上げようとすると `Concurrent subagent limit reached` エラーで失敗し、モデルには再試行しないよう指示される。セッション全体で立ち上げられる総数に上限はない。いずれの上限も環境変数で設定できる。

設定の優先順位はスコープによる。管理された組織の設定から、単一セッションのためにコマンドラインで JSON として定義されたサブエージェント、プロジェクト、次いでユーザーのディレクトリへと下り、プラグインが提供するサブエージェントが最も低い。プロジェクトのスコープの内側では、作業ディレクトリから上へ辿って入れ子の `.claude/agents/` ディレクトリが走査され、そのディレクトリに最も近い定義が勝つ。プラグインのサブエージェントはセキュリティ上の理由からさらに制限されており、エージェントがプラグインから読み込まれるときには `hooks`、`mcpServers`、`permissionMode` のフロントマターのフィールドが無視される。サブエージェントが自らのコンテキストだけでなくリポジトリ自身のコピーを必要とする場合には `isolation: worktree` がそれを提供し、ドキュメントは Claude Code がその境界を能動的に強制する様子を説明している——各コマンドの作業ディレクトリを確認し、git をメインのチェックアウトへ向け直すコマンドをブロックし、worktree の内側に留まると検証できない形のコマンドを拒否する。

### コンテキストのファイアウォールと、それが向かないもの

[[BlogPosting/skill-issue-harness-engineering-for-coding-agents]] は、著者らにとってうまくいかなかったこの機構の用途について異例なほど率直である。役割ベースのサブエージェント——「フロントエンドエンジニア」のサブエージェント、「バックエンドエンジニア」のサブエージェント、「データアナリスト」のサブエージェント——であり、同記事はそれが「機能しない」と端的に述べている。機能すると報告されているのは分離の性質そのものであり、これを**コンテキストのファイアウォール**と呼んでいる。1セッション分の作業がまるごとカプセル化され、派遣元のエージェントは自らが書いたプロンプトとサブエージェントの最終的な結果だけを見るのであり、中間のツール呼び出し、ツールの結果、その他のメッセージは親のウィンドウへ入らない。同チームはサブエージェントを難しい問題に対する特に強力なレバーと呼んでいる。そうした問題が要する多数のコンテキストウィンドウにわたって一貫性を保つのが分離だからである。

その説明では、二つの運用上の慣習が伴う。サブエージェントは高度に凝縮された応答を返すべきであり、その応答自体が [[DefinedTerm/progressive-disclosure]] に従うべきである——彼らのエージェントは出典を `filepath:line` 形式または URL として引用するため、親はサブエージェントが読んだすべてに晒されることなく、必要なら見に行ける。そしてこの分割はコンテキストだけでなくコストのためにも用いられる。計画とオーケストレーションが起きる親セッションには高価なモデルを、各サブエージェントにはより安く速いモデルを充てるのであり、個別のタスクはより小さな指示の予算で足りるという理由による。

同記事はまた、ネイティブに対応していないハーネスのための回避策も記録している。親からのプロンプトで新しいエージェントのセッションを起動し、その最後のメッセージを返すツールを公開する MCP サーバーである。これをサブエージェントに*対応している*ハーネスと組み合わせると、ネイティブのサブエージェントが MCP を通じてさらにサブエージェントを派遣できてしまうこと、そして多くのハーネスが MCP のツール呼び出しにタイムアウトを課しており、それを引き上げる必要があるかもしれないことを警告している。

### 階層的な委任

[[BlogPosting/the-code-agent-orchestra]] は、同じ機構の二次的な用途を*チームのチーム*と呼んで説明している。オーケストレーターが6つのサブエージェントを直接立ち上げる——これはオーケストレーター自身のコンテキストを断片化する——のではなく、2人のフィーチャーリードを立ち上げ、それぞれが自らの担当を2〜3の専門家へ分解する。「検索機能を作れ」と与えられたフィーチャーリードは、それを自分でデータ・ロジック・API のサブエージェントへ分割し、親はその細部を一切見ない。Osmani の掲げる類比は、実際のエンジニアリング組織では VP が個々のエンジニアにタスクを割り当てることはなく、仕事はテックリードの層を通っていく、というものである。

同記事はまた、素朴なサブエージェントの構成になお欠けているものを率直に述べ、それを [[DefinedTerm/agent-teams]] へ進む理由として扱っている。親が依存グラフを手作業で管理せねばならず、サブエージェント間のピア間メッセージングがなく、共有のタスク一覧がなく、ファイルのスコープ設定がずさんだと2つのサブエージェントが同じファイルへ書いてしまう。同記事の3サブエージェントの実例では、協調のコストはすべて親が負っている。2つの独立したサブエージェントが並行して走ってレポートファイルを書き、3つ目は両方のレポートを待ってから始まる。

### 圧縮としてのサブエージェント

[[TechArticle/how-we-built-our-multi-agent-research-system]] は、この機構がなぜ検索に特に適するのかを簡潔に述べている。「検索の本質は圧縮である。膨大なコーパスから洞察を蒸留することだ」。サブエージェントは、自らのコンテキストウィンドウを持って並行して動作し、問いの異なる側面を同時に探索したうえで、リードエージェントのために最も重要なトークンを凝縮することによって、その圧縮を助ける。名指しされる第二の性質は関心の分離——それぞれ異なるツール、プロンプト、探索の軌跡——であり、それが経路依存性を減らし、徹底した独立の調査を可能にすると論じている。

同記事はまた、委任の指定が不十分なときに何が起きるかも記録している。各サブエージェントには目標、出力形式、どのツールと出典を使うかの案内、そして明確なタスクの境界が必要である。詳細なタスクの記述がなければ「エージェントは作業を重複させ、穴を残し、あるいは必要な情報を見つけられない」。実例となる失敗は、リードエージェントが「半導体不足について調べて」という短さの指示を出したもので、その後1つのサブエージェントは2021年の自動車向けチップ危機を探索し、他の2つは2025年のサプライチェーンについて互いに重複した。

同じ理由から、労力の調整もプロンプトへ押し込まれた。エージェントは適切な労力を判断するのが苦手であるため、明示的な規則が埋め込まれた。単純な事実調査には3〜10回のツール呼び出しを伴うエージェント1体、直接の比較には各10〜15回の呼び出しを伴うサブエージェント2〜4体、複雑な調査には責任が明確に分けられた10体超のサブエージェント、である。そうした規則のない初期のバージョンは単純なクエリに過剰投資しており、ある事例では単純な要求に対して50体のサブエージェントを立ち上げていた。

## 関連用語

サブエージェントは、設定に関する研究が目録化した八つの設定機構の一つであり、[[DefinedTerm/context-files]]、[[DefinedTerm/agent-skills]]、コマンド、ルール、設定、フック、MCP サーバーと並ぶ。著者らは、サブエージェントの利用パターンがスキルのそれに十分近いため、その内容とユースケースの違いは今後の専用の研究に値すると指摘している。アーキテクチャ的には、サブエージェントのオーケストレーションは [[DefinedTerm/agent-harness]] が調整するサブシステムの一つであり、フィルタされたエージェント自体は [[DefinedTerm/agent-scaffolding]] の段階でコンパイルされる。問題を複数のサブエージェントへ分割することは [[DefinedTerm/multi-agent-orchestration]] のもとで、タスクごとに新しいものを派遣しタスク間にレビューを挟むという具体的な規律は [[DefinedTerm/subagent-driven-development]] のもとで扱われる。そのコンテキスト分離の性質は、これを長期的な作業のための三つの標準的な技術の一つにしており、他に [[DefinedTerm/compaction]] と [[DefinedTerm/agentic-memory]] がある。
