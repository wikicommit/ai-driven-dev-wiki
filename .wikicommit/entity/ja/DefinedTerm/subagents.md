サブエージェントとは、エージェンティック AI コーディングツール、あるいは別のエージェントがタスクを委譲できる専門化された AI エージェントである。これを説明する情報源に共通する決定的な性質はコンテキストの分離である。サブエージェントは呼び出し元のコンテキストの中で実行されるのではなく、自身のコンテキストウィンドウの中で動作し、その結果を親のエージェントに返す。

[[ScholarlyArticle/configuring-agentic-ai-coding-tools]] の説明によれば、サブエージェントは技術的には [[DefinedTerm/agent-skills]] の定義と同じ YAML フロントマターの構造を共有する Markdown ファイルである。2つの仕組みの機能上の違いは、作業がどこで行われるかにある。サブエージェントは自分のコンテキストウィンドウを得るのに対し、Skill はその指示を呼び出し元のエージェントのコンテキストの中で実行する。

## 用法

**設定機構として。** サブエージェントのサポートは Skills のサポートほど普遍的ではない。この研究で調査された5つのツールのうち、[[SoftwareApplication/claude-code]]（`.claude/agents/`）、[[SoftwareApplication/github-copilot]]（`.github/agents/`）、[[SoftwareApplication/cursor]]（`.cursor/agents/`）はこの仕組みを提供するが、[[SoftwareApplication/codex-cli]] と [[SoftwareApplication/gemini-cli]] は提供していない。

採用は Skills に近いパターンを示す。研究は 131 のリポジトリにわたって 452 個のサブエージェントを発見した。1リポジトリあたり平均 3.45 個で中央値は 2（最小 1、最大 18）であり、これを使うリポジトリは3つ未満しか定義しないことが多い。サブエージェントはまた、Settings、Skills、MCP を含むいくつかの他の設定機構と正の相関を示している。

研究が探して使われていなかった機能の一つが永続的なメモリである。Claude Code のサブエージェントは自分のメモリ——エージェントとのやり取りをまたいで生き残る永続的なディレクトリで、デバッグの知見のように時間をかけて知識を積み上げるのに使える——を持てるが、著者らはサンプルの中でそうしたメモリファイルを保存しているリポジトリを1つも見つけられなかった。

**アーキテクチャ上の仕組みとして。** [[ScholarlyArticle/building-effective-ai-coding-agents-for-the-terminal]] は、[[SoftwareApplication/opendev]] の設計において、実装する側からサブエージェントのオーケストレーションを記録している。そこでは各サブエージェントの種別がフィルタされたツールセットに制限されており——レポートが名前を挙げるのは Code-Explorer、Planner、PR-Reviewer、Security-Reviewer、Web-Clone、Web-Generator、Project-Init、Ask-User である——、その制限は実行時の権限チェックではなくスキーマのレベルで強制される。レポートはこれを安全性の論拠として提示する。書き込み系のツールは読み取り専用のサブエージェントのスキーマから単に存在しないため、エージェントはそれを呼び出そうとすることも、例外を主張することも、迂回の条件を探ることもできないからである。

同レポートはサブエージェントの能力を制限する3つの理由を挙げている。タスク管理のツールを除外してメインのエージェントだけがタスクリストを調整するようにし、競合状態を防ぐこと。コンテキストのサイズを減らし、各サブエージェントを固有の役割に集中させること。そして誤りの影響範囲を限定し、探索用のサブエージェントが誤ってファイルを変更できないようにすることである。

またレポートは2つの運用上の性質も説明している。メインのエージェントが同じ応答の中で複数の生成呼び出しを出すと、複数のサブエージェントが並行して動作しうる。レポートはこれを、独立した操作についてスレッドのオーバーヘッドとレイテンシの削減を交換するものとして枠づけている。そしてサブエージェントのプロンプトは、探索のしすぎを防ぐために明示的な終了条件を持つ。レポートは、明確な停止条件を欠いた初期のプロンプトが無制限の探索を招き、探索用のサブエージェントが同じファイルを繰り返し読んでいたこと、そして停止条件とループ防止の指示を加えることでそれが解消したことを記録している。さらに記録されている教訓は、初期の版がサブエージェントにメインのエージェントと同じツールを与えており、それがコンテキストの汚染、役割の混乱、そして両方のエージェントが同時にタスクリストを更新しようとしたときの衝突を引き起こした、というものである。

コンテキストの分離は、とりわけ検索においてサブエージェントを有用にするものでもある。レポートは、サブエージェントが多段階の検索を行うとき、数千行のコードに及びうる中間結果はサブエージェントのウィンドウの内側に留まり、蒸留された要約だけがメインのエージェントに返ることを指摘する——これによって、検索の過程そのものが、メインのエージェントが推論と行動のために必要とするコンテキスト予算を食い潰すことを防いでいる。

両方の情報源が含意し、OpenDev のレポートが明示的に述べている帰結として、サブエージェントの結果はユーザーには見えないため、親のエージェントはそれが見られたと前提するのではなく、自らその知見を提示しなければならない。

**日々の実践として。** Anthropic の Claude Code のドキュメントは、コンテキストが根本的な制約であることを理由に、サブエージェントをユーザーが使える最も強力なツールの一つとして提示する。コードベースを調べることは多数のファイルを読むことを意味し、それらはすべてメインの会話のコンテキストを消費するが、サブエージェントは別のコンテキストウィンドウで動作して要約を報告する。推奨される呼び出し方は明示的である——*「サブエージェントを使って X を調べて」*——。そして特に2つの用途を挙げている。探索がメインのコンテキストを消費しないよう調査の範囲を限定すること（これは「無限の探索」と呼ばれる失敗パターンへの対処として挙げられている）。そしてタスクを完了とみなす前に、新しいコンテキストで完了した作業をレビューし、作業を行ったエージェントがそれを採点する者にならないようにすること（[[DefinedTerm/llm-as-judge]] を参照）である。

[[Person/geoffrey-huntley]] は [[BlogPosting/ralph-wiggum-as-a-software-engineer]] で同じコンテキストの議論をさらに推し進め、主コンテキストウィンドウにはそもそも割り当てるべきではなく、ファイルシステムの検索やテストスイートが通ったかどうかの要約といった、割り当てを要する高コストな作業のためにサブエージェントを派遣するスケジューラとして動作すべきだと論じる。彼はまた限界も記録している。数百のサブエージェントに扇形展開してすべてにビルドとテストを走らせると「悪い形のバックプレッシャー」が生じるため、彼のプロンプトは検索とファイル書き込みには多数の並列サブエージェントを許すが、ビルドとテストには1つしか許さない。彼の説明では、並列度を制御することは実装上の細部ではなくこの仕組みを使うことの一部である。

### あるベンダーの実装において、分離が何を犠牲にするか

Anthropic の Claude Code サブエージェント専用ドキュメントは、サブエージェントが何を引き継ぎ何を引き継がないかについて具体的であり、これによってコンテキストの分離の背後にあるトレードオフが読み取れる。各サブエージェントは自分のコンテキストウィンドウ、自分のシステムプロンプト、自分のツールアクセス、独立した権限を持って動作し、ドキュメントはこれを使う5つの理由を挙げる。コンテキストの節約、ツールの制限を通じた制約の強制、プロジェクトをまたいだ設定の再利用、焦点の絞られたシステムプロンプトによる振る舞いの専門化、そしてより速く安価なモデルへ作業を回すことによるコストの制御である。

犠牲となる側面は、新しいサブエージェントが本当に何もない状態から始まることである。会話の履歴も、すでに呼び出されたスキルも、親がすでに読んだファイルも見えない。受け取るのは親が構成する委譲のメッセージと、自分自身のシステムプロンプトおよび付加された環境の詳細であって、親の完全なシステムプロンプトではない。ドキュメントはまた、境界をまったく越えない状態も名指ししている。セッションの出力スタイルはサブエージェントの応答を形作らず、メインの会話の自動メモリは読み込まれず、サブエージェントのコンテキストウィンドウは自身のモデルによってサイズが決まるため、より小さなモデルに委譲するとそのサブエージェントのウィンドウも小さくなる。そこから導かれる指針は、タスクが頻繁なやり取りを必要とするとき、複数のフェーズが重要なコンテキストを共有するとき、あるいはレイテンシが重要なときには、メインの会話を選ぶべきだ、というものである。フォークでないサブエージェントは何もない状態から始まり、コンテキストを集めるのに時間を要しうるからである。

組み込みのサブエージェントのうち2つは、読み込まれるものをさらに意図的に狭めている。Explore と Plan はいずれも Write と Edit を拒否された読み取り専用のエージェントであり、調査を速く安価に保つために CLAUDE.md の階層と親セッションの git status を読み飛ばす。ドキュメントは、どのエージェントがそれらを読み飛ばすかを変える設定は存在しないと注記している。示されている緩和策は、いずれにせよメインの会話が完全な CLAUDE.md のコンテキストのもとでその結果を読むのだから、あるルールを委譲のプロンプトで言い直す必要があるのは、それがサブエージェント自身に届かなければならない場合だけだ、というものである——例として挙げられているのは「`vendor/` ディレクトリを無視すること」である。

**フォーク** は、その分離から抜け出すための文書化された非常口である。`/subtask` で開始され、それまでの会話全体——同じシステムプロンプト、ツール、モデル、メッセージ履歴——を引き継ぐ。ドキュメントはこれを、サブエージェントが通常提供する入力の分離を意図的に手放しつつ、出力の分離は保つものだと説明する。フォーク自身のツール呼び出しは親の会話の外に留まり、最終結果だけが返ってくる。他のどのサブエージェントであっても有用になるには背景情報が多すぎるという場合、あるいは同じ出発点から複数のアプローチを並行して試したい場合に、フォークが推奨されている。

同じドキュメントは、この仕組みが規模において突き当たる運用上の限界も記録しており、これは実践者が語る並列度への懸念の具体的な形でもある。入れ子には上限がある——既定では、サブエージェントはメインの会話から3層下まで自分のサブエージェントを生成でき、それを超えると委譲のツールが与えられず、サブエージェントは自分で作業して1つの要約を返さなければならない。同時実行には別の上限がある。既定では、21個目の実行中のサブエージェントを生成しようとすると `Concurrent subagent limit reached` エラーで失敗し、モデルには再試行しないよう指示される。セッションを通じて生成される総数に上限はない。どちらの上限も環境変数で設定できる。

設定の優先順位はスコープによって決まる。管理された組織の設定から、単一のセッションのためにコマンドラインで JSON として定義されたサブエージェント、プロジェクト、そしてユーザーのディレクトリへと続き、プラグインが供給するサブエージェントが最下位である。プロジェクトのスコープの内側では、入れ子になった `.claude/agents/` ディレクトリが作業ディレクトリから上へ辿って走査され、そのディレクトリに最も近い定義が勝つ。プラグインのサブエージェントはセキュリティ上の理由でさらに制限される。エージェントがプラグインから読み込まれた場合、`hooks`、`mcpServers`、`permissionMode` のフロントマターのフィールドは無視される。サブエージェントが自分のコンテキストだけでなくリポジトリの自分用のコピーを必要とする場合には `isolation: worktree` がそれを提供し、ドキュメントは Claude Code がその境界を能動的に強制すると説明している。各コマンドの作業ディレクトリを確認し、git をメインのチェックアウトへリダイレクトするコマンドをブロックし、ワークツリーの内側に留まることを検証できない形のコマンドを拒否するのである。

## 関連用語

サブエージェントは、設定に関する研究で整理された8つの設定機構の一つであり、[[DefinedTerm/context-files]]、[[DefinedTerm/agent-skills]]、Commands、Rules、Settings、Hooks、MCP サーバーと並ぶ。著者らは、サブエージェントの利用パターンが Skills のそれと十分に似ているため、両者の内容とユースケースの違いは今後専用の研究に値すると指摘している。アーキテクチャの面では、サブエージェントのオーケストレーションは [[DefinedTerm/agent-harness]] が調整するサブシステムの一つであり、フィルタされたエージェント自体は [[DefinedTerm/agent-scaffolding]] の間にコンパイルされる。問題を複数のサブエージェントに分割することは [[DefinedTerm/multi-agent-orchestration]] で、タスクごとに新しいものを派遣しタスク間にレビューを挟むという具体的な規律は [[DefinedTerm/subagent-driven-development]] で扱われている。そのコンテキスト分離という性質は、これを長い時間軸の作業のための3つの標準的な技法の一つにしており、他には [[DefinedTerm/compaction]] と [[DefinedTerm/agentic-memory]] がある。
