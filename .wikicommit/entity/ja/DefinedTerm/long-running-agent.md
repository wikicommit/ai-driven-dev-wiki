長時間稼働エージェント（long-running agent）とは、一度きりの作業として構成されるのではなく、多数のコンテキストウィンドウとサンドボックスにまたがって、場合によっては数日から数週間にわたり、目標に向けた前進を続ける AI エージェントである。障害から回復し、構造化された成果物を残し、中断したところから再開できる。そのためには、単一のチャットウィンドウで動くエージェントには必要のない形で、永続化、回復、検証の問題を解決しなければならない。

## 用法

この用語は、実際の本番エージェントでは混ざり合ってしまう、少なくとも三つの異なるものを含んでいる。長期的な推論（long-horizon reasoning）はモデルの品質に関する性質で、互いに依存する多数のステップにわたって計画・実行し、何ステップも前に誤った方向へ進んだことから立ち直る能力である。長時間の実行（long-running execution）はハーネスの性質で、エージェントのプロセスそのものが数時間から数日にわたって動き続け、その実行の間にモデルを数千回呼び出すこともある。永続的なエージェンシー（persistent agency）はアイデンティティに関する性質で、エージェントが個々のタスクよりも長く存続し、セッションをまたいで記憶を蓄積し、好みを学習していく（この概念の「メモリバンク」的な側面）。

Anthropic、Cursor、Google は、とくに長時間の実行について、同じ基本形に収斂したと説明されている。すなわち、モデルのループと実行用サンドボックスと永続的なセッションログを分離し、計画と生成と評価を分け、コンパクション、フック、コンテキストのリセットを付随的なものではなく第一級のものとして扱う、という形である（[[DefinedTerm/brain-hands-session-split]]、[[DefinedTerm/planner-worker-model]]、[[DefinedTerm/ralph-loop]] を参照）。

Anthropic 自身の説明である [[BlogPosting/effective-harnesses-for-long-running-agents]] は、問題を一文に絞り込んでいる。エージェントは個別のセッションで作業し、新しいセッションはいずれも以前のことを何も覚えていない状態で始まる、というものである。そしてこれを、交代制で働くエンジニアが配置されたプロジェクトで、新たに来た者が前任者のことを何も覚えていない、という比喩で表している。この記事の貢献は分類ではなく具体的なハーネスである。高レベルのプロンプトに対してフロンティアモデルをループで動かした結果として、二つの失敗モードが報告されている。一つは、エージェントがアプリケーション全体を一度に作り上げようとして機能の途中でコンテキストを使い果たし、何が起きたのかの再構築を次のセッションに委ねてしまうこと。もう一つは、ある程度の進捗ができた後、後続のセッションがそれを見て仕事は完了したと判断し、止まってしまうことである。

示されている対策は、実行を二つに分けるものである。[[DefinedTerm/initializer-agent]] は一度だけ実行され、以降のすべてのセッションが依存する環境を構築する。起動スクリプト、進捗ログ、最初のコミット、そしてプロンプトが含意するすべての機能を列挙し、それぞれを未達成（failing）とした JSON のリストである。その後の各セッションはその状態を読み込み、ちょうど一つの機能を進め、それをエンドツーエンドで検証し、リポジトリをコミット済みかつ文書化された状態で残す。述べられている重要な洞察は、新しいコンテキストウィンドウが何よりも必要とするのは作業の状態を素早く把握する手段であり、それを git の履歴とあわせて進捗ファイルが提供する、というものである。記事は、これらの実践が、有能なソフトウェアエンジニアが日々行っていることを手本にしたものだと述べている。

## 適用される場面

通常のエージェント設計がこの規模で機能しなくなる理由として、三つの障害が挙げられている。有限のコンテキスト（大きなウィンドウでもいずれは埋まり、[[DefinedTerm/context-rot]] によってハードリミットに達する前から性能が劣化する）、永続的な状態の欠如（新しいセッションは白紙から始まるため、明示的な引き継ぎがなければセッションが替わるたびに生産性が失われる）、そして自己検証の欠如（「終わったか」と尋ねられたモデルは、本来よりも頻繁に「はい」と答える）である。こうした追加の設計労力に見合うかどうかの判断基準として示されているのは、エージェントが途切れずに遂行する必要のある最も長い作業単位である。数分であればこれらのパターンは不要だが、数時間や数日であれば必要になる。

[[TechArticle/2026-agentic-coding-trends-report]] は同じカテゴリーを、設計上の問題ではなく一つの発展の軌跡として描き、それがどこまで到達したかを数字で示している。同レポートは、初期のエージェントを、このバグを直す、この関数を書く、このテストを生成するといった数分程度の単発タスクを扱うものと特徴づけ、2025 年末にはエージェントが数時間かけて機能一式を作り上げるようになったとし、2026 年にはエージェントが一度に数日単位で作業し、人間の関与を戦略的な意思決定の場面に集中させつつアプリケーション全体を構築するようになると予測している。最先端の状況として報告されている例は、1,250 万行の多言語コードベースである vLLM に活性化ベクトル抽出手法を実装した、7 時間にわたる単一の自律実行であり、同レポートによれば参照手法に対して 99.9% の数値精度に達した。作業できる時間の長さがなぜ重要なのかについての同レポートの論拠は、技術的なものではなく経済的なものである。エージェントが長時間にわたって無人で作業できるなら、これまで人員を割く価値がなかったプロジェクトが実現可能になり、誰にも手をつける時間がなかったために積み上がった技術的負債のバックログを体系的に片づけていける、というのである。
