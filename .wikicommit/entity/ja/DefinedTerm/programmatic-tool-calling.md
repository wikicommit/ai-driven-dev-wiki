プログラマティックツール呼び出し（programmatic tool calling）とは、言語モデルエージェントがツールを利用する方法の一つで、
モデルが関数ごとに構造化された呼び出しを 1 つずつ出力してその結果を順に受け取るのではなく、ツールを呼び出すコードを
書くというものである。この用語は従来のツール呼び出しとの対比で定義される。ツールで拡張されたモデルの標準的な展開パターン
であるネイティブな JSON ツール呼び出しでは、モデルはツール呼び出し API を通じて関数呼び出しごとに構造化された JSON
オブジェクトを 1 つ出力し、依存するステップのたびにさらなる推論ターンが必要になる。呼び出しが通常のコードであるため、
スクリプトはそれらを連鎖させる — ある呼び出しの引数を別の呼び出しの結果から計算する — ことも、ループや `asyncio.gather`
ブロックでファンアウトさせることもでき、何かがモデルに返される前にその結果をフィルタリングしたり集約したりできる。

## 用法

この用語は、密接に関連する 2 つのもの、すなわちプラットフォームの機能と、研究で評価されているアプローチとに用いられている。

### Claude Developer Platform の機能

[[Organization/anthropic]] は [[BlogPosting/introducing-advanced-tool-use]] において、Programmatic Tool Calling を
Claude Developer Platform のベータ機能として導入した。開発者はコード実行ツールとあわせて `allowed_callers` フィールドで
ツールをオプトインし、API はそれらを Python 関数として Claude に公開する。Claude はオーケストレーション用のコードを書き、
それはサンドボックス化されたコード実行環境で実行される。コードがツールを呼び出すたびに、開発者は `caller` フィールドを
含むツールリクエストを受け取って結果を返し、その結果はモデルではなくスクリプトによって処理され、スクリプトの最終的な
出力だけが Claude のコンテキストに入る。Anthropic の動機は、従来のツール呼び出しに帰せられる 2 つの問題、すなわち
中間結果によるコンテキストの汚染と、呼び出しごとに 1 回のモデル推論を行ったうえで自然言語で統合するという推論の
オーバーヘッドである。Anthropic は、複雑なリサーチタスクでの平均トークン使用量が 43,588 から 27,297 へと 37% 減少した
こと、多数の呼び出しが 1 つのコードブロックで実行される場合に推論パスが減ること、社内のナレッジ検索（25.6% から 28.5%）
と GIA ベンチマーク（46.5% から 51.2%）で精度が向上したことを報告しており、Claude for Excel が数千行のスプレッドシートを
読み取り変更するためにこの機能を使っているとも述べている。

### 研究での用法

この用語は [[ScholarlyArticle/the-bitter-lesson-of-tool-calling]] でも用いられており、同論文はこれを、JSON のツール
呼び出しを実行可能なコードで置き換えるべきだという議論を拡張するものとして説明している。この系譜の研究には
[[DefinedTerm/codeact]] が含まれる。同論文の実装では、ツールは型付きの Python スタブとして公開される。システム
プロンプトには、利用可能な関数スキーマと一対一に対応する関数を持つスタブモジュールのソースが埋め込まれ、モデルは
そのモジュールをインポートして必要な関数を呼び出すスクリプトを 1 つ書き、エージェントループはそれをシェルのサブプロセス
で実行してその出力から結果を読み取る。サブプロセスが戻った後に追加の推論ターンはない。

## 適用される場面

どちらのソースも、これをあらゆる場合において従来のツール呼び出しに取って代わるものではなく、トレードオフとして
扱っている。Anthropic は、これが最も有益なのは、集約値だけが必要な大規模データセットの処理、依存するツール呼び出しが
3 つ以上あるワークフロー、モデルが目にする前に結果をフィルタリングまたは変換する場合、中間データがモデルの推論に影響
すべきでないタスク、多数の項目にわたる並列処理であり、あまり有益でないのは、単一のツール呼び出し、モデルがすべての
中間結果を見てそれについて推論すべきタスク、応答の小さい手早い参照だと説明している。また、モデルが正しいパース用
コードを書けるようにツールの戻り値の形式を明確に文書化すること、並列に実行できる、あるいは再試行しても安全なツールを
オプトインすることを推奨している。その数値は Anthropic 自身の社内テストによるものである。

同論文の主張は、すでに実行可能なコードを書けるモデルにとって、呼び出しごとに JSON オブジェクトを出力することは
必然ではなく設計上の選択だというものである。これは、モデルのスクリプトを実行できる実行環境と、有効な複数行のコードを
生成できるモデルを前提としている。同論文の評価では、3 つの旧世代の OpenAI モデルが改行の代わりにリテラルの `\n`
エスケープシーケンスを書き、自らの JSON ベースラインを大きく下回った一方、Anthropic の 5 つのモデルすべてと最新の
GPT-5.6 系のバリアントは自らのベースラインに並ぶか上回った。同論文が報告するその他のコストは、固定的なシステム
プロンプトのオーバーヘッドにより、並列呼び出しがおよそ 26 未満では JSON ツール呼び出しより高コストになること、そして
一部のモデルが実際には呼び出しを実行せずに、集約に関する質問にパラメトリックな知識から答えてしまう傾向があることである。

その証拠の基盤は、ベンダーの社内測定と 1 つの統制された比較である。後者は、
[[Dataset/berkeley-function-calling-leaderboard]] v4 のサブセットで 14 のモデルを対象とした単一の研究であり、
そのスタブは実際の API を呼び出すのではなく引数をそのまま返すため、エンドツーエンドのツール利用ではなく引数の
シリアライズを測定している。この証拠に基づき、同論文は、これが 14 モデル中 11 モデルで JSON ツール呼び出しに並ぶか
上回ること、Claude Sonnet 5 で JSON ツール呼び出しが示した呼び出し脱落の閾値なしに大規模な並列ファンアウトを処理できる
こと、そしておとりのスキーマがコンテキストにあふれても安定していることを見いだしている。
