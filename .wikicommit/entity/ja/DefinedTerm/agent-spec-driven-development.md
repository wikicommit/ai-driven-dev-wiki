Agent-Spec Driven Development（ASDD）は、[[Organization/mercari]] が、自社向けに最適化した [[DefinedTerm/spec-driven-development]] の形態として説明する開発手法に付けた名前である。この手法は 2 つのステップから成る。まず、エージェントが関連資料を読み、技術を調査し、コードベースを分析して、Agent Spec と呼ばれる実装計画を作成する。次に、エージェントがその Agent Spec に沿って実装する。Agent Spec はタスクを列挙し、それぞれについて詳細な設計、すなわちどの既存実装を参考にするか、どのファイルを変更するか、どのような変更を加えるかを記述するもので、AI にとって曖昧さがなく、かつ人間にも読めることが意図されている。プロジェクトの記述は、ASDD を SDD の仕様さえも自動で生成することを目指す手法とも特徴づけている。

## 用法

この用語はメルカリの pj-double プロジェクトに由来し、同プロジェクトは 2025 年 9 月に ASDD を全社標準として提案した（[[BlogPosting/pj-double-mercari-development-productivity]]）。同社による 2 つの記述は、Agent Spec を異なる力点で説明している。プロジェクト自身の記述は、それをエージェントが生成し検査する計画として説明している。同社の CTO は [[BlogPosting/choosing-ai-native-mercari-guiding-principles]] で、ASDD を AI フレンドリーな仕様フォーマット、つまり既存のコードベースとプロジェクトの規約に適合する、実装に即した設計文書のテンプレートとして説明している。計画生成のステップでは、社内のナレッジベースに合わせて調整されたエージェントが一次情報を集めて計画の草案を作り、2 つ目のエージェントが、その計画がサービスのコーディング規約に従っているか、定められたセキュリティ基準を満たしているかを検査する。2 つのエージェントは修正と評価を交互に繰り返し、要件や仕様に残った不確実な点は質問として開発者に投げかけられる。実装のステップでは、実装を担うエージェント、テストと静的解析を実行するエージェント、そして結果を Agent Spec と照らし合わせて検証するエージェントが、タスクが完了するまで協働する。

プロジェクトの記述は 4 つの利点を挙げている。AI は計画または実装に必要な情報だけを保持するため、そのコンテキストが高密度に保たれること。計画をレビューできるため、結果が予測可能になること。実装が計画から宣言的に導かれるため、再利用可能で透明性があること。そして各ステップへの貢献が全社的な知識として蓄積されること。実装が AI に委任でき非同期に実行できるプロセスになるため、同記述は、生産性向上の源泉と見なすスケーラビリティを ASDD によるものとしている。タスクは Agent Spec の生成時に合理的な最小の作業単位へと分割され、1 タスクにつき 1 つのプルリクエストとなる。これを採用した開発者は、AI が書いたコードのレビューにもはやストレスを感じなくなったと報告しており、プロジェクトの現時点での結論は、AI が書いたコードと人間が書いたコードの間でレビューの労力に有意な差はないというものである。

CTO の記述では、テンプレートは API 定義、データモデル、データベーススキーマ、処理フロー、テストシナリオ、具体的な実装手順、マイクロサービス間の依存関係を定義する。その目的は、誰がどのタスクをどのファイルでどのコードスタイルで実装するのかを明確にし、AI エージェントを使う誰もが同じ品質と規約で実装できるようにすることである。エージェントが正確にコーディングできるよう、小さなタスク粒度がテンプレートに組み込まれている。同記述はまた、Agent Spec を、コーディング以外のプロセスにわたるエージェントの基盤として提示している。バックエンド、フロントエンド、モバイルの開発、QA のテストケース生成、AI レビュー、カスタマーサポートにおける仕様調査、リスク管理、コンプライアンスチェックである。また、UI を生成するエージェントである PJ Aurora の仕様としても使われている。CTO は ASDD を直感的な [[DefinedTerm/vibe-coding]] と対比している。その要点は、誰にでも再現可能な開発の規範を与えるエージェント型のアプローチであり、Agent Spec は社内で集めたベストプラクティスから継続的に育てていくものとされている。

## 適用される場面

ASDD は、仕様と設計が固まった後の段階、pj-double の記述が実装という下流の作業と呼ぶ段階のために設計されている。エージェントが必要とする一次情報が利用可能であることを前提としており、メルカリの場合それは、計画を生成するエージェントが最適化されているナレッジベースを意味する。また実際には、Agent Spec の生成時に作業を実行可能な合理的な最小単位へと分割する。CTO の記述はこの前提を明示している。ASDD の品質は Agent Spec を書く際に与えられるコンテキストの質に大きく依存し、適切なコンテキストがなければ期待どおりには機能しない。そのため同社は、過去の仕様や意思決定の履歴を整理するナレッジマネジメントの取り組みを並行して進めている。

pj-double の記述は、上流でどのようにうまくいかなかったかを報告している。ASDD は誰も合意していない確度の低い依頼からでも実装を生成してしまうため、AI が自らギャップを埋め、「技術的には正しいが誰も合意していない」成果物を生み出す。開発者たちは、最も時間がかかったのは関係者間の合意形成であったこと、自動生成された文書には根拠が含まれないため合意のための媒体として機能しないこと、そして毎回ゼロから書き直される Agent Spec をレビューするのは、手で書くより時間がかかりうることを報告した。記事の著者は独自の分析として、長大な生成済み Agent Spec は開発者の認知負荷を超えてしまい、一次情報と正確性の不確かな生成内容が混在していることが多いと付け加えている。プロジェクト自身の診断は、AI とともに考え決定する必要のある作業を、AI に引き渡す作業として扱ってしまったというものであった。

どの程度確立しているか: ASDD は 1 社の社内手法であり、それを構築したチームと同社の CTO によって説明されている。提示されている証拠は、そのチーム自身による測定、すなわち ASDD の土台である仕様駆動開発を採用したプロジェクトが工数見積もりに対して平均 150% 超の速度向上を示したという数値（見積もり工数と実績工数の主観的な比較から集めたもの）と、開発者からの定性的なフィードバックである。ASDD そのものについての個別の数値は示されていない。
