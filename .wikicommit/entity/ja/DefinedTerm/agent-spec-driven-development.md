Agent-Spec Driven Development（ASDD）は、[[Organization/mercari]] が、[[DefinedTerm/spec-driven-development]] を自社向けに最適化した形と位置づける開発手法に付けた名称である。これは 2 つのステップから成る。まず、エージェントが関連資料を読み、技術を調査し、コードベースを分析して、Agent Spec と呼ばれる実装計画を作成する。次に、エージェントがその Agent Spec に沿って実装する。Agent Spec はタスクを列挙し、それぞれについて詳細設計 — どの既存実装を参考にするか、どのファイルを変更し、どのような変更を加えるか — を記したもので、AI にとって曖昧さがなく、かつ人間にとっても読みやすいことを目指している。プロジェクト側の説明は、ASDD を SDD の仕様そのものまで自動生成することを目指す手法としても特徴づけている。

## 用法

この用語はメルカリの pj-double プロジェクトに由来し、同プロジェクトは 2025 年 9 月に ASDD を全社標準として提案した（[[BlogPosting/pj-double-mercari-development-productivity]]）。社内の 2 つの説明は Agent Spec を異なる力点で描いている。プロジェクト自身の説明は、それをエージェントが生成し検証する計画として描く。同社の CTO は [[BlogPosting/choosing-ai-native-mercari-guiding-principles]] で、ASDD を AI フレンドリーな仕様フォーマット、すなわち既存のコードベースとプロジェクトの規約に適合する、実装指向の設計ドキュメントのテンプレートとして説明している。計画生成のステップでは、社内のナレッジベースに合わせて調整されたエージェントが一次情報を収集して計画の草案を作り、第 2 のエージェントがその計画がサービスのコーディング規約に従っているか、定められたセキュリティ基準を満たしているかを検証する。両者は修正と評価を交互に繰り返し、要件や仕様に残った不確実性は開発者への質問として提示される。実装のステップでは、実装を担うエージェント、テストと静的解析を実行するエージェント、結果を Agent Spec と照らし合わせて検証するエージェントが、タスクが完了するまで協働する。

プロジェクト側の説明は 4 つの利点を挙げている。AI は計画または実装に必要な情報だけを保持するので、そのコンテキストが高密度に保たれること。計画をレビューできるので、結果が予測可能になること。実装が計画から宣言的に導かれるので、再利用可能で透明性があること。そして各ステップへの貢献が全社的なナレッジとして蓄積されること。実装が AI に委任でき非同期に実行できるプロセスになるため、この説明は、生産性向上の源泉と見るスケーラビリティを ASDD がもたらしたものとしている。タスクは Agent Spec の生成時に、動作する単位として合理的な最小の単位に分割され、1 タスクにつき 1 つのプルリクエストとなる。これを導入した開発者からは、AI が書いたコードのレビューにストレスを感じなくなったとの報告があり、プロジェクトの現時点での結論は、AI が書いたコードと人間が書いたコードとでレビューの手間に有意な差はないというものである。

CTO の説明では、このテンプレートは API 定義、データモデル、データベーススキーマ、処理フロー、テストシナリオ、具体的な実装手順、マイクロサービス間の依存関係を定める。その目的は、誰がどのタスクを、どのファイルで、どのコードスタイルで実装するかを明確にし、AI エージェントを使う人が誰であっても同じ品質と規約で実装できるようにすることであり、エージェントが正確にコーディングできるよう、小さなタスク粒度がテンプレートに組み込まれている。この説明はまた、Agent Spec をコーディング以外のプロセスにわたるエージェントの基盤としても示している。バックエンド、フロントエンド、モバイルの開発、QA のテストケース生成、AI レビュー、カスタマーサポートの仕様調査、リスク管理、コンプライアンスチェックである。これは UI を生成するエージェントである PJ Aurora の仕様としても用いられている。CTO は ASDD を直感的な [[DefinedTerm/vibe-coding]] と対比している。その要点は、誰にでも再現可能な開発規律を与えるエージェント的なアプローチにあり、Agent Spec は社内で集めたベストプラクティスから継続的に育てていくことが想定されている。

## 適用される場面

ASDD は、仕様と設計が固まった後のフェーズ — pj-double の説明が実装という下流の作業と呼ぶもの — を対象に設計されている。エージェントが必要とする一次情報が利用可能であることを前提としており、メルカリの場合それは計画生成エージェントが最適化されているナレッジベースを意味する。また実際には、Agent Spec の生成時に作業を、動作しうる合理的な最小単位に分割する。CTO の説明はこの前提を明示している。ASDD の品質は Agent Spec を書く際に与えられるコンテキストの質に大きく依存し、適切なコンテキストがなければ期待どおりには機能しない。だからこそ同社は、過去の仕様や意思決定の履歴を整理するナレッジマネジメントの取り組みを並行して進めている。

pj-double の説明は、上流でどのようにうまくいかなかったかを報告している。ASDD は誰も合意していない確度の低い要望からでも実装を生成してしまうため、AI が空白を自ら埋め、「技術的には正しいが誰も合意していない」成果物を生み出す。開発者からは、最も時間がかかったのは関係者間の合意形成だったこと、自動生成されたドキュメントには根拠が書かれていないため合意のための媒体として機能しないこと、毎回ゼロから書き直される Agent Spec のレビューは手で書くより時間がかかることがあったことが報告された。投稿の著者は自身の分析として、生成された長い Agent Spec は開発者の認知負荷を超え、一次情報と正確性の不確かな生成内容とが混在していることが多いと付け加えている。プロジェクト自身の診断は、AI とともに考え決めることが必要な仕事を、AI に委ねる仕事として扱ってしまっていた、というものだった。

どの程度確立されているか：ASDD は一企業の社内手法であり、それを構築したチームと同社の CTO によって説明されている。示されている根拠は、そのチーム自身の測定 — ASDD の土台である仕様駆動開発を採用したプロジェクトは、工数見積もりに対して平均 150% を超える速度向上を示したというもので、この数値は見積もり工数と実績工数の主観的な比較から集められたもの — と、開発者からの定性的なフィードバックである。ASDD 自体についての個別の数値は示されていない。
