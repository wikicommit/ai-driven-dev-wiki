エージェントハーネスとは、ステートレスな言語モデルを機能するエージェントへと変えるものであり、そのためにモデルの出力を外部での実行、永続的な状態、検証可能なフィードバックに根拠づける。[[ScholarlyArticle/code-as-agent-harness]] は、あらゆるハーネスにとっての中心的な設計上の問いを媒体の問い — モデルとそのタスク環境を何がつなぐのか — として捉え、その答えはコードであると論じる。コードは自然言語にはない形で実行可能であり、検査可能であり、状態を持つからである。この説明によれば、これらは記法としてのコードの性質ではなく、コードをハーネスのインターフェースとして機能させる性質である。実行可能性は、モデルが何を意図したかをハーネスが検証できることを意味し、検査可能性は、失敗を診断してフィードバックできることを意味し、状態を持つことは、エージェントのやり取りの履歴がステップ間で失われないことを意味する。

[[ScholarlyArticle/coding-benchmarks-are-misaligned-with-agentic-software-engineering]] は、この用語をより狭く、2 つのオーケストレーションレベルの一方として用いる。そこでは、エージェントハーネスとは、ツールとやり取りしながら単一のタスクに取り組む言語モデルであり、何らかのシステムプロンプトと参照できるコンテキストを備えたものである。[[DefinedTerm/system-harness]] はその外側の層であり、より上位の目標を具体的なタスクへと変換し、各タスクを 1 つ以上のエージェントハーネスに振り分け、それらが作用する環境を管理し、その出力をフィードバックに通す。この読み方では、「コーディングエージェント」と呼ばれる成果物の大半 — 論文はその中に Claude Code、Codex、Cursor Agent、SWE-Agent、OpenHands を挙げている — は、この意味でのエージェントハーネスである。同じ論文は、エージェントハーネスを、モデル、プロンプト、ツール、ループから構成される設定可能な実行器として扱い、それを取り巻くシステムハーネスはこれを調整することも、ブラックボックスとして扱うこともできるとしている。

## 用法

このサーベイは、ハーネスとその内部で動くコードを区別する。コードはハーネスの*内部*にある実行可能な媒体であり、ハーネスは、どのコードを実行し、信頼し、永続化し、再利用し、将来のワークフローへと昇格させてよいかを決める、より大きなポリシー統制されたシステムである。この枠組みでは、信頼性はモデルの判断やエージェントが作成した成果物だけでなく、人間が設計したポリシー、サンドボックスの境界、パーミッションの階層、検証オラクル、監査ログ、人間によるレビューのゲートにも依存する。

ハーネスのインターフェースにおけるコードには 3 つの役割が挙げられている。**推論のためのコード**は、内部の論理を、インタープリタ、記号ソルバー、実行トレースが検査し洗練できる検証可能な計算へと外在化する。**行動のためのコード**は、高レベルの意図を、身体性を持つ環境、GUI、ソフトウェア、ツール利用の環境に根ざした実行可能な操作へと変換する — サーベイは、実行可能な行動コードは知覚、アフォーダンス推定、コントローラー、安全層へのインターフェースであって、それらの代わりではないことを強調している。**環境モデリングのためのコード**は、世界の状態、遷移のダイナミクス、フィードバック信号を、エージェントが実行、編集、照会できるプログラムの状態、リポジトリ、シミュレーター、テスト、ログによって表現する。

そのインターフェースの上に位置するのが、サーベイが相互に作用する 5 つのカテゴリーにまとめるハーネスの仕組みである。長期にわたる実行を組織するプランニング。何をアクティブなコンテキストに残し、何を要約へとコンパクションし、何を永続的な外部ストレージへ退避させるかを決める状態管理層として説明される、メモリとコンテキストエンジニアリング。補助的な能力ではなく、モデルの意図と外部システムとの間の統制されたインターフェースとして扱われるツール利用。[[DefinedTerm/plan-execute-verify-loop]] による制御。そして、ハーネスそのものをどう測定し改善できるかを研究する [[DefinedTerm/harness-engineering]] である。

サーベイはまた、ハーネスを単なるコンテキストマネージャーやツール実行器ではなく、安全のための統制装置としても扱う — 提案された行動をリスクによって分類し、パーミッションの階層を強制し、厳格な制約に違反する行動を拒否し、不可逆な遷移や外部に影響を及ぼす遷移には人間の承認を求める層である。サーベイが提案する構成は、多層のパーミッションモデルである。閲覧、検索、静的検査、ログ分析のための読み取り専用の階層。隔離されたワークスペース内でのローカルなパッチ適用、テスト実行、一時的な依存関係のインストールのためのサンドボックス編集の階層。そして、ネットワークアクセス、認証情報、デプロイコマンド、パッケージの公開、破壊的なファイルシステム操作、Git 履歴の変更を対象とするフルアクセスの階層である。著者らは、同じコマンドが使い捨てのサンドボックスでは安全でも本番のリポジトリでは安全でないことがあるため、パーミッションはツールの種類だけでなく、引数、環境の状態、データの機密性、想定される副作用にも依存すべきだと論じる。

サーベイが安全性について行うもう 1 つの主張は、ヒューマン・イン・ザ・ループの制御は、ときおりのプロンプトによる割り込みではなく、永続的なハーネスの状態になるべきだというものである。承認、却下、ポリシーの例外、レビュアーによる修正のそれぞれが、ハーネスのパーミッションルール、エスカレーションのポリシー、検証基準、将来のメモリ検索を更新すべきであり、重大な承認は、何が提案され、どの証拠が示され、どのリスクが提示され、誰が決定し、どの責任の境界が変わったかを記録する、監査可能な状態遷移であるべきだとする。著者らはこれを実行可能な説明責任（executable accountability）と呼ぶ。

Gorinova らは、エージェントハーネスを測定に関する議論として用いる。ハーネスはベンチマークが実際に採点する対象の一部であるため、モデル名だけを挙げたリーダーボードのエントリは仕様として不十分だというのである。彼らは、単一の固定されたモデルについて Terminal-Bench のエントリを複数のエージェントハーネスで再現し、正答率がおよそ 58% からおよそ 80% までばらつくことを示したうえで、モデルが固定されている以上、このばらつきはモデルの能力の違いとしては説明できないと論じる — それは、プロンプト、ツールのインターフェース、行動ループ、環境の扱い、リトライの振る舞い、ターミナルの慣習が測定対象の一部であることを示している。さらに彼らは、モデルが特定のツール利用の慣習のもとで訓練または調整されている場合があるため、タスク固有の推論が始まる前から、ハーネスがモデルとよく噛み合うことも噛み合わないこともあると付け加えている。

LangChain の Harrison Chase は、この用語を、モデルを取り巻くシステム一般ではなく、エージェント構築ソフトウェアの階層構造における位置を指すものとして用いる。[[BlogPosting/agent-frameworks-runtimes-and-harnesses]] で彼は、エージェントハーネスを [[DefinedTerm/agent-framework]] の上に位置づける。フレームワークの価値がその抽象化にあり、その下にある [[DefinedTerm/agent-runtime]] が本番運用のためのインフラストラクチャを提供するのに対し、ハーネスはデフォルトのプロンプト、ツール呼び出しの独自の扱い方、プランニング用のツール、ファイルシステムへのアクセスを加える — いわば「バッテリー同梱」である。彼が例に挙げるのは LangChain 自身の [[SoftwareApplication/deep-agents]] であり、LangChain 上に構築され、「Claude Code の汎用版」と説明されている。彼は Claude Agent SDK を同じ方向への Claude Code の一歩と読み、すべてのコーディング CLI がある種のエージェントハーネスだと主張することもできると認めている。彼は、この用語を考案したのは自分ではなく、その定義は、3 つの層の間の境界と同様に、まだ明確ではなかったと述べている。

その後の LangChain の投稿で、Vivek Trivedy による [[BlogPosting/the-anatomy-of-an-agent-harness]] は、Chase の階層構造よりもはるかに広い定義を提案している。「Agent = Model + Harness」であり、「モデルでないなら、それはハーネスである」というものである。この説明では、ハーネスとはモデルそのもの以外のあらゆるコード、設定、実行ロジックである — システムプロンプト。説明文を伴うツール、スキル、MCP サーバー。ファイルシステム、サンドボックス、ブラウザといった同梱のインフラストラクチャ。サブエージェントの生成、ハンドオフ、モデルルーティングといったオーケストレーションのロジック。そして、コンパクション、継続、lint チェックといった決定論的な実行のためのフックやミドルウェアである。投稿は、ハーネスが状態、ツール実行、フィードバックループ、強制可能な制約を与えるまでは、生のモデルはエージェントではないと論じる。Trivedy はこれを、境界を引く多くの方法のうち、自身の見解として最もすっきりしたものとして提示し、各構成要素を、モデルが単独ではできないことから逆算して導いている。永続的な状態のためのファイルシステム、汎用ツールとしての bash とコード実行、安全な実行と自己検証のためのサンドボックス、重みを超えた知識のためのメモリファイルと検索、[[DefinedTerm/context-rot]] に対抗する [[DefinedTerm/compaction]] と [[DefinedTerm/tool-call-offloading]]、そして長期にわたる作業のための [[DefinedTerm/ralph-loop]] とプランニングである。投稿はまた、Claude Code や Codex のような製品はハーネスをループに含めた状態でポストトレーニングされているため、モデルがそのハーネスに過適合しうると論じる — しかし、あるタスクにとって最良のハーネスは、必ずしもモデルが訓練に用いられたハーネスではない。

Anthropic 自身のドキュメントも、自社製品についてこの用語を同じ広い意味で用いている。[[SoftwareApplication/claude-code]] の仕組みを説明する中で、ドキュメントは、エージェント的ループは 2 つの構成要素 — 推論するモデルと行動するツール — によって動いており、Claude Code はツールを提供し、モデルが見るコンテキストを管理する、モデルを取り巻く層であると述べ、これこそがエージェント的ハーネス（agentic harness）という用語の指すものだとしている。そのハーネスが回すループは、コンテキストの収集、行動の実行、結果の検証という、互いに溶け合う 3 つのフェーズとして説明されている。

オープンソースの [[SoftwareApplication/openharness]] プロジェクトは、README の中でこの用語を同じ広い意味で定義している。エージェントハーネスとは、LLM を包み込んで機能するエージェントにする完全なインフラストラクチャであり、モデルが知能を提供し、ハーネスが「手、目、記憶、安全の境界」を提供するというものである。README は「The model is the agent. The code is the harness.（モデルがエージェントであり、コードがハーネスである）」という一文で締めくくられている。それが実装するハーネスは、モデルが要求する各ツール呼び出しをパーミッションチェックとライフサイクルフックに通してから結果をフィードバックするエージェントループを中心に構成され、その周囲をツール、スキル、プラグイン、パーミッション、フック、コマンド、MCP、メモリ、バックグラウンドタスク、マルチエージェントの協調のためのサブシステムが取り囲んでいる — README の言葉を借りれば、モデルが何をするかを決め、ハーネスがそれをどう行うかを扱う。
