エージェントハーネスとは、エージェントの中核となる推論ループを包み、その周りでツールの実行、コンテキストの管理、安全性の強制、セッションの永続化を調整する実行時のオーケストレーション層である。[[ScholarlyArticle/building-effective-ai-coding-agents-for-the-terminal]] はこれを [[DefinedTerm/agent-scaffolding]] との明示的な対比で定義している。スキャフォールディングが最初のプロンプトより前にエージェントを構築することに関わるのに対し、ハーネスはその後に起きるすべて——ツールの派遣、コンテキストのコンパクション、安全性の不変条件の強制、ターンをまたぐ状態の永続化——に関わる。同報告は、この語の形式化を、長時間稼働するエージェントのための効果的なハーネスについての Justin Young の記述に帰し、それを長い時間幅にわたって動作するエージェントのためにこれらの関心事を調整する実行時のフレームワークと説明している。

## 用法

同報告が記録するアーキテクチャにおいて、ハーネスは支援的なサブシステムに囲まれた ReAct の実行ループを中心に据える。各イテレーションは固定された順序のフェーズを走る。前回のイテレーション以降に UI スレッドが注入したメッセージを取り出し、コンテキストの圧力を確認して削減の戦略を適用し、任意でツールへのアクセスなしに推論のトレースを生成し、完全なツールスキーマを添えて行動用のモデルを呼び、生じたツール呼び出しをレジストリを通じて派遣し、反復するか返すかを決める。

そのループの周りには七つのサブシステムが位置し、それぞれが異なる関心事に対処する。モジュール化され優先順位づけられたセクションからシステムプロンプトを組み立てるプロンプト合成エンジン。専門化されたハンドラへ派遣するツールレジストリ。複数の独立した層を通じて多層防御を提供する安全システム。会話を有限の資源として扱うコンテキストエンジニアリングのサブシステム。会話ログと学習された戦略のプレイブックの双方を永続化するメモリおよびセッションのサービス。そして、ツールへのアクセスをフィルタした隔離されたエージェントのインスタンスを立ち上げるサブエージェントのオーケストレーションである。

ハーネスはまた、推論モデル自体には提供できないいくつかの信頼性の機構が置かれる場所でもある。同報告は、キャンセルを伝播させるためにフェーズの境界でポーリングされる割り込みトークン、追加のユーザーメッセージが黙って落とされるのではなくイテレーションの境界で取り出され完了前に確認されるようにするスレッドセーフな注入キュー、そして各モデル呼び出しの後に累積トークン使用量を記録するコスト追跡を説明している。終了も同様にハーネスの責務である。ループは明示的な完了、モデルがツール呼び出しなしにテキストを返したときの暗黙の完了、エラー回復の予算の枯渇、あるいはイテレーションの安全上限によって終わりうる——そして終了を受け入れる前に、システムは未完了のタスク項目と未処理のメッセージを確認する。

同報告はスキャフォールディングとハーネスの分割そのものを転用可能な教訓として提示し、この分離が構築時の関心事と実行時の関心事の絡み合いを防ぐと論じている。ハーネスはエージェントが完全に初期化されているかを決して確認しない。スキャフォールディングの時点での先行的な構築が、常にそうであることを保証しているからである。実務上の利点として述べられるのは、各関心事が独立に進化できることである。新しいツールの追加は構築時のレジストリの変更だけを要し、コンパクション戦略の変更は実行時のハーネスの変更だけを要する。

### 一つのコンテキストウィンドウより長く続く作業のためのハーネス

その典拠とされた出典はいまや直接に参照できる。[[TechArticle/effective-harnesses-for-long-running-agents]] は、ハーネスの問題を上の実行時サブシステムの説明とは別の軸で枠づけている。単一の推論ループを何が包むかではなく、連続するセッションを何が橋渡しするか、である。掲げられる中核的な課題は、エージェントが離散的なセッションで作業せねばならず、新しいセッションはそれ以前に何があったかの記憶なしに始まることである——同記事の類比は、交代制で働くエンジニアが配属されたプロジェクトで、各人が前任者の記憶を持たずにやって来る、というものである。

その答えはサブシステムの目録ではなく、二部構成のハーネスである。ごく最初のセッションで環境を構築する専用のプロンプトを持つ**初期化エージェント**と、以後の毎セッションで走って漸進的な進捗を作り構造化された更新を残す**コーディングエージェント**である。脚注はこの分割が聞こえるより狭いものであることを明かしている。両者は最初のユーザープロンプトだけが異なり、システムプロンプト、ツール、ハーネスは共有している。初期化エージェントが残す環境こそが、実際に境界を越えて状態を運ぶものである。後のエージェントが失敗から成功へ反転させることだけを許される項目からなる JSON の機能一覧、開発サーバーを起動する `init.sh` スクリプト、そして各セッションの冒頭で git のログとあわせて読まれる進捗ファイルである。

同記事は、これがモデル単独では解けない問題に対するハーネス水準の答えであることを明言している。コンパクションだけでは十分でないこと、そしてフロンティアのモデルを高水準のプロンプトでコンテキストウィンドウをまたいでループさせてもなお本番品質のアプリケーションは作れないことを報告している。環境の各要素は、観察された特定の失敗に対する修正として導入されている。勝利宣言が早すぎること、環境をバグだらけあるいは未文書のまま残すこと、機能を早々に完了と印すこと、そして毎セッションでアプリの起動方法を導き直すことである。

### 設定の面としてのハーネス

第三の枠づけは、ハーネスを構築すべきアーキテクチャというより、調整すべき面として扱う。[[BlogPosting/skill-issue-harness-engineering-for-coding-agents]] は、その分解を `コーディングエージェント = AI モデル + ハーネス` と述べ、ハーネスをエージェントのランタイム、あるいはその周辺機器——モデルが環境とやり取りするために用いるもの——と定義している。その説明では、スキル、MCP サーバー、サブエージェント、メモリ、フック、コンテキストファイルは技術的には別々の概念だが、一つの設定の面をなしており、それを意図的に調整することが [[DefinedTerm/harness-engineering]] である。

同記事はまた、上のサブシステムの説明が扱っていない結合も記録している。フロンティアのコーディングモデルは自らのハーネス上で事後訓練されるため、訓練されたハーネスの上でモデルがよりよく働くことがありうる——例として、OpenCode が GPT/Codex 系のモデルのために `apply_patch` ツールを特別に追加せねばならなかった一方、Claude その他のモデルは通常の編集と書き込みのツールを使い続けていることが挙げられている。その反対の観察として、この結合が過適合にもなりうることが挙げられ、Terminal Bench 2.0 の結果——Opus 4.6 が Claude Code では33位、事後訓練で見ていないハーネスでは5位、いずれも上下およそ4位の誤差幅を伴う——が引かれている。

### 進化するソフトウェアシステムとしてのハーネス

上の説明はハーネスをアーキテクチャあるいは設定の面として扱う。[[ScholarlyArticle/dont-blame-the-large-language-model]] はこれを*活発に開発されているコードベース*として扱い、その開発がエージェントの品質に何をするかを測定する。その定義は他と両立する——「開発者と大規模言語モデルのあいだのミドルウェア層であり、システムプロンプト、ツールの実行、コンテキストの管理、反復的な推論ループをオーケストレートするもの」——が、研究の対象は設計ではなくリリースの履歴である。

まず見出されるのは、**ハイパーチャーン**と名づけられる開発のパターンである。五つのオープンソースのハーネスにわたり、週あたり1.5〜18回のリリースと1日あたり2.8〜34件のマージされたコミットを測定し、プルリクエストのレビュー時間の中央値は4時間未満で、最も活発なものは同じ期間の VS Code や GitHub CLI より13〜28倍リリース集約的である。バグ修正のコミットが開発努力のおよそ30% を占め、課題のバックログは閉じるどころか増えていく。ここから同論文が導く結論は直接に定義に関わる。「LLM を取り巻くエージェントハーネスは安定していない。それどころか、絶えず進化するソフトウェアシステムである」。

その統制された結果は、この進化がエージェントを確実に改善するわけではないというものである。Qwen Code CLI の35の連続するリリースにわたってモデルを固定し、層化された50件の SWE-bench Verified のタスクで評価したところ、解決率に統計的に有意な改善は見られなかった——初期のバージョンが後のものを上回ることさえあった——一方で、トークンの使用量とツール呼び出しの回数は場合によっては倍以上になった。コミットを参照用のハーネスのアーキテクチャへ対応づけることで、変更が品質の劣化に先行することが最も多い構成要素として LLM プロバイダ層とコンテキスト管理を、一貫して安全なものとして拡張性とセキュリティを同定している。ハーネスについて推論する者への実務的な推奨は、そのバージョン自体を一つの変数として扱うことである。開発者はリリースをまたいで解決率、トークン消費、ツール呼び出しのオーバーヘッドを追跡すべきであり、研究者は「基盤となる LLM と並んでエージェントハーネスのバージョンを報告し統制すべきである」。

### ハーネスの基層としてのコード

[[ScholarlyArticle/code-as-agent-harness]] はさらに別の整理の軸を提案する。ハーネスが何でできているか、どう調整されるかではなく、それがどの媒体で動作するか、である。その主張は、「立ち現れつつあるエージェンティックなシステムにおいて、コードはもはや目標とされる出力であるだけではない。それはますます、エージェントの推論、行動、環境のモデル化、そして実行に基づく検証のための運用上の基層として機能している」というものであり——それゆえハーネスは、モデルを取り巻くサービスの集合としてではなく、コード中心のインフラとして理解するのが最善だとする。

同サーベイの三層構成は、関心の空間の使える地図である。コードがエージェントを推論・行動・環境のモデル化へつなぐ**ハーネスインターフェース**層。長い時間幅の実行のための計画・メモリ・ツール利用と、フィードバック駆動の制御および最適化を扱う**ハーネス機構**層。そして共有されたコードの成果物が複数のエージェントにわたる協調・レビュー・検証を支える**スケーリング**層である。その制御に関する節は、機構を計画・実行・検証のループとして枠づけ、計画は契約の形成として扱われ、実行は権限管理された状態遷移のもとでサンドボックス化され、検証は決定的なセンサーを通じて行われる。

未解決の問題の一覧は、この概念になお欠けているものの表明でもある。最終的なタスクの成否を超えた評価、不完全なフィードバックのもとでの検証、退行のないハーネスの改善、複数エージェントにわたる一貫した共有状態、安全上重大な行動に対する人間の監督、そしてマルチモーダルな環境への拡張である。このうち二つ目と三つ目は、上の実証的な研究が取り組みはじめたものである。

### 自分ではなくモデルのためにハーネスを設計する

[[BlogPosting/building-a-c-compiler-with-parallel-claudes]] は、長時間稼働の自律的なプロジェクトにおける労力の大半が、ループそのものではなくエージェントを取り巻く環境——テスト、環境、フィードバック——に費やされたと報告している。ループが有用なのは、エージェントがどうすれば前進できるかを判断できる場合に限られるという理由による。著者はその規律を、自分は Claude のためのテストハーネスを書いているのであって自分のためではない、と繰り返し自分に言い聞かせねばならなかったことだと述べており、それはテストが結果をどう伝えるべきかについての前提を考え直すことを意味した。

そこから三つの具体的な規則が出てくる。各エージェントはコンテキストのない新しいコンテナで始まり、自らの位置を把握するのに実際の時間を費やすため、プロンプトは、現在の状況を頻繁に更新した詳細な README と進捗ファイルを保守するよう指示する。**コンテキストウィンドウの汚染**に対しては、ハーネスはせいぜい数行を表示し、重要なものはすべてファイルへログするようにし、ログの行は機械処理向けに整形される——grep で見つかるよう `ERROR` とその理由を同じ行に書き——さらに集計の要約統計をあらかじめ計算しておいて、エージェントが再計算しなくてよいようにする。**時間の見えなさ**に対しては、エージェントは時刻を知ることができず、前進する代わりに何時間もテストを走らせて平気でいるため、ハーネスは漸進的な進捗をまれにしか表示せず、既定でテストの1% ないし10% をサンプリングする `--fast` オプションを使う。これはエージェントごとには決定的だがマシン間ではランダムであるため、各エージェントは退行を完璧に同定でき、なおフリート全体としてはすべてのファイルを覆う。

同じ説明は、検証器の品質をこの仕組み全体を縛る制約に据えている。エージェントは与えられた問題を何であれ自律的に解いてしまうため、「タスクの検証器がほぼ完璧であることが重要である。さもなくば Claude は間違った問題を解いてしまう」。

### ハーネスの前提は期限切れになる

[[TechArticle/scaling-managed-agents]] は耐久性の問題を直接に述べている。ハーネスは、モデルが自力では何をできないかについての前提を符号化しており、その前提はモデルが良くなるにつれて古びるため、頻繁に問い直す必要がある。実例として挙げられるのは、**コンテキスト不安（context anxiety）**と名づけられた振る舞い——Claude Sonnet 4.5 がコンテキストの上限が近づくのを感じ取ってタスクを早々に切り上げてしまうもの——であり、これにはハーネスへコンテキストのリセットを加えることで応じた。同じハーネスを Claude Opus 4.5 で走らせるとその振る舞いは消えており、リセットはお荷物になっていた。

同記事の応答は、ハーネスを耐久性のある成果物として扱うのをやめることである。エージェントを三つのインターフェースへ仮想化する。起きたことすべての追記専用ログを保持するセッション、モデルを呼びそのツール呼び出しを振り分けるループを保持するハーネス、そして実行環境を提供するサンドボックスである。プロセスやファイルといった抽象がその下のハードウェアより長生きしたというオペレーティングシステムの類比に基づき、それぞれは他を乱すことなく置き換えられる。この構成において生き延びるのは、特定のループではなくインターフェースの集合であり、その結果は [[DefinedTerm/meta-harness]] と呼ばれている。

ハーネスの設計に限っても二つの帰結がある。ハーネスは使い捨てになる。セッションのログがその外側にあるため、ハーネス内の何もクラッシュを生き延びる必要はなく、代わりのものが同じセッションで目覚めて最後のイベントから再開できる。そしてハーネスは環境を所有しなくなる。他のあらゆるツールを呼ぶのとまったく同じようにサンドボックスを呼ぶため、死んだサンドボックスはセッションの喪失としてではなくモデルへ返されるツール呼び出しのエラーとして表面化し、ハーネスはそのサンドボックスがコンテナなのか、電話なのか、ゲームのエミュレータなのかを知らない。

## 関連用語

ハーネスは [[DefinedTerm/agent-scaffolding]] と対をなす一方の半分である。それが調整する機構のいくつかは独自の項目を持つ。[[DefinedTerm/adaptive-context-compaction]]、[[DefinedTerm/system-reminders]]、[[DefinedTerm/subagents]] である。同報告はこの組み立て全体を、単一のモデル呼び出しに頼るのではなく複数のモデル・検索器・ツールを合成することで最先端の結果が得られる複合 AI システムの一事例として位置づけている。
