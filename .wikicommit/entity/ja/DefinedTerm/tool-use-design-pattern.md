ツール利用デザインパターンは、言語モデルに対し、言語だけで回答するのではなく外部の関数やサービスを呼び出す能力を与える。モデルには利用可能なツールの記述が与えられる。モデルはリクエストに合うツールを選び、呼び出しの引数を生成し、その結果得られた出力がモデルの推論へと戻されるので、最終的な応答には呼び出しが生み出したものが反映される。AWS はこのパターンを、エージェントが言語の理解から行動の実行へと移る地点として説明し、エージェントが「応答を返すだけでなく行動する」ことを可能にするものだとしている。Microsoft のコースは、ツールを、エージェントを限られた行動の集合から幅広い行動へと広げるものと位置づけている。ツールのインターフェースは意図的に汎用的であり、算術からデータベースの検索、外部 API やクラウドサービスに至るまで、呼び出し可能なあらゆる機能を表す。

## 用法

ここでは、このメカニズムについて公開されている 4 つの説明を取り上げる。クラウドベンダーのアーキテクチャパターンカタログ、ベンダーが公開している教育コース、フレームワークベンダーのエンジニアリングブログ記事、そして研究とベンダー API を概観した独立した実務家の記事である。これらはメカニズムについては一致しているが、その周辺で何を強調するかは異なる。

**AWS Prescriptive Guidance** は、これを *tool-based agents for calling functions*（関数呼び出しのためのツールベースエージェント）という名前のアーキテクチャパターンとして提示し、5 段階の制御フローを示している。エージェントが自然言語のクエリを受け取る。内部のメタデータやツールレジストリから、利用可能なツール、スキーマ、機能を検索する。モデルがクエリを関数名、入力の型、説明といったツールのメタデータとともに受け取り、最も関連性の高いツールを選び、入力引数を組み立て、構造化された関数呼び出しを返す。エージェントシェルまたはツールランナーが選ばれた関数を実行して結果を返す。そしてモデルがその結果を、直接に、あるいは更新されたプロンプトを通じて、自然言語の回答に組み込む。このパターンについて挙げられている機能は、タスクの文脈に基づく動的なツール選択、OpenAPI や JSON Schema に基づくスキーマベースのプロンプティング、ツール出力を推論へと戻す連鎖、そしてステートレスまたはセッションを意識した動作である。挙げられているユースケースは、外部データにアクセスするバーチャルアシスタント、金融の計算機や見積もりツール、API ベースのナレッジワーカー、そしてマネージドクラウドサービスを呼び出すモデルである。この説明は最後に、このパターンをエンタープライズ環境におけるエージェント型 AI の重要な構成要素として位置づけ、特に宣言的なスキーマ、認可フレームワーク、マルチエージェントシステムと組み合わせた場合にそうだとしている。

**Microsoft の *AI Agents for Beginners*** コースは、これを *Tool Use Design Pattern* として扱い、それを実装するには何が必要かにより重きを置いている。コースは 6 つの構成要素を挙げている。名前、目的、必須パラメータ、期待される出力を定義する関数またはツールのスキーマ。ツールがいつどのように呼び出されるかを司る関数実行ロジック（プランナーモジュールやルーティングを伴うこともある）。ユーザー入力、モデルの応答、ツール呼び出し、ツール出力の間の流れを管理するメッセージ処理システム。エージェントをツールそのものに接続するツール統合フレームワーク。エラー処理とパラメータ検証。そして、ターンをまたいでコンテキストや過去のツールとのやり取りを追跡する状態管理である。ユースケースとしては、動的な情報検索、コードの実行と解釈、ワークフローの自動化、カスタマーサポート、コンテンツの生成と編集を挙げている。

同コースは用語についても直接述べている。*関数* と *ツール* はしばしば同じ意味で使われる。関数、すなわち再利用可能なコードのブロックこそが、エージェントがタスクを遂行するために使うツールだからである。関数呼び出しを実装するには 3 つのものが必要である。それをサポートするモデル、利用可能な関数を記述するスキーマ、そして各関数を実装するコードである。コースが説明する仕組みは 2 回の呼び出しによるやり取りである。スキーマとユーザーのリクエストがモデルに送られ、モデルは最終的な回答ではなく、選んだ関数の名前とその引数を返す。アプリケーションがその関数を実行して出力を返す。そして 2 回目の呼び出しで、ユーザーが目にする応答が生成される。コースは、1 回目の呼び出しから返ってくるのは回答ではなくツール呼び出しであることを明示している。

Microsoft の説明は、AWS のページが取り上げていないセキュリティ上の考慮事項も加えている。モデルが SQL を動的に生成する場合、インジェクションや破壊的なステートメントのリスクは現実のものだが、それにはモデルを信頼することではなく、データベースのパーミッションを設定することで対処する。すなわち、アプリケーションを読み取り専用のロールで実行し、エンタープライズ環境では運用システムからデータを投入した読み取り専用のデータベースやデータウェアハウスに対して実行する。さらに、アプリケーションを安全な環境で実行すれば、この対策はいっそう強化されると述べている。

Microsoft のコースはさらに、関数呼び出しはほとんどのエージェントのツール利用設計の中核にあるが、ゼロから実装するのは難しい場合があると述べ、実用的な道筋としてエージェント型フレームワークを挙げている。そして、このパターンを [[SoftwareApplication/microsoft-agent-framework]] と [[SoftwareApplication/microsoft-foundry-agent-service]] で実演している。前者では関数がデコレーターによってツールになり、フレームワークがそれをモデルに送るスキーマへとシリアライズする。後者ではツール呼び出しがサーバー側で処理され、ツールはツールセットにまとめられる。

**フレームワークベンダーのブログ記事**（[[BlogPosting/agentic-design-pattern-tool-calling]]）は、メカニズムに入る前に紙幅の大半を用語に費やしており、「ツール」「関数」「構造化出力」の区別は実際以上に複雑にされていると判断している。その答えは、ツールと関数は同義語だというものである。コードで構築されたエージェントにとって、ユーザーに代わって何かを行う最も簡単な方法は関数を呼ぶことであり、「ツール」は同じものを指すより高水準の言葉である。この説明は、これこそが「function call」と「tool use」を融合させた「tool call」という言い回しが使われる理由だとしている。また、業界はまだ 1 つの言葉に揃っておらず、主要なモデルプロバイダーが自社の API やドキュメントで同じ機能に別々の名前を付けていると指摘している。

同記事は、構造化出力をこのパターンとは別の軸で区別している。モデルがツールを選んだときに返すのはツールとその引数を名指しする JSON であり、この JSON を生成する振る舞いは、背後にツールがまったくない完全に構造化された応答を得るためにも流用できる。この説明はそれを、特定のプロバイダーのツール呼び出し API を超えて一般化する方法として提示している。また、このパターンが開発者に求める発想の転換を平易な言葉で述べている。現在のモデルは大部分がインターネットから閉ざされているため、モデルに投げかけるべき問いは「天気はどうか」ではなく「X、Y、Z ができるとして、天気をどう判断するか」であり、モデルの強みは実行することではなく、意図を判断して何をすべきかを述べることにある、というものである。

実装について、この説明はこのパターンを、ツール呼び出しをサポートするあらゆるプロバイダー API の上に載る薄いレイヤーとして扱っている。ただし、その実例は終始 1 つのプロバイダーを前提としている。関数シグネチャを Python の `inspect` モジュールで読み取り、そのプロバイダーが期待する型に整形するので、ツールを追加することは関数を追加することを意味する。同記事は、モデルが自身の知識から回答できるフォールバック用のツールを含めることを推奨している。また、フローを [[SoftwareApplication/burr]] のステートマシンとしてモデル化し、単一のディスパッチ用アクションではなくツールごとに 1 つのアクションを設けることを主張している。そうすれば、利用可能なすべてのツールがアプリケーショングラフ上で見えるようになるからである。4 つの説明のうち、このパターンがうまく振る舞わなかったことを報告しているのもこの記事だけである。モデルはツールの選択について気まぐれで、ツールを選ぶこと自体を拒むこともあれば、指示を見失うこともあった。まともな振る舞いが得られたのは、フレームワーク自身のデバッグ UI を使ってプロンプトエンジニアリングを反復した結果だった。

**独立した実務家の記事** である Han Lee の投稿は、このパターンに 2 つの方向から同時にアプローチしている。先行研究が何を提案したか、そしてモデルベンダーが実際に何を出荷したかである。その出発点となる前提は、言語モデルは最新の情報や独自の情報へのアクセスの欠如、推論や計画の能力の欠如、そしてハルシネーションに悩まされており、したがってエージェントとしての言語モデルにツールを提供するための別のメカニズムが必要だ、というものである。Lee は研究の系譜を深入りせずに要約している。ChatGPT 以前には、言語モデルを外部のエキスパートモジュールで拡張するという提案があった。ニューラルなモジュールは他の言語モデルであり、シンボリックなモジュールは計算機、通貨換算、API 呼び出しといった呼び出し可能なものであって、生成された入力アダプターを通じてそれらに到達する。同時期には、モデルに Web ブラウジングや Python インタープリターを与える取り組みがあった。ChatGPT 以後には、計算機や検索エンジンといったツールを使うようにモデルを訓練する研究と、固定された少数のツールではなく大量のツールの集合から取得させる研究があった。

この記事が最も具体的なのは、ベンダーが収束した先を比較する部分である。記事は、2023 年 6 月に Chat Completion API に追加された OpenAI の `tools` パラメータを基準として示している。これは関数仕様のリストであり、関数に名前を付け、それを説明し、必須フィールドを備えた JSON Schema オブジェクトとしてパラメータを宣言するもので、モデルが仕様に従う引数を生成できるようにするために存在する。そのうえで記事は、他のベンダーのものを、キー名が異なるだけの同じスキーマとして読み解いている。Google の Gemini Pro（2023 年 11 月発表）は `functionDeclarations` を使い、ツールの `type` を省略している。Anthropic のツール呼び出しベータ（2024 年 4 月）は `parameters` を `input_schema` に改名している。Cohere のもの（2024 年 4 月）はそれを `parameter_definitions` に改名している。LangChain は同じ月にモデル横断の汎用的なサポートを追加し、`@tool` デコレーターまたは `BaseTool` クラスの継承を通じてそれを公開した。Lee がこれらを並べて示す狙いは、スキーマは本質的に決着しており、実際に品質を左右するのは記述だという点にある。記述とは、モデルが最適な入力パラメータをどう生成するかを判断するために使うプロンプトなのである。

記事の結論は 1 つの定義である。言語モデルにとってのツールとは、名前、説明、そして明確に定義された入力の JSON スキーマを備えた呼び出し可能なもの（関数、API、SQL クエリ）である。そしてこの結論は、ツールについてのよくある言い方の訂正でもある。Lee の説明によれば、LLM はツールをまったく使っていない。LLM は入力パラメータを生成するだけであり、それを使ってツールを呼び出し、その結果を会話履歴に追加してモデルに最終出力を生成させるのは開発者の責任である。これは、AWS と Microsoft の説明がベンダーの内側から述べているのと同じ役割分担を、どのベンダーにも属さない外側の立場から言い直したものである。

## エージェントのためのツール設計

5 つ目の説明である [[BlogPosting/writing-effective-tools-for-agents]] は、上述のメカニズムを前提として受け入れたうえで、ツールをどう設計すべきかについて何が導かれるかを問うている。その出発点となる主張は、ツールは関数とは異なる種類の成果物だというものである。従来のソフトウェアは決定論的なシステム同士の間に契約を確立し、同じ呼び出しは毎回同じものを同じ方法で取得する。これに対してツールは、決定論的なシステムと非決定論的なエージェントとの間の契約であり、エージェントはツールを呼び出すこともあれば、一般的な知識から回答することも、まず明確化のための質問をすることも、使い方を理解できないこともある。そこから導かれる帰結として、ツールや MCP サーバーは、他の開発者やシステム向けに関数や API を書くのと同じやり方で書くべきではなく、エージェント向けに設計する必要があるとされる。

ここから 4 つの設計上の立場が導かれる。**既存のエンドポイントを単にラップしないこと**。ツールが多ければ常に良い結果につながるわけではないとされ、その理由として、エージェントは従来のソフトウェアとは異なるアフォーダンスを持つことが挙げられている。エージェントのコンテキストは限られているため、すべてのレコードを返すツールは、関連するレコードへ直接飛ぶのが自然な場面でも、無関係なレコードを読み通すことを強いる。推奨されるのは、影響の大きいワークフローに狙いを定めた少数のよく考えられたツールであり、頻繁に連鎖して使われるワークフローでは複数の基盤となる操作を統合することである。**名前空間化すること**（[[DefinedTerm/tool-namespacing]] を参照）。そうすれば、数百のツールを持つエージェントでもそれらを区別できる。**シグナルの高いコンテキストだけを返すこと**。低レベルの技術的な識別子よりも、エージェントの次の行動に役立つフィールドを優先する。著者らは、任意の英数字の UUID を意味のある言葉に解決するだけで、あるいは 0 始まりの ID 体系にするだけでも、ハルシネーションが減って検索タスクにおける Claude の精度が大きく向上したと報告しており、エージェントが簡潔な出力と詳細な出力を選べるレスポンス形式のパラメータを提案している。**レスポンスのサイズを制限すること**。ページネーション、フィルタリング、切り詰めを適切なデフォルトで用いる。記事は、Claude Code がデフォルトでツールのレスポンスを 25,000 トークンに制限していると述べている。また、切り詰めのメッセージやエラーテキストを不透明なコードとしてではなく、エージェントをよりトークン効率の高い戦略へと誘導する場として扱うべきだとしている。

この説明は、何が最も重要かについて、上述の独立した実務家の概観と一致している。その概観が、スキーマは本質的に決着しており品質を決めるのは記述だと結論づけているのに対し、この記事は、ツールの記述と仕様をプロンプトエンジニアリングすることを利用可能な最も効果的な手法の 1 つとして挙げ、新入社員に説明するように、つまり暗黙のコンテキストを明示するように書くことを推奨している。そして、ツールの記述を精密に改良した結果、Claude Sonnet 3.5 が [[Dataset/swe-bench-verified]] で最先端の性能に達したと報告している。そこに至るための方法は、判断ではなく評価のループである。現実的な作業から評価タスクを作り、それを単純なエージェント型ループとして実行し、得られたトランスクリプトを読む。記事はこの規律を Anthropic 自身の社内ツールに適用したと報告しており、ホールドアウトのテストセットでは、同社の研究者が書いたものであれ Claude が書いたものであれ、エキスパートによる実装を上回る改善が示されたという。
