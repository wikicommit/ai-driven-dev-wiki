ツール利用デザインパターンは、言語モデルに対し、言語だけで答えるのではなく外部の関数やサービスを呼び出す能力を与える。モデルには利用可能なツールの説明が与えられる。モデルはリクエストに合うツールを選び、呼び出しのための引数を生成し、その結果として得られた出力がモデルの推論に戻されることで、最終的な応答が呼び出しの結果を反映したものになる。AWS はこのパターンを、エージェントが言語の理解からアクションの実行へと移行する地点として説明し、エージェントが「応答を返すだけでなく行動する」ことを可能にするものだとしている。Microsoft のコースは、ツールを、エージェントを限られたアクションの集合から幅広いアクションへと広げるものとして位置づけている。ツールのインターフェースは意図的に汎用的に作られており、算術からデータベース検索、外部 API やクラウドサービスに至るまで、呼び出し可能なあらゆる機能を表す。

## 用法

ここでは、この仕組みについて公開されている六つの説明を取り上げる——クラウドベンダーのアーキテクチャパターンカタログ、ベンダーが公開している教育コース、フレームワークベンダーのエンジニアリングブログ記事、研究とベンダー API についての独立した実務者による概観、二つ目のフレームワークベンダーによるプロバイダ横断インターフェースの発表、そして AI ニュースレターに掲載されたレター——であり、これらは仕組みについては一致しつつ、その周辺で何を強調するかが異なっている。

**AWS Prescriptive Guidance** は、これを *tool-based agents for calling functions*（関数を呼び出すためのツールベースのエージェント）という名前のアーキテクチャパターンとして提示し、五つのステップからなる制御フローを示している。エージェントが自然言語のクエリを受け取る。エージェントが内部のメタデータまたはツールレジストリを検索し、利用可能なツール、スキーマ、機能を探す。モデルが、関数名、入力の型、説明といったツールのメタデータとともにクエリを受け取り、最も関連性の高いツールを選び、入力引数を組み立て、構造化された関数呼び出しを返す。エージェントシェルまたはツールランナーが選ばれた関数を実行してその結果を返す。そしてモデルがその結果を、直接、あるいは更新されたプロンプトを通じて、自然言語の回答に組み込む。このパターンについて挙げられている機能は、タスクのコンテキストに基づく動的なツール選択、OpenAPI や JSON Schema に基づくスキーマベースのプロンプティング、ツールの出力を推論に連鎖的に戻すこと、そしてステートレスまたはセッションを意識した動作である。挙げられているユースケースは、外部データにアクセスする仮想アシスタント、金融計算機や見積もりツール、API ベースのナレッジワーカー、そしてマネージドクラウドサービスを呼び出すモデルである。この説明は最後に、このパターンを、特に宣言的なスキーマ、認可フレームワーク、マルチエージェントシステムと組み合わせた場合に、エンタープライズ環境におけるエージェント型 AI の重要な構成要素として位置づけている。

**Microsoft の *AI Agents for Beginners*** コースは、これを *Tool Use Design Pattern* として扱い、それを実装するために何が必要かに重きを置いている。挙げられている構成要素は六つある。名前、目的、必須パラメータ、期待される出力を定義する関数またはツールのスキーマ。ツールがいつどのように呼び出されるかを制御する関数実行ロジック（プランナーモジュールやルーティングを伴うこともある）。ユーザー入力、モデルの応答、ツール呼び出し、ツールの出力の間の流れを管理するメッセージ処理システム。エージェントをツールそのものに接続するツール統合フレームワーク。エラー処理とパラメータの検証。そしてターンをまたいでコンテキストと過去のツールとのやり取りを追跡する状態管理である。そのユースケースは、動的な情報取得、コードの実行と解釈、ワークフローの自動化、カスタマーサポート、そしてコンテンツの生成と編集である。

同コースは用語についても直接述べている。*関数*と*ツール*はしばしば同じ意味で使われるが、それは関数——再利用可能なコードのブロック——こそがエージェントがタスクを遂行するために使うツールだからである。関数呼び出しを実装するには三つのものが必要である。それをサポートするモデル、利用可能な関数を記述するスキーマ、そして各関数を実装するコードである。同コースが説明する仕組みは二回の呼び出しからなるやり取りである。スキーマとユーザーのリクエストがモデルに送られ、モデルは最終的な回答ではなく、選んだ関数の名前とその引数を返す。アプリケーションがその関数を実行して出力を返す。そして二回目の呼び出しでユーザーが目にする応答が生成される。同コースは、一回目の呼び出しから返ってくるのは回答ではなくツール呼び出しであることを明言している。

Microsoft の説明は、AWS のページが取り上げていないセキュリティ上の考慮事項を付け加えている。モデルが SQL を動的に生成する場合、インジェクションや破壊的なステートメントのリスクは現実のものだが、それはモデルを信頼することによってではなく、データベースの権限を設定することによって対処される——アプリケーションを読み取り専用のロールで実行し、エンタープライズ環境では業務システムからデータを取り込んだ読み取り専用のデータベースやデータウェアハウスに対して実行する。アプリケーションを安全な環境で実行することで、これがさらに強化されるとも述べている。

Microsoft のコースはさらに、関数呼び出しはほとんどのエージェントのツール利用設計の中核にあるが、一から実装するのは難しい場合があると付け加え、実践的な手段としてエージェントフレームワークを挙げている。そして、関数がデコレータによってツールになり、フレームワークがそれをモデルに送るスキーマへとシリアライズする [[SoftwareApplication/microsoft-agent-framework]] と、ツール呼び出しがサーバー側で処理され、ツールがツールセットにまとめられる [[SoftwareApplication/microsoft-foundry-agent-service]] を通じて、このパターンを実演している。

**あるフレームワークベンダーのブログ記事**（[[BlogPosting/agentic-design-pattern-tool-calling]]）は、仕組みに入る前に用語から始めており、「ツール」「関数」「構造化出力」の区別が実際以上に複雑にされていると判断している。その答えは、ツールと関数は同義語だというものである。コードで構築されたエージェントにとって、ユーザーに代わって何かを行う最も簡単な方法は関数を呼び出すことであり、「ツール」は同じものを指すより高水準の言葉である——同記事は、これこそ「関数呼び出し（function call）」と「ツール利用（tool use）」を合わせて「ツール呼び出し（tool call）」という言い方になっている理由だとしている。また、業界はまだ一つの言葉にまとまっておらず、主要なモデルプロバイダが自社の API やドキュメントで同じ機能を異なる名前で呼んでいると指摘している。

同記事は、構造化出力をこのパターンとは別の軸で区別している。モデルがツールを選んだときに返すのはツールとその引数を指定する JSON であり、この JSON を生成する振る舞いを流用すれば、背後にツールがまったくない完全に構造化された応答を得ることができる——同記事はこれを、特定のプロバイダのツール呼び出し API を超えて一般化する方法として提示している。また、このパターンが開発者に求める発想の転換を平易な言葉で述べている。現在のモデルはおおむねインターネットから切り離されているので、モデルに投げかけるべき問いは「天気はどうか」ではなく、「X、Y、Z ができるとして、天気をどうやって判断するか」であり、モデルの強みは意図を判断して何をすべきかを述べることであって、それを実行することではない、というのである。

実装について、同記事はこのパターンを、ツール呼び出しをサポートする任意のプロバイダ API の上に載る薄い層として扱っているが、その実例は全体を通じて一つのプロバイダを前提としている。関数のシグネチャは Python の `inspect` モジュールによって読み取られ、そのプロバイダが期待する型に整形されるので、ツールを追加することは関数を追加することを意味する。同記事は、モデルが自身の知識から回答できるようにするフォールバック用のツールを含めることを勧め、また——フローを [[SoftwareApplication/burr]] のステートマシンとしてモデル化しつつ——単一のディスパッチ用アクションではなくツールごとに一つのアクションを設けるべきだと主張している。そうすれば、利用可能なすべてのツールがアプリケーショングラフ上で見えるようになるからである。同記事は、これらの説明の中でこのパターンがうまく動かなかったことを報告している唯一のものでもある。モデルはツールの選択に関して気まぐれで、ツールを選ぶのを拒むこともあれば指示を見失うこともあり、妥当な振る舞いはフレームワーク自身のデバッグ UI を使ってプロンプトエンジニアリングを繰り返すことで得られた。

**独立した実務者である Han Lee による記事**は、このパターンに二つの方向から同時にアプローチしている。すなわち、先行研究が何を提案したか、そしてモデルベンダーが実際に何を出荷したかである。その出発点となる前提は、言語モデルは最新の情報や独自の情報にアクセスできないこと、推論や計画の能力が欠けていること、そしてハルシネーションに悩まされており、そのためエージェントとしての言語モデルにツールを提供する別の仕組みが必要だということである。Lee は研究の系譜を深入りせずに要約している。ChatGPT 以前の、言語モデルを外部の専門モジュール——ニューラルなものは他の言語モデル、シンボリックなものは電卓、通貨換算、API 呼び出しといった呼び出し可能なもの——で拡張し、生成された入力アダプタを介してそれらにアクセスするという提案、同時期の、モデルにウェブブラウジングや Python インタプリタを与える取り組み、そして ChatGPT 以後の、電卓や検索エンジンといったツールを使うようにモデルを訓練する研究と、固定された少数のツールではなく大規模なツール群から検索させる研究である。

同記事が最も具体的なのは、ベンダーが何に収束したかを比較している部分である。同記事は、2023 年 6 月に Chat Completion API に追加された OpenAI の `tools` パラメータを基準として示している。これは関数の仕様のリストで、関数に名前を付け、説明し、そのパラメータを必須フィールドを持つ JSON Schema オブジェクトとして宣言するものであり、モデルが仕様に従った引数を生成できるようにするために存在する。そのうえで他のベンダーのものを、キー名が異なるだけの同じスキーマとして読み解いている——Google の Gemini Pro（2023 年 11 月発表）は `functionDeclarations` を使い、ツールの `type` を省略している。Anthropic のツール呼び出しベータ（2024 年 4 月）は `parameters` を `input_schema` に改名し、Cohere のもの（2024 年 4 月）はそれを `parameter_definitions` に改名している。LangChain は同じ月にモデル横断の汎用的なサポートを追加し、それを `@tool` デコレータ、または `BaseTool` クラスの拡張を通じて公開した。Lee がこれらを並べて示す意図は、スキーマは本質的に定まっており、実際に品質を決めるのは説明だという点にある。説明こそが、最適な入力パラメータをどう生成するかをモデルが判断するために使うプロンプトなのである。

同記事の結論は、一つの定義——言語モデルにとってのツールとは、名前、説明、そして明確に定義された入力 JSON スキーマを持つ呼び出し可能なもの（関数、API、SQL クエリ）である——と、それについてのよくある言い方の訂正である。Lee の説明によれば、LLM はツールをまったく使っていない。LLM は入力パラメータを生成するだけであり、それを使ってツールを呼び出し、その結果を会話履歴に追加してモデルが最終的な出力を生成できるようにするのは開発者の責任である。これは、AWS と Microsoft の説明がベンダーの内側から述べているのと同じ役割分担を、どのベンダーにも属さない外側から言い直したものである。

そのモデル横断サポートについての **LangChain 自身の発表**である [[BlogPosting/tool-calling-with-langchain]] は、同じ収束をフレームワークの側から語っている。同記事は、ネイティブなツール呼び出しの起源を、記事のおよそ一年前にリリースされ、その年の 11 月に「ツール呼び出し（tool calling）」へと発展した OpenAI の「関数呼び出し（function calling）」に求めている。その後の数か月で Gemini、Mistral、Fireworks、Together、Groq、Cohere、Anthropic が続いたが、それぞれインターフェースが少しずつ異なり、中でも OpenAI、Anthropic、Gemini のものは互いに互換性がなかった。Lee がベンダーのスキーマを本質的に同じものとして読むのに対し、LangChain の対応は、残る違いを一つのインターフェースの背後に隠すことだった。任意のツール呼び出し対応モデルにツール定義を付与する `bind_tools()`、各呼び出しを名前、引数、ID として返す `tool_calls` 属性、そしてその両方を実装する任意のモデルで動作するエージェントのコンストラクタである。同記事はこのパターンを構造化出力とも関連づけている。その `with_structured_output()` はほとんどのモデルでツール呼び出しの上に構築されており、常に指定されたスキーマで出力を返すのに対し、ツールをバインドした場合はモデルが一つのツールを呼び出すことも、複数を呼び出すことも、まったく呼び出さないこともできる。

**DeepLearning.AI の *The Batch* に掲載されたレター**である [[BlogPosting/agentic-design-patterns-part-3-tool-use]] は、エージェント型デザインパターンに関するシリーズの三回目で、Tool Use を AI のエージェント型ワークフローの重要なデザインパターンと呼んでいる。そこでは LLM に、情報の収集、アクションの実行、データの操作のために呼び出しを要求できる関数が与えられる。同レターは仕組みを生成テキストのレベルで説明している。モデルはファインチューニングされるか、あるいは（おそらく few-shot プロンプティングを用いて）プロンプトで指示されて、呼び出しを要求する特別な文字列を出力する——呼び出し先は検索エンジンや、モデルが答えを直接生成したのでは正しく求められそうにない算術式を評価するための Python インタプリタである——そして後処理のステップがその文字列を検出し、関連するパラメータで関数を呼び出し、その結果を追加のコンテキストとしてモデルに戻す。文字列の正確な形式は実装によって異なる。同レターは規模の問題も提起している。モデルが数百のツールにアクセスでき、そのすべてをコンテキストに入れるには多すぎるシステムでは、ヒューリスティックによって現在のステップに最も関連するサブセットを選ぶことがあり、同レターはこれを、検索拡張生成（retrieval augmented generation）システムがテキストのサブセットを選ぶやり方になぞらえている。また、初期のツール利用の研究の多くはコンピュータビジョンのコミュニティから生まれたと指摘している。大規模なマルチモーダルモデルが広く利用できるようになる前は、LLM ベースのシステムが画像を操作するには、その画像に対して関数を呼び出すしかなかったからである。そして GPT-4 の関数呼び出し機能を、汎用的な実装に向けた重要な一歩と呼んでいる。

## エージェントのためのツール設計

さらにもう一つの説明である [[BlogPosting/writing-effective-tools-for-agents]] は、上記の仕組みを前提としたうえで、ツールをどう設計すべきかについてそこから何が導かれるかを問うている。その出発点となる主張は、ツールは関数とは異なる種類の成果物だということである。従来のソフトウェアは決定論的なシステム同士の契約を確立し、同じ呼び出しは毎回同じものを同じ方法で取得する。これに対してツールは、決定論的なシステムと非決定論的なエージェントとの間の契約であり、エージェントはツールを呼び出すかもしれないし、一般的な知識から答えるかもしれないし、まず確認の質問をするかもしれないし、使い方を理解できないかもしれない。そこから述べられる帰結は、ツールや MCP サーバーは、他の開発者やシステムのために関数や API を書くのと同じやり方で書くべきではなく、エージェントのために設計する必要があるということである。

そこから四つの設計上の立場が導かれる。**既存のエンドポイントを単にラップしないこと**：ツールが多ければ常により良い結果につながるわけではないとされ、その理由として、エージェントは従来のソフトウェアとは異なるアフォーダンスを持つことが挙げられている——エージェントのコンテキストは限られているため、すべてのレコードを返すツールは、関連するレコードに直接飛ぶのが自然な場面で、無関係なレコードを読み通すことをエージェントに強いる。推奨されるのは、影響の大きいワークフローを対象とした、よく考え抜かれた少数のツールであり、あるワークフローが頻繁に連鎖して実行される場合には、その基盤となる複数の操作を統合する。**名前空間化すること**（[[DefinedTerm/tool-namespacing]] を参照）：数百のツールを持つエージェントがそれらを区別できるようにする。**シグナルの高いコンテキストだけを返すこと**：低レベルの技術的な識別子よりも、エージェントの次のアクションに役立つフィールドを優先する。著者らは、任意の英数字からなる UUID を意味のある言葉に解決するだけで、あるいは 0 から始まる ID 方式にするだけでも、ハルシネーションが減ることで検索タスクにおける Claude の精度が大幅に向上したと報告しており、エージェントが簡潔な出力と詳細な出力を選べる応答形式パラメータを提案している。**応答のサイズを制限すること**：ページネーション、フィルタリング、切り詰めを適切なデフォルト値で用いる——同記事は、Claude Code がデフォルトでツールの応答を 25,000 トークンに制限していると述べている——また、切り詰めのメッセージやエラーテキストを、不透明なコードとしてではなく、よりトークン効率の高い戦略へとエージェントを導く場として扱う。

この説明は、どの部分が最も重要かについて、上記の独立した実務者による概観と一致している。その概観が、スキーマは本質的に定まっており品質を決めるのは説明だと結論づけているのに対し、この記事は、ツールの説明と仕様をプロンプトエンジニアリングすることを、利用できる最も効果的な方法の一つとして挙げている。そして、新入社員に説明するように——暗黙のコンテキストを明示的にしながら——それらを書くことを勧め、ツールの説明を精密に改良した結果、Claude Sonnet 3.5 が [[Dataset/swe-bench-verified]] で最先端の性能に達したと報告している。そこに至る方法は、判断ではなく評価のループである。現実的な作業から評価タスクを作り、それを単純なエージェント型ループとして実行し、その結果のトランスクリプトを読む——同記事は、この規律を Anthropic 自身の内部ツールに適用したところ、ホールドアウトしたテストセットで、同社の研究者または Claude のいずれかが書いた専門家による実装を上回る改善が見られたと報告している。

Anthropic 自身のツール定義に関する API ドキュメントは、同じ助言のうち宣言の側を、同社の Claude API について示している。ユーザー定義のツールは、リクエストの `tools` パラメータの中で、`name`（英字、数字、アンダースコア、ハイフンからなる最大 128 文字）、詳細なプレーンテキストの `description`、JSON Schema オブジェクトとして与える `input_schema`、そして任意で `input_examples` を指定して宣言する。`input_examples` はスキーマに対して検証が通らなければならない入力例であり、ドキュメントはネストしたオブジェクトや形式に敏感なパラメータを持つツールに推奨しており、単純な例ではおよそ 20〜50 プロンプトトークン、複雑にネストした例では 100〜200 プロンプトトークンが追加されるとしている。ツール定義、ツールの設定、そしてユーザーが指定したシステムプロンプトから、API はモデルにツールを使うよう指示する特別なシステムプロンプトを構築する。そのベストプラクティスは、上記の立場をベンダーのリファレンスドキュメントとして言い直したものである。極めて詳細な説明を、ツールの性能にとって群を抜いて最も重要な要因と呼び、ツールごとに少なくとも三〜四文を求め、ツールが何をするのか、いつ使うべきでいつ使うべきでないか、各パラメータが何を意味するか、ツールが何を返さないかをカバーするよう求めている。また、アクションごとに一つのツールを設けるのではなく、関連する操作を `action` パラメータを持つ一つのツールに統合すること、ツール名にそれが属するサービスのプレフィックスを付けること、そして意味があり安定した識別子と、モデルが次のステップで必要とするフィールドだけを返すことを推奨している。

同じページは、上記の説明がカバーしていない制御についても記述している。`tool_choice` であり、これは四つの値をとる——モデルがツールを呼び出すかどうかを判断する `auto`（ツールが提供されている場合のデフォルト）、提供されたツールのいずれかを呼び出さなければならない `any`、指定された一つのツールを呼び出さなければならない `tool`、そしてツールを呼び出してはならない `none`（ツールが提供されていない場合のデフォルト）である。`any` または `tool` の場合、API はツール呼び出しを強制するためにアシスタントのターンを事前に埋めるので、モデルはその前に自然言語の説明を出力しない。強制的なツール利用はどこでも使えるわけではない。ドキュメントによれば、手動の拡張思考（extended thinking）では `any` と `tool` が拒否され、Claude Opus 5.5、Claude Fable 5.1、Claude Mythos 5.1 では思考の設定にかかわらずこれらに対してエラーが返される。その代わりに、厳格なツール利用と組み合わせた `auto`、あるいは固定の JSON 形式の応答が必要な場合には構造化出力を使うよう案内している。
