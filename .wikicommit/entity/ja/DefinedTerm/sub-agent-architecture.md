サブエージェントアーキテクチャ（Sub-agent architecture）とは、専門化されたサブエージェントがクリーンなコンテキストウィンドウで焦点の絞られたタスクを処理し、メインエージェントが高レベルの計画に基づいて作業を調整する構成である — 1 つのエージェントがプロジェクト全体にわたって状態を維持しようとするのではない。Anthropic はこれを、長期タスクにおけるコンテキストウィンドウの制約を回避するための 3 つの手法の 1 つとして、[[DefinedTerm/compaction]] および [[DefinedTerm/structured-note-taking]] と並べて提示している。

## 用法

サブエージェントは深い技術的作業を行ったり、ツールを使って関連情報を探したりする。それぞれが広範に探索することもある — Anthropic はその量を数万トークン以上としている — が、返すのは作業を凝縮・蒸留した要約だけであり、その量は多くの場合 1,000〜2,000 トークンとされる。その結果、関心の明確な分離が得られる。詳細な検索コンテキストはサブエージェントの内部に隔離されたままとなり、リードエージェントは結果の統合と分析に集中する。

Anthropic の Claude Code のベストプラクティスのドキュメントは、同じ仕組みに 2 つの異なる役割を記述しており、両者は新しいコンテキストの異なる性質に依拠しているため、区別しておくと有用である。1 つ目は**調査**である。コードベースの調査には多くのファイルを読む必要があり、そのすべてがメインの会話のコンテキストを消費するため、調査をサブエージェントに委任して別に探索させ、要約を報告させることで、メインのウィンドウを実装のためにクリーンに保てる。これは上述のコンテキスト節約の議論を、調査ではなくコーディングの場面に置き換えて述べ直したものである。

2 つ目は**敵対的レビュー**であり、ここでの価値は節約ではなく独立性にある。新しいサブエージェントのコンテキストで動作するレビュアーは、変更を生み出した推論ではなく、差分と与えられた基準だけを見るため、結果をそれ自体として評価する — ドキュメントの捉え方では、エージェントが無人で長く作業するほど、作業が完了とみなされる前の独立したチェックが重要になる。レビュアーはサブエージェントとして動作するため、その指摘は実装を行っているセッションに直接返され、そのセッションは人間がウィンドウ間で指摘を運ぶことなく修正と再レビューを行える。

同じドキュメントは、2 つ目の用途の失敗モードを率直に述べており、これはパターンとあわせて記録しておく価値のある注意点である。ギャップを見つけるよう促されたレビュアーは、作業に問題がない場合でも通常いくつかのギャップを報告する。それが求められたことだからである。すべての指摘を追いかけると過剰設計 — 余分な抽象化レイヤー、防御的なコード、起こりえないケースのテスト — につながるとされており、推奨される緩和策は、正しさや明示された要件に影響するギャップだけを指摘するようレビュアーに指示し、残りは任意のものとして扱うことである。

3 つ目の説明である [[BlogPosting/how-we-built-our-multi-agent-research-system]] は、同じ構成を実際に出荷された形で説明しており、それを**オーケストレーター・ワーカーパターン**と名づけている。リードエージェントがユーザーのクエリを分析し、戦略を立て、さまざまな側面を同時に探索するサブエージェントを生成する。サブエージェントはインテリジェントなフィルターとして振る舞い、検索ツールを反復的に使って発見を返し、リードエージェントはそれを統合したうえで、さらなる調査が必要かどうかを判断する。その本番システムの 2 つの詳細は、パターンの形ではなく、それを長時間運用することに固有のものである。200,000 トークンを超えるコンテキストウィンドウは切り詰められるため、リードエージェントは計画をメモリに保存する。また、別の CitationAgent が最後に文書とドラフトのレポートを処理し、引用を置くべき箇所を特定する。その記事はこの構成全体を、検索拡張生成（Retrieval Augmented Generation）の静的な検索 — クエリに最も類似したチャンクを取得すること — と対比し、発見が得られるにつれて適応する多段階の検索を支持している。

その説明はまた、このパターンがなぜ機能するかについて、賢さではなく容量に関わる説明を与えている。BrowseComp の評価で、チームは 3 つの要因が性能の分散の 95% を説明すると報告しており、トークン使用量だけで 80% を説明し、ツール呼び出しの回数とモデルの選択が残りの 2 つであるという — チームはこれを、並列的な推論容量を加えるために作業を別々のコンテキストウィンドウに分散させるアーキテクチャの妥当性を裏づけるものと読んでいる。

4 つ目の説明はベンダー側ではなく導入側からのものであり、このパターンを調査ではなく通常のプロダクト開発に適用している。[[BlogPosting/two-engineers-ai-driven-product-development]] は、37 個の Skill と 24 個の SubAgent を運用する 2 人のエンジニアのチームを説明している。そこでは Skill が専門知識や求められる振る舞い — どの順序で物事を行うか、品質基準は何か、失敗時に何をするか — を定義し、SubAgent は 1 つの領域を担う専門エージェントであり、それ自体が Skill を使うこともある。メインエージェントは Skill を使って SubAgent をオーケストレーションし、その構成はクエリごとではなくフェーズごとである。ビジネス要件には 3 つの SubAgent（analyzer、generator、validator）、技術設計とタスク分割に 7 つ、実装には言語によって選ばれるさらなる一群、そして並列に実行される 2 つのレビュアーである。

1 つのエージェントに仕事全体を任せない理由についての答えは、同じコンテキストの議論を実践の側から述べたものである。1 つのエージェントがすべてを行うとコンテキストが膨れ上がり性能が低下するのに対し、専門家に分割すると出力品質が安定する — さらに、ベンダーの説明のいずれも*アーキテクチャの根拠として*は挙げていない 2 つ目の運用上の理由を加えている。失敗したフェーズを、実行全体ではなくそのフェーズ単独でやり直せることである。（Anthropic も別の箇所で実行途中からの回復を扱ってはいるが、それは作業を分割する理由としてではなく、自らのシステムが備えるよう構築された性質としてである。）その記事はまた、サブエージェントを独立に保つための具体的な仕組みを示している — これは自らのものとしてではなく、以前の記事に由来するとしている定式化である。各タスクファイルは自己完結的に書かれ、独自のスキーマ、API 仕様、完全な Given-When-Then のテスト項目をもつため、実装時に設計ドキュメントを参照する必要がない。その理由として述べられているのは、別々のセッションがこれらのタスクを並列に実装するため、タスク間のコンテキスト依存はゼロでなければならないということである — エージェント間のインターフェースは会話ではなくファイルなのである。

5 つ目の説明は他よりも範囲が狭く、そもそもサブエージェントがどのように選ばれるのかを扱っている。[[BlogPosting/growing-ai-code-review-with-single-responsibility]] は、各サブエージェントを Markdown ファイル — フロントマターに名前、`description`、モデル設定、本文にシステムプロンプト — として定義するチームを説明しており、オーケストレーションを行うエージェントがそれらの `description` フィールドを読んでどれを実行するかを選ぶと報告している。その説明によれば、トリガー条件は description とは別の場所で設定されるのではなく、description の中に — このサブエージェントを選ぶべきファイルパターンの明示的なリストとして — 書き込まれる。したがって description を具体的に書くこと*こそが*ディスパッチの仕組みであり、抽象的な description は、呼び出し漏れと誤った呼び出しの双方の原因として挙げられている。チームは、各 description をサブエージェント自身のシステムプロンプトからモデルに書かせていると報告しているが、それが意図どおりに呼び出されるかどうかは別の問題として、テスト用のプルリクエストを作成することで経験的に確かめている。明確なファイルパターンのトリガーはオーケストレーターにとって判断しやすいが、それ以外のケースはそうではないからである。

## 適用される場面

- 並列的な探索が大きな効果をもたらす、複雑な調査や分析に適用される。Anthropic はこれを、広範なやり取りを必要とするタスクに推奨するコンパクション、および明確なマイルストーンをもつ反復的な開発に推奨するノートテイキングと対比している。
- 高レベルの計画を保持するメインエージェントと、新しいコンテキストウィンドウで焦点の絞られたタスクを与えられるサブエージェント、そして各サブエージェントが作業コンテキスト全体ではなく蒸留された要約を返すという慣習を前提とする。
- Anthropic は、このパターンが複雑な調査タスクにおいてシングルエージェントのシステムを大幅に上回る改善を示したと報告している。同社の Research に関するエンジニアリング記事は、その主張に数値と構成を与えている。Claude Opus 4 をリードエージェントとし Claude Sonnet 4 をサブエージェントとするシステムは、チームの社内調査評価において、シングルエージェントの Claude Opus 4 を 90.2% 上回った。とりわけ、複数の独立した方向を同時に追う幅優先のクエリで優れていたとされる。挙げられている具体例は、S&P 500 の情報技術セクターに属する企業の取締役をすべて特定するというものであり、シングルエージェントのシステムは遅い逐次的な検索によってこれに答えられなかった。その数値の根拠となった評価の内容は説明されていないため、その難易度や網羅範囲をここから確かめることはできない。
- 加える容量に比例してトークンを消費する。同じ記事は、エージェントは通常チャットでのやり取りの約 4 倍、マルチエージェントシステムは約 15 倍のトークンを使うと報告しており、この構成にはその性能に見合う価値の高いタスクが必要となる。
- すべての領域に適するわけではない。その記事は、現時点で適さないものとして、すべてのエージェントが同じコンテキストを共有する必要がある領域や、エージェント間に多くの依存関係を伴う領域、そして特にほとんどのコーディングタスクを挙げている — その理由は、コーディングタスクは調査に比べて真に並列化可能なサブタスクが少ないこと、そしてエージェントがまだリアルタイムで互いに調整し委任し合うのが得意でないことである。
- 上記の導入側の説明は、この最後の点に対する直接的な対抗材料であり、両者は調停しようとするよりも並べて読む価値がある。その説明は、要件定義からプルリクエストのレビューまでのコーディングパイプライン全体でこのパターンを運用し — リリースは今後の課題のリストに残っている — 3〜4 個のタスクを並列に維持していると報告している。それは、各タスクファイルを自己完結的にし、各実行をそれぞれの `git worktree` とセッションに隔離することで、Anthropic が挙げる依存関係を取り除いたからである — したがって並列のタスクの流れの*間*の調整は、実行時に交渉されるのではなく、タスクが書かれる時点で前もって決着している。単一のタスクの実行の中では、調整は依然としてリアルタイムかつ集中的である。オーケストレーターの Skill が、そのタスクに必要な専門の SubAgent を選んで起動し、結果を判断し、修正を再委任する。したがってその構成が移し替えているのはタスク間の依存関係であり、エージェント間の調整そのものではない。どちらの側も測定されていない。導入側のチームは並列コーディングの主張の背後に評価をもたずに自らの構成を報告しており、ベンダーの領域適合性に関する制約も、同じ記事の他の箇所の数値とは異なり、評価の裏づけなしに述べられた一般的な記述である。したがって導入側の説明が示しているのは、その制約がタスクの切り分け方に依存するということであって、その制約が誤っているということではない。
- 前提とするのではなく、プロンプトによって取り除かなければならない調整コストを伴う。そのシステムの初期バージョンは、単純なクエリに対して 50 個のサブエージェントを生成し、タスクの記述が曖昧な場合には互いの作業を重複させたと報告されており、チームはアーキテクチャの変更ではなく、明示的な労力スケーリングのルールと詳細な委任の指示によってこれに対処した。
- その実装の制約として述べられているのは同期実行である。リードエージェントはサブエージェントの各セットが終わるのを待つ。これは調整を単純にするが、実行途中でサブエージェントを方向づけることができず、サブエージェント同士が調整することもできず、1 つの遅いサブエージェントがシステム全体をブロックすることを意味する。
