コンパクションとは、コンテキストウィンドウの上限に近づいた会話を取り上げ、その内容を要約し、その要約とともに新しいコンテキストウィンドウを開始しなおす実践である。[[TechArticle/effective-context-engineering-for-ai-agents]] はこの定義を与え、長期的な一貫性を高めるために [[DefinedTerm/context-engineering]] で最初に手を伸ばすレバーとなるのが通例だと説明している。その核心は、コンテキストウィンドウの内容を高い忠実度で蒸留し、エージェントが性能の劣化を最小限に抑えて継続できるようにすることである。

## 用法

Anthropic は Claude Code における実装を、メッセージ履歴をモデルに渡して最も重要な詳細を要約・圧縮させるもの——アーキテクチャ上の決定、未解決のバグ、実装の詳細を保ちつつ、冗長なツール出力やメッセージを捨てる——と説明しており、エージェントはその圧縮されたコンテキストに加えて、直近にアクセスした5つのファイルから継続する。掲げられる目標は、ユーザーがコンテキストウィンドウの上限を意識せずに継続性を得られることである。

Claude Code のドキュメントは、これをコンテキスト上限に近づいたときの自動コンパクションとしてユーザーに露出させ、加えて手動の制御も提供している。何を保つかを誘導する `/compact <instructions>`（例として `/compact Focus on the API changes`）、会話の一部だけを凝縮する「Summarize from here」「Summarize up to here」を備えた rewind メニュー、そして振る舞いをカスタマイズする `CLAUDE.md` 内の指示（例として「コンパクションの際は、変更されたファイルの完全な一覧とすべてのテストコマンドを常に保持すること」）である。また、より大雑把な代替として、無関係なタスクのあいだには `/clear` を推奨している——コンテキストを要約するのではなく完全にリセットするものである。

[[BlogPosting/context-engineering]] はコンパクションを「圧縮（compress）」の分類に置き、モデルを用いて蒸留する要約と、古いメッセージを削除するといったハードコードされたヒューリスティクスでフィルタ・剪定する**トリミング**とを区別している。要約は会話の末尾以外の地点でも適用できると指摘し——トークンを大量に消費するツール呼び出しの後や、知識の受け渡しの際にトークンを減らすためのエージェント間の境界で——また Cognition がこのステップにファインチューニングされたモデルを用いていることを伝え、これをここにどれだけの労力を注ぎうるかの一つの目安として提示している。

名指しされるリスクは喪失である。Anthropic は、過度に攻撃的なコンパクションは微妙だが重要な、その重要性が後になって初めて明らかになるコンテキストを捨てうると警告し、複雑なエージェントのトレースでコンパクションのプロンプトを調整する際は、まず再現率を最大化し、次に適合率を高めることを推奨している。安全で手近なコンパクションの例として挙げられるのはツール結果のクリアである。メッセージ履歴の奥深くで一度呼ばれたツールについて、エージェントが生の結果を再び見る必要はめったにない。

タスクが一つではなく多数のコンテキストウィンドウをまたいで続く場合、同じベンダーはコンパクションが必要ではあるが十分ではないと報告している。[[TechArticle/effective-harnesses-for-long-running-agents]] は、Claude Agent SDK 上で複数のコンテキストウィンドウにわたってループさせたフロンティアのコーディングモデルでさえ、高水準のプロンプトから本番品質のウェブアプリを構築するには及ばないと述べ、その不足の一部をコンパクションそのものに帰している。実装の途中でコンテキストが尽きたエージェントは、半分だけ実装され文書化されていない機能を次のセッションに残すのであり、これは「コンパクションがあってもなお起きる。コンパクションは必ずしも完全に明確な指示を次のエージェントへ渡すわけではないからだ」。同記事の処方箋は、要約だけに頼るのではなく、セッションをまたぐ状態を耐久性のある成果物——進捗ファイル、git の履歴、構造化された機能一覧——に置くことである。

### コンパクションは何のために最適化されており、その代償は何か

上で名指しされたリスクは*タスク*のコンテキストの喪失である。[[ScholarlyArticle/governance-decay]] は、性格の異なる第二の喪失の類型を指摘している。コンパクションはエージェントが従っている常設の規則をも削除するのであり、しかもそれはコンパクションが正しく働いているからこそ起きる。その議論は、タスクの継続性のために最適化する要約器にはポリシーを残す理由がない——「ポリシーは『古く』、現在のサブゴールではなく、縮みゆくトークン予算をめぐって進行中のタスク状態と競合する」——というものであり、それゆえコンパクションは「常設のポリシーを顕著性の低い内容として扱う」。

7つのモデル系列と4つのコンパクション戦略にわたり、[[Dataset/constraintrot]] ベンチマークの1,323エピソードをプールして測定された帰結は、コンパクションがツール呼び出しの違反率を0% から30% へ、最悪の構成では59% へと引き上げるというものである。要約で条件づけると、機構がコンテキスト長ではなく削除であることが切り分けられる。制約がコンパクションを生き延びた場合の違反率は0%、落とされた場合は38% である。この浸食は運用上重要な仕方で不均等である——硬い安全規範に比べ、柔らかい組織のポリシーでは8.3倍大きい。つまり消えるのは、まさに運用者が書いた配備固有の規則なのである。

規則がどこに置かれているかが、コンパクションの手が届くかどうかを決める。同論文のチャネル比較では、保持されるシステムメッセージ内のポリシーは劣化を示さなかったのに対し、常設のユーザー指示、メモリ項目、ツール出力としてはそれぞれ +50、+45、+33 パーセントポイントであった。同論文が提案する対策である Constraint Pinning は、ガバナンス上の制約を損失を伴うコンパクションから隔離し、ターンをまたいで完全性を検査するもので、およそ47トークンのピン留めで違反率を0% に戻す。素朴なピン留めがなお失敗する場合についても報告している。より広い結論は、コンパクションがどのような種類の意思決定であるかを捉え直す。それはトークン予算についての経済的な判断であるだけでなく、「一級のエージェントガバナンスの面」である、というのである。

### 何を捨てるかを決める代わりにコンテキストを保存する

[[TechArticle/scaling-managed-agents]] は、コンテキストウィンドウを超えることへの標準的な答え——コンパクション、メモリファイル、コンテキストのトリミング——が一つの性質を共有していると枠づける。いずれも「何を残すかについての不可逆な決定を伴う」のである。掲げられる異議は技術的というより認識論的である。将来のターンがどのトークンを必要とするかを知るのは難しく、いったんコンパクションのステップがメッセージを変換しハーネスがそれらをウィンドウから取り除いてしまえば、どこかに保存されていた場合にのみ回復可能となる。

そこで示される代替案は、コンテキストをコンテキストウィンドウの*外側*に生きるオブジェクトとして、追記専用のセッションログに耐久的に保存することである。`getEvents()` インターフェースにより、エージェントはその保存領域を位置によるスライスで問い合わせられる——前回読み終えたところから再開する、ある瞬間の少し前まで巻き戻して経緯を見る、特定の行動の前のコンテキストを読み直す、といった具合である。コンパクションその他の変換は依然として行われるが、それはウィンドウへ入る途上のハーネスの中でであって、保存層で破壊的に行われるのではない。

これらの関心事を分ける理由として述べられているのは、将来のモデルが必要とする具体的なコンテキストエンジニアリングは予測できない、ということである。それゆえ耐久層は、記録が生き延びて問い合わせ可能であることだけを保証し、それをどう扱うかは走っているハーネスに委ねる。

## 関連用語

コンパクションは長期的な作業のための3つの標準的な技術の一つであり、他に [[DefinedTerm/agentic-memory]] と [[DefinedTerm/multi-agent-orchestration]] がある。Anthropic はこれを、広範なやり取りを要するタスクに特に対応づけている。[[DefinedTerm/adaptive-context-compaction]] は、硬い上限での単一のイベントとしてではなく、コンテキストの圧力が高まるにつれて段階的に削減を適用する、より具体的な変種を指す。それが管理するために存在する根底の問題は [[DefinedTerm/context-rot]] である。
