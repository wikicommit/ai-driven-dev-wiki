コンパクションとは、コンテキストウィンドウの上限に近づいた会話を取り上げ、その内容を要約し、その要約をもって
新しいコンテキストウィンドウを立ち上げ直す実践である。Anthropic はこれを、長期的な一貫性を高めるために
[[DefinedTerm/context-engineering]] で最初に引かれるレバーであるのが通例だと述べている。その核にあるのは
コンテキストウィンドウの内容を高い忠実度で蒸留することであり、それによってエージェントは性能の劣化を最小限に
とどめたまま作業を継続できる。

## 用法

[[SoftwareApplication/claude-code]] において、Anthropic はメッセージ履歴をモデルに渡して最も重要な詳細を要約・圧縮
させることでコンパクションを実装している。モデルはアーキテクチャ上の決定、未解決のバグ、実装の詳細を保ちつつ、
冗長なツール出力やメッセージを捨てる。エージェントはその圧縮されたコンテキストに、直近でアクセスされた 5 つの
ファイルを加えて作業を続けるため、ユーザーはコンテキストウィンドウの制限を気に掛けることなく連続性を得られる。

Anthropic は、ツール呼び出しとその結果を消去することを、取り除きやすい余剰内容として挙げている——メッセージ履歴の
深部でいったんツールが呼ばれてしまえば、その生の結果を再び見る必要は一般にない——そして、ツール結果の消去を
コンパクションの形態のうち最も安全で最も侵襲の少ないものの一つと呼んでいる。これは Claude Developer Platform 上で
機能として提供が始まったと述べられている。

要約のパスは常に単一の工程であるとは限らない。[[ScholarlyArticle/dive-into-claude-code]] は Claude Code の v2.1.88 時点の
ソースを読み解き、そこでのコンパクションを、モデル呼び出しのたびに順に走る 5 つのシェイパーからなるパイプラインとして
記述している。後のものほど積極的で、ツール結果ごとの予算が過大な出力をコンテンツ参照に置き換え、古い履歴区間を軽く
刈り込み、キャッシュを意識した細粒度の圧縮を行い、保存された履歴はそのままに折り畳まれたビューを提示する読み取り時の
射影を施し、最後に、他の 4 つが走ってもなおコンテキストが圧力しきい値を超える場合にのみ、モデルによる完全な要約が
発火する。著者らはこれを遅延劣化の原則——最も破壊的でない圧縮をまず適用し、より安価な戦略が不十分と判明した場合にのみ
段階を上げる——と述べ、コンパクションの出力は先行するトランスクリプト行を上書きするのではなく追記されるため、
以前の内容は再構成のために利用可能なまま残ると注記している。

同じ研究は、この段階的な設計が何を代償としているかについても明示的である。5 つの相互作用する層があり、いくつかは
フィーチャーフラグで制御されるため、ユーザーにとって予測の難しい挙動を生む。しかも圧縮はおおむね不可視である。
予算による置き換え、刈り込み、折り畳みが何を取り除いたのかをユーザーが容易に検分する術はなく、キャッシュを意識した
挙動は、圧縮の判断をプロンプトキャッシュに依存させるが、そのことはユーザーに提示されない。著者らはまた、要約に基づく
コンパクションのさらに 2 つの代償を報告する外部の研究も伝えている——要約の工程はブロッキングな推論の停滞であること、
そして非決定的であり、同一入力に対する実行ごとに保持される内容が揺らぐことである。彼らはこのアプローチ全体を、
より単純な代替——一回限りの切り詰めや単一の要約工程——と対比している。後者は情報を犠牲にするが、その分だけ
推論しやすい。

## 適用条件

- トークン数がコンテキストウィンドウを超える長期タスク、とりわけ広範なやり取りを要する作業に当てはまる。Anthropic は、
  コンパクションはそうしたタスクにおいて会話の流れを保つと述べ、明確なマイルストーンを伴う反復的な開発に優れるとする
  ノートテイキングと対比している。
- メッセージ履歴がモデルによって要約可能であること、そしてコンパクションのプロンプトが当該のトレースに合わせて
  調整済みであることを前提とする。Anthropic は、そのプロンプトを複雑なエージェントのトレース上で入念に調整することを
  推奨している。まず再現率を最大化してトレース中の関連する情報をすべて捉えられるようにし、次に余剰な内容を削ることで
  適合率を高めるよう反復せよ、という。
- 過度に積極的に適用すると破綻する。Anthropic は、コンパクションの妙味は何を残し何を捨てるかの選択にあり、過度に
  積極的なコンパクションは、後になって初めて重要性が明らかになるような微妙だが決定的なコンテキストを失わせうると
  述べている。
- Anthropic 自身が Claude Code で実装した実践として、またプラットフォームの提供機能として確立されたものであり、
  測定された結果としてではなくエンジニアリング上の経験から述べられている。上記の 5 層の記述は、ある単一バージョンの
  ソースに対する一つの研究の読解に依拠しており、その著者らはフィーチャーフラグによってビルドごとに差異が生じることに
  注意を促している。
- 長時間稼働するエージェントについてのある記事は、非常に長いジョブに対して要約としてのコンパクションだけでは十分では
  ないと Anthropic が明言していると述べている。通常のコンパクションを超えて、Anthropic のハーネスは完全なコンテキスト
  リセットも行う。そこではハーネスがセッションを解体し、構造化されたハンドオフファイルから組み立て直す——人間が新しい
  エンジニアをオンボードするやり方に本質的に等しいと説明されている。
- Anthropic は [[BlogPosting/effective-harnesses-for-long-running-agents]] において同じ限界を自ら述べ、その背後にある
  機構を名指ししている。すなわち、コンパクションは *次のエージェントに常に完全に明快な指示を引き渡せるわけではない*。
  報告されている証拠は、フロンティアモデルが [[SoftwareApplication/claude-agent-sdk]] 上で複数のコンテキストウィンドウに
  またがるループを、コンパクションを利用可能な状態で走らせてもなお、高水準のプロンプトから本番品質の Web アプリを
  構築するには及ばなかったこと、そして結果として残された中途半端で文書化されていない機能が、次のセッションに何が
  起きたのかを推測させる羽目に陥らせたことである。そこで述べられている是正策は、より良いコンパクションではなく、
  コンテキストウィンドウの外側にある永続的な成果物である。すなわち進捗ログ、git の履歴、そして構造化された機能一覧で
  ある（[[DefinedTerm/initializer-agent]] を参照）。

- その後の Anthropic のエンジニアリング記事
  [[BlogPosting/harness-design-for-long-running-application-development]] は、コンパクションと完全な
  [[DefinedTerm/context-reset]] の境界を、それぞれが何をもたらすかという観点から引いている。コンパクションは会話の
  以前の部分をその場で要約するので、同じエージェントが短縮された履歴の上で作業を続けられる。これは連続性を保つが、
  エージェントに白紙の状態を与えるものではない。リセットはウィンドウを完全に消去して新しいエージェントを始動させるが、
  その代償として、作業を滞りなく引き継ぐに足る状態をハンドオフの成果物が担わねばならない。
- この区別は、とりわけ一つの失敗モードにとって決定的である。同じ記事は、コンパクションが同じエージェントを走らせ続ける
  がゆえに、[[DefinedTerm/context-anxiety]]——モデルが自らのコンテキスト上限と見なすものに近づくにつれて作業を早々に
  切り上げてしまうこと——がそれを通り抜けて持続しうると報告している。Claude Sonnet 4.5 はこの振る舞いを、コンパクション
  だけでは長いタスクでの強い性能には不十分なほど強く示したため、そのハーネスの設計においてコンテキストリセットが
  不可欠となったこと、そして Claude Opus 4.5 ではこの振る舞いがおおむね自律的に解消されたため、後のハーネスでは
  リセットを完全に取り払い、[[SoftwareApplication/claude-agent-sdk]] の自動コンパクションがコンテキストの増大を処理する
  単一の連続セッションとして走らせられるようになったことが述べられている。したがってコンパクションで足りるか否かは、
  技法だけでなくモデルにも依存するものとして報告されている。

- コンパクションはいくつかある設計上の選択肢の一つであり、[[ScholarlyArticle/inside-the-scaffold]] は、これをオープン
  ソースのコーディングエージェントが最も広く分岐する次元として報告している——分析対象の 13 のスキャフォールドにわたって
  7 つの異なる戦略があり、まったく管理しないものからモデル自身が要求するコンパクションまで幅がある。同論文はこれらを
  2 つの思想に整理する。*予防*型のエージェントは、作業単位ごとにメッセージをスコープする、検索ラウンドに上限を設けて
  結果を切り詰める、あるいはトラジェクトリの深さを制限するといった構造的な手段でコンテキストの増大を抑え込む。
  *治療*型のエージェントはコンテキストを増大させるに任せ、トークンのしきい値に達した時点で圧縮する。予防は要約の
  コストと情報の損失を避けられるが、コンテキストがどう増大するかをスキャフォールドが先回りして見通す必要がある。
- 両極の間に同論文が見分ける戦略は、規則に基づく切り詰め（最初と最後の N 個の観測を保持し、間を省略する）、構造的な
  隔離、予算内でのトークンに基づく選択的な取り込み、スキャフォールドが発火させるモデルによる要約、要約の後に重要な
  情報が失われていないかを確かめる検証ターンを挟むもの、そしてモデル主導のコンパクション——スキャフォールドではなく
  モデル自身がいつコンパクションするかを決められるようにするツールを与えるもの——である。同論文は、あるエージェントが
  すべてのモデル呼び出しを会話履歴を持たない単一ターンにすることでこの問題自体を回避しており、その結果、作業を
  コンテキストに収めることが実行時の問題ではなくプロンプト構築の問題になっていると観察している。
- 同じ論文はコンパクションを、収束している次元ではなく *分岐している* 次元のほうに位置づけ、その分岐をノイズではなく
  真正の不確実性として読む。情報の保存とトークンコストの釣り合いの最適点は、タスクの長さ、モデルの能力、コスト許容度に
  依存し、単一の戦略がそれを解決することはないと述べている。
