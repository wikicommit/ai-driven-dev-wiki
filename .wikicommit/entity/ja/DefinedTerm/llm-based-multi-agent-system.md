LLM ベースのマルチエージェントシステム（LLM-Based Multi-Agent (LMA) system）とは、相互作用するエージェントが大規模言語モデルによって駆動されるマルチエージェントシステムである。マルチエージェントシステムとは一般に、相互作用する複数の知的エージェントから構成され、それらが協働して、単一のエージェントの能力を超える複雑な問題を解決したり目標を達成したりする計算フレームワークであり、エージェントは通信し、協調し、知識を共有し、しばしばタスクの異なる部分にそれぞれの専門性を発揮する。[[ScholarlyArticle/llm-based-multi-agent-systems-for-software-engineering]] は、LMA システムを 2 つの主要な構成要素、すなわちオーケストレーションプラットフォームと、それが協調させる LLM ベースのエージェントから成るものと定義している。この定式化では、各エージェントはグラフのノードとして表現でき、そのエッジはエージェント間の相互作用である。

## 使われ方

オーケストレーションプラットフォームは、相互作用と情報の流れを管理する中核的な基盤である。同論文はこれを 3 つの軸で特徴づけている。協調モデルはエージェントがどのように相互作用するか — 協調的、競争的、階層的、あるいはそれらの混合 — を定める。通信メカニズムは情報がどのように流れるかを定め、チャネルは集中型（中央のエージェントが通信を仲介する）、分散型（エージェントが直接通信する）、あるいは階層型（情報が権限の層を通って流れる）に編成される。ソフトウェアエンジニアリングの文脈では、やり取りされるデータにはコード片、コミットメッセージ、フォーラムの投稿、バグレポート、脆弱性レポートなどが含まれうる。計画と学習のスタイルは、タスクがどのように割り当てられ協調されるかを決め、その戦略には Centralized Planning, Decentralized Execution（集中型計画・分散型実行）や Decentralized Planning, Decentralized Execution（分散型計画・分散型実行）が含まれる。

エージェント自体は、事前に定義されたものであることも、LLM によって動的に生成されたものであることもあり、また同質的（同一の機能）であることも、異質的（多様な機能と専門性）であることもある。

同論文がこの形態の動機として挙げるのは、現実世界の問題は複数の領域にまたがるため、単一の LLM ベースのエージェントでは限界に突き当たる、という点である。連携して働く複数の専門化されたエージェントは、自律的な問題解決を可能にし、意思決定における相互検証を通じて頑健性を高め、エージェントを追加しタスクを再配分することで複雑なシステムへとスケールできると論じられている。同論文はまた、この構成を Mixture of Experts のパラダイムと対比している。後者では、専門化された構成要素がゲーティング機構によって動的に活性化されるが、構成要素同士は互いに通信しない。

[[ScholarlyArticle/llm-based-multi-agent-systems-for-code-generation]] は同じ主題に、アーキテクチャの側ではなく証拠の側から取り組み、特にコード生成に関する学術文献およびグレーリテラチャの研究 114 件をレビューしている。同レビューは、そうしたシステムを採用する理由として述べられているものが 9 つのカテゴリーに分かれることを見出しており、その筆頭は性能の向上（114 件中 12 件、10.5%）と、より小さな協調されたサブタスクへの分解を通じた複雑なタスクの処理（9 件、7.9%）である。著者らはこの分布を、マルチエージェントアーキテクチャが主として精度、効率、ワークフロー協調のための技術的メカニズムとして位置づけられていることを示すものと読んでおり、適応性や自律的な実行はより少なく、中心的なものではなく依然として萌芽的なものとして現れているとしている。

同じレビューは、何がうまくいかないかも記録している。正しさと信頼性が最大の課題カテゴリーであり、26 件（22.81%）の研究で報告され、その筆頭はハルシネーション、低い精度、オーケストレーションの失敗である。オーケストレーションの失敗に対して報告されている解決策は、制約のない自然言語のやり取りを明確に定義された機械可読なメッセージ形式に置き換える、構造化されたスキーマベースの通信プロトコルと、衝突や終了しない相互作用を防ぐために個々のファイル、サービス、プロセスに対する責任を明示的に割り当てることである。その他の課題カテゴリーは、セキュリティとプライバシーのリスク、計算資源とリソースの制約、コンテキストとメモリの制限、ベンチマークの課題、検証の課題、そしてプロンプト設計の課題である。

これらのシステムを駆動するモデルについて、同レビューはコーパス全体で LLM の使用例を 83 件数えており、そのうち 57 件がクローズドソース、26 件がオープンソースで、OpenAI の GPT シリーズが 43 件を占め、Meta の Llama が 17 件でオープンソースとして最も一般的な選択であった。同レビューは、プロプライエタリなプラットフォームへの依存がデータプライバシー、セキュリティ、依存性についての懸念を生みうる一方で、オープンソースの代替手段はデプロイの制御、コスト効率、データプライバシーの向上をもたらすと述べている。

第 3 の出典は、同じ主題に、アーキテクチャや証拠としてではなく運用のハンドブックとして取り組んでいる。Jimmy Song のオンラインハンドブック『智能体构建指南』のある章は、そうしたシステムを構築することの実践的な中身として扱う 4 つの関心事を示しており、その一貫した警告は過剰設計に対するものである。フレームワークは仕組みを提供するが、協調のオーバーヘッドは専門化による利得を相殺しうるものであり、タスクが逐次的で密結合である場合や、より優れたプロンプトエンジニアリングを施した適切に設計された単一のエージェントで足りる場合には、複雑なフレームワークは不要なコストでしかない。

**役割の分離。** 同章が挙げる役割は、Planner（タスクを分解し戦略を立てる）、Worker（サブタスクを実行する。ドメインの専門家であることもある）、Reviewer（結果を確認し改善する）、Orchestrator（作業を割り振り最終的な決定を下す）であり、責任が重ならないように境界が引かれる。同章は、[[SoftwareApplication/crewai]] がこれをエージェントごとの `role` と `goal` 属性として設定の中に持っていること、また [[SoftwareApplication/langgraph]] の Supervisor パターンが Orchestrator を、リクエストをサブエージェントへルーティングするエージェントとして実現していることを指摘している。

**合意と調停。** エージェント間で意見が分かれる場合について、同章は 3 つの戦略を挙げる。1 つ目は多数決または順位付け投票で、[[SoftwareApplication/autogen]] の討論の構成がその例である。そこでは解答者エージェントが複数ラウンドにわたって議論し、集約者が最終ラウンドを多数決で決着させる。2 つ目は複数のモデルにまたがる確信度重み付き投票で、同章はこれを ReConcile フレームワークに帰している。3 つ目は信頼値によるルーティングで、エージェントの重みを過去の成績から調整し、より信頼できるエージェントの意見がより大きな影響力を持つようにする。

**トレーシング。** 同章の推奨は、フレームワークがすでに永続化している状態 — LangGraph のグラフ状態、CrewAI の Flow States — に加えて、エージェントのインタラクションごとに一意のトレース ID を付与し、ログと呼び出しのコンテキストを結びつけることである。同章は各フレームワーク独自の可観測性機能（CrewAI の Tracing & Observability、LangGraph の LangSmith 連携）に触れ、各エージェントの意思決定の詳細を 1 つのログに出力するためにコールバックを用いることを提案している。

**封じ込め。** マルチエージェントの実行は過剰な呼び出しとコストを生むため、同章は、エージェントごとまたはワークフローごとのトークンと呼び出しの割り当て、しきい値を超えると終了または縮退させる予算監視、リトライ制限とサーキットブレーキング、そして入力フィルタリングを挙げている — 最後のものについては、オープンソースのフレームワークではユーザー自身が実装しなければならないと注記している。

同章はまた、比較した 6 つのフレームワークのいずれも解決していないとする限界として、効率的な **エージェント間のコンテキスト受け渡し** を挙げている。利用可能なアプローチは、すべてを共有する（遅く高コストである）か、要約を共有する（詳細が失われる）かであり、選択的で意味的な受け渡しこそがマルチエージェントシステムの経済性を左右するものだとする。そして、チームはフレームワークがこれを解決しないことを承知のうえでフレームワークを選ぶべきだと論じている。過剰設計についての警告も同じ方向を向いている — 協調のオーバーヘッドは専門化による利得を相殺しうるものであり、現在のモデルの限界を補うために加えられた構造は、より優れたモデルが登場したときに取り除けるように作っておくべきである。これらはそこでは立場として述べられており、その背後に計測されたものは何もない。
