エージェント型ソフトウェアとは、[[ScholarlyArticle/agentic-software-restructuring-paradigm]] が、意思決定ロジックが事前に書かれるのではなく実行時に生成されるソフトウェアを指して定式化した用語である。同論文はこの用語を自ら作り出したとは主張していない。同論文が自らの貢献として示しているのは、決定論的ソフトウェアとエージェント型ソフトウェアの区別を定式化したことである。この対比は形式的に描かれている。従来のソフトウェアシステムはそこで、計算資源、ソースコードに符号化された決定論的な決定ルールの集合、そしてそれらのルールを入力に対して評価する実行環境という三つ組として特徴づけられ、その決定的な性質は、ルールが実行に対して静的であること、すなわちシステムが何らかの入力に出会う前に、そのすべてが人間のエンジニアによって書かれていなければならないことだとされる。これに対して AI エージェントシステムは、推論エンジンとして働く言語モデル、実行可能なツールの集合、メモリサブシステム、そしてユーザーの意図を行動の系列へと分解する計画メカニズムとして特徴づけられる。

この用語に意味を与える帰結は、コードに何が起きるかである。この説明では、モデルは動的にコードを生成し、ツールを呼び出し、中間結果に応じて振る舞いを調整することができ、そのいずれも事前にプログラムされてはいない。したがって、モデルが書くコードはシステムそのものではなく一時的な成果物であり、必要に応じて生み出されては捨てられる。同論文はこの転換を「AI → Software → Result」が「Agent → Result」へと縮約されることとして端的に述べている。それはソフトウェアが消えるからではなく、エージェントがソフトウェアシステムであると同時にその実行エンジンでもあるため、間に静的にコーディングされた別個の成果物を置く必要がなくなるからだ、とされる。

## 用法

この用語はソフトウェアの作り方ではなくソフトウェアの種類を指しており、そこが同じ論文の枠組みにおける隣接する語彙との違いである。そこでは [[DefinedTerm/agentic-engineering]] がそのようなシステムを構築・デプロイ・統治する分野を、[[DefinedTerm/agent-as-a-service]] がそれらを提供する際の商業モデルを指し、エージェント型ソフトウェアは成果物そのものを指すものとして残される。この三分割は同論文独自のものである。

同論文はこの概念を Karpathy の「Software 2.0」と対置している。同論文は Software 2.0 を、手作りのプログラムロジックを学習された重みに置き換えるものと読み、エージェント型システムはさらに一歩先へ進むと論じる。ネットワークがプログラムを置き換えるだけでなく、より広い推論目標に奉仕する道具としてコードを使い、必要に応じてプログラムを書くからである。同論文はこのパターンを、推論トレースとツール使用の行動を交互に行う ReAct フレームワーク、および Chain-of-Thought プロンプティングと結びつけている。

これがなぜ異なる形でスケールするのかについての同論文の議論は、複雑さに関するものである。従来のパラダイムでは、人間のエンジニアがタスクの解空間を頭の中でたどり、その経路を静的なプログラムとして符号化しなければならず、固定された認知能力によって制約される。そのため、解空間がその能力を超えるタスクは、現実的などんなコストでも実現不可能となる。エージェント型パラダイムでは、モデルが解空間をたどり、その能力はモデルの規模と学習計算量に応じてスケールすると同論文は論じる。計画はタスクを独立に扱える部分問題へと分解し、コードはあらゆる事態に備えてではなく、特定の解の経路のためだけに生成される。ここから引き出される主張は、何パーセントの改善というものではなく、どの問題が経済的に扱えるようになるかという質的な変化である。

## 適用される場面

同論文の形式的な定義から読み取れる限りでは、この概念は、システムの振る舞いが事前に指定された命令の系列からではなく、モデル、ツール、メモリ、計画の相互作用から実行時に立ち現れる場合に当てはまる。これは、タスクを分解して行動を選択できる推論エンジンと、それを通じて行動できるツールがあることを前提とする。同論文は定義を述べているのであって、こうした適用条件を述べているわけではない。

同論文が述べる失敗条件は、同論文が最も楽観的でない部分である。同論文は、エージェントの成功率が、独立したタスクでの 80% 超から、継続的なソフトウェア進化のもとでは最大 38% にまで低下するという [[Dataset/evoclaw]] ベンチマークの知見を報告し、そこから四つの課題を読み取っている。コードベースが実効的なコンテキストウィンドウを超えて大きくなるにつれて生じるコンテキストのドリフト。初期の小さな誤りが連鎖的に波及し、エージェントには堅牢な回復手段がないという誤りの伝播。エージェントは長期的なコストをモデル化せずに目の前のタスク完了を最適化するため、技術的負債への意識が欠けていること。そして、エージェントはテストに合格しながら、新しい入力でしか表面化しない意味的な誤りを持ち込みうるという検証の忠実度の問題である。同論文自身の結論は、このパラダイムは拡張（augmentation）のパラダイムとしては今日すでに現実的で変革的だが、完全に自律的なソフトウェア開発は依然として数年がかりの研究課題だというものである。

この用語がどの程度確立しているかについて言えば、それは一本の論文に依拠しており、その論文は独自の測定からではなく、第一原理と他の研究から引用した結果に基づいて論じている。同論文は区別の定式化を自らの貢献として示しているが、用語そのものがどこから来たのかは述べていない。実行時にコードを生成しては捨てるモデルは、プログラムとは異なる種類の成果物であるという根底の観察は、その資料の中で争われてはいない。それを軸に組み立てられた三世代という枠組みは、同論文独自のものである。
