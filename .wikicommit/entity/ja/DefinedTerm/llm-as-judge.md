LLM-as-Judge とは、別のモデル呼び出しを用いて、あるモデルが生み出した作業を評価するパターンである。その定義的な性質は分離にある。ジャッジは出力と基準を見るのであって、その出力を生み出した推論は見ない。したがって作業をしているエージェント自身がそれを採点することはない。エージェンティックコーディングにおいては、通常は品質ゲートとして現れる——作業が受理される前に通過しなければならないステップであり、失敗はリトライへとフィードバックされる。

## 用法

[[SoftwareApplication/context-engineering-kit]] はこのパターンを品質ゲートの機構として名指しで用いており、計画と実装の各ステップを、あらかじめ定義された検証ルーブリックに照らした証拠ベースの採点によって評価するものと説明している。そのコマンド群はいくつかの形態を露出させている。`/judge` は完了した作業を構造化されたルーブリックに照らして評価する。`/do-and-judge` は実装サブエージェントを独立したジャッジおよび自動リトライループと組み合わせ、作業が通過するまで繰り返す。`/judge-with-debate` は複数ジャッジによる反復的な討論を走らせ、合意を形成するか不一致を報告する。`/critique` は専門化されたジャッジを用い、討論と合意形成を伴う多視点のレビューを走らせる。そのレビュープラグインは、役割特化のレビュアー——バグ探し、コード品質、契約、歴史的文脈、セキュリティ、テストカバレッジ——を影響度と確信度でフィルタするという、関連する考えを適用している。

Anthropic の Claude Code のドキュメントは、同じ分離をこの名称なしに説明し、敵対的なレビューステップを加えるものとして枠づけている。タスクを完了とみなす前に、サブエージェントに新しいコンテキストで差分をレビューさせ、抜けを報告させるのである。掲げられる理由はこのパターンの前提と一致する——新しいコンテキストで動くレビュアーは、差分と与えられた基準だけを見るのであって、その変更を生み出した推論は見ないため、結果をそれ自体の条件で評価する——のであり、実装中のセッションが抜けを直接受け取り、人間が発見事項をウィンドウ間で書き写すことなく修正と再レビューができるという実務上の利点も指摘している。

同ドキュメントはこのパターンの最も一般的な失敗モードも記録している。抜けを見つけるよう促されたレビュアーは、作業が健全でも通常は何かしら報告する。それがそう求められたことだからである。そしてすべての指摘を追いかけると過剰設計——余分な抽象層、防御的なコード、起こりえないケースのためのテスト——に至る。推奨される緩和策は、正しさや明示された要件に影響する抜けだけを挙げ、残りは任意として扱うようレビュアーに伝えることである。

### ゲートではなくループとして——evaluator-optimizer

[[TechArticle/building-effective-agents]] はこの構成を **evaluator-optimizer** と名づけている。一方の LLM 呼び出しが応答を生成し、もう一方がループのなかで評価とフィードバックを与えるため、判定は受理/却下だけでなく改訂へと供給される。

適合の良さを示す二つの兆候として挙げられるのは、タスクの分類ではなく実践的なテストである。人間がフィードバックを言語化したときに LLM の応答が明らかに改善されること、そしてモデル自身がそうしたフィードバックを与えられることである。このパターンは、評価基準が明確で、反復的な洗練が測定可能な価値を生む場合に推奨される。

同じ記事は、並列化の*投票*バリエーションのもとで、判定の構成をもう一箇所で用いている。同じタスクを異なるプロンプトで複数回走らせ、評決を集約するのである——脆弱性についてコードを複数のプロンプトでレビューし、それぞれに問題を挙げさせる、あるいは偽陽性と偽陰性の釣り合いを取るために異なる投票閾値でコンテンツを評価する、といった具合である。

### 本番のルーブリックと、なぜ単一のジャッジが複数に勝ったか

[[TechArticle/how-we-built-our-multi-agent-research-system]] は、自由形式の研究成果を五部構成のルーブリックに照らして採点するために LLM ジャッジを用いたと報告している。事実の正確さ（主張は出典と一致するか）、引用の正確さ（引用された出典は主張と一致するか）、網羅性（求められたすべての側面が扱われているか）、出典の質（低品質な二次資料より一次資料が優先されたか）、そしてツールの効率（適切なツールが妥当な回数使われたか）である。

注目すべき否定的な結果はアーキテクチャに関わるものである。同チームは複数のジャッジが各構成要素を個別に評価する方式を試したが、「単一のプロンプトで 0.0〜1.0 のスコアと合否判定を出力する単一の LLM 呼び出しが、最も一貫しており、人間の判断とも整合していた」ことを見出した。この手法は、テストケースに明確な答えがあり、ジャッジが正しさを確認するだけでよい場合に特に有効だった。

同記事は、この技術の規模だけでなくその限界も述べている。自動化されたジャッジが見逃したものを人間のテスターが捕らえた——珍しいクエリに対する幻覚の回答、システムの故障、そして初期のエージェントが学術論文の PDF や個人ブログといった権威はあるが検索順位の低い出典よりも SEO 最適化されたコンテンツファームを一貫して選ぶという、微妙な出典選択のバイアスである。その結論は、「自動評価の世界にあってさえ、手作業のテストは依然として不可欠である」というものである。

その両方の根底にあるのは、なぜここで判定が必要になるのかである。マルチエージェントシステムは同一の出発点から完全に異なる妥当な経路を取りうる。それゆえ評価は、定められた手順が踏まれたかを確認することはできず、結果が正しかったか、過程が妥当だったかを判定しなければならない。

## 関連用語
