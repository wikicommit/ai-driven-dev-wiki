高速統合の負債とは、LLM が生成した出力を適切な検証なしに急いでソフトウェアプロジェクトへ統合することで生じる、不安定な土台を残すリスクである。このカテゴリは [[ScholarlyArticle/faster-code-deeper-debt]] で名づけられ定義されたもので、同論文はこれを、自らが依拠する既存の分類体系が扱っていない 6 つの負債の形態の一つとして同定している。通常のコードの負債と異なるのは、問題がどこに発するかである。個々の成果物の品質にではなく、LLM の出力がどれほど速く採り入れられるかと、開発者がその下流での保守性と設計上の帰結をどれほど速く評価しうるかとの隔たりにある。

## 用法

同レビューは高速統合の負債が 13 件のグレーリテラチャで論じられていると報告しており、これは [[DefinedTerm/governance-debt]] に次いで、実務者の文章で 2 番目に頻繁に論じられる LLM 固有の負債ということになる。とりわけ、開発者が AI の提案を、その含意を理解しないまま素早く実装すること、すなわち vibe coding と結びつけられている。

同レビューにおけるその意義は、単にカテゴリ上のものというより構造的なものだ。著者たちはドミノ効果を記述している。放置されれば、高速な統合はガバナンス上のリスクの連鎖と長期的な保守コストの増大を引き起こす——高速統合の実践は監督を要するコードをより多く生み、それが後にガバナンスの負債へと変わるのである。これが同レビューの表題の問いが組み立てられている機構である。

実務者の報告に見られる特徴的な様相は遅れである。同レビューが引くある開発者の記述は、AI アシスタントに React のコンポーネントや API のハンドラを生成させながらスプリント中に機能を急いで追加し、ベロシティの指標は申し分なく見えていた——そしてバグ報告が届いたのは直後ではなく数週間後、AI が考慮していなかったエッジケースにおいてだった、というものである。

## 適用条件

この概念は、生成されたコードが理解されうる速さよりも速く受け入れられうるところならどこにでも適用される。同レビューはこれを、速い開発一般ではなく LLM を用いたワークフローに固有のものとして結びつけている。

レビューされた文献が収斂する緩和策は human-in-the-loop のモデルであり、同レビューの 73 件のグレー情報源のうち 58 件で推奨されている。すなわち LLM の出力をレビューと改良を要する下書きとして扱うことであり、ある情報源はこれを、熱意はあるが時に自信過剰な若手開発者に対して本物のコードレビューを行うことと表現し、別の情報源は「信頼せよ、されど検証せよ」と表現している。報告されている関連する実践には、生成された出力にクリーンコードの原則を適用すること、AI の提案の検証にユニットテストを用いること、多層的なレビュープロセスを課すこと、そして組織のレベルでは短期的な生産性の向上より長期的な保守性を優先することが含まれる。

このカテゴリは新しく、測定ではなく実務者の報告に依拠している。同レビューはこれをグレーリテラチャから帰納的に同定しており、対象とした形式的な情報源には現れない。これについての標準的なベンチマークや指標は存在しない——同レビューは LLM に起因する技術的負債について、そうしたものをそもそも一つも見出せなかった。
