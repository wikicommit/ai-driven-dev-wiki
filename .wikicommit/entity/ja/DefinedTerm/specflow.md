Specflow とは、[[Organization/specstory]] が公開した、構造化された計画とコーディングエージェントによる反復的な実行を通じて意図をソフトウェアへ変換するためのワークフローである。自らを「オープンで柔軟なワークフロー」と説明しており、[[Report/beyond-code-centric]] によれば、Cursor・Copilot・Claude Code をエージェントとともに使った数千時間を経て形式化されたという。ブランチモデルを置き換えるものではなく、トランクベース開発の上で走らせるよう設計されており、その統治原理は「まず計画し、次に行動する」と述べられている。

## 用法

ワークフローは5つのステップからなる。**事前計画（pre-plan）**では、プロダクトマネージャーがユーザーの成果を定義し、デザイナーがパターンを加え、エンジニアが制約を列挙し、最上位の推論モデルがその結果の統合を助ける。**ロードマップ（roadmap）**では、全員が共同でリポジトリに置かれる Markdown のロードマップを執筆する。**ワークプラン（workplans）**では、ロードマップの各フェーズが人間と AI の実行可能なタスクへ分解される。ホワイトペーパーはこれを、暗黙知を表に押し出させるステップだと説明している。**実行（execute）**では、エージェントがタスクに取り組み、コンテキストが git に存在するため誰でも介入できる。**更新と洗練（update and refine）**では、サイクルごとに文書が進化し、意思決定と「作られたままの真実」を共有プロジェクトメモリに記録していく。

創発的設計の伝統と Specflow を分かつのは、公開元の説明によれば、第三の層である。コードとテストは依然として仕様の役割を果たすが、エージェントファーストの開発はそこに、人間と AI の双方が解釈できる、宣言された意図——ロードマップ、ワークプラン、ドキュメント、いずれも Markdown——を加える。

このワークフローが対置する失敗モードは、ホワイトペーパーが場当たり的な逆境（ad-hoc adversity）と呼ぶものである。この構造がなければ、曖昧なプロンプトは誤った出力、繰り返しの手直し、リグレッション、困難な統合、そして手に負えない技術的負債を生み、「複数の役割が複数の場所で」行う [[DefinedTerm/vibe-coding]] は整合しない断片的な結果を生む。示される診断はコンテキストの喪失である。AI への各プロンプトは比較的ステートレスであるため、共有された構造がなければシステムは収束せず、複数のチームメンバーから散らばって出される指示が断片化をさらに悪化させる。

公開元は、このワークフローが複雑さを取り除くのではなく再配分するものだと明言しており、残るコストとして、熟練した開発者であれば直観で処理してしまうであろう判断を列挙している。すなわち、どのプロンプトの前にもどのコンテキストを読み込むかを決めること、各段階にどのモデルが適するかを選ぶこと、人間なら通常は口にしないスコープの前提を明示すること、そしてエージェントをタスクの途中で中断すべき時機を見極めることである。最後の点については、早すぎる停止は得られたはずの進捗を無駄にし、遅すぎる停止はほどくべき大きな絡まりを生む、と述べている。また進捗の追跡も明示的になる。完了基準、コミットポイント、ブランチとドキュメントの方針を、感覚で捉えるのではなくすべて定義しなければならないからである。

以上はすべて、ワークフローの公開元が自らの手法について語った説明である。報告されている成果——3人が4週間で SpecStory の Studio 製品の完全なエンドツーエンドの macOS アルファ版を届けたというもの——は、独立した検証のない一次当事者の数字である。

## 関連用語

Specflow は [[DefinedTerm/spec-driven-development]] の具体的な実装の一つであり、同じ一般的な考えに対する他の名前を持つワークフローと並び立つものであって、その考え自体を定義するものではない。
