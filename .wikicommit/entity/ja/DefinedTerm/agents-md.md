AGENTS.md は、慣例としてリポジトリのルートに置かれる Markdown ファイルであり、プロジェクト固有の規約や制約を伝えるために、プロンプトのたびに AI コーディングエージェントのコンテキストへ読み込まれる。一般的なコーディングエージェントは `/init` 形式のコマンドでこのファイルを自動生成でき、そのコマンドはコードベースを走査して、ディレクトリ構造、技術スタック、テストの規約についての説明を生成する。

このフォーマット自身のプロジェクトは、これを一言で「コーディングエージェントを導くためのシンプルでオープンな
フォーマット」と説明し、エージェントのための README、すなわち AI コーディングエージェントがプロジェクトで作業する
のを助けるコンテキストと指示を提供するための、専用の予測可能な置き場所であると言い換えている。フォーマットは
`agentsmd/agents.md` リポジトリから MIT ライセンスで公開されており、プロジェクトの目標を説明するウェブサイト
<https://agents.md/> が併設され、リポジトリには技術憲章（technical charter）も置かれている。プロジェクトが
提供する最小限の例は、3 つの `##` セクション — 開発環境のヒント、テストの手順、プルリクエストの手順 — を持つ
プレーンな Markdown ファイルであり、その中身はコードベースについての散文ではなく、具体的なコマンドと規約
（どのパッケージマネージャーのコマンドを使うか、CI の計画がどこにあるか、必須のタイトル形式、コミット前に
実行すべきチェック）である。

## 起源と名称

このファイルが現在の名前を持つに至った経緯は、ある採用者の記述が補っている。[[BlogPosting/taming-agents-in-the-mercari-web-monorepo]] には、あるチームがこの標準を見つけた時点ではそれが単数形の `AGENT.md` であったことが記録されている — そこでは Sourcegraph が自社の AmpCode プロジェクトを通じて提案した RFC と説明されている。チームは既存の Cursor と Claude のルールをそのような 1 つのファイルに統合したが、チームの他のメンバーはその RFC がどれだけ存続するかを疑問に思っていた。続いてこの投稿は、OpenAI が agents.md ドメインを確保したと報告しており、それこそが標準を複数形の表記にすることを妨げていた唯一の要因であり、またそれは OpenAI 自身の Codex がすでに使っていたファイル名でもあったと述べている。投稿は、OpenAI の後押しによってこの標準がそのチームの使うツールの間で大きく普及したとし、チームは複数形の形式を唯一の信頼できる情報源（single source of truth）として採用した。これは採用者として観察したことについての 1 つのチームの記述であり、標準がどのように設計されたかについての当事者の記述ではない。また、投稿が言及している発表そのものは、このウィキの情報源には含まれていない。

この投稿は、ツールごとのルールファイルがすでに存在するコードベースでこの標準を採用したことの実務上の帰結も記述している。`CLAUDE.md` やその他の多くのルールファイルは、メインのファイルへのシンボリックリンクにするだけで済み、既存のフォーマットは内容を二重に保守することなく引き続き機能した。

後の記述は、この標準が最終的にどこに落ち着いたかを付け加えている。
[[BlogPosting/division-of-labor-in-ai-instruction-files]] は、その出発点として Sourcegraph の Amp チームを
挙げており — 始まりについては上記の採用者の記述と一致している — その後 OpenAI、Google、Cursor、Factory などが
共同で推進し、2025 年 12 月に Linux Foundation に寄贈されたと説明している。つまり、上記の採用者の記述が
未解決のまま残した問い、すなわち 1 つのベンダーの RFC が存続するかどうかは、標準をどの単一ベンダーの手からも
切り離すことによって答えが出た。この投稿はまた、シンボリックリンクによる構成を、1 つのチームの便宜的な手段では
なく、フォーマットのプロジェクト自身が推奨するパターンとして示している。Claude Code は `AGENTS.md` ではなく
`CLAUDE.md` を読むため、`AGENTS.md` を実体のファイルとし、`CLAUDE.md` をそこへのシンボリックリンクにすることが
推奨されている。投稿は `CLAUDE.md` を、単に Claude 専用の `AGENTS.md` であると特徴づけている。

## 用法

情報源で要約されている引用研究によれば、真に発見不可能で運用上重要な事実（例：「パッケージ管理には `uv` を使う」）を記録した人間作成の `AGENTS.md` は、エージェントの振る舞いを測定可能な形で変え、タスクの成功率を向上させた。一方、自動生成されたファイル — 典型的には、エージェントがリポジトリを直接読めば発見できるコードベースの概要 — は、タスクの成功率を改善することなく、場合によっては低下させながら、コストを増やすことがわかった。この情報源は「アンカリング効果」も記述している。ある技術やパターンがファイル内で一度言及されると、その後のすべてのプロンプトでコンテキストに残り続けるため、それがもはや現行の規約ではなくなった場合でも、エージェントをその方向へ偏らせうる。

同じ著者による別の投稿は、OpenAI の Codex のドキュメントを引用し、どのテストを実行するか、lint ルール、依存関係のポリシー、ドキュメントの要件についてエージェントに一貫した期待を持たせるために `AGENTS.md` ファイルを置くことが推奨されていると述べている — これはそこで、新入社員がコードを書き始める前に規約の地図を渡してオンボーディングすることになぞらえられている。この投稿はまた、`AGENTS.md` や関連するチェックリストの更新を、繰り返し可能なオーケストレーションループの最後の「振り返り（retro）」ステップと位置づけており、それによって次の実行がより賢い状態から始まるとしている（[[BlogPosting/your-ai-coding-agents-need-a-manager]]）。

GitHub は、[[SoftwareApplication/agent-hq]] とともに発表された VS Code のカスタムエージェントの設定面の 1 つとして
このファイルを採用した（[[BlogPosting/introducing-agent-hq]] を参照）。そこでは `AGENTS.md` ファイルが、明確な
ルールとガードレールを設定するためのソース管理されたドキュメントとして説明されており — 例として「このロガーを
優先する」「すべてのハンドラーにテーブル駆動テストを使う」が挙げられている — その目的は、毎回プロンプトで
指示し直すことなく Copilot の振る舞いを形づくることだとされている。

[[SoftwareApplication/github-copilot-code-review]] についての GitHub のドキュメントは、このファイルを 4 つの
カスタマイズ面の 1 つに位置づけ、それらをスコープによって区別している。これは、このファイルを*使うべきでない*
場面について、このウィキが持つ最も明確なベンダーの記述である。`.github/copilot-instructions.md` は Copilot に
固有の、リポジトリ全体に常時適用されるルールを保持する。`.github/instructions/` 以下のパス固有の
`*.instructions.md` ファイルは、特定のパス、ファイルタイプ、ディレクトリに常時適用されるルールを保持する。
リポジトリのルートから読まれる `AGENTS.md` は、複数の AI ツールやエージェントの間で共有されることを意図した、
常時適用のルールを保持する。そして `.github/skills/` 以下のスキルは、必要に応じて、または関連する場合に実行される
タスク固有のワークフローを保持する。GitHub はこの区別を 4 つの目安に圧縮している — 「Copilot、このリポジトリでは
常にこれを知っておいて」「Copilot、これらのパスで作業するときは常にこれを知っておいて」「どのエージェントも、
常にこれを知っておいて」「必要なときにこれをやって」。したがってこの説明において `AGENTS.md` を際立たせているのは
リポジトリ内でのスコープではなく、ツールをまたいだ到達範囲であり、それは上記の採用者の記述がこのファイルを
選んだ理由と同じ性質である。同じドキュメントは、プルリクエストのレビュー中、Copilot がカスタム指示、エージェント
指示、スキルをベースブランチではなくヘッドブランチから読み込むと述べている。そのため、これらのいずれかへの変更は、
マージする前に、それを導入するプルリクエストの中でテストできる。

[[ScholarlyArticle/agentic-software-engineering-foundational-pillars]] は、`CLAUDE.md`、`.clinerules`、`AGENT.md` のようなプロジェクトレベルの設定ファイルを、エージェントのタスクの前に毎回「組織的知識」を読み込ませる、初期の草の根的な実践として論じている — スタイルガイド、アーキテクチャ上の制約、得られた教訓を、AI チームメイトのための継続的に改善される「従業員ハンドブック」として成文化するものである。論文はこの実践を、自らが [[DefinedTerm/mentorscript]] として形式化を提案するものの初期の例と位置づけ、そのようなファイルに何を含めるべきか、どの程度の詳細さが適切かについてコミュニティに合意はないと述べている。そして今後の課題には、この目的のためのより形式的な言語を定義することだけでなく、これらのファイルを効果的に使うためのベストプラクティスを見出すことも含まれると論じている。

ある実務者の記述は、このファイルを他のどの記述もこの深さでは扱っていない用途に用いている。エージェントが読む
コンテキストとしてだけでなく、*手順*全体を置く場所としてである。
[[BlogPosting/human-intent-ai-implementation-codex-workflow]] は、プロジェクトの初期化時に `AGENTS.md` を、
著者が AI の記憶と呼ぶものとして作成し、そこにプロジェクトの概要、フォルダ構成、参照必須のドキュメント、
作業ルール、現在のステータスを収めている。この投稿がそこに記録している 4 つの作業ルールは、行動する前に計画を
立て承認後に実行すること、計画や提案の際には 3 つの選択肢を示すこと、実装前に関連する仕様を確認・更新すること、
そして完了時にストーリーごとのコンテキストファイルを更新することである。これらと並んで、自動生成のルールそのもの
— ルーチンを起動するフレーズ、実行する手順、生成するフォルダとファイルの構成、そして結果として得られるファイルの
形 — も格納されている。著者が主張する効果は、エージェントではなくプロンプトに現れる。配置と手順がすでに
書き留められているため、プロンプトは出力パスを列挙する代わりに要件を述べるだけでよくなる（「`vision.md` を読んで
ユーザーストーリーを生成して」）。著者が述べる経験則は、これらのルールファイルが充実するほどプロンプトは単純になり、
出力は良くなるというものである。これはサンプルプロジェクトでの 1 人のエンジニアによる実演であり、測定の裏付けは
ない。

## 適用される場面

この情報源は、良い `AGENTS.md` を恒久的な設定ではなく、コードベースの摩擦を記録し続ける生きた記録と位置づけている。エージェントが同じ間違いを繰り返すときに 1 行を追加し、根本的な問題（わかりにくいディレクトリ構造や、何かを自動的に検出すべきビルドパイプラインなど）が代わりに修正されたら、その行を削除する。実務上のフィルターとしては、エージェントがコードを読めば発見できる事実なら、それはファイルに属さない、と述べている。この情報源はまた、単一で静的な、リポジトリのルートに置かれるファイルを、一定以上の複雑さを持つコードベースにとっては構造的な限界とみなしている。フラットな指示セットでは、実行されるタスクの種類に応じて内容を条件付けることができないからである。そして、その代替として意図されるものとして、自動的に保守される、ディレクトリ単位やモジュール単位のファイルの階層を提案している。さらに、この考えをより精緻にした 3 層の版（最小限のルーティングファイル、タスク単位のスキルファイル、保守用のサブエージェント）も説明しつつ、そのより完全なアーキテクチャをきれいに構築するのに必要なライフサイクルフックを公開している主要なコーディングエージェントはまだないと指摘している。

**このウィキの情報源は、ファイルに何を含めるべきかについて一致していない。** 上記の最初の情報源は発見可能性のフィルターを設けている — エージェントがコードを読めば得られる事実には 1 行を割く価値がない — これは、LLM が生成したコンテキストファイルがコストを大幅に増やしつつタスクの成功率をわずかに下げることを見出した研究から、著者が引き出した実務上の教訓である。上記の実務者の記述は、フォルダ構成、作業ルール、自動生成の手順をそこに格納しており、それはこのフィルターが認めるよりはるかに多い。そして逆方向の主張をしている。すなわち、ルールファイルが充実するほどプロンプトは単純になり、出力は良くなるというものである。両者は同じものを測っているわけではない — 一方はタスクの成功率についての実験結果を、もう一方はサンプルプロジェクトでの 1 人のエンジニアの作業方法を報告している — し、どちらも他方に言及していないため、ここでは両者を調停せずに併記する。両者を分けるのは目的なのかもしれない。発見可能性のフィルターはエージェントが何を*知る*必要があるかについてのものであり、起動されるために書かれた手順はエージェントが何を*すべき*かについてのものである。後者は、いくらコードを読んでも得られない。

あるチームは、最初の情報源が提案する階層に近いものを実践に移しており、その形は記録しておく価値がある。この不一致を解決するのではなく、回避しているからである。[[BlogPosting/taming-agents-in-the-mercari-web-monorepo]] では、ルートの `AGENTS.md` 自体はほとんど何も保持していない。各セクションは見出しと、`docs/` 以下の別のドキュメントへのポインタからなる — ビルドとテストのコマンド、コードスタイルと標準、プロジェクトのアーキテクチャ、認証パターン、テスト戦略である。投稿は、自らのリポジトリがモジュール構造であることを踏まえてアーキテクチャのドキュメントを極めて重要なものとして挙げ、そのコンテキストを省くことのコストを、毎回同じ初期コンテキストを注意深くプロンプトで与えない限り、ほとんどのツールの出力は開発者が完全に作り直さなければならなくなることだと述べている。また、プロジェクトのデザインシステムを ALWAYS/NEVER という強い表現でエージェントに教えている — コンポーネントは常にソースファイルからではなくデザインシステムのパッケージからインポートすること、デザインシステムのコンポーネントやネイティブの HTML 要素に決してインラインスタイルを追加しないこと — その理由として、プロジェクトはそのデザインシステムに従わなければならず、バイブコーディングで書かれた CSS に頼ることはできないと述べている。

そうしたファイルを最新に保つことに対するこのチームの答えは、それを委任することである。上位の設計に大きな影響を与えるプルリクエストについては、エンジニアが変更セットとルールフォルダを合わせてエージェントを実行し、モデル自身にルールの編集を提案させるか、コード中の不整合を指摘させる。これを自動化する理由として述べられているのは、タスクに集中しているエンジニアにとって、別フォルダにある非ローカルな Markdown ファイルを編集するのは面倒だということであり、チームはその結果を、自己強制的で自己更新的なドキュメントと呼んでいる。これはチーム自身による、測定を伴わない特徴づけである。また執筆時点で構築中だったもの — ルールから逸脱したコードをフラグ付けする、すべてのプルリクエストに対するエージェント — はまだリリースされていなかった。

長時間稼働エージェントについての後の投稿は、長時間または夜間にわたるコーディングジョブを実行する開発者向けに、同じファイルにさらなる設計原則を与えている。`AGENTS.md` をパイロットのチェックリストのように扱い、短く保ち、すべての行を過去の実際の失敗によって正当化されたものにする、というものである。投稿はそれとは別に、Anthropic 自身の科学計算エージェントが `CLAUDE.md` を同様の役割で — エージェント自身が学ぶにつれて編集する生きた計画として — 用い、ポータブルな実験ノートとして機能する `CHANGELOG.md` と組み合わせていることも説明している（[[DefinedTerm/ralph-loop]] を参照）。

このようなファイルが実際にどう解釈されるかについての最も明示的な記述は、ベンダー側から出ている。
OpenAI は [[BlogPosting/introducing-codex]] の付録として codex-1 のシステムメッセージを公開しており、その一節は
エージェントが従うルールとして書かれた `AGENTS.md` の仕様である。そこではエージェントに対して次のように述べている。
これらのファイルはコンテナのファイルシステムのどこにでも現れうる — 典型的な場所はルート、ホームディレクトリ、
git リポジトリ内のさまざまな場所であり、したがってリポジトリ内にある必要はまったくない。ファイルのスコープは、
それを含むフォルダをルートとするディレクトリツリー全体であり、最終的なパッチで触れるすべてのファイルについて、
エージェントはそのファイルをスコープに含むあらゆる `AGENTS.md` に従わなければならない。コードスタイル、構造、
命名に関する指示は、ファイルが別途定めない限り、そのスコープ内でのみ適用される。指示が衝突する場合は、より深く
ネストされたファイルが優先される。そして、プロンプト中のシステム、開発者、ユーザーによる直接の指示はファイルより
優先される。さらに 2 つの規定は、ファイルがどこに適用されるかではなく、ファイルが何を要求できるかに関するもので
ある。ファイルが指定するプログラム的なチェックは、すべてのコード変更の後に、ドキュメントのような単純な変更であっても、
すべて実行し、それらが通ることを最大限確認しなければならない。また、プルリクエストのメッセージについてファイルが
与える指示は尊重されなければならない。OpenAI は、開発者がモデルのデフォルトの振る舞いを理解し、Codex を自らの
ワークフローに合わせて調整できるようにするためにシステムメッセージを公開したと説明しており、そのような変更の例として、
時間がないときにそれらのテストを省略することを挙げている。つまり、この優先順位のルールは単なる衝突解決の細則ではなく、
ユーザーが頼りにできるものとして提示されている。

## セキュリティ上の考慮事項

このファイルを有用にしている性質は、同時にそれを標的にもしている。エージェントは設計上これらのファイルを信頼されたプロジェクトコンテキストとして読み込むため、作業ツリーにこのファイルを書き込める者は誰でも、その立場を伴う指示を与えることができる。NVIDIA AI Red Team の報告は、これを Codex に対して実証した。悪意のある Go の依存関係が、どの依存関係にも可能なようにビルドステップ中に実行され、ユーザー自身の要求より優先すると主張する指令を含む `AGENTS.md` を書き込んだところ、エージェントは与えられたタスクよりもそれらの指令に従った。報告は、このファイルの信頼モデルは欠陥ではなく意図的なものであること、そしてこの攻撃は侵害された依存関係 — それ自体がすでにコード実行を意味する — を前提としていることを明言している。したがってこの攻撃が付け加えるのは、そのアクセスを得る新しい方法ではなく、そのアクセスの新しい使い道である。

報告が提案する緩和策のうち、ファイル自体を対象とするものは、その内容ではなく完全性に関するものである。エージェントが読み書きできるファイルを制限すること、エンドポイントセキュリティや集中型の構成管理を用いて、特に設定ファイルに対して完全性の管理を強制すること、そして想定外のファイル変更に対してアラートを出すことである。ファイルとはまったく関係のない緩和策も提案されている — 依存関係のバージョンを厳密に固定してパッケージをスキャンすること、エージェントが生成したプルリクエストを専用のセキュリティエージェントで監査すること、そしてモデル自体をスキャンしてガードレールを設けることである。攻撃そのものについては [[DefinedTerm/indirect-agents-md-injection]] を参照。

これは上記の優先順位のルールに関わる。codex-1 の仕様は、システム、開発者、ユーザーによる直接の指示がファイルより優先すると述べている。しかし報告された攻撃では、エージェントはその逆を主張するファイルに従って行動した。したがってこの順序は文書化されたデフォルトにすぎず、注入されたファイルが異を唱えられないものではない。
