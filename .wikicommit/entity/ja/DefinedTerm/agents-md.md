AGENTS.md とは、慣例としてリポジトリのルートに置かれる Markdown ファイルであり、プロジェクト固有の慣習と制約を伝えるために、プロンプトのたびに AI コーディングエージェントのコンテキストへ読み込まれる。主要なコーディングエージェントは `/init` 系のコマンドでこれを自動生成でき、そのコマンドはコードベースを走査して、ディレクトリ構成・技術スタック・テストの慣習についての記述を生成する。

この形式のプロジェクト自身はこれを「コーディングエージェントを導くための、シンプルでオープンな形式」と 1 行で説明し、エージェント向けの README、すなわち AI コーディングエージェントがプロジェクトで作業する助けとなるよう文脈と指示を与えるための、専用の予測可能な場所だと言い換えている。`agentsmd/agents.md` リポジトリから MIT ライセンスのもとで公開されており、プロジェクトの目標を説明するウェブサイト <https://agents.md/> が併設され、リポジトリにはテクニカルチャーターが置かれている。プロジェクトが同梱する最小の例は、`##` の節を 3 つ持つ素の Markdown ファイル — 開発環境のヒント、テストの手引き、プルリクエストの手引き — であり、その中身はコードベースについての散文ではなく、具体的なコマンドと慣習（どのパッケージマネージャのコマンドを使うか、CI の計画がどこにあるか、必須のタイトル書式、コミット前に走らせるチェック）である。

## 由来と名前

ある採用者の記録が、このファイルが今の名前を持つに至った経緯を補ってくれる。[[BlogPosting/taming-agents-in-the-mercari-web-monorepo]] は、あるチームがこの標準を、まだ単数形の `AGENT.md` だった時点で見つけたことを記している。そこでは Sourcegraph が AmpCode プロジェクトを通じて提案した RFC として説明されている。チームは既存の Cursor と Claude のルールを 1 つのそうしたファイルへ統合したが、一方でチームの他のメンバーはその RFC がどれだけ長持ちするのかを訝しんでいた。その記事は続けて、OpenAI が agents.md ドメインを確保したことを報告し、それこそがこの標準を複数形の表記へ進ませずに引き留めていた唯一のものであり、かつ OpenAI 自身の Codex がすでに使っていたファイル名でもあったと述べている。記事は、この標準がそのチームの使うツール群の間でずっと大きな支持を得るようになったのは OpenAI の後ろ盾のおかげだとし、チームは複数形の表記を単一の情報源として採用した。これは採用者として観察したことについての、あるチームの記録であって、標準がどう設計されたかについての当事者の記録ではなく、そこで言及されている発表そのものはこの wiki の出典には含まれていない。

その記事はまた、ツールごとのルールファイルがすでに存在していたコードベースでこれを採用したことの実際的な帰結についても述べている。`CLAUDE.md` をはじめとする多くのルールファイルは、単に本体のファイルへのシンボリックリンクになった。こうして、内容を二重に保守することなく、既存の形式もそのまま動き続けたのである。

## 用法

出典がまとめている引用研究によれば、人間が書いた `AGENTS.md` が、本当に発見しようのない、運用上重要な事実（たとえば「パッケージ管理には `uv` を使う」）を記録している場合には、エージェントの振る舞いが測定できる形で変わり、タスクの成功率も上がった。一方、自動生成されたファイル — たいていはリポジトリを直接読めばエージェント自身が発見できるコードベースの概要 — は、コストを増やすだけで成功率を改善せず、場合によってはむしろ下げることが見出された。出典はまた「アンカリング効果」についても述べている。ある技術やパターンがいったんファイルに書かれると、以後すべてのプロンプトでコンテキストに残り続けるため、それがもはや現行の慣習でなくなってもエージェントをそちらへ引き寄せてしまいうるのである。

同じ著者による別の記事は、OpenAI の Codex のドキュメントが `AGENTS.md` ファイルを推奨していることを引き、どのテストを走らせるか、リントの規則、依存関係の方針、ドキュメントの要件について、エージェントに一貫した期待を持たせるためのものだとしている。そこではこれが、新しく入った人がコードを書き始める前に慣習の地図を渡してオンボーディングすることになぞらえられている。その記事はまた、`AGENTS.md` と関連するチェックリストを更新することを、繰り返し回せるオーケストレーションのループにおける最後の「振り返り」の段階として位置づけ、次の実行がより賢い状態から始まるようにしている（[[BlogPosting/your-ai-coding-agents-need-a-manager]]）。

GitHub は、VS Code のカスタムエージェント向けの設定面の 1 つとしてこのファイルを採用し、[[SoftwareApplication/agent-hq]] と併せて発表した（[[BlogPosting/introducing-agent-hq]] を参照）。そこでは `AGENTS.md` ファイルを、明確なルールとガードレールを定めるためのバージョン管理下の文書として説明しており、例として挙げられているのは「このロガーを優先せよ」「すべてのハンドラにはテーブル駆動テストを使え」である。その狙いは、毎回プロンプトを与え直すことなく Copilot の振る舞いを形づくることだとされている。

[[SoftwareApplication/github-copilot-code-review]] に関する GitHub のドキュメントは、このファイルを 4 つのカスタマイズ面の中に位置づけ、それらをスコープによって切り分けている。これは、いつこれを使う*べきでない*かについて、この wiki が保持する最も明快なベンダーの言明である。`.github/copilot-instructions.md` は、Copilot 固有の、リポジトリ全体に常時適用される規則を持つ。`.github/instructions/` 以下のパス固有の `*.instructions.md` ファイルは、特定のパス・ファイル種別・ディレクトリに常時適用される規則を持つ。リポジトリのルートから読まれる `AGENTS.md` は、AI ツールやエージェントの間で共有されることを意図した、常時適用の規則を持つ。そして `.github/skills/` 以下のスキルは、必要に応じて、あるいは関連する場面で実行されるタスク固有のワークフローを持つ。GitHub はこの区別を 4 つの目安へと圧縮している — 「Copilot よ、このリポジトリについては常にこれを知っておけ」「Copilot よ、これらのパスで作業するときは常にこれを知っておけ」「どのエージェントであれ、常にこれを知っておけ」「必要なときにこれをせよ」。したがってこの説明において `AGENTS.md` を際立たせているのは、リポジトリ内でのスコープではなくツールをまたぐ到達範囲であり、それは先の採用者の記録がこれを選んだ理由と同じ性質である。同じドキュメントは、プルリクエストのレビューの際に Copilot がカスタム指示・エージェント指示・スキルをベースブランチではなくヘッドブランチから読むことも述べており、したがってそれらへの変更は、先にマージすることなく、それを導入するプルリクエストの中で試すことができる。

[[ScholarlyArticle/agentic-software-engineering-foundational-pillars]] は、`CLAUDE.md`、`.clinerules`、`AGENT.md` といったプロジェクト単位の設定ファイルを、エージェントのあらゆるタスクに先立って「組織の知」を読み込ませる、草の根の初期の実践として論じている。スタイルガイド、アーキテクチャ上の制約、そして得られた教訓を、AI のチームメイトのために絶えず改善されていく「従業員ハンドブック」へと成文化する営みである。論文はこの実践を、自らが [[DefinedTerm/mentorscript]] として形式化することを提唱しているものの初期の例として位置づけ、そうしたファイルに何を書くべきか、どの程度の詳しさが適切かについてコミュニティに合意はないと述べたうえで、今後の課題にはこの目的のためのより形式的な言語を定義することだけでなく、これらのファイルを効果的に使うためのベストプラクティスを見出すことも含まれると論じている。

ある実践者の記録は、他のどの出典もここまで踏み込んでは述べていない用途にこのファイルを充てている。エージェントが読む文脈としてだけでなく、*手順*そのものが住まう場所としてである。[[BlogPosting/human-intent-ai-implementation-codex-workflow]] は、プロジェクトの初期化時に `AGENTS.md` を、著者が AI の記憶と呼ぶものとして書き起こし、そこにプロジェクトの概要、フォルダ構成、参照すべき文書、作業上の規則、そして現在の状況を持たせている。その記事がそこに記録している 4 つの作業上の規則は、行動の前に計画し承認の後に実行すること、計画や提案の際には選択肢を 3 つ提示すること、実装の前に関連する仕様を確認し更新すること、そして完了時にストーリーごとのコンテキストファイルを更新することである。それらと並べて、自動生成の規則そのもの — ルーチンを起動する言い回し、走らせる手順、作るべきフォルダとファイルの配置、そして出来上がるファイルの形 — も保存されている。そこで主張されている帰結は、エージェントにではなくプロンプトに現れる。配置と手順がすでに書かれているおかげで、プロンプトは出力先のパスを列挙する代わりに要求を述べる（「`vision.md` を読んでユーザーストーリーを生成せよ」）だけで済む、というのである。著者が掲げる目安は、これらのルールファイルが埋まっているほどプロンプトは単純になり、出力は良くなる、というものである。これはサンプルプロジェクト上での 1 人のエンジニアによる実演であり、その背後に測定はない。

## 適用範囲

出典は、良い `AGENTS.md` を恒久的な設定ではなく、コードベースの摩擦を記録し続ける生きた記録として捉えている。エージェントが同じ間違いを繰り返すときに 1 行が加えられ、その根底にある問題（分かりにくいディレクトリ構成、本来なら自動で検出すべきビルドパイプライン）が代わりに直されたら取り除かれる。実際的な判別基準としては、エージェントがコードを読んで知りうる事実なら、このファイルに書くべきではない、と述べられている。出典はまた、単一で静的な、リポジトリのルートに置かれるファイルを、一定の複雑さを超えたコードベースにとっては構造的な限界だとも捉えている。平坦な指示の集合では、どんな種類のタスクが走っているかに応じて内容を変えることができないからである。そして、自動的に保守される、ディレクトリ単位ないしモジュール単位のファイルの階層構造を、あるべき置き換えとして提案している。さらにこの発想をより手の込んだ 3 層構成にしたもの（最小限のルーティング用ファイル、タスク単位のスキルファイル、そして保守を担うサブエージェント）も述べたうえで、そのより完全なアーキテクチャをきれいに組み上げるのに必要なライフサイクルフックを、まだどの主要なコーディングエージェントも公開していないと指摘している。

**この wiki の出典は、このファイルに何が属するかについて一致していない。** 上に挙げた最初の出典は発見可能性の判別基準を置く — エージェントがコードを読んで得られる事実は 1 行を割くに値しない — というものであり、その著者はこれを、LLM が生成したコンテキストファイルがタスクの成功率をわずかに下げ、コストは大きく上げたという研究からの実践的な教訓として引き出している。一方、上に挙げた実践者の記録はフォルダ構成・作業上の規則・自動生成の手順をそこに保存しており、これはその判別基準が認めるであろう範囲をかなり超えている。そして正反対の方向を論じる。ルールファイルが充実しているほどプロンプトは単純になり出力は良くなる、と。この 2 つは同じものを測ってはおらず — 一方はタスクの成功率についての実験結果を報告し、他方はサンプルプロジェクト上での 1 人のエンジニアの作業法である — 互いに噛み合ってもいないため、ここでは調停せずに両方を記録する。両者を分けているのは目的かもしれない。発見可能性の判別基準はエージェントが何を*知る*必要があるかについてのものであり、起動されることを前提に書かれた手順はエージェントが何を*すべき*かについてのものであって、後者はコードをいくら読んでも得られない。

最初の出典が提案する階層構造に近いものを実際に運用しているチームが 1 つあり、その形は、この不一致を決着させるのではなく迂回している点で記録に値する。[[BlogPosting/taming-agents-in-the-mercari-web-monorepo]] では、ルートの `AGENTS.md` はそれ自体にはほとんど何も持っていない。その各節は見出しと、`docs/` 以下の別の文書への指し示しからなる — ビルドとテストのコマンド、コードスタイルと規約、プロジェクトのアーキテクチャ、認証のパターン、テスト戦略である。記事は、そのリポジトリのモジュール構造を踏まえるとアーキテクチャの文書がとりわけ決定的だと名指しし、その文脈を欠いた場合の代償を、毎回同じ初期文脈を注意深くプロンプトで与えない限り、たいていのツールの出力を開発者が全面的に組み直さねばならなくなることだと述べている。また、プロジェクトのデザインシステムを、強調された ALWAYS／NEVER の言い方でエージェントに教え込んでもいる — コンポーネントは常にソースファイルからではなくデザインシステムのパッケージからインポートせよ、デザインシステムのコンポーネントやネイティブの HTML 要素に対してインラインスタイルを決して付けるな — その理由として挙げられているのは、プロジェクトがそのデザインシステムに従わねばならず、雰囲気で書かれた CSS に頼るわけにはいかないことである。

そうしたファイルを最新に保つことへのそのチームの答えは、それを委ねてしまうことである。より上位の設計に大きな影響を与えるプルリクエストについては、エンジニアが変更セットとルールのフォルダを併せてエージェントに与えて走らせ、モデル自身にルールへの修正を提案させるか、コード中の不整合を指摘させる。これを自動化する理由として述べられているのは、タスクに集中しているエンジニアにとって、別のフォルダにある手元から離れた Markdown ファイルを編集するのは煩わしいということであり、チームはその結果を、自ら強制し自ら更新するドキュメントと呼んでいる。これはそのチーム自身による特徴づけであって測定を伴わず、執筆時点で作っていたもの — すべてのプルリクエストに対してルールから逸脱したコードを指摘するエージェント — はまだ稼働していなかった。

長時間動くエージェントについての後年の記事は、長時間あるいは夜通しのコーディング作業を走らせる開発者に向けて、同じファイルにさらなる設計原則を与えている。`AGENTS.md` をパイロットのチェックリストのように扱い、短く保ち、どの 1 行も実際に起きた過去の失敗によって勝ち取られたものにせよ、というものである。その記事は別途、Anthropic 自身の科学計算向けエージェントが `CLAUDE.md` をこれに比肩する役割で — エージェント自身が学びながら書き換えていく生きた計画として — 用い、持ち運び可能な実験ノートとして働く `CHANGELOG.md` と組み合わせていることも述べている（[[DefinedTerm/ralph-loop]] を参照）。

そうしたファイルが実際にどう解釈されるのかについての最も明示的な言明は、ベンダーの側から来ている。OpenAI は codex-1 のシステムメッセージを [[BlogPosting/introducing-codex]] の付録として公開しており、その一節は、エージェントが従う規則として書かれた `AGENTS.md` の仕様になっている。そこではエージェントに次のように伝えられている。これらのファイルはコンテナのファイルシステムのどこにでも現れうること（典型的な置き場所はルート、ホームディレクトリ、そして git リポジトリ内のさまざまな場所であり、したがってリポジトリの中にある必要すらない）。ファイルのスコープは、それを含むフォルダを根とするディレクトリツリー全体であり、最終的なパッチで触れたすべてのファイルについて、そのファイルをスコープに含むあらゆる `AGENTS.md` にエージェントは従わねばならないこと。コードのスタイル・構造・命名に関する指示は、ファイルが別段の定めをしない限り、そのスコープ内でのみ適用されること。指示が衝突する場合はより深くネストされたファイルが優先すること。そして、プロンプト中の直接的なシステム・開発者・ユーザーの指示はファイルに優先すること。さらに 2 つの定めは、どこに適用されるかではなく、ファイルが何を要求できるかについてのものである。ファイルが指定するプログラム的なチェックは、すべてのコード変更の後に、そしてドキュメントのような単純な変更に対してさえ、すべて実行し、通ることを最大限努力して確認しなければならないこと。そして、プルリクエストのメッセージについてファイルが与える指示は尊重されるべきこと。OpenAI は、開発者がモデルの既定の振る舞いを理解し Codex を自らのワークフローに合わせられるようにするためにシステムメッセージを公開したと述べ、そうした変更の例として、時間がないときにそれらのテストを飛ばすことを挙げている。したがってこの優先順位の規則は、単なる衝突解決の細目ではなく、利用者が寄りかかれるものとして提示されている。

## セキュリティ上の考慮

このファイルを有用にしている性質は、それを攻撃対象にもしている。エージェントは設計上これらのファイルを信頼できるプロジェクトの文脈として読み込むのだから、作業ツリーにそれを書き込めるものは何であれ、その資格を帯びた指示を送り込めることになる。NVIDIA の AI レッドチームの報告は、これを Codex に対して実証した。悪意ある Go の依存パッケージが、あらゆる依存パッケージがそうできるようにビルドの段階で実行され、ユーザー自身の要求に優先すると称する指示を持つ `AGENTS.md` を書き込み、エージェントは与えられていたタスクよりもそちらに従ったのである。報告は、このファイルの信頼モデルが欠陥ではなく意図的なものであること、そしてこの攻撃が侵害された依存パッケージ — それはすでにコード実行を意味する — を前提としていることを明言している。したがってこれが加えているのは、そのアクセスを得る新しい手立てではなく、そのアクセスの新しい使い道である。

報告が提案する緩和策のうち、ファイルそのものに向けられたものは、その内容ではなく完全性についてのものである。エージェントが読み書きできるファイルを限定すること、エンドポイントセキュリティや集中的な構成管理を用いて設定ファイルに特化した完全性の制御を課すこと、そして予期しないファイルの変更に警告を上げることである。ファイルとはまったく関係のないものも提案されている。依存パッケージのバージョンを厳密に固定してパッケージを走査すること、エージェントが生成したプルリクエストを専用のセキュリティエージェントで監査すること、そしてモデル自体を走査しガードレールで囲うことである。攻撃そのものについては [[DefinedTerm/indirect-agents-md-injection]] を参照のこと。

このことは、上で述べた優先順位の規則に関わってくる。codex-1 の仕様は、直接的なシステム・開発者・ユーザーの指示がファイルに優先すると述べている。それにもかかわらず、報告された攻撃においてエージェントは、それとは逆だと称する指示を持つファイルに従って行動した。つまりその順序づけは、文書化された既定であって、注入されたファイルが争えないものではないのである。
