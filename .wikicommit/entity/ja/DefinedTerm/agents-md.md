AGENTS.md とは、エージェンティックな AI コーディングツールが読む、リポジトリレベルの Markdown の [[DefinedTerm/context-files]] である。公式サイトはこれを「コーディングエージェントを導くためのシンプルでオープンな形式」と説明し、6万を超えるオープンソースプロジェクトで使われていると述べている（この数値の出典としてサイトは GitHub のコード検索を挙げている）。[[ScholarlyArticle/configuring-agentic-ai-coding-tools]] によれば、これはツール横断で支持が広がりつつあるオープンでツール非依存の慣習として機能しており、CLAUDE.md、GEMINI.md、copilot-instructions.md といったベンダー固有の代替とは対照的である。

## 用法

### この形式自身による説明

公式サイトはこのファイルを「エージェントのための README」と枠づけている。AI コーディングエージェントがプロジェクトで作業する助けとなるコンテキストと指示を提供する、専用の予測可能な場所である。README.md と分けておく理由として挙げられるのは、README は人間のためのもの——クイックスタート、プロジェクトの説明、コントリビューションのガイドライン——であるのに対し、AGENTS.md はエージェントが必要とする追加の、ときに詳細なコンテキスト——ビルド手順、テスト、慣習など、README を散らかすか人間の貢献者には無関係なもの——を保持する、というものである。サイトはこの分離の理由を三つ挙げている。エージェント向けの指示のための明確で予測可能な場所、簡潔で人間に焦点を合わせた README、そして既存のドキュメントを補完する的確なエージェント向けの案内である。サイトはまた、別の独自ファイルを導入するのではなく誰にとっても機能するよう、この名称と形式が選ばれたと述べている。

必須のフィールドはない。サイトは AGENTS.md が標準の Markdown にすぎず、エージェントは与えられたテキストをそのまま解析するだけなので、どんな見出しを使ってもよいと述べている。扱うとよい一般的なセクションとして、プロジェクトの概要、ビルドとテストのコマンド、コードスタイルのガイドライン、テストの手順、セキュリティ上の考慮点を挙げ、さらに新しいチームメイトに伝えるであろうこと——コミットメッセージやプルリクエストのガイドライン、セキュリティ上の落とし穴、大規模なデータセット、デプロイ手順——も同様にここに属すると付け加えている。このファイルは生きたドキュメントとして扱うよう助言している。

振る舞いに関する規則が二つ述べられている。モノレポでは各パッケージの内側に別の AGENTS.md を置いてよい。エージェントはディレクトリツリー上で最も近いファイルを読むため、最も近いものが優先され、各サブプロジェクトが自分向けの指示を同梱できる。サイトは、執筆時点で OpenAI のメインリポジトリには88個の AGENTS.md があると指摘している。指示が衝突する場合は、編集対象のファイルに最も近い AGENTS.md が勝ち、ユーザーの明示的なチャットのプロンプトはすべてに優先する。テストコマンドについては、それが列挙されていれば、エージェントは関連するプログラム的なチェックを実行し、タスクを終える前に失敗を修正しようとする、と述べている。

既存のエージェント指示ファイルがあるプロジェクトについては、後方互換のためにリネームしてシンボリックリンクを作ることを提案している（`mv AGENT.md AGENTS.md && ln -s AGENTS.md AGENT.md`）。このファイルを読むのに明示的な設定が必要なツールが二つある。Aider は `.aider.conf.yml` に `read: AGENTS.md` を、Gemini CLI は `.gemini/settings.json` に `{ "context": { "fileName": "AGENTS.md" } }` を書く必要がある。

### 起源と管理

この形式がどこから来たのかについての説明は出典によって異なり、区別して扱う価値がある。公式サイトは、AGENTS.md が「OpenAI Codex、Amp、Google の Jules、Cursor、Factory を含む、AI ソフトウェア開発のエコシステム全体にわたる協働の取り組みから生まれた」と述べている。この形式について書いているのであって公開しているわけではない [[ScholarlyArticle/configuring-agentic-ai-coding-tools]] は、これを [[Organization/openai]] が導入したものと説明している。サイトは、この形式が現在は Linux Foundation 傘下の [[Organization/agentic-ai-foundation]] によって管理されていると述べている。

### 実証的な普及

同研究は、三つの方向からの証拠に基づき、AGENTS.md を台頭しつつある相互運用可能な標準と同定している。ファイル数では CLAUDE.md にわずかに及ばない——1,572ファイル（32.3%）対1,661（34.2%）——が、コンテキストファイルを含む2,634のリポジトリのうち1,069（40.6%）に現れており、CLAUDE.md の1,195（45.4%）に対している。作成順では、両方が存在する場合、通常は CLAUDE.md が先に現れ、AGENTS.md が後から追加される。そして参照のパターンでは、大差をつけて最も参照されるコンテキストファイルであり、368件の被参照を受けている。観察された単一で最も強いパターンは CLAUDE.md が AGENTS.md を指すもので、311回生じている。

著者らはこれを、ベンダーの指令によるのではなく開発者の実践と互換性の必要に駆動されたボトムアップの収束と読み、copilot-instructions.md から始まったリポジトリが、Copilot がすでに主要なコンテキストファイル形式のすべてに対応していたにもかかわらず、後に CLAUDE.md や AGENTS.md を導入することが多いと指摘している。そして、すでに Cursor と Codex が提供している AGENTS.md のネイティブ対応が、ツールベンダーにとって最低限の期待になりうると示唆している。同研究の2026年2月時点のスナップショットでは、Claude Code はまだこれに対応していなかったと著者らは指摘しており、CLAUDE.md が先に現れて AGENTS.md が後から追加されるという作成順のパターンの説明の一つとして、これを挙げている。

そこから導かれる実務者への案内は次のようなものである。複数のツールに依存する開発者は、共有された設定のベースラインとして AGENTS.md ファイルを保守し、ツール固有のファイルは共有の中核ファイルを参照するアダプタとして働かせることを検討すべきである。同じ研究は、一つのリポジトリで複数のコンテキストファイルを重ねることが、成果物間で冗長あるいは矛盾する指示を生むリスクを高めるとも警告している。

実務者の資料は、同研究が統計的に導いたのと同じ相互運用性の言葉でこのファイルを枠づけている。[[Person/arun-gupta]] の [[PresentationDigitalDocument/spec-driven-development-using-coding-agents]] もこれを「エージェントのための README」——AI 向けの指示の明確で予測可能な場所——と説明し、その価値として、セッションをまたいでエージェントがプロジェクトを覚えていられるよう持続するコンテキスト、多くのエージェントで機能する一つのファイル、新しいセッションが直ちに生産的に始まるオンボーディング時間ゼロ、そして一般的な誤りが起きる前に防ぐ組み込みのガードレールを挙げている。同スライドが提案する仕様駆動のワークフローにおいて、`AGENTS.md` はエージェントが*知っておくべきこと*を担い、*すべきこと*を担うスキルとも、何が作られつつあるかを担う実装計画とも区別される。

### OpenAI による説明

[[BlogPosting/introducing-codex]] における OpenAI 自身の説明は、上の実証的な説明より簡潔であり、それらとは分けて扱う価値がある。AGENTS.md ファイルは「README.md に類する text ファイル」でリポジトリ内に置かれ、そこで開発者はエージェントに、コードベースをどう渡り歩くか、テストにどのコマンドを走らせるか、プロジェクトの標準的な慣行にどう従うのが最善かを伝えられる。OpenAI はこの依存関係を類比で枠づけている。「人間の開発者と同様に、Codex のエージェントは、設定された開発環境、信頼できるテストのセットアップ、明確なドキュメントが与えられたときに最も良く働く」——一方で、自社の `codex-1` モデルは AGENTS.md ファイルやカスタムのスキャフォールドがなくてもコーディングの評価や社内ベンチマークで強い性能を示すとも主張しており、それゆえこのファイルは必須ではなく助けとして提示されている。

同じ記事は、このファイルがツールにとどまらずモデルの振る舞いにまで及ぶことも示している。OpenAI は `codex-1` のシステムメッセージを公開し、その透明性がなぜ有用かの例として、システムメッセージがエージェントに AGENTS.md ファイルに記されたすべてのテストを実行するよう促していること——時間の足りないユーザーはそれを飛ばすよう明示的に頼める——を挙げている。

### エージェントの効率に対する測定された効果

[[ScholarlyArticle/on-the-impact-of-agents-md-files]] は、このファイルがどれだけ普及しているかではなく、それが何をもたらすかについての初の統制された測定である。その設計は、10のリポジトリから実際にマージされた124件のプルリクエストをマージ前の状態で再現し、1タスクにつきエージェントを2回走らせる——一度はそのコミット時点で存在したリポジトリ自身のルートの `AGENTS.md` を伴って、もう一度はその1ファイルを削除して——というものであり、リポジトリ、タスク、コードベースの状態、エージェントの設定はすべて固定される。

ファイルが存在する場合、完了までの実時間の中央値は28.64% 減少し（98.57秒から70.34秒へ）、出力トークンの中央値は16.58% 減少する（2,925から2,440へ）。いずれの差も統計的に有意と報告されている。二つの効果は形が異なり、著者らはそれを分けて読んでいる。出力トークンの節約は、平均が中央値よりはるかに大きく改善することから、ごく少数の非常に高コストな実行に集中している。一方、実時間の改善は「タスク完了の高速化への全般的なシフト」を示すのに十分なほど一様である。入力トークンとキャッシュされた入力トークンはほとんど動かず、その中央値はわずかに逆方向へ動く。

その機構についての著者ら自身の仮説は、このファイルが「リポジトリの構造と慣習を前もって記述し、エージェントが探索的な渡り歩きによってプロジェクトの構成を推測する必要を減らす」というものであり、彼らはこれをトレース解析を待つ推測として明示している。

この研究が測るのは効率だけである。意味的な正しさや、マージされたプルリクエストとの機能的な等価性を評価することは範囲外であると明示しており、代わりにサンプリングした50タスクについて、エージェントが中断ではなく非自明な変更を生み出したことを確認する手作業の健全性チェックを行っている。したがって知見は、ルートの指示ファイルが小さな実タスクにおいてエージェントをより安く速くするというものであって、作業をより良くするというものではない。[[DefinedTerm/context-files]] で要約されている agentfiles の研究——エージェントがコンテキストファイルの指示に*より多くの*推論トークンを費やしながら解決率を改善しないと報告するもの——と並べても、両者は直接には矛盾しない。異なるタスク分布において異なる量を測っており、どちらもコストと正しさを同時には測っていない。

### 大きさを定める——百科事典ではなく目次

[[BlogPosting/survey-of-development-workflows-in-the-coding-agent-era]] は、収束しつつある大きさの指針を集めている。これらのファイルを百科事典ではなく目次として扱うべきで、60〜150行を目安とするという OpenAI の枠づけ、60行以下というより厳しい HumanLayer の推奨、そして40KB を8KB へ圧縮しつつ100% の通過率を維持したという Vercel の報告を伝えている。いずれの場合も推奨されるパターンは [[DefinedTerm/progressive-disclosure]] である——最上位のファイルにはファイルへのポインタを置き、詳細はサブフォルダのコンテキストファイル、スキル、外部ドキュメントへ分割する。

同記事は、必要に応じてすべてを読み込むやり方に逆らう結果も伝えている。Next.js 16 に関する Vercel のケーススタディでは、8KB の `AGENTS.md` のドキュメント索引が100% の通過率に達し、53% のスキルベースの検索を47ポイント上回った。説明として述べられているのは、常に利用可能な受動的コンテキストがオンデマンドの検索に勝ったということである。これは一つのチームによる一つのコードベース上の評価であって、一般的な知見ではない。

同記事はまた、これらのファイルが実務でどう分業しているかも示している。`AGENTS.md` は何をすべきかについてのツール非依存の普遍的な要約、`CLAUDE.md` は Claude Code 固有の運用上の指示、そして任意で `SOUL.md` がエージェントの人格を担う。さらにガバナンス上の節目——2025年8月に OpenAI が公開したこの形式が、2025年12月に Linux Foundation の [[Organization/agentic-ai-foundation]] へ移管されたこと——を、6万を超えるオープンソースプロジェクトという普及の数値、および Claude Code、Codex、Cursor、Copilot、Gemini CLI、Windsurf、Aider にわたる対応状況とともに記録している。

### ルーターのパターン

上の大きさの指針がファイルの長さを述べるのに対し、[[DefinedTerm/dotagents]] はそれが何を*含む*べきかを提案する。条件付きのポインタ以外は何も含まない、というものである。[[BlogPosting/dotagents-standard-agent-skill]] は、このファイルが常に読まれる痩せた**ルーター**となり、より深いコンテキストをどこに探すかをエージェントに伝えることを役割とし、重たい素材は隠しディレクトリ `.agents/` へ移されて種類——rules、context、memory、personas、skills、specs、logs——ごとに整理される様子を説明している。

これらのファイルがなぜ肥大するのかについての同記事の診断は、修正策とは別に記録する価値がある。それは長さの上限だけでは持ちこたえない理由を説明するからである。追加された一つ一つは書かれた日にはその場所を勝ち取っていた——エージェントが列名を繰り返し取り違えたためのスキーマの抜粋、派生した文書の出来が悪かった後の語調に関する一段落、誰も高い代償を払って学び直さずに済むよう記された CI の苦い傷跡——のであり、「失敗モードは累積的」で、最後には CSS を編集しながらデータベースのスキーマを読むエージェントに行き着く。

同記事が譲らない機構上の要件は条件性である。ルーティングの規則はトリガーを名指しし、行動を表す動詞を伴わねばならない。そうすることでエージェントは、そのポインタがいつ当てはまるのかと、それをどうすべきかの双方を知る。無条件に「常にすべてを読め」と言うルーターは「モノリスをディレクトリ一つ分だけ深いところに作り直すにすぎない」。
