AGENTS.md は慣例的にリポジトリのルートに置かれる Markdown ファイルであり、プロジェクト固有の規約や制約を伝えるために、
プロンプトのたびに AI コーディングエージェントのコンテキストへ読み込まれる。一般的なコーディングエージェントは
`/init` 系のコマンドでこれを自動生成でき、そのコマンドはコードベースを走査してディレクトリ構造・技術スタック・テストの
規約の説明を生成する。

この形式のプロジェクト自身は、それを一行で「コーディングエージェントを導くためのシンプルでオープンな形式」と述べ、
エージェント向けの README だと言い換えている。AI コーディングエージェントがプロジェクトで作業するのを助けるコンテキストと
指示を与えるための、専用の予測可能な置き場所である。これは `agentsmd/agents.md` リポジトリから MIT ライセンスで公開されて
おり、プロジェクトの目標を説明するウェブサイト <https://agents.md/> が併設され、リポジトリにはテクニカルチャーターが
置かれている。プロジェクトが同梱する最小の例は、3 つの `##` セクション——開発環境のヒント、テストの手順、プルリクエストの
手順——を持つ素朴な Markdown ファイルであり、その中身はコードベースについての散文ではなく、具体的なコマンドと規約
（どのパッケージマネージャのコマンドを使うか、CI のプランがどこにあるか、必須のタイトル形式、コミット前に走らせる
チェック）である。

## 由来と名称

ある採用者の記述は、このファイルが今の名前を持つに至った経緯を埋めてくれる。
[[BlogPosting/taming-agents-in-the-mercari-web-monorepo]] は、あるチームがこの標準を、まだ単数形の `AGENT.md` だった時点で
見つけたことを記録している——そこでは Sourcegraph が AmpCode プロジェクトを通じて提案した RFC として述べられている——
そして既存の Cursor と Claude のルールを 1 つのそうしたファイルへ統合した一方、チームの他のメンバーはその RFC がどれだけ
持つのかを訝しんでいた。記事はその後、OpenAI が agents.md ドメインを確保したことを報告している。それはこの標準が複数形の
表記へ移るのを阻んでいた唯一のものだったと述べられており、また OpenAI 自身の Codex がすでに使っていたファイル名でも
あった。記事は、この標準がそのチームの使うツール群の間ではるかに広く受け入れられるようになったことを OpenAI の後ろ盾の
おかげだとし、チームは複数形の形式を単一の信頼できる情報源として採用した。これは採用者として観察したことについてのある
チームの記述であって、この標準がどう設計されたかについての当事者の記述ではなく、そこで言及されている発表そのものはこの
wiki の出典には含まれていない。

この記事はまた、ツールごとのルールファイルをすでに持っていたコードベースでこれを採用したことの実際的な帰結も述べている。
`CLAUDE.md` をはじめとする多くのルールファイルは、単にメインのファイルへのシンボリックリンクになった。こうして既存の
形式は、内容を二重に保守することなく動き続けた。

後年の記述は、この標準が最終的にどこへ落ち着いたかを補っている。
[[BlogPosting/division-of-labor-in-ai-instruction-files]] は Sourcegraph の Amp チームをその出発点として挙げ——どこで
始まったかについて上の採用者の記述と一致している——その後 OpenAI、Google、Cursor、Factory らによって共同で推進され、
2025 年 12 月に Linux Foundation へ寄贈されたと述べている。つまり、あるベンダー 1 社の RFC が続くのかという、採用者の
記述が開いたままにした問いは、この標準を単一ベンダーの手の外へ移すことによって答えられた。この記事はまた、シンボリック
リンクという取り決めを、あるチームの間に合わせではなく、形式プロジェクト自身の推奨パターンとして挙げている。Claude Code
は `AGENTS.md` ではなく `CLAUDE.md` を読むので、`AGENTS.md` を実体のファイルとし、`CLAUDE.md` をそれへのシンボリック
リンクにすることが推奨されている。この記事は `CLAUDE.md` を、単に Claude 固有の `AGENTS.md` だと特徴づけている。

## 用法

出典で要約されている引用研究によれば、本当に発見不可能で運用上重要な事実（たとえば「パッケージ管理には `uv` を使う」）を
記録した人間が書いた `AGENTS.md` は、エージェントの振る舞いを測定可能なほどに変え、タスクの成功率を改善した。一方、自動
生成されたファイル——典型的には、エージェントがリポジトリを直接読めば他の方法でも発見できるコードベースの概観——は、
成功率を改善することなくコストを加え、場合によっては成功率を下げていることが見出された。出典はまた「アンカリング効果」に
ついても述べている。いったんある技術やパターンがこのファイルに書かれると、それは以後すべてのプロンプトでコンテキストに
居座り続け、もはや現行の規約でなくなった場合でもエージェントをそちらへ偏らせうる。

同じ著者の別の記事は、OpenAI の Codex のドキュメントが、どのテストを走らせるか、リントのルール、依存関係のポリシー、
ドキュメントの要件についてエージェントに一貫した期待を持たせるために `AGENTS.md` ファイルを推奨している、と引いている
——そこでは、新入社員がコードを書き始める前に規約の地図を渡してオンボーディングすることになぞらえられている。この記事は
また、`AGENTS.md` と関連チェックリストの更新を、繰り返し可能なオーケストレーションループの最後の「振り返り」ステップと
して位置づけており、それによって次の実行がより賢く始まるとしている（[[BlogPosting/your-ai-coding-agents-need-a-manager]]）。

GitHub はこのファイルを、VS Code のカスタムエージェントの設定面の一つとして採用し、[[SoftwareApplication/agent-hq]] と
あわせて発表した（[[BlogPosting/introducing-agent-hq]] を参照）。そこでは `AGENTS.md` ファイルを、明確なルールと
ガードレールを設定するためのソース管理下の文書として述べており——例として挙げられているのは「このロガーを優先せよ」
「すべてのハンドラにテーブル駆動テストを使え」である——その要点は、毎回プロンプトし直すことなく Copilot の振る舞いを
形づくることだとしている。

[[SoftwareApplication/github-copilot-code-review]] についての GitHub のドキュメントは、このファイルを 4 つのカスタマイズ
面の中に位置づけ、それらをスコープで区別している。これは、いつこれを使うべき*でない*かについて、この wiki が保持する中で
最も明快なベンダーの言明である。`.github/copilot-instructions.md` は Copilot 固有の、リポジトリ全体に常時効くルールを
保持する。`.github/instructions/` 以下のパス固有の `*.instructions.md` ファイルは、特定のパス・ファイル種別・ディレクトリに
対して常時効くルールを保持する。リポジトリのルートから読まれる `AGENTS.md` は、AI ツールやエージェントをまたいで共有される
ことを意図した、常時効くルールを保持する。そして `.github/skills/` 以下のスキルは、必要に応じて、あるいは関連する場面で
実行されるタスク固有のワークフローを保持する。GitHub はこの区別を 4 つの経験則へ圧縮している——「Copilot よ、このリポジトリ
については常にこれを知っておけ」「Copilot よ、これらのパスで作業するときは常にこれを知っておけ」「どのエージェントであれ、
常にこれを知っておけ」「必要なときにこれをせよ」——したがって、この説明において `AGENTS.md` を際立たせているのは
リポジトリ内でのスコープではなく、ツールをまたぐ到達範囲であり、それはまさに上の採用者の記述がこれを選んだ理由でもある。
同じドキュメントは、プルリクエストのレビュー中、Copilot はカスタム指示・エージェント指示・スキルをベースブランチではなく
ヘッドブランチから読むと述べており、したがってそれらへの変更は、先にマージすることなく、それを導入するプルリクエストの中で
テストできる。

[[ScholarlyArticle/agentic-software-engineering-foundational-pillars]] は、`CLAUDE.md`、`.clinerules`、`AGENT.md` といった
プロジェクトレベルの設定ファイルを、あらゆるエージェントタスクの前に「制度的知識」を読み込ませる初期の草の根的な実践として
論じている——スタイルガイド、アーキテクチャ上の制約、得られた教訓を、AI のチームメイトのために継続的に改善される「従業員
ハンドブック」へと成文化するものである。この論文はこの実践を、自らが形式化を提案する [[DefinedTerm/mentorscript]] の初期の
例と位置づけ、そうしたファイルが何を含むべきか、また適切な詳細度がどれほどかについてコミュニティに合意はないと述べ、今後の
研究にはこの目的のためのより形式的な言語を定義することだけでなく、これらのファイルを効果的に使うためのベストプラクティスを
発見することも含まれると論じている。

ある実践者の記述は、他のどれもこの深さでは述べていない用途にこのファイルを充てている。エージェントが読むコンテキストとして
だけでなく、*手順*そのものが住まう場所としてである。
[[BlogPosting/human-intent-ai-implementation-codex-workflow]] は、プロジェクトの初期化時に `AGENTS.md` を、そこで言うところ
の AI のメモリとして書き、プロジェクトの概要、フォルダ構成、参照すべき文書、作業ルール、現在のステータスを保持させている。
この記事がそこに記録している 4 つの作業ルールは、行動の前に計画し承認を得てから実行すること、計画や提案の際には 3 つの選択肢
を提示すること、実装の前に該当する仕様を確認し更新すること、そして完了時にストーリーごとのコンテキストファイルを更新する
ことである。それらと並んで、自動生成のルールそのもの——あるルーチンを起動する語句、実行する手順、生成すべきフォルダと
ファイルの構成、できあがるファイルの形——も格納されている。この記事が主張する帰結は、エージェントにではなくプロンプトに
関わるものである。配置と手順がすでに書き下されているので、プロンプトは出力パスを列挙する代わりに要件を述べる（「`vision.md`
を読んでユーザーストーリーを生成せよ」）だけで済む。そして著者の述べる経験則は、これらのルールファイルを埋めれば埋めるほど
プロンプトは単純になり、出力はよくなる、というものである。これはサンプルプロジェクト上での一人のエンジニアの実演であり、
その裏付けとなる測定はない。

## 適用される場面

出典はよい `AGENTS.md` を、恒久的な設定ではなく、コードベースの摩擦を記録した生きた記録として位置づけている。エージェントが
同じ間違いを繰り返すときに一行を加え、その根底にある問題（紛らわしいディレクトリ構造、何かを自動的に捕まえるべきビルド
パイプライン）が代わりに修正されたら取り除く。実際的な判定基準は次のように述べられている。エージェントがコードを読めば
その事実を発見できるのなら、それはこのファイルに属さない。出典はまた、単一で静的なリポジトリルートのファイルを、ある複雑さを
超えたコードベースにとっては構造的な限界とみなしている。平坦な指示の集合は、どんな種類のタスクが走っているかによって内容を
条件づけることができないからである。そして意図された置き換えとして、自動的に保守される、ディレクトリ単位あるいはモジュール
単位のファイル階層を提案している。さらに、この考えをより精緻にした 3 層版（最小限のルーティングファイル、タスク単位のスキル
ファイル、保守用のサブエージェント）も述べたうえで、そのより完全なアーキテクチャをきれいに構築するために必要なライフサイクル
フックを、主要なコーディングエージェントはまだどれも公開していないと注記している。

**この wiki の出典は、このファイルに何が属するかについて一致していない。** 上の最初の出典は発見可能性による判定基準を置く
——エージェントがコードを読んで得られる事実は一行を得るに値しない——これは、LLM が生成したコンテキストファイルがタスクの
成功率をわずかに下げつつコストを大きく上げることを見出した研究の、実際的な教訓として著者が引き出したものである。上の実践者の
記述は、フォルダ構成、作業ルール、自動生成の手順をそこに格納しており、それはその判定基準が認めるよりもかなり多い。そして
逆方向のことを論じている。ルールファイルが充実しているほど、プロンプトは単純になり、出力はよくなる、と。両者は同じものを
測っているのではなく——一方はタスクの成功率についての実験結果を報告し、他方はサンプルプロジェクト上での一人のエンジニアの
作業方法である——どちらも相手に向き合っていないので、ここでは調停せず両方を記録する。両者を分かつのは目的かもしれない。
発見可能性による判定基準はエージェントが何を*知る*必要があるかについてのものであり、起動されるために書かれた手順は
エージェントが何を*する*べきかについてのものであって、後者はコードをいくら読んでも得られない。

あるチームは、最初の出典が提案する階層に近いものを実践に移しており、その形は記録に値する。それはこの不一致を解決するのでは
なく、迂回しているからである。[[BlogPosting/taming-agents-in-the-mercari-web-monorepo]] では、ルートの `AGENTS.md` は
それ自体ほとんど何も保持していない。その各セクションは見出しと、`docs/` 以下の個別の文書——ビルドとテストのコマンド、
コードスタイルと標準、プロジェクトアーキテクチャ、認証のパターン、テスト戦略——へのポインタである。記事は、そのリポジトリの
モジュール構造を踏まえてアーキテクチャの文書をとりわけ重要なものとして挙げ、そのコンテキストを省いた場合のコストを、
同じ初期コンテキストを毎回注意深くプロンプトしない限り、ほとんどのツールの出力は開発者が完全に再構成しなければならなくなる、
と述べている。またこの記事は、プロジェクトのデザインシステムを、強調された ALWAYS/NEVER の言い方でエージェントに教えても
いる——コンポーネントはソースファイルからではなく常にデザインシステムのパッケージから import すること、デザインシステムの
コンポーネントやネイティブの HTML 要素にインラインスタイルを決して加えないこと——述べられている理由は、このプロジェクトは
そのデザインシステムに従わねばならず、バイブコーディングされた CSS に頼ることはできないから、というものである。

そうしたファイルを最新に保つことへのこのチームの答えは、それを委譲することである。より上位の設計に大きな影響を持つ
プルリクエストについては、エンジニアが変更セットとルールのフォルダをあわせてエージェントに与えて走らせ、モデル自身に
ルールへの修正を提案させるか、コード中の不整合を指摘させる。これを自動化する理由として述べられているのは、別のフォルダに
ある局所的でない Markdown ファイルを編集するのは、あるタスクに集中しているエンジニアにとって煩わしいから、というもので
あり、記事はその結果を自己強制的で自己更新的なドキュメントと呼んでいる。これはこのチーム自身の特徴づけであり、測定を伴わずに
述べられたものである。そして執筆時点で構築中だったもの——すべてのプルリクエストでルールから逸脱したコードを指摘する
エージェント——はまだ出荷されていなかった。

長時間稼働するエージェントについての後年の記事は、同じファイルに、長時間あるいは夜通しのコーディングジョブを走らせる開発者の
ための設計原則をさらに与えている。`AGENTS.md` をパイロットのチェックリストのように扱い、短く保ち、どの一行も実際に起きた
過去の失敗によって獲得されたものにせよ、というものである。この記事は別に、Anthropic 自身の科学計算向けエージェントが
`CLAUDE.md` を同様の役割で使っていることも述べている。エージェント自身が学びながら編集していく生きた計画として、そして
持ち運び可能な実験ノートとして働く `CHANGELOG.md` と組み合わせて、である（[[DefinedTerm/ralph-loop]] を参照）。

こうしたファイルが実際にどう解釈されるかについての最も明示的な言明は、ベンダー側から来ている。OpenAI は codex-1 の
システムメッセージを [[BlogPosting/introducing-codex]] の付録として公開しており、その一節はエージェントが従うルールとして
書かれた `AGENTS.md` の仕様である。そこではエージェントに次のように告げている。これらのファイルはコンテナのファイル
システムのどこにでも現れうる——典型的な場所はルート、ホームディレクトリ、および git リポジトリ内のさまざまな場所であり、
したがってリポジトリの中にある必要すらない。あるファイルのスコープは、それを含むフォルダを根とするディレクトリツリー全体
である。最終的なパッチで触れられるすべてのファイルについて、エージェントはそのスコープにそのファイルを含むあらゆる
`AGENTS.md` に従わねばならない。コードのスタイル・構造・命名についての指示は、ファイルが別段の定めをしない限りそのスコープ内
でのみ適用される。指示が衝突する場合はより深くネストしたファイルが優先する。そしてプロンプト中の直接のシステム・開発者・
ユーザーの指示は、このファイルより優先する。さらに 2 つの条項は、どこに適用されるかではなく、このファイルが何を要求できるかに
ついてのものである。ファイルが指定するプログラム的なチェックは、すべてのコード変更の後に——ドキュメントのような単純な変更に
ついてさえ——すべて実行されねばならず、それらが通ることを確認する最善の努力を払わねばならない。そしてプルリクエストの
メッセージについてファイルが与える指示は尊重されねばならない。OpenAI は、開発者がモデルのデフォルトの振る舞いを理解し、
Codex を自分たちのワークフローに合わせられるようにするためにシステムメッセージを公開したと述べ、そうした変更の例として、
時間がないときにそれらのテストを省くことを挙げている——したがって優先順位のルールは、単なる衝突解決の細目ではなく、ユーザーが
拠り所にできるものとして提示されている。

## セキュリティ上の考慮

このファイルを有用にしている性質は、同時にそれを標的にもしている。エージェントは設計上これらのファイルを信頼できる
プロジェクトのコンテキストとして読み込むので、作業ツリーにそれを書き込めるものは何であれ、その資格を帯びた指示を供給できる。
NVIDIA の AI レッドチームの報告は、これを Codex に対して実証した。悪意ある Go の依存関係が、どんな依存関係でもそうできる
ように、ビルドステップの最中に実行され、ユーザー自身の要求より優先すると謳う指示を持つ `AGENTS.md` を書き込んだところ、
エージェントは与えられたタスクよりもそちらに従った。報告は、このファイルの信頼モデルは欠陥ではなく意図的なものであること、
そしてこの攻撃は侵害された依存関係——それはすでにコード実行を含意する——を前提としていることを明言している。したがって
これが付け加えるのは、そのアクセスを得る新しい手段ではなく、そのアクセスの新しい用途である。

提案されている緩和策のうち、このファイル自体に向けられたものは、その内容ではなく完全性に関わるものである。エージェントが
読み書きしてよいファイルを制限すること、エンドポイントセキュリティや集中設定管理を用いて設定ファイルに特化した完全性制御を
強制すること、そして予期せぬファイル変更に対してアラートを上げることである。報告はまた、このファイルとはまったく関係のない
緩和策も提案している。依存関係のバージョンを厳密にピン留めしパッケージをスキャンすること、エージェントが生成したプル
リクエストを専用のセキュリティエージェントで監査すること、そしてモデル自体をスキャンしガードレールで囲むことである。攻撃
そのものについては [[DefinedTerm/indirect-agents-md-injection]] を参照。

これは上で述べた優先順位のルールにも関わる。codex-1 の仕様は、直接のシステム・開発者・ユーザーの指示がこのファイルより優先
すると述べている。しかし報告された攻撃では、エージェントは逆を謳う指示を持つファイルに従って行動した。つまりその順序は、
注入されたファイルが争えないものではなく、文書化されたデフォルトにすぎない。
