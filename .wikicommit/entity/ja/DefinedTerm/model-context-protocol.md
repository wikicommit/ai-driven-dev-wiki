Model Context Protocol（MCP）とは、異種混在の実行環境にまたがって、AI エージェントが外部ツールをどのように発見し呼び出すかを標準化するクライアント・サーバー型のプロトコルである。MCP サーバーはツールのメタデータ — 名前、入力スキーマ、説明 — を公開し、エージェントは接続された複数のサーバーにまたがってそれを問い合わせることができる。エージェントがツールを選択すると構造化されたリクエストを発行し、サーバーがそれを実行して結果をシリアライズされた形式で返す。

## 用法

[[ScholarlyArticle/from-determinism-to-delegation]] は、このプロトコルの起源と役割の構造を説明している。異種のモデルを独自のツールに接続するには、歴史的に個別仕様のコネクターが必要であったが、MCP — 同論文はこれを 2024 年後半のものとしている — は N × M 通りのカスタム統合を単一のクライアント・サーバー間の契約で置き換える。同論文は 3 つの役割を挙げている。同意とポリシーを管理する **MCP Host**、個々のサーバーに接続する **MCP Client**、そして読み取り専用の **Resources**、JSON Schema で検証され人間の承認によって制御される実行可能な **Tools**、再利用可能な **Prompts** を公開する **MCP Server** である。標準化されたツールプロトコルがなぜ重要かについての同論文の見方は構造的なものである。すなわち、それこそがエージェントに、古典的なソフトウェアエンジニアリングが提供する決定的な API を発見し、それに基づいて行動することを可能にするものであり、同論文はこれを 2 つの分野の共生における技術的な継ぎ目と呼んでいる。

MCP はツールのインターフェースを標準化するが、どれだけのメタデータと出力をモデルに公開しなければならないかは規定しない。既存の実装の大半が用いる従来型の（コンテキスト結合型の）実行モデルでは、ツールのメタデータ、スキーマ、出力はすべてエージェントの推論コンテキストへ直接送り込まれ、ユーザー入力や途中の推論と領域を奪い合う。接続されたサーバーと利用可能なツールの数が増えるにつれ、このメタデータと出力がコンテキストウィンドウに占める割合は増大しうるため、推論に使える容量が減り、広いコンテキストを要する分析タスクでの性能が低下する。これは、サーバーやツールを追加してもこのアーキテクチャでは克服できないスケーラビリティ上の限界である。

[[DefinedTerm/code-execution-mcp]] は、ツールのオーケストレーションをエージェントのコンテキストウィンドウから切り離すことでこの限界に対処するために導入された、代替の実行モデルである。
