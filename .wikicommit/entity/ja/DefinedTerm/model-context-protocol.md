Model Context Protocol（MCP）とは、AI アプリケーションを外部システム——ローカルファイルやデータベースといったデータソース、検索エンジンや計算機といったツール、特化したプロンプトといったワークフロー——へ接続するためのオープンな標準である。[[Organization/anthropic]] は2024年11月25日にこれを発表し、問題を孤立の問題として枠づけた。洗練されたモデルでさえ「情報のサイロとレガシーシステムの背後に閉じ込められて」おり、新しいデータソースはどれも「それ自身の個別の実装を必要とし、真に接続されたシステムを規模化することを難しくしている」——Wikipedia の説明が、Anthropic が述べたとする「N×M」のデータ統合問題と表現するものである。MCP はそれらの断片化した統合を単一のプロトコルに置き換え、開発者はエージェントに MCP を一度実装すれば、統合のエコシステム全体へのアクセスを得られる。公式ドキュメントの類比は AI アプリケーションのための USB-C ポートである。USB-C が電子機器を接続する標準化された方法を提供するのと同じように、MCP は AI アプリケーションを外部システムへ接続する標準化された方法を提供する。

## 用法

### アーキテクチャ

このプロトコルは三つの役割を区別する。**ホスト**は接続を開始する LLM アプリケーション——AI アシスタント、IDE、ワークフロー自動化ツール——である。必要とする各サーバーに対して、ホストはそのサーバーと通信する専用の**クライアント**を作る。**サーバー**は能力を公開するサービスである。ホストとクライアントは通常同じマシンで動作し、サーバーはローカルでもリモートでもよい。各クライアント・サーバー接続は、初期化と能力のネゴシエーションから始まる専用のステートフルなセッションであり、メッセージには JSON-RPC 2.0 を用いる。トランスポートはローカルプロセスには stdio、ネットワーク通信には Streamable HTTP である。HTTP 上の Server-Sent Events は仕様の 2025-06-18 改訂で非推奨となった。

仕様は、どちら側が提供するかによって能力を分類している。サーバーは **Resources**（ユーザーまたはモデルのためのコンテキストとデータ）、**Prompts**（ユーザー向けのテンプレート化されたメッセージとワークフロー）、**Tools**（モデルが実行する関数）を提供しうる。クライアントは **Sampling**（サーバー起点のエージェンティックな振る舞いと再帰的な LLM とのやり取り）、**Roots**（動作すべき URI またはファイルシステムの境界に関するサーバー起点の問い合わせ）、**Elicitation**（ユーザーへのさらなる情報を求めるサーバー起点の要求）を提供しうる。追加のユーティリティは設定、進捗の追跡、キャンセル、エラー報告、ログを扱う。

動作としては、クライアントが自らのサーバーに提供するツールとリソースの一覧を求め、サーバーは各能力の自然言語による説明と期待される呼び出し形式を返す。その情報が LLM に与えられ、モデルがツールを必要とするとホストが該当するクライアントにそれを呼ぶよう指示し、返ってきた結果を会話へ注入する。

仕様は、プログラミング言語の対応が開発ツールのエコシステム全体にわたってどう追加されるかを標準化した Language Server Protocol から着想の一部を得ていると述べている——MCP は同じ仕方で、追加のコンテキストとツールが AI アプリケーションのエコシステムへどう統合されるかを標準化する。Wikipedia の説明によれば、それ以前の間に合わせの手法は似た問題を解いてはいたが、ベンダー固有のコネクタを必要とした。[[Organization/openai]] の2023年の function-calling API と ChatGPT のプラグインの枠組みである。

### 配布とエコシステム

Anthropic の発表は三つの構成要素を伴っていた。仕様と SDK、Claude Desktop アプリにおけるローカル MCP サーバーの対応、そして Google Drive、Slack、GitHub、Git、Postgres、Puppeteer 向けの構築済みサーバーを備えた MCP サーバーのオープンソースリポジトリである。プロトコルは Python、TypeScript、C#、Java を含む言語の SDK とともに、サーバー実装の例を添えて公開された。`modelcontextprotocol/modelcontextprotocol` リポジトリは仕様、プロトコルのスキーマ、公式ドキュメントを保持し、MIT ライセンスのもとにあり、スキーマをまず TypeScript で定義しつつ、より広い互換性のために JSON Schema としても公開している。ドキュメントサイトは Mintlify で構築されている。

発表で名指しされた初期の採用者は Block と Apollo、そして開発ツール企業の Zed、Replit、Codeium、Sourcegraph であった。Block の最高技術責任者である Dhanji R. Prasanna は、MCP のようなオープンな技術を「AI を現実世界のアプリケーションへつなぐ橋」と説明したとして引用されている。Wikipedia が報告する後の採用には、OpenAI が ChatGPT デスクトップアプリを含む自社製品全体に統合したうえで2025年3月に MCP を公式に採用したこと、2025年9月に ChatGPT アプリへ MCP 対応を追加したこと、Microsoft Semantic Kernel および Azure OpenAI との統合、そして MCP サーバーの Cloudflare への配備が含まれる。公式ドキュメントは対応クライアントとして Claude、ChatGPT、Visual Studio Code、[[SoftwareApplication/cursor]]、MCPJam を挙げている。[[DefinedTerm/ai-assisted-software-development]] に限って言えば、IDE、Replit のようなコーディングプラットフォーム、Sourcegraph のようなコードインテリジェンスのツールが、AI コーディングアシスタントにプロジェクトの文脈へのリアルタイムなアクセスを与えるために MCP を採用した。

Wikipedia はガバナンスと規模に関する二つの進展を記録している。2025年12月、Anthropic は MCP を [[Organization/agentic-ai-foundation]] へ寄贈した。これは Anthropic、Block、OpenAI が共同で設立し他社の支援を受ける、Linux Foundation 傘下の指定基金である。2026年4月には同財団がニューヨーク市で MCP Dev Summit North America を開催し、およそ1,200名を集めた。同じ月に Salesforce の Headless 360 プラットフォームが顧客とエージェントのやり取りを MCP 経由で流しはじめ、5月下旬に Salesforce はローンチ以来450万回の MCP 呼び出しを処理したと報告した。mcp-ui の上に構築された公式の拡張である MCP Apps は、ダッシュボード、フォーム、データ可視化といった対話的なユーザーインターフェースをサーバーからホストアプリケーションへ届けることを標準化する。テキストと構造化データに限られる基本仕様が扱っていない領域である。

2025年11月までの Anthropic 自身の特徴づけでは、コミュニティは数千の MCP サーバーを構築しており、主要なプログラミング言語すべてに SDK が存在し、業界は MCP をエージェントをツールとデータへ接続する事実上の標準として採用していた。

### セキュリティ

仕様は、MCP が「任意のデータアクセスとコード実行の経路を通じて強力な能力を可能にする」ことを明示し、実装者に向けて四つの鍵となる原則——ユーザーの同意と制御、データのプライバシー、ツールの安全性、LLM のサンプリングの制御——を掲げている。ツールの安全性のもとでは、ツールは任意のコード実行を表すのであり、「アノテーションのようなツールの振る舞いの説明は、信頼できるサーバーから得られたものでないかぎり、信頼できないものとみなすべきである」と述べている。また、MCP 自体はこれらの原則をプロトコルの水準で強制できないことを認め、代わりに実装者は堅牢な同意と認可のフローを構築し、セキュリティ上の含意を文書化し、アクセス制御とデータ保護を実装し、セキュリティのベストプラクティスに従い、機能の設計においてプライバシーの含意を考慮**すべきである（SHOULD）**と述べている。

独立した分析はすぐに続いた。Wikipedia は、2025年4月にセキュリティ研究者が分析を公開し、プロンプトインジェクションや、他の接続されたツールを通じたデータの持ち出しを許す汚染されたツールを含む、MCP の複数の未解決のセキュリティ問題があると結論したことを記録している。Microsoft 自身のガイダンスは、名指しされる二つのリスクを [[DefinedTerm/indirect-prompt-injection]] と、その部分集合としての [[DefinedTerm/tool-poisoning]] として枠づけている。2026年1月8日に CoSAI のプロジェクト運営理事会によって承認されながら依然として「Status: Draft」と記されている [[Report/model-context-protocol-security]] は、40近い脅威を3階層にわたる12のカテゴリへ整理し、MCP が既存の AI リスクのフレームワークとは異なる脅威モデルを必要とすると論じている。それらのフレームワークは構成要素があらかじめ定義されたロジックに従って予測可能に振る舞うと前提しているのに対し、MCP は「自然言語入力によって振る舞いが形作られるエージェントである LLM を、セキュリティ上重大な意思決定の中心に置く」からである。

### 学術的な分析

二つの査読者向けのサーベイが、MCP を採用すべきツールではなく研究の対象として扱っており、いずれもセキュリティを通じてそこに接近している。

[[ScholarlyArticle/mcp-landscape-security-threats]]（2025年10月）は、公式ドキュメントと運用上のワークフローから導いた四段階のサーバーのライフサイクル——作成、配備、運用、保守——に分析を基礎づけ、四つの攻撃者類型にわたる16の脅威シナリオを、単一の段階にではなく各リスクの*起点*へ対応づけている。ツールポイズニングやラグプルのような攻撃は「作成段階で持ち込まれ、運用段階で発火する」という理由による。MCP をそれ以前のものから区別するものについての説明は、従来の function-calling の機構とは異なり、MCP が「アクセス制御、能力のネゴシエーション、スキーマの発見をプロトコルのプリミティブとして組み込んでいる」ということである。構造的な診断は、サーバーが独立した開発者によって管理され、ベースラインを監査する中央の権威が存在しないため、エコシステムに中央集権的なセキュリティの監督がないこと、そして MCP が「現在、クライアントとサーバーにまたがる認証と認可の標準化されたフレームワークを欠いている」ことである。

[[ScholarlyArticle/sok-security-and-safety-in-the-mcp-ecosystem]]（2025年12月）は、プロトコルの形についてより強いことを論じている。MCP が Resources（読み取り専用のコンテキスト）、Tools（外部への行動）、Prompts（再利用可能なテンプレート）を、独立したホスト・クライアント・サーバーにまたがって分離しているために、「伝統的な『単一の安全境界』は溶解する」のであり、一つのプリミティブにおける失敗が、別のプリミティブによって実行される有害な行動へと拡大しうる。同論文は、その結果生じるコンテキストと行動の結合を「意味的な攻撃面」と呼び、中心的な主張として、MCP のもとではセキュリティとセーフティの区別が崩れるとしている——ツールのパラメータについての幻覚が侵害を生みうるし、注入された文書は「モデルが正直にではあるが誤って、データベースを削除する権限があると信じている」状態を残しうる。

### 規模におけるトークンのコスト

接続されるツールの数が増えるにつれ、セキュリティとは別の問題が現れる。[[TechArticle/code-execution-with-mcp]] における Anthropic のエンジニアリングの説明は、エージェントのコストとレイテンシを増やす二つのパターンを指摘している。ほとんどのクライアントがすべてのツール定義を前もってコンテキストへ読み込むため、数千のツールに接続されたエージェントは要求を読む前に数十万トークンを処理する。そして中間のツールの結果はすべてモデルを通らねばならないため、データは繰り返しコンテキストを流れ、コンテキストウィンドウを丸ごと超えうる。そこで提案される答えである [[DefinedTerm/code-execution-with-mcp]] は、サーバーを直接のツール呼び出しとしてではなく、エージェントがそれに対してコードを書くコード API として提示する。

### 実務者が実際に何に使っているか

[[BlogPosting/skill-issue-harness-engineering-for-coding-agents]] は、仕様が示唆するより狭い実働の範囲を報告している。「MCP サーバーは主として、ファイル I/O と bash コマンドを超えて能力を拡張するために、コーディングエージェントにツールを差し込むためのものである」。仕様の追加機能——resources、prompts、elicitations——は「一般に MCP クライアントとコーディングエージェントのハーネスにはあまり対応されていない」からである。仕様上のプリミティブと実際に対応されているものとのこのギャップは、三つのプリミティブすべてが働いていることを前提に推論する上のセキュリティ分析にとって重要である。

同記事はまた、ツールのメタデータがどこに着地するかから、プロンプトインジェクションの帰結を直接引き出している。サーバーのツール一覧、説明、引数のスキーマはエージェントのシステムプロンプトへ注入されるため、サーバーはその説明だけでエージェントの振る舞いを形作りうる——それゆえ警告は、信頼していないサーバーには決して接続しないことである。インジェクションとは独立した第二の露出も加えている。STDIO サーバーその他、`npx` や `uvx` を通じてクライアント側で走るものは、ホスト上でコードを実行しうる。

トークンのコストの問題について、同記事は上の知見の実務者版と、ベンダーの説明が強調しない一つの対処法を示している。その助言は、積極的に使っていない多数のツールを提供するサーバーは無効にすること、そして——MCP サーバーが、訓練データによく表れている CLI としてすでに利用可能な機能を重複させている場合、例として GitHub、Docker、大半のデータベースが挙げられている——代わりにその CLI を使うようエージェントに促すことである。モデルはすでにそのツールを知っており、その出力は `grep` や `jq` と組み合わさるという理由による。彼ら自身の実例では、Linear の MCP サーバーを Linear API を包む小さな CLI に置き換え、コンテキストファイルに6つの呼び出し例として記載した。これによりツール定義の数千トークンに加え、冗長な MCP の応答からもさらに節約できたと報告している。

## 関連用語

MCP は、[[DefinedTerm/context-files]]、[[DefinedTerm/agent-skills]]、[[DefinedTerm/subagents]] と並んでコーディングツール向けに目録化された設定機構の一つであり、Anthropic は同じ手法に従う姉妹のオープン標準として Agent Skills を公開した。MCP サーバーを利用するツールは [[DefinedTerm/coding-agent]] のもとで扱われ、MCP のツール定義が生むコンテキスト予算への圧力は [[DefinedTerm/context-engineering]] の関心事の一つである。
