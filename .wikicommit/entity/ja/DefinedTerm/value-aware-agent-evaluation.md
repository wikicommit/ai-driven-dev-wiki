価値を考慮したエージェント評価とは、[[ScholarlyArticle/survey-on-agent-system-and-harness-design]] で示された提案であり、エージェントの評価を、タスクの成功によるスコア中心の順位づけから、タスクの価値とそれを完了するためのコスト、レイテンシ、リスク、信頼性とを結びつける目的関数へと移すものである。このサーベイは、現在のエージェントのリーダーボードがタスクの成功によってシステムを順位づけており、API コスト、レイテンシ、安全性、トレースの質は二の次か、まったく欠けていると指摘し、それを最先端の比較には有用だがデプロイにとっては不完全だとしている。成功だけを最大化する代わりに、サーベイはモデルとハーネスを同時に対象とする最適化を定式化する。すなわち、タスクの効用、そのモデルとハーネスの組の成功確率、そしてプロセスの質の要約値の積の期待値を最大化するものであり、期待コスト、レイテンシの分位点、安全性またはコンプライアンス上の期待リスクにそれぞれ上限を設け、反復実行時の信頼性に下限を設ける。著者らはこれを、普遍的なリーダーボードのスコアとしてではなく、デプロイの目標を明示するための、デプロイごとに固有な効用関数の族として提示している。

## 用法

サーベイは、結果をより豊かに読み解くためにカバーすべき 5 つの次元を挙げている。最終的な目的が達成されたかどうかというタスクの成功、確率的な実行、リトライ、環境の変動にわたって性能が安定しているかどうかという信頼性、トークン使用量や API もしくは計算コストでみた効率、実時間またはやり取りの回数でみたレイテンシ、そして軌跡が検査可能で、回復可能で、証拠に裏づけられているかどうかというプロセスの質である。これらに加えて、行動が許可された範囲内にとどまり、有害な副作用を避けているかどうかという安全性を挙げる。この組み合わせを採る根拠としてサーベイが示すのは、似たような最終スコアの裏に、ハーネスの大きな違いが隠れうるという点である。あるハーネスは長い軌跡、繰り返しのリトライ、大量のコンテキストの蓄積と引き換えに高い成功率を得るかもしれず、別のハーネスはわずかに低い成功率を、はるかに低いコストとレイテンシで達成するかもしれない。

サーベイが示す補完的な定式化が価値密度である。これは、タスクの価値に成功とプロセスの質を掛けたものを、正規化したコスト、レイテンシ、リスクを調整可能な指数のもとで組み合わせた分母で割るもので、価値の高いタスクはより強い検証を許容し、高頻度のワークフローはレイテンシとコストにペナルティを課す、といったことができる。同じ実行トレースからは、有効な成功 1 回あたりのコストや、成功したタスク 1 件あたりのレイテンシといった、より単純な報告も得られる。これらは、成功率は似ていても実行時のプロファイルが異なるシステムを区別する。この観点から、サーベイはハーネスエンジニアリングを資源配分の問題として描く。モデルのルーティング、コンテキストの圧縮、キャッシュの再利用、検証器の選択、回復ポリシー、早期打ち切りは、実装の細部ではなく、単位コストあたりの有用な進捗を決めるものだというのである。

## 適用される場面

これはエージェント評価をどう行うべきかについての提案であり、確立した報告の慣行ではなく 1 本のサーベイが打ち出したものである。サーベイ自身もこれを今後のベンチマークの方向性として位置づけている。この提案は、実行トレースが必要なフィールド、すなわち結果、コスト、ツール呼び出し、リトライ、検証器のシグナル、回復の試み、ポリシー違反を備えていることを前提とするが、サーベイ自身の経験では、そうでないことが多い。Terminal-Bench の分析では、報酬、エージェントの実行時間、全体の実行時間のフィールドはカバー率が高かった一方で、入力および出力トークンのフィールドは試行記録の 45.0% しかカバーしておらず、ドルでのコストのフィールドはわずか 15.2% であった。そのためサーベイは、ハーネス間の比較に関する主張に金銭的コストを用いることを見送っている。トレースのフィールドがまばらであったり、ハーネスごとに計上の仕方が異なったりする場合には、この定式化を具体化できず、サーベイは利用可能な範囲で成功、実行時間、タイムアウト時の振る舞い、トークン使用量に立ち戻っている。

これはまた、固定された指標ではなく立場として述べられている。指数や上下限はデプロイ上の選択であるため、同じシステムに適用しても、2 つのチームが異なる順位に至ることは設計上ありうる。定式化から切り離せるサーベイの具体的な推奨は、ベンチマークの報告に、モデルのバージョン、ハーネスの識別情報、ツールの権限、リトライとタイムアウトのポリシー、実行環境、利用可能な場合のトークンまたは API の使用量、そしてトレースまたは検証器のメタデータを含めるべきだというものである。その根拠は、ベンチマークのスコアは、それを生み出した実行時の構成と併せて初めて解釈可能になるという主張にある。
