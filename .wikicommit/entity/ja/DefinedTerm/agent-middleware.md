エージェントミドルウェアは、LangChain が [[SoftwareApplication/langchain]] 1.0 で導入した抽象化であり、エージェントの標準的なループを手放すことなくエージェントをカスタマイズするためのものである。コアとなるループは、モデルノードとツールノードという 2 つの部分をそのまま保つ。ミドルウェアは 3 つのフックを通じてこのループに接続する。`before_model` はモデル呼び出しの前に実行され、状態を更新したり他のノードへジャンプしたりできる。`after_model` はモデル呼び出しの後に実行され、同じことができる。`modify_model_request` はモデル呼び出しの前に実行され、そのリクエストに限って、ツール、プロンプト、メッセージリスト、モデル、モデル設定、出力形式、ツール選択を変更する。ミドルウェアは独自の状態スキーマやツールを提供することもできる。1 つのエージェントに複数のミドルウェアを与えることができ、それらは Web サーバーにおけるミドルウェアと同じように動作する — モデル呼び出しに向かう行きでは順番に、戻りでは逆順に実行される。

## 用法

LangChain は [[BlogPosting/agent-middleware]] で、ミドルウェアを、[[DefinedTerm/agent-framework]] に共通する問題への答えとして提示している。単純なモデル・プロンプト・ツールのループの上に構築された抽象化では [[DefinedTerm/context-engineering]] に対する制御が不十分なため、ユースケースが単純でなくなると、開発者はそれを離れて独自のコードに移ってしまうというものである。それ以前の対処は、エージェントにパラメータ — 動的なプロンプト、独自の状態、モデル呼び出し前後のフック、呼び出しごとのモデル選択 — を追加することだったが、投稿によれば、それらは数が多く、相互に依存し、組み合わせたり再利用可能なバリエーションとしてパッケージ化したりするのが難しくなった。ミドルウェアは、そうしたカスタマイズの箇所を、代わりに組み合わせ可能な単位としてまとめ直すものである。

1.0 アルファ版とともに提供された 3 つの実装が、フックの使われ方を示している。`after_model` を用いた、割り込みによるツール呼び出しの [[DefinedTerm/human-in-the-loop]] レビュー。`before_model` を用いた、しきい値を超えたメッセージの要約。そして `modify_model_request` を用いた、メッセージへの Anthropic のプロンプトキャッシュ用タグの付与である。LangChain はまた、ミドルウェアによって、これまで個別の LangGraph エージェントとして提供してきたエージェントアーキテクチャ — supervisor、swarm、bigtool、deepagents、reflection — を再現できるとし、既製のミドルウェアやコミュニティによるミドルウェアを提供するとも述べている。これらは、アルファ版の時点でベンダー自身が自社のフレームワークについて述べたものである。

その後の LangChain の投稿 [[BlogPosting/improving-deep-agents-with-harness-engineering]] は、ミドルウェアを — そこでは、モデル呼び出しとツール呼び出しの周囲のフックを指す LangChain の用語と説明されている — システムプロンプトとツールに並ぶ 3 つのハーネスの調整つまみの 1 つとして用い、自社のコーディングエージェントのために作った 3 つのミドルウェアを説明している。`LocalContextMiddleware` はエージェントの起動時に実行され、作業ディレクトリをその親ディレクトリと子ディレクトリとともにマッピングし、Python のインストールなどのツールを見つけ出す。これにより、このコンテキストはエージェントが発見するのではなく注入される。`LoopDetectionMiddleware` はツール呼び出しのフックを通じてファイルごとの編集回数を追跡し、1 つのファイルへの編集が一定回数に達すると、エージェントにアプローチを見直すよう促すコンテキストを追加する（[[DefinedTerm/doom-loop]] を参照）。`PreCompletionChecklistMiddleware` はエージェントが終了する前に割り込み、タスクの仕様に照らした検証パスを実行するよう促す。投稿は、この種の決定論的なコンテキスト注入を、プロンプティングを補完するものとして提示している。

## 適用される場面

このパターンは、開発者が標準的なフレームワークのループを保ったまま、モデルに何が入り、ステップがどう順序づけられるかを制御したいと考える、そのようなループの上に構築されたエージェントを前提としている。LangChain の説明によれば、その代替はフレームワークを離れて独自のコードに移ることである。このパターンが対処するリスクは、その前身が生み出したもの — 調整したり、組み合わせたり、既製のバリエーションとして提供したりするのが難しい、相互に作用する多数のパラメータ — である。これは 1 つのベンダーによる設計であり、そのベンダーの発表の中で説明されたもので、評価は報告されていない。
