エージェントミドルウェアは、LangChain が [[SoftwareApplication/langchain]] 1.0 で導入した、エージェントの標準的なループを
捨てずにエージェントをカスタマイズするための抽象化である。中核のループはモデルノードとツールノードという 2 つの部分を
そのまま保ち、ミドルウェアは 3 つのフックを通じてそこに取り付く。`before_model` はモデル呼び出しの前に実行され、状態を
更新したり他のノードへジャンプしたりできる。`after_model` はモデル呼び出しの後に実行され、同じことができる。
`modify_model_request` はモデル呼び出しの前に実行され、そのリクエストに限って、ツール、プロンプト、メッセージリスト、
モデル、モデル設定、出力形式、ツール選択を変更する。ミドルウェアはカスタムの状態スキーマやツールを提供することもできる。
1 つのエージェントに複数のミドルウェアを与えることができ、それらは Web サーバーにおけるミドルウェアと同じように
動作する — モデル呼び出しへ向かう行きでは順番に、戻りでは逆順に実行される。

## 用法

LangChain は [[BlogPosting/agent-middleware]] で、ミドルウェアを [[DefinedTerm/agent-framework]] に共通する問題への
答えとして示している。単純なモデル・プロンプト・ツールのループの上に作られた抽象化は
[[DefinedTerm/context-engineering]] に対する制御をほとんど与えないため、ユースケースが自明でなくなると開発者はそれを
離れてカスタムコードに移ってしまう、という問題である。それ以前の対処は、エージェントにパラメータを追加すること —
動的プロンプト、カスタムの状態、モデル呼び出し前後のフック、呼び出しごとのモデル選択 — だったが、記事によれば、
それらは数が増え、互いに依存し合い、組み合わせることも再利用可能なバリエーションとしてパッケージ化することも難しく
なった。ミドルウェアはそうしたカスタマイズのポイントを、組み合わせ可能な単位としてまとめ直したものである。

1.0 アルファ版に同梱された 3 つの実装が、フックの使われ方を示している。`after_model` を使った、割り込みによる
ツール呼び出しの [[DefinedTerm/human-in-the-loop]] レビュー。`before_model` を使った、メッセージがしきい値を超えた
時点での要約。そして `modify_model_request` を使った、メッセージへの Anthropic のプロンプトキャッシュ用タグの付与である。
LangChain はまた、ミドルウェアによって、以前は個別の LangGraph エージェントとして提供していたエージェントアーキテクチャ —
supervisor、swarm、bigtool、deepagents、reflection — を再現できるとし、既製のミドルウェアやコミュニティによる
ミドルウェアを提供していくと述べている。これらはアルファ版の時期に、ベンダーが自社のフレームワークについて述べたことである。

LangChain の後の記事 [[BlogPosting/improving-deep-agents-with-harness-engineering]] は、ミドルウェア — そこでは
モデル呼び出しとツール呼び出しの周囲のフックを指す LangChain の用語として説明されている — を、システムプロンプトや
ツールと並ぶ 3 つのハーネスのつまみの 1 つとして使い、自社のコーディングエージェント向けに作った 3 つのミドルウェアを
説明している。`LocalContextMiddleware` はエージェントの起動時に実行され、作業ディレクトリとその親および子の
ディレクトリをマッピングし、Python のインストールのようなツールを見つけることで、このコンテキストをエージェントに
探させるのではなく注入する。`LoopDetectionMiddleware` はツール呼び出しのフックを通じてファイルごとの編集回数を追跡し、
1 つのファイルへの編集が一定回数に達すると、エージェントにアプローチを考え直すよう促すコンテキストを追加する
（[[DefinedTerm/doom-loop]] を参照）。`PreCompletionChecklistMiddleware` はエージェントが終了する前に割り込み、
タスクの仕様に照らした検証のパスを実行するよう促す。記事は、この種の決定論的なコンテキスト注入を、プロンプティングを
補完するものとして示している。

## 適用される場面

このパターンは、標準的なフレームワークのループの上に構築されたエージェントで、開発者がそのループを維持しつつ、
何がモデルに入るか、ステップがどう順序づけられるかを制御したい場合を前提としている。LangChain の説明によれば、その
代替はフレームワークを離れてカスタムコードに移ることである。このパターンが対処するリスクは、その前身が生み出したもの —
調整し、組み合わせ、既製のバリエーションとして提供することが難しい、相互に作用する多数のパラメータ — である。
これは 1 つのベンダーの設計であり、そのベンダーの発表の中で説明されたもので、評価は報告されていない。
