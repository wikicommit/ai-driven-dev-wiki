ツールポイズニングとは、[[DefinedTerm/model-context-protocol]] サーバーを通じて外部の機能に到達する AI エージェントに対する攻撃であり、攻撃者は LLM が読み、あたかもユーザーから来たかのように従う指示を仕込む。ここに挙げた2つの説明はどちらもこれを [[DefinedTerm/indirect-prompt-injection]] の一形態として扱うが、毒の在り処を異なる場所に位置づけており、その違いは防御をどこに置くべきかにとって重要である。

Microsoft はツールポイズニングを「攻撃者が MCP ツールの説明の中に悪意ある指示を埋め込む脆弱性」だと説明する。サーバー上のあらゆるツールは名前や説明といったメタデータを伴い、LLM はそのメタデータを用いてどのツールを呼び出すかを判断する。したがって侵害された説明は、システムを守るための統制を迂回する意図しないツール呼び出しへとモデルを誘導しうる。指示はメタデータの中にあるため、ユーザーには見えないままモデルには読める。Microsoft は、ホスト型のサーバーを最も鋭いケースとして指摘する。ツールの定義は事後に修正して悪意ある内容を加えられるからである——一部の研究者がこれを「ラグプル」と呼んでいると報告している——。そのため、以前にあるツールを承認したユーザーが、その承認以降に変更され、宣言されていない動作を行えるようになったツールを手にしてしまいうる。

OWASP の説明は *MCP Tool Poisoning* という題で公開され、著者 kOaDT のクレジットが付されており、毒を実行時へ移す。そこでは攻撃者が悪意あるサーバーを運用し、その「ツールは正常に見えるが、その応答には隠された指示が含まれている」。エージェントがそれを呼び出すと、注入された指示がコンテキストウィンドウに入り、信頼できる入力として扱われ、モデルはそれに従う——制限されたツールを呼び出したり、データを漏らしたり、自身のシステムプロンプトを迂回したりする。その根本原因として述べられているのは接続時と実行時の間の信頼のギャップである。説明は接続時に一度だけレビューされるのに対し、応答は同等のチェックなしにそのままコンテキストに入る。

## 用法

OWASP はこの攻撃を一連の手順として示す。攻撃者は `get_compliance_status` や `fetch_user_data` といった正常に見えるツール名と説明を持つサーバーを作る。被害者は、ソーシャルエンジニアリング（「コンプライアンスチェックのためにこのサーバーを追加してください」）によって、あるいはそのサーバーが公開レジストリに現れていることによって、エージェントをそれに接続する。エージェントは通常の運用中にツールを呼び出す。サーバーは、本物らしく見えるデータと埋め込まれた指示——たとえば偽のコンプライアンス指令——を混ぜた応答を返す。モデルは応答全体を文脈として扱い、それに従う。そしてエージェントが行動する——制限されたツールを呼び出す、機微なファイルを読む、あるいは攻撃者の管理するエンドポイントへデータを送る。具体例として挙げられているのは、`get_compliance_status` ツールが捏造された「コンプライアンス指令」を返し、`/etc/shadow` を読んでその内容を「外部での検証」のために外部 URL へ POST するようエージェントに指示する、というサーバーである。

OWASP が同定する露出は3つの部分からなる。ユーザーが制限なくエージェントを任意のサーバー URL に向けさせられるアプリケーション。ファイルシステム、データベース、内部 API へのアクセスといった特権的なツールを持ちながら、同時に外部サーバーにも接続するエージェント。そしてツールの応答をそのままコンテキストへ渡すクライアントの実装である。最後の点について OWASP は、MCP の仕様がサーバーの出力を信頼できない可能性のあるものとして扱い、クライアントに信頼境界を考慮するよう助言してはいるものの、内容が LLM に届く前の応答の検証を必須としてはいないと注記する。名指しされているリスク要因は、検証されない応答、内部と外部のツールが1つの権限レベルを共有していること、そしてシステムプロンプトによる制限がバックエンドのアクセス制御ではなくモデルの指示追従だけによって強制されていることである。

その予防策の一覧は、それに応じて構造的である。応答の形式を固定スキーマに対する構造化出力へと制約し、合致しない応答は拒否すること——ただし自由文中の注入された指示を完全に検出することは未解決の問題であり、スキーマの検証は明白なケースしか捉えられないと認めている——。特権的なツールを、外部サーバーが到達できない別のエージェントのコンテキストに隔離すること。制限をプロンプトではなくツールの実行層でサーバー側で強制すること。精査済みのサーバーの許可リストを維持すること。そして破壊的あるいはデータを持ち出す動作の前に、LLM のコンテキストの外側で得られる明示的なユーザーの確認を要求することである。

CoSAI の脅威の分類——2026年1月8日に承認されながら依然として「ステータス：ドラフト」と記された報告書で提案されている——は、ツールポイズニングを7つの Tier 1 の MCP 固有の脅威の一つとして挙げ、`tools/list` メソッドを介してクライアントに注入される、ツールのメタデータ・設定・記述子への悪意ある変更と定義している。そして、ツールのアノテーションは信頼できるサーバーから得たものでない限り信頼できないものとみなすべきだという仕様自身の記述を引き、これが「クライアントが精査されていないサーバーに接続する際の、認識されたリスク」となっていると述べる。同報告書はまた、隣接する2つの脅威をこれと明示的に区別している。**完全なスキーマポイズニング** は、個々のメタデータではなくツールの構造的な定義と型システム全体——隠されたパラメータ、変更された戻り値型、悪意あるデフォルト値——を侵害する。そして **リソースコンテンツポイズニング** は、ツールの定義ではなく、サーバーが取得するバックエンドのデータソースに指示を潜ませる。

### 学術的な分類における位置づけ

2つのサーベイがこの攻撃をより大きな体系の中に置いており、いずれも名前を挙げる価値のある近隣とともに分類している。

[[ScholarlyArticle/mcp-landscape-security-threats]] はツールポイズニングを、分類における4種類の攻撃者の一つである **悪意ある開発者** による *機能の宣言* の下に位置づけ、攻撃の帰結として隠された悪意あるペイロードの実行を記録している。その群における直接の近隣は **ラグプル**——帰結はサービスの停止と信頼の喪失とされる——と、**クロスサーバーシャドウイング**——悪意ある機能が隠され、横方向の悪用が続く——であり、それらと並んで名前空間のタイポスクワッティング、ツール名の衝突、選好の操作、コマンドインジェクションが置かれている。同じ論文が、ライフサイクルのフェーズではなく起点によって分類する理由は、まさにこの攻撃にある。ツールポイズニングとラグプルは「作成の段階で持ち込まれるが、運用の段階で発火する」からである。

[[ScholarlyArticle/sok-security-and-safety-in-the-mcp-ecosystem]] は、ツールの偽装とコンテキストポイズニングを *敵対的なセキュリティ上の脅威* の例として挙げ、問題のもう半分として扱う *認識論的なセーフティ上の危険* と対比する。そしてラグプル攻撃を、サーバーのなりすましおよび権限のないツールの変更とともに、サプライチェーンおよびモデルの入れ替えによる攻撃の下にまとめている。またツールポイズニングを索引語の一つにも挙げており、そのより広い議論はこの攻撃のクラスがなぜ抑え込みにくいのかに直接関わる。文脈と行動の結合が、同論文の言う「意味的な攻撃面」を生むため、汚染された定義や応答は単に誤解を招く出力ではなく、現実世界の運用上の損害への経路になるのである。
