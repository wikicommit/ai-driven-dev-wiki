Ralph Loop は「Ralph Wiggum テクニック」とも呼ばれ、単一セッションのコーディングエージェントを複数セッションにまたがるものに変えるために Geoffrey Huntley と Ryan Carson によって広められたハーネスパターンである。開発は多数の小さなタスクに分割され、エージェントは繰り返しのサイクルでそれらを処理していく。To-Do リストから次のタスクを選び、実装し、変更を検証し（テスト、型チェック）、チェックに通ればコミットし、タスクのステータスを更新して得られた知見を記録し、そしてエージェントのコンテキストをリセットして繰り返す。反復のたびにコンテキストをリセットすることで、エージェントは以前のタスクに由来する混乱を蓄積せずに済み、1 つの巨大なプロンプトを、範囲の限られたプロンプトの繰り返しに置き換えることになる。

## 用法

それ以外の点ではステートレスなリセットをまたいで、4 つの記憶の経路が持続する。git のコミット履歴（各反復の変更はコミットされるので、後の反復は思い出す代わりに diff を調べられる）、各サイクルで何が起きたかを記すプレーンテキストの進捗ログ、どの作業が残っているかを追跡するタスク状態ファイル（例：タスクごとに pass/fail のフラグをもつ JSON）、そして発見されたパターンや落とし穴を、すべての反復が読んで追記できる長期的な意味記憶として蓄積する `AGENTS.md` ファイルである。このパターンは、計画立案（目標を手順に分解して計画ファイルに記録すること）や、プランナー／ジェネレーター／エバリュエーターへの分割と並んで、モデルが早期に停止しがちな傾向、複雑な問題の分解の拙さ、長い作業にわたる一貫性の欠如を回避する方法として紹介されている。

## 適用される場面

これが当てはまるのは、タスクが 1 つのコンテキストウィンドウに収まる以上に長く続くと見込まれ、反復の合間に（たとえば夜通し）無人で継続する必要がある場合である。前提となるのは、新しいコンテキストウィンドウのそれぞれが読み込んで前回の続きから再開できる、ファイルシステム上の永続的な状態、合否基準の明確な小さなタスク、そして無人の実行が害を及ぼさないようにするための安全策である。報告されている安全策には、フィーチャーブランチ上でのみ実行すること、失敗したテストやビルドの出力をエージェントに戻して自動リトライさせること、同じエラーで 3 回以上の反復にわたって行き詰まったエージェントを停止して別のエージェントに割り当て直すこと、反復回数・時間・トークンに対するハードリミット（役割ごとの予算を含む）、そして自動でマージするのではなく人間のレビューのためにプルリクエストを開くことが含まれる。

このパターンを説明するソースのうち 2 つは、Geoffrey Huntley と Ryan Carson をこれを広めた人物としており、いずれかの著者自身の発明としては提示していない。その 2 つのうち 1 つは、独立した `ralph` ツールの実装を特に Carson の功績としている。3 つのソースのうち最も早く公開されたものは、このパターンを以前に書いたことのあるものとして論じており、考案者の名前は挙げていない。

4 つ目のソースは、Anthropic が自社の科学計算向けエージェントスタックを、同じパターンの一種にまで絞り込んだことを述べている。エージェントが学びながら編集する生きた計画としての `CLAUDE.md`、持ち運び可能な実験ノートとしての `CHANGELOG.md`、実行と協調の層としての `tmux` と `SLURM` と `git`、そしてエージェントが完了を主張するたびにそれをコンテキストに引き戻し、本当に終わったのかを問う `for` ループである。そのソースの目玉となる事例研究は、Claude Opus 4.6 が数日かけて構築したボルツマンソルバーであり、参照実装である CLASS と 1 パーセント未満の差で一致するに至った。
