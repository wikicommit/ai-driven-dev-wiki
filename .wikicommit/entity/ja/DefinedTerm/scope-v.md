SCOPE-V は、Christopher Koch が提案した [[DefinedTerm/agentic-agile-v]] フレームワークのタスクレベルの実行ループである。このフレームワークのマクロ層である Agile-V がインクリメントのライフサイクルを統べるのに対し、SCOPE-V は個々のエージェンティックなタスクがどう実行されるかを統べ、6つの名前付きのステップを通過させる。

## 用法

| ステップ | 何を扱うか |
| --- | --- |
| **S**pecify（仕様化） | 意図を、目的、スコープ、非目標、影響を受けるモジュール、依存関係、受け入れ基準、必要な証拠を伴うタスクブリーフに変換する |
| **C**onstrain（制約） | 境界を定める——承認なしに公開 API を変えない、無関係なファイルに触れない、正当な理由なく新しい依存関係を加えない、バグ修正の最中に広範なリファクタリングをしない、セキュリティに敏感なコードには明示的なレビューを行う、そしてハードウェアのタイミングと安全性の制約を必ず保持する |
| **O**rchestrate（オーケストレーション） | エージェントがどう働くべきかを定める——まず調べ、現在の設計を要約し、計画を提案し、小さなスライスで実装し、ローカルのチェックを走らせ、残存リスクを添えた差分の要約を作る |
| **P**rove（証明） | リスクに見合った証拠を要求する——単体・統合・回帰テスト、静的解析、型チェック、リント、セキュリティスキャン、シミュレーション、形式的な検査、ハードウェア・イン・ザ・ループの結果、あるいはレビューのチェックリスト |
| **E**volve（進化） | 検証された学びをリポジトリの指示、テンプレート、テスト、エンジニアリングの基準に還流させ、古くなったり有害になったりした指示を取り除く |
| **V**erify（検証） | 検証を最終工程ではなく反復的なものとして扱う——実装の前、パッチ適用の最中、マージの前、デプロイの後、そして現場からのフィードバックの後 |

最後のステップこそ、[[ScholarlyArticle/agentic-agile-v]] が慣例からの逸脱として強調するものである。検証は最終的な品質ゲートではなく、全体を通じて繰り返し現れる——論文はこの立場を、テストに関する指針でも補強しており、テストはエージェントのループの後ではなく内側になければならないと論じる。実装の前に期待されるテスト、エッジケース、失敗のモードを洗い出し、実装中は小さな変更のたびに的を絞ったテストを走らせ、マージの前には CI、静的解析、型チェック、セキュリティチェック、レビューを要求し、マージの後にはログ、欠陥、パフォーマンス、ユーザーからのフィードバックを監視する、というものである。

Orchestrate ステップの「まず調べ、次に計画し、それから実装する」という順序は、論文のタスク別のワークフローにも再び現れる。機能開発については、機能ブリーフを書き、影響を受けるモジュールとテストを特定し、エージェントに現在の設計を調べて要約させ、編集の前に計画を要求し、最小の有用なスライスを実装し、実装と並行してテストを追加・更新し、的を絞ったチェックと回帰チェックを走らせ、証拠のバンドルと残存リスクの注記を作り、アーキテクチャ・セキュリティ・保守性・エッジケースについて人間のレビューを要求することを推奨する。バグ修正については——論文はこれを機能の生成ではなく因果の診断として枠づける——エージェントは即座にパッチを当てるのではなく、観測された振る舞いと期待される振る舞いを捉え、再現手順と環境の詳細を提示し、仮説を立てて欠けている証拠を名指しし、可能性の高いファイルと呼び出し経路を特定し、可能なら失敗する回帰テストを作り、最小限のパッチを適用し、回帰テストと近傍のテストを走らせ、なぜその修正が効くのか、そして何には対処していないのかを説明することを推奨する。

## 関連用語

SCOPE-V は [[DefinedTerm/agentic-agile-v]] のミクロ層であり、その Prove と Verify のステップは、このフレームワークの [[DefinedTerm/verification-debt]] に対する直接の答えである。
