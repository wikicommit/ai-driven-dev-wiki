影響半径とは、[[Person/birgitta-bockeler]] が [[BlogPosting/the-role-of-developer-skills-in-agentic-coding]] において、エージェンティックなコーディングアシスタントと働く中で観察した失敗を整理するために用いる分類である。AI がどれだけ間違っていたかではなく、その帰結がどこまで及ぶかによって仕分ける。コミット前に自分の作業を遅らせた失敗、イテレーション内でチームに摩擦を生む失敗、そして長期的な保守性を損なう失敗である。彼女を貫く観察は、半径が大きいほどチームがその問題を捉えるまでのフィードバックループが長くなる、というものだ——これは直感的な順位づけを反転させ、最も目立たないカテゴリを最も有害なものにする。

## 用法

**コミットまでの時間** は最も内側の半径であり、彼女の説明では最も問題が少ない。失敗が明白であり、その変更はまずコミットに至らないからである。例として挙げられるのは、単純に動かないコード——ここでは経験が、素早い修正として、あるいはいつ諦めるべきかを早い段階で知っていることとして現れる——、そして誤診断である。アシスタントが Docker のビルドの問題をアーキテクチャの設定のせいだと決めつけたが、真の原因は誤ったアーキテクチャ向けにビルドされた `node_modules` だった、という例が挙げられている。

**イテレーション内のチームの流れ** は、レビューの欠落がデリバリ中の摩擦を生む場合を扱う。Böckeler が挙げるのは、事前作業のやりすぎ——アシスタントが動く垂直スライスを実装するのではなく横に広げてしまうこと。スタックの移行時に、まず1つのコンポーネントから始めてバックエンドと統合するのではなく、すべての UI コンポーネントを一度に変換しようとした例。根本原因の分析ではなく力任せの修正——なぜそれほどのメモリが必要だったのかを問うのではなく、Docker のビルドのメモリ設定を引き上げる例。開発者のワークフローを複雑にすること——フロントエンドとバックエンドを1つではなく2つのコマンドで動かすことになった例や、ホットリロードが動くことを確認できなかった例。そして要件の誤解や不完全な理解である。この半径についての未解決の問いは、コーディングのスループットが増えることでこれらの二次的な影響が、チームが持続的に吸収できる範囲を超えて悪化するのかどうかだと彼女は指摘している。

**長期的な保守性** は最も外側の半径であり、彼女いわく最も陰険である——今は動くが変更しにくくなるコードであり、数週間から数か月後に表面化し、彼女の20年を超えるプログラミング経験が最も物を言ったカテゴリでもある。例として挙げられるのは、冗長で重複したテスト——アシスタントが既存のテスト関数にアサーションを加えるのではなく新しいテスト関数を作ったり、他所ですでにカバーされているアサーションを重複させたりすることで、スイートが脆くなり、1つの変更が多数のテストを落とすようになる。再利用の欠如——UI コンポーネントがすでに存在することに気づかず重複させたり、クラスや変数の代わりにインライン CSS を使ったりすること。そして過度に複雑あるいは冗長なコード——既存の依存性注入の連鎖を認識できず、不要なコンストラクタ引数を追加したリファクタリングの例が含まれる。

## 関連用語

この分類は、綿密な監督なしの [[DefinedTerm/agentic-coding]] で何がまずくなるのかを見立てるための診断の枠組みであり、Böckeler がそれに対して提案する防護策——注意深いレビュー、品質の監視、シフトレフトのチェック、チームの儀式——は、[[DefinedTerm/vibe-engineering]] が LLM の恩恵を引き出すとする実践と重なる。最も外側の半径は、[[DefinedTerm/verification-debt]] で説明される蓄積と密接に関連している。
