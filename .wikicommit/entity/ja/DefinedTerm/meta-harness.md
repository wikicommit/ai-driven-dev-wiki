メタハーネスとは、[[ScholarlyArticle/harness-engineering-anatomy-architecture-and-evolution-of-coding-agents]] の用法では、1 つ以上のコーディングエージェントのハーネスを上位から協調させ、独自の編集ループを一切実装しないオーケストレーションレイヤーである。[[DefinedTerm/agent-harness]] がモデルを包んでリポジトリに対して行動させるのに対し、メタハーネスはハーネス全体 — Claude Code、Codex、Cursor など — を共通のインターフェースの背後にある交換可能なコンポーネントとして包む。同論文はこれを、ハーネスではない 4 つのものの一つとして扱っており、ハーネスと同じサブシステムでこれを評価することは、同論文の言葉では、カテゴリーの誤りになるという。同論文は、自らが知る限り最初のそのようなシステムである [[SoftwareApplication/omnigent]] を分析し、どのハーネスの機能が独立したレイヤーへと上方に移りつつあるかを示す証拠としている。

## 用法

同論文は、Omnigent の場合にメタレイヤーがハーネスの境界の上に加えるものを次のように説明している。登録されたどのハーネスも他のどのハーネスのサブエージェントセッションとして呼び出せるようにする合成。各ベンダー自身の拡張機構 — Claude Code のフックや ACP のパーミッション要求など — を通じて外部のハーネスに適用される、ハーネス横断のポリシープレーン。統一されたサンドボックスとエグレスのスタック。そして、共有可能でサーバー側に永続化され、セッションの途中でハーネスを切り替えられるセッション。境界の下に残るのはハーネスのコア — 編集ループ、リポジトリのコンテキスト、編集の適用戦略 — である。

著者らはメタハーネスを、ハーネスがコモディティ化したコンポーネントになりつつあり、持続的な価値は一つ上のレイヤーにあるという賭けとして読み解き、これをコーディングハーネスがツールからプラットフォームへと変わったという、より広い自らの主張の中に位置づけている。著者らは、検討した 1 つのシステムから、この読み方に 2 つの緊張関係があることを指摘している。1 つは、メタレイヤーがハーネスを同等なものとして装ってはいないことで、ベンダー固有の機能記録が設計上その共通 API を通して漏れ出ている。もう 1 つは、サンドボックス化を一貫しない形で適用していることで、あるベンダーの CLI は独自のサンドボックスで包む一方、別のベンダーについてはそのネイティブのサンドボックスモードに委ねている。同論文はこれを、OS レベルの分離が共有サービスとして切り出されることに抵抗する証拠と見なしている。上位からのコモディティ化の経済性は、今後の研究課題として挙げられている。

同論文の分析は単一のシステムと単一のソースコード調査に基づいており、Omnigent を確立されたカテゴリーの代表ではなく、同論文が知る限り最初のメタハーネスと呼んでいる。

Anthropic は同じ語を別の設計に用いている。[[BlogPosting/scaling-managed-agents-decoupling-the-brain-from-the-hands]] で Anthropic は [[SoftwareApplication/claude-managed-agents]] を「メタハーネス（a meta-harness）」と呼んでいる。これは、Claude が将来必要とする特定のハーネスについて特定の立場をとらず、代わりに汎用的なインターフェース — 永続的なセッションと、ツール呼び出しのインターフェースを通じて利用されるサンドボックス — を提供するシステムを意味し、その上では Claude Code のような汎用のものからタスク特化のものまで、多種多様なハーネスが動作できる。論文のメタハーネスが既存ベンダーのハーネスを上位から協調させるのに対し、Anthropic のものは Claude とそれらのインターフェースの間に位置するハーネスが何であれそれをホストする。Anthropic はこの設計を、ハーネスそのものではなく Claude の周囲のインターフェースについて明確な立場をとるものだと説明している（[[DefinedTerm/brain-hands-session-split]] を参照）。どちらの情報源も、もう一方の用法には言及していない。
