Claude Code プラグインマーケットプレイスとは、[[SoftwareApplication/claude-code]] のプラグインが配布されるカタログであり、
発見・バージョン管理・自動更新を一箇所で扱う。プラグインそのものは、数種類の構成要素を束ねたパッケージである。Claude が
参照するガイドラインを保持し、`/create-pr` のようなスラッシュコマンドが実際に住まう場所でもある Skills。特定の仕事を自律的に
遂行するサブエージェントである Agents。タスクの完了といった特定のイベントで発火する処理である Hooks。そして外部サービスへ
接続するための MCP サーバー設定（[[DefinedTerm/model-context-protocol]] を参照）である。

## 用法

使えるプラグインに至るまでには 1 段階ではなく 2 段階を要し、この区別は実際上重要である。マーケットプレイスを追加しても、
そのカタログが見えるようになるだけでプラグインはまだ 1 つもインストールされておらず、そこから各プラグインを個別にインストール
する（`/plugin marketplace add <org>/cc-plugin-marketplace` の後に `/plugin install my-plugin@cc-plugin-marketplace`）。

構造は 2 層になっている。マーケットプレイスそのものは Git リポジトリのルートに置かれた 1 つの JSON ファイル
`.claude-plugin/marketplace.json` であり、配布するすべてのプラグインの名前とリポジトリ内でのパスを列挙する。次に各プラグイン
のディレクトリが、そのプラグイン自身のメタデータ——名前、バージョン、説明——を保持する固有の `.claude-plugin/plugin.json`
を持つ。マーケットプレイスファイルの 1 エントリは、プラグイン自身のメタデータの内容に `source` のパスを加えたものであり、
そのパスは相対パスなので、プラグインをリポジトリ内の特定の場所に配置する必要はない。パスさえ合っていれば、マーケットプレイス
は好きなようにそれらをまとめられる。ただしこの相対形式は同一リポジトリ内のプラグインにしか届かない。他のリポジトリにある
プラグインは、GitHub ソースなど別の手段で参照できる。

バージョンの扱いには、意図的に最小限の選択肢が用意されている。プラグインのメタデータから `version` フィールドを省くと、
Claude Code は Git のコミット SHA をバージョンとして扱うので、マージすること自体が最新バージョンを出荷する行為になる。

検証は一次提供のコマンドとして利用できる。カタログで捕まえるに値する構造上の欠陥として挙げられているのは、JSON の構文、
必須フィールドの欠落、プラグイン名の重複、`SKILL.md` とエージェントのフロントマターの欠陥、そして `hooks.json` の構文で
あり、そのチェックのほとんどすべては `claude plugin validate` に委ねられる。README の有無と、固有のメタデータファイルは
持つがカタログに登録されなかったプラグインは、このコマンドが扱わないものとして名指されている。またこのコマンドは、`../`
を使うものなど、マーケットプレイスのルートの外を指す `source` パスを拒否する——プラグインはインストール時にキャッシュ
ディレクトリへコピーされるので、ルートの外を指すソースは、単に形式が不正であるにとどまらず、動作しないか意図しない場所に
届くおそれがある。

第二の記述 [[BlogPosting/raising-productivity-floor-with-harness]] は、カタログがどう構築されるかではなく、組織がこの方法で
何を配布するかに関心を寄せている。その論点は、この機構は組織の働き方を公開するためのプラットフォームと読んだほうがよい、と
いうものである。共有モジュールはワークフロープラグインになり、ライブラリの公開はマーケットプレイスへのアップロードになる。
変わるのは中身がコードからプロンプトとエージェントのロジックになることだけである。2 つの用途が素描されている——main ブランチ
へのコミットの試みを捕まえ、エージェントをフィーチャーブランチの作成へ誘導するフックであり、この記事はそれを、ブロックする
だけのリンタと対比している。そしてある強力なエンジニアの機能開発ワークフロー全体を担う単一のスラッシュコマンドであり、それに
よってチームの誰もがそれを呼び出せるようになる。同じ記事は、この目的にはマーケットプレイスのほうが検索拡張生成よりも予測
可能だと論じている。その根拠は、プラグインは開発者が完全に制御できる明示的なテキストであり、デプロイを伴わずにローカルで
改訂し検証できることである。これらはすべて結果ではなく方向性として提示されており、この記事へのあるコメントは、積み重なった
多くのプラグインのどれが有効なのかを追跡すること自体が可視性の問題になるだろうと論じている。

## 適用される場面

この機構は、手渡されるのではなく人々が自分で見つけて採り入れることが期待されるプラグイン群を配布するのに適しており、だから
こそ発見と更新がインストールする側に委ねられずにそこへ束ねられている。利用者が到達できる Git リポジトリを前提とし、相対パス
形式の場合には、プラグインがその同じリポジトリに置かれていることを前提とする。

その構造上の弱点は、[[BlogPosting/shared-claude-code-plugin-marketplace]] で述べられているとおり、マーケットプレイスが
配布するすべてが 1 つの共有ファイルに列挙されることである。複数のチームが 1 つのカタログに貢献する場合、あらゆる変更がその
ファイルに着地するのでマージが衝突する。そしてそのファイルこそがカタログであるため、構文的に壊れたファイルはマーケット
プレイス全体で `/plugin marketplace update` を失敗させ、すべての利用者が新しいものを一切取得できなくなる。この記述はまた、
この形式が表現しないことも指摘している。プラグインのメタデータは作者を記録するが、そのプラグインが 1 つのチーム向けなのか
全員向けなのか、壊れたときに誰が直す責任を負うのかは、構造の中のどこにも書かれていない。

どれほど確立しているか。機構そのものは Claude Code 自身のものであり、ベンダーによって文書化されている。上の運用上の特徴
づけは、共有マーケットプレイスを運営したある組織の約 10 か月にわたる記述から来ており、著者らによって 2026 年 8 月と日付が
付けられている。
