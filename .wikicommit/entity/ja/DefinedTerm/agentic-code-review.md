エージェンティックコードレビューとは、[[ScholarlyArticle/rethinking-code-review-in-the-age-of-ai]] で提案されたモデルであり、そこではレビュアーが「手作業の検査者からエージェントの監督的な操作者へと移行する」。その決定的な一手はスコープにある。レビューの一段階を自動化するのではなく、レビューの有効性をプルリクエストのライフサイクル全体の帰結として扱い、段階の境界を越えてコンテキストを運ぶフレームワークを構築する。これはその論文が提案するビジョンであり、実装され評価されたシステムではない。

ライフサイクル全体を一度に扱う理由は、段階ごとの改善が合成されないからである。有益なレビューコメントは、その根拠が書き留められた PR があってはじめて成立する。レビュアーのマッチングは、行動上のコンテキストがレビュアーに届くことに依存する。将来の変更は、以前のレビューからの教訓が記録されていることに依存する。これらの依存関係はツールの境界をまたぐため、どれか一つの段階を単独で改善しても、鎖はどこか別の場所で切れたままになる。

## 用法

**5つの段階、それぞれに人間のゲート。** PR 作成では、タイトル、説明、Issue のリンクを生成し、最初の自動チェックを走らせ、著者が正式な提出前に検証する。PR 拡充では4つの分析——要件との整合、バグの起こりやすさ、サンドボックス内でのランタイム実行、モジュール横断の影響——を同時に走らせ、検証可能な主張の構造化された要約へと統合する。レビュアー選定では、候補者を専門性、レビュー履歴、現在の作業負荷、その変更への習熟度でランクづけする。AI 支援コードレビューでは、それらの分析への自然言語インターフェースとして PR Review Agent をレビュアーの前に置く。PR 振り返りでは、レビューの要約をリポジトリのメモリとして捉え、プロセスのメトリクスを算出する。

**人間のゲートの目的として述べられているのは、儀式ではなく誤りの封じ込めである。** 上流のエージェントの出力が下流のタスクに流れ込むため、早い段階でのハルシネーションや誤分類は伝播する。論文の具体例は、認可の変更を読み違えて誤った説明を生成し、その結果レビュアー選定がセキュリティの専門家ではなくバックエンドの担当者を割り当ててしまう、というものだ。ゲートは「誤りの蓄積に対する自然なファイアウォール」と説明され、生成された説明を著者が検証することで鎖が早い段階で断ち切られる。

**論文は、それらのゲートが自足的ではないことを明言している。** ヒューマンインザループの仕組みが本質的に堅牢だと想定することは根本的な欠陥だと論じる。自動化バイアスによって、著者は権威ありげなアーティファクトを確認せずに受け入れがちだからだ——そして未検証の Issue リンクが一つあれば、それが拡充を経てレビュアーの割り当てへとカスケードしていく。求められているのは、信頼を前提とするのではなく、明示的な品質の指標を人間に見せることである。

**レビューに接ぎ木したチャットボットとこれを区別する仕組みが2つある。** [[DefinedTerm/diff-map]] は、レビュアーが目にするすべての主張をソースコードの位置と、それを生み出したレポートに紐づける。論文はこれを、レビューを記憶の作業から検証可能な検索のタスクへ変えるものだと説明する。もう一つは、コードではなく*レビュアー自身の*出力に対して働く2つの測定エージェントである。有害なコメントは将来の貢献を妨げるという理由から、フィードバックが書かれている最中にそれを評価する Toxicity Measurement Agent と、些末な議論（bikeshedding）を抑えるために表面的な指摘を同定する Usefulness Measurement Agent である。

**チームの能力に対して名指しされているリスク**は、レビューの持つ欠陥検出以外の目的が浸食されることである。論文は、知識の伝達とチームの状況認識も同じくレビューの重要な成果であること、そして説明をエージェント経由にすることでレビュアーが手作業の検査を迂回する誘因が生まれ、シニアとジュニアの開発者の間の暗黙のメンタリングが失われうることを指摘する。提案されている緩和策は、マージのブロックが解除される前に必須の人間による批評のチェックポイントを設けることである。
