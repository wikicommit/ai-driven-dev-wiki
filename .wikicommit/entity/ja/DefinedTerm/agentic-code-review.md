エージェント型コードレビューとは、AI エージェントがレビュアーの役割を占めるコードレビューを指す。このウィキが保持する
2 つのソースはこの用語を異なるレベルで用いており、どちらも他方の特殊なケースではない。一方はプロジェクトのレビュー実践の
ある局面を、他方は 1 回のレビューについてのタスクの定義を指している。

[[ScholarlyArticle/from-human-centric-to-agentic-code-review]] は、プロジェクトが通過しうる 3 つのコードレビューの時代の
うち最も新しいものに対してこの語を用いている。その研究は、レビューが主として人間のプロセスである人間中心のレビュー、
LLM 支援のレビュー、そして AI エージェントのレビュアーが人間のレビュアーや大規模言語モデルのレビュアーと並んでレビューの
プロセスに参加するエージェント型コードレビューを区別する。これらの時代は、研究が導き出したカテゴリーではなく、その研究が
作業する枠組みである。研究が経験的に特定しているのは、207 の GitHub プロジェクトにおける 102 万件のレビュー済み
プルリクエストから得られた、プロジェクトがそれらを移行していく 3 つの採用の実践である。

[[ScholarlyArticle/swe-review]] はこれに対し、リポジトリに接地したタスクとして形式化している。レビューのインスタンスは、
該当するコミットにおけるリポジトリのチェックアウト、自然言語の issue、そして差分・タイトル・本文を伴う候補のプルリク
エストを与え、正解のパッチと隠されたテストの結果は伏せる。レビュアーはファイルを閲覧し、コードを検索し、依存関係を調べ、
コマンドを実行してから、2 つのフィールドをもつレポートを提出できる。承認するか変更を要求するかの二値の判断と、変更を
要求する場合には、具体的な欠陥を特定し、可能な限りコードの位置を引用し、後段の修正エージェントのために実行可能な修正案を
提示する診断である。

## 用法

時代という意味では、この用語は特定のツールではなく実践の局面を指し示す。プロジェクトは、その時代へ至るまでに 3 つの採用の
実践 — 漸進的な AI の採用、急速な LLM の採用、急速な AI エージェントの採用 — のどれをたどるかによって特徴づけられ、
レビューの議論は人間・LLM・エージェントのレビュアーのあいだのやりとりの系列としてモデル化される。

その研究がこの時代について報告しているのは分裂である。エージェントが関与する協働のパターン、とりわけ AI エージェントに
よって開始されたレビューや複数の AI エージェントが関わるレビューは、それら採用の実践のうち 2 つのもとでレビュー判断の
速さと結びついているが、著者らは効率の向上がレビューの品質の向上には転化していないと述べている。

タスクという意味では、決め手となるのは、レビュアーが差分を単独で読むのではなくリポジトリの中で行為することである。
そこはまた、測定された優位が存在する場所でもある。[[ScholarlyArticle/swe-review]] は、エージェント型のレビューが単一
ターンの固定コンテキストのレビューを、判断の正確さと修正後の解決率の双方で上回り、その差はリポジトリ全体にわたる非局所的な
推論を要するタスクで最大だったと報告している — これは、探索こそが追加されたケイパビリティが買うものであるならば予期される
結果である。この枠組みにおいてレビューは終端の講評のステップではなく、[[DefinedTerm/generate-review-revise-loop]] の
要となる転回点である。

2 つの用法は、何を証拠とみなすかについて異なる方向へ引っ張る。時代としての記述は観察的であり、GitHub 上のプロジェクトが
実際に行ったことから引き出され、速いことは良いことではないと慎重に断っている。タスクとしての記述は構成されたもので実行
可能であり、レビューを、その後パッチが issue を解決するかどうかで採点する。エージェント型コードレビューについての主張は、
ソースが 2 つのどちらを意味しているかに照らして確かめる価値がある。

## ベンダーにおける用法

この形容詞の 3 つ目の用法はベンダーの側から来ており、上のいずれの意味よりも具体的な何かを指しているので記録に値する。
[[SoftwareApplication/github-copilot-code-review]] についての GitHub のドキュメントには「Agentic capabilities for
Copilot code review」と題された節があり、その見出しの下に置かれているのはレビュー全体ではなく 2 つの特定の能力である。
変更の文脈をよりよく理解するためにリポジトリ全体を解析するプロジェクト全体のコンテキストの収集と、提案された修正を適用した
新しいプルリクエストを作る Copilot のクラウドエージェントへ提案を渡す能力である。同じドキュメントはこの形容詞をレビュー
そのものに対しても率直に用いており、特定のプルリクエストはエージェント型のレビューの対象になりうると述べているので、
狭い読み方はドキュメント全体が保持している定義ではなく、1 つの節の強調である。

その強調が落ち着く先は、上のタスクとしての意味が線を引くところとおおよそ同じである。レビューをエージェント型たらしめるのは、
差分だけを読むのではなくリポジトリに対して行為することである。ドキュメントはこれらのケイパビリティに、どちらの研究の記述も
言及する理由をもたない代償を結びつけている。それらは GitHub Actions 上で走るので、既定では差分を超えて届くレビューはモデルの
使用量に加えて GitHub Actions の分数を消費する。その既定が唯一の構成というわけではない。ドキュメントは、セルフホストの
ランナーは Actions の分数を消費しないこと、そして GitHub ホストのランナーを無効にした組織はセルフホストのものを使えること、
そうしなければレビューはより限定された形へフォールバックすることに触れている。これらのケイパビリティが使えない場合でも
レビュー自体は生成され、ただそれらが加えるものを欠くだけである。これは用語についての独立した特徴づけではなく、あるベンダーに
よる自社製品のドキュメントであり、ここではそのようなものとして記録されている。

## ツールにおける用法

このウィキのソースに含まれる 2 つのオープンソースのプロジェクトは、上の 2 つ目の意味が定義するリポジトリに接地したタスクに
向けて作られており、そこから生じるループのどこまでをエージェントに任せてよいかで意見を異にしている。このラベルを自ら採用して
いるのは 2 つのうち一方だけである。AsyncReview は自らをエージェント型コードレビューだと率直に称するのに対し、
Open Code Review はこの形容詞を一度も使わず、自らをハイブリッドなアーキテクチャをもつ AI 駆動のコードレビュー CLI として
説明している。ここに記録されているのは、この用語を主張しているからではなく、その論がこのケイパビリティについてのものだから
である。

[[SoftwareApplication/asyncreview]] は最大限の読み方をとる。その README は、単純な差分の解析を超えて、自律的にリポジトリを
探索し、コンテキストを取得し、答える前にサンドボックスで発見を検証することを、推論し、Python のコードを生成し、それを実行し、
結果を観察するという再帰的なループの中で行うと説明している。他のレビューツールとの対比として掲げられているのは 4 つの組の
リストである。限られたコンテキストに対してリポジトリ内のどのファイルでも読めること、コードがどう動くかを推測する静的解析に
対して検索クエリと検証スクリプトを実行すること、ライブラリのメソッドをでっち上げることに対して実在するファイルパスと行を
引用すること、そして一発の生成に対して答える前に反復することである。このうち 3 つ目は、このアプローチが取り除こうとしている
失敗としてハルシネーションを名指ししており、これはタスクとしての意味が接地について行うのと同じ主張である。

[[SoftwareApplication/open-code-review]] は同じ前提を受け入れつつ — そのエージェントはファイルの全文を読み、コードベースを
検索し、変更された他のファイルを調べる — 別のものに反対して論じる。リポジトリへのアクセスにではなく、レビューのプロセスを
モデルに委ねてしまうことにである。そしてそれを、汎用のエージェントがこの仕事をしてきた記録から論じる。その README は、汎用の
エージェントをコードレビューに使うことに帰される 3 つの問題を述べている。大きめの変更セットではエージェントが手を抜き、一部の
ファイルだけをレビューして他を見落とすこと、報告される問題が実際のコードの位置からずれること、そしてプロンプトの些細な違いで
品質が揺れることである。掲げられている診断は、純粋に言語に駆動されたアーキテクチャはレビューのプロセスに対する硬い制約を
欠いているというものであり、その応答は 4 つのステップをモデルから取り上げることである。どのファイルをレビューするか、関連する
ファイルをどう隔離されたサブエージェントの単位へまとめるか、どのルールがどのファイルに一致するか、そしてコメントの位置決めと
内省のための 2 つの外部モジュールである。エージェントに残されるのは動的な判断と動的なコンテキストの取得だけになる。同じモデル
上の汎用のエージェントに対して、[[Dataset/aacr-bench]] で自ら実施した比較において、およそ 9 分の 1 のトークンでより高い
適合率と F1 を、意図的なトレードオフとしてより低い再現率とともに報告している。

どちらの記述もそれぞれのプロジェクト自身による自己説明であり、後者の数値は自ら実施した比較における自己報告の結果である。
両者が合わせて確立しているのは決着した答えではなく、この用語のタスクとしての意味が争われる領域になったということである。
共有された前提はレビューにリポジトリへのアクセスが必要だということであり、生きた問いは、そこから生じるループのどこまでを
モデルに走らせるべきかである。
