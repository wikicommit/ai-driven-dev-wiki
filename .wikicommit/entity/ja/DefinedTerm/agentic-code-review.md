エージェント型コードレビューとは、AI エージェントがレビュアーの役割を担うコードレビューを指す。このウィキが保持する 2 つのソースはこの用語を異なるレベルで使っており、どちらも他方の特殊な場合ではない。一方はプロジェクトのレビュー実践の段階を、他方は 1 回のレビューについてのタスク定義を指している。

[[ScholarlyArticle/from-human-centric-to-agentic-code-review]] は、この用語を、プロジェクトが経ていく可能性のある 3 つのコードレビューの時代のうち最も新しいものに使っている。この研究は、レビューが主として人間のプロセスである人間中心のレビュー、LLM 支援のレビュー、そして AI エージェントのレビュアーが人間のレビュアーや大規模言語モデルのレビュアーとともにレビュープロセスに参加するエージェント型コードレビューを区別している。これらの時代はこの研究が導き出した分類ではなく、研究が前提とする枠組みである。研究が実証的に特定しているのは、プロジェクトがそれらの時代のあいだを移行していく 3 つの導入パターンであり、207 の GitHub プロジェクトにおける 102 万件のレビュー済みプルリクエストから導かれている。

[[ScholarlyArticle/swe-review]] は、これをリポジトリに根ざしたタスクとして形式化している。1 つのレビューインスタンスは、該当するコミット時点のリポジトリのチェックアウト、自然言語で書かれたイシュー、そして差分・タイトル・本文を備えた候補のプルリクエストを提供し、正解パッチと非公開のテスト結果は伏せられる。レビュアーは、ファイルを閲覧し、コードを検索し、依存関係を調べ、コマンドを実行したうえで、2 つの項目からなるレポートを提出できる。1 つは承認するか変更を要求するかの二値の判断であり、もう 1 つは、変更を要求する場合の診断である。診断は具体的な欠陥を特定し、可能であればコードの位置を示し、後段の修正エージェントのために実行可能な修正案を提示する。

## 用法

時代という意味では、この用語は特定のツールではなく実践の段階を示す。プロジェクトは、その時代へどの導入パターン — Gradual AI Adoption（段階的な AI 導入）、Rapid LLM Adoption（急速な LLM 導入）、Rapid AI Agent Adoption（急速な AI エージェント導入）— をたどったかによって特徴づけられ、レビューでの議論は、人間、LLM、エージェントのレビュアーのあいだのやりとりの系列としてモデル化される。

この研究がこの時代について報告しているのは、ある分裂である。エージェントが関与する協働パターン、とりわけ AI エージェントが開始したレビューや複数の AI エージェントが関与するレビューは、3 つの導入パターンのうち 2 つにおいて、より速いレビュー判断と関連している。しかし著者らは、その効率の向上はより良いレビュー品質にはつながっていないと述べている。

タスクという意味では、その決定的な特徴は、レビュアーが差分を単独で読むのではなく、リポジトリの中で行動することにある。測定された優位性もそこにある。[[ScholarlyArticle/swe-review]] は、エージェント型レビューが、固定コンテキストの単一ターンのレビューを、判断の正確さと修正後の解決率の両方で上回ったと報告しており、その差が最も大きいのは、リポジトリの局所的でない推論を必要とするタスクである。これは、追加された能力によって得られるものが探索であるならば予想されるとおりの結果である。この枠組みでは、レビューは最後に付け加えられる論評の工程ではなく、[[DefinedTerm/generate-review-revise-loop]] の要となる。

2 つの用法は、何を証拠とみなすかについて異なる方向を向いている。時代の説明は観察に基づくもので、GitHub 上のプロジェクトが実際に何をしたかから引き出されており、速いことが良いことではないという点に慎重である。タスクの説明は構成された実行可能なもので、レビューを、その後にパッチがイシューを解決するかどうかによって採点する。エージェント型コードレビューに関する主張は、ソースがこの 2 つのどちらを意味しているかに照らして確かめる価値がある。

## ベンダーの用法

この形容詞の 3 つ目の用法はベンダー側から来ており、上の 2 つの意味のどちらよりも具体的なものを指しているので記録しておく価値がある。GitHub の [[SoftwareApplication/github-copilot-code-review]] のドキュメントには「Agentic capabilities for Copilot code review」という見出しの節があり、その見出しの下に置かれているのはレビュー全体ではなく、2 つの特定の能力である。1 つは完全なプロジェクトコンテキストの収集で、変更の文脈をより良く理解するためにリポジトリ全体を分析するもの、もう 1 つは提案を Copilot クラウドエージェントに渡す機能で、提案された修正を適用した新しいプルリクエストを作成するものである。同じドキュメントは、特定のプルリクエストはエージェント型レビューの対象になると述べ、この形容詞をレビューそのものにも使っている。したがって、この狭い読み方は 1 つの節の強調であり、ドキュメント全体を通じて保持されている定義ではない。

その強調が置かれる場所は、上のタスクの意味が線を引く場所とほぼ一致する — レビューをエージェント型にするのは、差分だけを読むのではなくリポジトリに対して行動することである。このドキュメントは、どちらの研究の説明にもそうする理由がない、これらの機能のコストにも触れている。これらの機能は GitHub Actions 上で動作するため、デフォルトでは、差分の外にまで及ぶレビューはモデルの使用量に加えて GitHub Actions の実行時間（分）を消費する。このデフォルトが唯一の構成というわけではない。ドキュメントは、セルフホストランナーは Actions の実行時間を消費しないこと、そして GitHub ホストランナーを無効にした組織はセルフホストランナーを使うことができ、そうしない場合はレビューがより限定された形式にフォールバックすることを記している。これらの機能が利用できない場合でもレビューは生成されるが、それらが付け加えるものは得られない。これは、ある 1 つのベンダーによる自社製品のドキュメントであって、この用語の独立した特徴づけではなく、ここではそのようなものとして記録している。

## ツールでの用法

このウィキのソースに含まれる 2 つのオープンソースプロジェクトは、上の 2 つ目の意味が定義する、リポジトリに根ざしたタスク向けに作られており、その結果生じるループのどこまでをエージェントに任せて実行させてよいかについて意見が分かれている。この呼び名を採用しているのは 2 つのうち一方だけである。AsyncReview は自らをはっきりとエージェント型コードレビューと呼ぶ一方、Open Code Review はこの形容詞を一度も使わず、自らをハイブリッドアーキテクチャを持つ AI 搭載のコードレビュー CLI と説明している。後者をここに記録するのは、それがこの用語を名乗っているからではなく、その主張がこの能力についてのものだからである。

[[SoftwareApplication/asyncreview]] は最大限の読み方をとる。その README は、単純な差分解析を超えて、回答する前にリポジトリを自律的に探索し、コンテキストを取得し、サンドボックス内で発見事項を検証すると説明しており、それは推論し、Python コードを生成し、それを実行し、結果を観察するという再帰的なループで行われる。他のレビューツールとの対比として同プロジェクトが挙げるのは 4 つの組み合わせである。限られたコンテキストに対してリポジトリ内のどのファイルでも読めること、コードの動作を推測する静的解析に対して検索クエリや検証スクリプトを実行すること、ライブラリのメソッドをでっち上げることに対して実在するファイルパスと行を引用すること、そして一度きりの生成に対して回答前に反復することである。このうち 3 つ目は、このアプローチが取り除こうとする失敗としてハルシネーションを名指ししており、これはタスクの意味がグラウンディングについて行う主張と同じである。

[[SoftwareApplication/open-code-review]] は同じ前提を受け入れている — そのエージェントはファイルの内容全体を読み、コードベースを検索し、他の変更されたファイルも調べる — が、それとは別のものに異を唱えている。リポジトリへのアクセスではなく、レビューのプロセスをモデルに委ねることである。同プロジェクトはこの主張を、汎用エージェントがこの仕事をしてきた実績から論じている。その README は、コードレビューに汎用エージェントを使うことに起因するとする 3 つの問題を挙げている。大きな変更セットではエージェントが手を抜き、一部のファイルだけをレビューして他を見落とすこと、報告された問題が実際のコードの位置からずれていくこと、そしてプロンプトのわずかな違いで品質が変動することである。同プロジェクトの診断は、純粋に言語駆動のアーキテクチャにはレビュープロセスに対する厳格な制約が欠けているというもので、その対応として 4 つのステップをモデルから取り上げている — どのファイルをレビューするか、関連するファイルをどのように分離されたサブエージェント単位にまとめるか、どのルールがどのファイルに適合するか、そしてコメントの位置決めとリフレクションのための一対の外部モジュールである — 。エージェントに残されるのは、動的な判断と動的なコンテキスト取得だけである。同じモデルを使った汎用エージェントと比べて、同プロジェクトは、トークン量がおよそ 9 分の 1 で、より高い適合率と F1 を達成し、意図的なトレードオフとして再現率は低くなったと報告している。これは [[Dataset/aacr-bench]] 上で同プロジェクト自身が行った比較である。

どちらの説明もそれぞれのプロジェクトによる自己記述であり、2 つ目の数値はそのプロジェクト自身が行った比較で報告された結果である。両者が合わせて示しているのは、決着のついた答えではなく、この用語のタスクの意味が争点となっているということである。共通の前提は、レビューにはリポジトリへのアクセスが必要だということであり、いま問われているのは、その結果生じるループのどこまでをモデルに実行させるべきかである。
