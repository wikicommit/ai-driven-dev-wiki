振る舞い評価（behavioral evaluation）とは、AI エージェントがタスク全体をエンドツーエンドで解決したかどうかを採点するのではなく、実行中にとる個別の観測可能なアクションに対してアサーションを行うことでエージェントを測定する実践である。たとえば、仕様が不十分なプロンプトを与えられたときに確認の質問をしたか、ビルドファイルの変更を完了と宣言する前にローカルのバリデーターを実行したか、記憶から答えるのではなくライブ検索を参照したか、といったことである。Google のエンジニアたちは、こうした評価はエージェントハーネスの動作を改善するための統合テストのように機能し、最終的な文字列の一致ではなく、特定のツール呼び出しやファイル変更といった中間的な実行ステップに対してアサーションを行うものだと説明している。

## 用法

この実践が対比によって定義される相手は、エンドツーエンドのベンチマークである。Google のエンジニアたちは、一般的なアプローチを、試験を受ける学生を評価するようにエージェントを評価するものだと特徴づけている。大きなコードベースを渡し、制限時間を課し、何件のテストが通るかで採点するというものである。そして、その結果得られる複合スコアが数パーセントポイント動いたとき、そうしたベンチマークは通常、その理由に直接答えてくれないと論じている。答えられないまま残る問いの例として彼らが挙げるのは、曖昧なプロンプトに対してモデルが過信するようになったのか、提出前にテストスイートを確認するのを忘れたのか、あるいは CLI のフラグをハルシネーションしたのか、といったことである。

彼らの説明では、振る舞い評価のアーキテクチャは、振る舞いに関するアサーションを、ローカルで実行される高速で決定論的なユニットテスト風のチェックへと切り分ける。彼らの例では、ローカルの振る舞いスイートが 5 秒未満で実行される。そうしたチェックが十分に揃えば、チームは狙っている振る舞いのベースラインを持つことができ、中核的な振る舞いが壊れたらすぐにわかる状態で、システムプロンプトを反復的に改善したりモデルを切り替えたりできる、と彼らは論じる。さらに彼らは、このスイートでプロンプトエンジニアリングを自動化できるとも示唆している。失敗しているテストが通るまで LLM が自らのシステムプロンプトを調整し、その間スイートの残りの部分は既存の機能を壊さないための CI/CD 的なガードレールとして働く、というものである。

別のベンダーも、この用語は使わないものの、同じ形のチェックをより狭い対象について説明している。OpenAI の [[BlogPosting/testing-agent-skills-systematically-with-evals]] は、それを [[SoftwareApplication/openai-codex]] 向けのエージェントスキルに適用している。各評価はプロンプトに対してエージェントを実行し、エージェントが行ったことを構造化された JSONL のイベントトレースとして記録し、そのトレースを決定論的なチェックで採点する。エージェントが `npm install` を実行したか、`package.json` が作成されたか、期待されるコマンドが期待される順序で実行されたか、といったチェックである。同記事は、あらかじめ定義しておくべき四種類の成功の一つとして、成果・スタイル・効率の目標と並んで「プロセス目標」——エージェントがスキルを呼び出し、意図されたツールとステップに従ったか——を挙げ、失敗の理由をトレースを開いてすべてのコマンド実行を順に読むことで説明できる点をこれらのチェックの価値としている。Google のエンジニアたちと同様に、固定されたチェックでは捉えられないものに対してはモデルによる採点のステップを加えている。スタイルと規約をルーブリックに照らして採点する、読み取り専用の二回目の実行であり、結果を実行間で比較できるよう JSON スキーマに制約されている。また、スキルの実行だけでなくスキルの発火もテストしており、少なくとも一つのネガティブコントロール——スキルを呼び出すべきではないプロンプト——を含む小さなプロンプト集合を用いて、スキルが過剰に発火することを検出する。

## 適用される場面

Google のエンジニアたちは、こうした評価をエージェント開発の第二段階に位置づけている。彼らが示す前提は、エージェントをゼロから立ち上げる際には開発者の直感とドッグフーディングから始めるべきであり、エージェントが自らのコードベースをドッグフーディングできるようになるまで——ボイラープレートを処理し、自前の Markdown レンダラーを書き、日常的な開発タスクを実行できるようになるまで——評価を実行することにはそもそも意味がない、というものである。評価は前進を確かなものにし、リグレッションを防ぐためのものであり、スイートの主な目的は 2% の改善を祝うことではなく、プロンプトの微調整、ツールスキーマの変更、あるいはモデルのアップグレードによってエージェントが全体として悪化していないという確信を与えることだと彼らは述べている。

この実践は、エージェントの中間ステップが観測可能でアサーションの対象にできること——彼らの例はレスポンスで返されるツール呼び出しに対してアサーションを行う——と、チームが保持する価値のある具体的な振る舞いを名指せることを前提としている。彼らが勧める出発点は三段階のループである。エージェントが実際に犯した最近の誤りから失敗モードを一つ選ぶこと、タスクの複雑さに見合ったアサーションを書くこと、そしてバッチ評価を自動化して安定性を監視することである。

彼らは、この実践が誤って適用される二つのケースを明示している。一つは、固定されたツールの順序に対して硬直的な単一ターンのアサーションを書くことで、これは複雑なタスクでは失敗する。モデルが予想外だが完全に正しい経路をとることがあるからである。そうしたタスクには、[[DefinedTerm/llm-as-a-judge]] のような、より柔軟で成果ベースのチェックを彼らは推奨している。もう一つは、単一の評価実行でプルリクエストをブロックすることで、モデルの非決定性によってノイズが多くなるため妥当ではない。彼らは集計した合格率を時系列で追跡し、その方向性のシグナルを行動の根拠とすることを推奨している。

どれほど確立されたものかについて言えば、Google の説明は一つのエンジニアリングチームが推奨する実践であり、雇用主の開発者ブログで公開され、自社の SDK を用いて例示されたものであって、測定された結果でも業界のコンセンサスでもない。OpenAI のガイドも同種の情報源であり、ベンダーが自社のエージェントについて推奨する実践で、測定結果は報告していない。OpenAI 版も段階的な出発点を共有しており、単一のスキルに対して 10〜20 個のプロンプトを推奨し、実際の失敗からその集合を育て、ビルドやランタイムのスモークテストのような遅いチェックはリスクを減らす場合にのみ追加するとしている。彼らは、これをより大きなエンドツーエンドのスイートを置き換えるものではなく補完するものとして慎重に提示している。彼らの捉え方では、マクロなベンチマークが最終的な到達点を検証し、ミクロな振る舞い評価が安全で迅速な反復を可能にするのであり、推奨は両方を採用することである。
