Ralph——『ザ・シンプソンズ』の登場人物にちなみ Ralph Wiggum 技法とも呼ばれる——とは、コーディングエージェントを無人で走らせるための技法であり、[[Person/geoffrey-huntley]] が [[BlogPosting/ralph-wiggum-as-a-software-engineer]] で名づけたものである。最も純粋な形では、固定のプロンプトファイルをエージェントへ何度も繰り返しパイプする Bash のループ（`while :; do cat PROMPT.md | claude-code ; done`）であり、1イテレーションにつき1タスクを行い、各イテレーションを新しいコンテキストウィンドウで始める。なぜこれが機能するかについての Huntley の特徴づけは、「この技法は非決定的な世界において決定的に悪い」というものである。どのループも識別可能な仕方で失敗するのであり、それらの失敗にはツールを変えるのではなくプロンプトへ指示を加えることで応じる。彼はこれを、ツール呼び出しと使用量に上限を設けないツールであれば何でも実用になると述べている。

## 用法

Huntley の説明はいくつかの運用規則を与えている。

**1ループにつき1項目。** エージェントは1イテレーションにつき1つのことを行うよう求められ、どれが最も重要かの選択は任される——彼はこれが完全に手放しのバイブコーディングに読め、「責任あるエンジニアリングと自分がみなすものの限界を試すことになる」と認めている。この制限はプロジェクトが安定するにつれて緩めてよく、結果が脱線し始めたら狭め直すべきである。

**決定的なスタック割り当て。** 各ループは同じものをコンテキストに置くべきである——計画ファイル（`fix_plan.md`）と仕様である。毎ループその割り当てを費やし直すのは無駄ではあるが、コンテキストウィンドウが埋まっているほど結果は悪くなるという理由による。

**スケジューラとしての一次コンテキストウィンドウ。** メインのウィンドウに割り当てるのではなく、ループはファイルシステムの検索やテスト実行の要約といった高価な作業に対して [[DefinedTerm/subagents]] を派遣すべきである。Huntley は、ビルドとテストのために数百のサブエージェントへ扇形に展開すると「悪い形のバックプレッシャー」が生じると指摘しており、それゆえ彼のプロンプトは検索とファイル書き込みには多数の並列サブエージェントを許しつつ、ビルドとテストには1つしか許さない。

**二つのフェーズ。** 生成は安価であり、仕様とプロジェクト固有の標準ライブラリによって舵取りされる。難しいのは誤った出力を却下することであり、それが [[DefinedTerm/backpressure]] の仕事である。

**標識を立てることによる調整。** 繰り返し現れる比喩は、Ralph が飛び降りる前に見るよう滑り台の脇に標識を立てることである。Huntley が挙げる二つの失敗モードは、エージェントが `ripgrep` を走らせて何かが未実装だと結論し、それを再び作ってしまうこと——決めつけないようにという指示で応じる——と、モデルのプレースホルダや最小限の実装への偏り——完全な実装を要求する、段階的に強くなる指示で応じる——である。彼は、モデルは自らの報酬関数を追いかけるのであり、その報酬関数はコンパイルの通るコードだと指摘している。

**将来のループのために推論を記録する。** 各イテレーションは新しく始まるため、エージェントはあるテストとその裏づけとなる実装がなぜ重要なのかを文書化するよう指示される。Huntley はこれを、その推論をコンテキストウィンドウに持たない将来のイテレーションへメモを残すことだと説明し、失敗しているテストを直すべきか、変えるべきか、消すべきかをモデルが判断する助けになると報告している。

**使い捨てとして扱われる TODO リスト。** ループは優先順位づけされた計画ファイルを保守し、それが陳腐化したときには別の計画用ループによって再生成される。Huntley は何度も削除したことがあり、それを「鷹のように」見張っていると述べている。

### 同じループについての二つ目の説明

[[BlogPosting/the-code-agent-orchestra]] はこのパターンを **Ralph ループ**の名で説明し、[[Person/geoffrey-huntley]] と Ryan Carson によって広められたと述べている——これは誰が技法を広めたかについての主張であって、誰が最初に作ったかについてのものではない。中核となる考えについての独自の枠づけは「ステートレスだが反復的」である。エージェントは各イテレーションでリセットされるため混乱を蓄積せず、継続性はコンテキストウィンドウの外で担われる。

そこで示されるサイクルは5ステップからなる。`tasks.json` ファイルから次のタスクを選び、変更を実装し、テスト・型・リントを走らせて検証し、チェックが通ればコミットしてタスクの状態を更新し、コンテキストをクリアして新しく始める。リセットを越えて記憶が生き延びる4つのチャネルが挙げられている。git のコミット履歴、進捗ログ、タスク状態ファイルそのもの、そして長期の意味記憶としての [[DefinedTerm/agents-md]] である。掲げられる安全策は、エラーを自動リトライのために戻す一方で、3イテレーション以上行き詰まったら打ち切って割り当て直すこと、常にフィーチャーブランチで作業すること、イテレーション・時間・トークンに厳格な上限を設けること、そしてマージ前に開発者がレビューするプルリクエストである。示される導入の道筋は、一晩に1ループから始め、10ブランチ上の10ループへと進むというものである。

同じ説明は、このパターンの上に築かれた二つの実装も記録している。Ryan Carson の単体ツール `ralph`（snarktank/ralph）は中核のループを実装しており、彼の Antfarm プロジェクトは同じパターンを用いて OpenClaw の上にマルチエージェントのオーケストレーションを重ねている。同記事の主張は、中核の考えがツールを越えて一般化するというものであり、これは上の Huntley 自身のより狭い適用範囲の言明を置き換えるのではなく、それと並び立つ。

### このループの行き着いた先

[[BlogPosting/survey-of-development-workflows-in-the-coding-agent-era]] は Ralph ループを長時間セッションの設計パターンのなかに位置づけ、それらすべてが一つの原理を共有すると述べている。コンテキストウィンドウをステートレスに保ち、ファイルシステムと git を永続的な保存領域として用いることである。その機構の説明は原典と一致する——`PROMPT.md` に置かれた目標仕様、1パスにつき1イテレーション分の作業、コンテキストが埋まるか作業が終わったら終了、そして新しいコンテキストでループが再開する——うえで、どのイテレーションも0% の充填率から始まるためコンテキストロットが避けられるという構造上の主張を加えている。同記事はこのパターンを2025年6月に位置づけ、Anthropic が2025年12月に公式の `ralph-wiggum` プラグインとして統合したことを記録している。

二つの拡張が挙げられている。Rust による実装である `ralph-orchestrator` は、テスト・リント・型チェックが通るまで前進を止めるバックプレッシャーのゲートに加え、7万トークンでの警告と8万トークンでの強制ローテーションを追加している。`oh-my-claudecode` の Ralph モードは、32の専門化されたエージェント、5つ以上の同時タスクの並列実行、そしてノートパッドファイルによるコンパクション耐性のある永続メモリを提供する。

同調査はまた、このループをセッション設計の複雑さのスペクトルのなかに置いている。1行の bash ループから、公式のループコマンド、手法としての [[DefinedTerm/frequent-intentional-compaction]]、2エージェント構成、19エージェントのフレームワークへと至るもので、優劣ではなく洗練の度合いの順である。

### エージェントチームのハーネスの土台としてのループ

[[BlogPosting/building-a-c-compiler-with-parallel-claudes]] は同じ形を出発点として用いており、そう明言している——著者は、Ralph ループを見たことがあれば、このハーネスは「見覚えがあるはずだ」と述べている。実装は bash の `while true` ループで、前のセッションが終了するや否や新しい Claude Code セッションを開始し、各実行を現在のコミットに紐づけて記録する。プロンプトはエージェントに、問題を小さな部分に分け、何に取り組んでいるかを追跡し、次に何をするかを決め、完璧になるまで続けるよう指示する。著者は、ループが永遠に回るため最後の点についてエージェントに選択の余地はないと指摘し、Claude が誤って自分のシェルを終了させてループを止めてしまった一件を記録している。

このプロジェクトがパターンに加えるのは並列性である。同じ生成ループが新しいセッションをそれぞれ新しいコンテナで立ち上げ、そうしたループが複数同時に走り、協調はエージェント間のプロトコルではなく共有リポジトリ内のロックファイルによって処理される。

## 関連用語

Ralph は [[DefinedTerm/agentic-coding]] の一つの具体的な実装であり、その自律的な端に位置する。エージェントに決めさせようとする姿勢において [[DefinedTerm/vibe-coding]] に近く——Huntley 自身がその語を Ralph に当てている——一方で、[[DefinedTerm/vibe-engineering]] や [[DefinedTerm/spec-driven-development]] が人間のレビューに置く規律を、[[DefinedTerm/backpressure]] と仕様に頼っている。[[DefinedTerm/multi-agent-orchestration]] とは意図的に異なる。Huntley は、当時エージェント間の協調は必要なかったと論じ、非決定的なエージェントをマイクロサービスとして扱うことを、単一のモノリシックなプロセスと比べて否定的に評価している。

その適用範囲は狭いと明言されている。Huntley はこれをグリーンフィールドのプロジェクトを立ち上げるための技法として提示し、おおよそ9割方まで進むことを見込むとし、既存のコードベースでは使わないだろうと率直に述べている。
