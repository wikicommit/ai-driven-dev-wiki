Agent2Agent プロトコル（略称 A2A）は、エージェントどうしがどのように通信するかを定める標準である。これは、
[[TechArticle/model-ai-governance-framework-for-agentic-ai]] がエージェントの中核的な構成要素の 1 つとして挙げる
プロトコル — エージェントがツールや他のエージェントと通信するための標準化された方法 — の 1 つであり、そこでは、
エージェントがツールと通信するために開発された [[DefinedTerm/model-context-protocol]] に対する、エージェント間の側の
対応物として位置づけられている。同フレームワークは、ここが急速に発展している領域であり、とりわけエージェント型コマースに
おいて、エージェント間のやりとりを標準化するためのプロトコルがさらに開発されつつあると述べている。

## 用法

同フレームワークでは、プロトコルは構成要素であると同時にリスクの源としても扱われている。プロトコルは不適切に配備されたり
侵害されたりしうるからであり、その例として、ユーザーのデータを外部に持ち出すコードを含む信頼できない MCP サーバーが
挙げられている。マルチエージェントのやりとりに関する推奨統制は A2A を名指ししてはいないが、あらゆるエージェント間の
チャネルに関わるものである。すなわち、エージェント間で意図しない指示が受け渡されるのを減らすため、自由記述のテキストでは
なく型付きの関数呼び出しのような構造化されたスキーマを通じて通信させること、そしてエージェント間の共有メモリへのアクセスを
制限することである。

報告されたある導入事例は、実際に使うとどのようなコストがかかるかを示している。
[[BlogPosting/agentic-engineering-swarms-of-ai-agents]] は、すべてのワーカーエージェントが A2A で通信し、A2A を
サポートしないエージェントには [[DefinedTerm/model-context-protocol]] のラッパーを介して到達するマルチエージェントの
エンジニアリングシステムを説明している。著者らは、統合したかった AI コーディングエージェントがネイティブの A2A 機能を
持っていないことに気づき、そのコーディングエージェントからのリクエストをワーカーエージェントへ中継する MCP アダプターツールを
構築した。著者らは、この構成によってシステムが IDE に依存しないものになったと述べている。

3 つ目のソースは、このプロトコルが現在どこまで進んでいるかを報告し、何と組み合わされつつあるかを挙げている。Jimmy Song の
オンラインハンドブック『智能体构建指南』のある章は、A2A を Google 主導のものと説明し、2026 年のアップデートで
エージェントディレクトリが導入されたと述べ、それによって組織をまたぎ、フレームワークをまたいだエージェントの発見と呼び出しが
可能になると位置づけている。また、主流の Python エージェントフレームワークの 1 つが最初にネイティブの A2A サポートを
得たことも報告している。同章はこの 2 つの出来事について、リリース日やバージョン番号にも触れているが、それらの根拠となる
発表はこのページのソースに含まれていないため、ここでは再掲しない。

同章がこの結果に与える枠組みは、業界が落ち着きつつあるという 2 つのプロトコルからなるスタックである。すなわち
**MCP はツールをつなぎ、A2A はエージェントをつなぐ** — 前者はエージェントが外部の機能にどう到達するかに、後者は
エージェントどうしがどう相互運用するかに答えるものであり、両者が合わさって
[[DefinedTerm/llm-based-multi-agent-system]] のプロトコル基盤をなす。2026 年のまとめの表では、MCP を事実上の
標準になったものとし、A2A を Google 主導のもので、エージェントディレクトリをその特徴的な追加要素としている。これらは
エコシステムの現状についての評価として述べられたものであり、測定された知見ではない。

4 つ目のソースは、エコシステムにおける位置づけではなく、このプロトコルの構成要素を説明している。jimmysong.io で公開されている
『AI 原生应用架构白皮书』（AI ネイティブアプリケーションアーキテクチャ白書）の第 3 章は、A2A を異種エージェント間の効率的な
通信と協調のためのオープン標準と呼び、3 つの中核的な役割 — ユーザー、A2A クライアント、A2A サーバー — と、5 つの主要な
要素を挙げている。すなわち、エージェントの能力とサービスエンドポイントを記述する JSON 形式のメタデータである
**Agent Card**、マルチターンのやりとりをサポートするステートフルな単位である **Task**、1 回のやりとりの基本単位である
**Message**、タスク完了時に生成される具体的な成果物である **Artifact**、そしてメッセージや成果物の中の最小のコンテンツ単位で
ある **Part** である。やりとりの仕組みとしてはポーリング、ストリーミング、プッシュ通知の 3 つを挙げ、フローとしては 3 つの
ステップ — A2A サーバーの Agent Card を発見する、認可と認証を行う、そして同期またはストリーミングの A2A リクエストを
送信する — を示している。

同章は、分散配備がもたらす問題として発見を扱っている。Agent Card をリモートエージェントのデジタル名刺と呼び、A2A
クライアントはそれを解析してそのエージェントを発見するとし、それを入手する方法として、直接設定、固定 URI、レジストリの
3 つを挙げる。最後のものについては、Nacos が A2A レジストリとして機能し、エージェントの登録・発見・取得を一元的に管理し、
エージェントのバージョン管理とグレーリリースをサポートすると説明しており、それによって分散エージェントシステムの保守性と
拡張性が高まると位置づけている。

5 つ目のソースは、発見の仕組みが実際に使われる様子を示している。Google の
[[BlogPosting/developers-guide-to-ai-agent-protocols]] は、リモートのエージェント — 異なるチームが、異なる
フレームワークで構築し、異なるサーバー上で動いている可能性がある — に宿る専門性への答えとして A2A を紹介し、一部のデータは
API では決して公開されないかもしれないが、エージェント的なインターフェースを通じてなら公開されうると指摘している。その説明
では、各 A2A エージェントは well-known パス `/.well-known/agent-card.json` で自らの名前・能力・エンドポイントを記述した
Agent Card を公開する。呼び出し側のエージェントはこれらのカードを取得して各リモートエージェントが何をするかを把握し、
実行時にクエリを適切なエージェントへルーティングする。そのため、新しいリモートエージェントを追加するにはその URL を追加する
だけでよく、コードの変更や再デプロイは不要である。同ガイドの実例は
[[SoftwareApplication/agent-development-kit]] を使っており、その `RemoteA2aAgent` は 1 ターンにつき 1 つの
リモートエージェントへルーティングする。1 つのクエリが複数のリモートエージェントに同時にまたがる場合、同ガイドは
`a2a-sdk` を直接使っている。同ガイドは A2A を 6 つのプロトコルからなるスタックの中に位置づけ、そこでの役割を一行で
要約している。すなわち、MCP はエージェントをツールやデータにつなぎ、A2A はエージェントを他のエージェントにつなぐ。
また、[[DefinedTerm/universal-commerce-protocol]] が A2A の well-known URL による発見のパターンを再利用しており、
A2A をトランスポートとしてその上で動作できることにも触れている。

新たに登場した 4 つのエージェント通信プロトコルのサーベイである
[[ScholarlyArticle/a-survey-of-agent-interoperability-protocols]] は、A2A を、能力に基づく Agent Card を使った
ピアツーピアのタスク委任を可能にし、エンタープライズのエージェントワークフローにまたがる安全でスケーラブルな協調を
サポートするものと要約している。同サーベイは A2A を [[DefinedTerm/model-context-protocol]]、
[[DefinedTerm/agent-communication-protocol]]、[[DefinedTerm/agent-network-protocol]] と比較しており、それが提案する
段階的な導入ロードマップでは、A2A は MCP（ツールへのアクセス用）と ACP（メッセージング用）の後に、協調的なタスク実行の
ために導入され、その後に分散型のエージェントマーケットプレイス向けの ANP へと導入が広がる。
