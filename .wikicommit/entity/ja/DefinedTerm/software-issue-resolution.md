**ソフトウェアイシュー解決**とは、開発者による自然言語での記述に基づいて、現実のコードリポジトリにおけるイシューを理解し、特定し、解決するタスクである。自動化されたエンドツーエンドの形態では、イシューの記述とコードリポジトリを入力として受け取り、そのイシューを解決するリポジトリレベルのパッチを生成する。バグ修正、機能追加、効率の最適化など多様な保守活動を含み、ソフトウェア保守の一部である。ソフトウェア保守は、[[ScholarlyArticle/agentic-software-issue-resolution-with-large-language-models]] によればソフトウェアのライフサイクルコストのおよそ 3 分の 2 を占める。

## 用法

この用語はタスクの境界を画定するために用いられる。上記のサーベイは、イシュー解決を自動プログラム修復の下位事例として扱うべきではないと、2 つの根拠から論じている。1 つは、修復よりも多様な保守活動を包含すること、もう 1 つは、バグ修正のイシューであっても、そのバグを引き起こすテストの存在を前提としないことである。2 つ目の点はシステムの構築方法に影響を及ぼす。報告された振る舞いを再現するテストを生成することが、所与のものではなく作業の一部になるからである。

同じサーベイは、自動化されたタスクを 5 つの論理的フェーズへと抽象化している。サーベイは、これらが固定された実行順序ではなく機能を表すことを強調しており、システムはそれらを順番に実行してもよいし、推論時に動的に織り交ぜてもよい。

- **リポジトリの前処理（Repo preprocessing）** — リポジトリについて、アクセスしやすく理解しやすい知識表現を構築すること。たとえばファイル、クラス、関数のツリーや、さらに呼び出し、継承、インポート、参照をエンコードしたグラフである。
- **位置特定（Localization）** — 報告されたイシューの原因である可能性が最も高いコード片を特定し、後続のフェーズの探索空間を絞り込むこと。
- **修復（Repair）** — 特定されたコードに対する候補パッチを生成すること。正しい修正を生み出す可能性を最大化するため、通常は複数生成する。
- **パッチ検証（Patch validation）** — イシューの状況を模擬する再現テストを生成するか、候補パッチが既存の振る舞いを壊していないことを確認する回帰テストを選択し、失敗したパッチを除外すること。
- **パッチ選択（Patch selection）** — 正規化されたパッチに対する自己一貫性投票によって、あるいはモデルに各候補をイシューに照らして評価させることによって、提出すべき最も有望な候補を選ぶこと。

サーベイは、これらのフェーズが十分条件ではなく診断のためのものであることを明言している。専用の位置特定手法は、下流のパッチ生成に投入された場合にエンドツーエンドの解決率を高めることが示されており、生成された再現テストは候補のフィルタリングと再ランキングに広く用いられている。しかし正しい位置特定が正しいパッチを保証するわけではなく、弱い再現テストは、もっともらしいが振る舞いとしては誤っているパッチを受け入れてしまうことがある。

[[ScholarlyArticle/advances-and-frontiers-of-llm-based-issue-resolution]] は、このタスクにフェーズ分解ではなく形式的な定式化を与えており、両者は両立する。インスタンスは `I = (D, C, T)`、すなわちイシューの記述、コードベース、対応するテストとして書かれ、そのうち解決中に観測可能なのは `D` と `C` だけであり、それに加えて探索可能な環境 `E` がある。手法はパッチ `P = M(D, C, E)` を生成することが求められ、そのパッチが適用されたうえで `T` を実行して評価される。このサーベイが用いる集計指標は **Resolved Rate** であり、データセット全体にわたるインスタンスごとの二値の結果の平均である。

このサーベイは、手法に関する文献を訓練不要（training-free）と訓練ベース（training-based）の 2 つに分けて整理している。訓練不要の手法は、フレームワーク（シングルエージェント、マルチエージェント、固定ワークフローの設計）、プラグアンドプレイのモジュール（リポジトリとのやり取りのためのツール、経験を蓄積するためのメモリ）、そして推論時スケーリングによって分類される。推論時スケーリングは、モデルのパラメータを変えずに探索や並列化を用いて成功率を高めるものである。訓練ベースの手法は、教師ありファインチューニングと強化学習に分かれる。このサーベイ自身の統計では、強化学習のロールアウトに最も広く使われているスキャフォールドは [[SoftwareApplication/openhands]] であり、それにワークフローベースの手法（とりわけ [[DefinedTerm/agentless]] と 2 段階のワークフロー）が続く。また R2E-Gym や SWE-Gym といった環境ネイティブのフレームワークも、訓練データと整合するため頻繁に採用されていると報告されている。

同じサーベイは、このタスクの証拠基盤について鋭く指摘している。エージェントの成功率は、解答の漏洩、曖昧なイシュー記述、誤ったパッチを検出できない弱いテストスイートによってしばしば水増しされていると報告し、手作業でのクリーンアップは大規模には高コストで一貫性を欠くため、この分野はモデルベースの合意を用いて有効な修正を偽陽性から切り分ける自動検証へと移行しつつあると述べる。サーベイが挙げる未解決の問題には、効率を考慮した評価の欠如（解決率は測定されるが API コストや推論時間は測定されず、高性能な手法の計算的・経済的な負担が見えにくくなっている）と、結果レベルの報酬への依存がある。後者は通常テストの合否という二値であり、サーベイは、マルチターンのタスクが必要とする多数の行動ステップにわたって、それが信用割り当てを曖昧にすると論じている。
