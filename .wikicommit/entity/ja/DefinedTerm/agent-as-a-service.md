Agent-as-a-Service（AaaS）は、[[ScholarlyArticle/agentic-software-restructuring-paradigm]] が商用ソフトウェア
提供の第 3 世代だと論じるものに与えた名称である。この論文の歴史の読み方では、各世代は複雑さをエンドユーザーから
引き離し、それを最もよく吸収できる側へと移してきた。ローカルにインストールするライセンス型ソフトウェアは
インストールと保守を顧客の側に残し、SaaS はサブスクリプションと引き換えにインフラと更新をベンダーへ移し、
AaaS はシステムを理解し、構築し、運用することをエージェントへ移して、成果に基づいて価格をつける。

この段階が前の段階と異なると論文が主張するのは、移される複雑さの*種類*である。SaaS は企業をサーバールームから
解放した — 運用上の複雑さである。論文の論に従えば、AaaS が企業を解放するのは、結果を*どう*生み出すべきかを
指定すること自体からである。顧客はどんな結果が欲しいかを指定すればよい。

## 用法

論文が示す相互作用のモデルでは、人間が意図と制約をエージェントに言語化して伝え、エージェントは自律的に計画し、
実行し（必要に応じてコードを生成し）、検証し、結果を届ける。そして人間はその成果を監査してフィードバックを返す。
エージェントは数千行のコードを生成し、データベースクエリを実行し、外部 API を呼び、可視化を生成しうるが、その
すべては一時的なものである。残るのは中間生成されたコードではなく、エージェントの能力である。

この語は単独で成り立つのではなく、同じ出典に由来する一連の関連概念の末尾に位置している。
[[DefinedTerm/agentic-software]] が成果物を名指し、[[DefinedTerm/agentic-engineering]] がそれを構築し統治する
規律を名指し、AaaS がそれが顧客に届くときの商業的な取り決めを名指す。論文がこの転換を圧縮して述べた
「AI → ソフトウェア → 結果」から「エージェント → 結果」へという表現は、エージェンティックソフトウェアに
ついて用いているのと同じものを、提供の側から読んだものである。

## 適用範囲

適用されるのは、そこへ至る道筋を指定せずとも結果を指定し監査できる場合であり、それはそのまま、この方式が破綻する
条件でもある。組織がどこから始めるべきかについての論文自身のリストは、その境界を実務的に言い換えたものである。
すなわち、成功基準が明確で、スコープが明確に定義されており、テスト基盤がすでに存在するタスクである。論文は、
すべてのソフトウェア作業がエージェントによる自動化に等しく適しているわけではないと直截に述べている。

前提となるのは、届けられた成果を判断できるだけの十分な評価シグナルである。このモデルの下では顧客は実装を検査する
のではなく結果を買っているからである。論文は、エージェントの出力の品質が評価シグナルの品質に決定的に依存すると
明言し、正しさにとどまらず堅牢性・保守性・ビジネス上の意図との整合性を測るテストスイートを構築することを
推奨している。

経済面について論文は結論を出さず、開かれたままにしている。価格づけは、緊急と見なす未解決問題の 1 つとして
挙げられている。解決されたイシューあたり、デプロイされた機能あたりといった成果ベースの価格づけが
サブスクリプション型や使用量型のモデルに取って代わるかもしれないが、インセンティブ構造とリスク配分は慎重な分析を
要する、と述べられている。用語としての AaaS は、境界が合意された確立したカテゴリーではなく、進行中だとこの論文が
論じる趨勢に対するこの論文自身の枠づけである。論文は各世代の代表例を挙げているが、それらをどう選んだかは
述べていない。
