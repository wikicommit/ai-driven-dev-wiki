Agent-as-a-Service（AaaS）とは、[[ScholarlyArticle/agentic-software-restructuring-paradigm]] が、商用ソフトウェア提供の第 3 世代であると論じるものに与えた名称である。その歴史の読み方によれば、各世代は複雑さをエンドユーザーから引き離し、それを最もよく吸収できる者へと移してきた。ローカルにインストールするライセンス型ソフトウェアでは、インストールと保守は顧客の側に残されていた。SaaS はサブスクリプションと引き換えに、インフラと更新をベンダーへ移した。AaaS は、システムを理解し、構築し、運用することをエージェントへ移し、その対価は成果に基づいて設定される。

論文が主張する、このステップを前のステップと分けるものは、移される複雑さの *種類* である。SaaS は企業をサーバールーム — 運用上の複雑さ — から解放した。論文の議論では、AaaS は企業を、結果が *どのように* 生み出されるべきかをそもそも指定しなければならないことから解放する。企業はどんな結果が欲しいかを指定するだけでよい。

## 用法

論文が示す相互作用モデルでは、人間が意図と制約をエージェントに伝え、エージェントが自律的に計画し、実行し（必要に応じてコードを生成し）、検証し、結果を届け、人間がその成果を監査してフィードバックを返す。エージェントは数千行のコードを生成し、データベースクエリを実行し、外部 API を呼び出し、可視化を作成することがあるが、それらはすべて一時的なものである。残るのは中間的なコードではなく、エージェントの能力である。

この用語は単独で存在するのではなく、同じ情報源に由来する一連の関連概念の終端に位置する。[[DefinedTerm/agentic-software]] は成果物を、[[DefinedTerm/agentic-engineering]] はそれを構築し統治する分野を、そして AaaS はそれが顧客に届く際の商業的な形態を指す。論文がこの転換を圧縮して表した言い方 — 「AI → Software → Result」から「Agent → Result」へ — は、エージェント型ソフトウェアについて用いたものと同じであり、それを提供の側から読んだものである。

## 適用される場面

結果へ至る経路を指定することなく、結果を指定し監査できる場合に適用される — そしてそれは、この形態が破綻する条件でもある。組織がまず何から始めるべきかについて論文自身が挙げるリストは、その境界を実務的に言い表したものである。明確な成功基準、明確に定義された範囲、既存のテスト基盤を備えたタスクである。論文は、すべてのソフトウェア作業が等しくエージェントによる自動化に適しているわけではないと明言している。

このモデルでは顧客は実装を検査するのではなく結果を買うことになるため、提供された成果を判断するのに十分な評価シグナルを前提とする。論文は、エージェントの出力の質は評価シグナルの質に決定的に依存すると明示しており、正しさにとどまらず、堅牢性、保守性、ビジネス上の意図との整合性まで測定するテストスイートを構築することを推奨している。

論文は経済的な側面を決着済みとはせず、未解決のまま残している。論文は価格設定を、急を要すると考える未解決の問題の 1 つに挙げている。成果ベースの価格設定 — 解決された Issue ごと、デプロイされた機能ごと — がサブスクリプション型や従量課金型のモデルに取って代わる可能性はあるが、インセンティブ構造とリスク配分には慎重な分析が必要だと述べている。用語としての AaaS は、合意された境界を持つ確立したカテゴリではなく、進行中だと論文が主張する流れについての、この論文自身の枠組みである。論文は各世代について代表例を挙げているが、それらがどのように選ばれたかは述べていない。
