Agent-as-a-Service（AaaS）は、[[ScholarlyArticle/agentic-software-restructuring-paradigm]] が商用ソフトウェア
提供の第 3 世代だと論じるものに与えた名称である。この論文による歴史の読み解きでは、各世代は複雑さをエンドユーザー
から引き離し、それを最もよく吸収できる側へと移してきた。ローカルにインストールするライセンス型ソフトウェアは
インストールと保守を顧客側に残し、SaaS はサブスクリプションと引き換えにインフラと更新をベンダーへ移し、AaaS は
システムを理解し、構築し、運用することをエージェントへ移して、成果に基づいて価格をつける。

この段階が前の段階と異なると論文が主張するのは、移される複雑さの*種類*である。SaaS は企業をサーバールームから
解放した — 運用上の複雑さである。論文の主張によれば、AaaS は企業を、結果を*どう*生み出すべきかを指定すること
そのものから解放する。企業は望む結果を指定するだけでよい。

## 用法

論文が示すインタラクションモデルでは、人間が意図と制約をエージェントに伝え、エージェントが自律的に計画し、
実行し（必要に応じてコードを生成し）、検証し、結果を届け、人間はその成果を監査してフィードバックを返す。
エージェントは何千行ものコードを生成し、データベースクエリを実行し、外部 API を呼び出し、可視化を作成することが
あるが、それらはすべて一時的なものである。残るのは中間的なコードではなく、エージェントの能力である。

この用語は単独で成り立つものではなく、同じ出典に由来する一連の関連概念の終端に位置する。
[[DefinedTerm/agentic-software]] は成果物を、[[DefinedTerm/agentic-engineering]] はそれを構築し統制する分野を、
そして AaaS はそれが顧客に届く商業的な形態を指す。論文によるこの転換の要約 — 「AI → ソフトウェア → 結果」から
「エージェント → 結果」へ — は、エージェント型ソフトウェアについて用いているものと同じであり、それを提供の側
から読んだものである。

## 適用範囲

AaaS が適用できるのは、そこへ至る道筋を指定せずに結果を指定し監査できる場合であり、これはそのまま、成り立たなく
なる条件でもある。組織がまず何から始めるべきかについて論文自身が挙げるリストは、この境界を実務的に言い換えた
ものである。すなわち、明確な成功基準、明確に定義されたスコープ、既存のテスト基盤をもつタスクである。論文は、
すべてのソフトウェア作業が等しくエージェントによる自動化に向いているわけではないと明言している。

このモデルでは顧客は実装を検査するのではなく結果を買うため、届けられた成果を判断できるだけの質をもつ評価シグナル
が前提となる。論文は、エージェントの出力の質は評価シグナルの質に決定的に依存すると明言し、正しさにとどまらず、
堅牢性、保守性、ビジネス上の意図との整合性まで測るテストスイートを構築することを推奨している。

論文は経済面を確定したものではなく未解決のものとして残している。価格づけを、緊急性が高いと考える未解決問題の
1 つに挙げている。成果ベースの価格づけ — 解決された課題ごと、デプロイされた機能ごと — がサブスクリプション型や
従量課金型のモデルに取って代わる可能性があるが、インセンティブ構造とリスク配分には慎重な分析が必要だと述べている。
用語としての AaaS は、進行中だと論文が論じる流れに対するこの論文独自の捉え方であり、境界について合意のある確立した
カテゴリーではない。論文は各世代の代表例を挙げているが、それらをどう選んだかは述べていない。
