構造化クエリ（Structured query）とは、両方を含む単一の文字列ではなく、プロンプト（指示）とデータという 2 つの別々の部分からなる LLM への入力である。これは [[ScholarlyArticle/struq]] で、プロンプトインジェクションに対する汎用的なアプローチとして提案された。その議論によれば、既存の LLM は設計上安全でない API を公開しており、そこではアプリケーション開発者がプロンプトとデータを連結し、1 つにまとめた入力としてモデルに送ることが想定されている。そして自然な対策は、制御部分がデータ部分と分離して提示されるよう API を変更することである。プロンプト部分にある指示にのみ従い、データ入力にある指示には決して従わないよう訓練された LLM は、プロンプトインジェクションに対して免疫をもつことになる。ユーザーが影響を及ぼせるのは、モデルが指示を探さないよう教えられたチャネルだけだからである。

## 用法

論文はこのアイデアに、言語モデルについての第一原理からではなく、類推によって到達している。[[DefinedTerm/prompt-injection]] を古典的なインジェクションのパターンの最新の事例として扱う。そこでは制御とデータが同じチャネルで送られ、悪意をもって構築されたデータがコマンドを偽装できる。例として、交換機が聞き取っていたのと同じ音声チャネルを通じて phone phreaker たちが受話器に流した 2600 Hz のトーン、データベース API がコマンドの種類と照合する値とを混ぜた 1 つの文字列を受け付けるために生じる SQL インジェクション、HTML ページがマークアップとページの内容を混ぜた 1 つの文字列であるために生じるクロスサイトスクリプティング、そして Unix シェルがプログラム名や区切り文字と引数を混ぜた単一の文字列を実行するために生じるコマンドインジェクションが挙げられている。論文の読みでは、いずれの場合も最も堅牢な解決策は両者を混ぜるのをやめることであった。その代表例として挙げられているのが SQL のプリペアドステートメントであり、クエリテンプレートを 1 つの引数、パラメータを別の引数として受け取ることで、設計上安全でない API を設計上安全な API に変えるものである。

構造化クエリをサポートするシステムを構築するための研究課題として 3 つが挙げられている。セキュリティ、すなわちシステムがいかなる条件下でもデータ部分にある指示を実行してはならないこと。有用性、すなわち能力の面で既存の LLM に近い水準を保たなければならないこと。そして実現可能な訓練、すなわち最先端の LLM をゼロから訓練するには数百万ドルのコストがかかるため、既存の LLM 技術の上に構築する方法を見つけなければならないことである。StruQ はこの 3 つ目に対する論文の答え — 既存のベースモデルに適用されるフロントエンドと [[DefinedTerm/structured-instruction-tuning]] — であり、論文はこれをビジョンの完成ではなくそこに向けた第一歩と位置づけ、他の研究者により堅牢な実装を見つけるよう呼びかけている。

## 適用される場面

このアプローチは、開発者が API やライブラリを通じてモデルを呼び出し、プロンプトとデータを別々に受け取るモデルを進んで使う可能性がある、プログラムによる LLM 統合アプリケーションに適用される。論文は、複数ターンの自由な会話を提供する Web ベースのチャットボットには適用できないと述べている。エンドユーザーが、自分の入力のどの部分が指示でどの部分がデータかを明示することを喜ぶとは考えにくいというのがその理由である。これは特にプロンプトインジェクションに対する防御であり、論文はジェイルブレイク、データ抽出、その他の LLM への攻撃を防ぐようには設計されていないと述べている。その証拠は 1 つの実装であり、著者ら自身が 2 つの 7B のオープンソースモデルで評価したものである。論文自身の結論は、構造化クエリは決着のついた方向ではなく、有望な方向だというものである。
