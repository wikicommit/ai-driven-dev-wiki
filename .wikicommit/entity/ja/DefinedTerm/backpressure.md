バックプレッシャーとは、[[Person/geoffrey-huntley]] が [[BlogPosting/ralph-wiggum-as-a-software-engineer]] でエージェンティックループについて用いる語であり、無効なコード生成を却下するためにループへ組み込まれるもの全般を指す。彼の捉え方は無人のループを二つのフェーズに分ける。いまや安価になった生成と、「エンジニアの帽子をかぶる必要がある」バックプレッシャーである——コードを生成するのが容易になれば、難しいのは正しいものが生成されたと確かめることになるからである。

## 用法

Huntley の主張は、機械可読な合否を出すものなら何でもこの役割を果たせるというものである。型システム、テストスイート、静的解析器、セキュリティスキャナ。静的型付け言語は型システムを通じてその一部を本質的に備えている。動的型付け言語については、静的解析器や型チェッカを明示的に組み込むことを強調し、Erlang の Dialyzer と Pyrefly を例に挙げ、これを省くと「結果の焚き火」になると警告している。

彼が強調する選定基準は、厳密さだけでなくスループットである——「正しさの軸との釣り合いのなかで問題になるのは、車輪が回る速さだ」。彼の実例は Rust である。コンパイラが極度の正しさを要求するという理由で CURSED に採用した一方で、コンパイルが遅いことと、モデルが初回で正しい Rust を出すのが苦手であることが試行回数を増やしループを遅くすると指摘し、それを誤りではなくトレードオフとして提示している。

彼のループの定番プロンプトは、生成と即時の検証を組にする。機能を実装したり問題を解決したりした後、そのコード単位のテストを実行すること、そして欠けている機能はスタブで済ませるのではなく仕様に従って追加すべきものとして扱うことである。彼はこの義務を無関係な失敗にまで広げ、現在の作業の外で壊れたテストも同じ変更の増分の一部として直すようエージェントに指示している。

この語には同じ記事の中に、第二の、正反対の意味もある。Huntley は、数百の並列 [[DefinedTerm/subagents]] へ扇形に展開してすべてにビルドとテストを走らせると「悪い形のバックプレッシャー」が生じると警告している——ここではループを守るチェックではなく、ループを劣化させる競合を意味する。彼のプロンプトが検索とファイル書き込みには多数のサブエージェントを許しつつ、ビルドとテストには1つしか許さないのはそのためである。

### 検証もまたコンテキスト効率的でなければならない

[[BlogPosting/skill-issue-harness-engineering-for-coding-agents]] はこの語を Huntley の第一の意味で用いつつ、彼の説明にはない制約を加えている。チェックは実時間で速いだけでなく、コンテキストの上でも安価でなければならない。そこで掲げられる中核的な洞察は彼のものと一致する——コーディングエージェントで問題を解ける見込みは、エージェントが自らの作業を検証できる能力と強く相関する——のであり、同チームはこれらの機構を自分たちのリポジトリに組み込むことを「時間を費やしたなかで最もレバレッジの高いことの一つ」と呼んでいる。その一覧は、型チェックとビルドステップ、単体テストと統合テスト、カバレッジが下がったときにエージェントを促す Stop フック付きのカバレッジレポート、そして UI 操作のテストである。

この制約は、彼らが報告する具体的な失敗から来ている。変更のたびに完全なテストスイートを走らせたところ、成功したテストの4,000行がコンテキストウィンドウを埋め尽くし、その後エージェントは実際のタスクを見失い、直前に読んだテストファイルについて幻覚を語りはじめた。彼らの対処は出力を飲み込んでエラーだけを表に出すことで、ビルドにも同じく適用された——成功は沈黙、失敗は饒舌に。同じ記事は、5分かかるテストスイートを毎セッションの最後に走らせることを、うまくいかなかったことの一つに挙げ、代わりに部分集合を推奨している。

## 関連用語

バックプレッシャーは [[DefinedTerm/ralph]] の検証側の半分であり、その根底にある考え——合否を返す何かをエージェントに与え、人間を挟まずにループを閉じる——は [[DefinedTerm/agentic-coding]] の実践全般に繰り返し現れる。関連する機構には、[[DefinedTerm/vibe-engineering]] が LLM が報いる実践として挙げる自動テストと継続的インテグレーション、チェックする側が決定的なツールではなく別のモデルである [[DefinedTerm/llm-as-judge]] の品質ゲート、そして [[DefinedTerm/agent-hooks]] のもとで扱われるイベント駆動のチェックがある。
