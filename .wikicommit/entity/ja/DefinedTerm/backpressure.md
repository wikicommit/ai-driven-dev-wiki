バックプレッシャーとは、[[Person/geoffrey-huntley]] が [[BlogPosting/ralph-wiggum-as-a-software-engineer]] においてエージェンティックループについて用いる語であり、不正なコード生成を拒絶するためにループに組み込まれるもの全般を指す。彼の枠づけは無人のループを2つのフェーズに分ける。いまや安価になった生成と、「エンジニアリングの帽子をかぶる必要がある」バックプレッシャーである——コードを生成するのが容易になれば、難しいのは正しいものが生成されたことを保証するほうになるからだ。

## 用法

Huntley の主張は、機械可読な合否を出すものであれば何であれこの役割を果たせる、というものである。型システム、テストスイート、静的解析器、セキュリティスキャナである。静的型付け言語は型システムを通じてその一部を本来的に備えている。動的型付け言語については、静的解析器や型チェッカーを明示的に組み込むことを強調し、Erlang の Dialyzer や Pyrefly を例として挙げ、これを省くと「結果の焚き火」になると警告する。

彼が強調する選定基準は、厳格さだけではなくスループットである——「正確性の軸と釣り合わせた、車輪の回る速さこそが重要だ」。彼の具体例は Rust である。コンパイラが極端な正確性を要求するという理由で CURSED に Rust を選んだ一方、コンパイルが遅いことと、モデルが最初の試行で正しい Rust を書くのが難しいことが試行回数を増やしてループを遅くすることも認めている。彼はこれを誤りではなくトレードオフとして提示している。

彼のループの定番のプロンプトは、生成と即時の検証を対にする。機能を実装したり問題を解決したりした後は、そのコード単位のテストを実行し、欠けている機能はスタブで済ませるのではなく仕様に従って追加すべきものとして扱う。彼はこの義務を無関係な失敗にまで広げ、現在の作業の外で壊れたテストも同じ変更のインクリメントの一部として直すようエージェントに指示している。

この語には、同じ記事の中で第二の、正反対の意味もある。Huntley は、数百の並列な [[DefinedTerm/subagents]] に扇形展開してすべてにビルドとテストを走らせると「悪い形のバックプレッシャー」が生じると警告する——ここではループを守るチェックではなく、ループを劣化させる競合を意味している——。だからこそ彼のプロンプトは、検索とファイル書き込みには多数のサブエージェントを許す一方、ビルドとテストには1つしか許さない。

## 関連用語

バックプレッシャーは [[DefinedTerm/ralph]] の検証を担う半分であり、その根底にある考え——合否を返す何かをエージェントに与え、人間を介さずにループが閉じるようにする——は [[DefinedTerm/agentic-coding]] の実践全般に繰り返し現れる。関連する仕組みには、[[DefinedTerm/vibe-engineering]] が LLM の恩恵を引き出す実践として挙げる自動テストと継続的インテグレーション、チェックする側が決定論的なツールではなく別のモデルである [[DefinedTerm/llm-as-judge]] の品質ゲート、そして [[DefinedTerm/agent-hooks]] で扱われるイベント駆動のチェックがある。
