イニシャライザーエージェントとは、長時間にわたる実行における最初のエージェントセッションであり、後続のセッションとの違いはプロンプトだけである。タスクを前に進める代わりに、以降のすべてのセッションが依存する土台を用意する。この用語の出典となった記述では、それは次のものを作ることを意味する。開発サーバーを起動できる `init.sh` スクリプト、エージェントがこれまでに行ったことを記録する進捗ファイル、追加されたファイルを示す最初の git コミット、そしてユーザーのプロンプトが含意するすべての機能を、それぞれ「まだ通っていない」状態として記した構造化リストである。出典は、この分離がプロンプトのみによるものであることを明言している — システムプロンプト、ツールセット、ハーネスは、それ以外の点ではコーディングエージェントのものと同一である。

## 用法

この役割は、特定の失敗に対処するために存在する。高レベルの目標を与えられた [[DefinedTerm/long-running-agent]] は、全体を一度にこなそうとして実装の途中でコンテキストを使い果たしがちである。また、ある程度の進捗ができると、後のセッションが周囲を見回し、作業が済んでいるのを見て、仕事は完了したと宣言してしまうことがある。どちらもセッション内の振る舞いを改善しても解決しない。どちらのセッションも、タスク全体として何が必要なのかを見ることができないからである。作業を事前に列挙しておくこと — すべての項目が失敗状態にある機能リスト — によって、後続の各セッションは、完全な機能の明確な輪郭と、次にやるべき紛れのない一手の両方を得る。

このエージェントが生成する成果物は、git 履歴とともに、新しいコンテキストウィンドウが状況を把握するために読むものである。出典は、試行を経て機能リストに JSON を選んだと報告しており、その理由として、モデルは Markdown ファイルよりも JSON ファイルのほうを不適切に変更したり上書きしたりしにくいことを挙げている。さらに、後続のエージェントには機能の合否ステータスの編集のみを許可し、テストの削除や編集を強い言葉で禁じる指示を与えることで、これを補強している。

## 適用される場面

このパターンは、複数のコンテキストウィンドウにまたがるほど大きなタスクであり、かつ検証可能な機能へと事前に分解できるほど具体的な目標であることを前提とする — 実例では、ひとつのプロンプトが 200 以上の機能に展開された。また、後続のセッションが共有する永続的なストレージを前提とする。仕組み全体が、ディスク上の成果物と git 履歴で成り立っているからである。さらに、後続の各セッションが実際に機能を検証できることも前提としており、出典の環境ではそれはブラウザ自動化を意味していた。

その誤用は、このパターンが正す失敗の裏返しである。プロンプトが要求するものを見越していない機能リストは、後続のセッションを誤った輪郭に向かって作業させてしまう。そして、後続のエージェントがそのリストを書き換えることに対する出典自身の防御策は、強制ではなくプロンプトの文言にすぎない。どの程度確立された手法かは、その出自を念頭に置いて読むべきである — これは Anthropic が、自社の SDK で構築した単一のフルスタック Web アプリケーションに関する社内での試行から報告したものであり、考えられる解決策のひとつとして提示されている。専門化したエージェントによるマルチエージェントアーキテクチャのほうがうまくいくかどうかは、明示的に未解決のまま残されている。[[BlogPosting/effective-harnesses-for-long-running-agents]] を参照。
