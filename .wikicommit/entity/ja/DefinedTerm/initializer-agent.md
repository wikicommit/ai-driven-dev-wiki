イニシャライザーエージェント（initializer agent）とは、長時間にわたる実行における最初のエージェントセッションであり、後続のセッションとはプロンプトのみによって区別される。タスクを前に進める代わりに、それ以降のすべてのセッションが依存する土台を築く。この用語の出典となった記述では、それは次のものを書くことを意味する。開発サーバーを起動できる `init.sh` スクリプト、エージェントが何を行ったかを記録する進捗ファイル、追加されたファイルを示す最初の git コミット、そしてユーザーのプロンプトが含意するすべての機能を、それぞれ未通過とマークした構造化されたリストである。出典は、この区別がプロンプトだけによるものであることを明言している — システムプロンプト、ツールセット、ハーネスはそれ以外の点ではコーディングエージェントのものと同一である。

## 使われ方

この役割は、特定の失敗に対処するために存在する。高水準の目標を与えられた [[DefinedTerm/long-running-agent]] は、すべてを一度に試みようとして実装の途中でコンテキストを使い果たしがちである。また、ある程度の進捗が存在するようになると、後続のセッションが周囲を見回し、作業が行われていることを見て、仕事は完了したと宣言してしまうことがある。どちらもセッション内の振る舞いを改善することでは解決しない。いずれのセッションも、タスク全体として何が求められているかを見ることができないからである。作業を事前に列挙しておくこと — すべての項目が未通過である機能リスト — によって、後続の各セッションには、完全な機能の明確な輪郭と、次に行うべき曖昧さのない作業の両方が与えられる。

このエージェントが生成する成果物は、git の履歴とともに、新しいコンテキストウィンドウが状況を把握するために読むものとなる。出典によれば、機能リストには試行錯誤の末に JSON が選ばれた。その理由は、モデルが Markdown ファイルよりも JSON ファイルのほうを不適切に変更したり上書きしたりしにくいという点にある。さらに、後続のエージェントには機能の通過状態のみの編集を許し、テストの削除や編集を強い言葉で禁じる指示によって、これを補強している。

## 適用される場面

このパターンは、複数のコンテキストウィンドウにまたがるほど大きなタスクと、検証可能な機能へと事前に分解できるほど具体的な目標を前提としている — 実例では、1 つのプロンプトが 200 を超える機能へと展開された。また、後続のセッションが共有する永続的なストレージを前提としている。仕組み全体がディスク上の成果物と git の履歴からなるからである。さらに、後続の各セッションが実際に機能を検証できることを前提としており、出典の環境ではそれはブラウザ自動化を意味した。

その誤用は、このパターンが解決する失敗の裏返しである。プロンプトが求めるものを見通せていない機能リストは、後続のセッションを誤った輪郭に向かって作業させることになる。また、後続のエージェントがそのリストを書き換えることに対する出典自身の防御は、強制ではなくプロンプトの文言によるものである。どの程度確立されたものかは、その来歴を踏まえて読むべきである — これは Anthropic が、自社の SDK で構築した単一のフルスタック Web アプリケーションに対する内部実験から報告したものであり、ありうる解決策の 1 つとして提示されている。専門エージェントからなるマルチエージェントアーキテクチャのほうがよりよい結果を出すかどうかは、明示的に未解決のまま残されている。[[BlogPosting/effective-harnesses-for-long-running-agents]] を参照。
