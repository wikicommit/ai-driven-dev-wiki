コンテキスト盲目性は、構造化されたエージェンティックワークフローをもってしても解消されないと [[ScholarlyArticle/spec-kit-agents]] が述べる失敗モードに与えられた名称である。エージェントの中間成果物は、内部的には首尾一貫していながら、現に存在するリポジトリとは両立しないことがある。同論文が引く区別は、*誤っている*成果物と、単に*係留を失っている*成果物とのあいだにある——仕様や計画は完璧に自己整合的でありながら、なお実在しないものを指していることがあるのだ。

## 用法

論文が挙げる症状は、存在しない API を参照すること、存在しないファイルパスを提案すること、そしてローカルなアーキテクチャ上ないしスタイル上の規約に違反することである。この失敗がなぜ重大なのかについての説明は、頻度ではなくタイミングに関わる。こうした誤りが実装中やテスト実行中といった遅い段階で表面化すると、エージェントはしばしば後戻りし、先行する成果物を改訂し、あるいはさらなる不整合を持ち込む——その結果、誤りは計画、タスク分解、実装の各段階を通じて複合し、無駄な反復と信頼できない結果を生むことになる。

論文はこの用語を、段階的なワークフローそれ自体で十分だという前提に対置している。中間成果物を外部化することが意図を明示的にし、監査証跡を提供すること、そして原理的にはこの「コーディングの前に推論する」という構造が信頼性とデバッグ容易性を高めるはずであることは認める——だが実際には、構造だけでは、成果物が対象とするコードベースと両立するために必要なリポジトリ側の証拠を供給しない、と論じる。

そこから導かれる処方は診断に従っている。グラウンディングを、計画と生成を行うのと同じエージェントの軌跡内の振る舞いにするのではなく、明示的なワークフロー上の操作にせよ、というものだ。著者らは、グラウンディングを生成エージェント自身の責務に委ねると、プロンプト設計とコンテキストウィンドウのノイズに左右されやすいままになると論じ、それに対して各段階の前にフェーズごとに範囲を限った読み取り専用のプロービングを行い、段階の後に成果物を検証するほうが、再現性があり検査もしやすいとする。
