コンテキスト盲目（context blindness）とは、[[ScholarlyArticle/spec-kit-agents-context-grounded-agentic-workflows]] において、構造化されたエージェント型ワークフローを採用しても残り続ける失敗モードに付けられた名前である。エージェントの中間成果物——仕様、実装計画、タスクのチェックリスト——は、それ自体としては首尾一貫していながら、実際に存在するリポジトリとは相容れないことがある。この用語が指すのは、成果物の内部の不整合ではなく、とくに成果物とコードベースとの食い違いであり、だからこそこれはワークフローの構造を経ても残る。仕様は内部の一貫性についてレビューされて合格しうる一方で、それが記述しているリポジトリのほうは仕様と一致していない、ということが起こるのである。

## 用法

この用語を導入した文献は、三つの症状を挙げている。存在しない API を参照すること、存在しないファイルパスを提案すること、そしてローカルなアーキテクチャ上またはスタイル上の規約に違反することである。同文献はまた、進化し続けるコードベースで複数ステップのタスクが失敗する理由として、現在のアーキテクチャについてのコンテキストの欠如、依存関係についての古くなった前提、リポジトリの規約との食い違いを挙げている。

同文献の説明によれば、この状態を高くつくものにしているのは、それが起こること自体よりも、それがいつ発見されるかである。誤りは実装やテストの実行の段階になって遅れて表面化し、その時点でエージェントは後戻りしたり、以前の成果物を修正したり、さらなる不整合を持ち込んだりする。そのため失敗は、計画、タスク分解、実装といった段階をまたいで積み重なっていく。同文献はこれを、無駄な反復と信頼できない結果を生むものとして描いている。

この用語は解決策の必要性を示すために導入されたものであり、そのため一つの診断を暗に含んでいる。すなわち、計画と生成を行うのと同じエージェントが軌跡の中で行う振る舞いとしてグラウンディングを扱うと、それはプロンプト設計やコンテキストウィンドウのノイズに左右されやすい、という診断である。これと併せて提案されている対応は、グラウンディングと検証をワークフローの明示的な操作にすること——各フェーズの前にリポジトリを探り、各フェーズの後で各中間成果物を環境と照合すること——であり、これによって、存在しないパスを参照する計画は、そこからコードが生成される前に捕捉される。

用語としては新しく、ただ一つの文献に依拠している。その文献はこの用語を、他者がすでに使っている用語として確立するためではなく、自らの貢献を位置づけるために用いている。
