マルチエージェントオーケストレーションとは、それぞれが自らのコンテキストウィンドウを持つ複数のエージェントへ作業を分割し、リードエージェントないしオーケストレーターがそれらを協調させる実践である。掲げられる二つの動機は、コンテキストの分離——単一のウィンドウがすべてを蓄積しない——と並列性である。別々のエージェントが問題の異なる部分を同時に探索できるからである。これは、コンテキストウィンドウが有限の資源であることに対する標準的な答えの一つであり、[[DefinedTerm/compaction]] や [[DefinedTerm/agentic-memory]] と並ぶ。

## 用法

[[TechArticle/effective-context-engineering-for-ai-agents]] はこのアーキテクチャを具体的に説明している。一つのエージェントがプロジェクト全体にわたって状態を保つのではなく、専門化されたサブエージェントがきれいなコンテキストウィンドウで焦点の絞られたタスクを扱い、メインのエージェントが高水準の計画で協調する。各サブエージェントは数万トークン以上を使って広く探索するかもしれないが、返すのは凝縮された要約だけである——同記事はおよそ1,000〜2,000トークンという数字を挙げている。掲げられる利点は関心の明確な分離であり、詳細な検索のコンテキストはサブエージェントの内側に隔離され、リードエージェントが結果を統合し分析する。同記事はまたこの手法をタスクの形に対応づけており、並行的な探索が報われる複雑な調査と分析に推奨している。対話的なやり取りにはコンパクション、明確なマイルストーンを伴う反復的な開発にはノートテイキングを対置している。

[[BlogPosting/context-engineering]] は同じアーキテクチャを、四つの分類のなかでコンテキストを*分離*する最も普及した方法として扱い、各エージェントが自らのツール、指示、コンテキストウィンドウを持つことを指摘し、OpenAI の Swarm ライブラリの背後にある動機として関心の分離を挙げている。またコストも率直に述べている。Anthropic が報告するチャットの最大15倍のトークン、サブエージェントの作業を計画するための入念なプロンプトエンジニアリングの必要、そして協調のオーバーヘッドである。

[[Report/2026-agentic-coding-trends-report]] は、単体のエージェントから協調するチームへの移行を、予測する2026年の八つのトレンドの一つとして扱い、それを採用するのに何が要るかを説明している。タスクの分解、エージェントの専門化、協調のプロトコルに関する新しいスキルに加え、複数の同時実行中のエージェントセッションの状態を示す開発環境と、同時並行のエージェント生成による貢献を扱えるバージョン管理のワークフローである。顧客の例として挙げられるのは Fountain の階層的オーケストレーションであり、中央のオーケストレーションエージェントが候補者のスクリーニング、文書生成、感情分析のための専門化されたサブエージェントを協調させている。

すべての実務者がこれに手を伸ばすわけではない。[[Person/geoffrey-huntley]] は [[BlogPosting/ralph-wiggum-as-a-software-engineer]] で、エージェント間の通信と多重化は当時必要なかったと論じ、非決定的なエージェントをマイクロサービスとして扱うことを単一のモノリシックなプロセスと比べて否定的に評価している——一方でその単一のプロセスの内側では、スケジューラとして働く一次コンテキストウィンドウから派遣される [[DefinedTerm/subagents]] を大いに用いている。

### 2026年のツールの地形——三つの階層

[[BlogPosting/the-code-agent-orchestra]] は同じアーキテクチャを、開発者自身の役割の転換として枠づけている。コンテキストウィンドウを硬い天井としながら一つのエージェントを同期的に導く*指揮者*から、それぞれ自らのコンテキストウィンドウを持ち非同期に働くエージェントの合奏を協調させ、その間に開発者は計画し様子を見る*オーケストレーター*へ、である。その帰結として述べられるのは、作業場が会話のスレッドではなくコードベースになること、そして求められるスキルもそれに応じて変わること——コードを書くことではなく、明確な仕様、作業の分解、出力の検証である。

同記事はツールを三つの階層に分類している。**Tier 1** はプロセス内——Claude Code の [[DefinedTerm/subagents]] と [[DefinedTerm/agent-teams]]——で、単一のターミナルセッションだけがあればよく、追加のツールを要さない。**Tier 2** はローカルのオーケストレーターで、開発者のマシンが隔離された git worktree でエージェントを立ち上げ、開発者はダッシュボード、差分のレビュー、マージの制御を保つ。[[SoftwareApplication/conductor]]、[[SoftwareApplication/vibe-kanban]]、Gastown、Antfarm を伴う OpenClaw、Claude Squad、[[SoftwareApplication/google-antigravity]]、Cursor Background Agents が挙げられ、既知のコードベースで3〜10エージェントが適する範囲とされている。**Tier 3** はクラウドの非同期エージェントで、クラウドの VM で走ってプルリクエストを返す——Claude Code Web、[[SoftwareApplication/github-copilot]] のコーディングエージェント、[[SoftwareApplication/jules]]、Codex Web である。同記事の見立てでは、2026年の大半の開発者は三つすべてを使う。対話的な作業に Tier 1、並列のスプリントに Tier 2、一晩でバックログを片づけるのに Tier 3 である。

その運用上の助言は、階層の一覧が示唆するよりも保守的である。意味のあるレビューができる以上のエージェントを走らせるべきではないという理由から3〜5エージェントを最適域とし、「1ファイル1オーナー」を厳格な規則とし、張り付くのではなく5〜10分ごとに進捗を確認することを推奨し、打ち切りの基準——同じエラーで3イテレーション以上行き詰まったエージェントは停止して割り当て直す——を定めている。また複数モデルのルーティングをコストのレバーとして挙げ、計画・実装・レビューをそれぞれ `MODEL_ROUTING.md` ファイルを通じて異なるモデルへ振り分けている。

### リポジトリを介した協調と、単一の巨大タスクという天井

[[BlogPosting/building-a-c-compiler-with-parallel-claudes]] は、オーケストレーターに対する意図的に最小限の代替案を説明している。16のエージェントはそれぞれ、ベアの git リポジトリをマウントした自分専用の Docker コンテナで走り、ローカルのコピーをクローンし、終わったら push して戻す。衝突はロックによって防がれる。エージェントは `current_tasks/` ディレクトリへテキストファイルを書くことでタスクを主張し、二つのエージェントが同じものを主張した場合は、git 自身の同期によって二番目が別を選ばざるをえなくなる。エージェント間のメッセージングも、高水準の目標を管理する強制されたプロセスも、オーケストレーションエージェントも存在しない。各エージェントが何をするかを決め、たいていは「次に最も明白な」問題を取り、行き詰まったときには失敗した手法の記録文書を保守する。マージ衝突は頻繁だが、エージェント自身が処理すると説明されている。

同報告が記録する失敗モードは、協調の仕掛けではなくタスクの形に関わるものである。失敗しているテストが多数あるときには並列化は容易である。各エージェントが別々のものを取るからである。作業が単一の巨大なタスク——Linux カーネルのコンパイル——になったとき、すべてのエージェントが同じバグに当たり、それを直し、互いの変更を上書きしてしまい、16のエージェントを走らせていることは何の助けにもならなかった。対処は独立性を作り出すことだった。既知の良好なコンパイラをオラクルとして用い、ハーネスがカーネルの大部分を GCC で、一部分だけをエージェントのコンパイラでコンパイルするようにしたのである。そうすれば失敗はバグをその部分集合に局在化させ、異なるエージェントが異なるファイルに取り組めた。その後もなお、単独では動くが組み合わせると失敗するファイルの対を見つけるために差分デバッグが必要だった。

同報告はまた、専門化をスループットとは別の見返りとして扱っている。問題を解くエージェントたちと並んで、重複したコードの統合（LLM が書いたコードは既存の機能をしばしば再実装する）、ツール自体の性能、その出力の効率、Rust 開発者の視点からのプロジェクト設計の批評、そしてドキュメントに、個別のエージェントが割り当てられた。

### オーケストレーター・ワーカーと、並列化との違い

[[TechArticle/building-effective-agents]] はこのパターンを**オーケストレーター・ワーカー**と名づけている。中央の LLM がタスクを動的に分解し、その断片をワーカーの LLM へ委任し、その結果を統合するものである。単純な並列化との区別として述べられるのは、両者を選び分けるうえで重要な点である。二つは地形的には似ているが、並列化ではサブタスクがあらかじめ定義されているのに対し、オーケストレーター・ワーカーではオーケストレーターが特定の入力から決定する。それゆえ同記事は、サブタスクを事前に予測できない作業にこれを推奨しており、例として、変更すべきファイルの数と各変更の性質がタスク次第であるコードの変更と、複数の情報源から情報を集める検索のタスクを挙げている。

同記事はまた、このパターンを意図的に保守的な選択の規則のなかに位置づけている。エージェンティックなシステムはレイテンシとコストをタスクの性能と引き換えにするのであり、それゆえ推奨は機能する最も単純な解であって、オーケストレーター・ワーカーは五つのワークフローのパターンのなかで複雑な端の近くに位置し、既定ではない。

### このアーキテクチャが何を買い、何を要するか

[[TechArticle/how-we-built-our-multi-agent-research-system]] は、これを本番で運用するベンダーによる、このパターンの最も明快な費用対効果の言明を与えている。便益の側では、社内評価において、Claude Opus 4 をリードエージェント、Claude Sonnet 4 をサブエージェントとするマルチエージェントシステムが、単体の Claude Opus 4 を社内の調査評価で90.2% 上回った——実例は S&P 500 の情報技術企業すべての取締役を特定するというもので、マルチエージェントシステムはこれをサブエージェントのタスクへ分解した一方、単体のエージェントは遅い逐次検索で失敗した。

*なぜ*かについての説明は、アーキテクチャ的というよりデフレ的である。「マルチエージェントシステムが機能するのは、主として、問題を解くのに十分なトークンを費やす助けになるからである」。あるブラウジングのベンチマークの分析では、三つの要因が性能のばらつきの95% を説明し、トークンの使用量だけで80% を占め、次いでツール呼び出しの回数、モデルの選択が続いた。またモデルの世代更新が効率の乗数として働き、一世代の更新が、前世代のモデルでトークン予算を倍にするより大きな利得を生んだとも指摘している。

コストの側は同じ言葉で述べられる。エージェントはチャットでのやり取りのおよそ4倍、マルチエージェントシステムはおよそ15倍のトークンを使う。それゆえこのアーキテクチャは「向上した性能に見合うだけ、タスクの価値が十分に高いタスクを必要とする」。

このウィキの主題に照らして注目に値するのは、*適合しない*場合として述べられているものである。すべてのエージェントが同じコンテキストを共有せねばならない領域や、エージェント間に多くの依存関係が存在する領域は、現時点では相性が悪いとされ、**大半のコーディングのタスクが名指しされている**——調査に比べて真に並列化可能なサブタスクが少ないこと、そして LLM エージェントがまだリアルタイムで互いに協調し委任することが得意でないことを理由としている。同記事の説明で真価を発揮するのは、重い並列化を伴う価値の高いタスク、単一のコンテキストウィンドウを超える情報、そして多数の複雑なツールとの接続である。

同記事はまた、自らの実装の限界も記録している。リードエージェントはサブエージェントを同期的に実行するため、協調は単純になるものの、リードが飛行中のサブエージェントを操縦できず、サブエージェント同士が協調することもできず、一つの遅いサブエージェントでシステム全体が止まりうる。
