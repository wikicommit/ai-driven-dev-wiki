コードレビューエージェント——**CRA** と略される——は、プルリクエストにフィードバックを投稿する自動レビュアーであり、本来なら人間のレビュアーが占めるゲートキーパーの位置に収まる。[[ScholarlyArticle/code-review-agents-in-pull-requests]] は、エージェントによるプルリクエストの量が増えるにつれて CRA が開発ワークフローの日常的な一部になったと述べ、例として `coderabbitai` を挙げている。その操作的定義は能力の列挙ではなく区別によるものだ。著者らはレビューコメントから GitHub のボットアカウントを抽出したうえで、それぞれを機能によって手作業で分類し、`github-actions[bot]` のような CI/CD やワークフロー自動化を行うボットを除外して、コードレビューのフィードバックを生み出すものだけを残した。

## 用法

**手続き上できること・できないこと。** その研究が分析したデータセットでは、CRA だけがレビューしたプルリクエストは例外なく GitHub の Commented レビュー状態に現れる。著者らの読み解きは、単一の CRA レビュアーは独立に承認・却下・変更要求を行えないというものだ——エージェントはマージの判断を下すことなくフィードバックを供給する。

**主張されている効果と観測された効果のギャップ。** この論文はそのギャップを軸に構成されている。主張の側として、CRA 利用者の 81% が品質の向上を、69% がスピードの向上を実感していること、CRA を有効にすると PR の 80% が人間からのコメントを受け取らなくなること、開発者の 82% が CRA を日次または週次で使っていることを報告するベンダーおよび業界の資料を引用する。観測の側としては、CRA のみがレビューしたプルリクエストのマージ率が 45.20% であるのに対し人間のみのものは 68.37% であり、放棄率は 34.88% 対 21.60% であったと報告する。さらに、人間のレビューコメントが対応される割合（60%）が CRA のコメント（0.9%〜19.2%）よりはるかに高いという先行研究も引用している。

**シグナルとノイズ。** 結果のギャップに対する論文の説明はフィードバックの品質であり、それをシグナル対ノイズ比として測定する。すなわち、PR のレビューコメント全体のうち、クリティカルなシグナル（ランタイムエラー、クラッシュ、コンパイル失敗、API 破壊的変更、セキュリティ脆弱性）または重要なシグナル（アーキテクチャ上の問題、パフォーマンスの問題、保守性への懸念）を指摘しているものの割合である。この枠組みは著者らが考案したものではなく、AI コードレビューにおけるシグナルとノイズの測定を扱った外部のブログ記事から採り入れられている。クローズ済みで CRA のみがレビューした 98 件の PR に適用したところ、60.2% が 0〜30% のバンドに入り、13 の異なるエージェントのうち 12 が平均 60% を下回った。そのクローズ済み集合で名前が挙がっているエージェント別の平均には、36 件の PR にわたる `github-advanced-security[bot]` の 27.62%、24 件の PR にわたる Copilot の 19.79% があり、相当数の件数を持つエージェントの中では `entelligence-ai-pr-reviews[bot]` が 52.29% で最も高い。ただしいくつかの数値は、それぞれごく少数の PR に基づいている。

**どこに適合すると論じられているか。** この論文の推奨は、汎用的なレビューよりも狭く絞った設定である——セキュリティ脆弱性やスタイル違反といった特定のチェックに限定するというもので、専門化されたチェックのほうが偽陽性を減らすという理由による——のに加えて、マージ前の人間による承認を必須とすること、そして CRA のコメントが開発者の直接的な応答ではなく人間のレビューを起動するようなワークフローを組むことである。また、CRA が同じプロバイダーによって生み出されたコードをレビューすることが多いという先行研究由来の構造的な懸念も提起し、これをクローズドループのバイアスリスクとして位置づけている。

### 単一ステージのツールからライフサイクル全体のアーキテクチャへ

[[ScholarlyArticle/rethinking-code-review-in-the-age-of-ai]] は、現在のレビューツールを断片的なもの——レビュアー推薦、PR 説明文の生成、コメント提案といった孤立したタスクを扱うもの——として特徴づけ、そうしたステージ単位の進歩はそれ自体では組み合わさらないと論じる。有益なレビューコメントは、その理由が書き残された PR に依存し、レビュアーのマッチングは行動的な文脈がレビュアーに届くことに依存するからである。

同論文が提案する代替は [[DefinedTerm/agentic-code-review]] であり、レビューを1体の汎用レビュアーではなく、プルリクエストのライフサイクル全体に分散した狭く専門化されたエージェント群へと分解する。それぞれの端にいるオーケストレーターも人間も異なる。PR 作成時には、PR 詳細の生成、Issue のリンク付け、初回の自動レビューパス、修正提案を担うエージェントが PR Creation Agent の下に置かれ、PR の*作成者*が提出前に自然言語でこれを指揮する。レビュー時には、説明、自動レビュー、修正提案、コメント測定を担うエージェントが PR Review Agent の下に置かれ、*レビュアー*がこれに語りかける。この PR Review Agent はさらに、PR Augmentation Agent 配下の、要件整合性の分類、バグ混入しやすさのスコアリング、サンドボックス化されたランタイム解析、モジュール横断の影響分析を担うサブエージェント群も参照する。レビュー段階のエージェントのうち2つは、コードではなく人間自身のアウトプットを評価する——レビューコメントが書かれている最中に、その毒性と有用性を測定するのである。

単一パスの自動レビューがなぜ期待に届かないのかについて同論文が挙げる証拠は、上記のサーベイの知見と重なる。変更内容の理解の壁ゆえにレビューの 54% がバグを検出できないこと、レビューフィードバックのおよそ 44.47% が有用でないことを報告する実証研究を引用し、さらに、AI に支援されたレビュアーは低深刻度の問題をより多く浮かび上がらせるものの、高深刻度の欠陥を追加で見つけるわけではないという知見も引く。同論文はこれを、自動化された支援が注意をより易しい問題のほうへ引き寄せている結果と読んでいる。

## 関連用語
