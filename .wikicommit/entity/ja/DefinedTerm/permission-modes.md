パーミッションモードとは、エージェントがツールをどう使うかをグローバルに制御する、セッション全体の設定である。
[[SoftwareApplication/claude-agent-sdk]] のドキュメントにおいて、これは固定された評価順序の中の特定の位置を占めている。
フック、拒否ルール、確認ルールが参照された後で、許可ルールと実行時コールバックの前である。この位置こそが概念に正確な
意味を与えている。すなわち、モードは、それ以前のステップで決着しなかった要求の基本的な扱いを決めるのである。

この位置がこの考え方の本質である。拒否ルールと確認ルールはモードが適用される前に評価されるので、ドキュメントは、最も
寛容なモードにおいてさえ両者は引き続き効力をもつと述べている。したがって、モードはデフォルトを上げ下げするが、その周囲に
宣言された制御を取り除くことはない。

## 用法

6 つのモードが文書化されている。`default` はモードにもとづく自動承認を何も加えないので、承認が必要でどの許可ルールにも
一致しない呼び出しはコールバックに到達する。`dontAsk` は、本来ならプロンプトが出るものをすべて拒否し、コールバックを
一切呼び出さないが、ルールによって承認された呼び出しと承認を必要としない呼び出しは引き続き実行する。`acceptEdits` は
ファイル編集とファイルシステム操作を自動承認し、それ以外のツールは通常の扱いに委ねる。`bypassPermissions` は、どの
モードも自動承認しないと文書化されている一連のアクションを除いて、プロンプトなしにツールを実行する。`plan` はファイル
編集が自動承認されないようにし、エージェントがソースファイルを編集せずに調査と計画を行うようにする。`auto` は判断を
モデルの分類器に委ねる。

モードはクエリの作成時に設定することも、セッション中に変更することもでき、ドキュメントは、制限的な設定から始めて信頼が
築かれるにつれて緩めるためにこれを使うことを勧めている。サブエージェントについては親セッションから継承されるが、文書化
された例外として、最も寛容なモードは親自身がそのモードで動いている場合を除いてサブエージェントには決して適用されない。
その理由として述べられているのは、サブエージェントは異なるシステムプロンプトとより制約の少ない振る舞いをもつ可能性が
あり、それを継承させればシステムへの完全な自律的アクセスを与えてしまう、というものである。

SDK のドキュメントがモードを対等な選択肢の一覧として示すのに対し、Claude Code のベストプラクティスのドキュメントは、
セッションが実際にどのモードで始まるかを説明しており、それをユーザーの選択ではなくプランに依存するデフォルトとして
扱っている。Pro、Max、Team プランでは、**auto モード** が対話的なターミナルと VS Code のセッションの組み込みの開始
モードであり、それ以外のプランでは **Manual モード** である。両者は、誰がレビューを行うかによって特徴づけられる。
Manual モードでは、エージェントはシステムを変更しうるもの——ファイルの書き込み、Bash コマンド、MCP ツール——の前に
必ず確認を求める。ドキュメント自身がこれを安全だが煩わしいと呼び、10 回目の承認のころにはユーザーはレビューするのでは
なくクリックして通過させるようになっていると述べている（[[DefinedTerm/approval-fatigue]] を参照）。auto モードでは、
ユーザーの代わりに別の分類器モデルがほとんどのアクションをレビューし、危険そうに見えるものだけをブロックする。名前が
挙げられているカテゴリは、スコープの拡大、未知のインフラストラクチャ、敵対的なコンテンツに駆動されたアクションの 3 つ
である。

Manual モードでの中断を減らしつつ、auto モードでも同様に適用されるものとして 2 つのツールが文書化されている。安全だと
分かっている特定のツールを事前に承認するパーミッションの許可リストと、ファイルシステムとネットワークの OS レベルの隔離を
有効にし、定められた境界の中でエージェントがより自由に作業できるようにする [[DefinedTerm/sandboxing]] である。同じ
ドキュメントは、分類器モードを対話的に使う場合と非対話的に使う場合の振る舞いの違いにも触れている。非対話的な実行で
分類器が繰り返しアクションをブロックしたとき、実行は停止されず、代わりに文書化されたフォールバックが適用される。

### 作り手の説明による分類器モードの仕組み

Claude Code チームの 2 人のメンバーが、対談の中で auto モードについてのより詳しいメンタルモデルを示しており、それは
[[BlogPosting/a-fireside-chat-with-cat-and-thariq-from-the-claude-code-team]] で伝えられている。彼らの説明によれば、
分類器は Sonnet モデルであり、それが判断するのはツール呼び出し単体ではなく、ユーザー自身の指示を含む会話の文脈 *と合わせた*
呼び出しである。彼らがこのモードに固有の性質として示すのはこの点、すなわち要求に依存するパーミッションである。彼らの
例示はこうである。コーディングエージェントにリモートへの push の恒常的な許可を与えることはないだろうが、「これを GitHub
に push して」と言えばそれは許可されるべきであり、「push しないで」と言えば拒否されるべきである。そして彼らは、2 つ目の
ケースが実際によく起きると報告している。エージェントが役に立ちそうなことを提案し、ユーザーがそれを除外していたために
モードがそれを浮かび上がらせる、というものである。

彼らはまた、これを OS レベルの隔離と重複するものではなく、それを補完するものとして説明している。彼らの説明では、
サンドボックス化にはエッジケースが非常に多く、それらを決定論的に追いかけるのは難しい。そこで、何かがサンドボックスの
外に出る必要があるとき——挙げられている例はネットワーク要求である——分類器がその要求を検査し、許可する前にそれが理に
かなっているかを判断できる。より一般的には、2 人のうちの 1 人は、このモードは、本来ならユーザーが目にしたはずのあらゆる
パーミッションのプロンプトと相互作用すると述べている。同じ議論の中で、隣接する 2 つの仕組みにも言及されている。リモート
コントロールのユーザー向けの信頼済みデバイスと、プロキシがエージェントの送信要求に認証情報を挿入することで、エージェント
がその認証情報にアクセスできないまま利用できるようにする認証情報のインジェクションである。

## 適用される場面

この概念が当てはまるのは、ツールのパーミッションがモデルの外で評価されるハーネスであり、それと並ぶルールシステムを前提と
している。モード単体が表すのは姿勢だけであり、ポリシーではない。ドキュメントはこの区別を、明示的な許可リストと `dontAsk`
を組み合わせた、固く締められた構成で説明している。そこでは一覧にあるツールは実行され、プロンプトが出るそれ以外の呼び出し
はすべて拒否される。

文書化されている誤用は、モードをデフォルトではなく制約として扱うことである。許可リストは `bypassPermissions` を狭め
ない。一覧にないツールはどの許可ルールにも一致せず、モード自体によって承認されるからである。ツールを手の届かないところに
置くには、代わりに拒否ルールを使うようドキュメントは読者に指示している。

実践者の報告は、同じトレードオフの反対側にある 2 つ目の誤用を付け加えている。
[[BlogPosting/ai-coding-agent-speed-and-safety-2026]] は、まず許可リストと拒否リストを整備し、そのうえで編集を
自動承認するモードで作業することを勧めており、その際どちらに誤るべきかについて具体的である。問題のない操作は、プロンプトに
任せたままにせず、積極的に許可リストに入れるべきだというのである。その理由は、プロンプトが多すぎる構成は自らを無効化する
というものである。人々は何を承認しているのかを読まずに承認し始めるので、最も慎重に見える姿勢が実際にはセキュリティを
下げてしまう（[[DefinedTerm/approval-fatigue]] を参照）。同じ記事は、人間による承認を完全にオフにして動かすことは商用の
開発には不適切だとしており、著者自身はそれを隔離されたコンテナ内でのオープンソースの作業にのみ使っていると報告している。
エージェントが [[DefinedTerm/sandboxing]] のもとで動く場合には、シェルコマンドをサンドボックス化されている *がゆえに*
自動許可する設定を、チェックを取り除かずにプロンプトの数を減らす方法として挙げている。

どの程度確立されているか。これは 1 つのベンダーが自社の SDK と自社のコーディングツールのために文書化した設計であり、上記の
モード名は業界全体の標準ではなく、そのベンダーの用語である。2 つ目のソースは、それとは種類の異なるさらなる注意点を加えて
いる。そこではセッションがどのモードで始まるかがユーザーのサブスクリプションプランに結びつけられており、したがって開始時の
姿勢は安全上の判断であると同じくらい商業上の判断でもある。

分類器モードについてなされている最も強い主張はベンダー自身のものであり、ドキュメントではなく上で引いた対談の中でその
チームによってなされたもので、しかもインタビュアーはそのうちの 1 つにその場で異を唱えている。彼らは、社内のほぼ全員が
auto モードを使っていると報告し、それを Claude Code で長時間の作業を安全に行う最良の方法と呼んでいる。そして、何千もの
評価、社内の全ユーザーにわたって実行された評価、プロンプトインジェクションや悪意ある入力を含む敵対的な環境を構築する複数の
委託レッドチームを挙げ、それらのチームが見つけた問題はすべて緩和されたと述べている。彼らはより強い主張ははっきりと退けて
おり——100% を捕捉するわけではなく、それはあまりに強すぎる主張だと言う——代わりに比較を相対的なものとして示している。
彼らが重視するリスクのカテゴリ、とりわけ [[DefinedTerm/prompt-injection]] とデータの流出については、リスクは平均的な
人間のレビュアーよりもはるかに低いと主張している。裏づけとなる評価は公開されると彼らは述べたが、その対談が伝えられた
時点では何も公開されておらず、したがってこれらの数字の根拠はここからは独立に検証できない。出自についてもう 1 つ細かい点を
挙げると、彼らは社内での利用を、一般公開よりもかなり前の 1 月にさかのぼるものとしており、また、このモードを、Slack に常駐
する彼らのエージェント [[SoftwareApplication/claude-tag]] をそもそも成り立たせる基盤として挙げている。誰でも投稿できる
チャンネルを読むエージェントは、構造上プロンプトインジェクションにさらされているからである。
