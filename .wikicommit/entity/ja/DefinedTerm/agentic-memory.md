エージェンティックメモリとは、コンテキストウィンドウの外の保存領域へ情報を書き出し、後で読み戻す実践であり、それによってエージェントの継続性がすべてをコンテキストに留め置くことに依存しないようにするものである。[[TechArticle/effective-context-engineering-for-ai-agents]] はこの語を**構造化されたノートテイキング**と互換的に用い、エージェントが定期的にコンテキストウィンドウの外のメモリへ永続化されるノートを書き、それが後の時点で引き戻される技術として定義している。[[BlogPosting/context-engineering]] は同じ考えを4つの分類のうち2つに分けている。コンテキストを*書く*ことはそれをウィンドウの外に保存することであり、コンテキストを*選ぶ*ことはその適切な部分を引き戻すことである。

## 用法

[[BlogPosting/context-engineering]] はこの考えをスコープによって整理している。その説明では、**スクラッチパッド**はエージェントが単一のタスクに取り組むあいだ情報を保持するもので、ファイルへ書き込むツールとしても、セッション中に持続する実行時状態オブジェクトのフィールドとしても実装できる。その違いが、エージェントがそれをどう読み戻すか——ツール呼び出しによるのか、開発者が各ステップで状態のどの部分を露出させるかを選ぶのか——を決める。同じ説明において、**メモリ**は多数のセッションをまたいで持続する。同記事はこの考えを、各エージェントターンの後に振り返り、自己生成されたメモリを再利用することを導入した Reflexion と、過去のフィードバックの集合から定期的にメモリを合成した Generative Agents に遡らせ、ChatGPT、Cursor、Windsurf のいずれもがユーザーとのやり取りから長期メモリを自動生成する機構を備えていることを指摘している。

Anthropic の説明は長期的な作業に対する見返りを強調する。このパターンは最小限のオーバーヘッドで永続的なメモリを提供し、エージェントが複雑なタスクにわたって進捗を追跡し、さもなくば数十回のツール呼び出しのあいだに失われるであろう重要なコンテキストと依存関係を保てるようにする。挙げられる例は、Claude Code が TODO リストを作ることと、カスタムエージェントが `NOTES.md` ファイルを保守することである。最も印象的な例はコーディングの外にある——Claude がポケモンをプレイする事例では、エージェントは数千のゲームステップにわたって正確な集計を保ち、探索した地域の地図を作り、解除した実績を覚え、どの攻撃がどの相手に有効かの戦略メモを保つ。しかもメモリの構造について何も促されないままである。コンテキストのリセット後には自らのノートを読んで数時間に及ぶ手順を継続するのであり、同記事はこれを、要約のステップをまたぐ一貫性がコンテキストだけでは不可能な戦略を可能にしたものとして提示している。

より難しいのは選択のほうである。LangChain の記事は、エピソード記憶（望ましい振る舞いの少数例）、手続き記憶（振る舞いを導く指示）、意味記憶（タスクに関連する事実）を区別し、多くのコードエージェントが常に狭い固定のファイル集合——Claude Code の `CLAUDE.md`、Cursor と Windsurf のルールファイル——を読み込むことで選択を完全に回避していると指摘している。より大きな集合が保存される場合には、索引付けに埋め込みやナレッジグラフが一般的に用いられるが、同記事は選択が依然として難しいことを認めている。ChatGPT が Simon Willison の所在地をメモリから取り出し、依頼された画像に予期せず注入した例を伝え、この種の望まない検索がユーザーに、コンテキストウィンドウが「もはや自分のものではない」と感じさせうると述べている。

[[TechArticle/effective-harnesses-for-long-running-agents]] は、同じパターンをコンテキストの補助としてではなく、セッションをまたぐ継続性の主たる機構として用いたと報告している。そのハーネスでは、初期化エージェントが進捗ファイルと最初の git コミットを書き、以後のすべてのセッションは git のログと進捗ファイルを読むことから始めて、直近に何が行われていたかを把握し、あわせて構造化された機能一覧から次のタスクを選ぶ。同記事自身の枠づけでは、レバレッジがあるのはここである。報告される鍵となる洞察は、新しいコンテキストウィンドウで始めるエージェントが作業の状態を素早く理解できる方法を見つけたことであり、その設計を、有能なソフトウェアエンジニアが日々していることの観察に帰している。

同じ説明は、保存形式についての異例なほど具体的な発見も寄せている。いくらかの試行を経て著者らは機能一覧に JSON を採用した。彼らの言葉では「モデルは Markdown ファイルに比べ、JSON ファイルを不適切に変更したり上書きしたりする可能性が低い」からである——これは上述の選択の問題とは区別される、ノート自体の耐久性に関わる性質である。

### ノートを壊さずに保守する

ウィンドウの外にノートを書くことは、上の説明が開いたままにしている保守上の問いを提起する。そのノート自体が更新されるときに何が起きるのか、である。[[ScholarlyArticle/agentic-context-engineering]] は、明白な答え——蓄積されたノートを各ステップでモデルに書き直させる——が、[[DefinedTerm/context-collapse]] と呼ぶ特有かつ深刻な仕方で失敗すると報告している。その AppWorld のケーススタディでは、18,282トークン・正確度66.7 のコンテキストが、次の適応ステップで122トークン・正確度57.1 へと崩壊した。これは同じ設定で蓄積されたコンテキストをまったく持たない場合の63.7 を下回る。

そこで提案される代替案は、ノートを再生成すべき文書ではなく、追記と洗練を重ねる成果物として扱う。三つの役割が仕事を分担する。Generator が推論の軌跡を生み、Reflector がその成功と誤りから教訓を蒸留し、Curator が簡潔な差分エントリを出力して既存のコンテキストへ決定的にマージする——それゆえどのステップも全体を書き直すことはなく、複数の差分を並列にマージできる。同論文は、この構成によりエージェントのベンチマークで平均10.6%、ドメイン固有のもので8.6% の向上を報告しており、これはラベル付きの教師信号ではなく実行のフィードバックから構築されたものである。評価はコーディングのタスクではなくエージェントと金融のベンチマーク上で行われており、測定は著者ら自身のものである。

### ベストエフォートのノートテイキングから強制可能な契約へ

[[ScholarlyArticle/clawvm]] は上のすべてを必要なものとして受け入れたうえで、それでは十分でないと論じる。既存の構成要素——剪定、検索、コンパクション、コンパクション前のメモリのフラッシュ、外部メモリのプラグイン——への批判は、「これらは想起の質を高めるが、いずれも常駐性・耐久性・監査可能性についての強制可能な契約を提供しない」というものであり、それゆえ実務では「フラッシュは依然として迂回されうるし、書き戻しは依然として破壊的でありうるし、重要な状態がライフサイクルの遷移を生き延びることを保証する機構は存在しない」。これが実害を生むという証拠として、公開の課題追跡と実務者の報告から得た三つのパターンが挙げられている。コンテキストの要約後に失われる規則と制約、セッションのリセット時に黙って落とされる状態、そしてマージではなく上書きをする永続化の操作である。

そこで提案される抽象はノートテイキングではなくオペレーティングシステムから借りられている。エージェントの状態は**型付きページ**となり、各ページはトークンの圧力が高まるにつれて完全な詳細のまま保持されるか、圧縮されるか、構造化されたフィールドへ縮約されるか、ポインタにまで縮められる。そして各ページは、空間が回収される前にどこまで劣化してよいかを述べる**最小忠実度の不変条件**を担う。ハーネスがすべてのライフサイクル境界でそれらの不変条件を、検証付きの書き戻しによって強制する——そこに置かれる理由として同論文は、ハーネスが「すでにプロンプトを組み立て、ツールを仲介し、ライフサイクルのイベントを観測している」ことを挙げ、それが常駐性と耐久性を創発的なものではなく決定的で監査可能なものにするとしている。

報告される結果は条件付きであり、その条件こそが興味深い部分である。ポリシーで制御可能な障害はすべて、「最小忠実度の集合がトークン予算に収まるかぎり」除去され、その際のポリシーエンジンのオーバーヘッドは1ターンあたり中央値50マイクロ秒未満である。その集合に何が属するかを決めるのは依然として人間の判断である。この機構はそれを作るのではなく、強制するのである。
