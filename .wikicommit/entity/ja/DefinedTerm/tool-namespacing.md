ツールの名前空間化とは、関連するツールを共通のプレフィックスの下にまとめ、ツールを選ぶエージェントにとってツール同士の境界が読み取れるようにする実践である。この名前で説明されているのは [[BlogPosting/writing-effective-tools-for-agents]] であり、同記事はその動機を、エージェントがますます置かれるようになっている状況に求めている。すなわち、数十の [[DefinedTerm/model-context-protocol]] サーバーと数百のツール——他の開発者が書いたツールも含む——にアクセスでき、機能の重複や目的の曖昧さのためにエージェントがどれを呼び出すべきか迷ってしまう状況である。一部の MCP クライアントはデフォルトで名前空間化を適用していると報告されている。

## 用法

同記事は、組み合わせることもできる二つの軸を挙げている。ツールは**サービス単位**で名前空間化でき、そうすればある製品での検索と別の製品での検索が、どちらも「search」という名前の二つのツールとして競合するのではなく、別々のプレフィックスを持つことになる。また**リソース単位**でも名前空間化でき、そうすれば同じサービス内でのプロジェクトの検索とユーザーの検索がさらに区別される。挙げられている例は、サービス単位では `asana_search` や `jira_search` の形式の名前、リソース単位では `asana_projects_search` や `asana_users_search` の形式の名前である。

どの方式を選ぶかは、慣例ではなく経験的な問いとして提示されている。著者らは、プレフィックス方式とサフィックス方式の名前空間化のどちらを選ぶかが自社のツール利用評価に無視できない影響を与えたこと、その影響はモデルによって異なることを報告し、規則を採用するのではなく自分たちの評価に基づいて命名方式を選ぶよう勧めている。

OpenAI の関数呼び出しガイド（[[DefinedTerm/function-calling]] を参照）は、この実践を命名規則としてではなく API の機能としてサポートしている。関連するツールはドメインごとに名前空間にまとめることができ、その例として `crm`、`billing`、`shipping` が挙げられている。ガイドが示す動機も同じで、名前空間は、CRM 用の検索ツールとサポートチケットシステム用の検索ツールのように、異なるシステムや目的に役立つツールの間でモデルが選択しなければならない場合に特に有用だとしている。名前空間化されたツールを [[DefinedTerm/tool-search]] によって遅延読み込みする場合について、ガイドは、名前空間の説明は簡潔にとどめ、詳しい指示は各関数の説明に書くよう勧めている。名前空間はモデルが何を読み込むかを選ぶ助けとなり、関数の説明は読み込まれたツールをモデルが正しく使う助けとなるからである。

同記事は名前空間化を、関連するもう一つの規律と並べて位置づけている。それは、タスクの自然な区分を反映した名前を持つツールを選択的に実装することである。エージェントのコンテキストに読み込まれるツールとツール説明の数を減らすと同時に、エージェント的な計算をそのコンテキストからツール呼び出しそのものへと移し替える効果があるとして同記事が評価しているのは、この二つ目の実践のほうである。

## 適用される場面

エージェントが利用できるツールが十分に多く、選択そのものが失敗の原因となる場合に適用される。同記事が挙げる失敗の形は、誤ったツールを呼び出すこと、正しいツールを誤ったパラメータで呼び出すこと、呼び出すツールが少なすぎること、ツールの応答を誤って処理することである。同記事が名前空間化そのものの効果として挙げているのは、境界を明確にする助けとなること、そしてエージェントが適切なタイミングで適切なツールを選ぶ助けとなることである。エージェントが誤りを犯すリスク全体を下げるという、より広い主張については、タスクの自然な区分にちなんでツールに名前を付けるという隣接する実践に結び付けている。

この手法は、ツールの名前を自分で付けられること、あるいは少なくともクライアントが名前を途中で書き換えられることを前提としている。同記事は別途、MCP クライアントがデフォルトで名前空間化を適用することがあること、そしてエージェントのツールには他の開発者が書いたものが含まれうることにも触れている。また、名前がモデルにとって意味を持つことも前提としており、これは、ツールの説明をプロンプトエンジニアリングすることや、パラメータに曖昧さのない名前を付けることについての同記事の別の助言の背後にあるのと同じ前提である。

この手法は、それだけで十分なものとしては提示されていない。同じ記事の中でこれは五つの原則の一つであり、その直前の原則——あらゆる API エンドポイントをラップするのではなく、よく考え抜かれ統合された少数のツールを作ること——は、そもそも重複するツールを作らないことによって、同じ根本的な問題に反対側から取り組んでいる。

どの程度確立しているか：命名に関する助言は、一つのベンダーが自社の内部ツールを自社の評価に照らして最適化した経験から引き出したエンジニアリング上の指針である。助言の方向性は知見として述べられているが、プレフィックスとサフィックスのどちらを選ぶかという具体的な選択は、明示的に読者自身の測定に委ねられている。OpenAI の関数呼び出しガイドは、これとは別に、ツールをドメインごとにまとめるための第一級の API 機能として名前空間を提供している。
