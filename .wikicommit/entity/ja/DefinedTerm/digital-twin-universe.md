デジタルツイン・ユニバース、略して DTU とは、[[Organization/strongdm]] の AI チームによる呼称で、自社ソフトウェアが
依存するサードパーティサービスの振る舞いのクローンを指す。それらのサービスの API、エッジケース、観察可能な
振る舞いを複製するように作られている。ツインが作られたのは Okta、Jira、Slack、Google Docs、Google Drive、
Google Sheets である。ツインの眼目は忠実さそれ自体ではなく、検証を走らせる場所があることだ。DTU を備えることで、
本番の制限をはるかに超える規模と頻度で検証でき、実サービスに対しては危険ないし不可能な故障モードを試験でき、
レート制限にかかったり不正利用検知を誘発したり API 費用を積み上げたりすることなく毎時何千ものシナリオを
走らせられる、とチームは述べている。

## 用法

ツイン自体がエージェントによって作られており、これがこの着想を実行に移せるほど安くしている。
[[BlogPosting/how-strongdms-ai-team-build-serious-software-without-even-looking-at-the-code]] がこの技法を理解した
ところによれば、ツインはあるサービスの公開 API ドキュメント一式をチームのエージェントハーネスに流し込み、
自己完結した Go のバイナリとして模倣を作らせることで生み出され、その上に簡略化された UI が生成されて
シミュレーションを完成させる。同記事の更新は、忠実さについて DTU の作成者が語った再現可能な戦略を伝えている。
すなわち、公開されている中で最も広く使われているリファレンス SDK のクライアントライブラリを互換性の目標として
用い、常に 100% の互換性を目指すというものである。

チームの [[DefinedTerm/software-factory]] の中で、DTU はシナリオが走る対象である。彼らのシナリオテストは、
システムが構築されつつあるその最中に、エージェントがそのシステムに対して継続的に実行するスクリプトとなり、
ツインはシミュレートされたユーザーとトラフィックで満たされる——挙げられている例は、それぞれ異なるシミュレートされた
システムへのアクセスをこれから必要とする、シミュレートされたディレクトリユーザーの流れを抱えた Slack のツインである。

## 適用条件

条件は、試験対象のソフトウェアが何と話すかによって定まる。DTU が扱うのは、振る舞いの大半がサードパーティの
SaaS API を介するソフトウェアであり、チームが望む検証を妨げているのが難易度ではなく実サービスのレート制限、
不正利用検知、費用、そして取り消し不能性であるような場面である。それらのサービスが、エージェントがそれを
頼りに構築できるほど十分に詳細な公開 API ドキュメントを持つこと、そしてクライアントライブラリのレベルでの
互換性という目標が、本当に問題となる振る舞いの十分によい代理指標であることを前提とする。

なぜこれが新しいのかについてのチーム自身の論拠は、技術的というより経済的なものだ。重要な SaaS アプリケーションの
高忠実度のクローンを作ることは常に可能ではあったが、経済的に成り立ったことがなかった。そして彼らは、何世代もの
エンジニアが試験用にシステムの完全なインメモリの複製を欲しがっていたかもしれないのに、それを作るという提案を
自主規制してきたのだと述べている。それに対応する弱みは、ツインが模倣であるということだ——その忠実さは
リファレンスのクライアントライブラリに対して主張されているのであって、実サービスの振る舞い全体に対してではない
——したがって取りこぼしうるのは、互換性の目標が働かせない部分すべてである。

どれほど確立しているか。これは一つのチームが名づけた実践であり、彼ら自身によって説明され、そのデモを見た
一人の実践者によって伝えられたものであって、構築の技法については明示的に彼らの文書ではなく伝え手の理解として
述べられている。測定された結果でもなければ、独立した実践者を伴う慣行でもない。
