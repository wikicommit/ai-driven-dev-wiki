コンテキストファイルとは、それが使われるリポジトリについての文脈情報を、中央集約された機械可読な形で提供する Markdown ファイルであり、エージェンティック AI コーディングツールのコンテキストに毎セッション永続的に読み込まれる。[[ScholarlyArticle/configuring-agentic-ai-coding-tools]] はこれを「エージェントのための README」と特徴づけ、ビルドコマンド、コーディング規約、CI/CD パイプラインのルールといった文脈固有の情報を担い、他の設定成果物と同様にバージョン管理され、検査可能で、共同で保守されるものだとしている。

## 用法

ツールごとに読むファイル名は異なる。[[SoftwareApplication/claude-code]] は CLAUDE.md、[[SoftwareApplication/github-copilot]] は `.github/copilot-instructions.md` と `.github/instructions/*.md`、[[SoftwareApplication/codex-cli]] は [[DefinedTerm/agents-md]]（および AGENTS.override.md）、[[SoftwareApplication/cursor]] は AGENTS.md と現在は非推奨の `.cursorrules`、[[SoftwareApplication/gemini-cli]] は GEMINI.md である。Copilot はこれに加えて CLAUDE.md、AGENTS.md、GEMINI.md もサポートする。

研究の 2,926 リポジトリのサンプルにおいて、コンテキストファイルは大差をつけて最も頻繁に採用された設定機構であり、多くの場合リポジトリにはコンテキストファイルという成果物が1つだけ含まれていた。著者らは 2,634 リポジトリにわたって 4,860 個のコンテキストファイルを同定した。最も多いファイル種別は CLAUDE.md の 1,661 ファイル（34.2%）で、次いで AGENTS.md が 1,572（32.3%）、copilot-instructions.md が 1,344（27.7%）だった。GEMINI.md（159 ファイル、3.3%）と `.cursorrules`（73、1.5%）はまれだった。ファイル数ではなくリポジトリ数で測り、コンテキストファイルを含む 2,634 リポジトリを母数とすると、CLAUDE.md は 1,195（45.4%）、AGENTS.md は 1,069（40.6%）、copilot-instructions.md は 925（35.1%）に現れた。コンテキストファイルを使うリポジトリの大半は、そのうち1つか2つしか含んでいない。

コンテキストファイルは内容を重複させるのではなく、互いを参照し合うことが多い。研究は3つの参照パターンを同定している。*直接のポインタ*——ファイル名、命令形の文、あるいは Markdown リンクによって他のファイルを指名する一行。*文脈を伴う短い参照*——参照先のファイルをどう扱うべきかを述べる2〜5行。そして *簡潔な要約＋参照*——1〜2文の文脈を伴う見出しに続くポインタ。互いを参照し合う 518 のファイル対のうち、CLAUDE.md が最も多くの発参照（357）を持ち、AGENTS.md が最も多くの被参照（368）を持っていた。

## 執筆の指針

Anthropic の Claude Code のドキュメントは、その書き方についてベンダーとして最も明示的な指針を与えている。推奨される出発点は、`/init` を実行してプロジェクト構造から出発点となるファイルを生成し、時間をかけて洗練していくことであり、ファイルが読み込まれたかの確認には `/context` を用いる。必須の形式はないが、中心的な指示はファイルを短く人間可読に保つことである。このファイルは毎セッション読み込まれるため、広く当てはまるものだけがそこに属する——ときどきしか関係しないドメイン知識やワークフローは、代わりに必要に応じて読み込まれる [[DefinedTerm/agent-skills]] に属する。

各行に対して提案されているテストはこうである。*「これを削ったら Claude は誤りを犯すだろうか？」* もしそうでないなら削れ。含める／含めないの表では、モデルが推測できない Bash コマンド、既定と異なるコードスタイルのルール、テストの指示、リポジトリ上の作法、プロジェクト固有のアーキテクチャ上の決定、環境の癖、自明でない落とし穴が「含める」側に置かれる。そして、モデルがコードから読み取れること、標準的な言語の慣習、詳細な API ドキュメント、頻繁に変わる情報、長い説明、ファイルごとの記述、そして「きれいなコードを書け」のような自明な作法が「含めない」側に置かれる。

述べられている失敗のモードは肥大化である。長すぎるファイルは、重要なルールがノイズに埋もれてしまうため、モデルが指示を無視する原因になる——したがって、ルールがあるのにモデルが何かをし続ける場合、ドキュメントの診断はルールが不明瞭なのではなくファイルが長すぎるというものである。一方、ファイルがすでに答えている質問をモデルがしてくる場合は、言い回しが曖昧であることを示唆する。推奨される処置は、このファイルをコードと同じように扱うことである。うまくいかないときにレビューし、定期的に刈り込み、変更は実際に振る舞いが変わるかを観察して検証する。例外なく従わせなければならない指示については、より強い言葉で言い直すのではなくフック（[[DefinedTerm/agent-hooks]] を参照）に変換することを推奨している——もっとも「IMPORTANT」や「YOU MUST」といった強調が遵守率を高めうることにも触れている。ファイルは `@path/to/import` 構文で他のファイルを取り込むことができ、チームが貢献できるよう git にチェックインすることが推奨されている。

実務者の文章も、別の方向から同じ点に収束している。[[BlogPosting/agentic-engineering-surpasses-vibe-coding]] は、`CLAUDE.md` や `README.md` を通じてコンテキストを明示的に渡すことを5つの原則の一つとして挙げる。[[BlogPosting/context-engineering]] は、常時読み込まれるファイルを、メモリの選択問題を完全に回避する手立てとして枠づけ——毎回引き込まれる固定された狭い一群のファイルであり、手続き記憶として機能する——、Claude Code の `CLAUDE.md` と、Cursor および Windsurf のルールファイルを名指ししている。[[TechArticle/effective-context-engineering-for-ai-agents]] は同じ振る舞いを、ハイブリッドな検索戦略の半分として説明する。`CLAUDE.md` は先んじてコンテキストに投入され、それ以外はすべて glob と grep がジャストインタイムで取得する、というものである。

## 関連用語

コンテキストファイルは、同じ研究で整理された他の7つの設定機構——[[DefinedTerm/agent-skills]]、[[DefinedTerm/subagents]]、Commands、Rules、Settings、Hooks、MCP サーバー——と並ぶが、最も広く採用されていると同時に執筆の摩擦が最も小さい点で際立っている。研究は、この優勢が意味するのは、設定が現在のところ自動化よりもドキュメントとして使われているということだ、と指摘している。
