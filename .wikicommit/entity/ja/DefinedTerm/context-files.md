コンテキストファイルとは、それが用いられるリポジトリについての中心的で機械可読な文脈情報を提供する Markdown ファイルであり、エージェンティックな AI コーディングツールのコンテキストへ毎セッション持続的に読み込まれる。[[ScholarlyArticle/configuring-agentic-ai-coding-tools]] はこれを「エージェントのための README」と特徴づけ、ビルドコマンド、コーディングの慣習、CI/CD パイプラインの規則といった文脈固有の情報を担い、他の設定成果物と同様にバージョン管理され、検査可能で、協働で保守されるものだとしている。

## 用法

各ツールは自らのファイル名を読む。[[SoftwareApplication/claude-code]] は CLAUDE.md、[[SoftwareApplication/github-copilot]] は `.github/copilot-instructions.md` と `.github/instructions/*.md`、[[SoftwareApplication/codex-cli]] は [[DefinedTerm/agents-md]]（および AGENTS.override.md）、[[SoftwareApplication/cursor]] は AGENTS.md と現在は非推奨の `.cursorrules`、[[SoftwareApplication/gemini-cli]] は GEMINI.md である。Copilot はさらに CLAUDE.md、AGENTS.md、GEMINI.md にも対応している。

同研究の2,926リポジトリのサンプルにおいて、コンテキストファイルは大差をつけて最も多く採用された設定機構であり、多くの場合リポジトリには単一のコンテキストファイルの成果物しか含まれていなかった。著者らは2,634のリポジトリにわたり4,860のコンテキストファイルを同定しており、最も一般的なファイル種別は CLAUDE.md で1,661ファイル（34.2%）、次いで AGENTS.md が1,572（32.3%）、copilot-instructions.md が1,344（27.7%）であった。GEMINI.md（159ファイル、3.3%）と `.cursorrules`（73、1.5%）はまれであった。ファイル数ではなくリポジトリ単位で、コンテキストファイルを含む2,634リポジトリに対して測ると、CLAUDE.md は1,195（45.4%）、AGENTS.md は1,069（40.6%）、copilot-instructions.md は925（35.1%）に現れた。コンテキストファイルを使うリポジトリの大半は、そのうち1つか2つしか含まない。

コンテキストファイルは内容を重複させるのではなく、互いを参照することが多い。同研究は三つの参照パターンを同定している。*直接のポインタ*——ファイル名、命令形の文、あるいは Markdown のリンクによって別のファイルを名指しする一行。*文脈を伴う短い参照*——参照先のファイルをどうすべきかを述べる2〜5行。そして*簡単な要約に参照を添えたもの*——見出しと1〜2文の文脈に続くポインタである。互いを参照する518のファイル対のうち、CLAUDE.md が最も多くの外向き参照（357）を持ち、AGENTS.md が最も多くの被参照（368）を持っていた。

## これらのファイルは実際どのようなものか

二つの研究が、周辺のツールではなく成果物そのものを特徴づけており、それぞれがそれをどのような種類のものかについて独自の結論に至っている。

[[ScholarlyArticle/agent-readmes]] は、これがドキュメントというより設定として振る舞うと結論している。1,925リポジトリの2,303ファイルを分析し、その点を率直に述べている。これらは「静的なドキュメントではなく、頻繁で小さな追加を通じて設定コードのように進化する、複雑で読みにくい成果物」である。保守に関する証拠は、Claude Code のファイルの67.0% が複数のコミットにわたって変更されており、GitHub Copilot が59.8%、OpenAI Codex が59.4% であること、そしてそれが小さな漸進的追加の短く急な連続であり、削除はごくわずかであることである。長さはタスクの複雑さとは独立にツールによって異なり——GitHub Copilot のファイルは中央値535.0語、Claude Code は485.0語で、いずれも OpenAI Codex のファイルよりかなり長い——構造は単一の H1 に H2 と H3 の小節が続く浅い階層へ収束する。読みやすさについて同研究の評価は芳しくない。多くのファイルが、著者らが高校レベルの教材に比する「難しい」帯に落ちる。

16の指示カテゴリからなる内容のタクソノミーは、開発者が実際に何を書き込んでいるかを示す。テストが75.9% で首位、次いで実装の詳細が70.8%、アーキテクチャが68.1% である。およそ半数がシステムの概観を含み、24.1% がエージェントの役割と責任を明示的に定義している。著者らが強調する欠落は非機能面である。セキュリティはファイルの14.8%、性能は14.5%、UI/UX は8.7% にしか現れず、そこから彼らは、開発者はエージェントを機能させるためにコンテキストファイルを使っている一方で、「エージェントが書いたコードが安全であるか高性能であるかを保証するガードレールはほとんど与えていない」と結論している。

[[ScholarlyArticle/context-engineering-for-ai-agents-in-open-source-software]] は同じ成果物を別様に——「機械のためのドキュメント」、開発者がいま書き保守するようになった新しい形式のドキュメントとして——記述し、AGENTS.md に焦点を当てたより小さなサンプルから、その慣習がなお流動的であると報告している。確立された内容構造はなく、コンテキストの表現の仕方——記述的、規範的、禁止的、説明的、条件的——にも大きなばらつきがある。その普及の数値は考えさせられるものである。走査した1万の成熟したリポジトリのうち、探した4つの形式のいずれかを採用していたのはわずか5% であった。そもそもこの成果物が研究に値する理由の枠づけは、プロンプトは生成後に保存されることがめったにないため、バージョン管理されたコンテキストファイルは現実世界の [[DefinedTerm/context-engineering]] を覗く数少ない直接の窓である、というものである。

## 執筆の指針

Anthropic の Claude Code のドキュメントは、これを書くことについて最も明示的なベンダーの案内を与えている。推奨される出発点は、`/init` を実行してプロジェクト構造から出発点となるファイルを生成し、時間をかけて洗練していくことであり、`/context` でファイルが読み込まれたことを確認する。必須の形式はないが、その中心的な指示は、ファイルを短く人間に読めるものに保つことである。このファイルは毎セッション読み込まれるため、広く当てはまることだけがそこに属する——ときどきしか関係しないドメイン知識やワークフローは、代わりに必要に応じて読み込まれる [[DefinedTerm/agent-skills]] に属する。

各行について提案される試金石はこうである。*「これを取り除いたら Claude は誤りを犯すようになるか」*。そうでなければ削る。含める／除くの表では、モデルが推測できない Bash コマンド、既定と異なるコードスタイルの規則、テストの手順、リポジトリの作法、プロジェクト固有のアーキテクチャ上の決定、環境の癖、自明でない落とし穴が含める側に置かれる。コードから分かること、標準的な言語の慣習、詳細な API ドキュメント、頻繁に変わる情報、長い説明、ファイルごとの説明、そして「きれいなコードを書く」といった自明な慣行は除く側に置かれる。

述べられる失敗モードは肥大である。長すぎるファイルは、重要な規則がノイズに埋もれるためにモデルが指示を無視する原因になる——それゆえ、規則があるのにモデルが何かをし続けるなら、ドキュメントの診断は規則が不明瞭なのではなくファイルが長すぎるというものであり、逆にファイルがすでに答えている質問をモデルがしてくるなら、表現が曖昧であることを示唆する。推奨される対処はこのファイルをコードのように扱うことである。うまくいかないときにレビューし、定期的に剪定し、振る舞いが実際に変わるかを観察して変更をテストする。例外なく守られねばならない指示については、より強く言い直すのではなくフック（[[DefinedTerm/agent-hooks]] を参照）へ変換することを推奨しているが、「IMPORTANT」や「YOU MUST」といった強調が遵守を高めうるとも指摘している。ファイルは `@path/to/import` 構文で他のファイルを取り込むことができ、チームが貢献できるよう git にコミットしておくことが推奨されている。

実務者の記述も別の方向から同じ点へ収束している。[[BlogPosting/agentic-engineering-surpasses-vibe-coding]] は、`CLAUDE.md` と `README.md` を通じてコンテキストを明示的に渡すことを五つの原則の一つに挙げている。[[BlogPosting/context-engineering]] は、常時読み込まれるファイルをメモリの選択問題を丸ごと回避する方法——毎回引き込まれる狭い固定のファイル集合であり、手続き記憶として機能するもの——として枠づけ、Claude Code の `CLAUDE.md`、Cursor と Windsurf のルールファイルを挙げている。[[TechArticle/effective-context-engineering-for-ai-agents]] は同じ振る舞いをハイブリッドな検索戦略の半分として説明しており、`CLAUDE.md` が前もってコンテキストへ投入される一方、他はすべて glob と grep がジャストインタイムで取り出す。

### これらのファイルの大半は役に立たないという証拠

コンテキストファイルがその場所に値するかについて公表された最も強いチェックは、このウィキには [[BlogPosting/skill-issue-harness-engineering-for-coding-agents]] を通じて間接的に届いている。同記事は、さまざまなリポジトリにわたって138のエージェントファイルを検証した ETH チューリッヒの研究を要約し、その知見を次のように報告している。LLM が生成したファイルは実際には性能を*損ない*ながら20% 以上のコスト増を招いたこと。人間が書いたものは4% ほどしか助けにならなかったこと。エージェントはコンテキストファイルの指示の処理に14〜22% 多くの推論トークンを費やし、より多くのステップを踏み、より多くのツールを走らせながら、解決率を改善しなかったこと。そしてコードベースの概観とディレクトリ一覧はまったく助けにならなかったこと——エージェントはリポジトリの構造を自力で発見するからである。研究そのものはここに取り込まれていないため、これらの数値は研究自身の記述ではなく、同記事による特徴づけとして記録されている。

同記事の読みは、これらの知見が上の執筆の指針を掘り崩すのではなく裏づけるというものである。指摘された失敗の一つ一つが、同チームがすでに与えていた助言に対応する。ファイルを自動生成しないこと、指示は合理的な範囲でできるだけ少なくすること、段階的開示を用いること、そして内容を簡潔かつ普遍的に当てはまるものに保つことである。同記事は自分たちのファイルが60行未満であると報告している。これは、[[PresentationDigitalDocument/claude-code-advanced-patterns]] が大規模なコードベースに推奨する200行の上限とも、無視される規則を表現の問題ではなく長さの問題と診断する上のベンダーの案内とも収束する。

### プロジェクトのファイルの上に提案される層

[[ScholarlyArticle/agentic-ai-assisted-coding-epistemic-grounding]] は、現在一般に使われているファイル種別がある欠落を共有していると論じる。計画ファイルはユーザーの意図を、プロジェクトのコンテキストファイルはプロジェクトのガイドラインを、`SKILL.md` は技法を担うが、そのいずれも「ドメイン固有の妥当性の制約を強制」しない——このユーザーが、このプロジェクトが、この技法が何を望むかにかかわらず成り立つ規則を、である。

その提案は第四の、分野をスコープとする層 [[DefinedTerm/epistemic-grounding-document]] であり、リポジトリの所有者ではなくドメインのコミュニティによって書かれ統治される。示される順序は可塑性の低下する順——セッション、プロジェクト、技法、分野——であり、各層はその下の層より安定的かつ権威的である。それゆえ分野をスコープとする不変条件はその下のすべてを制約し、「計画やスキルとの衝突では、逆ではなくそちらが勝つ」。

二つの設計上の細部が、これを上で述べたファイルから区別する。その内容は、他のあらゆるコンテキストに優先する Hard Constraints と、警告するにとどまる Convention Parameters に分かれる——ここで述べた単一層のファイルが行わない厳格さの区別である。そしてその権威は、場所ではなく来歴から来ると主張される。規則が個人の好みではなくドメインのコミュニティの合意であるがゆえに、「専門家でない者によって覆されることに抵抗する」と同論文は論じており、エージェントを操る人がドメインの専門家であるとは限らないことを踏まえた、この層全体についての論拠がこれである。これは草案として書かれた例示ファイルによって示され、いまのところ単一構成・単一ターンの原理実証テストに裏づけられた提案である——Hard Constraint をそれぞれ侵す6つのプロンプトを、科学的な妥当性を無視するようエージェントに指示する敵対的なプロジェクトのコンテキストファイルに対して走らせたものである。著者らは遵守が大幅に改善する一方、「明示的な上書きの指示や、規範的な言い回しが弱められた場合には劣化する」と報告しており、この権威の順序をネイティブに実装するエージェントのスキャフォールドは存在せず、システムプロンプト経由の読み込みが最も一貫した回避策だったと指摘している。

## 関連用語

コンテキストファイルは、同じ研究が目録化した他の七つの設定機構——[[DefinedTerm/agent-skills]]、[[DefinedTerm/subagents]]、コマンド、ルール、設定、フック、MCP サーバー——と並ぶが、最も広く採用され、かつ執筆の摩擦が最も小さい点で際立っている。同研究は、この優勢が、設定が現在は自動化としてよりもドキュメントとして使われていることを意味すると観察している。
