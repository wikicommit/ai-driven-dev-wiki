エージェントスキル（Agent Skills）——文献では単に Skills と呼ばれる——は、エージェンティック AI コーディングツールの能力を、専門的な文脈知識とワークフローによって拡張する設定機構である。[[ScholarlyArticle/configuring-agentic-ai-coding-tools]] はこれを、エージェントが必要に応じて呼び出せるプロンプト、ツール、ドキュメントをひとまとめにするものだと説明している。Anthropic によって導入され、現在は複数のツールにまたがってサポートされるオープン標準として機能している。

構造としては、Skill は SKILL.md ファイルを含むディレクトリである。このファイルには、少なくとも name と description を持つ YAML フロントマターと、それに続いてタスクをどう遂行すべきかを記した本文の指示が含まれていなければならない。Skill はその指示を呼び出し元のエージェント自身のコンテキストの中で実行する。この点が [[DefinedTerm/subagents]] との違いである。

## 用法

この研究で調査された5つのツールはいずれも Skills をサポートしており、それぞれ独自のディレクトリを用いる。`.claude/skills/`、`.github/skills/`、`.codex/skills/`、`.cursor/skills/`、`.gemini/skills/` である。

Skill は3種類の省略可能なリソースを利用でき、これらは必要になったときにエージェントによって読み込まれる。エージェントが実行できる実行可能コードのための `scripts/`（言語の選択肢には Python、Bash、JavaScript などがある）、エージェントが必要に応じて読めるドキュメントのための `references/`（技術リファレンス、テンプレート、構造化データを含む）、そして文書や設定のテンプレート、画像、データファイルといった静的リソースのための `assets/` である。

実際の採用は、この表現力の幅に比べると浅い。研究は 158 のリポジトリにわたって 601 個の Skills を発見した。1リポジトリあたり平均 3.8 個だが中央値は 2（最小 1、最大 28）である。大半——501 個、83.3%——は追加のリソースをまったく含んでいなかった。リソースが存在する場合、最も多かったのは `references/`（48 個、8.0%）で、次いで `scripts/`（34 個、5.7%）だった。12 個（2.0%）が両方を組み合わせ、`assets/` はわずか 4 個（0.7%）にしか現れず、残りの組み合わせはそれぞれ 1 回ずつだった。著者らはこれを、Skills が動的で実行可能なリソースよりも静的なドキュメントに大きく依存していると要約し、実務上 Skills は実行可能なワークフローのバンドルというより、主に構造化されたテキストとして機能していると結論づけている。

一方で、開発者は仕様の長さに関するガイダンスには従っているようだ。仕様は SKILL.md ファイルを 500 行未満に保ち、詳細な内容は別ファイルに移すことを推奨しているが、発見された 601 個の Skills のうちこれを超えていたのは 25 個（4%）にとどまった。

Anthropic の Claude Code のドキュメントは、この仕組みの2つの異なる用途を説明している。第一は、プロジェクト、チーム、ドメインに固有の知識であり、関連する場面で自動的に適用されるもの——例として挙げられるのは REST 設計ルールを保持する `api-conventions` スキルである。第二は、`/skill-name` として直接呼び出される反復可能なワークフローであり、例として挙げられるのは、GitHub の Issue を分析して修正する手順を番号付きで記した本文を持つ `fix-issue` スキルである。副作用を伴うワークフローについては、意図的にトリガーされたときにだけ実行されるよう `disable-model-invocation: true` を推奨している。またドキュメントは Skills を [[DefinedTerm/context-files]] と、読み込みの基準という観点で対比する。コンテキストファイルは毎セッション読み込まれるため、そこに置くべきなのは広く適用可能な内容だけである。一方、ときどきしか関係しない知識は、すべての会話を膨らませることなく必要に応じて読み込まれる Skill に置くべきだ、というわけである。

Skills はサードパーティによる配布のパッケージング形式でもある。[[SoftwareApplication/context-engineering-kit]] は自らの技法を、agentskills.io の仕様に従うスキルを持つプラグインとして出荷している。そのメンテナは、一般的な情報スキルよりも、サブエージェントと組み合わせたコマンド志向のスキルを好むと述べており、その理由は必要にならない情報でコンテキストを埋めないためだという——同じオンデマンド性についての、トークン効率の観点からの論拠である。彼らは制約も指摘している。汎用のツールを通じてスキルをインストールしてもサブエージェントは一緒に運ばれないため、両方に依存するプラグインは部分的にしか可搬ではない。

### あるベンダーによる仕組みの文書化

Anthropic の Claude Code スキル専用ドキュメントは、上記の調査よりも詳しく仕組みを記しており、そこで文書化されているものがスーパーセットであることを明言している。Claude Code のスキルは agentskills.io で公開されている Agent Skills オープン標準に従っており、ドキュメントはこれを複数の AI ツールにまたがって機能するものだと説明する。そのうえで Claude Code は、呼び出しの制御、サブエージェント内でのスキル実行、動的なコンテキスト注入という独自の機能でこの標準を拡張している。この境界は助言的ではなく強制的である。Claude Code の外では仕様に定められた6つのフロントマターフィールド（`name`、`description`、`license`、`compatibility`、`metadata`、`allowed-tools`）しか受け付けられず、それ以外のフィールドを含めると、無視されるのではなくパッケージングやアップロードがハードエラーで失敗する。

このドキュメントにある2つの設計上のポイントは、この仕組みがコンテキストファイルとどう違うのかに関わる。第一は、すでに述べた読み込みの基準であり、そこではコストの観点から述べられている。スキルの本文は使われるときにだけ読み込まれるため、長いリファレンス資料も必要になるまではほとんどコストがかからない。第二は、読み込まれた後に何が起こるかである。レンダリングされた `SKILL.md` は単一のメッセージとして会話に入り、その後セッションの残りの間そこに留まる。したがって、ドキュメントの枠づけによれば、一行一行が反復的なトークンコストであり、タスク全体を通じて適用されるべきガイダンスは一回限りの手順ではなく恒常的な指示として書かれるべきである。自動コンパクションは、呼び出されたスキルを予算の範囲内で引き継ぐ。要約の後に各スキルの最新の呼び出しを再添付し、合計 25,000 トークンの予算の中でそれぞれの先頭 5,000 トークンを保持し、直近に呼び出されたスキルから順に埋めていく。そのため、多数のスキルを呼び出したセッションでは古いスキルが完全に落とされることもある。

ドキュメントはスキルの内容を、どうトリガーされることを意図しているかによって2種類に分けている。**リファレンス的な内容**——規約、パターン、スタイルガイド、ドメイン知識——はインラインで動作し、モデルが会話と並行してそれを適用できるようにする。**タスク的な内容**——デプロイ、コミット、コード生成の手順——は通常、`/skill-name` として意図的に呼び出されることを想定している。どちらが可能かを制御するフロントマターのフィールドが2つある。`disable-model-invocation: true` はユーザーだけがそのスキルを呼び出せることを意味し、副作用を伴うものすべてに推奨される——コードが準備できているように見えるからといってモデルにデプロイを決めさせたくない、というのがその理由である。`user-invocable: false` はモデルだけが呼び出せることを意味し、ユーザーが取る行動としては意味をなさない背景知識のためのものである。

これ以外に文書化されているフロントマターは、引数の扱い（`arguments`、`argument-hint`）、スキルが有効な間に適用されるモデルと推論努力の上書き、スキルが自動的に有効化される条件を絞る `paths` の glob、スキルが呼び出されたときに登録する `hooks`（[[DefinedTerm/agent-hooks]] を参照）、そして `context: fork` を扱う。最後のものはスキルをインラインではなくフォークされたサブエージェントのコンテキストで実行するもので、スキルが呼び出し元エージェントのコンテキストで実行 *されない* 唯一の文書化されたケースである。`allowed-tools` はスキルを呼び出すターンに対してツールを事前承認するもので、ドキュメントはこれ自体をサプライチェーン上の懸念として明示している。ワークスペースの信頼はこのフィールドをゲートしないため、リポジトリにチェックインされたスキルは自らに広範なツールアクセスを付与できる。そのため、そこでエージェントを実行する前にリポジトリのスキルの `allowed-tools` を確認することが推奨されている。

スキルファイルがどこに置かれるかが、誰がそれを使えるかを決める。名前の衝突は近さではなく出所によって解決される。エンタープライズが個人を上書きし、個人がプロジェクトを上書きし、これらいずれのレベルのスキルも同名のバンドル済みスキルを上書きする——ただしそのバンドル済みスキルのエイリアスは上書きしない。プラグインのスキルは `plugin-name:skill-name` という名前空間に置かれるため、他のレベルのスキルとは衝突しない。またスキルは作業ディレクトリ配下の入れ子になった `.claude/skills/` ディレクトリからも読み込まれ、エージェントがそのサブディレクトリ内のファイルを最初に読むか編集した時点で利用可能になる。これによって、モノレポ内のパッケージが自分自身にスコープされたスキルを提供できる。

Claude Code は **バンドル済みスキル** も出荷している。ドキュメントが名前を挙げているのは `/doctor`、`/code-review`、`/batch`、`/debug`、`/loop`、`/claude-api` である。これらはプロンプトベースであり、モデルに詳細な指示を与えて自身のツールで作業をオーケストレーションさせるものだと説明されている。固定のロジックを直接実行する大半の組み込みコマンドとは対照的である。関連する場面で自動的に呼び出されるものもあれば、明示的な呼び出しでしか動かないものもある。ドキュメントは後者を、実行に時間とトークンを要するチェックをいつ走らせるかの主導権をユーザーに残すためだと説明している。

### 可搬なエンジニアリング実践としてのスキル

[[Person/arun-gupta]] の [[PresentationDigitalDocument/spec-driven-development-using-coding-agents]] は、この仕組みをコンテキストの観点ではなく再利用の観点から擁護し、スキルを可搬なエンジニアリングパターンとして説明する。解法を一度捉えれば複数のプロジェクトとエージェントにまたがって適用でき、プロジェクトごとにプロンプトを作り直す代わりにベストプラクティスをバージョン管理されたスキルとして成文化できる、というのである。彼が挙げるカテゴリは、テストのパターン、API 連携、デプロイスクリプト、コードレビューのガイドライン、Infrastructure as Code であり、Helm チャートを書く際の一貫したアプローチを強制する例として Helm スキルが示されている。彼は `agentskills.io` の仕様と、再利用可能なエージェントの能力を発見・共有・提供するためのスキルリポジトリを指し示している。

彼が [[DefinedTerm/spec-driven-development]] との間に引く関係は、両者が互いを強化するというものである。仕様が標準化されたスキルを参照することで、仕様自体がより正確で実行可能になり、一方でスキルはプロンプトエンジニアリングの手間を減らす。彼の具体例は、実装計画の一つのサブセクションを端から端まで実装するスキルである——コンテキストの汚染を避けるためにクリーンなコンテキストから始め、計画から要件を読み取り、タスクの追跡を作成し、プロジェクトのパターンに沿って実装し、テストを書き、必ず通らなければならない品質チェックを実行し、ドキュメントを更新し、コミットする——。そのスキルの本文は、エラーハンドリング、API エンドポイントの実装、テストの記述、コミットの書式について、他のスキルを名前で参照している。

### MCP の姉妹標準として

[[DefinedTerm/model-context-protocol]] に関する Wikipedia の記述は、Anthropic による Agent Skills の公開を 2025年12月としており、AI エージェントが必要に応じて読み込むタスク固有の指示とリソースをパッケージングするための姉妹オープン標準であり、MCP と同じオープン標準のアプローチに従うものだと説明している。Anthropic が MCP そのものを [[Organization/agentic-ai-foundation]] に寄贈したのと同じ月のことである。

Anthropic 自身のエンジニアリング記事は、別の方向からスキルにたどり着く。[[TechArticle/code-execution-with-mcp]] はスキルを、専門的なタスクにおける性能を高めるためにモデルが使う、再利用可能な指示・スクリプト・リソースのフォルダとして説明し、ファイルシステムにアクセスできるエージェントの自然な到達点として扱う。あるタスクのために動作するコードを作り上げたエージェントは、その実装を将来のために保存でき、そうして保存された関数に `SKILL.md` ファイルを加えれば、モデルが参照できる構造化されたスキルができあがる。この見方では、エージェントは徐々により高水準の能力の道具箱を築き上げ、最も効果的に働くために必要な足場を自ら進化させていく——[[DefinedTerm/code-execution-with-mcp]] を参照。

## 関連用語

Skills は、この研究で整理された8つの設定機構の一つであり、他には [[DefinedTerm/context-files]]、[[DefinedTerm/subagents]]、Commands、Rules、Settings、Hooks、そして MCP サーバー（[[DefinedTerm/model-context-protocol]] を参照）がある。著者らは、Skills には静的な指示を超えて反復的なワークフローを符号化する未開拓の可能性があると論じ、その可能性と現在の使われ方の隔たりは、この仕組みの新しさと、Markdown の指示を書くのに比べて実行可能な Skills の設計と保守に要する労力の両方を反映しているのではないかと示唆している。
