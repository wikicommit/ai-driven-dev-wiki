Agent Skills は、エージェントの機能を拡張するモジュラーなケイパビリティをパッケージ化するための、Anthropic が Claude
向けに文書化したフォーマットである。スキルのパッケージは、エージェントのベンダー以外の者によっても書かれ公開されている。
Google のデベロッパーリレーションズのチームは、エージェントスキルは、モデルの固定された訓練知識と、速く動くライブラリや
SDK とのあいだのギャップを埋める、極めて軽量でありながら有効になりうる方法として浮上してきたと書き、どんな SDK の
メンテナでもそのギャップに対して何ができるかを示そうとしている。各スキルは、指示、メタデータ、そしてスクリプトや
テンプレートといった任意のリソースをひとまとめにし、モデルは関連する場面でそれらを自動的に用いる。ベンダーのドキュメント
はスキルをプロンプトと、スコープと持続性を根拠に区別している。プロンプトは一度きりのタスクに対する会話レベルの指示で
あるのに対し、スキルは再利用可能でファイルシステムに基づくリソースであり、必要に応じて読み込まれるため、同じガイダンス
を会話のたびに繰り返す必要がない。掲げられている利点は、ドメイン固有のタスクに向けてモデルを専門化できること、
ガイダンスを繰り返さず一度作れば済むこと、そして多段階のタスクのために複数のスキルを組み合わせられることである。

このフォーマットについての Anthropic 自身のエンジニアリングの記述
（[[BlogPosting/equipping-agents-for-the-real-world-with-agent-skills]]）は、これを欠陥への対応ではなくケイパビリティへの
対応として位置づけている。汎用のエージェントがひとたび計算環境をまるごと操作できるようになると、開かれた問いは、それら
にドメインの専門性を、組み合わせ可能に、スケーラブルに、そして可搬なしかたでどう備えさせるかになる。この記述はある
たとえを提示している — スキルを作ることは新入社員向けのオンボーディングガイドを組み立てることに似ている — とともに、
それが置き換えるのはユースケースごとに別々に設計されたエージェントを作ることだと論じる。2025 年 12 月 18 日にこの記事に
加えられた注記は、Agent Skills がその後、クロスプラットフォームの可搬性のためにオープン標準として公開されたことを記録
している。製品の発表（[[BlogPosting/introducing-agent-skills]]）は同じ日付の独自の注記を載せており、それと並ぶさらに
2 つの追加を記録している。スキルの組織全体での管理と、パートナーが作ったスキルを紹介するディレクトリである。

Anthropic が Claude 向けに文書化しているとおり、このフォーマットは設計上ファイルシステムに基づいている。スキルは Claude
の仮想マシン環境の中にディレクトリとして存在し、Claude はごく普通のシェルコマンドでそれらとやりとりする。`SKILL.md` を
読んでその指示をコンテキストへ取り込み、指示が他のファイルを参照していればそれを読み、同梱されたスクリプトをシェル経由
で実行して、そのコードではなく出力だけがコンテキストウィンドウへ入るようにする。他のハーネスは別の手段でスキルに到達
する。たとえば Google の評価では、モデルに `activate_skill` ツールとドキュメントをダウンロードするための `fetch_url`
ツールが与えられた。

## 用法

すべてのスキルには、`name` と `description` という 2 つの必須フィールドを YAML フロントマターに載せた `SKILL.md`
ファイルが必要である。ドキュメントはそれぞれの制約を述べている。名前は最大 64 文字で、小文字・数字・ハイフンに限られ、
XML タグと予約語は使えない。説明は空であってはならず最大 1024 文字で、やはり XML タグは使えない。説明には、そのスキルが
何をするのかと、いつ使われるべきかの両方を書かなければならない。モデルがスキルを発火させるかどうかを判断する際に、
要求と突き合わせるのがこの説明だからである。

内容は 3 つのレベルに整理され、それぞれ異なるタイミングで読み込まれる — ドキュメントが
[[DefinedTerm/progressive-disclosure]] と呼ぶ配置である。メタデータは常に読み込まれ、その費用はスキル 1 つあたりおよそ
100 トークンとされる。`SKILL.md` の本体はスキルが発火したときに読み込まれ、その予算は 5,000 トークン未満とされる。
そして同梱されたリソースは、読まれるまで費用がかからない。文書化されている帰結は、コンテキスト上のペナルティなしに多数の
スキルをインストールできること、そしてスキルには膨大な資料 — 網羅的な API ドキュメント、大きなデータセット — を同梱でき、
それが使われない限りコンテキストに計上されないことである。

ベンダーのエンジニアリングの記事は、この配置を具体的な事例で通して説明している。Claude のドキュメント編集能力の背後に
ある PDF スキルである。その `SKILL.md` は同梱された 2 つのファイル、`reference.md` と `forms.md` を参照しており、記事が
フォーム記入の指示を `forms.md` へ移した理由として挙げているのは、スキルの中核を軽く保つことである。モデルが実際に
フォームを記入するときにだけそのファイルを読むだろうという見込みに立ってのことだ。同じスキルは、PDF を読んでその
フォームフィールドを抽出する Python スクリプトも同梱しており、モデルはスクリプトも PDF もコンテキストに入れることなく
それを実行できる。記事はこの配置を 2 つの根拠で正当化している。コードがすでに行う操作を実行するためにトークンを生成する
のははるかに高くつくこと、そして多くのアプリケーションはコードだけが提供する決定論を必要とすることである。

執筆の進め方について、この記事は評価から始めることを勧めている。代表的なタスクでエージェントを走らせてどこでつまずくか
を見つけ、次に何が必要になるかを先回りするのではなく、観察されたそのギャップに対して段階的にスキルを作っていくのである。
`SKILL.md` は、扱いにくくなった時点で参照される別ファイルへ分割することを勧め、コンテキストが相互排他的であったり一緒に
使われることが稀であったりする場合は、それらの経路を分けておくとトークンの使用量が減ると付け加えている。また、同梱の
コードは実行可能なツールでありドキュメントでもあるので、あるスクリプトがそのどちらなのかをスキルは明確にすべきだと
述べている。`name` と `description` については特に注意を向けるよう強調している。そもそもスキルを発火させるかどうかを
モデルが判断するのに使うのがそれらだからである。最後の提案は、作業を進めながらモデル自身にうまくいったアプローチと
繰り返し起きる間違いをスキルへ書き取らせること、そして道を外れたときには自己内省するよう求めることである。

利用できる範囲はベンダーの製品ごとに異なる。API ではスキルはコード実行ツールを必要とし、コンテナのパラメータの
`skill_id` によって選択される。PowerPoint、Excel、Word、PDF 向けの既製のドキュメントスキルがあり、カスタムのスキルは
Skills API を通じてアップロードされワークスペース内で共有される。[[SoftwareApplication/claude-code]] ではカスタムの
スキルはファイルシステムに基づいていてアップロードは不要で、個人用またはプロジェクトのディレクトリに置かれる。一方で
既製のドキュメントスキルはそこでは利用できない。claude.ai では両方とも動作し、カスタムのスキルは zip ファイルとして
アップロードされ、中央集権的に管理されるのではなくユーザーごとに個別のものになる。ドキュメントは、それらが組織全体で
共有されることはなく管理者が中央集権的に管理することもできないこと、そして claude.ai はカスタムのスキルの中央集権的な
管理者による管理や組織全体への配布をサポートしていないことを述べている。これは、スキルの組織全体での管理が追加された
という製品発表の 2025 年 12 月の注記と整合しないまま並存している。2 つのソースは異なることを述べており、どちらも互いに
対して日付づけられていない。エンジニアリングの記事は、公開時点でこのフォーマットが Claude.ai、Claude Code、
[[SoftwareApplication/claude-agent-sdk]]、そして Claude Developer Platform にわたってサポートされていたと述べている。

製品の発表は、各サーフェスへの到達のしかたを埋めている。Claude のアプリでは、このフォーマットは Pro、Max、Team、
Enterprise のユーザーが利用できるとされ、Team と Enterprise では管理者が先に組織全体で有効にする必要がある。呼び出しは
手動で選択するのではなく自動であり、発表によればスキルは Claude が作業する際の思考の連鎖の中に現れる。Developer
Platform では、スキルは Messages API のリクエストに追加でき、`/v1/skills` エンドポイントがカスタムスキルのバージョン
管理と管理をプログラム的に制御できるようにする。またスキルは Code Execution Tool のベータを必要とするとされ、それは
スキルが動くのに必要な安全な環境を提供するものと説明されている。Claude Code では、`anthropics/skills` マーケット
プレイスからプラグインとしてインストールするか、手動で `~/.claude/skills` に置くことでインストールし、バージョン管理を
通じてチームと共有する。

ある実務家の記述は、同じ構造上の助言に逆の方向から到達しており、それを検証したと報告している唯一のソースである。
[[BlogPosting/mercari-pm-agent-design]] は、プロダクトマネージャーのワークフローを端から端まで担うスキルを作った経緯を
述べ、まずすべての定義を 1 つの `SKILL.md` にまとめ、次に別の評価スキルによるスコアリングを通じて、ファイルが長くなる
ほど出力の精度が悪くなることを発見したと報告している。著者の対応は、振る舞いの定義 — 何をどの順序で行うか — を、
`references/` ディレクトリに置かれた参照データやテンプレートから切り離すことであり、この構造上の変更だけでスコアに
明確な改善が生じたと報告している。記事はこれを、ソフトウェアエンジニアリングの関心の分離をプロンプトの設計に適用した
ものとして位置づけ、その根底にある問題を、モデルが長いコンテキストの中ほどにある情報に十分な注意を向けられなくなる、
しばしば「Lost in the Middle」と呼ばれる現象と関連づけている。また、英語の指示のほうが Claude では精度が高くなる傾向が
あるという理由で `SKILL.md` を英語で書いていることにも触れている。この記述が上記のベンダーの助言に加えているのは、
異なるルールではなくそれに従うべき理由である。ベンダーはファイルが扱いにくくなったら分割することを勧めているが、この
著者はそうしなかった場合の代償を測ったことを報告している。

その記事のもう一方の設計上の主張は、スキルの指示がどう整理されるかではなく、何を禁じるべきかに関わる。掲げられている
立場は、LLM を業務のワークフローに組み込むうえで最も危険なリスクは、もっともらしいが根拠のない出力 — データが存在しない
ところにもっともらしく見える数字をモデルが出してしまうこと — であり、これはモデルに嘘をつくなと告げることでは解決でき
ない、というものである。スキルは、データの欠落を認識したときにどう振る舞うかを規定しなければならない。著者が用いている
ルールは、未確認のデータには「未提供」または「要検証」とラベルを付けなければならないこと、数字と出典を決して捏造しては
ならないこと、そしてエージェントが完全性を推測することを禁じる指示を併せることで、ユーザーからの明示的な確認があった
ときにのみ次のステップへ進めるようにすることである。著者のまとめは、スキルを設計することは振る舞いの仕様を書くことに
近く、モデルが*してはならない*ことを明確に定義するほうが、命令よりも直接的に精度を高める、というものである。

2 つ目の実務家の記述は、このフォーマットが個人の著者によってではなく、組織で共有されるインフラストラクチャとして使われて
いる様子を述べている。[[BlogPosting/agentic-engineering-at-zalando-a-snapshot]] は [[Organization/zalando]] における
中央集権的なスキルのコレクションを報告している。それはプラグインごとにまとめられ、職能をまたぐ共通のタスクや関心事 —
記事はデータ、エンジニアリング、フロントエンド、SRE を挙げている — と、プログラミング言語をまたぐそれらに対応している。
記事は、マルチアーキテクチャのビルドのような新しいプラットフォームのツールやインフラの実践をチームが採用するのを導く
マイグレーションのスキルが、広く人気のある種類だと述べている。配布は、マネージドな設定か、必要なシンボリックリンクを
インストールする CLI コマンドによって行われ、記事はこれを一部のエージェントがプラグインのマーケットプレイスを
サポートしていないことに帰している。

その記述が配布の仕組みを超えて加えているのは、広い貢献を促したことに帰される二次的な効果である。このコレクションは、
CI/CD パイプラインでプラグインの構文を検証することや、スキルとスクリプトの境界をどこに引くべきか — 記事の例は OAuth の
トークン生成がどちらに属するか — といった問いについて、組織全体でベストプラクティスを発見し広める手段になった。自分たち
のスキルを書くチームは、このコレクションを参照と着想の源として使っているという。これらは 1 つの組織の実践についての著者
自身の観察であり、評価は報告されていない。

執筆はそれ自体のスキルによって支えられている。発表は、対話的なガイダンスを与える `skill-creator` スキルを説明している。
ワークフローについて尋ね、フォルダ構造を生成し、`SKILL.md` ファイルを整形し、リソースを同梱する — 手作業でのファイル
編集は一切不要である。これはフォーマットがそれ自身に適用されたものだ。スキルを書くための手続き的な知識が、スキルとして
パッケージ化されているのである。

3 つ目の実務家の記述は、このフォーマットがここで現れる最も小さなスケール — チームや組織ではなく 1 人の開発者 — である。
[[BlogPosting/lessons-from-releasing-a-product-with-ai-agents]] は、繰り返すプロンプトを打ち直すのが面倒になった時点で
それらをスキルとしてテンプレート化したことを報告しており、その例はコミットされていない変更を分析してそれに対するテスト
を書かせるという定型の依頼である。そしてそのようなスキルとは単なるプロンプトではなく、エンジニアのノウハウをコーディング
の規約へ移植したものだと述べている。2 つ目の用途は、他人が書いたスキルの利用である。バックエンド開発者である著者は、
サードパーティ製の SEO スキルを自分のサイトに対して走らせて改善点のリストを作らせ、そのリストをエージェントへ戻して
ソースに適用させるというループを、およそ週に一度繰り返した。そこから引き出された観察は、このフォーマットが最も役立つのは
自分の専門ではない領域だ、というものである。これは Google の記述が速く動く SDK について行っている知識ギャップの論と同じ
ものだが、モデルの訓練データのカットオフではなく開発者自身の専門性のほうから到達されている。この記述は評価を報告して
おらず、エージェントとして Claude Code を挙げる以上に、どのハーネスの機能セットを説明しているのかを特定していない。

## 適用される場面

このフォーマットが当てはまるのは、エージェントがドメインの専門性 — ワークフロー、コンテキスト、ベストプラクティス —
を必要とし、それがなければ会話のたびに述べ直されることになる場面である。Anthropic が文書化している配置では、モデルに
ファイルシステムへのアクセスとコマンドの実行能力を与える実行環境が前提となる。

ドキュメントは、このフォーマットが伴うセキュリティ上の前提について率直である。スキルは信頼できる出所のものだけを使う
べきである。スキルは指示とコードを通じてモデルに新しいケイパビリティを与えるものであり、悪意あるスキルは、表明された
目的に合わないしかたでツールを呼び出したりコードを実行したりするようモデルを仕向けうるからである。ドキュメントは同梱
されたすべてのファイルを監査するよう助言し、外部の URL からデータを取得するスキルを特に危険なものとして名指ししている
（取得された内容そのものが悪意ある指示を含みうるため）。そして、インストールをソフトウェアのインストールと同じように
扱うことを勧めている。エンタープライズの組織には、claude.ai と Claude Cowork を通じてアップロードされたカスタムの
スキルに対するコンテンツスキャンが提供される。ドキュメントは、これが Skills API やコンソールを通じてアップロードされた
スキルは対象外であることに触れている。エンジニアリングの記事は同じ助言を独自の言い方で与えており、悪意あるスキルは
それが使われる環境に脆弱性を持ち込んだり、データを持ち出したり、モデルを意図しないアクションへ差し向けたりしうると警告
し、信頼性の低い出所のスキルは使う前に、そのコードの依存関係、画像やスクリプトといった同梱リソース、そして信頼できない
外部のネットワークへ接続するあらゆる指示に注意しながら読み通すよう求めている。どちらの記述も、フォーマット自体が提供する
何らかの機構ではなく、人手による監査を提案している。

## 証拠と限界

Google は Gemini API 向けのスキル（[[SoftwareApplication/gemini-api-developer-skill]]）を作り、117 のコード生成プロンプト
からなるハーネスに対して評価したことを報告しており、強い推論のサポートをもつ新しめのモデルでは結果が著しく向上し、古い
モデルでははるかに向上が小さかったとしている。Google はこの結果を、スキルは機能しているが、スキル単体ではなくモデルの
推論能力に依存している、と読んでいる。手法と数値は
[[BlogPosting/closing-the-knowledge-gap-with-agent-skills]] にある。

上記のメルカリの記述は、スキルが何を付け加えるかではなく、スキル自身の*構造*についての評価を報告しているここでの唯一の
ソースである。その手法には但し書きが必要である。スコアは同じ著者が書いた評価スキルから得られたもので、同じ著者が実際の
改善テーマから組み立てたデータセットに対して、同じ著者が実装前に定義した基準 — 理解の正確さ、仕様の具体性、実現可能性、
UX の妥当性 — に照らして走らされている。記事は数値を示さず、改善を定量化せずに「明確」と述べており、短いファイルのほうが
高いスコアになった理由についての著者自身の推論を報告していて、その変数を切り分けた実験を報告しているわけではない。基準を
先に定義すること自体が 1 つの手法として提示されており、記事はこれを Prompt TDD と呼んでいる。

Anthropic 自身のエンジニアリングの記事は、このフォーマットの評価や測定を何も報告していない。スキルに同梱されるコンテキスト
が事実上無制限であるという主張は、ファイルシステムに支えられたエージェントが何を読まずに済むかについてのアーキテクチャ上の
論であって測定された結果ではなく、フォーマットの利点についてのその記述は設計者自身のものである。

Google の著者らは 2 つの限界を挙げている。Vercel の作業から、[[DefinedTerm/agents-md]] を通じた直接の指示のほうがスキルを
使うより有効になりうると知っていること、そしてそれゆえに、ドキュメント用の MCP サーバーのような、生きた SDK の知識を供給
する他の経路も探っていることである。Vercel の評価そのものはこのウィキのソースに含まれていないので、ここに記録されているの
は Google の著者らがそこから得たと述べている内容である。2 つ目はメンテナンスである。Google は、ユーザーに手動で更新するよう
求める以上のまともなスキルの更新の筋書きは存在しないと述べ、長期的にはこれがユーザーのワークスペースに古びたスキルの情報を
残し、益より害をもたらしかねないと警告している。この懸念は、このフォーマットがここで用いられている目的に反するものである。
エージェントを最新に保つために採り入れられた機構が、それ自身その場で古びうるからである。

Anthropic は 2 つの方向を、出荷済みの振る舞いとしてではなく意図として述べている。外部ツールを伴うワークフローをエージェント
に教えることで、スキルが [[DefinedTerm/model-context-protocol]] のサーバーをどう補完できるかを探ること、そしてエージェント
が自らスキルを作り、編集し、評価できるようにすることである。
