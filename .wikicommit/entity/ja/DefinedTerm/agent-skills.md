エージェントスキル（Agent Skills）——文献では単にスキルと呼ばれる——とは、エージェンティックな AI コーディングツールの能力を、専門化された文脈的な知識とワークフローによって拡張する設定機構である。[[ScholarlyArticle/configuring-agentic-ai-coding-tools]] は、これをエージェントが必要に応じて呼び出せるプロンプト、ツール、ドキュメントを束ねるものと説明している。Anthropic によって導入され、現在はツール横断で支持されるオープン標準として機能している。

構造としては、スキルは SKILL.md ファイルを含むディレクトリである。そのファイルは少なくとも name と description を持つ YAML フロントマターを含み、続いてタスクをどう遂行すべきかの本文の指示を含まねばならない。スキルは呼び出し元のエージェント自身のコンテキストの内側でその指示を実行するのであり、これが [[DefinedTerm/subagents]] との違いである。

## 用法

同研究が調査した五つのツールはいずれもスキルに対応しており、それぞれ自らのディレクトリ——`.claude/skills/`、`.github/skills/`、`.codex/skills/`、`.cursor/skills/`、`.gemini/skills/`——のもとに置く。

スキルは三種類の任意のリソースを利用でき、必要に応じてエージェントが読み込む。`scripts/` はエージェントが実行できるコードで、言語の選択肢には Python、Bash、JavaScript がある。`references/` はエージェントが必要に応じて読めるドキュメントで、技術的なリファレンス、テンプレート、構造化データを含む。`assets/` は文書や設定のテンプレート、画像、データファイルといった静的なリソースである。

実際の普及は、この表現力の幅に比べて浅い。同研究は158のリポジトリにわたって601のスキルを見出しており、1リポジトリあたり平均3.8だが中央値は2（最小1、最大28）である。圧倒的多数——501スキル、83.3%——は追加のリソースをまったく含んでいなかった。リソースが存在する場合、最も一般的なのは `references/`（48スキル、8.0%）、次いで `scripts/`（34、5.7%）であり、12スキル（2.0%）が両方を組み合わせ、`assets/` はわずか4件（0.7%）に現れ、残りの組み合わせはそれぞれ1件ずつであった。著者らはこれを、スキルが動的で実行可能なリソースではなく静的なドキュメントに主として依拠していると要約し、実務においてスキルは実行可能なワークフローの束というより構造化されたテキストとして機能していると結論している。

開発者は仕様の長さの指針には従っているようである。仕様は SKILL.md ファイルを500行未満に保ち詳細な素材は別ファイルへ移すことを推奨しているが、見出された601スキルのうちこれを超えたのは25件（4%）だけであった。

Anthropic の Claude Code のドキュメントは、この機構の二つの異なる用途を説明している。第一は、プロジェクト・チーム・ドメインに固有の知識で、関連するときに自動的に適用されるものである——例として REST の設計規則を保持する `api-conventions` スキルが挙げられている。第二は、`/skill-name` として直接呼び出される反復可能なワークフローで、例として GitHub の課題を分析し修正する番号付きの手順を本文とする `fix-issue` スキルが挙げられている。副作用のあるワークフローについては、意図的にトリガーされたときにのみ走るよう `disable-model-invocation: true` を推奨している。ドキュメントはまた、スキルを [[DefinedTerm/context-files]] と読み込みの基準で対比している。コンテキストファイルは毎セッション読み込まれるため、広く当てはまる素材だけがそこに属する。ときどきしか関係しない知識は、あらゆる会話を膨らませることなく必要に応じて読み込まれるスキルに属する。

スキルは第三者による配布のパッケージ形式でもある。[[SoftwareApplication/context-engineering-kit]] は自らの技術を、agentskills.io の仕様に従うスキルを持つプラグインとして提供しており、その保守者は、必要とされない情報でコンテキストを埋めることを避けるために、一般的な情報スキルよりサブエージェントと組み合わせたコマンド志向のスキルを好むと述べている——同じ必要時読み込みの性質についてのトークン効率の議論である。彼らは、汎用のツールでスキルをインストールしてもサブエージェントは持ち越されないため、両方に依存するプラグインは部分的にしか可搬でないという限界を指摘している。

### ベンダーが最初に導入したときの機構

2025年10月16日に公開された [[TechArticle/equipping-agents-for-the-real-world-with-agent-skills]] が、この機構を導入した発表であり、そこではオープン標準化の段階が別に記されている。同記事の2025年12月18日付の更新は、エージェントスキルがクロスプラットフォームの可搬性のためにオープン標準として公開されたと述べている。掲げられる動機は、モデルが完全な計算環境を操作できるほど有能になるにつれ、ドメイン固有の専門性を与えるには、ユースケースごとに専用のエージェントを作るよりも合成可能で、規模化でき、可搬なものが必要になるということである——同記事のスキル執筆の類比は、新しく入った人のためのオンボーディングガイドである。

同記事はまた、抽象的な形式の背後にある実例も提供している。Claude の文書編集能力を支える PDF スキルが存在するのは、Claude がすでに PDF を理解している一方で、フォームへの記入のようにそれを直接操作することには限界があるからである。その `SKILL.md` はさらに二つの同梱ファイル、`reference.md` と `forms.md` を参照しており、同記事はこの分割を意図的な軽量化の判断として説明している。フォーム記入の指示を外へ出すことで中核は小さく保たれるのであり、これは Claude が実際にフォームを記入するときにのみ `forms.md` を読むという著者の信頼に基づく。同じスキルは、PDF のフォームフィールドを抽出する、あらかじめ書かれた Python スクリプトを同梱しており、Claude はスクリプトも PDF もコンテキストへ読み込むことなくこれを実行できる。

そもそもコードを同梱することについて同記事が述べる論拠は、コンテキストではなくコストと決定性に関わるため、パッケージングの話とは分けておく価値がある。「トークン生成によってリストをソートすることは、単にソートアルゴリズムを走らせることよりはるかに高価である」のであり、多くの応用はコードだけが提供する決定的な信頼性を必要とする。これは、上の普及の研究が実務ではほとんど使われていないと見出したのと同じ性質であり、調査されたスキルの83.3% は追加のリソースをまったく同梱していなかった。

執筆の四つの指針は、形式の規則というより過程として述べられている。評価から始めること——何かを書く前に、代表的なタスクでエージェントを走らせて能力の欠落を同定する。規模のための構造化——手に負えなくなった `SKILL.md` を参照されるファイルへ分割し、共起することのまれな経路を分けてトークンの使用量を減らしつつ、スクリプトが実行されるべきものかリファレンスとして読まれるべきものかを明確にする。Claude の視点から考えること——実際の使用を観察して予期しない軌跡に注意し、スキルがそもそも発火するかを決めるのは `name` と `description` であるためそこに特に注意を払う。そして Claude とともに反復すること——必要なコンテキストを前もって予測しようとするのではなく、作業が進むにつれてうまくいった手法と一般的な誤りをスキルへ書き留めるよう頼む。

セキュリティについて同記事は、上の普及とマーケットプレイスの研究が別の方向から裏づけるのと同じ立場を取っている。スキルは指示とコードの双方を供給するため、悪意あるスキルは脆弱性を持ち込んだり、Claude にデータを持ち出させ意図しない行動を取らせたりしうる。推奨は、信頼できる出所からのみインストールすること、そしてそれより信頼度の低いものについては使用前に監査すること——同梱ファイルを読み、コードの依存関係と同梱リソースに特に注意し、信頼できない可能性のある外部のネットワークの出所へ接続する指示やコードに目を光らせることである。

### 仕様そのものが記述する形式

エージェントスキルの仕様リポジトリは、この形式の目的を「AI エージェントに新しい能力と専門性を与える標準化された方法」と述べ、これを「専門化された知識とワークフローで AI エージェントの能力を拡張するための、軽量でオープンな形式」と呼んでいる。その最小限の定義は上の調査の説明と一致する。スキルとはメタデータ——最低限 `name` と `description`——に加え、特定のタスクをどう遂行するかをエージェントに伝える指示を担う `SKILL.md` ファイルを含むフォルダであり、任意で同梱のスクリプト、参照資料、テンプレートその他のリソースを伴う。

そこで挙げられる動機はコンテキストの欠落である。エージェントはますます有能になっているが、実際の仕事を確実にこなすのに必要な文脈をしばしば欠いている。スキルは、手続き的な知識を、企業・チーム・ユーザーに固有の文脈とともに、エージェントが必要に応じて読み込む可搬でバージョン管理されたフォルダへパッケージすることでこれに応える。そこから生じる三つの性質が挙げられている。ドメインの専門性——法務レビューの手順からデータ分析のパイプライン、プレゼンテーションの整形に至る専門知識が、再利用可能な指示とリソースになる。反復可能なワークフロー——多段階のタスクが一貫した監査可能な手順になる。そして製品を越えた再利用——一度作ったスキルは、スキルに対応した任意のエージェントで使える。

読み込みは三段階の [[DefinedTerm/progressive-disclosure]] によって働く。**発見**の段階では、エージェントは起動時に各利用可能なスキルの name と description だけを読み込む——それが関連しうるかを知るのにちょうど足りるだけである。**活性化**の段階では、タスクがスキルの description と合致したとき、エージェントは完全な `SKILL.md` の指示をコンテキストへ読み込む。**実行**の段階では、エージェントはその指示に従い、必要に応じて同梱のコードを走らせたり参照されるファイルを読み込んだりする。完全な指示はタスクが求めるときにのみ読み込まれるため、仕様はエージェントが小さなコンテキストのフットプリントで多数のスキルを手元に置けると述べている。

ガバナンスについて、仕様リポジトリはこの形式が「もとは [[Organization/anthropic]] によって開発され、オープン標準として公開され、増えつつある数のエージェント製品に採用されてきた」こと、そしてこの標準がより広いエコシステムからの貢献に開かれていることを述べている。リポジトリ内のコードは Apache 2.0、そのドキュメントは CC-BY-4.0 のもとにある。リポジトリはドキュメントと形式の仕様について `agentskills.io` を指し示し、別途 `agentskills.io/clients` の Client Showcase を、この形式に対応する AI ツールとエージェンティックなクライアントの一部を探る手段としてリンクしており、それらは多数にのぼるとしている。

### あるベンダーが文書化する機構

Anthropic の Claude Code のスキル専用のドキュメントは、上の調査より詳しくこの機構を示しており、自らが文書化するものが上位集合であることを明示している。Claude Code のスキルは agentskills.io で公開されているエージェントスキルのオープン標準に従い、ドキュメントはそれが複数の AI ツールにまたがって機能すると説明したうえで、Claude Code がその標準を独自の機能——呼び出しの制御、サブエージェントでのスキルの実行、動的なコンテキストの注入——で拡張しているとしている。その境界は助言ではなく強制である。Claude Code の外では仕様の六つのフロントマターのフィールド（`name`、`description`、`license`、`compatibility`、`metadata`、`allowed-tools`）だけが受け入れられ、他のフィールドを含めるとフィールドが無視されるのではなく、パッケージングやアップロードが強いエラーで失敗する。

同ドキュメントの二つの設計上の点が、この機構がコンテキストファイルとどう異なるかに関わる。第一は上ですでに触れた読み込みの基準であり、そこではコストの議論として述べられている。スキルの本文は使われたときにのみ読み込まれるため、長い参照資料は必要になるまでほとんど何のコストも生じない。第二は読み込まれた後に何が起きるかである。描画された `SKILL.md` は単一のメッセージとして会話へ入り、そのセッションの残りのあいだそこに留まる。それゆえドキュメントの枠づけでは、どの行も繰り返し生じるトークンのコストであり、タスク全体に適用されるべき案内は一度きりの手順ではなく常設の指示として書かれるべきである。自動コンパクションは、呼び出されたスキルを予算の範囲内で持ち越し、要約の後に各スキルの最新の呼び出しを再添付する。各スキルの最初の5,000トークンを、直近に呼び出されたスキルから順に埋める合計25,000トークンの予算の内側に保つため、多くのスキルを呼び出したセッションでは古いスキルが丸ごと落とされうる。

同ドキュメントはスキルの内容を、どうトリガーされることを意図しているかによって二種類に分けている。**リファレンスの内容**——慣習、パターン、スタイルガイド、ドメイン知識——はインラインで走り、モデルが会話と並行してそれを適用できるようにする。**タスクの内容**——デプロイ、コミット、コード生成のための手順——は通常、`/skill-name` として意図的に呼び出されることを想定している。どちらが可能かを二つのフロントマターのフィールドが制御する。`disable-model-invocation: true` はユーザーだけがスキルを呼び出せることを意味し、副作用のあるものすべてに推奨される。コードが準備できたように見えるからといってモデルがデプロイを決めることは望ましくない、という理由による。`user-invocable: false` はモデルだけが呼び出せることを意味し、ユーザーが取る行動としては意味をなさない背景知識のためのものである。

これらに加え、文書化されたフロントマターは引数の扱い（`arguments`、`argument-hint`）、スキルが有効なあいだ適用されるモデルと労力の上書き、スキルが自動的に活性化する条件を限定する `paths` のグロブ、スキルが呼び出されたときに登録する `hooks`（[[DefinedTerm/agent-hooks]] を参照）、そしてスキルをインラインではなく fork されたサブエージェントのコンテキストで走らせる `context: fork` を扱う。この最後のものが、スキルが呼び出し元のエージェントのコンテキストで実行*されない*、文書化された唯一の場合である。`allowed-tools` はスキルを呼び出すターンについてツールを事前承認するものであり、ドキュメントはこれをそれ自体サプライチェーン上の懸念として明示している。ワークスペースの信頼はこのフィールドを制御しないため、リポジトリにコミットされたスキルは自らに広範なツールのアクセスを与えられるのであり、そこでエージェントを走らせる前にリポジトリのスキルの `allowed-tools` を確認することが推奨されている。

スキルのファイルがどこにあるかが誰が使えるかを決め、名前の衝突は近さではなく出所によって解決される。エンタープライズが個人に優先し、個人がプロジェクトに優先し、それらいずれの水準のスキルも同名の組み込みスキルに優先する——ただしその組み込みスキルのエイリアスには優先しない。プラグインのスキルは `plugin-name:skill-name` の名前空間に置かれるため、他の水準のスキルとは衝突しない。スキルはまた作業ディレクトリより下の入れ子の `.claude/skills/` ディレクトリからも読み込まれ、エージェントがそのサブディレクトリのファイルを最初に読むか編集した時点で利用可能になる。これによりモノレポ内のパッケージが、自らにスコープされたスキルを提供できる。

Claude Code はまた**組み込みスキル**の集合も同梱している——ドキュメントは `/doctor`、`/code-review`、`/batch`、`/debug`、`/loop`、`/claude-api` を挙げている——のであり、これらをプロンプトベースのもの、すなわちモデルに詳細な指示を与え、モデル自身のツールで作業をオーケストレートさせるものと説明し、固定のロジックを直接実行する大半の組み込みコマンドと対比している。一部は関連するときに自動的に呼び出され、他は明示的な呼び出しでのみ走る。ドキュメントは後者を、時間とトークンを費やす長めのチェックをいつ行うかの制御をユーザーの手に残すためだと説明している。

### 可搬なエンジニアリングの実践としてのスキル

[[Person/arun-gupta]] の [[PresentationDigitalDocument/spec-driven-development-using-coding-agents]] は、コンテキストではなく再利用を根拠にこの機構を推しており、スキルを可搬なエンジニアリングのパターン——解決策を一度捉えて複数のプロジェクトとエージェントにわたって適用し、プロジェクトごとにプロンプトを作り直す代わりにベストプラクティスをバージョン管理されたスキルとして成文化するもの——と説明している。挙げられるカテゴリはテストのパターン、API 統合、デプロイのスクリプト、コードレビューのガイドライン、Infrastructure as Code であり、Helm チャートを書く一貫した手法を強制する例として Helm のスキルが挙げられている。彼は `agentskills.io` の仕様と、再利用可能なエージェントの能力を発見・共有・貢献するためのスキルのリポジトリを指し示している。

彼が [[DefinedTerm/spec-driven-development]] との間に引くつながりは、両者が互いを強めるというものである。仕様が標準化されたスキルを参照することで仕様自体がより的確で実行可能になり、一方でスキルはプロンプトエンジニアリングのオーバーヘッドを減らす。彼の実例は、実装計画の一つの小節をエンドツーエンドで実装するスキルである——コンテキストの汚染を避けるために明確なコンテキストから始め、計画から要件を読み出し、タスクの追跡を作り、プロジェクトのパターンに沿って実装し、テストを書き、通過が必須の品質チェックを走らせ、ドキュメントを更新し、コミットする——のであり、そのスキルの本文はエラー処理、API エンドポイントの実装、テストの執筆、コミットの形式について他のスキルを名前で参照している。

### MCP の姉妹標準として

[[DefinedTerm/model-context-protocol]] についての Wikipedia の説明は、Anthropic によるエージェントスキルの公開を2025年12月としており、AI エージェントが必要に応じて読み込むタスク固有の指示とリソースをパッケージするための姉妹オープン標準であり、MCP と同じオープン標準の手法に従うと説明している。同じ月に Anthropic は MCP 自体を [[Organization/agentic-ai-foundation]] へ寄贈している。

Anthropic 自身のエンジニアリングの記述は、別の方向からスキルに至っている。[[TechArticle/code-execution-with-mcp]] はこれを、専門化されたタスクでの性能を高めるためにモデルが使う、再利用可能な指示・スクリプト・リソースのフォルダと説明し、ファイルシステムへのアクセスを持つエージェントの自然な行き着く先として扱っている。あるタスクについて動くコードを作り上げたエージェントは、その実装を将来の使用のために保存でき、そうして保存された関数に `SKILL.md` ファイルを加えれば、モデルが参照できる構造化されたスキルになる。その説明では、エージェントは徐々により高水準の能力の道具箱を築き、最も効果的に働くために必要なスキャフォールドを自ら進化させていく——[[DefinedTerm/code-execution-with-mcp]] を参照。

### スキルが自らに宣言する安全の規則

スキルは自然言語の指示を任意の実行可能なスクリプトとともに束ねるため、その安全上の制約はランタイムによって強制されるのではなく散文として書かれる——そして [[ScholarlyArticle/no-attack-required]] は、それらの制約がしばしば保たれないと報告している。OpenClaw のマーケットプレイスの402スキルに対する意味的ファジングは、そのうち120件（29.9%）に [[DefinedTerm/specification-violations]] を見出し、配備済みのスキルにおける未知の悪用可能なガードレール違反26件を含んでいた。そこで記述される失敗に攻撃者は要らない。ごく普通のユーザーの要求が、スキルに自らの仕様が宣言した規則を破らせるのである。

その知見のうち二つは、スキルがどう書かれるかに直接関わる。第一は、明快な散文では十分でないということである。違反した120スキルのうち46件（38%）は、独立した LLM ジャッジによってすべてのガードレールが「よく書けている」と判定されていながら、「重要なドメイン」や「明示的な承認」といった語に実行時の定義がなかったために違反された。第二は実行環境に関わる。スキルの仕様は通常、人間との対話的な使用か CI/CD の自動化のために書かれるが、エージェントの実行は第三のモダリティであり、stdin がないのに人間には到達できる。そのためシェルや `input()` の読み込みに基づく確認プロンプトは黙って失敗し、意図されたゲートを迂回する `--yes` や `--force` のフラグへエージェントを追いやる。同論文のスキル執筆者への推奨は、ガードレールが「確率的に解釈されるものではなく、運用上テスト可能でなければならない」というものである。

### MCP 経由でドキュメントを読み込むことの代替としてのスキル

[[BlogPosting/level-up-your-agents-google-skills-repository]] は、明白な代替案の特定のコストに対してスキルを枠づけている。Google は自社の開発者向けドキュメントのための [[DefinedTerm/model-context-protocol]] サーバーを提供しているが、同記事は MCP の多用が**コンテキストの肥大**——膨大な量のコンテキストがウィンドウへ読み込まれ、モデルを混乱させ、トークンのコストを押し上げること——を招くと論じている。スキルは置き換えではなく補完として提示されている。「エージェントに追加の凝縮された専門性を与える方法」であり、特定の技術やタスクのための、Markdown で書かれ、参照ファイル・コード片その他の資産を担うことができ、必要なときにのみ読み込まれる、コンパクトでエージェントファーストのドキュメントである。

この枠づけは測定された比較ではなく自社のローンチについてのベンダーの議論であり、同記事は肥大についても節約についても数値を挙げていない。具体的に記録されているのは、組織規模のスキルのライブラリの姿である。Google の公式リポジトリは Google Cloud Next 2026 で13のスキルを三つのグループに分けて公開された——AlloyDB、BigQuery、Cloud Run、Cloud SQL、Firebase、Gemini API、Google Kubernetes Engine のためのプロダクトスキル、Security・Reliability・Cost Optimization のための Well-Architected Pillar のスキル、そしてオンボーディング、認証、ネットワークの可観測性のための「レシピ」スキルである——のであり、`npx skills install` の単一のコマンドでエージェント横断にインストールされる。

### スキルの解剖学——ある大規模なパックの作り方

[[SoftwareApplication/addyosmani-agent-skills]] は、24のスキルすべてに適用する一貫した内部構造を文書化している。小文字ハイフンの `name` と「Guides agents through [task]. Use when…」の形式の `description` を担うフロントマターに続き、スキルが何をするかの Overview、トリガーの条件を与える When to Use、段階的なワークフローを与える Process、言い訳とその反論を対にした Rationalizations、何かがおかしいことを示す Red Flags、そして証拠の要件を述べる Verification である。

その形の背後に四つの設計上の選択が述べられている。スキルは**散文ではなく過程**である——エージェントが読む参照文書ではなく、ステップ、チェックポイント、終了基準を持つワークフローである。**反・合理化**が一級のセクションとして扱われる。各スキルは、エージェントが手順を飛ばすのに使う言い訳——例として挙げられるのは「テストは後で追加する」——を、文書化された反論と並べて表にする。**検証は交渉不可能**であり、あらゆるスキルは証拠の要件——テストの通過、ビルドの出力、実行時のデータ——で終わり、「『正しそう』では決して十分でない」という規則を伴う。そして [[DefinedTerm/progressive-disclosure]] が読み込みを統べ、`SKILL.md` を入口とし、補助的な参照はトークンの使用量を最小に保つため必要なときにのみ引き込まれる。

同リポジトリはまた、この形式の可搬性に関わる帰結も文書化している。`npx` で単一のスキルをインストールするとそのスキル自身のディレクトリだけがコピーされるため、リポジトリ水準で共有される `references/` ディレクトリは持ち越されず、補助的なチェックリストへのパスはリポジトリ全体を統合しないかぎり壊れる。

### MCP サーバーと対立するのではなく同梱される

[[SoftwareApplication/google-skills]] は、二つの機構が代替としてではなく一緒に配布される様子を示している。スキルと並んで、同リポジトリは Google の製品**プラグイン**を、スキルに [[DefinedTerm/model-context-protocol]] サーバーを加えたものとして定義して同梱しており、エージェントのハーネス向けにパッケージされ、各ハーネス自身のプラグイン機構——Claude Code と Codex ではマーケットプレイスの追加、Antigravity CLI では直接のプラグインパスのインストール——を通じてインストールされる。これはスキルを MCP 由来のコンテキスト肥大への答えとする枠づけとは異なる構成であり、しかも両者は同じベンダーから出ている。

### 三つの読み込みの水準と、そのコスト

[[BlogPosting/survey-of-development-workflows-in-the-coding-agent-era]] は、この形式のトークンの経済を三つの水準として示している。**L1 メタデータ**——YAML フロントマターの name と description——は起動時に常に読み込まれ、1スキルあたりおよそ100トークンである。**L2 指示**——`SKILL.md` の本文——はスキルが活性化したときに読み込まれ、5,000トークン未満である。**L3 リソース**——スクリプト、参照その他のファイル——は必要に応じてのみ読み込まれ、事実上上限がない。その帰結として述べられるのは、使われないスキルについては98% のトークン削減であり、それゆえ10以上のスキルをインストールしても、コンテキストのコストは活性化したものについてだけ生じる。

同記事の利用に関する案内は同じ計算から導かれる。プロジェクトの慣習とフレームワークの知識は常時読み込まれる [[DefinedTerm/agents-md]] ファイルへ圧縮し、スキルは TDD やコードレビューのような、必要に応じて読み込まれるべき複雑な多段階のワークフローのために取っておくことである。

同記事はまた、スキルの配置がツールごとに異なること——Claude Code は `.claude/skills/`、Codex CLI は `.agents/skills/`、Gemini CLI は `.gemini/skills/` または `.agents/skills/` であり、Gemini CLI は自律的な活性化のための `activate_skill` ツールを公開している——、そして Claude Code 自身のプラグインがスキル、MCP、スラッシュコマンド、エージェントを単一のパッケージへ束ねることも記録している。
