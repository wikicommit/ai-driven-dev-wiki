Agent Skills とは、Anthropic が Claude 向けに文書化した、エージェントの機能を拡張するモジュール式の能力をパッケージ化するためのフォーマットである。Skill のパッケージは、エージェントのベンダー以外の者によっても作成・公開されている。Google のデベロッパーリレーションズチームは、エージェントの Skill が、モデルの固定された学習知識と変化の速いライブラリや SDK とのギャップを埋める、きわめて軽量でありながら効果的になりうる手段として浮上してきたと書き、そのギャップに対してどの SDK メンテナーにも何ができるかを示そうとしている。各 Skill は指示、メタデータ、そしてスクリプトやテンプレートといった任意のリソースをひとまとめにしたもので、モデルは関連する場面でそれを自動的に使う。ベンダーのドキュメントは、範囲と永続性という観点から Skill をプロンプトと区別している。プロンプトは 1 回限りのタスクのための会話単位の指示であるのに対し、Skill はオンデマンドで読み込まれる、再利用可能なファイルシステムベースのリソースであり、同じ指針を会話のたびに繰り返す必要がなくなる。挙げられている利点は、ドメイン固有のタスクに向けてモデルを特化させられること、指針を繰り返すのではなく一度作成すれば済むこと、そして複数の Skill を組み合わせて多段階のタスクに対応できることである。

Anthropic 自身によるこのフォーマットのエンジニアリング解説（[[BlogPosting/equipping-agents-for-the-real-world-with-agent-skills]]）は、これを欠陥ではなく能力への応答として位置づけている。汎用エージェントが完全なコンピューティング環境を操作できるようになると、未解決の問いは、ドメインの専門知識をいかに組み合わせ可能で、スケーラブルで、ポータブルな形でエージェントに備えさせるかになる、というのである。同解説は、Skill を作ることは新入社員向けのオンボーディングガイドをまとめることに似ているというたとえを示し、このフォーマットが置き換える代替策は、ユースケースごとに個別に設計されたエージェントを構築することだと論じている。2025 年 12 月 18 日にこの記事に追記された注記は、その後 Agent Skills がクロスプラットフォームでの可搬性のためのオープン標準として公開されたことを記録している。製品発表（[[BlogPosting/introducing-agent-skills]]）にも同日付の注記があり、それと並んでさらに 2 つの追加、すなわち Skill の組織全体での管理と、パートナーが作成した Skill を掲載するディレクトリを記録している。

Anthropic が Claude 向けに文書化しているとおり、このフォーマットは設計上ファイルシステムベースである。Skill は Claude の仮想マシン環境内のディレクトリとして存在し、Claude は通常のシェルコマンドを使ってそれとやり取りする。`SKILL.md` を読んでその指示をコンテキストに取り込み、指示が参照している場合には追加のファイルを読み、同梱されたスクリプトをシェル経由で実行する。このためコンテキストウィンドウに入るのはスクリプトの出力だけで、そのコードが入ることはない。他のハーネスは別の手段で Skill にアクセスする。たとえば Google の評価では、モデルに `activate_skill` ツールと、ドキュメントをダウンロードするための `fetch_url` ツールが与えられていた。

## 用法

すべての Skill には、`name` と `description` という 2 つの必須フィールドを持つ YAML フロントマター付きの `SKILL.md` ファイルが必要である。ドキュメントはそれぞれの制約を述べている。name は 64 文字以内で、小文字・数字・ハイフンに限られ、XML タグと予約語を含んではならない。description は空でない 1024 文字以内の文字列で、やはり XML タグを含んではならない。description には、その Skill が何をするのかと、いつ使うべきかの両方を書かなければならない。モデルが Skill を起動するかどうかを判断する際にリクエストと照合するのが description だからである。

内容は 3 つの段階に整理され、それぞれ異なるタイミングで読み込まれる。ドキュメントが [[DefinedTerm/progressive-disclosure]] と呼ぶ仕組みである。メタデータは常に読み込まれ、そのコストは Skill あたりおよそ 100 トークンとされる。`SKILL.md` の本文は Skill が起動されたときに読み込まれ、その予算は 5,000 トークン未満とされる。同梱されたリソースは読まれるまでコストがかからない。文書化されている帰結は、多数の Skill をコンテキスト上の不利益なしにインストールできること、そして Skill が包括的な API ドキュメントや大規模なデータセットといった大量の素材を同梱しても、使われない限りコンテキストに計上されないことである。

ベンダーのエンジニアリング記事は、この仕組みを具体的な事例、すなわち Claude の文書編集機能を支える PDF の Skill を通して説明している。その `SKILL.md` は同梱された 2 つの追加ファイル `reference.md` と `forms.md` を参照しており、フォーム入力の指示を `forms.md` に移した理由として記事が挙げるのは、Skill の中核を簡潔に保つことである。モデルがそのファイルを読むのは実際にフォームを入力するときだけだと想定されている。同じ Skill には、PDF を読んでそのフォームフィールドを抽出する Python スクリプトが同梱されており、モデルはスクリプトも PDF もコンテキストに入れることなくそれを実行できる。記事はこの仕組みを 2 つの根拠で正当化している。すでにコードが行っている操作をトークンの生成によって行うのははるかに高コストであること、そして多くの用途ではコードだけが提供できる決定性が必要であることである。

作成方法について、同記事は評価から始めることを推奨している。代表的なタスクでエージェントを動かしてつまずく箇所を見つけ、必要になりそうなものを予測するのではなく、観察されたギャップに対して Skill を段階的に構築していくというものである。`SKILL.md` が扱いにくくなったら別々の参照ファイルに分割するよう助言し、コンテキストが互いに排他的であるか一緒に使われることがまれな場合には、それらの経路を分けておくことでトークン使用量が減ると付け加えている。また、同梱されたコードは実行可能なツールとドキュメントの両方の役割を果たすため、あるスクリプトがそのどちらなのかを Skill 内で明確にすべきだと指摘している。とくに注意を払うべきものとして `name` と `description` を挙げており、その理由は、モデルがそもそも Skill を起動するかどうかを判断する際に使うのがこれらだからである。最後の提案は、作業を進めながら、成功したアプローチや繰り返される誤りをモデル自身に Skill として記録させ、軌道を外れたときには自己反省を求めることである。

利用可能性はベンダーの製品によって異なる。API では、Skill にはコード実行ツールが必要で、コンテナパラメータ内の `skill_id` で選択される。PowerPoint、Excel、Word、PDF 用の組み込みの文書 Skill があり、カスタム Skill は Skills API を通じてアップロードされ、ワークスペース全体で共有される。[[SoftwareApplication/claude-code]] では、カスタム Skill はファイルシステムベースでアップロードは不要であり、個人またはプロジェクトのディレクトリに配置される。一方、組み込みの文書 Skill はそこでは利用できない。claude.ai では両方の種類が動作し、カスタム Skill は zip ファイルとしてアップロードされ、一元管理されるのではなく各ユーザー個別のものとなる。ドキュメントは、それらが組織全体で共有されず、管理者が一元管理することもできないこと、そして claude.ai はカスタム Skill の一元的な管理者による管理や組織全体への配布をサポートしていないことを述べている。これは、Skill の組織全体での管理が追加されたと記録する製品発表の 2025 年 12 月の注記と整合が取れないままになっている。2 つの情報源は異なることを述べており、どちらも自らを他方に対して日付づけていない。エンジニアリング記事は、公開時点でこのフォーマットが Claude.ai、Claude Code、[[SoftwareApplication/claude-agent-sdk]]、Claude Developer Platform でサポートされていたと述べている。

製品発表は、それぞれの利用面へのアクセス方法を補っている。Claude のアプリでは、このフォーマットは Pro、Max、Team、Enterprise のユーザーが利用できるとされ、Team と Enterprise では管理者がまず組織全体で有効にする必要がある。起動は手動で選択するのではなく自動で行われ、発表によれば、Skill は Claude が作業する際の思考の連鎖の中に現れる。Developer Platform では、Skill を Messages API のリクエストに追加でき、`/v1/skills` エンドポイントによってカスタム Skill のバージョン管理と運用をプログラムから制御できる。また Skill には Code Execution Tool のベータが必要とされ、これは Skill の実行に必要な安全な環境を提供するものと説明されている。Claude Code では、`anthropics/skills` マーケットプレイスからプラグイン経由で、あるいは `~/.claude/skills` に手動で配置することでインストールされ、バージョン管理を通じてチームで共有される。

ある実践者の記述は、同じ構造上の助言に反対側から到達しており、ここではそれを検証したと報告している唯一の情報源である。[[BlogPosting/mercari-pm-agent-design]] は、プロダクトマネージャーのワークフローを端から端まで担う Skill の構築について述べている。まずすべての定義を 1 つの `SKILL.md` にまとめたところ、別の評価用 Skill による採点を通じて、ファイルが長くなるほど出力の精度が悪化することがわかったと報告している。著者の対応は、何をどの順序で行うかという振る舞いの定義を、`references/` ディレクトリに置いた参照データやテンプレートから分離することであり、この構造の変更だけでスコアが明確に改善したと報告している。記事はこれを、ソフトウェアエンジニアリングにおける関心の分離をプロンプト設計に適用したものと位置づけ、根底にある問題を、モデルが長いコンテキストの中ほどにある情報にうまく注意を向けられない、一般に「Lost in the Middle」と呼ばれる現象と結びつけている。また、英語の指示のほうが Claude では精度が高くなる傾向があるという理由で、`SKILL.md` を英語で書いていることにも触れている。この記述が上記のベンダーの助言に加えるのは、別のルールではなく、それに従う理由である。ベンダーはファイルが扱いにくくなったら分割するよう推奨しているのに対し、この著者はそうしないことのコストを測定したと報告している。

同記事のその他の設計上の主張は、Skill の指示をどう整理するかではなく、指示が何を禁じるべきかに関わるものである。記事の立場は、LLM を業務ワークフローに組み込む際の最も危険なリスクは、もっともらしいが根拠のない出力、つまりデータが存在しないところでモデルがそれらしい数値を生み出すことであり、これはモデルに嘘をつかないよう指示するだけでは解決できない、というものである。Skill は、データが欠けていると認識したときにどう振る舞うかを規定しなければならない。記事が用いているルールは、確認されていないデータには「Not provided」または「To be validated」のラベルを付けること、数値や情報源を決して捏造しないことであり、それに加えて、エージェントが完了を推測することを禁じる指示を置き、ユーザーによる明示的な確認があった場合にのみ次のステップへ進めるようにしている。著者のまとめは、Skill を設計することは振る舞いの仕様を書くことに近く、モデルがしてはならないことを明確に定義するほうが、命令よりも直接的に精度を向上させるというものである。

2 つ目の実践者の記述は、個々の作成者によるものではなく、組織の共有インフラとして使われるこのフォーマットを描いている。[[BlogPosting/agentic-engineering-at-zalando-a-snapshot]] は、[[Organization/zalando]] における一元的な Skill コレクションについて報告している。それはプラグインにまとめられ、分野横断的な共通のタスクや関心事を扱っており（記事はデータ、エンジニアリング、フロントエンド、SRE を挙げている）、プログラミング言語もまたいでいる。記事によれば、マルチアーキテクチャビルドのような新しいプラットフォームツールやインフラのプラクティスを導入する際にチームを導く移行用の Skill が、広く人気のある種類である。配布は管理された構成設定か、必要なシンボリックリンクをインストールする CLI コマンドによって行われ、記事はその理由を、一部のエージェントがプラグインマーケットプレイスをサポートしていないことに帰している。

この記述が配布の仕組み以上に加えているのは、幅広い貢献を促したことによると記事が考える二次的な効果である。このコレクションは、CI/CD パイプラインでプラグインの構文を検証することや、Skill とスクリプトの境界をどこに引くべきかといった問題（記事の例は OAuth トークンの生成をどこに置くかである）について、組織全体でベストプラクティスを発見し広める手段になったという。独自の Skill を書くチームは、このコレクションを参考やヒントとして使っているとされる。これらは 1 つの組織のプラクティスについての著者自身の観察であり、評価は報告されていない。

作成作業そのものも、専用の Skill によって支援されている。発表は `skill-creator` という Skill について述べており、これはワークフローについて質問し、フォルダ構造を生成し、`SKILL.md` ファイルを整形し、リソースを同梱するという対話的な指針を与えるもので、ファイルを手作業で編集する必要はない。これはフォーマットを自分自身に適用したものであり、Skill を書くための手続き的な知識が Skill としてパッケージ化されているのである。

3 つ目の実践者の記述は、ここでこのフォーマットが登場する最も小さな規模、つまりチームや組織ではなく 1 人の開発者の事例である。[[BlogPosting/lessons-from-releasing-a-product-with-ai-agents]] は、繰り返し使うプロンプトを打ち直すのが面倒になった時点でそれを Skill としてテンプレート化したと報告しており、その例は、コミットされていない変更を分析してテストを書くよう求める定型の依頼である。そして、そうした Skill とは単なるプロンプトではなく、エンジニアのノウハウをコーディング規約に移植したものだと述べている。2 つ目の使い方は、他人が書いた Skill の利用である。バックエンド開発者である著者は、サードパーティ製の SEO 用 Skill を自分のサイトに対して実行して改善点のリストを作成し、そのリストをエージェントに戻してソースに適用させるというループを、およそ週に 1 回繰り返した。そこから引き出されている観察は、このフォーマットは自分の専門外の領域で最も役に立つというものである。これは、Google の記述が変化の速い SDK について述べている知識ギャップの議論と同じものに、モデルの学習データのカットオフではなく開発者自身の専門性という方向から到達したものである。この記述は評価を報告しておらず、エージェントとして Claude Code を挙げている以外に、どのハーネスの機能群について述べているのかも明らかにしていない。

このフォーマットは Anthropic の製品に限られない。ChatGPT と [[SoftwareApplication/openai-codex]] で Skill を構築するための OpenAI のドキュメントは、同社の Skill がオープンなエージェント Skill 標準に基づいていると述べ、同じ形を説明している。すなわち、`name` と `description` を含まなければならない `SKILL.md` ファイルを持つディレクトリに、任意の `scripts/`、`references/`、`assets/` ディレクトリと、UI メタデータ、起動ポリシー、ツール依存関係のための任意の `agents/openai.yaml` ファイルを加えたものである。段階的開示についても説明しており、ChatGPT と Codex は各 Skill の名前と説明から始め、その Skill を使うと判断したときにのみ `SKILL.md` 全体を読み込む。さらに Codex 固有の上限を加えている。Codex では各 Skill のファイルパスも含む最初の Skill 一覧は、モデルのコンテキストウィンドウの最大 2%、ウィンドウの大きさが不明な場合は 8,000 文字までしか使わず、多数の Skill がインストールされている場合、Codex はまず説明を短縮し、一部の Skill を省略することもある。起動は、プロンプトで Skill の名前を挙げる明示的なものか、タスクが Skill の `description` に合致したときの暗黙的なもののいずれかであり、`agents/openai.yaml` で `allow_implicit_invocation: false` を設定すると、明示的な起動は機能させたまま暗黙的な起動を無効にできる。Codex は、リポジトリ内の場所（作業ディレクトリからリポジトリのルートまでの各ディレクトリにある `.agents/skills`）、ユーザー用の場所、管理者用の場所、そして Codex に同梱されたセットから Skill を読み込む。ドキュメントはこれらの場所を作成とローカルでの発見のためのものとして扱い、Skill を他者に配布するには、複数の Skill を MCP サーバー接続とともに同梱できるプラグインを使うよう示している（[[DefinedTerm/agent-plugins]] を参照）。そのベストプラクティスの一覧は、各 Skill を 1 つの仕事に絞ること、決定的な振る舞いや外部ツールが必要でない限りスクリプトより指示を優先すること、明示的な入力と出力を伴う命令形の手順を書くこと、そして Skill の description に対してプロンプトを試し、正しく起動されることを確認することである。

## 研究における位置づけ

学術文献は、この用語をどの 1 つの製品のファイルフォーマットよりも広い意味で用いている。[[ScholarlyArticle/comprehensive-survey-on-agent-skills]] は、エージェントの Skill を、タスク固有の制約のもとでツール、メモリ、実行時のコンテキストを協調させる再利用可能な手続き的成果物と定義し、Skill を 3 つの部分から成る組として形式化している。すなわち、エージェントが読み込んで従うことのできるルートの指示文書、参照文書・テンプレート・実行可能なスクリプトといった補助リソースの集合、そして Skill をいつ取得・適用すべきかを定める適用条件であり、最後のものはメタデータ、自然言語による説明、あるいは埋め込みとして表現される。このサーベイは、この組がすべてのシステムで完全に具体化されている必要はないと述べている。上で述べたフォーマットに照らして読むと、`SKILL.md` の本文は指示文書に、同梱ファイルはリソースに、フロントマターの `description` は適用条件に対応する。サーベイ自身は、その手法が進化させる成果物の中に `SKILL.md` ファイルや Skill のフォルダを挙げているが、概念をそれらに結びつけてはいない。

サーベイの説明では、Skill が必要とされる理由は、それが [[DefinedTerm/procedural-gap]] と呼ぶものにある。ツールにアクセスできても、ある能力をいつ呼び出すべきか、ツールをどう協調させるべきか、失敗をどう扱うべきか、出力をどう検証すべきかはわからない。サーベイはエージェントを高レベルのプランナー、Skill をその下の運用層と位置づけ、Skill を生のツールや MCP サーバーと区別する。その根拠は、ツールが操作を公開するだけなのに対し、Skill はトリガー、手順、フォールバック、落とし穴といった状況に即したノウハウを符号化しているという点にある。また、レビュー用チェックリストのように、まったくツール中心ではない Skill も認めている。これらは主にモデル自身の知識に依拠するが、それでもその場しのぎのプロンプトを超える構造を与える。

ベンダーのドキュメントが Skill の書き方と読み込まれ方を説明しているのに対し、サーベイは研究をライフサイクルに沿って整理している。Skill がどう表現されるか（リソースの中身に応じてテキストベース、コードベース、またはハイブリッド）、どう獲得されるか（人間の専門家から、エージェント自身の過去の実行から、現在のタスクのためにオンデマンドで、あるいは外部のコーパスから）、大規模なプールからどう取得・選択されるか、そして存在した後にどう進化するか（改訂され、検証され、共有リポジトリを通じて伝播し、実行時に統制される）である。サーベイが指摘する問題は、作成の問題ではなくライフサイクルの問題である。有用な手続きがうまく振り分けられないままになる弱いトリガー条件、Skill の主文書と添付スクリプトの間のずれ、ライブラリが整理できるよりも速く低品質な Skill が蓄積すること、そして Skill を追加することには長けていても、それを安全に書き換えたり廃止したりすることがはるかに苦手なシステムである。

## 適用される場面

このフォーマットが当てはまるのは、ワークフロー、コンテキスト、ベストプラクティスといった、さもなければ会話のたびに言い直すことになるドメインの専門知識をエージェントが必要とする場面である。Anthropic が文書化している仕組みでは、モデルにファイルシステムへのアクセスとコマンドの実行能力を与える実行環境が前提とされている。

ドキュメントは、このフォーマットが伴うセキュリティ上の前提について率直である。Skill は指示とコードを通じてモデルに新しい能力を与えるため、信頼できる情報源からのものだけを使うべきであり、悪意のある Skill は、表明された目的に合わない形でツールを呼び出したりコードを実行したりするようモデルを誘導しうる。ドキュメントは、同梱されたすべてのファイルを監査するよう助言し、取得されたコンテンツ自体が悪意のある指示を含んでいる可能性があることから、外部 URL からデータを取得する Skill をとくに危険なものとして挙げ、インストールをソフトウェアのインストールと同様に扱うよう推奨している。Enterprise の組織には、claude.ai と Claude Cowork を通じてアップロードされたカスタム Skill のコンテンツスキャンが提供されている。ドキュメントは、これが Skills API や Console を通じてアップロードされた Skill を対象としないことを注記している。エンジニアリング記事も独自の表現で同じ助言をしており、悪意のある Skill は、それが使われる環境に脆弱性を持ち込んだり、データを流出させたり、モデルを意図しない行動へ導いたりしうると警告し、信頼度の低い情報源からの Skill は、使用前に通読し、そのコードの依存関係、画像やスクリプトといった同梱リソース、信頼できない外部のネットワーク上の情報源に接続する指示に注意を払うよう求めている。どちらの記述も、フォーマット自体が提供する仕組みではなく、手作業による監査を提案している。

## 証拠と限界

Google は、Gemini API 向けの Skill（[[SoftwareApplication/gemini-api-developer-skill]]）を構築し、117 件のコード生成プロンプトから成るハーネスで評価したと報告している。その結果、強力な推論をサポートする新しいモデルでは成績が顕著に向上したが、古いモデルではそれほど向上しなかった。Google はこの結果を、Skill は機能するが、それは Skill 単独ではなくモデルの推論能力に依存していると読んでいる。手法と数値は [[BlogPosting/closing-the-knowledge-gap-with-agent-skills]] に記載されている。

上記のメルカリの記述は、Skill が何を加えるかではなく、Skill 自体の*構造*についての評価を報告している、ここで唯一の情報源である。その手法には注意書きが必要である。スコアは、同じ著者が書いた評価用 Skill によるもので、同じ著者が実際の改善テーマから集めたデータセットに対して、同じ著者が実装前に定義した基準（理解の正確さ、仕様の具体性、実現可能性、UX の妥当性）に照らして算出されている。記事は数値を示しておらず、改善を定量化するのではなく明確だったと述べるにとどまり、短いファイルのほうが良いスコアになった理由については、その変数を切り離した実験ではなく著者自身の推論を報告している。基準を先に定義すること自体が 1 つの手法として示されており、記事はそれを Prompt TDD と呼んでいる。

Anthropic 自身のエンジニアリング記事は、このフォーマットの評価や測定を報告していない。Skill に同梱できるコンテキストは事実上無制限だという主張は、ファイルシステムを備えたエージェントが読む必要のないものについてのアーキテクチャ上の議論であって測定結果ではなく、フォーマットの利点についての説明も設計者自身によるものである。

Google の著者たちは 2 つの限界を挙げている。1 つ目として、彼らは Vercel の取り組みから、[[DefinedTerm/agents-md]] による直接的な指示のほうが Skill を使うよりも効果的でありうることを知っていると述べ、そのためドキュメント用の MCP サーバーなど、最新の SDK の知識を提供する他の方法も探っているとしている。Vercel の評価そのものはこのウィキの情報源に含まれていないため、ここに記録しているのは Google の著者たちがそこから得たと述べている内容である。2 つ目は保守である。Google は、ユーザーに手動での更新を求める以外に Skill の良い更新手段がないと述べ、これが長期的にはユーザーのワークスペースに古い Skill の情報を残し、益よりも害をもたらしかねないと警告している。この懸念は、ここでこのフォーマットが用いられている目的そのものに反するものである。エージェントを最新の状態に保つために採用された仕組みが、それ自体その場で古くなりうるからである。

Anthropic は、出荷済みの挙動ではなく意図として 2 つの方向性を述べている。外部ツールを伴うワークフローをエージェントに教えることで Skill が [[DefinedTerm/model-context-protocol]] サーバーをどう補完できるかを探ること、そして、エージェントが自ら Skill を作成・編集・評価できるようにすることである。
