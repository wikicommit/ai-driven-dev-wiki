バイブコーディングとは、生成されるコードを気にかけずに AI でコードを生成することである。[[Person/andrej-karpathy]] は 2025年2月6日にこの語を造り、「完全にバイブに身を委ね、指数関数を受け入れ、コードが存在することさえ忘れる」「新しい種類のコーディング」だと説明した——差分を読まずにすべての提案を受け入れ、エラーメッセージをコメントなしで貼り戻し、コードが自分の理解を超えて育つに任せ、モデルが直せないバグは消えるまでランダムな変更を頼んで回避する。Karpathy はそれが可能になった理由を LLM が「良くなりすぎた」ことに帰し、本番のソフトウェアを作る手法としてではなく「使い捨ての週末プロジェクトにはそう悪くない」ものとして枠づけた。

## 用法

[[Person/simon-willison]] は、造語から6週間後、すでにこの語が『ニューヨーク・タイムズ』『Ars Technica』『ガーディアン』に取り上げられていた時点である 2025年3月19日の [[BlogPosting/not-all-ai-assisted-programming-is-vibe-coding]] で、狭い読みを最初に示した。そこでの彼の定義は「LLM が書いたコードをレビューせずにソフトウェアを作ること」であり、彼が引く線はツールではなくコードへの関与についてのものである。LLM がコードを書いたとしても、それをレビューし、十分にテストし、どう動くのかを他人に説明できるのなら、「それはバイブコーディングではなくソフトウェア開発であり」、LLM を使ったかどうかは本質的な問題ではない。彼は本番品質の作業についての黄金律として、他人に正確に説明できないコードは自分のリポジトリにコミットしないと述べている。同じ記事はこの実践をそれ自体の条件において擁護してもいる。コンピュータサイエンスの学位もブートキャンプの経験もない人にとって「最初の障壁をほとんど平らに削る」アクセスの物語として、そして経験ある開発者が LLM に何ができて何ができないのかの直観を養うための、現在利用可能な最良の方法として——彼はこの主張を、こうして作った80を超える自身の実験によって裏づけている。

Karpathy はその4日後にこの記事へ返信し、自らの造語に留保を加えた。「定義が落ち着くには時間がかかるだろう」と書き、自分自身は「何をしているのか全く分からない」という GIF の犬のような気分のときに「バイブコーディング」という語を使う——前夜に作った iOS アプリを挙げている——としつつ、「実際にはフルのバイブコーディングをすることはめったにない。たいていは今もコードを見ているし、複雑さは少しずつ加えるし、部品がどう動くのかを時間をかけて学ぼうとするし、確認の質問もする」と述べた。この返信を記録した Willison は、同じ日に Bluesky で「この件では負け戦をしている」と感じており、「明確で広く受け入れられた定義を持つ AI 関連の用語が一つ」得られる機会が失われたと書いていた。

[[Person/simon-willison]] は [[BlogPosting/not-vibe-coding]] で、この語が AI 支援プログラミング全般に当てられつつあり、その読みは誤りだと論じ、区別はどのツールを使うかではなく、開発者が生成されたコードにそもそも関与するかどうかにあるとしている。彼の説明では、責任を持って本番のコードを作る過程の一部として LLM のツールを使うことはバイブコーディングではない。彼は近刊の二冊、[[Book/vibe-coding]] と [[Book/vibe-coding-the-future-of-programming]] を、この語が明示的に対象としていなかったプロフェッショナルなワークフローを説明しながらこの語を採用している書名として挙げている。

Willison はまた、この語がツールではなく受け手を指しているとも論じている。ソフトウェア開発者ではなく、開発者になりたいとも思っていないが、いまや自分のためのカスタムソフトウェアを作る道を得た人々である。その受け手にとって開かれている問いを、彼はどのような種類のプロジェクトがこの方法で作れるのか、そしてセキュリティ、プライバシー、信頼性、使いすぎのリスクをどう扱うのか、として枠づけている。

Bamil の論文は、より広く緩い用法が辞書にも記録されたことを報告している。2025年3月までに Merriam-Webster のオンライン辞書は「vibe coding」を「AI の支援を得て、いくらか無造作にコンピュータのコードを書くこと」を意味する俗語として掲載していた。Merriam-Webster 自身の項目はこれを、AI のプログラムに欲しいものを伝えて成果物を作らせることでコードを書き、ウェブページを作り、アプリを作ることと定義し、コーダーはコードがどう、なぜ動くのかを理解する必要がなく、しばしば一定数のバグや不具合を受け入れねばならないと指摘している。この語はまた『コリンズ英語辞典』の2025年の Word of the Year にも選ばれた。

初期の一次証言は職業の外から来た。2025年2月、プロのコーダーではない『ニューヨーク・タイムズ』の記者 Kevin Roose がバイブコーディングを試して小規模なアプリケーションをいくつか作り、それらがどれほど個人向けに作り込めるかから「一人のためのソフトウェア」と呼んだ——同時に、結果はしばしば限定的で誤りが出やすく、ある事例では EC サイトのために偽のレビューを捏造したとも述べている。認知科学者の Gary Marcus は、Roose の LunchBox Buddy アプリの背後にあるアルゴリズムはおそらく同種のタスクの既存のコードで訓練されており、Roose の熱狂は独創性ではなく再生産に由来すると応じた。この名称自体を受け入れない者もいた。2025年6月、Andrew Ng はこれに異を唱え、ソフトウェアエンジニアが AI ツールでアプリケーションを作るとき単に「バイブに任せている」のだと人々に思い込ませる、と述べた。

この語の最初の1年で報告された普及は急速だった。2025年3月、Y Combinator は2025年冬バッチのスタートアップの25% がコードベースの95% を AI 生成にしていたと報告した。2025年7月には『ウォール・ストリート・ジャーナル』が、商用のユースケースでプロのソフトウェアエンジニアにバイブコーディングが採用されていると報じた。2026年1月には、Linus Torvalds が [[SoftwareApplication/google-antigravity]] を使って自身の AudioNoise オーディオエフェクト生成器のための可視化ツールをバイブコーディングしたことが報じられ、プロジェクトの README で「Python の可視化ツールは基本的にバイブコーディングで書かれた」と説明している。

[[Book/spec-driven-development-ai-native-software-engineering]] はこの語を、ツールと実践のあいだのギャップに対する業界自身の自認として扱っている。[[Person/kevin-ryan]] は、ツールが実践を飛び越してしまった——「我々はプロンプトを打ち、反復し、だいたい機能する何かを得て、次へ進む」——と書き、「業界はそれを『バイブコーディング』と呼びはじめた。半分は冗談で、半分は行き当たりばったりでやっているという自認である」と述べている。

### 誰に、何に向くか

実務者の証言は適切な用途の狭い帯へ収束している。[[NewsArticle/engineers-are-using-ai-to-code-based-on-vibes]] は、専門家でない2人が実用的な社内ツールを世に出したことを報じている——C で書かれた iPad アプリを約2時間で JavaScript のウェブアプリへ変換した機械エンジニア（元の開発にはほぼ1か月かかっていた）と、職務では使ったことのないクラウドサービスで概念実証を作ったデータエンジニアリングのリード——のと並んで、25年のキャリアを持つソフトウェアエンジニアが、そのどちらも本当のバイブコーディングではなかったと論じ、定義を字義どおりに取ると「AI に何をしてほしいかを指定することが、自分でやるより難しい問題になっている」と見出したことも報じている。3人はある一点で一致している。この実践は、エンジニアがまだ知らない言語やスタックのスキルを得るのに役立つということであり、若手エンジニアへの助言は、すでに持っているスキルの高速化としてではなく、新しいスキルを獲得するための加速装置として扱うことである。

Qiita の日本語の解説記事は、反対の方向から似た形に至っており、想定される読者を、何かが壊れたときに立て直せるだけの十分なコーディングの素養がすでにある人か、あるいは自分では実装できないビジョンを持つ完全な初心者のいずれかとして説明している。適する事例として小規模なプロジェクト、個人用ないし業務自動化のツール、そしてゼロからの構築を挙げ、実際のループを、指示し、実行し、コードを読まずにエラーを貼り戻すこととして特徴づけている。ツールの分類では、要件を議論するための汎用アシスタントとチャットボット、ファイルを見ながら最終調整するエディタ統合のエージェント、環境構築とファイルの一括生成のための CLI ベースのエージェント、そして指示を口述するための音声入力を区別しており、成果は基盤となるモデルの能力に大きく依存すると指摘している。また段階的な実務の流れ——要件定義、技術選定、コードベースの作成、そして微調整——も示しており、そのもとで人間の役割はエージェントが提案するコマンドを承認することが大半になり、こまめな Git のコミットが安全網となる。この流れは仕様優先の実践に十分近く、この語の厳密な定義とは座りが悪い。

### 条件と安全策

Willison の2025年3月の記事は、バイブコーディングが適切な場合の条件を示している。プロジェクトを低リスクに保つこと——バグのある、あるいは安全でないコードがどれだけの害をなしうるかを量り、他人が使うのであれば特に注意する。セキュリティを慎重に扱うこと——オンラインのツールへアクセスするための API キーのような秘密情報と、マシンの外へ出うる私的なデータの双方に目を配る。良いネットワーク市民であること——他のプラットフォームへ要求を出すものはすべて、それらのサービスの負荷、ひいてはコストを増やす。そして従量課金の API に用心すること——請求上限のない API に対してバイブコーディングされた機能が数千ドルの請求を積み上げた恐ろしい話を引いている。彼は、バイブコーディングしたソフトウェアを他人と共有しようとしている初心者に、まずより経験のある人に見てもらうことを推奨している。

彼はバイブコーディングを安全にすることを、サンドボックスを出発点とする未解決の設計問題として扱っている。承認されたライブラリのみ、他サイトへのネットワーク要求なしという [[SoftwareApplication/claude-artifacts]] の閉じ込められた `<iframe>` を、害をなすことを非常に難しくすると同時にそうしたプロジェクトにできることも大きく制限するものとして称賛し、当初はプロの開発者向けに意図され安全策がはるかに少ないと彼が説明する [[SoftwareApplication/cursor]] と対比している。彼はこの領域のツールに「カンブリア爆発」を期待していると述べている。

### 批判

> **出典についての但し書き。** この節の大部分は Wikipedia のバイブコーディングの記事に由来する。同記事の「Criticism」節には2026年8月付の管理用バナーが付されており、それが「記事の中立性を損ないうる」と警告して、編集者に否定的な情報を他の節へ統合するか、些細な批判や論争への不当な焦点を除くよう求めている。以下の個々の報告は同記事の帰属に従って帰属させているが、主題の他の部分に対するその比重は、このバナーを念頭に読まれるべきである。

最も多く引かれる懸念はコードの品質とセキュリティである。論者たちは、AI が生成したコードを理解しないままコミットする開発者は検出されないバグと脆弱性を後に残すこと、そしてこの手法はプロトタイピングや Karpathy が当初思い描いた「使い捨ての週末プロジェクト」には適しうるものの、デバッグ・保守・セキュリティのために深い理解が必要な職業的な現場ではリスクをもたらすことを指摘している。報告された事案と研究には次のものがある。2025年5月、バイブコーディングのアプリである Lovable で作られた1,645のウェブアプリケーションのうち170件に、誰でも個人情報にアクセスできてしまう問題があったという報告。2025年10月の Veracode の研究で、3年のあいだに LLM は機能するコードを生成する能力が劇的に向上した一方、生成されたコードのセキュリティは概して改善しておらず、より大きなモデルが小さなものより優れているわけでもなかったという知見。2025年12月の CodeRabbit による470件のオープンソースの GitHub プルリクエストの分析で、AI が共著したコードには人間が書いたコードのおよそ1.7倍の「重大」な問題が含まれ、設定ミスは75% 多く、セキュリティ脆弱性は2.74倍高かったという知見。そして2025年7月、変更を加えないよう明示的に指示していたにもかかわらず Replit の AI エージェントがデータベースを削除したという SaaStr の創業者の証言である。

さらに二つの事案が記録されている。2025年12月、コンピュータセキュリティ研究者の Etizaz Mohsin がバイブコーディングのプラットフォーム Orchids にセキュリティ上の欠陥を発見し、2026年2月に BBC News の記者にそれを実演した。そして2026年5月20日に rsync が 3.4.3 へ更新された際、増分ファイルバックアップができなくなった複数のユーザーが、rsync 3.4.1 以降の数十のコミットが「tridge and claude」によってなされており、コーディングの過程で Anthropic の Claude が使われていたことを見出した。*Please Do Not Vibe Fuck Up This Software* と題された GitHub の課題が他のサイトへ広まり、重要なオープンソースのインフラに AI 生成のコードが受け入れられることをめぐる論争を引き起こした。Tridge は *rsync and outrage* と題したブログ記事で応じ、テストスイートと「多層防御の堅牢化技法」をコードに追加するために AI を使ったと述べ、一部のユーザーが乗り換えようとしていた代替である OpenBSD の openrsync はその AI 支援のテストスイートに通らないと付け加えた。OSNews の編集者 Thom Holwerda はこの最後の発言を「子どもじみて不必要であり、自信のなさが匂う」と批判した。

[[Person/arun-gupta]] は [[PresentationDigitalDocument/spec-driven-development-using-coding-agents]] で同じ不満の構造的な版を述べ、バイブコーディングをワンショットの「プロンプトを打って祈る」手法と特徴づけている。構造なし、計画なし、幻覚されたファイルの多発、コードベースの誤解、企業標準への無知であり、拡張が難しく、元の心的モデルが失われれば安全に変更することがほぼ不可能で、レビューもより難しいコードを生む。彼の処方箋はより良いプロンプトではなく、意図が先、コードが後の手法である——[[DefinedTerm/spec-driven-development]] を参照。

保守性については、2025年初頭の GitClear による2020年から2024年までの2億1,100万行のコード変更の縦断分析が、リファクタリングが2021年の変更行の25% から2024年には10% 未満へ落ちたこと、コードの重複がおよそ4倍に増えたこと、コピー&ペーストされたコードが20年で初めて移動されたコードを上回ったこと、そしてコードのチャーンがほぼ倍増したことを見出した。生産性については、2025年7月の METR のランダム化比較試験で、16人の経験あるオープンソース開発者が成熟したリポジトリで246のタスクを完了したところ、2025年初頭の AI ツールの使用を許すと完了時間が19% 増加した——参加者は事前に AI が24% 短縮すると予測していた——ことが見出された。

2025年9月、『Fast Company』は「バイブコーディングの二日酔い」が来ていると報じ、シニアのソフトウェアエンジニアたちが AI 生成コードを扱う際の「開発地獄」を挙げていると伝えた。デバッグが繰り返し理由に挙がる。LLM はコードを動的に生成し、その構造は一定しないうえ、開発者はそのコードを自分で書いていないため、その構文や概念を理解するのに苦労しうる。2026年5月、『ウォール・ストリート・ジャーナル』は、OpenClaw の AI エージェントシステム内の Pi コーディングハーネスを手がけたエンジニアである Mario Zechner と Armin Ronacher からの批判を報じ、迫りくる「バイブスロップ」の危機への警告を伝えた。企業は目先の生産性を、より長期のバグだらけのソフトウェア、サービス障害、セキュリティ脆弱性、技術的負債と引き換えにしている、という議論である。Zechner の発言が引かれている。「インフラは崩れつつあり、ソフトウェアは以前と比べて非常に、非常にバグだらけになっている。このゲームはあと数か月、あるいは数年は続けられるかもしれないが、いずれ我々に追いついてくる」。

さらに二つの筋は、個々のコードベースではなくエコシステムに関わる。2026年1月の「Vibe Coding Kills Open Source」と題された論文は、バイブコーディングが既存のコードを使い、その上に構築するコストを下げることで生産性を高める一方、多くのメンテナが見返りを得る経路であるユーザーの関与を弱め、生産性が高まるにもかかわらずオープンソースソフトウェアの可用性と品質を下げると論じている。同論文への論評は、モデルが訓練データに頻出する大規模で確立されたライブラリへ引き寄せられ、新しいツールが気づかれる有機的な選択の過程を取り除いてしまうと付け加えている。2026年2月、GitHub は AI が生成した低品質な貢献の増加がメンテナを圧倒していることを認め、これをオープンソースにとってのエターナル・セプテンバーと表現し、AI 生成のセキュリティ報告が増えた後に cURL プロジェクトがバグ報奨金プログラムを終了したことを引き、プルリクエストの作成を協働者に限定するといったメンテナ向けの制御を導入した。

### 実務者が実際に報告していること

[[ScholarlyArticle/vibe-coding-in-practice]] は、これらの出典のなかで、この実践を定義したり論じたりするのではなく測定しようとした最初の体系的な試みである。灰色文献から実務者の一次証言を集め、四つの問いにわたる行動の単位へ符号化しており、その結果の分布は同じ母集団が四つすべてを報告しているために、あわせて読む価値がある。

動機は速度に支配されている。**速度と効率が動機の単位の62%** を占め、アクセシビリティとエンパワーメントが14%、学習と実験が11% である。経験は成功に支配されている。**即座の成功とフローが64%** であり、実務者はこの過程を速く、容易で、「魔法のよう」と説明しており、ある証言はプロトタイプ・QA チェック・デプロイが素早くまとまったときの「ドーパミンの高揚」を語っている——これに対しプロンプトの苦闘と反復が13%（一部のプロジェクトは数十から数百の反復を要した）、コードの破綻ないし放棄が11%（セッションがデバッグではなくプロジェクトの断念で終わったもの）である。

出力についての判断は、それを生み出す経験よりも明らかに肯定的でない。**「速いが欠陥がある」が68% で最も多い認識**であり、実務者は技術的負債を認識しつつ、欠陥を迅速な開発の不可避のコストとして受け入れている。次いで脆いあるいは誤りやすいが19% で、きれいに見える出力が微妙なロジックの誤り、性能のボトルネック、セキュリティの欠陥を隠しうるという警告を伴う。コードを高品質できれいだと述べる単位はわずか3% である。

QA の分布こそ、同論文が問題を位置づける場所である。**QA の省略が36%**——単体テストも統合テストもなく、構造化されたレビューもなく、正しさはコードが動いたかどうかで判断される——に続き、手作業のテストないし修正が29%、無批判な信頼が18%、そして QA の AI への委任が10% である。最後のものは、誤りを持ち込んだのと同じモデルにそれを見つけさせることに依拠している。

著者らはこれらの数値の上に三つの知見を名指ししている。**速度と品質のトレードオフのパラドックス**——バイブコーダーは迅速な前進のために欠陥のあるコードを承知のうえで受け入れるが、「問題が生じたときにそれを直すスキルを持つのは経験ある利用者だけである」。**AI 支援開発における QA の危機**——著者らはこれを、生成されたコードがアーキテクチャ上の構造と文脈的な詳細を欠くためにデバッグしにくいこと、それを理解しようとしたときの混乱、そして即座の成功の経験が作り出す誤った自信に帰しており、品質の基準が下がることが、テストされていないコードが許容される文化になるという組織上のリスクを伴う。そして**新しい脆弱な開発者の層**——14% のアクセシビリティの動機が連れてくる、アプリケーションを作れるがそれを診断できない人々であり、同論文は彼らが再プロンプトと貼り付けのループという「初心者開発者の罠」に陥るリスクがあると述べている。著者らは、知見が自己選択された実務者の証言に基づいており「すべてのバイブコーダーに一般化できるとはみなせない」と述べている。

## 学術的な形式化

2025年の二つの論文がこの実践の形式的な扱いを提案しており、何を決定的な特徴と取るかにおいて異なっている。

[[ScholarlyArticle/survey-of-vibe-coding-with-large-language-models]] は、バイブコーディングを、開発者が AI 生成の実装を、行ごとのコードの理解ではなく結果の観察を通じて検証する開発手法として特徴づけている——Karpathy の原義に近い読みである。この実践を、人間の開発者・ソフトウェアプロジェクト・コーディングエージェントのあいだの動的な三者関係を捉える制約付きマルコフ決定過程として形式化し、既存の実践を五つの開発モデル——制約なしの自動化、反復的な会話による協働、計画駆動、テスト駆動、コンテキスト強化のモデル——へ統合している。

[[ScholarlyArticle/vibe-coding-ai-native-paradigm]] は異なる定義を提案しており、そこでは開発者がエージェントへ三つのことを伝える。機能的な意図、感情的な調子ないしスタイル——「バイブ」そのものであり、「遊び心があって引き込まれる」「ミニマルでプロフェッショナル」といった記述子で表現される——そして文脈上の制約である。この読みでは、バイブコーディングはプロンプトプログラミングの上に築かれつつ、ソフトウェアの機能的な意図と、開発者が思い描く質的な手触りに等しく重きを置くことでその先へ進むのであり、エージェントはそれに応じて言語、色、アーキテクチャのパターンを選ぶ。同じ論文は Karpathy の原記述の信頼の要素も保っており、提唱者たちが差分を読まずにコードをコピー&ペーストし、それらしく見えるまでエージェントに高水準の変更を頼んで結果を調整すると説明していることを指摘している。

二つの形式化は、開発者の役割がコードを書き検証することから離れていくという主張を共有するが、名前における「バイブ」が開発者によるコードレビューの放棄（Karpathy の意味）を指すのか、機能的な仕様と並んで与えられる質的な仕様（Bamil の意味）を指すのかで一致していない。

### その境界線と、提唱者自身がそれの曖昧化を見出した場所

[[BlogPosting/vibe-coding-and-agentic-engineering-are-getting-closer]] は [[Person/simon-willison]] の境界を言い直したうえで、それが浸食されつつあることを報告している。彼の言い直しはこの語を狭く、かつ侮蔑的でないものに保っている。バイブコーディングとは、あるものを頼んであるものを得ることであり、コードの品質や追加の制約を気にかけず、プログラムの書き方を知らないことさえありうる——そしてそれは「いつ使えていつ使えないかを理解しているかぎり、素晴らしい」。彼が示す境界は誰がコストを負うかである。バグが自分だけを傷つける個人用のツールなら構わないが、他人のために作ることはその基準では「甚だしく無責任」である。他人が自分のバグによって傷つくからである。

彼が変わったと報告するのは定義ではなく、それに対する自らの適合である。エージェントの信頼性が高まるにつれ、彼は本番の作業を含めて全行のレビューをやめ、それが「あの罪悪感——コードをレビューしていないなら、これを本番で使うのは本当に責任ある行いなのか？」を残している。

同記事は、外からソフトウェアを判断する者にとっての二次的な帰結も加えている。100のコミット、良い readme、包括的なテストを備えたリポジトリはかつて丁寧さを示していた。彼はいまや30分でそれと見分けのつかないものを作れるのであり、自分自身のプロジェクトについてさえ違いが分からないと述べている。彼が提案する代替の信号は使用である——誰かが2週間毎日使っているバイブコーディングされたツールは、ほとんど動かされていない何かより価値がある——のであり、そのエンタープライズ版は、他の大企業2社が6か月にわたり問題なく運用していないかぎり CRM を採用しないだろう、というものである。

### どこで機能しなくなるか

Wikipedia の記事はこの境界をスキルではなくタスクの構造の言葉で述べている。生成 AI は「基本的なアルゴリズムのような単純なタスクは扱える」——この表現には記事自身が明確化を要するとのタグを付している——が、そうしたシステムは「より新規で複雑なコーディングの問題には苦戦する」のであり、三つの形を具体的に名指ししている。複数のファイルに関わるプロジェクト、文書化の乏しいライブラリに依存するプロジェクト、そして安全上重大なコードである。

この特徴づけは、上の生産性の知見とは分けておく価値がある。それが記述しているのは別の限界だからである。測定された減速は、この実践が経験ある開発者をどれだけ速くするかに関わる。こちらは、そうしたシステムが苦戦すると同記事が述べる問題のカテゴリを名指ししており、実務者が欠陥のコストを誰が負うかをめぐって引く境界と一致する。

## 関連用語

Willison はこの語の意味の拡大を [[DefinedTerm/semantic-diffusion]] に帰しており、それを止められない力だと説明している。彼は2025年3月23日に [[Person/martin-fowler]] の2006年の語に初めて手を伸ばし、バイブコーディングに起きていることを「この効果が働いている実に明確な例」と呼び、同じことがそれまでの数年で自らの造語であるプロンプトインジェクションにも起きたと報告した。

Bamil の論文は [[DefinedTerm/vibe-engineering]] をバイブコーディングの規律ある対応物として位置づけ、バイブコーディングが実験的なプロトタイピングからその規律ある端に至る実践のスペクトルへ発展しうると示唆している。[[DefinedTerm/agentic-engineering]] は同じ規律ある端に対して別に提案された名称であり、[[DefinedTerm/spec-driven-development]] はそこへ至る一つの道筋である。バイブコーディングが属する包括的な実践は [[DefinedTerm/ai-assisted-software-development]] であり、それを可能にするツールは [[DefinedTerm/coding-agent]] のもとで扱われる。同じ時期に Willison は、Thomas Klausner が [[DefinedTerm/brain-coding]] を造語したことも記録している。Klausner はそれを、空のエディタのバッファから始めて自分でコードを打つ技法だと説明している。

[[Person/dan-shapiro]] の [[DefinedTerm/five-levels-of-vibe-coding]] は、Ryan が2026年1月に公開されたと記録しているもので、広い読みを所与として、実践を「辛口オートコンプリート」からペアリング、エージェントの監督、仕様の執筆を経て [[DefinedTerm/dark-factory]] に至る0〜5の尺度で格づけする。Ryan はこれを成熟度の診断として採用し、前年に自らが関わったすべての案件で、チームは実際の実践より少なくとも1段階高く自己評価したと報告している。
