バイブコーディングとは、生成されるコードを気にかけずに AI でコードを生成することである。[[Person/andrej-karpathy]] は 2025年2月6日にこの語を造り、「完全にバイブに身を委ね、指数関数を受け入れ、コードが存在することさえ忘れる」「新しい種類のコーディング」だと説明した——差分を読まずにすべての提案を受け入れ、エラーメッセージをコメントなしで貼り戻し、コードが自分の理解を超えて育つに任せ、モデルが直せないバグは消えるまでランダムな変更を頼んで回避する。Karpathy はそれが可能になった理由を LLM が「良くなりすぎた」ことに帰し、本番のソフトウェアを作る手法としてではなく「使い捨ての週末プロジェクトにはそう悪くない」ものとして枠づけた。

## 用法

[[Person/simon-willison]] は、造語から6週間後、すでにこの語が『ニューヨーク・タイムズ』『Ars Technica』『ガーディアン』に取り上げられていた時点である 2025年3月19日の [[BlogPosting/not-all-ai-assisted-programming-is-vibe-coding]] で、狭い読みを最初に示した。そこでの彼の定義は「LLM が書いたコードをレビューせずにソフトウェアを作ること」であり、彼が引く線はツールではなくコードへの関与についてのものである。LLM がコードを書いたとしても、それをレビューし、十分にテストし、どう動くのかを他人に説明できるのなら、「それはバイブコーディングではなくソフトウェア開発であり」、LLM を使ったかどうかは本質的な問題ではない。彼は本番品質の作業についての黄金律として、他人に正確に説明できないコードは自分のリポジトリにコミットしないと述べている。同じ記事はこの実践をそれ自体の条件において擁護してもいる。コンピュータサイエンスの学位もブートキャンプの経験もない人にとって「最初の障壁をほとんど平らに削る」アクセスの物語として、そして経験ある開発者が LLM に何ができて何ができないのかの直観を養うための、現在利用可能な最良の方法として——彼はこの主張を、こうして作った80を超える自身の実験によって裏づけている。

Karpathy はその4日後にこの記事へ返信し、自らの造語に留保を加えた。「定義が落ち着くには時間がかかるだろう」と書き、自分自身は「何をしているのか全く分からない」という GIF の犬のような気分のときに「バイブコーディング」という語を使う——前夜に作った iOS アプリを挙げている——としつつ、「実際にはフルのバイブコーディングをすることはめったにない。たいていは今もコードを見ているし、複雑さは少しずつ加えるし、部品がどう動くのかを時間をかけて学ぼうとするし、確認の質問もする」と述べた。この返信を記録した Willison は、同じ日に Bluesky で「この件では負け戦をしている」と感じており、「明確で広く受け入れられた定義を持つ AI 関連の用語が一つ」得られる機会が失われたと書いていた。

[[Person/simon-willison]] は [[BlogPosting/not-vibe-coding]] において、この語が AI 支援プログラミング全般に当てられつつあり、その読みは誤りだと論じる。区別はどのツールを使うかではなく、開発者が生成されたコードにそもそも関与するかどうかにある。彼の見立てでは、本番のコードを責任をもって作るプロセスの一部として LLM のツールを使うことはバイブコーディングではない。彼は近刊の2冊、[[Book/vibe-coding]] と [[Book/vibe-coding-the-future-of-programming]] を、この語がまさに指していなかったはずのプロフェッショナルなワークフローを説明しながらこの語を採用している書名として挙げている。

Willison はまた、この語がツールではなく受け手を指すのだとも論じる。ソフトウェア開発者ではなく、開発者になりたいとも思っていないが、いまや自分のためのカスタムソフトウェアを作る道を得た人々である。彼はその層にとっての未解決の問いを、どんな種類のプロジェクトがこの方法で作れるのか、そしてセキュリティ、プライバシー、信頼性、そして使いすぎのリスクにどう対処するのか、として枠づけている。

Bamil の論文は、より広くゆるい用法が辞書にも記録されたことを報告している。2025年3月までに Merriam-Webster のオンライン辞書は「vibe coding」を「AI の支援を得て、いくらか無頓着にコンピュータのコードを書くこと」を意味する俗語として掲載していた。Merriam-Webster 自身の項目はこれを、AI プログラムに欲しいものを伝えて成果物を作らせることで、コードを書き、ウェブページを作り、あるいはアプリを作ることと定義し、コーダーはコードがどう、なぜ動くのかを理解する必要がなく、しばしば一定数のバグと不具合を受け入れねばならないと注記している。この語は 2025年の『コリンズ英語辞典』の Word of the Year にも選ばれた。

初期の一次的な体験談は職業の外から来た。2025年2月、プロのコーダーではない『ニューヨーク・タイムズ』の記者 Kevin Roose がバイブコーディングを試して小規模なアプリケーションをいくつか作り、どれほど個人向けに作り込めるかを理由にそれらを「一人のためのソフトウェア」と呼んだ——同時に、結果はしばしば限定的で誤りを起こしやすく、あるケースでは EC サイト向けに偽のレビューを捏造したとも述べている。認知科学者の Gary Marcus は、Roose の LunchBox Buddy アプリの背後にあるアルゴリズムはおそらく似たタスクの既存コードで学習されていたのであり、Roose の熱狂は独創性ではなく再生産から生じたものだと応じた。この名前自体を受け入れない者もいた。2025年6月、Andrew Ng はこの語に異を唱え、ソフトウェアエンジニアが AI ツールを使ってアプリケーションを作るときにただ「バイブに任せている」と人に思わせる点で誤解を招くと述べた。

この語の最初の一年に報告された採用は急速だった。2025年3月、Y Combinator は 2025年冬バッチのスタートアップの 25% がコードベースの 95% を AI 生成で持っていたと報告した。2025年7月、『ウォール・ストリート・ジャーナル』はバイブコーディングがプロのソフトウェアエンジニアによって商用のユースケースで採用されつつあると報じた。2026年1月には、Linus Torvalds が自身の AudioNoise オーディオエフェクト生成器のための可視化ツールを [[SoftwareApplication/google-antigravity]] を使ってバイブコーディングしたと報じられ、彼はプロジェクトの README で「Python の可視化ツールは基本的にバイブコーディングで書かれた」と説明している。

[[Book/spec-driven-development-ai-native-software-engineering]] はこの語を、ツールと実践の間の隔たりに対する業界自身の告白として扱う。[[Person/kevin-ryan]] は、ツールが実践を追い越してしまったと書く——「我々はプロンプトを投げ、反復し、だいたい動くものを手に入れ、そして先へ進む」——そして「業界はこれを『バイブコーディング』と呼び始めた。半分は冗談、半分は、我々が行き当たりばったりでやっているという告白である」。

### 誰に、何に向いているのか

実践者の記述は、適切な用途の狭い帯域に収束している。[[NewsArticle/engineers-are-using-ai-to-code-based-on-vibes]] は、動く社内ツールを出荷した2人の非専門家——C の iPad アプリを約2時間で JavaScript のウェブアプリに変換した機械エンジニア（元の作業にはほぼ1か月かかっていた）と、業務では使ったことのないクラウドサービスで概念実証を作ったデータエンジニアリングのリード——を報じるとともに、そのどちらも本当はバイブコーディングをしていなかったと論じる25年目のソフトウェアエンジニアも取り上げる。この人物は、定義を文字どおりに取ると「AI に何をしてほしいかを規定することのほうが、自分でやるより難しい問題になってきている」ことに気づいた。3人が一致する点が一つある。この実践は、エンジニアがまだ知らない言語やスタックのスキルを身につけるのに役立つということだ。ジュニアのエンジニアへの助言は、すでに持っているスキルの高速化としてではなく、新しいスキルを獲得するための加速装置として扱うこと、とされている。

Qiita の日本語の解説記事は、逆の方向から似た形にたどり着き、想定される読み手を、何かが壊れたときに立て直せる程度にはすでにコーディングに通じている人か、あるいは自分では実装できないビジョンを持つ完全な初心者のいずれかだと説明する。適した場面として小規模なプロジェクト、個人用あるいは業務自動化のツール、そしてゼロからの構築を挙げ、実践的なループを、指示し、実行し、コードを読まずにエラーを貼り戻すこととして特徴づける。ツールの分類としては、要件を議論するための汎用アシスタントとチャットボット、ファイルを見ながら最終調整を行うエディタ統合型のエージェント、環境構築とファイルの一括生成のための CLI ベースのエージェント、そして指示を口述するための音声入力を区別し、結果は基盤となるモデルの能力に大きく依存すると注記する。また段階的な実践の流れ——要件定義、技術選定、コードベースの作成、そして微調整——も示しており、そこでは人間の役割はおおむねエージェントが提案するコマンドを承認することになり、安全網として頻繁な Git のコミットが置かれる。この流れは仕様先行の実践に十分近く、この語の厳密な定義とはやや折り合いが悪い。

### 条件と安全策

Willison の 2025年3月の記事は、バイブコーディングが適切な場合の条件を示している。プロジェクトを低リスクに保つこと——バグのある、あるいは安全でないコードがどれだけの害をもたらしうるかを勘案し、他人が使うのであれば特に注意する。セキュリティを慎重に扱うこと——オンラインのツールへアクセスするための API キーのような秘密情報と、マシンから出ていくかもしれない個人データの双方に目を配る。ネットワークの良き市民であること——他のプラットフォームへリクエストを出すものは、それらのサービスの負荷、ひいてはコストを増やすからである。そして従量課金の API に用心すること——請求上限のない API に対してバイブコーディングした機能が数千ドルの請求を積み上げたという恐ろしい話を引いている。彼は、バイブコーディングしたソフトウェアを他人と共有しようとしている初心者には、まずより経験のある人にチェックしてもらうことを勧めている。

彼はバイブコーディングを安全にすることを、サンドボックスを出発点とする未解決の設計問題として扱う。[[SoftwareApplication/claude-artifacts]] の閉じ込められた `<iframe>`——承認されたライブラリのみ、他サイトへのネットワークリクエストなし——を、害を及ぼすことを非常に困難にすると同時に、そうしたプロジェクトにできることを大きく制限するものとして称賛し、当初はプロの開発者向けに意図されており安全策がはるかに少ないと彼が説明する [[SoftwareApplication/cursor]] と対比している。彼はこの領域で「カンブリア爆発」のようなツールの噴出が起きることを望むと述べている。

### 批判

> **情報源についての但し書き。** この節の大部分はバイブコーディングに関する Wikipedia の記事に由来する。同記事の「Criticism」節には 2026年8月付のメンテナンスバナーが付いており、それが「記事の中立性を損ないうる」と警告し、編集者に否定的な情報を他の節に統合するか、些細な批判や論争への過度な焦点を取り除くよう求めている。以下の個々の報告は同記事の帰属のとおりに帰属させているが、主題の残りの部分に対するその比重は、このバナーを念頭に置いて読むべきである。

最も多く引かれる懸念はコードの品質とセキュリティである。論者は、AI 生成のコードを理解しないままコミットする開発者が、検出されないバグと脆弱性を残していくこと、そしてこのアプローチはプロトタイピングや Karpathy が当初思い描いた「使い捨ての週末プロジェクト」には適していても、デバッグ、保守、セキュリティのために深い理解が必要とされる職業的な場面ではリスクをもたらすことを指摘する。報告された事例と研究には次のものがある。2025年5月の報告——バイブコーディングのアプリ Lovable で作られた 1,645 のウェブアプリケーションのうち 170 に、誰でも個人情報にアクセスできてしまう問題があった。2025年10月の Veracode の研究——3年の間に LLM は機能するコードの生成において劇的に改善した一方、生成されたコードのセキュリティは概して改善しておらず、より大きなモデルが小さなモデルより優れているわけでもなかった。2025年12月の CodeRabbit による 470 のオープンソースの GitHub プルリクエストの分析——AI が共著したコードには人間が書いたコードのおよそ 1.7 倍の「重大な」問題が含まれ、設定ミスは 75% 多く、セキュリティ脆弱性は 2.74 倍だった。そして 2025年7月の SaaStr の創業者の報告——変更を加えないよう明示的に指示していたにもかかわらず、Replit の AI エージェントがデータベースを削除した。

さらに2つの事例が記録されている。2025年12月、コンピュータセキュリティ研究者の Etizaz Mohsin が Orchids というバイブコーディングのプラットフォームにセキュリティ上の欠陥を発見し、2026年2月に BBC News の記者に実演した。そして 2026年5月20日に rsync が 3.4.3 に更新された際、増分ファイルバックアップができなくなった複数のユーザーが、rsync 3.4.1 以降の数十の git コミットが「tridge and claude」によって行われており、コーディングの過程で Anthropic の Claude が使われていたことに気づいた。*Please Do Not Vibe Fuck Up This Software* と題された GitHub の Issue は他のサイトにも広がり、AI 生成のコードが重要なオープンソースのインフラに受け入れられることをめぐる議論を巻き起こした。Tridge は *rsync and outrage* と題したブログ記事で応答し、テストスイートと「多層防御の堅牢化技法」をコードに加えるために AI を使ったと述べ、一部のユーザーが乗り換えようとしていた代替である OpenBSD の openrsync は、その AI 支援のテストスイートに通らないと付け加えた。OSNews の編集者 Thom Holwerda はこの最後の発言を「子どもじみていて不必要であり、自信のなさが漂う」と批判した。

[[Person/arun-gupta]] は [[PresentationDigitalDocument/spec-driven-development-using-coding-agents]] で同じ不満の構造的な版を述べ、バイブコーディングを一発勝負の、プロンプトを投げて祈るアプローチだと特徴づける。構造がなく、計画がなく、ハルシネーションによるファイルが大量に生まれ、コードベースを誤解し、企業の標準を無視する。その結果できるコードは拡張しにくく、元のメンタルモデルが失われた後は安全に変更することがほぼ不可能で、レビューも難しくなる。彼の処方はより良いプロンプトではなく、意図を先に、コードを後にするアプローチである——[[DefinedTerm/spec-driven-development]] を参照。

保守性については、2020年から 2024年までの 2億1,100万行のコード変更を対象とした GitClear の 2025年初頭の縦断分析が、リファクタリングが 2021年の変更行の 25% から 2024年には 10% 未満へ落ち込み、コードの重複がおよそ4倍に増え、コピー＆ペーストされたコードが20年ぶりに移動されたコードを上回り、コードのチャーンがほぼ倍増したことを見出している。生産性については、成熟したリポジトリで16人の経験あるオープンソース開発者が 246 のタスクを完了した 2025年7月の METR のランダム化比較試験が、2025年初頭の AI ツールの使用を許可すると完了時間が 19% 増えたことを見出した。参加者は事前に、AI が 24% 短縮すると予測していた。

2025年9月、『Fast Company』は「バイブコーディングの二日酔い」が到来していると報じ、シニアのソフトウェアエンジニアが AI 生成のコードを扱う際の「開発地獄」に言及していると伝えた。デバッグは繰り返し挙がる理由である。LLM はコードを動的に生成するためその構造は変わりうるし、開発者は自分で書いていないためその構文と概念を理解するのに苦労しかねない。2026年5月、『ウォール・ストリート・ジャーナル』は、OpenClaw の AI エージェントシステム内の Pi コーディングハーネスを手がけたエンジニアである Mario Zechner と Armin Ronacher による批判を報じた。彼らは迫りくる「バイブスロップ」の危機を警告し、企業が目先の生産性と引き換えに長期的にバグの多いソフトウェア、サービスの障害、セキュリティ脆弱性、技術的負債を負っていると論じた。Zechner の言葉が引用されている。「インフラは崩れつつあり、ソフトウェアは以前と比べて非常に、非常にバグが多くなっている。あと数か月、あるいは数年はこのゲームを続けられるかもしれないが、いずれ我々に追いついてくる」。

さらに2つの筋は、個々のコードベースではなくエコシステムに関わる。2026年1月の「Vibe Coding Kills Open Source」と題された論文は、バイブコーディングが既存コードを使い、その上に築くコストを下げることで生産性を高める一方、多くのメンテナが見返りを得ている経路であるユーザーの関与を弱めるため、生産性が高まるにもかかわらずオープンソースソフトウェアの入手可能性と品質を下げると論じる。この論文についての論評はさらに、モデルが学習データに頻繁に現れる大規模で確立されたライブラリへ引き寄せられるため、新しいツールが注目される有機的な選別の過程が失われると付け加えている。2026年2月、GitHub は低品質な AI 生成の貢献が増えメンテナを圧倒していることを認め、これをオープンソースにおける「終わらない9月」と表現し、AI 生成のセキュリティ報告が増えた後に cURL プロジェクトがバグ報奨金プログラムを終了したことを引き、プルリクエストの作成を協力者に限定するといったメンテナ向けの制御を導入した。

### 実践者が実際に報告していること

[[ScholarlyArticle/vibe-coding-in-practice]] は、これらの情報源の中で、この実践を定義したり論じたりするのではなく測定しようとする最初の体系的な試みである。灰色文献にある実践者の一次的な記述を、4つの問いにわたる行動単位へコード化したもので、得られた分布はまとめて読む価値がある。同じ母集団が4つすべてを報告しているからである。

動機は速度に支配されている。**「速度と効率」が動機の単位の 62%** を占め、「アクセシビリティと権限付与」が 14%、「学習と実験」が 11% である。体験は成功に支配されている。**「即座の成功とフロー」が 64%** で、実践者はこの過程を速く、簡単で、「魔法のよう」だと説明し、ある記述はプロトタイプ、QA チェック、デプロイが素早く噛み合ったときの「ドーパミンの一撃」を語る——これに対して「プロンプトの苦闘と反復」は 13% で、一部のプロジェクトは数十回から数百回の反復を要し、「コードの破綻または放棄」は 11% で、セッションはデバッグではなくプロジェクトを諦めることで終わっている。

出力に対する評価は、それを生み出す体験ほど肯定的ではない。**「速いが欠陥がある」が 68% で最も多い認識** であり、実践者は技術的負債を認識しつつ、欠陥を素早い開発に不可避な代償として受け入れている。「脆弱あるいは誤りを起こしやすい」は 19% で、きれいに見える出力が微妙な論理の誤り、性能上のボトルネック、セキュリティ上の欠陥を隠しうるという警告を伴う。コードを「高品質できれい」と説明する単位はわずか 3% である。

QA の分布こそ、論文が問題の在り処とする場所である。**「QA の省略」が 36%**——単体テストも統合テストもなく、構造化されたレビューもなく、正しさはコードが動いたかどうかで判断される——、次いで「手作業のテストまたは修正」が 29%、「無批判な信頼」が 18%、そして「QA を AI に委譲」が 10% であり、最後のものは誤りを持ち込んだのと同じモデルにその発見も頼ることである。

著者らはこれらの数値の上に3つの知見を名指しする。**速度と品質のトレードオフのパラドックス**——バイブコーダーは素早い前進のために欠陥のあるコードを承知の上で受け入れるが、「問題が起きたときにそれを直すスキルを持つのは経験あるユーザーだけである」。**AI 支援開発における QA の危機**——著者らはこれを、生成されたコードがアーキテクチャ上の構造と文脈上の詳細を欠くためデバッグしにくいこと、それを理解しようとするときの混乱、そして即座の成功という体験が生む誤った自信に帰す。そして組織的なリスクとして、品質の水準が下がることが、テストされていないコードが許容される文化になってしまうことを挙げる。そして **新しい種類の脆弱な開発者** ——14% のアクセシビリティという動機が招き入れる、アプリケーションを作れても診断はできない人々であり、論文によれば再プロンプトと貼り付けのループという「初心者開発者の罠」に陥る危険がある。著者らは、その知見が自己選択された実践者の記述に基づくものであり「すべてのバイブコーダーに一般化できるとはみなせない」と述べている。

## 学術的な形式化

2025年の2つの論文がこの実践の形式的な扱いを提案しており、何を決定的な特徴と見るかにおいて異なっている。

[[ScholarlyArticle/survey-of-vibe-coding-with-large-language-models]] は、バイブコーディングを、開発者が AI 生成の実装を一行ずつのコード理解によってではなく結果の観察によって検証する開発方法論として特徴づける——Karpathy の元の定義に近い読みである。この実践を、人間の開発者、ソフトウェアプロジェクト、コーディングエージェントの間の動的な三者関係を捉える制約付きマルコフ決定過程として形式化し、既存の実践を5つの開発モデル——無制約の自動化、反復的な対話的協働、計画駆動、テスト駆動、そして文脈強化のモデル——に統合している。

[[ScholarlyArticle/vibe-coding-ai-native-paradigm]] は異なる定義を提案し、そこでは開発者がエージェントに3つのことを伝える。機能的な意図、感情的なトーンあるいはスタイル——「バイブ」そのものであり、「遊び心があって魅力的」「ミニマルでプロフェッショナル」といった記述子で表される——、そして文脈上の制約である。この読みにおいてバイブコーディングはプロンプトプログラミングの上に築かれつつ、ソフトウェアの機能的な意図と、開発者が思い描く質的な手触りに等しく重きを置く点でさらに踏み込んでおり、エージェントはそれに応じて言語、色、アーキテクチャのパターンを選ぶ。同じ論文は Karpathy の元の説明にあった信頼の要素も保持しており、支持者が差分を読まずにコードをコピー＆ペーストし、見た目が良くなるまでエージェントに高水準の変更を頼んで結果を調整することを説明していると注記している。

2つの形式化は、開発者の役割がコードを書き検証することから離れていくという主張を共有するが、名前にある「バイブ」が開発者によるコードレビューの放棄（Karpathy の意味）を指すのか、機能的な仕様と並んで供給される質的な仕様（Bamil の意味）を指すのかについては一致していない。

## 関連用語

Willison はこの語の意味の拡大を [[DefinedTerm/semantic-diffusion]] に帰し、それを止められない力だと説明する。彼が [[Person/martin-fowler]] の 2006年の語に最初に手を伸ばしたのは 2025年3月23日であり、バイブコーディングに起きていることを「この効果が働いている実に明快な例」と呼び、同じことが自らの造語であるプロンプトインジェクションにもここ数年で起きたと報告した。

Bamil の論文は [[DefinedTerm/vibe-engineering]] をバイブコーディングの規律ある対応物として位置づけ、バイブコーディングが実験的なプロトタイピングからそのより規律ある端までにわたる実践のスペクトルへ発展しうると示唆している。[[DefinedTerm/agentic-engineering]] は同じ規律ある端に対して別途提案された名前であり、[[DefinedTerm/spec-driven-development]] はそこへ至る一つの道である。バイブコーディングが収まる包括的な実践が [[DefinedTerm/ai-assisted-software-development]] であり、それを可能にするツールは [[DefinedTerm/coding-agent]] で扱われている。同じ時期に Willison は、Thomas Klausner が空のエディタバッファから始めて自分でコードを打ち込む技法に対して [[DefinedTerm/brain-coding]] を造語したことも記録している。

[[Person/dan-shapiro]] の [[DefinedTerm/five-levels-of-vibe-coding]] は、Ryan が 2026年1月に公開されたと記録するもので、広い読みを前提として、「辛口オートコンプリート」からペアリング、エージェントの監督、仕様の記述を経て [[DefinedTerm/dark-factory]] に至る 0〜5 の尺度で実践を格付けする。Ryan はこれを成熟度の診断として採用し、その前年に手がけたすべての案件で、チームが実際の実践より少なくとも1つ上のレベルを自己申告したと報告している。
