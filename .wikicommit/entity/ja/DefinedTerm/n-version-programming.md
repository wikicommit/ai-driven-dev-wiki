N バージョンプログラミング（N-version programming）とは、[[ScholarlyArticle/agentic-software-engineering-foundational-pillars]] で論じられている、同じタスクに対する解の独立した複数のバージョンを生成する実践である。同論文は、これがエージェント型ソフトウェアエンジニアリングにおいて再び現れていると述べる。エージェントのチームは同じチケットに対して複数の候補となるプルリクエストを並列に生成でき、これは試行錯誤を通じて成功する結果の確率を高める推論時計算の一形態としても、創造的な探索の手段としても役立つ。

## 用法

同論文の動機づけの例では、7 つのチケットを解決しようとする開発者がエージェントのチームを起動して 28 個の候補プルリクエストを並列に生成させる（チケットごとに 4 つ）。開発者はその後、チケットごとに最も有望な候補を選ぶか、受け入れられるものがなければ仕様を洗練してエージェントを再起動する。同論文は、自らが提案する [[DefinedTerm/agent-command-environment]]（ACE）が「規律ある N バージョンプログラミング」をサポートしなければならず、開発者がエージェントの生成した複数の解を可視化し、比較し、その構成要素を組み合わせられるようにすべきだと述べている。1 つの [[DefinedTerm/briefingscript]] を複数のエージェントに割り当てるという [[DefinedTerm/loopscript]] のタスク分解と並列化の能力こそが、N バージョンプログラミングを「日常的な」ものにし、重要な指標を単一タスクのレイテンシーからシステム全体のスループットへと移すと同論文は述べる。また、コーチの指導が、エージェントの生成した異なる草案から最終的な解を合成すること（たとえば、ある解の UI と別の解のバックエンドロジックを組み合わせること）を伴いうる場面として、N バージョンプログラミングを挙げている。

## 適用される場面

同論文は N バージョンプログラミングを、自らが生み出したものではなく、エージェント型コーディングのために転用されつつある、何十年も前からある既存の耐障害性の技法として扱っている。そしてこの実践の再登場を、複数の LLM ベースのエージェント（あるいは、高水準の計画を担うモデルと詳細なコード生成を担う別のモデルのような、専門化したエージェントの異種混成チーム）を同じ仕様に対して並列に走らせられるようになったことで実用的になったものとして挙げている。
