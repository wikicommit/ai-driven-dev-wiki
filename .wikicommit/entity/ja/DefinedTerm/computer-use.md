コンピュータ操作とは、モデルが専用の API を呼ぶのではなく、ユーザーに代わってグラフィカルなインターフェース——ブラウザ、モバイルアプリ、デスクトップ環境——を操作するエージェントの能力である。モデルは画面のスクリーンショットを、タスクのプロンプトおよびそれまでのコンテキストとあわせて入力とし、モデルの求めることを実際に遂行する環境は呼び出し側が用意する。モデルが何を返すかはベンダーによって異なる。クライアント側のハンドラが再生する個別の UI アクション（マウスクリック、キー入力、スクロール、ドラッグ&ドロップ）を発するものもあれば、自動化ライブラリを介してインターフェースを駆動するコードを書くものもある。

## 用法

公開されている実装はいずれもループを中心に構築されており、各ターンでモデルと環境の境界を越えるものが何かという点で異なる。

Google の Gemini API は、関数呼び出しに似た `computer_use` ツールを公開しており、ブラウザ、モバイル、デスクトップの各環境を対象とする。アプリケーションはスクリーンショットをタスクのプロンプトとともにモデルへ送り、モデルは UI アクションを返し（Gemini 3.x 系のモデルでは、各アクションにそれを選んだ理由を説明する `intent` 文字列が付く）、クライアントはモデルの正規化された座標を実際の画面にスケールしてブラウザまたは OS の自動化ライブラリでアクションを実行し、新たなスクリーンショットを取得して送り返すことでループを継続する。Gemini の実装は現行のアクション語彙（`click`、`type`、`scroll`、`navigate` など、環境によって異なる）と、旧来のモデル向けのレガシーな語彙（`click_at`、`type_text_at`、`scroll_at`）の両方をサポートし、呼び出し側が既定の定義済みアクションを除外して代わりに独自のアクションを登録することも許している——たとえば、モデルが安全でない、あるいは曖昧だと判断した場合に人間へ制御を返す `yield_to_user` 関数などである。

OpenAI のドキュメントは同じ能力について 2 つの統合スタイルを提示し、GPT-6 Astra モデルには前者を推奨しつつ、後者もサポート対象の代替として残している。**コード実行**では、モデルにスクリプトを受け取る通常の関数ツールが与えられる。アプリケーションはそのスクリプトを隔離されたブラウザまたはデスクトップ環境で実行し、スクリーンショットを含む出力を返す。やり取りの単位が単一の操作ではなくスクリプトであるため、1 回の呼び出しに複数のアクション、ループ、条件分岐を組み合わせられる。**computer ツール**では、モデルは代わりに構造化されたマウスおよびキーボードのアクションを返し、アプリケーションがそれをブラウザまたはデスクトップの入力へ変換する。ループはモデルが `computer_call` 項目を返さなくなるまで続く。いずれにせよ、モデルが以前の作業の上に積み重ねられるよう、環境は呼び出しの間も利用可能なままでなければならない。OpenAI は、関数呼び出しやリモート MCP ツールを通じてすでに UI 操作を公開しているアプリケーションなら、そのインターフェースをそのまま使い続けてよいと注記している。OpenAI は JavaScript/Playwright 版と Python/PyAutoGUI 版の実装を備えた CUA のサンプルアプリを公開している。

## 適用条件

コンピュータ操作エージェントは実在の画面環境の中で実際の行為を行うため、両ベンダーともこれを通常の関数呼び出しツールより高リスクと扱っており、その指針は 4 つの制御へ収斂する。

*環境を制限する。* Google はホストシステムではなく、権限を絞ったサンドボックス化された VM、コンテナ、あるいは専用のブラウザプロファイルを推奨し、加えてエージェントがどこへ遷移できるかを律する許可リストと拒否リストを求めている。OpenAI は隔離されたブラウザまたは VM と、サイトおよびアクションの許可リストを求め、アクセスをタスクに必要な範囲に限るよう述べている。

*画面上にあるものを信頼できないものとして扱う。* OpenAI はこの原則を直截に述べている。ページ、ドキュメント、ツール結果の中のテキストは、権限を与えることもユーザーの指示を上書きすることもできない。Google の安全性に関する指針も脅威の側から同じ点を述べており——ユーザーに代わって行為するモデルは画面上で信頼できない内容に遭遇しうる——Gemini 3.5 Flash 以降のモデルでは、行為に移る前にスクリーンショットを走査して隠された敵対的指示がないかを調べるオプトインの機能が提供されている。これは [[DefinedTerm/indirect-prompt-injection]] の、画面を媒介とする形態である。

*重大な行為には確認を求める。* Gemini の実装は、あるアクションに `require_confirmation` の印を付ける、あるいは端的にそれを阻止する `safety_decision` を返すことができ、金融取引、機微なデータの変更、アカウント作成、法的合意への同意といった組み込みのカテゴリを対象とする。OpenAI は、購入、データ送信、破壊的あるいは取り返しの難しい変更についてユーザーが制御を保ち続けることを求めており、機微な情報をフォームに入力することも送信に数えている。

*実行を制限し、検証する。* OpenAI はステップ数、時間、コストの上限、中断のサポート、そしてモデルの最終的な回答に頼るのではなくアプリケーション内で実際の結果を確かめることを推奨している。Google の対応する推奨は、ユーザー提供のテキストがプロンプトに届く前にサニタイズすること、そして後の監査のためにプロンプト、スクリーンショット、実行されたアクションをログに残すことである。Google はさらに、自らの Gemini 実装を「誤りやセキュリティ上の脆弱性を含みうる」プレビュー機能として文書化しており、重大な判断、機微なデータ、深刻な誤りが訂正できない行為には用いないよう推奨している。

第三のベンダーによる記述は、こうした能力の使い方ではなく、そのうちの一つが提供される前に何が起きたかを補っている。[[BlogPosting/building-safeguards-for-claude]] は、Anthropic が自社のコンピュータ操作ツールについて提供開始前に行った評価で、この能力がスパムの生成と配布を増幅しうると判断したこと、そしてそれを受けて——提供開始に先立って——悪用の兆候を示すアカウントに対してこのツールを無効化する選択肢を含む新たな検知手法と執行機構、ならびにプロンプトインジェクションからユーザーを守る新たな保護を開発したことを報じている。したがって上記のベンダー側の制御が、コンピュータ操作の運用を律するもののすべてではない。その一部は開発者の設定の外側、提供元自身のサービング経路において執行されている（[[DefinedTerm/guardrails]] を参照）。

この記述はまた、2 つの実装ガイドが主張するリスクの枠組みを裏づける証拠でもある。両ガイドが一般的な原則としてサンドボックス化と画面を信頼しないことを推奨しているのに対し、こちらはリリース前にこの能力を検証して見つかった具体的な悪用経路と、それに対して実際に投入された対応を報告している。
