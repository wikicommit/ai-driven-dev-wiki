批判的対話レビューとは、[[BlogPosting/ai-driven-development-two-commands]] が、モデルとそれ自身の間ではなく、異なるモデルで動作する 2 つのコーディングエージェントの間で回されるレビューのループに与えている名称である。そこで説明されている構成では、[[SoftwareApplication/claude-code]] がオーケストレーションを担う。すなわち、設計書を生成し、実装し、何を採用するかを判断し、修正を実行する。一方、[[SoftwareApplication/openai-codex]] はリポジトリのコードを独立に調査し、設計と実装を批判する。掲げられている狙いは、ある AI が出した答えを、別の AI が独立した視点から疑うことである。

## 用法

最小単位は 3 ラウンドである。Codex がリポジトリを独自に調査して設計または実装を批判的にレビューし、Claude Code が各指摘を精査して採用・却下・保留のいずれにするかを決め、どの場合も理由を記録する。続いて Codex が、却下された指摘と残っているリスクを再び批判する。ラウンド数は固定されておらず、難しい変更には追加のサイクルが必要になる一方、軽い変更はより早く収束すると説明されている。

レビューするエージェントに渡されるのは差分だけではない。この実践は単に `git diff` をレビューの指示とともに渡すことではないと明言されており、対象タスクの背景、目的、受け入れ基準、実装の詳細、設計上の制約が進捗表から取り出され、変更とともに送られる。その材料に照らして、2 つの軸でレビューが行われる。コード品質（バグ、リグレッション、設計上の欠陥、セキュリティ、テストの不足）と、仕様への適合（実装が受け入れ基準を満たしているか、掲げられた目的と整合しているか、実装方針に従っているか、過剰な実装になっていないか）である。設計フェーズでは、同じループが最後に一度だけではなく、設計書、タスク分解、実装方針という 3 つの別々の時点で適用される。その根拠として、設計や分解の時点で見つかった食い違いは実装後に見つかったものより修正コストが低いこと、そして AI が生成したタスク分解は、既存のコードが実際に行っていることから乖離していてももっともらしく見えうることが挙げられている。

2 つ目のエージェントに送られるプロンプトと差分は、送信前にシークレット — API キー、パスワード、トークン — が含まれていないか確認される。この説明はこれを、実行する人に委ねるのではなく、コマンドに組み込まなければならない運用ルールとして示している。

## 適用される場面

この実践は、コストに見合うほど品質が重要な場面で推奨されており、あらゆる場面で推奨されているわけではないことが明言されている。この説明によれば、Codex との組み合わせは Claude Code 単独で動かすよりも時間と費用がかかり、すべてのタスクに使うものではなく、重要な機能やリスクの高い変更に対して効果的であると結論づけられている。Claude Code 単独が通常モードとして維持され、ペアで回すループは品質重視のモードとして提供される。

前提となるのは、真に異なるモデルで動作する 2 つのエージェントであり、かつレビューする側が、1 つ目のエージェントが見せるものだけを見るのではなく、リポジトリを自ら調査できることである。より安価な代替手段に対して示される論拠は、単一のモデルは自らの盲点とプロバイダーによる性能調整にさらされること、そして同じモデルに自らの出力をレビューさせるのは実装こそ容易だが、視点の独立性が弱いということである。

掲げられている失敗モードは収束しないことであり、説明されている設計はそれを欠陥ではなく境界として扱う。自動実行はレビューポイントごとに最大 3 サイクルまで回り、同じ指摘が 2 サイクル連続で未解決のまま残った場合、ループは対話型に切り替わる。どちらのエージェントも最終的な判定者ではない。自動モードが収束しない場合、判断は人間に戻され、この説明はそれを品質保証の破綻ではなく、その一部と位置づけている。

確立の度合い: これは 1 つの部門による自らの導入事例の説明であり、測定された結果としてではなく設計上の根拠として提示されている。記事は、ペアで回すループと単一モデルによるレビューとの間で欠陥率を比較しておらず、効果測定を今後の課題の 1 つに挙げている。
