批判的対話レビューとは、[[BlogPosting/ai-driven-development-two-commands]] が、モデルと自分自身の間ではなく、異なる
モデルで走る 2 つのコーディングエージェントの間で回されるレビューのループに与えた名称である。そこで述べられている構成
では、[[SoftwareApplication/claude-code]] が統括役を担う。設計文書を生成し、実装し、何を採用するかを判断し、修正を
実行する。一方 [[SoftwareApplication/openai-codex]] は独立にリポジトリのコードを調査し、設計と実装を批判する。掲げ
られている狙いは、一方の AI が出した答えを、もう一方が独立した視点から疑うことである。

## 用法

最小単位は 3 ラウンドである。Codex が自らリポジトリを調査し、設計ないし実装を批判的にレビューする。Claude Code が各
指摘を精査し、採用するか、却下するか、保留するかを決め、いずれの場合も理由を記録する。続いて Codex が却下分と残存する
リスクを再批判する。ラウンド数は固定ではない——難しい変更には追加のサイクルが要り、軽いものはより早く収束すると
述べられている。

レビューするエージェントに手渡されるものは差分だけではない。この記述は、この実践が単に `git diff` を「レビューして」と
いう指示とともに渡すことではないと明言している。対象タスクの背景、目的、受け入れ基準、実装の詳細、設計上の制約が進捗表
から引き出され、変更とあわせて送られる。その材料に照らして 2 つの軸がレビューされる。コード品質（バグ、退行、設計上の
欠陥、セキュリティ、テストの不足）と、仕様への適合（実装が受け入れ基準を満たしているか、掲げられた目的と整合しているか、
実装方針に従っているか、過剰実装になっていないか）である。設計フェーズでは、同じループが最後に一度ではなく 3 つの別々の
地点に適用される。設計文書、タスクの分解、そして実装方針である。その理由として、設計や分解の時点で捉えられた食い違いは
実装後に捉えられたものより修正の費用が安いこと、そして AI が生成したタスクの分解は、もっともらしく見えながら既存の
コードが実際に行っていることから乖離しうることが挙げられている。

第二のエージェントへ送られるプロンプトと差分は、送出の前にシークレット——API キー、パスワード、トークン——がないか
確認される。この記述はこれを、実行する人に委ねるのではなくコマンドの中に組み込まねばならない運用上の規則として提示して
いる。

## 適用条件

この実践は、品質がその費用を正当化するだけ重要な場面について擁護されており、あらゆる場面についてではないと明示されて
いる。この記述は、Codex を組み合わせると Claude Code 単体より時間も費用もかかると報告し、あらゆるタスクで用いるものでは
なく、重要な機能とリスクの高い変更に対して有効だと結論している。Claude Code 単体が通常のモードとして保たれ、2 つを
組み合わせたループは品質重視のモードとして提供される。

これは、真に異なるモデルで走る 2 つのエージェントがあること、そしてレビューする側が、第一のエージェントが見せるものだけを
見るのではなく自らリポジトリを調査できることを前提とする。より安価な代替に対して立てられている論拠は、単一のモデルは
自らの死角と提供元による性能のチューニングにさらされており、同じモデルに自らの出力をレビューさせることは——実装は容易
でも——観点の独立性が弱い、というものである。

述べられている失敗モードは収束しないことであり、そこで述べられている設計はそれを欠陥ではなく境界として扱っている。
自動実行はレビュー地点ごとに最大 3 サイクルまでで、同じ指摘が連続する 2 サイクルにわたって未解決のまま残る場合、ループは
対話モードへ切り替わる。どちらのエージェントも最終的な裁定者ではない。自動モードで収束しない場合、判断は人へ戻る。
この記述はそれを、品質保証の破綻ではなくその一部として述べている。

どの程度確立されているか。これはある一部門が自らの導入について述べたものであり、測定された結果としてではなく設計の
根拠として提示されている——同記事は、組み合わせたループと単一モデルのレビューとの間で不具合率を比較しておらず、効果の
測定を今後の課題として挙げている。
