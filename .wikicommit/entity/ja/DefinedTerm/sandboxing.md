サンドボックス化とは、AI コーディングエージェントを隔離された環境――コンテナ、仮想マシン、別ブランチ、あるいは使い捨てのワークスペース――で実行する実践であり、そこではエージェントは実際の本番システムに影響を与えることなく、ファイルを読み、コードを書き、コマンドを実行できる。エージェントがディレクトリの削除、設定ファイルの破損、問題のある依存関係のインストールといった誤りを犯しても、被害はサンドボックス内にとどまり、実際のコードベースは無傷のまま保たれる。

## 用法

サンドボックス化の具体的な形態には次のものがある。Git ワークツリー（エージェントが作業するためのリポジトリの隔離されたコピーで、結果が良ければマージし、そうでなければ削除する）、コンテナ（ネットワークアクセスを制限し、ファイルシステムを隔離した Docker の中でエージェントを実行する）、エフェメラルな開発環境を提供する GitHub Codespaces や Gitpod などのクラウドサンドボックスサービス、エージェントが別ブランチで作業し、人間のレビューの前に CI が変更を検証するブランチベースの隔離、エージェントが外部 API を呼び出したり本番サービスにアクセスしたりすることを防ぐネットワーク制限、そして完全なサンドボックス化がなくても軽量な隔離の一形態となるパーミッションのスコーピング（大半のディレクトリは読み取り専用とし、書き込みは特定のパスに限る）である。

[[BlogPosting/designing-agentic-loops]] は、エージェントをローカルで隔離することと単にリスクを受け入れることとの中間の選択肢を示している。それは**他人のコンピュータ**上でエージェントを実行することであり、そうすれば暴走したエージェントの影響範囲（blast radius）は、それが自分のマシンではないという点で限定される。その投稿の著者はこれを自身のお気に入りとして挙げ、その実例として GitHub Codespaces を示し、最悪のケースを、環境にチェックアウトされたコードが持ち出されるか、接続されたリポジトリに悪いコードがプッシュされることに限定している――しかも消費される CPU は他人のものである。また、ホスト型のコードインタープリターのモードも同じ役割で驚くほど遠くまで使えると述べ、著者が OpenAI の Codex Cloud をそのように使って大きな成果を上げたと報告している。

[[BlogPosting/ai-coding-agent-speed-and-safety-2026]] は、これらの形態のうち 3 つを、4 つの軸――セットアップの手間、安定性、開発者がエディタを自由に選べるか、外部ツールとの統合のしやすさ――で互いに比較している。開発コンテナは、中程度の手間で、安定性とエディタの選択において良い結果を示す。その投稿は、エージェントのベンダー自身のリポジトリに iptables ベースのネットワーク制限を備えたコンテナ設定のサンプルが含まれていること、そして別の CLI とサードパーティのツールがいずれも同じ設定を外部から駆動できるため、コンテナ開発は 1 つのエディタに縛られないことを指摘している。その代償はホスト上で作業する際の利便性であり、パスワードマネージャーからのシークレットの取得、フック駆動の通知、ユーザーレベルのエージェント設定の共有がいずれも難しくなる。

エージェント自身の組み込みサンドボックスは、3 つの中でセットアップの手間が最も少なく、クラウド IDE と並んでコンテナを下回る。コンテナ定義を書くのではなく、エージェントの設定ファイルから有効化するものである。これは Linux では bubblewrap、macOS では Seatbelt で実装されている。その投稿はこれを 3 つの中で最も成熟度が低く、それに応じて内部で何かが失敗したときの診断が難しいと報告している。そして、サンドボックス外のコマンドを依然として許可する設定をオフにすることを推奨しつつ、そうするとサンドボックス自体が引き起こすエラーを回避する余地が小さくなることも認めている。3 つ目の選択肢はクラウド IDE であり、手間が少なく隔離もされているが、使うエディタが決まってしまう。

同じ投稿は、サンドボックスと承認設定を二者択一として扱うのではなく、サンドボックスを*より*許容的な承認設定と組み合わせるべきだという論拠も示している。シェルコマンドはサンドボックス化されている*からこそ*それらを自動許可する設定を推奨しており、その根拠は、安全性という特性を保ちながら体験が向上するというものである。そして、パーミッションプロンプトが大幅に削減されたことを、自ら計測するのではなく、ベンダー自身のエンジニアリング記事から伝えている。プロンプトが減ること自体が単なる利便性ではなく安全性の特性でもあるという点は、その投稿の別の節――パーミッション設定に関する節――で論じられており、ここでは [[DefinedTerm/approval-fatigue]] の項で説明されている。

## 適用される場面

サンドボックス化は、エージェントに与える自律性が大きくなるほど重要になる。エージェントは指示を誤解したり、解決策をハルシネーションしたり、意図しない副作用を伴うコマンドを実行したりしうるため、隔離がなければすべてのアクションが現実のリスクを伴い、各コマンドは実行前にレビューと承認を必要とする。サンドボックス化が整っていれば、エージェントは自由に試行錯誤でき、レビューが必要なのは最終結果だけになる。これはワークフローを劇的に高速化すると説明されている。これは特定の誰かによる提案ではなく、自律型エージェントのための一般的なベストプラクティスとして提示されており、エージェントの出力を信頼できないプルリクエストのように扱うこと、すなわち隔離された環境で作業させ、結果をレビューし、検証の後にのみマージすることとして要約されている。

上記の説明がネットワーク制限を複数ある隔離技法の 1 つとして扱うのに対し、[[BlogPosting/claude-code-for-web-async-coding-agent]] はそれを難所であり、かつセキュリティ上の論拠を担うものとして特に取り上げている。Anthropic のサンドボックス化の取り組みについて報告する中で、同投稿はファイルシステムの隔離は比較的容易で、ネットワークの隔離こそが難しい問題だと述べ、Anthropic のアプローチを引用している。すなわち、インターネットアクセスはサンドボックスの外で動作するプロキシサーバーに接続された Unix ドメインソケットを通じてのみ許可され、そのプロキシがプロセスが到達してよいドメインを強制し、新たに要求されたドメインについてはユーザーの確認を処理する。これが重要である理由として投稿が挙げるのは [[DefinedTerm/lethal-trifecta]] である。そうした攻撃に対する最善の防御は 3 つの要素のうち 1 つを断つことであり、外向きのネットワークアクセスを制限することが、持ち出しという要素を取り除く方法となる。また、部分的な遮断の限界にも言及している。依存関係のインストール用ドメインが数十にも及ぶ許可リストは、その内側に持ち出しの経路が残っているのではないかと著者を不安にさせたのに対し、ネットワークなしのモードであればその軸について心配すべきことは何もない。

その投稿は、各アクションを単に承認するのではなく、サンドボックス化に労力をかける価値がある理由についての論拠も示している。Anthropic の投資を、段階ごとのパーミッションプロンプトなしで実行されるエージェントは、それを必要とするエージェントよりはるかに生産的であることの認識と読み、それゆえ解くべき問題は承認を厳しくすることではなく、便利で安全な実行であるとする。著者はこのアプローチを、自分にとって信頼できると感じられる唯一のものと述べている。

これらのいずれかが実際にどれほど確実に達成されているかについては、[[BlogPosting/designing-agentic-loops]] がより懐疑的に扱っている。その投稿は、コーディングエージェントはそれぞれ独自のレベルのサンドボックス化を実装しているが、著者は信頼できるほど説得力のあるそれらのドキュメントを見たことがないと報告しており――これは検証された知見ではなく著者自身の評価である――、コンテナエスケープが存在することを指摘しつつも、Docker や Apple のコンテナツールを大半の人にとって受け入れるに足るリスクとして扱っている。より率直な観察は、技法よりも普及に関するものである。サンドボックス、他人のマシン、単にリスクを取ることの 3 つを提示されると、大半の人は 3 つ目を選ぶという。同じ投稿は、`--dangerously-skip-permissions` をインターネットアクセスのないコンテナ内で使うことを推奨する Anthropic の Claude Code ドキュメントを引用し、非公開のソースコードの持ち出しを防ぐ方法として、エージェントを信頼できるホストのリストに制限することを支持している。
