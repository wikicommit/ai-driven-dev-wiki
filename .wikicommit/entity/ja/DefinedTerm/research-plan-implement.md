Research → Plan → Implement——RPI と略される——は、コーディングエージェントと働くための3フェーズのワークフローである。[[BlogPosting/survey-of-development-workflows-in-the-coding-agent-era]] は、これを Cloudflare のエンジニアリングリードである Boris Tane が9か月にわたる Claude Code の利用から体系化したものとして説明し、Block と HumanLayer で独立に開発された方法論と収斂しているとする。その中心となる規則は簡潔に述べられている。詳細に書かれた計画をあなたがレビューし承認するまで、エージェントに一行たりともコードを書かせてはならない。

## 用法

**Research** はコードベースの深い読み込みであり、`research.md` を生み出す。サーベイはその説明からプロンプトの細部を記録している——*deeply*（深く）や *intricacies*（込み入った事情）といった語を使って、エージェントを一読しての回答ではなく徹底した調査へと押しやるのだ。

**Plan** は `plan.md` を、コード断片とファイルパスを伴う詳細な文書として生み出す。これは、人間がテキストエディタでインラインの注記を加える1回から6回の*注釈サイクル*を通じて洗練される。この注釈サイクルこそが、承認を形式的な追認ではなく実質的なものにする。人間のレビューは、計画への承認としてではなく計画への編集として着地するからだ。

**Implement** は、承認された計画に対するバッチでの実行であり、型チェックが継続的に走る。

これを特徴づける仕組みは、各フェーズ境界での [[DefinedTerm/frequent-intentional-compaction]] であり、80〜100% で事後的にコンパクションするのではなく、コンテキストの使用率を 40〜60% の帯に保つ。サーベイが伝える報告された成果は、30 万行の Rust コードベースにおいて、これによりチームが1週間分の仕事を1日で完了できたというものだ——これは独立した測定ではなく HumanLayer 自身の数字である。

適合するとされているのは、中規模のチーム、品質を重視するプロジェクト、そして既存のコードベースへの大きな変更である。サーベイによる4つのワークフローの比較において、RPI は検証の仕組みがテストや仕様への適合ではなく注釈サイクルである唯一のものであり、またフレームワークやプラグインではなくファイルの規約に依拠するため、ツールへの依存度が中程度にとどまる唯一のものでもある。

## 関連用語

RPI は、そのサーベイが組み合わせ可能なものとして提示する4つのプロジェクトワークフローの一つであり、ブレインストーム・計画・実行のフロー、[[DefinedTerm/spec-driven-development]]、[[SoftwareApplication/superpowers]] と並ぶ。実装の前にレビュー済みの成果物を求める点で SDD と共通するが、その成果物は意図された振る舞いの仕様ではなく、既存のコードベースの読み込みに根ざした計画である——だからこそサーベイは、SDD を機能開発に位置づけるのに対し、RPI をブラウンフィールドの作業に位置づけている。
