ハーネスエンジニアリングとは、エージェントの失敗のほとんどはモデルの問題ではなく設定の問題であるという前提のもと、コーディングエージェントの設定ポイントを用いてその出力品質と信頼性を高める実践である。[[BlogPosting/skill-issue-harness-engineering-for-coding-agents]] はこの造語を Viv（Viv Trivedy）に帰し、Mitchell Hashimoto による定式化を引用している。「エージェントが誤りを犯すのを見つけたときはいつでも、そのエージェントが二度とその誤りを犯さないような解決策を作り込むために時間をかける」という考えだ、と。

その土台にある分解は `コーディングエージェント = AI モデル + ハーネス` であり、ハーネスとはエージェントのランタイムないし周辺装置——モデルが環境とやり取りするために使うもの——である。スキル、MCP サーバー、サブエージェント、メモリ、フック、コンテキストファイルはそれぞれ別個の概念だが、これらが単一の設定面を形づくっており、その面を設定することにこそ利用可能なレバレッジがある、というのがこの主張である。

## 用法

**コンテキストエンジニアリングの部分集合として。** HumanLayer の説明は、ハーネスエンジニアリングを [[DefinedTerm/context-engineering]] ——Dex Horthy の 12-factor agents の仕事に帰されるより広い用語——の内側に、とりわけエージェントのコンテキストウィンドウを管理するためにハーネスの設定ポイントを活用する部分として位置づける。そしてこの実践を、どんなプロンプトでも答えられない一連の問いに答えるものとして枠づける。エージェントに新しい能力をどう与えるか、学習データに含まれないコードベースについての事柄をどう教えるか、システムメッセージに `CRITICAL: always do XYZ` と書く以上の決定性をどう加えるか、特定のコードベースに合わせて振る舞いをどう適応させるか、そしてコンテキストウィンドウが速く膨らみすぎたり悪いコンテキストで膨らんだりするのをどう防ぐか、である。

**レバー。** この記事は Viv の2つの投稿を指し示す。1つ目はカスタマイズの4つのレバー——システムプロンプト、ツールと MCP、コンテキスト、サブエージェント——を枠づけるもので、2つ目はモデルがネイティブにはできないことから逆算して、各ハーネス構成要素がなぜ存在するのかを導くものだ。記事はこの4つに自前の2つを加える。自動化された統合と決定論的な制御フローのための**フック**と、知識の段階的開示のための**スキル**（Dex Horthy はこれを「命令モジュール」と呼ぶことを好む）である。複雑なブラウンフィールドのエンタープライズ規模のコードベースで難題を解いてきた数か月を経て、記事はとりわけ強力なレバーとして [[DefinedTerm/subagents]] を挙げる。そうした問題が要する多数のコンテキストウィンドウをまたいで一貫性を保つのが、まさにサブエージェントだからである。

**争点となる射程。** 記事は、OpenAI もこの主題について書いていると述べ、その立場を、エージェントのランタイムの*外側*にあるすべてを設定することとしてハーネスエンジニアリングを捉え、バックプレッシャーと検証機構に焦点を当てるものと読んでいる——ただし、その記事の本文で「harness」という語が現れるのは一度きりで、しかも eval に言及する文脈であることから、自分のその読み方には確信がないとも断っている。

**事後学習からの反論と、それへの応答。** フロンティアのコーディングモデルは自らのハーネス上で事後学習されているため、最良の設定とはモデルが学習した手つかずのものだ、という議論がありうる。記事はこの結合が実在することを認める——例として挙げられるのは、OpenCode が Codex のハーネスを模倣するために GPT/Codex 系モデル専用に `apply_patch` ツールを追加せざるをえなかった一方、Claude や他のモデルは通常の編集ツールと書き込みツールを使い続けている、というものだ——が、この結合は両刃だと論じる。モデルは自らのハーネスに*過適合*しうるのである。挙げられている証拠は Terminal Bench 2.0 についての Viv の観察で、Claude Code 上の Opus 4.6 は 33 位につけるが、事後学習で見ていないハーネスでは5位に達する（順位の誤差はおよそ上下4位）というものだ。

**完璧主義ではなく実践。** 記事が掲げるアプローチは、出荷する側に寄せ、予期された失敗ではなく実際に起きた失敗に応じてのみ設定を行うことである。うまくいかなかったことのリストは、その推奨と同じくらい具体的だ。実際の失敗にぶつかる前に理想の設定を前もって設計すること。念のためにと数十ものスキルや MCP サーバーを入れること。毎セッションの最後に5分間のテストスイートを走らせること。そしてどのサブエージェントがどのツールにアクセスできるかを細かく最適化すること——これはツールの取り違えを招き、結果を悪化させたと報告されている。逆にうまくいったのは、記事の説明によれば、シンプルに始めて実際の失敗のあとにだけ設定を追加すること、反復して役に立たなかったものは捨てること（著者は、使っているフックよりはるかに多くのフックを捨てたと報告している）、実戦で鍛えられた設定をリポジトリレベルの設定を通じてチームに配布すること、一発で成功することよりも反復の速さを最適化すること、そしてまずエージェントに広い能力を与え、必要が分かってから公開する範囲を削り込んでいくことである。

### 一つの文献群と、その切り分けられ方

この用語がいまや数編の記事ではなく一つの文献群を持つに至ったこと自体が観察可能である。`ai-boost/awesome-harness-engineering` は GitHub 上の CC0 ライセンスのキュレーションリストで、読み取り時点で 3.7k のスター数と 440 のフォーク数を持ち、自らを「信頼できる AI エージェントのハーネスを構築するためのキュレーションされたリソース、パターン、テンプレート」と説明し、この分野を7つのトップレベルのセクション——Foundations、Design Primitives、Reference Implementations、Security/Sandbox & Permissions、Evals & Verification、Templates、Production Infrastructure & Operations——に加えて隣接する awesome リストへのポインタとして整理している。

定義という目的にとって最も内容のある部分はその **Design Primitives** のセクションである。というのも、そこではハーネスが明示的に「ベンダーごとではなく、それが解く問題ごとに」12 の領域へと分解されているからだ。エージェントループ、計画とタスク分解、コンテキストの配送とコンパクション、ツール設計、スキルと MCP、権限と認可、メモリと状態、タスクランナーとオーケストレーション、検証と CI 統合、可観測性とトレーシング、デバッグと開発者体験、そしてヒューマン・イン・ザ・ループである。この分解は上記の6つのレバーより広く、実践者の説明が背景として扱っていた運用面の関心事——可観測性、デバッグ、タスクの実行——をハーネスの構成要素として加えている。

「ハーネスエンジニアリングとは何であり、なぜ重要なのかを定義する規範的なエッセイ」と説明されるその **Foundations** のセクションは、この用語が一者に属するのではなく複数の当事者によって並行して使われていることを示している。[[Organization/anthropic]]、[[Organization/openai]]、Google、Microsoft、Red Hat、LangChain、deepset、IBM、Meta によるこの名の下のエッセイが、学術的な仕事と並んで列挙され、[[Person/martin-fowler]] と [[Person/birgitta-bockeler]] による文章も含まれている。このリストはさらに、別のグループが維持しているエージェントハーネスエンジニアリングに関する学術サーベイと読書リストへのリンクも張っている。

これは議論ではなくキュレーションされた索引であり、各項目にはリストの維持者自身による1行の性格づけが付されている。リンクされた文書のいずれも本ウィキには取り込まれていないため、それらに由来する主張はこのページには記録されていない。このリストが直接に裏づけるのは、この分野の輪郭である。すなわち、ハーネスエンジニアリングがベンダー、学術、実践にまたがって書かれていること、そしてその下に目録化されている構成要素が設定を超えて運用にまで及んでいることだ。

### 前提を支える証拠と、それに付された警告

この実践は、モデルではなくハーネスがエージェントの振る舞いの多くを決めるという前提の上に立っており、上記の実践者たちの説明はそれを経験から主張している。[[ScholarlyArticle/dont-blame-the-large-language-model]] はその前提の統制されたテストを提供しており、その結果は両刃である。

この研究は構成上その前提を支持している。言語モデルを固定してハーネスだけを変え、ある CLI の 35 の連続したリリースにわたって測定すると、品質に測定可能なばらつきが生じる。これはハーネスが実際に仕事をしているのでなければ起こりえない。だが、そのばらつきの向きこそが警告である。これらのリリースを通じて、用いられたベンチマークタスクの解決率に統計的に有意な改善はなく、初期のバージョンが後のバージョンを上回ることさえあり、トークン消費量とツール呼び出し回数はそれに見合う利得なしにおよそ倍増した。機能重視のリリースは効率を犠牲にして解決率を買い、修正重視のリリースは解決率を買わずにコストを上げる。

これが欠けていると示唆する実践こそ、論文が**エージェンティック品質保証**と名付けるものである。すなわち、生成されたパッチが正しいかどうかだけでなく、トークン消費量とツール呼び出しのオーバーヘッドを含むエージェントの非機能的な品質を測るリグレッションテストだ。この欠落が実在することの証拠は、論文が記録している具体的な品質劣化のすべてが、当該プロジェクトの既存の自動チェックをすべて通過していたことである。上に挙げた「エージェントが二度とその誤りを犯さないような解決策を作り込む」という定式化と併せて読むなら、これは同じ規律を、ハーネスの利用者ではなくハーネスの開発者に向けたものである。バージョンをまたぐ測定なしには、ハーネスの変更はエージェントを改善するのと同じくらい劣化させうるのであり、しかもその劣化は従来のテストからは見えない。
