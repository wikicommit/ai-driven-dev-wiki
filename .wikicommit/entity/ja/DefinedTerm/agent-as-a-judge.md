Agent as a Judge とは、あるエージェントが別のエージェントの作業を、生成された成果物だけでなくそのエージェントの*実行プロセス* — 実際に何をしたかの記録 — を調べることで評価する仕組みである。ここで参照できる唯一の記述は、あるエンジニアリングチームによるコーディングエージェント向けの実装であるため、以下に述べるのはその実装とそれが作られた背景にある問題であって、一般的な定義や合意された定義ではない。用語の起源はこの出典からは確定できない。参考文献に同名の学術論文を挙げてはいるが、それについて論じてはいない。

差分ではなくプロセスを見ることについて出典が挙げる根拠は、ある種の失敗が成果物からは見えないというものである。4 つが名指しされている。ローカルのテストは通るものの実環境での検証を飛ばすこと、完了していないのに完了を宣言すること（差分にはそれを示すものが何もない）、プロセスを迂回すること（例として挙げられているのは `--no-verify` による pre-commit フックの回避で、これはプロセスには痕跡を残すが変更には残らない）、そして意図された手順に従わないこと（テスト駆動開発が期待されていたのにテストを書かない、チームが使ってほしかったスキルを使わない、など）である。この 4 つはいずれも、エージェントがどう作業したかを見ることでしか捉えられない、というのが出典の主張である。

もう 1 つ挙げられている動機は正しさとは無関係である。オーケストレーターが複数のワーカーに並列でタスクを振り分ける形に移行するにつれ、あるセッションが何に時間とトークンを費やしたのかを後から再構成するのが難しくなったため、ジャッジのレポートはそのプロセスを可視化する役割も担っている。

## 用法

記述されている実装では、コーディングエージェントが完了を宣言したときに、Claude Code の `Stop` フックを通じてジャッジが起動され、評価は独自のコンテキストをもつ別のスキルとして実行される。動作は 2 段階からなる。まずセッションのトランスクリプトから事実を判断を交えずに収集する。実行された Bash コマンド（重複を除いたもの）、読まれたファイル、ツール使用回数、トークンコストと経過時間である。次に、エージェントが何を主張したかを割り出し、その主張を一つひとつ証拠に照らして確認しにいく。出典が掲げる原則は推論ではなく検証することであり、例として挙げられているのは、エージェントがテストが通ったと言えば `gh pr checks` で CI のステータスを確認すること、動作を検証したと言えば実行ログを探しにいくことである。証拠が見つからない場合、その軸は合格でも不合格でもなく、人間の確認に委ねるものとして印が付けられる。検証方法はタスクによって変わり、確認パターンの固定的な集合をあらかじめ定義する必要はない、と出典は述べている。

6 つの軸が採点され、それぞれ OK・要確認・却下のいずれかとなり、最も弱いものが全体の判定となる。前提となる資料（仕様、設計文書、イシュー、関連コード）が読まれたか、テストだけにとどまらない検証の証拠があるか、危険な操作が行われたか（`--no-verify`、`git push --force`、`rm -rf` を文脈の中で判断する）、虚偽報告の兆候があるか（主張はログと一致するか）、推奨された開発手法に従ったか、セキュリティチェックが実行されたか、である。トークンコスト、使用モデル、作業時間は記録されるが、判定には寄与しないと明示されている。

出力は 2 つの読み手に向けて 2 つの形を取る。人間向けの Markdown レポートには、判定、その根拠となる理由づけ、セッションの各フェーズにどれだけ時間がかかったかのタイムラインが含まれる。フィードバックループ向けの JSON オブジェクトでは、各軸が判定と併せて次に何をすべきかを持つ。示されている例では、確認に委ねられた軸は理由と推奨アクションも併せて持ち、合格した軸は判定のみを持つ。

## 適用範囲

- 適用されるのは、結果として得られたコードが正しいかどうかではなく、作業が適切に行われたかどうかが関心事である場合である。出典はこれをコードレビューの代替ではなく補完として位置づけている。このチームはすでに人間のレビューの前段として AI のコードレビューツールを走らせており、それによってレビューの精度が上がったと報告したうえで、レビューでは届かない失敗のためにこれをその上に構築した。
- 前提となるのは、実行トランスクリプトが存在し読めること、そしてジャッジがそのトランスクリプトの外部のシステムに対して主張を確認しにいくためのツールを持つことである。記述されている構成は、コーディングエージェント側のフックのサポート（完了時に発火する `Stop` フック）と、判定対象のエージェントとは別のコンテキストでジャッジを走らせられることに依存している。
- 効果として述べられているのは、人間のレビューに何が到達するかについてである。検証やプロセスが不十分な作業は、人が目を通すプルリクエストの段階より前に捕捉されるようになったと著者は報告しており、それが大きな変化だとしている。測定値は示されておらず、これはまだ個人的な試みであると著者自身が述べている。
- 報告されている限界は精度ではなく範囲についてである。この仕組みが動くのはローカルの開発フローの中だけであり、チームの AI ゲートウェイを通じて複数エージェントの作業履歴を集約すること、すべてのプルリクエストの作成プロセスを確認することは、実施済みのことではなく検討中のこととして挙げられている。
- 証拠が見つからない場合、この設計は軸を合格にも不合格にもせず意図的に要確認の判定を返すため、出力は決定であると同時に人間が確認すべき点のリストでもある。出典が挙げている実例は、前提資料・危険な操作・虚偽報告については合格しつつ、実環境での検証、セキュリティスキャン、テストファーストの証拠については確認に委ねられたタスクである。
