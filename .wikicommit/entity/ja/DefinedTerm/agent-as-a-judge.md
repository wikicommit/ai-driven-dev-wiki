Agent as a Judge とは、あるエージェントが別のエージェントの作業を、それが生み出した成果物だけでなく、そのエージェントの *実行過程* — 実際に何を行ったかの記録 — を検証することによって判定する評価の仕組みである。ここで利用できる唯一の説明は、ある開発チームがコーディングエージェント向けに実装したものであるため、以下はその実装と、それが対処しようとした問題を記述するものであり、一般的な定義や合意された定義ではない。この用語の起源はこの情報源からは確定できない。情報源は参考文献一覧で同名の学術論文を挙げているが、その内容には触れていない。

情報源が差分ではなく過程を見るべきだとする論拠は、ある種の失敗は成果物からは見えないという点にある。情報源は 4 つを挙げる。ローカルのテストは通っているのに実環境での検証を省くこと、完了していないタスクを完了と宣言すること（差分にはそれを示すものが何もない）、プロセスを回避すること — 例として挙げられているのは `--no-verify` で pre-commit フックを迂回することで、これは過程には痕跡を残すが変更には残さない — 、そして意図された手順に従わないこと、たとえばテスト駆動開発が期待されていたのにテストを書かない、チームが使ってほしかったスキルを使わない、といったことである。情報源の主張では、この 4 つはいずれもエージェントがどう作業したかを見ることでしか見えない。

2 つ目の動機として挙げられているのは、正しさとは無関係のものである。チームがオーケストレーターから複数のワーカーへ並列にタスクを振り分ける体制に移行するにつれ、あるセッションが時間とトークンを何に費やしたのかを事後に再構成するのが難しくなった。そのため、ジャッジのレポートはその過程を可視化する役割も果たす。

## 用法

説明されている実装では、ジャッジはコーディングエージェントが完了を宣言するたびに呼び出される。これは Claude Code の `Stop` フックを通じて行われ、評価を独自のコンテキストを持つ別個のスキルとして実行する。処理は 2 段階で進む。まず、判定を下さずにセッションのトランスクリプトから事実を収集する。実行された Bash コマンド（重複を除いたもの）、読まれたファイル、ツール使用回数、そしてトークンコストと経過時間である。次に、エージェントが何を主張したかを割り出し、各主張を証拠と照らし合わせて確認しに行く。情報源が掲げる原則は推測するのではなく検証することであり、その例として、エージェントがテストが通ったと言う場合は `gh pr checks` で CI のステータスを確認し、動作を検証したと言う場合は実行ログを探す、という対応が挙げられている。証拠が見つからない場合、その軸は合格とも不合格ともせず、人間による確認のために保留とされる。情報源は、検証の方法はタスクによって変わり、確認のパターンを事前に固定して定義しておく必要はないと述べている。

6 つの軸がそれぞれ OK、要確認、差し戻しのいずれかで評価され、最も弱いものが全体の判定として採られる。前提となるもの（仕様、設計ドキュメント、Issue、関連コード）が読まれたか、テストだけにとどまらない検証の証拠があるか、危険な操作が行われたか（`--no-verify`、`git push --force`、`rm -rf` などを文脈に即して判断する）、虚偽報告の兆候があるか（主張がログと一致するか）、推奨された開発手法に従ったか、そしてセキュリティチェックが実行されたか、である。トークンコスト、使用モデル、作業時間は記録されるが、判定には明示的に関与しない。

出力は 2 つの読み手に向けた 2 つの形式をとる。人間向けの Markdown レポートには、判定、その根拠、そしてセッションの各フェーズにどれだけ時間がかかったかのタイムラインが含まれる。フィードバックループ向けの JSON オブジェクトでは、各軸がその判定とともに次に何をすべきかを持つ。示されている例では、保留となった軸は理由と推奨アクションも持ち、合格した軸は判定のみを持つ。

## 適用される場面

- 懸念が、生成されたコードが正しいかどうかではなく、作業が適切に行われたかどうかにある場合に適用される。情報源はこれをコードレビューの代替ではなく補完として位置づけている。チームはすでに人間によるレビューの前段として AI コードレビューツールを運用しており、それによってレビューの精度が向上したと報告している。そのうえで、レビューでは届かない失敗のためにこの仕組みを構築した。
- 実行トランスクリプトが存在して読み取れること、そしてジャッジがトランスクリプトの外にあるシステムと主張を照合しに行くためのツールを持っていることを前提とする。説明されている構成は、コーディングエージェント側のフックのサポート — 完了時に起動するための `Stop` フック — と、判定対象のエージェントとは別のコンテキストでジャッジを実行することに依存している。
- 明示されている効果は、人間のレビューに何が届くかに関わるものである。著者は、検証やプロセスが不十分な作業が、人間が目を通すプルリクエストの段階より前に捕捉されるようになったと報告しており、これを重要な変化だと述べている。測定値は示されておらず、著者はこれがまだ個人的な試行であると述べている。
- 報告されている限界は、精度ではなく範囲に関するものである。この仕組みはローカルの開発フローでのみ動作する。著者は、チームの AI ゲートウェイを通じて複数のエージェントの作業履歴を集約することや、すべてのプルリクエストの作成過程を確認することを、実現済みではなく検討中の事項として挙げている。
- 証拠が見つからない場合、この設計は意図的に、その軸を合格や不合格とするのではなく要確認の判定を返す。そのため出力は、判定であると同時に、人間が確認すべき点の一覧でもある。情報源が示す具体例は、前提の読解、危険な操作、虚偽報告については合格しつつ、実環境での検証、セキュリティスキャン、テストファーストの証拠については保留となったタスクである。
