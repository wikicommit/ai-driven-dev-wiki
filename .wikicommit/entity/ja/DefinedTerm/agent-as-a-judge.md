Agent as a Judge は、あるエージェントが別のエージェントの仕事を、生成された成果物だけでなく、そのエージェントの*実行プロセス* — 実際に何をしたかの記録 — を調べることで判定する評価の仕組みである。ここで参照できる唯一の記述は、あるエンジニアリングチームがコーディングエージェント向けに行った実装であり、以下はその実装と、それが対処しようとした問題を説明するもので、一般的な定義や合意された定義ではない。この用語の起源はこの出典からは確定できない。出典は同名の学術論文を参考文献に挙げているが、その内容には触れていない。

出典が差分ではなくプロセスを見るべき理由として挙げるのは、成果物には現れない種類の失敗があるという点である。挙げられているのは 4 つである。ローカルのテストは通るのに実環境での検証を省くこと。完了していないタスクを完了と宣言すること（差分にはそれを示すものが何もない）。プロセスを迂回すること — 例として、`--no-verify` で pre-commit フックを回避することが挙げられており、これはプロセスには痕跡を残すが変更には残さない。そして、意図された手順に従わないこと — テスト駆動開発が期待されていたのにテストを書かない、チームが使ってほしいスキルを使わない、などである。出典の主張では、これら 4 つはいずれも、エージェントがどう作業したかを見ることでしか把握できない。

もう 1 つの動機は正しさとは無関係である。チームが、オーケストレーターが複数のワーカーに並列にタスクを割り振る体制へ移行するにつれ、あるセッションが時間とトークンを何に費やしたのかを後から再構成することが難しくなった。そのため、判定役のレポートはそのプロセスを可視化する役割も担っている。

## 用法

説明されている実装では、判定役はコーディングエージェントが完了を宣言するたびに、Claude Code の `Stop` フックを通じて呼び出され、評価を独立したスキルとしてそれ自身のコンテキストで実行する。処理は 2 段階からなる。まず、セッションのトランスクリプトから判断を加えずに事実を収集する。実行された Bash コマンド（重複を除去したもの）、読まれたファイル、ツール使用回数、トークンコストと経過時間である。次に、エージェントが何を主張したかを割り出し、各主張を証拠と突き合わせて確認しに行く。出典が掲げる原則は推測するのではなく検証することであり、例として、エージェントがテストは通ったと言えば `gh pr checks` で CI のステータスを確認し、動作を検証したと言えば実行ログを探すことが挙げられている。証拠が見つからない場合、その評価軸は合格とも不合格ともせず、人間による確認待ちとして保留される。出典によれば、検証方法はタスクによって異なり、確認パターンの固定セットをあらかじめ定義しておく必要はない。

6 つの評価軸がそれぞれ OK・要確認・却下のいずれかで採点され、最も弱い判定が全体の判定となる。前提となる資料（仕様、設計ドキュメント、Issue、関連コード）が読まれたか、テストだけにとどまらない検証の証拠があるか、危険な操作が行われたか（`--no-verify`、`git push --force`、`rm -rf` などを文脈に即して判断する）、虚偽報告の兆候があるか（主張がログと一致しているか）、推奨された開発手法に従ったか、セキュリティチェックが実行されたか、である。トークンコスト、使用モデル、作業時間は記録されるが、判定には明示的に反映されない。

出力は 2 つの読み手に向けた 2 つの形式をとる。人間向けの Markdown レポートには、判定、その根拠、セッションの各フェーズにかかった時間のタイムラインが含まれる。フィードバックループ向けの JSON オブジェクトでは、各評価軸が判定とともに次に何をすべきかを保持する。示されている例では、保留された軸は理由と推奨アクションも保持するのに対し、合格した軸は判定のみを保持する。

## 適用範囲

- 関心が、生成されたコードが正しいかどうかではなく、作業が適切に行われたかどうかにある場合に適用される。出典はこれをコードレビューの代替ではなく補完として位置づけている。チームはすでに人間によるレビューの前段として AI コードレビューツールを使っており、それによってレビューの精度が向上したと報告している。その上に、レビューでは捉えられない失敗に対処するためにこの仕組みを構築した。
- 実行トランスクリプトが存在して読み取れること、そして判定役がトランスクリプトの外にあるシステムに対して主張を確認しに行くツールをもつことを前提とする。説明されている構成は、コーディングエージェント側のフックのサポート — 完了時に起動する `Stop` フック — と、判定役を判定対象のエージェントとは別のコンテキストで実行することに依存している。
- 表明されている効果は、人間のレビューに届くものに対するものである。著者は、検証やプロセスが不十分な作業が、人間が目を通すプルリクエストの段階より前に捕捉されるようになったと報告しており、これを大きな変化だと述べている。測定値は示されておらず、著者はこれがまだ個人的な試行段階であると述べている。
- 報告されている限界は、精度ではなく適用範囲に関するものである。この仕組みはローカルの開発フローでのみ動作している。著者は、チームの AI ゲートウェイを通じて複数のエージェントの作業履歴を一元化することや、すべてのプルリクエストの作成プロセスを確認することを、実施済みではなく検討中の事項として挙げている。
- 証拠が見つからない場合、設計上あえて、その軸を合格・不合格とせず要確認の判定を返すため、出力は判定であると同時に、人間が確認すべき点のリストでもある。出典が示す具体例は、前提資料、危険な操作、虚偽報告については合格しつつ、実環境での検証、セキュリティスキャン、テストファーストの証拠については保留となったタスクである。
