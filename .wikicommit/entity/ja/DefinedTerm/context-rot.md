コンテキストロットとは、モデルのコンテキストウィンドウ内のトークン数が増えるにつれて、そのコンテキストから情報を正確に想起する能力が低下するという観察である。[[TechArticle/effective-context-engineering-for-ai-agents]] はこの概念を、干し草の山から針を探す形式のベンチマーク研究に帰し、他より緩やかに劣化するモデルもあるものの、この性質はすべてのモデルに現れると述べている。これは、コンテキストウィンドウを、公称の上限まで埋めるべきバッファではなく、限界収穫が逓減する有限の資源として扱うことの背後にある経験的な前提である。

## 用法

Anthropic が挙げる説明はアーキテクチャに関わるものである。モデルは、新しいトークンごとに消費される「アテンション予算」を持つものとして説明され、これは限られた人間のワーキングメモリとの類比から引かれている。その希少性はトランスフォーマのアーキテクチャに遡る。そこではあらゆるトークンが他のあらゆるトークンにアテンションを向けうるため、n 個のトークンに対して n² の対関係が生じる——それゆえコンテキスト長が伸びるにつれ、それらの関係を捉えるモデルの能力は薄く引き伸ばされ、コンテキストの大きさとアテンションの焦点のあいだに緊張が生まれる。第二の原因として挙げられるのは訓練の分布である。短い系列は長いものより一般的であるため、モデルはコンテキスト全体にわたる依存関係の経験が少なく、そのための専用のパラメータも少ない。位置符号化の補間といった技術は、元々訓練された小さいコンテキストへ適応させることで、モデルがより長い系列を扱えるようにするが、トークンの位置の理解にいくらかの代償を払う。同記事はこの効果の形について慎重であり、硬い崖ではなく性能の勾配だと説明している。モデルは長いコンテキストでも高い能力を保つが、情報検索と長距離の推論において精度の低下を示す。

実務上の帰結は、コンテキストウィンドウを大きくすること自体は解決策ではない、ということである。Anthropic は、当面のあいだ、あらゆる大きさのコンテキストウィンドウは、エージェントの最も強い性能を求めるかぎり、コンテキストの汚染と情報の関連性の問題を免れないと論じている。

[[BlogPosting/context-engineering]] は同じ領域に、機構ではなく失敗モードの側から接近し、Drew Breunig の記述から四つの名前付きのパターンを伝えている。**コンテキストポイズニング**——幻覚がコンテキストに入り込むこと。**コンテキストの注意散漫（context distraction）**——コンテキストが訓練を圧倒すること。**コンテキストの混乱（context confusion）**——余計なコンテキストが応答に影響すること。そして**コンテキストの衝突（context clash）**——コンテキストの各部分が食い違うことである。同記事はこれらを、長いコンテキストのより平凡なコスト——ウィンドウの超過、コストとレイテンシの膨張——と並べて提示している。

Claude Code 自身のドキュメントは、この語を使わずに実務版を述べており、コンテキストウィンドウを管理すべき最も重要な資源と説明し、それが埋まりつつあるときモデルは以前の指示を「忘れ」はじめたり、より多くの誤りを犯したりしうると指摘している。

この語彙が増えるなかで保つに値する区別がある。コンテキストロットとは、*まだ存在している素材に対する*想起の劣化である。[[ScholarlyArticle/agentic-context-engineering]] は、素材そのものがそこに無くなるという、反対の形をした二つの失敗を名指ししている。[[DefinedTerm/context-collapse]]——モデルが蓄積されたコンテキストを丸ごと書き直すときに起きる急激な圧縮——と、**簡潔性バイアス（brevity bias）**——反復的な最適化が「短く一般的なプロンプトへ」向かい、ドメイン固有の詳細を落とし、その種の欠陥を反復をまたいで伝播させる、より緩やかな漂流である。一方に向けた対処は他方に効かない。ウィンドウを大きくしても、アテンションを改善しても、内容を削除してしまった要約には何もできないし、追記専用の更新規律は、本当に埋まったウィンドウでアテンションが薄まることには何もできない。

### エージェンティックな設定でこれを測る

上の説明が依拠する干し草の山から針を探す研究は、モデルに手渡された長い文章からの想起を測っている。[[ScholarlyArticle/loca-bench]] は、これはエージェントにとって問題を過小評価していると論じる。エージェントのコンテキストは与えられるものではなく、ほとんど何も知らない状態から環境を探索することでエージェント自身が組み立てるものだからである。その捉え直しは、「中核的な難しさは正しい証拠を一度見つけることだけでなく、コンテキストが時間とともに増大するなかで、あらゆる行動において整然と信頼できる状態を保ち続けることにある」というものである。

そのベンチマークである [[Dataset/loca-bench]] は、これを制御された測定へと変える。タスクのプロンプトと意味論を固定したまま*環境*——スプレッドシートの大きさ、PDF、データベース——を拡大することで、タスクを難しくすることなくコンテキスト長を任意に伸ばせるのである。報告される曲線は急峻である。ほとんどのモデルは短いコンテキストでは70% 以上を記録するが、その後「根底のタスクが変わらないにもかかわらず性能が急落する」のであり、それとともにフロンティアモデルとオープンソースモデルの差は広がる。

同研究はまた、想起という枠づけが一つに潰してしまう四つの失敗の次元を切り分けている。複数箇所からの検索と統合的な推論。指示の遵守——複数制約のタスクにおいてエージェントは「以前の指示をしばしば忘れる」。探索——コンテキストが伸びるにつれてエージェントは探索を減らし、より保守的に振る舞うと報告されている。そして幻覚——より長いコンテキストは事実の詳細の微妙な改変を生むと報告されている。さらに、コンテキストエンジニアリングの戦略が損失の相当部分を回復するが、それは不均等であり——フロンティアモデルのほうがオープンソースのものよりおおむね恩恵を受ける——それゆえこの種の測定が実際に測っているものの一部はスキャフォールドである、と報告している。

### ヒューリスティクスと証拠を分けて扱う

[[ScholarlyArticle/the-spec-growth-engine]] は、実務者の描像のどの部分が裏づけられているかについて異例なほど慎重である。実務者が高充填の領域を **Dumb Zone** と略称し、おおよそ40% のコンテキスト充填を過ぎたら慎重になり、最後の約60% を作業領域として扱わないという、しばしば引かれる経験則があることを記録し——そのうえで、これは証明された閾値ではなくコーディングエージェントの実践から来た経験則であり、正確な地点はモデルとタスクによると率直に述べている。

その根底の効果については研究によく裏づけられていると扱い、モデルが長いコンテキストを不均等に用い中央部からの検索が最も苦手であるという知見、入力が増えるにつれて品質が一貫して下がるという知見、そして長いコンテキストのコーディングに関して具体的には、ウィンドウが32K から256K トークンへ伸びるにつれてある強力なモデルがソフトウェアエンジニアリングのベンチマークで29% から3% へ落ちたという知見を引いている。掲げられる教訓は数値的というより方向的である。少なくてもよく選ばれたコンテキストのほうが、多いコンテキストに勝る。

同論文が挙げる、スコープの定まらないコンテキストの実務的な帰結は、統計的というよりアーキテクチャ的である。リポジトリ全体を与えられたエージェントは無関係なモジュールの関心事を混同し、変更を求められていない境界に触れる「グローバルな修正」を生み出す。そして名指しされる根本原因は、エージェントに対して、ちょうど一つのことだけを知ってよくそれ以上は知らなくてよいと伝える原理的な方法が存在しないことであり、開発者はすべてを与えるか推測するかの二択を強いられる。その答えが [[DefinedTerm/spine]] であり、これはスコープをアーキテクチャから導出する。

### 100万トークン世代がどれだけの余裕を買ったか

[[BlogPosting/survey-of-development-workflows-in-the-coding-agent-era]] は、2026年3月時点でこの問題がどこにあるかについての実務者の読みを示している。中核的な知見——入力コンテキスト長が伸びるにつれて出力の品質が測定可能なほど劣化し、トークンの上限に達するはるか前から性能が連続的に低下すること——を、Chroma Research と Morph を引いて言い直している。そのうえで何が変わったかを記録している。Claude（Opus 4.6 と Sonnet 4.6）と Codex は100万トークンのコンテキストウィンドウに対応し、Opus 4.6 は MRCR v2 で78.3% を記録した。同記事はこれを長いコンテキストの検索に関するフロンティアモデル中の最高スコアと説明している。掲げられる結論は慎重である。コンテキストロットは消えていないが、実務上の余裕は大きく広がった。

その拡大によっても実務的な助言は変わらない。セッションは短く保ち、タスク1つにつきセッション1つを原則とし、フェーズの境界ごとに新しく始めること。調査と探索は [[DefinedTerm/subagents]] へ委ね、メインのコンテキストが汚染されないようにすること。[[DefinedTerm/compaction]] を恐れないこと。そして「念のため」にファイルを読み込まないこと。まとめて読み込むのは逆効果だからである。同記事自身のこの選択の枠づけでは、セッションを短く保つか、長いウィンドウを意図的に活かすかはタスクによる——100万コンテキストは Codex では明示的に有効化でき、ある Claude Code のプランでは Opus 4.6 に対して既定で動作し、環境変数で無効化できる、と指摘している。
