YOLO モードとは、コーディングエージェントがコマンドを 1 つ実行するたびに立ち止まって確認を求めるのではなく、そのコマンドがすべてデフォルトで承認される動作モードである。この名前は、これらのツールがそれぞれ独自の形で提供しているこの設定を指して、Simon Willison が好んで使うと述べている呼び名である。情報源におけるこのモードの意義は、トレードオフの両側に同時に位置している点にある。*非常に危険*であると同時に、最も生産的な結果を得るための鍵でもあると説明されているのである。エージェントは反復によって問題を解決するが、コマンドごとの承認はその反復を止めてしまうからだ。

## 用法

このモードは、[[DefinedTerm/designing-agentic-loops]] を可能にする条件として論じられている。エージェントは本質的に危険なものとして特徴づけられる。まずい判断を下すこともあれば、[[DefinedTerm/prompt-injection]] の犠牲になることもある。そしてコーディングエージェントが持つ最も強力なツールはシェルでのコマンド実行であるため、道を踏み外したエージェントは、その操作者が自らコマンドを実行してできることなら何でもできてしまう。これに対するデフォルトの対応は承認プロンプトであり、情報源がそれに対して抱く不満は、それが面倒だということではなく、エージェントを有用にしている力任せの反復を鈍らせてしまうということである。

このモードで無人のまま実行する場合のリスクとして 3 つが挙げられている。重要なものを削除したり壊したりするシェルコマンド、エージェントから見えるファイルやデータを盗み出す持ち出し攻撃（とくにソースコードと環境変数内のシークレットが狙われやすいとされる）、そして、サービス妨害のためであれ、他の攻撃の発信元を偽装するためであれ、マシンを第三者を攻撃するためのプロキシとして使われることである。

これらに対して 3 つの選択肢が示されている。1 つ目は、エージェントが到達できるファイル、シークレット、ネットワークを制限する安全なサンドボックスである（[[DefinedTerm/sandboxing]] を参照）。情報源は、コンテナエスケープが存在することを指摘しつつも、Docker や Apple のコンテナツールを多くの人にとって妥当なリスクだと判断している。2 つ目は、他人のコンピュータを使うことであり、これによって暴走したエージェントの影響範囲が限定される。これは著者自身が好む方法であり、彼はその実例として GitHub Codespaces を挙げ、最悪の場合でも、チェックアウトされたコードの持ち出しや、接続されたリポジトリへの悪いコードのプッシュにとどまるとしている。3 つ目は単にリスクを受け入れることであり、情報源によれば、ほとんどの人が選んでいるのはこれである。
