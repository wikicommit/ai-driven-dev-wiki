バイブエンジニアリングは、[[DefinedTerm/vibe-coding]] の規律ある対応物を指す語である。[[ScholarlyArticle/vibe-coding-ai-native-paradigm]] の説明によれば、2025年10月に [[Person/simon-willison]] が造語したもので、経験あるエンジニアが LLM を、自動テスト、計画、ドキュメント、コードレビューといったベストプラクティスと組み合わせ、保守可能で本番品質のソフトウェアを生み出すことを促す。

## 用法

この語は、Willison がバイブコーディングと AI 支援プログラミング全般の間に引く区別から生まれた。彼の見立てでは、生成された一行一行を注意深くレビューし理解する開発者は、そもそもバイブコーディングをしていない。バイブエンジニアリングは、この区別が余地を残す、意図的でエンジニアリングの規律を伴うコーディングエージェントとの働き方に名前を与える。

[[BlogPosting/vibe-engineering]] における Willison 自身の説明は、この語を用語上の空白を埋めるものとして枠づける。AI でソフトウェアを作ることの、速く、ゆるく、無責任な側にはバイブコーディングという語が定着した一方、もう一方の端——「熟練した専門家が LLM で自らの仕事を加速させながら、自分が生み出すソフトウェアに対して誇りをもって確信をもって説明責任を負い続ける」側——には名前がなかった。彼はこれを「半分だけ冗談めかして」提案し、この働き方が *難しい* ことを強調する。エージェントが動くコードを吐き出す速さは、人間の参加者に求められる水準を下げるどころか上げるのである。

彼の中心的な主張は、LLM が既存の一流のエンジニアリングの実践を積極的に報いる、というものだ。彼が挙げる一覧は次のとおり。

- **自動テスト** — 堅牢で網羅的かつ安定したテストスイートがあれば、エージェンティックなツールは「飛べる」。テストがなければ、エージェントはテストもせずに何かが動くと主張しかねないし、無関係な機能が気づかれずに壊れうる。彼は、ループの中で反復するエージェントにはテストファーストの開発がとりわけ有効だと指摘する。
- **事前の計画** — まず高水準の計画を反復して練り、それからエージェントに渡す。
- **網羅的なドキュメント** — LLM はコードベースの一部しかコンテキストに保持できないため、関連するドキュメントを渡せれば、コードを先に読まなくても他の領域の API を使える。
- **良いバージョン管理の習慣** — 元に戻せること、そして何がいつ変わったのかを理解できることは、その変更をエージェントが行った場合にいっそう重要になる。彼は LLM を「Git については恐ろしく有能」であり、`git bisect` については大半の開発者より上手だと説明する。
- **効果的な自動化** — CI、自動整形とリント、プレビュー環境への継続的デプロイ。
- **コードレビューの文化** — 自分でコードを書くほうを好むのではなく、レビューを素早く生産的にこなせること。
- **非常に奇妙な形のマネジメント** — 明確な指示、十分な文脈、実行可能なフィードバックを与えること。彼はこれによって、既存のマネジメントの経験が驚くほど役立つようになると述べる。
- **本当に優れた手動 QA** — エッジケースを予測し、掘り下げることを含む。
- **強い調査力** — 多数のアプローチのうちどれが最良かを見極めること。彼はこれがエージェントを解き放つうえで依然としてボトルネックだと述べる。
- **プレビュー環境への出荷** — レビューを生産的にし、壊れたものを出荷するリスクを減らす。
- **何を AI に外注でき、何を手作業で扱うべきかの勘** — 彼は、これがツールの改善とともに変わり続けると指摘する。
- **更新された見積もりの感覚** — AI 支援のコーディングはこれを容易にするどころか難しくする。かつての所要時間はもはや通用せず、新しい要因はまだ整理の途上だからである。

これが総体として何を意味するかについての彼の要約は、エンジニアはいまや「アプローチを調査し、高水準のアーキテクチャを決め、仕様を書き、成功基準を定義し、エージェンティックなループを設計し、QA を計画し、隙あらば必ずズルをする奇妙なデジタルのインターンの増え続ける軍団を管理し、そして *コードレビューにものすごく多くの時間を費やしている*」というものであり、そしてこれらのほとんどはすでにシニアエンジニアの特徴である。そこから彼が引く主張は、AI ツールは既存の専門性を増幅するというものだ。エンジニアが持つスキルと経験が多いほど、その結果は速く、良くなる。

Willison はこの名前を、明白な反論に対しても擁護している。おそらくばかげた名前であり、AI の概念としての「バイブ」にはもう飽きが来ていることを認めつつ、この語がバイブコーディングとの明確な区別を打ち立て、より難しくより洗練された働き方を示すと論じる。彼は「コーダー」と「エンジニア」の人為的な区別を好んだことがなく、それをゲートキーピングと結びつけてきたと述べる——「しかしこの場合、少しばかりのゲートキーピングこそ、まさに我々に必要なものだ」。

Bamil の論文は、バイブコーディングについて同論文が同定する特定の問題への是正として、この語を2度持ち出している。保守性とデバッグの項では、バイブコーディングによって生み出されたコードは確立されたアーキテクチャのパターンに従わないことがあり、他人が理解しにくくなりうると論じ、バイブエンジニアリングが唱えるように、テスト、ドキュメント、モジュール的な設計といったソフトウェアエンジニアリングのベストプラクティスをエージェンティックなワークフローに統合することで、これを緩和できるとしている。その結論は、バイブコーディングが最終的に、実験的なプロトタイピングから規律あるバイブエンジニアリングまでにわたる実践のスペクトルへ発展しうると示唆している。

## 関連用語

同論文は、バイブコーディングとバイブエンジニアリングをめぐる進行中の議論を、この領域における明確な用語と責任ある実践の必要性を際立たせるものだと特徴づけている。

[[DefinedTerm/agentic-engineering]] は、スペクトルの実質的に同じ規律ある端に対して別途提案された語であり、別の著者がこの語を参照することなく、重なり合う原則の集合にたどり着いたものである。その到来がこの実践を必要にしたと Willison が評するツールは [[DefinedTerm/coding-agent]] で、働き方のモードは [[DefinedTerm/agentic-coding]] で、同じ規律へ至る一つの構造化された道は [[DefinedTerm/spec-driven-development]] で扱われている。
