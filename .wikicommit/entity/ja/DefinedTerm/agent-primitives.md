エージェントプリミティブとは、AI エージェントに特定の能力やルールを 1 つ提供する、シンプルで再利用可能なファイルまたはモジュールである。この用語は [[BlogPosting/how-to-build-reliable-ai-workflows-with-agentic-primitives-and-context-engineering]] において、3 層フレームワークの中間層として提案された。下層に Markdown によるプロンプトエンジニアリング、上層にコンテキストエンジニアリングを置くこのフレームワークの目的は、場当たり的なプロンプティングを再現可能な実践に変えることだとされている。プリミティブはごく普通の Markdown ファイルであり、それに付随する主張は、タスクごとに完璧なプロンプトを手で書くことは持続不可能なので、プロンプトを機能させる技法をファイルとしてコミットしておくべきだ、というものである。

出典が挙げるのは 6 種類のファイルで、それぞれ独自の接尾辞とスコープを持つ。対象範囲を絞ったモジュール式のガイダンスのための `.instructions.md`、そのモードが使用できる MCP ツールによって範囲が限定された役割ベースの専門性のための `.chatmode.md`、検証が組み込まれた再利用可能なワークフローのための `.prompt.md`、すぐに実装に移せる設計図のための `.spec.md`、セッションをまたいで保持される知識のための `.memory.md`、情報取得を高速化する補助のための `.context.md` である。出典は、VS Code が最初の 3 つをネイティブにサポートしていると述べ、残りの 3 つは自らのフレームワークが追加するパターンとして提示している。

## 用法

プリミティブは 1 つずつ使うのではなく、組み合わせて使うことを想定している。出典の作業例では、安全なユーザー認証を実装するという依頼を一連のプリミティブ全体に通している。まず `backend-dev` チャットモードが選択され、これが `applyTo: "auth/**"` パターンによって `security.instructions.md` を自動的に起動する。続いて `.memory.md` のセクションと `.context.md` ファイルからコンテキストを読み込み、構造化テンプレートから `user-auth.spec.md` を生成し、検証ゲートを備えた `implement-from-spec.prompt.md` ワークフローを実行する。このように複数のプリミティブを調整する `.prompt.md` ファイルを、出典はエージェント型ワークフロー（agentic workflow）と呼び、それが IDE、ターミナル、CI パイプラインのいずれでも同じように動作するよう設計されていると述べている。

この構成で主要な役割を担うのは 2 つの設計上の慣習である。1 つは、指示を 1 つの大きなファイルにまとめるのではなくモジュール式に保ち、`applyTo` フロントマターのパターンによって、該当するパスに対してのみファイルを有効にすることである。出典はこれを、作業そのもののためにコンテキスト空間を確保する [[DefinedTerm/context-engineering]] の施策として位置づけている。もう 1 つは、チャットモードにそのドメインが必要とする MCP ツールだけを与えることである。出典はこれを、集中を保つ施策であると同時にセキュリティ境界でもあるものとして示し、専門職の資格になぞらえている。建築家は設計をするが、施工はしない、というわけである。出典が挙げるモードは、アーキテクト、フロントエンドエンジニア、バックエンドエンジニア、テクニカルライターであり、それぞれに何ができて何ができないかが明示されている。

出典は、指示、チャットモード、再利用可能なプロンプト、仕様テンプレートの順という決まった順序で構築することを推奨しており、意図する見返りを蓄積として説明している。失敗は `.memory.md` に記録され、うまくいくパターンは `.instructions.md` に文書化され、ワークフローは `.prompt.md` で洗練されていく。出典はこれを複利的な知性（compound intelligence）と呼んでいる。

## 適用される場面

この実践が当てはまるのは、同じ種類の AI 支援タスクが繰り返し発生し、そのたびにプロンプトを導き直すのが無駄になる場合であり、かつ複数の人がエージェントから同じ振る舞いを必要とする場合である。前提として、エージェントがリポジトリから指示ファイルを読み込むことが必要である。出典の例は VS Code の GitHub Copilot 向けに書かれており、ファイルは `.github/instructions/`、`.github/chatmodes/`、`.github/prompts/` 配下に置かれる。また、フレームワークのうちスケーリングに関する半分については、エディタの外でプロンプトファイルを実行できるエージェント CLI ランタイムが前提となる。

どのように失敗するかは、第 3 層が解決するために存在する問題として間接的に述べられている。優れたプリミティブであっても、無関係なコンテキストがモデルの限られたアテンションを奪い合えば失敗する。だからこそ出典は、ファイルだけで十分とはみなさず、セッションの分割、スコープを絞った指示、モードの境界とそれらを組み合わせている。`applyTo` の仕組みは指示ファイルがあらゆる場所に適用されるのを防ぐものであり、1 つの巨大な指示ファイルに対する出典の警告は、出典が直接名指ししている誤用である。

この実践がどの程度確立されているかについて言えば、これは 2025 年 10 月に GitHub のブログで公開された一人の著者による提案であり、出典はその評価を何も報告していない。6 種類のファイルのうち 3 つは、VS Code がネイティブに認識するフォーマットではなく、著者のフレームワークが導入した慣習である。また、それらを配布するために出典が提案するツール（[[SoftwareApplication/apm-agent-package-manager]]）も同じ著者のプロジェクトである。同様のニーズに取り組む他のファイルベースの慣習については、[[DefinedTerm/agents-md]] と [[DefinedTerm/agent-skills]] を参照のこと。
