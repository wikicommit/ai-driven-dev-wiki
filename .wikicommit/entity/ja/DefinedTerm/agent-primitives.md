エージェントプリミティブとは、AI エージェントに 1 つの特定のケイパビリティやルールを提供する、単純で再利用可能な
ファイルまたはモジュールである。この用語は
[[BlogPosting/how-to-build-reliable-ai-workflows-with-agentic-primitives-and-context-engineering]]
で、3 層フレームワーク — 下に Markdown によるプロンプトエンジニアリング、上にコンテキストエンジニアリング — の中間層
として提案されたもので、その掲げる目的は場当たり的なプロンプティングを反復可能な実践へと変えることである。プリミティブ
はごく普通の Markdown ファイルであり、それに付随する論は、タスクごとに完璧なプロンプトを手で書くのは持続可能ではない
のだから、プロンプトを機能させている技術のほうをファイルにコミットすべきだ、というものである。

ソースが挙げるのは 6 つのファイル種別で、それぞれに独自のサフィックスとスコープがある。対象を絞ったスコープをもつ
モジュラーなガイダンスのための `.instructions.md`、モードが使ってよい MCP ツールによって境界づけられた役割ベースの
専門性のための `.chatmode.md`、検証を組み込んだ再利用可能なワークフローのための `.prompt.md`、実装可能な設計図のための
`.spec.md`、セッションをまたいで保たれる知識のための `.memory.md`、そして情報検索を速めるヘルパーのための
`.context.md` である。ソースは、VS Code が最初の 3 つをネイティブにサポートしていると述べ、残る 3 つは自身の
フレームワークが加えるパターンとして提示している。

## 用法

プリミティブは 1 つずつ使うものではなく、組み合わせて使うことが意図されている。ソースの実例は、安全なユーザー認証を
実装するという要求を一式全体に通していく。`backend-dev` チャットモードが選択され、それが `applyTo: "auth/**"` パターン
を介して `security.instructions.md` を自動的に発火させ、それが `.memory.md` のセクションと `.context.md` ファイルから
コンテキストを読み込み、構造化テンプレートから `user-auth.spec.md` を生成し、検証ゲートを備えた
`implement-from-spec.prompt.md` ワークフローを実行する。このようにして複数のプリミティブを協調させる `.prompt.md`
ファイルこそ、ソースがエージェント的ワークフローと呼ぶものであり、これらは IDE でもターミナルでも CI パイプラインでも
同じように走るよう設計されていると述べられている。

その組み立てにおいて重みの大半を担っているのは 2 つの設計上の慣習である。インストラクションは 1 つの大きなファイルに
まとめるのではなくモジュラーに保たれ、`applyTo` のフロントマターパターンによって、一致するパスに対してのみファイルが
有効になる — ソースはこれを [[DefinedTerm/context-engineering]] の施策として位置づけ、コンテキストの空間を作業そのもの
のために温存するのだとしている。チャットモードには、その領域が必要とする MCP ツールだけが与えられる。ソースはこれを
集中のための施策であると同時にセキュリティの境界としても提示し、職能の免許にたとえている。アーキテクトは建てるのでは
なく計画するのだ、というわけである。挙げられているモードはアーキテクト、フロントエンドエンジニア、バックエンド
エンジニア、テクニカルライターで、それぞれに何ができて何ができないかが明示されている。

ソースはこれらを決まった順序で — インストラクション、次にチャットモード、次に再利用可能なプロンプト、次に仕様テンプレート
と — 作っていくことを勧め、意図された見返りを蓄積として説明している。失敗は `.memory.md` に捉えられ、うまくいった
パターンは `.instructions.md` に文書化され、ワークフローは `.prompt.md` で洗練される。ソースはこれを複利的な知性
（compound intelligence）と呼んでいる。

## 適用される場面

この実践が当てはまるのは、同じ種類の AI 支援タスクが十分に繰り返し現れ、毎回プロンプトを導き直すのが無駄になる場面、
そして複数の人が同じ振る舞いをエージェントに求める場面である。前提となるのは、そもそもリポジトリからインストラクション
ファイルを読むエージェントであること — ソースの例は VS Code の GitHub Copilot 向けに書かれており、ファイルは
`.github/instructions/`、`.github/chatmodes/`、`.github/prompts/` の下に置かれる — であり、フレームワークのうち
スケールに関わる半分については、エディタの外でプロンプトファイルを実行できるエージェントの CLI ランタイムである。

どう失敗するかは、第 3 の層が解決するために存在する問題として間接的に述べられている。よいプリミティブであっても、
無関係なコンテキストがモデルの限られた注意を奪い合えばやはり失敗する。だからこそソースはこれらを、ファイルだけで十分と
みなすのではなく、セッションの分割、スコープを絞ったインストラクション、モードの境界と組み合わせている。`applyTo` の
機構はインストラクションファイルがどこにでも適用されてしまうのを防ぐものであり、1 つの巨大なインストラクションファイル
に対するソースの警告は、直接名指しされた誤用である。

この実践がどれだけ定着しているかについて。これは 1 人の著者の提案であり、2025 年 10 月に GitHub のブログで公開された
もので、ソースはそれに対する評価を何も報告していない。6 つのファイル種別のうち 3 つは、VS Code がネイティブに認識する
フォーマットではなく著者のフレームワークが導入する慣習であり、ソースがそれらの配布のために提案しているツール —
[[SoftwareApplication/apm-agent-package-manager]] — は同じ著者のプロジェクトである。同様のニーズに応える他のファイル
ベースの慣習については [[DefinedTerm/agents-md]] と [[DefinedTerm/agent-skills]] を参照。
