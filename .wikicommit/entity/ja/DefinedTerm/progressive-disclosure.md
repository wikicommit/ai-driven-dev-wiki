段階的開示とは、すべてを最初からコンテキストウィンドウに置くのではなく、エージェントが情報を必要になるにつれて段階的に読み込むようにするプラクティスである。Anthropic のドキュメントは、これをファイルシステムベースの [[DefinedTerm/agent-skills]] アーキテクチャが可能にする特性として提示し、その目的を率直に述べている。すなわち、どの時点においても関連する内容だけがコンテキストウィンドウを占めるようにすることである。同じベンダーによるこのフォーマットのエンジニアリング解説（[[BlogPosting/equipping-agents-for-the-real-world-with-agent-skills]]）はさらに踏み込み、これをフォーマットを柔軟かつスケーラブルにする中核的な設計原則と呼んで、目次から始まり、次に個別の章、最後に詳細な付録へと続く、よく整理されたマニュアルにたとえている。

## 用法

このフォーマットについて文書化されているとおり、この戦略は 3 つの段階で実現される。**メタデータ**、すなわち Skill の YAML フロントマターにある `name` と `description` は常に読み込まれ、起動時にシステムプロンプトに含まれる。そのコストは Skill あたりおよそ 100 トークンとされる。この 2 つのフィールドのうち、ドキュメントは、Skill を起動するかどうかを決める際にリクエストと照合されるのは `description` であるとしている。**指示**、すなわち `SKILL.md` の本文は、リクエストが一致したときに初めてファイルシステムから読み込まれ、その予算は 5,000 トークン未満とされる。**リソース**、すなわち追加の Markdown ファイル、参考資料、実行可能なスクリプトは、アクセスされるまでコストがかからない。参照ファイルは読み込まれた時点でコンテキストに入り、スクリプトはその出力だけがコンテキストに寄与する。

エンジニアリング記事は、同じ 3 つの段階を 1 つのリクエストを通してたどっている。コンテキストウィンドウは、中核となるシステムプロンプト、インストールされたすべての Skill のメタデータ、ユーザーのメッセージから始まる。次にエージェントは、Bash ツールを呼び出して関連する Skill の `SKILL.md` を読むことで、その Skill を起動する。さらに同梱されている別のファイル（記事の例では、PDF の Skill と一緒に配布されている `forms.md`）を読むことを選び、そうして初めてタスクに取りかかる。3 段階目のファイルを読むという判断は、直前に読み込んだ指示がそのファイルに言及しているために、エージェント自身が下すものとして説明されている。

文書化されている帰結は、この段階化から導かれる。起動されていない Skill が占めるのは名前と説明だけなので、多数の Skill をコンテキスト上の不利益なしにインストールできる。1 つの Skill が数十の参照ファイルを同梱していても、あるタスクで読み込まれるのは必要な 1 つだけであり、残りはコストゼロのままディスク上にとどまる。また、コードそのものが決してコンテキストウィンドウに入らないため、スクリプトはモデルに同等のコードを生成させるよりも効率的である。ドキュメントの例は、寄与するのが短い合格メッセージかエラーメッセージだけの検証スクリプトであり、エンジニアリング記事の例は、スクリプトも PDF も読み込まれることなく、PDF を読んでそのフォームフィールドを抽出するスクリプトである。ファイルシステムとコード実行を備えたエージェントは Skill を全部読む必要がないため、同記事は、1 つの Skill に同梱できる素材は事実上無制限であると述べている。

## 適用される場面

この戦略が当てはまるのは、大量の指針や参考資料が存在するものの、あるタスクに関係するのはそのごく一部だけである場合である。この戦略は 2 つのことを前提とする。1 つは、常に読み込まれる安価な要約だけで高価な部分が必要かどうかを判断できるように素材を分割できること。もう 1 つは、エージェントが残りをオンデマンドで取得できること（文書化されている事例では、シェルコマンドで読めるファイルシステム）である。

この戦略の失敗モードは、1 つ目の前提にある。常に読み込まれる説明が、残りを読み込むかどうかを決める唯一の根拠であるため、素材が何をするのかと、いつ使うべきなのかの両方を述べていない説明では、より深い段階に実際には到達できなくなる。同じドキュメントが、まさにこの理由から、両方を記述することをこのフィールドの要件としている。エンジニアリング記事も作成者の側から同じ結論に達しており、エージェントが Skill を起動するかどうかを判断する際に使うのは `name` と `description` であるため、そこに特に注意を払うよう助言している。

この戦略が作成者に求める判断は、どこで分割するかである。同記事の指針は長さを分割のきっかけとしており、`SKILL.md` が扱いにくくなったら、参照される別ファイルに分割せよとする。さらに、コンテキストが互いに排他的であるか、一緒に使われることがまれである場合には、それらの経路を分けておくことでトークン使用量が減るとも付け加えている。分割を促すのは大きさであり、どの素材が一緒に必要とされるかが分割の位置を決める。

どの程度確立されたものかについて言えば、ここには独立した 2 つの説明があり、両者は性質が異なる。一方は、あるベンダーが自社のフォーマットについて記したドキュメントとエンジニアリング記事であり、3 段階の構成とそのトークン予算を示しているが、この戦略の効果の測定は報告していない。もう一方の OpenDev のレポートは測定を示しているが、そうした段階化されたフォーマットはもたず、それ自体も統制された比較ではなく、単一のシステムについて作者自身が書いた設計レポートである。どちらの説明も、この戦略の一般的な評価ではない。

## もう 1 つの実現形

この戦略は、ドキュメントのフォーマットに縛られるものではない。[[ScholarlyArticle/building-effective-ai-coding-agents-for-the-terminal]] は同じ段階化をエージェントの *ツール* に適用し、その数値を報告している。このレポートは問題をトークンの観点から捉えている。スキーマが平均 200 トークンの外部ツールを 100 個もつシステムは、ツール定義だけで 2 万トークンを費やすことになるため、すべてのスキーマを含めるのは無駄が多いが、外部ツールを除外すればエージェントにできることが制限される。[[SoftwareApplication/opendev]] の答えは遅延発見である。コンテキストは外部ツールのスキーマをゼロの状態で始まり、エージェントは `search_tools` ツールを呼び出す。このツールは登録されたツールの名前と説明をキーワードクエリに照らして採点し、一致したものを返す。そのスキーマがその後の呼び出しに含まれるようになる。3 つの詳細度レベルにより、エージェントは結果にどれだけのコンテキストを費やすかを選べ、修飾名でツールを呼び出せば、事前の検索なしにそのツールが発見される。レポートによれば、すべての外部スキーマを先行して含めていた場合には、最初のユーザーメッセージより前にコンテキストの最大 40% が消費されていたが、遅延発見によってこのベースラインは 5% 未満になり、実際に機能が使われるにつれてのみ増加するようになった。

このレポートは、自らの Skill にも同じ 2 段階の扱いを適用している。起動時には名前、説明、起動条件からなるメタデータのインデックスを読み込み、完全な内容は呼び出されたときにのみ読み込む。そしてこのパターンを教訓として一般化し、先行読み込みは規模が大きくなると破綻し、どちらの場合も答えは、起動時にメタデータのインデックスを読み込み、完全な内容の読み込みは使用時点まで遅らせることだとしている。同レポートが挙げるトレードオフは、文書化されたフォーマットにも暗黙のうちに含まれているものである。発見には追加の往復が 1 回かかり、これは利用可能な項目のうち少数しか使わないワークフローでは元が取れるが、多数を使うワークフローでは、上限はあるものの積み重なっていく。
