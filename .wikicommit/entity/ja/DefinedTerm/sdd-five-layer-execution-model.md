SDD の 5 層実行モデルは、[[DefinedTerm/spec-driven-development]]（SDD）を構造化する方法の 1 つであり、深蓝居ブログの中国語の記事（2026 年 2 月）で説明されている。同記事はこれを SDD の「骨格」として提示している。すなわち、各層が定義された入力、出力、責務を持ってその下の層を制約する上から下への連鎖であり、これによって仕様の権威が、意図から実装、検証、ガバナンスに至るまでシステム全体を貫くようにする。5 つの層は、下から順に、**仕様層**（宣言的な意図 — API モデル、メッセージ契約、ドメインパターン、ポリシー制約）、**生成層**（言語横断のコード、型定義、SDK など、意図を実行可能な形に変換する）、**実行層**（人間が統制する骨格アーキテクチャと AI が生成するビジネスロジックからなる実行時の実装）、**検証層**（契約テスト、スキーマ検証、仕様からのドリフトの阻止）、そして**ガバナンス層**（バージョン管理、セキュリティポリシー、仕様をどう進化させるかについてのヒューマン・イン・ザ・ループの意思決定）である。

## 用法

同記事は、ユーザー登録インターフェースを例にこれらの層を順にたどっている。仕様層はリクエストとレスポンスの形式、エラーコード、セキュリティ要件を定義する。生成層は対応する Go の構造体、API ドキュメント、クライアント SDK を生成する。実行層では AI がビジネスロジックを書き、人間がコアアーキテクチャを担う。検証層はコードを仕様と継続的に比較し、逸脱があればアラートを発する。そしてガバナンス層は、仕様のバージョンアップ、権限管理、重要な変更に対する人間のレビューを扱う。生成層の例として、同記事は OpenAPI スキーマが oapi-codegen のようなコードジェネレーターによって Go の型に変換される様子を示している。

このモデルは、同記事がアーキテクチャ的決定性（architectural determinism）と呼ぶもの — コードではなく仕様こそが最高の権威であり、実装は常にそれに合わせ続けなければならないという考え方 — に立脚している。同記事がそのための手法として挙げるのはドリフト検出であり、これによってアーキテクチャは設計時の文書から実行時の制約へと変わる。
