AI コーディングエージェントとは、大規模言語モデルを動力とし、コードベースに対して自律的に行動できるソフトウェアのことである。人が次に何を打つべきかを提案するだけにとどまらず、ファイルを読み、周囲の文脈を理解し、コードを書いたり編集したりし、コマンドを実行し、テストを走らせ、観測した結果をもとに反復する。もう 1 つの説明は、その定義の線をたった 1 つの能力へと狭めている。コーディングエージェントとはコードを*書くことと実行することの両方*ができるエージェントであり、モデルを使ってコードを生み出す他のどんなやり方からもそれを分かつのは実行である、というものである。

## 用法

定義づけとなる性質は自律性である。エージェントは次の 1 行を予測するのではなく、ループの中で動作し、タスクが終わるまで行動を起こしては結果を観測する。ファイルを作り、import が足りないことに気づいて直し、テストを走らせ、失敗を見て、各ステップで人が介入することなく方針を調整する、といった具合である。このカテゴリの例として挙げられているツールには、Claude Code、Cursor、Windsurf、そして GitHub Copilot のエージェントモードがある。もう 1 つの出典は、よく使われている例として Claude Code、OpenAI Codex、Gemini CLI を挙げている。

コーディングエージェントは、エージェント型エンジニアリングがその上に築かれる土台として説明されている。それらがなければ AI の支援は自動補完のような提案にとどまるのに対し、それらがあればタスクを丸ごと委ねて、動くコードとして返してもらえるのである。エージェントが生み出すものの質は、与えられる文脈 — 明快な仕様、足場、ガードレール — に大きく依存すると述べられており、その方向づけを効果的に与える営みがエージェント型エンジニアリングと名指されている。

実際にはこれはいくつかの形を取る。述べられた 1 つの機能や修正を端から端まで実装し、人間のレビューに供する単一タスクのエージェント。複数のエージェントが同時にコードベースの別々の部分に取り組むマルチエージェントの構成。そして、人が他のことをしている間に、PR のレビューや依存関係の更新といったタスクを非同期に走らせるバックグラウンドのエージェントである。

## どう作られているか

[[CreativeWorkSeries/agentic-engineering-patterns]] のある章がその内部を説明しており、その組み立ての軸となる主張は、コーディングエージェントとは言語モデルのための**ハーネス**である、というものである。すなわち、ユーザーが決して目にしないプロンプトを動力とし、呼び出し可能なツールとして実装された、モデルに追加の能力を与えるソフトウェアである。他のすべてはその切り分けから導かれる。

中心にあるのはモデル自身で、テキストを補完し、単語ではなく整数のトークンの単位で働く。これが重要なのは、章が指摘するように、プロバイダがトークン単位で課金し、一度に扱えるトークン数に限りがあるからである。モデルとのやりとりは [[DefinedTerm/chat-templated-prompt]]、すなわち話者のラベルが付いた会話として整形された補完プロンプトとして表現される。モデルは状態を持たないため、ハーネスが自ら状態を保持し、毎ターン会話全体を再生する。したがってセッションが長くなるにつれて入力のコストは増えていく。これを部分的に打ち消すのが [[DefinedTerm/token-caching]] であり、エージェントが会話の以前の内容を書き換えないように作られているのはそのためである。

**ツール**とは、ハーネスがモデルに利用可能にする関数のことである。プロンプトの水準ではシステムのターンの中で記述され、モデルは呼び出しを発してターンを終え、ハーネスがその呼び出しを取り出し — 章の例示は正規表現である — 実行して、結果をさらなるターンとして追加する。章は、たいていのコーディングエージェントが十数個以上のツールを定義しており、最も強力なのは `Bash()` や `Python()` のようなコード実行のツールだと報告している。隠された**システムプロンプト**は、エージェントをそのように振る舞わせる指示を担っており、数百行に及ぶこともある。**推論**、すなわちモデルが応答の前に余分なトークンを費やして問題を考え抜くことは、複雑なコードの経路を辿らせ、そこにツール呼び出しを織り交ぜさせられることから、デバッグにとりわけ有用だと述べられている。多くのエージェントは、これにどれだけ費やすかのつまみを公開している。

章の結論は意図的に熱を冷ますものである。LLM とシステムプロンプトとループの中のツールがあれば、コーディングエージェントを作るのに必要なもののほとんどは揃う。単純なツールのループなら既存の API の上に数十行で実現できる。本当の仕事を成しているのは、基本的な機構ではなく*良い*ツールのループのほうである。

## 研究文献はこれをどう捉えているか

[[ScholarlyArticle/a-survey-on-code-generation-with-llm-based-agents]] は同じカテゴリに研究の側から到達し、それを**コード生成エージェント**と名付け、そうしたエージェントを従来のコード生成技術から分かつとする 3 つの特徴によって特徴づけている。第 1 は*自律性*である。タスクの分解からコーディング、デバッグに至るワークフロー全体を独立して取り仕切る能力であり、従来のコード生成モデルはコード補完や関数生成を通じて人間の開発者を受動的に助けるにとどまっていた。第 2 は*タスク範囲の拡大*である。以前の研究が扱っていたのは、文脈から 1 行を補完する、シグネチャから関数本体を生成するといった、境界が明確で仕様がよく定義されたタスクであるのが典型だったが、エージェントはソフトウェア開発のほとんどを覆える — 曖昧な要求を扱い、プロジェクト全体を実装し、テストとリファクタリングを行い、リアルタイムのフィードバックに基づいて反復的に最適化するのである。第 3 は*工学的な実用性の強化*である。研究の重点がアルゴリズム的な精度から工学的な実装 — エージェントの信頼性、複雑なワークフローの管理、外部ツールの効率的な呼び出し — へと移ることであり、このサーベイはこれを、問題が古典的なソフトウェアエンジニアリングにより近い領域へ移っていくことだと述べている。

このサーベイは、言語モデルとエージェントの境界を能力によってではなくアーキテクチャによって引いている。モデルの動作は単一で受動的な応答の過程であって、能動的な計画も、状態の保持も、環境との継続的な相互作用も欠いている。一方エージェントは、自律性・対話性・反復性を備えた動的なワークフローを組み立て、そこではモデルが、現在の環境の状態から次の行動を決める推論エンジンとして働く。この捉え方は、上に挙げた実践者たちの説明と同じ重みをループに置きつつ、変わったのはソフトウェアに何ができるかだけではなく、仕事のどの部分が人の手に残されるかでもある、という主張を加えている。サーベイは開発者の役割が、タスクの定義者、過程の監督者、最終結果のレビュアーへと移っていくと述べている。
