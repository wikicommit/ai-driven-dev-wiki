AI コーディングエージェントとは、大規模言語モデルを動力とし、コードベースに対して自律的に行動できるソフトウェアである。ファイルを読み、周囲のコンテキストを理解し、コードを書いたり編集したりし、コマンドを実行し、テストを走らせ、観察した結果に基づいて反復する。人が次に何を入力すべきかを提案するだけにとどまらない点が特徴である。2 つ目の説明は、定義上の境界線を 1 つの能力に絞り込んでいる。コーディングエージェントとは、コードを*書くことと実行すること*の両方ができるエージェントであり、コードを生成するためにモデルを使う他のあらゆる用途と区別しているのは、実行である。

## 用法

決定的な特性は自律性である。エージェントは次の 1 行のコードを予測するのではなく、タスクが完了するまで行動を取り結果を観察するというループの中で動作する。ファイルを作成し、import の欠落に気づいてそれを直し、テストを実行し、失敗を見て、各ステップで人が介入することなくアプローチを調整する、といった具合である。このカテゴリーの例として挙げられるツールには、Claude Code、Cursor、Windsurf、GitHub Copilot のエージェントモードがある。別の情報源は、代表的な例として Claude Code、OpenAI Codex、Gemini CLI を挙げている。

コーディングエージェントは、エージェント型エンジニアリングが築かれる土台だと説明されている。それがなければ AI の支援はオートコンプリート的な提案に限られるが、それがあればタスク全体を委任し、動くコードとして返してもらうことができる。エージェントが生み出すものの品質は、与えられるコンテキスト、すなわち明確な仕様、足場（スキャフォールディング）、ガードレールに大きく依存するとされ、その方向づけを効果的に与える規律としてエージェント型エンジニアリングの名が挙げられている。

実際には、これはいくつかの形をとる。説明された 1 つの機能や修正をエンドツーエンドで実装し、人間がレビューする単一タスクのエージェント。複数のエージェントがコードベースの異なる部分を同時に扱うマルチエージェント構成。そして、人が別の作業をしている間に、PR レビューや依存関係の更新といったタスクを非同期に実行するバックグラウンドエージェントである。

さらに別の説明は、このカテゴリーをどう使うべきかについての規範的な論点を加えている。コーディングエージェントは自分が書いたコードを実行できるので、変更が動くことを実証するよう求めることができる。[[BlogPosting/your-job-is-to-deliver-code-you-have-proven-to-work]] は、これらのツールを使いこなすとは、まさにそれをさせることだと論じている。すなわち、作業を進めながら変更を手動で試し、その後も動き続けるように自動テストを構築させることである。この説明によれば、エージェントにとっては手動テストと自動テストの区別はほとんど意味をなさなくなる。どちらも、エージェントが観察するものではなく自ら実行するものだからである。同じ投稿は、エージェントはテストを書くよう促す必要がほとんどなく、既存のテストスイートがあれば言われなくてもそれを拡張し、そこで見つけたパターンを再利用すると報告している。そこから、テストコードをよく整理し、再現してほしいパターンで満たしておくべきだという実践的な推奨を導いている。

## どのように作られるか

[[CreativeWorkSeries/agentic-engineering-patterns]] のある章が内部構造を説明しており、その中心となる主張は、コーディングエージェントは言語モデルのための**ハーネス**だというものである。すなわち、ユーザーが目にすることのないプロンプトによって動かされ、呼び出し可能なツールとして実装された追加の能力でモデルを拡張するソフトウェアである。それ以外のすべてはこの分離から導かれる。

中心にあるのはモデルそのものであり、モデルはテキストを補完し、単語ではなく整数のトークン単位で動作する。章によれば、これが重要なのは、プロバイダーがトークン単位で課金し、一度に考慮できるトークン数にも上限があるからである。モデルとのやり取りは [[DefinedTerm/chat-templated-prompt]] として表現される。これは、ラベル付きの会話として整形された補完プロンプトである。モデルはステートレスなので、ハーネスが自前で状態を保持し、毎ターン会話全体を再送する。そのためセッションが長くなるにつれて入力コストが増えていくが、これは [[DefinedTerm/token-caching]] によって部分的に相殺される。エージェントが会話の前半の内容を変更しないように作られているのはこのためである。

**ツール**とは、ハーネスがモデルに利用可能にする関数である。プロンプトのレベルでは、ツールはシステムターンの中で記述され、モデルは呼び出しを出力することで自分のターンを終え、ハーネスはその呼び出しを抽出し（章の例示では正規表現が使われている）、実行し、その結果をさらなるターンとして追加する。章によれば、ほとんどのコーディングエージェントは十数個以上のツールを定義しており、中でも最も強力なのは `Bash()` や `Python()` ツールのようなコード実行である。隠された**システムプロンプト**には、エージェントをそのように振る舞わせる指示が含まれており、数百行に及ぶこともある。**推論**、すなわちモデルが返答する前に追加のトークンを費やして問題を考え抜くことは、デバッグに特に有用だと説明されている。複雑なコードパスを追い、ツール呼び出しを織り交ぜることができるからである。多くのエージェントは、推論にどれだけ費やすかを調整するダイヤルを提供している。

章の結論は意図的に拍子抜けさせるものである。LLM にシステムプロンプトとツールを加えてループで回すことが、コーディングエージェントを作るのに必要なもののほとんどであり、単純なツールループは既存の API の上に数十行で実現できる。そして本当の仕事となるのは、基本的な仕組みではなく、*良い*ツールループなのだという。

## 研究文献での捉え方

[[ScholarlyArticle/a-survey-on-code-generation-with-llm-based-agents]] は研究の側から同じカテゴリーにたどり着き、それを**コード生成エージェント**と呼んでいる。このサーベイは、そうしたエージェントを以前のコード生成技術から区別する 3 つの特徴によってそれを特徴づけている。1 つ目は*自律性*である。タスク分解からコーディング、デバッグまで、ワークフロー全体を独立して管理する能力であり、従来のコード生成モデルがコード補完や関数生成を通じて人間の開発者を受動的に支援していたのとは対照的である。2 つ目は*タスク範囲の拡大*である。以前の研究は典型的には、コンテキストから 1 行を補完する、シグネチャから関数本体を生成するといった、境界が明確で仕様がよく定義されたタスクを扱っていたのに対し、エージェントはソフトウェア開発の大部分をカバーできる。曖昧な要件への対応、プロジェクト全体の実装、テストとリファクタリング、リアルタイムのフィードバックに基づく反復的な最適化などである。3 つ目は*エンジニアリング上の実用性の向上*である。研究の重点がアルゴリズムの正確さから、エンジニアリング上の実装、すなわちエージェントの信頼性、複雑なワークフローの管理、外部ツールの効率的な呼び出しへと移っていることであり、サーベイはこれを、問題を古典的なソフトウェアエンジニアリングに近い領域へと移すものだと説明している。

このサーベイは、言語モデルとエージェントの境界線を、能力ではなくアーキテクチャによって引いている。モデルの動作は単一の受動的な応答プロセスであり、能動的な計画、状態の維持、環境との継続的な相互作用を欠いている。一方エージェントは、自律性、対話性、反復性を備えた動的なワークフローを構築し、モデルは現在の環境の状態から次の行動を決める推論エンジンとして機能する。この捉え方は、上記の実践者の説明と同じくループに重きを置いており、さらに、変わったのはソフトウェアにできることだけではなく、仕事のどの部分を人が担うことになるかでもある、という主張を付け加えている。サーベイは、開発者の役割がタスクの定義者、プロセスの監督者、最終結果のレビュアーへと移っていくと説明している。
