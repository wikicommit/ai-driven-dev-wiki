AI コーディングエージェントとは、大規模言語モデルによって駆動され、コードベースに対して自律的なアクションを取れる
ソフトウェアである。人が次に何を打つべきかを提案するだけでなく、ファイルを読み、周囲のコンテキストを理解し、コードを書いたり
編集したり、コマンドを実行し、テストを走らせ、観察した結果に基づいて反復する。もう一つの説明は、定義の線を単一の能力へと
狭めている。コーディングエージェントとは、コードを*書くことと実行することの両方*ができるエージェントであり、モデルを使って
コードを生み出す他のあらゆる用法からそれを分かつのは実行である、と。

## 用法

定義的な性質は自律性である。エージェントはループの中で動作し、次の一行のコードを予測するのではなく、タスクが完了するまで
アクションを取り結果を観察する。ファイルを作り、import が足りないことに気づいて直し、テストを走らせ、失敗を見て、各ステップで
人が介入することなくアプローチを調整する、といった具合である。このカテゴリの例として挙げられるツールには Claude Code、
Cursor、Windsurf、GitHub Copilot のエージェントモードがあり、もう一つの出典は Claude Code、OpenAI Codex、Gemini CLI を
その代表例として挙げている。

コーディングエージェントは、エージェント型エンジニアリングがその上に築かれる土台として述べられている。それがなければ AI の
支援はオートコンプリート的な提案に限られるが、それがあればタスクまるごとを委譲し、動くコードとして返してもらえる。
エージェントが生み出すものの品質は、与えられるコンテキスト——明確な仕様、足場、ガードレール——に大きく依存すると述べられて
おり、その方向づけを効果的に供給する規律としてエージェント型エンジニアリングが名指されている。

実際には、これはいくつかの形を取る。記述された一つの機能や修正を端から端まで実装し、人間のレビューに回す単一タスクの
エージェント。複数のエージェントがコードベースの異なる部分に同時に取り組むマルチエージェント構成。そして、人が別のことに
取り組んでいる間に、PR レビューや依存関係の更新といったタスクを非同期に走らせるバックグラウンドエージェントである。

さらに別の記述は、このカテゴリをどう使うべきかについて規範的な点を加えている。コーディングエージェントは自らが書いたコードを
実行できるので、変更が動くことを実証する義務を負わせられる。[[BlogPosting/your-job-is-to-deliver-code-you-have-proven-to-work]]
は、これらのツールを使いこなすとはまさにそれをさせることだと論じている——作業しながら変更を手で動かしてみせ、その後もそれが
動き続けるようにする自動テストを構築させるのである。この説明では、手動テストと自動テストの区別はエージェントにとってほぼ崩れる。
どちらもエージェントが観察するのではなく実行するものだからである。同じ記事は、エージェントはテストを書くのにほとんど後押しを
必要とせず、すでにあるテストスイートを言われずとも拡張し、そこに見つけたパターンを再利用すると報告しており、そこから、
テストコードはよく整理し、再現してほしいパターンで満たしておくべきだという実践的な推奨を引き出している。

## どのように作られているか

[[CreativeWorkSeries/agentic-engineering-patterns]] のある章はその内部構造を述べており、その中心的な主張は、コーディング
エージェントとは言語モデルのための**ハーネス**である、というものである。すなわち、ユーザーの目に触れないプロンプトによって
駆動され、呼び出し可能なツールとして実装された、モデルの能力を拡張するソフトウェアである。他のすべてはこの切り分けから
導かれる。

中心にあるのはモデル自身であり、これはテキストを補完し、単語ではなく整数のトークンを単位に働く——章が指摘するとおり、これは
重要である。プロバイダはトークン単位で課金し、一度に考慮できるトークン数に上限があるからである。モデルとのやり取りは
[[DefinedTerm/chat-templated-prompt]] として表現される。ラベル付きの会話として整形された補完プロンプトである。モデルは
ステートレスなので、ハーネスが自前で状態を保持し、毎ターン会話全体を再生する。したがってセッションが長くなるにつれ入力コストは
増大する——[[DefinedTerm/token-caching]] がそれを部分的に相殺しており、エージェントが会話の過去の内容を書き換えないように
作られているのはそのためである。

**ツール**とは、ハーネスがモデルに利用可能にする関数である。プロンプトのレベルではシステムターンの中で記述され、モデルは
呼び出しを出力してターンを終え、ハーネスはその呼び出しを抽出し——章の図解では正規表現である——実行し、その結果をさらなる
ターンとして追記する。章の報告によれば、ほとんどのコーディングエージェントは十数個以上のツールを定義しており、最も強力なのは
`Bash()` や `Python()` といったコード実行のツールである。隠された**システムプロンプト**は、そのエージェントをそのように
振る舞わせる指示を担っており、数百行に及ぶこともある。**推論**——モデルが返答の前に問題を考え抜くために追加のトークンを
費やすこと——はデバッグにとりわけ有用だと述べられている。複雑なコードパスを追い、その間にツール呼び出しを織り交ぜられる
ようになるからである。多くのエージェントは、それにどれだけ費やすかのつまみを公開している。

章の結論は意図的に拍子抜けするものである。LLM とシステムプロンプトとループの中のツールがあれば、コーディングエージェントを
作るのに必要なもののほとんどは揃う。単純なツールループなら既存の API の上に数十行で実現できる。そして本当の仕事は、基本的な
仕組みではなく*よい*ツールループのほうにある。

## 研究文献はこれをどう位置づけているか

[[ScholarlyArticle/a-survey-on-code-generation-with-llm-based-agents]] は研究の側から同じカテゴリにたどり着き、それを
**コード生成エージェント**と名付け、従来のコード生成技術からそうしたエージェントを分かつとする 3 つの特徴によって特徴づけて
いる。第一は*自律性*である。タスクの分解からコーディング、デバッグまで、ワークフロー全体を独立して管理する能力であり、
従来のコード生成モデルはコード補完や関数生成を通じて人間の開発者を受動的に支援するにとどまっていた。第二は*タスク範囲の
拡大*である。従来の研究が扱ってきたのは、コンテキストから一行を補完する、シグネチャから関数本体を生成するといった、明確な
境界と十分に定義された仕様を持つタスクだったが、エージェントはソフトウェア開発のほとんどを覆える——曖昧な要件を扱い、
プロジェクト全体を実装し、テストとリファクタリングを行い、リアルタイムのフィードバックに基づいて反復的に最適化するので
ある。第三は*工学的実用性の向上*である。研究の重心がアルゴリズム的な正確さから工学的な実装——エージェントの信頼性、複雑な
ワークフローの管理、外部ツールの効率的な呼び出し——へ移ることであり、このサーベイはそれを、問題を古典的なソフトウェア
エンジニアリングにより近い領域へ動かすものだと述べている。

このサーベイは、言語モデルとエージェントの間の線を、能力によってではなくアーキテクチャによって引いている。モデルの動作は
単一の受動的な応答プロセスであり、能動的な計画、状態の保持、環境との継続的な相互作用を欠く。エージェントは自律性・相互作用
性・反復性を備えた動的なワークフローを構築し、モデルはそこで、現在の環境状態から次のアクションを決める推論エンジンとして
働く。この捉え方は、上の実践者たちの記述と同じ重みをループに置いており、そのうえで、変わったのはソフトウェアに何ができるか
だけでなく、仕事のどの部分が人の手に残されるかでもある、という主張を加えている。サーベイは開発者の役割を、タスクの定義者・
プロセスの監督者・最終結果のレビュアーへ移るものとして述べている。
