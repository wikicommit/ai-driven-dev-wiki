間接プロンプトインジェクション（indirect prompt injection）とは、Greshake らが [[ScholarlyArticle/not-what-youve-signed-up-for]] においてその攻撃経路を明らかにした手法であり、攻撃者が自らモデルに直接プロンプトを与える必要なく、LLM を組み込んだアプリケーションが取得する可能性の高いデータの中に敵対的なプロンプトを戦略的に仕込むことで、そのアプリケーションを遠隔から悪用するものである。この手法は、LLM を組み込んだアプリケーションではデータと指示の境界が曖昧になるという事実を突く。そのため、アプリケーションが単に取得してコンテキストとしてモデルに渡すだけのコンテンツが、直接の指示と同じようにモデルに作用しうる。

## 使われ方

この手法を導入した研究における敵対的な位置づけを超えて、同じ仕組みは防御的な用途にも用いられてきた。12 億件の URL を対象とした計測研究である [[ScholarlyArticle/indirect-prompt-injection-in-the-wild]] は、Web ページに埋め込まれた指示が、攻撃的、防御的、そして目的が不明確な用途にまたがる 6 つの異なる目的を追求していることを明らかにしている。攻撃的な側では、同研究はシステムの妨害 — エージェントにランダムな文字列、繰り返される無意味な文、あるいはコンテキストの上限を使い果たさせることを意図したテキストを出力させる指示 — に加え、コンテンツの宣伝、引用の強制、好意的なレビューの強制による評判の操作、そして少数のデータ持ち出しの試みを記録している。防御的な側では、サイト所有者が自動化された再利用に対して著作権や個人データの制限を主張する例や、読み取るあらゆるモデルに対して応答に目印となるフレーズを含めるよう求めることで自動化された訪問者を検出する、AI ボット識別のパターンを記録している。著者らはこれを、純粋に悪意ある慣行ではなく、競合するインセンティブを持つ多様な利害関係者からなるエコシステムとして読み解き、現在の展開は確実な制御によってというよりも、摩擦や性能劣化を通じて機能していると特徴づけている。

同研究は、こうした指示が実際にどのように届けられているかも報告している。タスクの上書き — モデルを説得するのではなく、モデルの現在の指示を直接置き換えること — は、検証された事例の 99% に見られ、しばしばジェイルブレイク風の言い回しによって補強されている。ほとんどは人間の目に触れることを意図していない。約 70% は、HTTP レスポンスヘッダー、コメント、構造化データ、メタデータのフィールドなど、決して描画されないチャネルに置かれており、描画される HTML に埋め込まれたものの大多数も、色やコントラストの操作、遮蔽、ビューポートを利用した隠蔽といった手法によって隠されている。また、指示は高度にテンプレート化されており、54 の語彙的テンプレートが事例の 95% を占める。そして持続的でもあり、影響を受けたページの 65% は、分析されたスナップショットの 12 か月前の時点ですでにインジェクションを含んでいた。

## 適用される場面

この手法が当てはまるのは、敵対的なコンテンツを含む可能性の高いデータを取得し、取得したデータを指示から分離することなく、それをコンテキストの一部としてモデルに渡す、LLM を組み込んだアプリケーションである。この手法を導入した論文は、Bing の GPT-4 を搭載したチャットやコード補完エンジンを含む実世界のシステム、および GPT-4 上に構築された合成的なアプリケーションに対して、その実用的な有効性を実証した。そして、取得されて注入されたプロンプトが、アプリケーションの観点からは任意コード実行として作用しうること、またアプリケーションが他の API を呼び出すかどうか、どのように呼び出すかを操作しうることを示した。導入論文は、執筆時点ではこの種の攻撃に対する有効な緩和策が欠けていたと述べている。

どの程度成功するかは、取得されたコンテンツがモデルにどのように提示されるかに大きく依存する。13 のモデルと 4 種類のページ表現にわたる 5,200 回の統制された試行において、計測研究は、指示への追従は限定的ではあるが無視できない水準であることを見出した。最大は平文を与えた小規模モデルでの 8% であり、構造的な手がかりが保持されている場合には 0.2% から 1.1% の間に下がった — その説明は、ページを平坦化すると、指示が隠されていて場違いなものであることを示すはずのマークアップ、コメント、メタデータ、スタイルが剥ぎ取られてしまう、というものである。この結果には 2 つの注意点が伴う。より豊かな表現での追従率の低さは頑健性と同じではない。そうした表現ははるかに長く、モデルが使える出力を生成する前にそもそも失敗してしまうことが頻繁にあったからである。そして、インジェクションを認識することは、それに抵抗することと同じではない。同研究は、モデルが注入された指示について明示的に警告しながら、それでもその指示に従った事例を記録している。

著者らは、自らの数値を下限として提示している。そのコーパスは主に公開 Web のクロールに依拠しており、認証が必要なコンテンツが過小に表現されている可能性があるうえ、検出は難読化された変種や英語以外の変種を見逃しうる指標リストに依存しているからである。また、観測された指示の圧倒的多数が静的な文字列であることにも触れ、現在の控えめな有効性を長期的な上限として読むことに注意を促している。

3 つ目の出典は、同じ種類の攻撃をエージェントセキュリティの側から扱っている。
[[ScholarlyArticle/from-determinism-to-delegation]] は、間接プロンプトインジェクションを、エージェント型システムのリスクがエージェンシーそのものによって増幅される事例として扱う。汚染された文書や Web ページは、エージェントに正当なツールを悪用させうる — その例は、メール機能を通じてデータを持ち出すことである。同論文は、ツールを統合したベンチマークを引用し、ReAct でプロンプトされた GPT-4 エージェントがおよそ 24% のケースで攻撃に成功されたと報告している — これはツールを統合したエージェントのベンチマークであるため、上述の Web ページ要約における追従率とは直接比較できない。同論文が挙げる防御策は、古典的な境界型セキュリティとは種類が異なる。すなわち、ツールのパーミッションの厳格なスコープ設定、出力のガードレール、サンドボックス化された実行、そして破壊的なアクションに対するヒューマン・イン・ザ・ループのチェックポイントである。同論文はエージェンシー下でのセキュリティを未解決問題の 1 つに挙げ、防御策は未成熟であるとして、来歴、能力のスコープ設定、検証可能なガードレールのさらなる形式化を求めている。

4 つ目の説明はベンダーの側からのものである。Anthropic のプラットフォームドキュメントは、間接プロンプトインジェクションを、アプリケーションが防御しなければならない 2 つの脅威モデルの 1 つとして扱い、敵対者が誰であるかによってそれを定義している。ユーザーは信頼されており、攻撃者が影響を及ぼしている可能性があるのは、モデルがそのユーザーに代わって読む*第三者のコンテンツ* — 受信メールの本文、取得した Web ページ、アップロードされたファイルの OCR 出力、ツール呼び出しの結果 — である。ドキュメントはこれを、アプリケーション自身のユーザーが敵対者であるジェイルブレイクや直接プロンプトインジェクションと対比させている（[[DefinedTerm/jailbreaking]] を参照）。

そこで示される緩和策は、信頼できないコンテンツとアプリケーション自身の指示をモデルが確実に区別できるようにアプリケーションを構造化することから導かれる。第三者のコンテンツは `tool_result` ブロックの内側でのみ渡し、システムプロンプトや通常のユーザーテキストブロックには決して含めないこと。その根拠として述べられているのは、Claude はツール結果の内側に現れる指示を適切な懐疑心をもって扱うよう訓練されているという点である。ツールの説明や結果の構造によって、そのコンテンツが何であり、どこから来たのかを示し、埋め込まれた指令をどの程度信頼すべきかをモデルが調整できるようにすること。そして、システムプロンプトにおいて、ツール、文書、検索の結果は信頼できないデータであり、システムプロンプトやユーザーの依頼を決して上書きしてはならないと明言することである。また、信頼できない文字列を自由形式のテキストに連結するのではなく JSON エンコードすることを推奨している。JSON のエスケープは、攻撃者が引用符やタグを閉じて抜け出すことのできない、曖昧さのない区切りを与えるからである。その説明によれば逆もまた成り立つ。ツール結果のコンテンツは信頼できないものとして扱われるため、開発者自身の指示をそこに置くと無視されたり警告されたりする可能性があり、それは後続のユーザーターンに置くべきである。メッセージ構造以外では、モデルが到達できるデータとアクションに対する最小権限、各ツールの生の出力を返す前に小規模な分類器で審査すること、そして意図的にインジェクションの試みを含む文書やツール出力を用いてワークフローをレッドチーミングすることを挙げている。さらに、Anthropic はコンピュータ操作（Computer Use）ツールとブラウザ操作ツールが返すものに対して追加の分類器を実行しており、スクリーンショットやページのテキストを潜在的なインジェクションについてスキャンし、行動する前にその指示が本当にユーザーから来たものかを確認するよう Claude を誘導していると述べている。

5 つ目の説明は、攻撃経路をコーディングエージェント自身の設定ファイルに絞り込む。NVIDIA AI Red Team の報告は、悪意ある依存関係がビルド中に [[DefinedTerm/agents-md]] ファイルを書き込み、その結果、指示が取得されたコンテンツとしてではなく、プロジェクト設定としての地位をもってエージェントに届く事例を記述している。この事例を上述の取得文書型と区別するのは、注入されたテキストがエージェントの信頼モデルのどこに位置するかである。指示ファイルはエージェントが従うように作られているものであるため、この攻撃はモデルから身を隠す必要がなく、代わりに人間のレビュアーから身を隠した。プルリクエストを要約するモデルに宛てたソースコメントを通じて、2 つ目のインジェクションを連鎖させたのである。その前提条件はそれに応じてより強い — 攻撃者はビルド環境ですでにコード実行権限を持っていなければならない — ため、影響を受けたベンダーはそれを根拠に、この攻撃は侵害された依存関係以上に実質的にリスクを高めるものではないと結論づけた。[[DefinedTerm/indirect-agents-md-injection]] を参照。

6 つ目の説明である、プロンプトインジェクションに関する IBM の一般的な解説は、上記の内容を繰り返すのではなく、全体像に 2 つのことを付け加えている。1 つは非テキストの攻撃経路である — 悪意あるプロンプトは平文で書かれている必要はなく、モデルが読み取る画像に埋め込むこともできると指摘している。もう 1 つは、注入された指示が伝播する具体的な連鎖である。研究者らが AI を搭載したバーチャルアシスタントを介して拡散するワームを設計したと報告されており、そこでは悪意あるプロンプトがメールで届き、それを要約するよう頼まれたアシスタントに機密データを攻撃者へ送信させ、さらにその悪意あるプロンプトを他の連絡先へ転送するようアシスタントに指示する。同解説自身の導入例は、より単純な取得コンテンツの事例である。攻撃者がフォーラムに、ユーザーをフィッシングサイトへ誘導するようモデルに指示するプロンプトを投稿し、その議論を要約するよう頼まれたアシスタントが、何も知らないユーザーにその指示を中継してしまう、というものである。同出典はこの手法を、[[DefinedTerm/direct-prompt-injection]] と並ぶ、プロンプトインジェクションの 2 つの類型の 1 つとして分類している。

## 増幅要因としてのブラウザ操作

あるベンダーの説明は、この種の攻撃を封じ込めるのが最も難しい環境としてブラウザエージェントを特に取り上げている。[[BlogPosting/mitigating-prompt-injections-in-browser-use]] は 2 つの理由を挙げており、いずれもモデルではなく展開形態の性質である。攻撃対象領域は広大である — あらゆる Web ページ、埋め込まれた文書、広告、動的に読み込まれるスクリプトが運び手になりうる。そして、アクション空間が広い。ブラウザエージェントは URL へ移動し、フォームに入力し、ボタンをクリックし、ファイルをダウンロードできるため、その振る舞いに影響力を得た攻撃者には利用できるものが非常に多い。

その具体例は、最近のメールを読んで会議の依頼に対する返信を下書きするよう頼まれたエージェントである。そのうち 1 通のメールには白い文字で — 読み手には見えないがエージェントには処理される — 指示が書かれており、「confidential」という単語を含むメッセージはまず外部のアドレスへ転送するよう指示している。

この投稿が記述する防御策は 3 つの層にあり、いずれも提供者側のものである。モデルは、シミュレートされた Web コンテンツに埋め込まれたプロンプトインジェクションを用いた強化学習によって、この攻撃に対して直接訓練されており、権威的あるいは緊急であるかのように書かれていても悪意ある指示を拒否することに対して報酬を与えられる。分類器は、隠されたテキスト、操作された画像、欺瞞的な UI 要素を含むさまざまな運び手にわたって、コンテキストウィンドウに入ってくる信頼できないコンテンツをすべてスキャンし、検出時にはモデルの振る舞いを調整する。そして内部のレッドチームがエージェントを継続的に探査している。その根拠として述べられているのは、創造的な攻撃経路を見つけることにおいて人間の研究者は一貫して自動化システムを上回るという点であり、あわせて外部のアリーナ形式のチャレンジにも参加している。

報告されている結果は、環境あたり 100 回の試行を与えられた内部の適応的な「Best-of-N」攻撃者に対する攻撃成功率 1% である — これはそのベンダー自身の方法論の範囲内で計測されたものであり、ベンチマークと攻撃コーパスは公開されていない。心に留めておく価値があるのは、この投稿自身の注釈である。1% の成功率でもなお意味のあるリスクであり、いかなるブラウザエージェントも免疫を持たず、これらの数値は解決ではなく進展を示すために提示されている。
