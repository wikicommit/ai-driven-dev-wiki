コンテキストエンジニアリングとは、LLM ベースのエージェントがコンテキストウィンドウで何を見るかを管理する機構の総体である。[[ScholarlyArticle/building-effective-ai-coding-agents-for-the-terminal]] はその前提を直接に述べている。エージェントは単にユーザーのメッセージをモデルへ送って応答を受け取るのではなく、あらゆる応答の質は主として、モデルがどの指示を受け取るか、会話履歴がどれだけ保持されるか、以前のやり取りから何を学んだか、そして各呼び出しの前に関連する外部情報がどう組み立てられるかによって決まる。

## 実務者による定義

広く流通した2025年の二つの記事が、この語をベンダーの側から定義しており、両立するが整理の異なる説明に至っている。

[[TechArticle/effective-context-engineering-for-ai-agents]] は、コンテキストエンジニアリングをプロンプトエンジニアリングの自然な発展として提示する。プロンプトエンジニアリングが指示——主にシステムプロンプト——を書き整理することに関わるのに対し、コンテキストエンジニアリングは推論の最中に最適なトークンの集合をキュレーションし維持する戦略の総体であり、プロンプトの外でウィンドウへ着地するすべてを含む。掲げられる転換は、どの語を書くべきかを問うことから、「どのようなコンテキストの構成が、モデルの望ましい振る舞いを最も生み出しやすいか」を問うことへの転換である。同記事はこれをトークンの上限ではなくアテンションについての議論に基礎づけており、あらゆるトークンが「アテンション予算」を消費する（[[DefinedTerm/context-rot]] を参照）がゆえにコンテキストを限界収穫の逓減する有限の資源として扱い、その指針を一つの原理へ蒸留している。望ましい結果の見込みを最大化する、高信号なトークンの可能なかぎり最小の集合を見つけること、である。実務的な処方は、「適切な高度」——脆いハードコードされた if-else のロジックと、共有された文脈を誤って前提する曖昧な案内との中間——にあるシステムプロンプト、ある状況でどのツールが当てはまるかを人間が言えるほど小さなツールの集合、網羅的なエッジケースの一覧ではなくキュレーションされた規範的な例、そしてエージェントがファイルパスといった軽量な識別子を保持し、すべてを前もって処理するのではなく実行時にデータを読み込むジャストインタイムの検索に及ぶ。

[[BlogPosting/context-engineering]] は同じ領域を、コンテキストに対してできる四つのこと——ウィンドウの外に**書く**、選んで**引き戻す**、タスクが必要とするものだけに**圧縮する**、そしてエージェント・サンドボックス・状態フィールドをまたいで**分離する**——として整理し、各分類を実運用のエージェントと論文からの例で埋めている。管理すべきコンテキストを指示・知識・ツールに分け、その枠組みを、モデルを CPU に、コンテキストウィンドウを RAM になぞらえる Andrej Karpathy の類比から取っている。

両者が異なるのは中身ではなく強調点である。Anthropic はモデルの振る舞いから議論して最小性の原理へ至り、LangChain は実践を概観してカテゴリの集合へ至る。いずれもコンテキストウィンドウより長く続く作業のための同じ三つの技術——[[DefinedTerm/compaction]]、[[DefinedTerm/agentic-memory]]、[[DefinedTerm/multi-agent-orchestration]]——を挙げている。LangChain はさらに、トレースとトークン使用量の追跡を前提条件として枠づけており、それによってコンテキストエンジニアリング上のあらゆる変更の効果を検証できるようにしている。

この語はまた製品のカテゴリにもなった。[[SoftwareApplication/context-engineering-kit]] はコンテキストエンジニアリングの技術をインストール可能なプラグインとして提供しており、その掲げる設計基準——最小限のトークンのフットプリント、使わないプラグインが何も読み込まないきめ細かいインストール、そして一般的な情報スキルよりサブエージェントを伴うコマンド志向のスキルを選ぶこと——は、それ自体が最小性の原理をエージェント自身の設定へ適用したものである。

## 用法

同報告は、コンテキストエンジニアリングのサーベイ文献からの形式的なタクソノミーを要約している。それはモデルへ供給されるコンテキストを、指示的コンテキスト、外部知識、ツールのスキーマ、メモリ、実行の状態、ユーザーのクエリから組み立てられる構造化されたタプルとして扱い、三つの柱——*コンテキストの検索*（外部の情報源から関連する情報を選ぶこと）、*コンテキストの処理*（取得した内容を変換・圧縮・再構成すること）、*コンテキストの管理*（ターンをまたいで一貫性と関連性を保つこと）——を軸に整理する。

同報告はまた「コンテキストエンジニアリング 2.0」の研究からの歴史的な枠づけも要約している。それは四つの時代——単一ターンの指示に焦点を当てた初期のプロンプトエンジニアリング、外部知識を導入した検索拡張生成、行動空間を広げたツール拡張エージェント、そしてコンテキストを一級の工学的関心事として扱う現在——を辿り、三つの指導原理を明示している。*エントロピーの削減*——各コンテキスト要素は望ましい出力についての不確実性を減らすべきである。*最小限の十分性*——アテンションの希釈を避けるため必要なものだけを含めるべきである。*意味的な連続性*——コンテキストは一から再構成されるのではなく、ターンをまたいで一貫して進化すべきである。同研究はまた現在のシステムにおける狭さのギャップも同定しており、同報告はそれを、チャット履歴の管理に圧倒的に焦点が当たる一方、ツールの状態、環境からの信号、セッションをまたぐ知識といった全体的な次元が軽視されている、と説明している。

実務において同報告は、コンテキストを長時間稼働のエージェントの中心的な設計上の制約として扱っている。述べられる経験は、ツールの出力——ファイルの内容、コマンドの結果、検索のヒット——が典型的なセッションのコンテキストの70〜80% を消費し、システムプロンプトやエージェント自身の推論を圧倒するというものである。これがコンテキストの利用率をエージェントの寿命にとって最も重要な単一の指標にし、行き渡った緊張を課す。より豊かなツールの出力はターンごとの正確さを高めるが、セッションの有効な寿命を縮めるのである。

同報告がこの規律のもとにまとめる具体的な技術には、次のようなものがある。

- **条件付きプロンプトの合成** — 振る舞いに関する指示を、条件の述語と優先度を持つ独立したセクションへ分解し、ファイルを読む前に無関係なセクションを除外する
- **キャッシュのためのプロンプト構造** — システムプロンプトを安定した接頭部と動的な接尾部に分け、接頭部を複数ターンのセッションにわたってキャッシュできるようにする
- **ツール結果の最適化** — 生の出力を簡潔な要約に置き換え、あるサイズの閾値を超える出力はプレビューと参照パスを添えてスクラッチファイルへ退避する
- **二重メモリのアーキテクチャ** — 推論用のモデルに、全履歴の圧縮されたエピソード的要約を、逐語的な直近のメッセージと並べて供給する
- [[DefinedTerm/adaptive-context-compaction]] — コンテキストの圧力が高まるにつれて適用される段階的な削減
- [[DefinedTerm/system-reminders]] — アテンションの減衰に対抗するため、意思決定の地点で注入される短く的を絞ったメッセージ
- **経験駆動のメモリのパイプライン** — プロジェクト固有の知識を、有効性・新しさ・意味的類似度で採点された自然言語の箇条書きからなるプレイブックとして蓄積する

同報告が広く適用可能なものとして枠づける教訓は二つある。第一は、コンテキストをバッファではなく予算として扱い、硬い上限での単一の緊急コンパクションではなく段階的な削減を設計することである。第二は、ローカルの推定ではなく API が報告するトークン数で較正することである。プロバイダは目に見えない内容——安全性の前置き、ツールスキーマの直列化、内部の整形——を注入するため、ローカルでの計数は実際の使用量を体系的に過小評価する。著者のシステムではこのずれが十分に大きく、コンパクションの発火が遅れてコンテキスト溢れのエラーを生じさせていた。

同報告はまた、サーベイ文献からの知見を設計上のレバーとして扱っている。LLM は生成のタスクにおけるよりも理解のタスクにおいて、圧縮されたコンテキストに対して頑健である。これは、攻撃的な圧縮が最も成立しやすいのは、出力のテキストを直接形作るコンテキストではなく、推論に情報を与えるコンテキストであることを示唆する。

ツールの層は、能力の層であるだけでなく、それ自体が一つのコンテキストエンジニアリングの面である。[[TechArticle/writing-effective-tools-for-agents]] は、同じ最小性の推論をツールが返すものへ適用している。コンピュータのメモリが安価で潤沢であるのに対しエージェントのコンテキストは限られているため、すべてを返すツールはエージェントに無関係な素材を読み進めるコンテキストを費やさせる。それゆえツールは、高信号な情報だけを返すよう選ばれ形づくられるべきである。その具体的な処方は上の定義と一続きである。`list_contacts` ツールより `search_contacts` ツールを選ぶこと、頻繁に連鎖する操作を単一の呼び出しへ統合して中間の出力がコンテキストへ入らないようにすること、`uuid` や `mime_type` といった低水準の識別子を落としてエージェントが実際に用いるフィールドを優先すること、そして妥当な既定値を伴うページング・フィルタ・切り詰めを適用すること——Claude Code は既定でツールの応答を25,000トークンに制限している。同記事はまた、ツール自身のテキストも設計されるべきコンテキストとして扱っている。説明、仕様、さらにはエラーメッセージまでがエージェントのウィンドウへ読み込まれ、それゆえ振る舞いを導くのであり、他のすべてと同じ予算のもとに置かれる。

### 四つの柱と、プロンプトエンジニアリングとの境界線

[[BlogPosting/context-engineering-a-practical-guide-for-ai-agents]] は新しい定義ではなくこの規律の整理を提示しており、その切り分けが一つの選択にすぎないことに率直である。他の著者は階層的なレイヤーを挙げたり、七つの構成要素を挙げたり、列挙せずに各部を辿ったりしていると指摘し、実務的な代替として四つの柱を提案している。**指示** — 最初のユーザーメッセージより前の役割、制約、出力形式であり、そこで述べられる失敗モードは長さではなくモデルの訓練とのミスマッチである。モデルの既定のツール利用のヒューリスティクスに反する指示は、毎ターンそれを混乱させる。**検索** — 外部データがウィンドウへ入る経路であり、RAG、構造化されたクエリ、ファイルの読み込み、あるいはジャストインタイムの読み込みによる。**メモリ** — 短期の会話履歴と長期のセッションをまたぐ状態で、通常はコンパクションのステップを伴う。**ツール** — 実行可能な面であり、この規律が「最も容赦なくなる」場所と説明される。あらゆる定義とあらゆる結果がトークンを費やし、ほぼ重複するツールはモデルに選択のためのターンを浪費させるからである。

上のプロンプトエンジニアリングとの比較に対する同記事の寄与は、タクソノミーではなく使える試金石である。「名詞と形容詞を差し替えているなら、まだプロンプトエンジニアリングをしている。エージェントがどのデータを、どの順序で、どう再ランキングして取得するか、そしてコンテキストウィンドウが埋まったとき何を追い出すかを変えているなら、コンテキストエンジニアリングをしている」。同記事がこの規律を還元する四つの問いは、何を取得するか、いつ取得するか、どう圧縮するか、そしていつ捨てるか、である。

同記事が強調する二つの機構は、上のベンダーの説明には見られない。**トークン予算の管理**は、そこでは低信号な内容をウィンドウへ入った*後で*はなく入る*前に*削ることと定義される——ツールの出力を切り詰め、古いターンをコンパクトにし、関連度の閾値を下回る取得済みの断片を落とし、各検索呼び出しが寄与する候補数に上限を設ける。**再ランキング**は、素朴な RAG のパイプラインが機能しはじめるか機能しなくなるかの分かれ目のステップとして提示される。より小さなクロスエンコーダや安価なモデルが候補を採点し、精度の高い上位 k 件を残すのである。その例示は、高い再現率で50件の候補を取得し、それを5件へ再ランキングすることであって、50件すべてをプロンプトへ投げ込むことではない。

同記事はまた、順序をこの規律に持ち込み、Liu らの「中央で迷子になる（lost in the middle）」という知見を引いている。性能は「関連する情報が入力コンテキストの冒頭または末尾に現れるときに最も高いことが多く、モデルが長いコンテキストの中央にある関連情報にアクセスせねばならないときには著しく劣化する。明示的に長いコンテキストに対応したモデルにおいてさえそうである」。実務的な帰結は、組み立ての順序が重要であり、最も信号の強い素材は埋もれさせるのではなく上か下に置くべきだということである。同論文はこのページの出典には含まれていない。この知見は同ガイドによる引用として記録されている。

この語そのものの帰属について、同ガイドは2025年半ばに Phil Schmid がその普及を助けたとしている——これは、[[BlogPosting/skill-issue-harness-engineering-for-coding-agents]] が造語を、著者の共同創業者である Dex Horthy の 12-factor agents の仕事に帰していることと、対立するのではなく並び立つ。同記事はまた、この規律の名前を持つ部分集合として [[DefinedTerm/harness-engineering]] を提案している。エージェントの設定点を通じて働く部分である。

### 内容だけでなく手順を最適化する

上のすべての説明は手順を固定したうえで、そこを何が流れるべきかを論じる。[[ScholarlyArticle/meta-context-engineering]] は、手順を固定すること自体が制約となる選択だと論じる。現在の手法は「硬直した生成・反省のワークフローやあらかじめ定義されたコンテキストのスキーマといった、手作業で作られたハーネスに依拠して」おり、それが「構造的なバイアスを課し、コンテキストの最適化を狭く直観に縛られた設計空間へ制限する」からである。それが乗り越えるものとして名指しされる例は、[[ScholarlyArticle/agentic-context-engineering]] の生成・反省・キュレーションのワークフローである。

その提案は作業を二つの水準へ分ける。メタ水準のエージェントが、エージェンティッククロスオーバーと呼ぶもの——スキルの履歴、その実行、その評価にわたる熟慮的な探索——を通じてコンテキストエンジニアリングの*スキル*を進化させる。進化の単位として用いられるのは [[DefinedTerm/agent-skills]] である。次に基底水準のエージェントがそれらのスキルを適用し、あらかじめ定義されたスキーマを埋めるのではなく、「コーディングのツールキットとファイルシステムへのアクセスを活かして、コンテキストを柔軟でプログラム的な成果物として具現化し最適化する」。従来のエージェンティックなコンテキストエンジニアリングの手法に対して報告される利得は、五つのドメインと四つのモデルにわたって相対で5.6〜53.8%、平均16.9% である。この幅は見返りがドメインにどれだけ依存するかを示唆しており、これらの数値は著者ら自身のベースラインに対する著者ら自身のものである。

### 選択だけでなく符号化

コンテキストエンジニアリングの大半の説明は、*何が*モデルに届くかに関わる。[[Person/simon-willison]] のリンク記事は、*それがどう書き下されるか*に関わる研究を紹介している。SQL の生成をプログラム的なエージェントの操作の代理として用い、9,649の実験、11のモデル、四つの形式（YAML、Markdown、JSON、Token-Oriented Object Notation）、そして10から10,000テーブルに及ぶスキーマを対象としたものである。

その結果のうち二つが伝えられている。第一に、最も大きな効果はモデルそのものであった。フロンティアモデルは主要なオープンソースのモデルを上回り、ファイルシステムに基づくコンテキストの検索から説得力をもって恩恵を受けたのはフロンティアモデルだけであった——Willison はこれを、ファイルシステムを用いるコーディングエージェントのループがオープンウェイトのモデルではまだうまく扱われていないという自らの感覚を補強するものと読んでいる。第二に、[[DefinedTerm/grep-tax]] の結果である。ディスク上でおよそ25% 小さい形式が、500テーブルでは YAML より138% 多く、10,000テーブルでは740% 多くのトークンを消費した。モデルが、慣れていない構文において効果的な絞り込みのパターンを組み立てられなかったからである。

そこから導かれる実務上の教訓は、形式のトークン数を単独で見るのは誤った尺度だということである。重要なのは、モデルがそれに対してどれだけ安価に反復できるかである。

### 実践であるだけでなく役割として

[[BlogPosting/context-engineering-a-practical-guide-for-ai-agents]] は担い手も名指ししている。*コンテキストエンジニア*とは、その定義では「AI システムに適切なコンテキストを適切なタイミングで供給するアーキテクチャに責任を負う人（あるいはプラットフォームチーム上の役割）」であり、その仕事は検索のパイプライン、長期メモリを含むメモリのシステム、ツールの設計、そして評価に及び、「プロンプトを書くことよりもシステムエンジニアリングに近い」ところに位置する。

その比較表は、二つの規律を分けるのと同じ軸で担い手を割り当てている。プロンプトエンジニアリングは「プロンプトを書く者なら誰でも」に属し、コンテキストエンジニアリングは「エージェントのパイプラインを構築するプラットフォームチーム」に属する。これは仕事が何であるかについてだけでなく、それが組織のどこに位置するかについての主張であり、確立された職務の定義ではなくこのベンダーの枠づけである。

## 関連用語

コンテキストエンジニアリングは、実行時に [[DefinedTerm/agent-harness]] が調整する関心事の一つであり、それが管理するモジュール化されたシステムプロンプトは [[DefinedTerm/agent-scaffolding]] の段階で組み立てられる。それが管理するために存在する問題は [[DefinedTerm/context-rot]] であり、その主要な技術は [[DefinedTerm/compaction]]、[[DefinedTerm/agentic-memory]]、[[DefinedTerm/multi-agent-orchestration]] であり、その最も単純な常時読み込みの形態は [[DefinedTerm/context-files]] のもとで扱われる。[[DefinedTerm/coding-agent]] のエンドユーザーは、同じ規律にセッションの衛生管理として出会う。Claude Code のドキュメントは、根本的な制約としてのコンテキストウィンドウを軸に推奨を組み立てており、無関係なタスクのあいだの `/clear`、指示を伴う `/compact`、そして探索がメインの会話を消費しないための [[DefinedTerm/subagents]] への委任を処方している。同報告はまた、コンテキストエンジニアリング自体を手作業の設計課題ではなく最適化問題として扱い、システムプロンプト、ツールのスキーマ、メモリの戦略といったコンテキストの構成を探索するメタ水準の研究も概観している。
