コンテキストエンジニアリングとは、LLM ベースのエージェントがコンテキストウィンドウの中で何を見るのかを管理する仕組みの総体である。[[ScholarlyArticle/building-effective-ai-coding-agents-for-the-terminal]] はその前提を端的に述べている。エージェントは単にユーザーのメッセージをモデルに送って応答を受け取っているのではなく、あらゆる応答の品質は主として、モデルがどの指示を受け取るか、会話履歴がどれだけ保持されるか、過去のやり取りから何を学んだか、そして各呼び出しの前に関連する外部情報がどう組み立てられるかによって決まる、というのである。

## 実践者による定義

広く読まれた 2025年の2つの記事が、ベンダー側からこの語を定義しており、両立するが整理の仕方の異なる説明にたどり着いている。

[[TechArticle/effective-context-engineering-for-ai-agents]] は、コンテキストエンジニアリングをプロンプトエンジニアリングの自然な発展として提示する。プロンプトエンジニアリングが指示——主にシステムプロンプト——を書き整理することに関わるのに対し、コンテキストエンジニアリングは推論時に最適なトークンの集合をキュレーションし維持するための戦略の総体であり、プロンプト以外でウィンドウに入るものすべてを含む。掲げられている転換は、どんな言葉を書くべきかを問うことから「どのようなコンテキストの構成が、モデルに望む振る舞いを最も生みやすいか」を問うことへの転換である。これはトークンの上限ではなくアテンションについての議論に基礎づけられており、すべてのトークンが「アテンション予算」を消費するがゆえに（[[DefinedTerm/context-rot]] を参照）コンテキストを限界効用逓減を伴う有限の資源として扱い、その指針を一つの原則に蒸留する。望む結果の確率を最大化する、可能な限り小さな高シグナルのトークン集合を見つけよ、というものである。具体的な処方は、「ちょうどよい高度」のシステムプロンプト——脆いハードコードされた if-else のロジックと、共有された文脈を誤って前提する曖昧な指針の中間——、ある状況でどのツールを使うべきか人間が言えるくらい小さなツールの集合、網羅的なエッジケースの一覧ではなくキュレーションされた正典的な例、そしてエージェントがファイルパスのような軽量な識別子を保持し、すべてを事前処理するのではなく実行時にデータを読み込むジャストインタイムの検索、を扱う。

[[BlogPosting/context-engineering]] は同じ領域を、コンテキストに対してできる4つのこととして整理する。ウィンドウの外に **書く**、それを **選んで** 引き戻す、タスクに必要なものだけに **圧縮する**、そしてエージェント・サンドボックス・状態フィールドをまたいで **分離する** である。そして各分類を、出荷済みのエージェントと論文から取った例で埋めていく。管理すべきコンテキストを指示・知識・ツールに分け、その枠組みをモデルを CPU、コンテキストウィンドウを RAM に見立てる Andrej Karpathy の比喩から取っている。

両者が異なるのは実質ではなく力点である。Anthropic はモデルの挙動から論じて最小性の原則へ向かい、LangChain は実践を概観してカテゴリの集合へ向かう。どちらも、コンテキストウィンドウより長く続く作業のための同じ3つの技法——[[DefinedTerm/compaction]]、[[DefinedTerm/agentic-memory]]、[[DefinedTerm/multi-agent-orchestration]]——を挙げている。LangChain はさらに、コンテキストエンジニアリング上のどんな変更の効果も検証できるよう、トレースとトークン使用量の追跡を前提条件として位置づけている。

この語はプロダクトのカテゴリにもなっている。[[SoftwareApplication/context-engineering-kit]] はコンテキストエンジニアリングの技法をインストール可能なプラグインとしてパッケージ化しており、掲げられている設計基準——最小のトークンフットプリント、使わないプラグインが何も読み込まないような粒度の細かいインストール、そして一般的な情報スキルよりもサブエージェントを伴うコマンド志向のスキルを好むこと——は、それ自体が最小性の原則をエージェント自身の設定に適用したものである。

## 用法

レポートは、コンテキストエンジニアリングのサーベイ文献にある形式的な分類を要約している。それはモデルに供給されるコンテキストを、指示的コンテキスト、外部知識、ツールスキーマ、メモリ、実行状態、ユーザーのクエリから組み立てられた構造化されたタプルとして扱い、3つの柱の周りに整理する。*コンテキストの検索*（外部の情報源から関連する情報を選ぶこと）、*コンテキストの処理*（検索された内容を変換・圧縮・再構造化すること）、そして *コンテキストの管理*（ターンをまたいだ一貫性と関連性を保つこと）である。

レポートはまた、「コンテキストエンジニアリング 2.0」に関する研究からの歴史的な枠づけも要約している。それは4つの時代——単一ターンの指示に焦点を当てた初期のプロンプトエンジニアリング、外部知識を導入した検索拡張生成、行動空間を広げたツール拡張エージェント、そしてコンテキストを一級のエンジニアリング上の関心事として扱う現在の時代——をたどり、3つの指導原理を明確化する。*エントロピーの削減*——各コンテキスト要素は望ましい出力についての不確実性を減らすべきである。*最小十分性*——アテンションの希釈を避けるため、必要なものだけを含めるべきである。そして *意味の連続性*——コンテキストは一から再構成されるのではなく、ターンをまたいで一貫して進化すべきである。この研究はまた現在のシステムにおける視野の狭さも指摘しており、レポートはこれを、ツールの状態、環境からのシグナル、セッションをまたいだ知識といった全体的な次元を軽視して、チャット履歴の管理に圧倒的に集中していることだと説明している。

実務上、レポートはコンテキストを長時間動作するエージェントの中心的な設計上の制約として扱う。述べられている経験によれば、ツールの出力——ファイルの内容、コマンドの結果、検索のヒット——が典型的なセッションのコンテキストの 70〜80% を消費し、システムプロンプトやエージェント自身の推論を圧倒する。このためコンテキストの利用率はエージェントの寿命にとって最も重要な単一の指標となり、遍在する緊張を生む。ツールの出力が豊かであるほどターンごとの正確性は上がるが、セッションの有効寿命は短くなるのである。

レポートがこの分野の下にまとめる具体的な技法には次のものがある。

- **条件付きプロンプト構成** — 振る舞いの指示を、条件述語と優先度を持つ独立したセクションに分解し、ファイルを一つも読む前に無関係なセクションを除外する
- **キャッシュのためのプロンプト構造** — システムプロンプトを安定した接頭部と動的な接尾部に分け、複数ターンのセッションにわたって接頭部をキャッシュできるようにする
- **ツール結果の最適化** — 生の出力をコンパクトな要約に置き換え、あるサイズのしきい値を超える出力はプレビューと参照パスを添えてスクラッチファイルに退避する
- **二重メモリのアーキテクチャ** — 思考モデルに、履歴全体の圧縮されたエピソード的な要約と、逐語的な直近のメッセージを併せて供給する
- [[DefinedTerm/adaptive-context-compaction]] — コンテキストの圧迫が高まるにつれて適用される段階的な削減のステージ
- [[DefinedTerm/system-reminders]] — アテンションの減衰に対抗するため、意思決定の地点で注入される短く的を絞ったメッセージ
- **経験駆動のメモリパイプライン** — プロジェクト固有の知識を、有効性・新しさ・意味的類似度でスコア付けされた自然言語の箇条書きのプレイブックとして蓄積する

レポートが引き出す2つの教訓は、広く適用可能なものとして枠づけられている。第一は、コンテキストをバッファではなく予算として扱い、ハードリミットにおける単発の緊急コンパクションではなく段階的な削減のステージを設計することである。第二は、ローカルな推定値ではなく API が報告するトークン数から較正することである。プロバイダは目に見えない内容——安全性の前置き、ツールスキーマのシリアライズ、内部的な書式——を注入するため、ローカルな計数は実際の使用量を系統的に過小評価する。著者のシステムではこのずれが十分に大きく、コンパクションの発動が遅すぎてコンテキストのオーバーフローエラーを引き起こしていた。

レポートはまた、サーベイ文献から得られた知見のうち、設計上のレバーとして扱っているものにも触れている。LLM は生成タスクよりも理解タスクにおいて圧縮されたコンテキストに対して頑健である、というものだ。これは、積極的な圧縮が最も有効なのは、出力テキストを直接形作るコンテキストではなく、推論に情報を与えるコンテキストに対してであることを示唆している。

## 関連用語

コンテキストエンジニアリングは、実行時に [[DefinedTerm/agent-harness]] が調整する関心事の一つであり、それが管理するモジュール化されたシステムプロンプトは [[DefinedTerm/agent-scaffolding]] の間に組み立てられる。これが管理するために存在する問題が [[DefinedTerm/context-rot]] であり、その主要な技法が [[DefinedTerm/compaction]]、[[DefinedTerm/agentic-memory]]、[[DefinedTerm/multi-agent-orchestration]] である。そして最も単純な、常時読み込まれる形態は [[DefinedTerm/context-files]] で扱われている。[[DefinedTerm/coding-agent]] のエンドユーザーは、同じ分野にセッションの衛生管理として出会う。Claude Code のドキュメントは、コンテキストウィンドウを根本的な制約として推奨事項を枠づけ、無関係なタスクの間の `/clear`、指示を伴う `/compact`、そして探索がメインの会話を消費しないようにするための [[DefinedTerm/subagents]] への委譲を処方している。レポートはさらに、コンテキストエンジニアリング自体を手作業の設計タスクではなく最適化問題として扱い、システムプロンプト、ツールスキーマ、メモリ戦略といったコンテキストの構成を探索するメタレベルの研究も概観している。
