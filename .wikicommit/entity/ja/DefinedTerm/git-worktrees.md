Git ワークツリーは、単一のリポジトリから、同一リポジトリの複数のブランチをそれぞれ自分のディレクトリへ同時にチェックアウトすることを可能にする。エージェント型コーディングにおいては、これによって並列に走る複数のエージェントのそれぞれが隔離された作業用の複製を持つことになり、実行中に互いの変更が干渉し合わずに済む。

## 用法

Osmani は、[[SoftwareApplication/claude-code]] 自身のドキュメントが、インスタンスどうしが干渉しないよう並列セッションに対して git ワークツリーを明示的に推奨していると述べ、Anthropic のベストプラクティスの指針が、ワークツリーの利用と「ワークツリーごとに端末のタブを一つ」という運用パターンを組み合わせた手順を段階的に示していることを引いている。彼はこの技法を、チームでの調整から借りた明示的な境界のルールと対にしている。すなわち、一つのエージェントが一つのプルリクエストを持ち、複数のエージェントから組み上げた巨大な PR は作らない。2 つのエージェントが同じファイルに触れる可能性があるなら、タスクの分割のほうを設計し直す。そして共有されるインターフェースは、まず人間が主導するプルリクエストで扱い、エージェントはその上に積み上げる。

## 適用条件

Git ワークツリーは、同じリポジトリに対して複数のコーディングエージェントを並列に走らせる際、それらが同一の作業用複製を同時に編集することを防ぐために適用される。出典は、ディレクトリを隔離するだけでは不十分だという立場をとる——マージ衝突はツールの失敗ではなく境界の失敗として記述されており、したがってワークツリーは上記のタスクの境界のルールの代わりとしてではなく、それと対にして用いられる。この実践は、Osmani の説明によれば、この記事自身の発明ではなく、Claude Code 自身のドキュメントと Anthropic のベストプラクティスの指針の双方において推奨されているパターンとして提示されている。

後年の記事は、[[SoftwareApplication/cursor]] のバックグラウンドのクラウドエージェントが同じ技法をホスティングされたプロダクトのレベルで用いていると述べている。長時間走る各バックグラウンドエージェントは自らの隔離された git ワークツリーの中で動き、その結果をプルリクエストを介してコードベースへマージして戻す。そのため、ローカルで始めたタスクをクラウドへ引き渡し、他の作業と衝突することなく後から再び接続することができる。
