エージェントフックは、AI エージェントのツール呼び出しを開発者が横取りできるようにするものであり、呼び出しが実行される
直前または直後に独自のロジックを走らせることで、その呼び出しを承認したり、ブロックしたり、事後処理を行ったりできる
ようにする。この機構は、ランタイムが読み込む外部設定としても、エージェントフレームワークが公開するプロセス内の
コールバック API としても現れる。Google の Gemini API は前者を、名前付きルールの下にイベント定義をまとめ、標準の RE2
正規表現でツール名に照合する `hooks.json` 設定として実装しており、[[SoftwareApplication/strands-agents]] は後者を、
フレームワークのライフサイクルイベントに対して登録されるコールバックとして実装している。

この機構が*何のためのもの*かを最も直截に述べているのは
[[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] である。フックを走らせるかどうかを決めるのはモデルでは
なくランタイムなので、フックに実装されたルールは毎回必ず効く。同じルールをプロンプトやコンテキストファイルに書いた
場合、それはモデルがそのターンで従うかもしれないし従わないかもしれない提案にすぎない。この記事はフックを、エージェント
の確率的な指示追従に対する決定論的な釣り合いとして提示し、モデルがコンテキストをどう読むかに依存してはならない少数の
ルールのために取っておくべきだとしている。

## 用法

Google の Gemini API では、フックは 2 つのライフサイクルイベントのいずれかで発火する。`pre_tool_execution` はツール
呼び出しの前に走り、実行前にそれを承認（`allow`）またはブロック（`deny`）できる — ブロックされた場合、モデルには拒否
理由が見えるので適応できる。`post_tool_execution` は呼び出しの完了後に走り、コードの整形、テストの実行、テレメトリの
記録といった事後処理しか行えない。すでに起きてしまったアクションを取り消すこともブロックすることもできないからである。
各ルールグループは `matcher`（`code_execution`、`read_file`、`write_file` のようなツール名に照合される正規表現）と、
それが一致したときに走らせる `hooks` の順序付きリストを指定する。フックは `command`（サンドボックス内で走り、イベントを
JSON として標準入力から読み、判断を標準出力へ書く）か `http` ハンドラ（サンドボックスの送信プロキシを通してイベントを
外部の HTTPS エンドポイントへ POST する。このプロキシは送信リクエストに認証ヘッダーを差し込めるので、フックの設定その
ものに秘密情報を保存する必要がない）のいずれかである。コマンドスクリプトがクラッシュした場合、HTTP フックが 2xx 以外の
ステータスを返した場合、フックがタイムアウトした場合、あるいは認識できない出力を返した場合、ランタイムはそれをブロック
ではなく承認として扱うので、壊れたフックがエージェントをデッドロックさせることはない。Gemini API の実装では、フックは
サンドボックス自身の組み込みツール（コード実行とファイルシステム操作）に限定され、コンテナの外で扱われるカスタムの
function calling ツールや外部の MCP サーバーのツールに対しては発火しない。

同じ実行前の横取りは、[[SoftwareApplication/strands-agents]] ではプロセス内 API として現れる。そこでは `HookProvider`
が `HookRegistry` を通じて `BeforeToolCallEvent` に対するコールバックを登録する。コールバックは保留中の呼び出しの名前と
入力を受け取り、`event.cancel_tool` にメッセージを代入することでそれをブロックする。フレームワークはそのメッセージを
ツールの結果の代わりにモデルへ返す。それを説明する記事がこの仕組みから引き出しているのは、強制がどこに属するべきかに
ついての論である。コールバックはモデルの外側で走るのだから、そこで評価されるルールは、同じルールをプロンプトやツールの
docstring に書いた場合と違って、モデルが解釈し直せるものではない。この用法は [[DefinedTerm/neurosymbolic-validation]]
の下で展開されている。

[[SoftwareApplication/claude-code]] は [[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] において、競合に
先んじてフックを出荷し、AI コーディングエージェントの中でいまなお最も深い実装をもつものとして説明されており、権限
リクエスト、サブエージェントのライフサイクル、コンテキストの圧縮、設定の変更、ファイル監視にわたる計 30 のイベントが
リファレンスに記載されている。この記事はそれらをカデンスで分類している。セッションごとに 1 回発火するもの
（`SessionStart`、`SessionEnd`）、会話のターンごとに 1 回発火するもの（`UserPromptSubmit`、`Stop`）、そしてこの記事が
最も有用とみなす、エージェントループ内のツール呼び出しごとに発火するもの — ツールの実行前の `PreToolUse` と、成功後の
`PostToolUse` である。`PreToolUse` フックはツール呼び出しを JSON として `stdin` から受け取り、そこにはこれから実行される
コマンドや触れられるファイルパスがそのまま含まれる。フックはその呼び出しを許可することも、理由をモデルへ返しつつ拒否
することも、権限プロンプトへエスカレーションすることも、実行前にツールの入力を書き換えることもできる。

Claude Code の 2 つの判断機構は、この記事では互いに逆向きに失敗する代替手段として説明されている。フックは終了コードで
シグナルを出すこともできる — `exit 2` は呼び出しをブロックし `stderr` を理由としてモデルへ返し、`exit 0` は判断なしを
報告する — し、`exit 0` した上で `allow`、`deny`、`ask` のいずれかの `permissionDecision` を載せた
`hookSpecificOutput` ブロックを出力することもできる。JSON はスクリプトが `0` で終了したときにしか読まれないので、不正な
形式の deny はそもそもパースされず呼び出しは進んでしまう。つまり JSON の経路は fail open であり、一方 `exit 2` は
`stdout` の内容が何であれブロックするので fail closed である。この記事自身の運用は、コマンドが決して実行されてはならない
ケースには `exit 2` を使い、明確なメッセージやより柔らかい結果のほうが重要な場合には JSON 形式を使う、というものである。
また `exit 2` がイベントによって異なる意味をもつ点にも注意を促している。

Anthropic 自身の Claude Code のドキュメントは、同じ強制についての論を一文で述べている — CLAUDE.md の指示は助言であり、
フックは決定論的でアクションが起きることを保証する — とともに、上記の説明が扱っていない用途を付け加えている。ターンの
*終了*をいつ許すかをゲートすることである。`Stop` フックはチェックをスクリプトとして走らせ、それが通るまでターンの終了を
ブロックする。これはテストスイートやビルドを、エージェントがそれを満たさずには自ら完了を宣言できない条件に変える。
ドキュメントはその上限も記している。Claude Code は 8 回連続でブロックされるとフックを上書きしてターンを終了するので、
この機構はエージェントを縛るものであって、ループに閉じ込めるものではない。同じドキュメントは、フックが求めに応じて
エージェント自身によって書かれうることにも触れている。

## 適用される場面

フックが適用されるのは、ある結果が単に望ましくないというだけでなく、不可能でなければならない場面である。
[[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] は繰り返し現れるケースとして、破壊的なシェルコマンド、
`.env` ファイル・秘密情報・本番設定へのアクセス、そして組織が依拠する 1 つか 2 つの CI/CD 標準を挙げている。そして実際に
最もよく使われているフックは最も地味なものだと報告している — ファイル編集のたびに走る `PostToolUse` のフォーマッタと
リンタである。この機構は、そもそもランタイムがそれをサポートしているエージェントを前提とし、かつルールがツール呼び出し
だけからコードで判定できることを前提とする。

配置場所はそのポリシーのスコープそのものである。個人のマシン全体に効く安全網ならユーザー設定、チームの標準ならプロジェクト
にコミットされる `.claude/settings.json`、組織のガードレールなら管理者が制御するマネージドポリシー設定である。その配置は
同時に、この機構の主要な失敗モードでもある。フックはランタイムがユーザーの権限で自動的に実行するコードであり、
`SessionStart` フックはプロジェクトを開いた瞬間、何かを打ち込む前に走る — つまり、設定ファイルに書き込めるものは何でも
実行されるコードを仕込める。この記事は、リポジトリの設定に悪意ある `SessionStart` フックを仕込んだ 2026 年 4 月の PyPI
ワームを挙げ、設定ファイルを CI の設定と同じように扱うよう助言している。あらゆる変更をレビューすること、そしてクローン
したリポジトリの `.claude` フォルダを、開く前にレビューすることである。

この記事はまたコストの観点から使いすぎに反対してもいる。フックはエージェントループの内側で走るので、一致するツール呼び出し
のたびにスクリプトを起動する分を支払うことになる。そして、その重要な少数の外にあるものはすべてプロンプトとスキルに属する
と論じる。そこでならたまの取りこぼしは危険ではなく煩わしいだけだからである。この慣行がどれだけ定着しているかは、その
広がりから読み取れる。記事によれば、Cursor は同じ終了コードのセマンティクスを保ったままバージョン 1.7 でフックを出荷し、
Gemini CLI と GitHub Copilot CLI はそれぞれ独自のフックシステムを出荷し、OpenAI Codex は Claude Code の命名を映した 5 つの
イベントをもつ実験的なフックをフィーチャーフラグの背後に追加した — そして Claude Code の JSON-on-`stdin` と `exit 2` で
ブロックという設計が事実上の慣習になりつつある。
