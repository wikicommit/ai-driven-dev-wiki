フックとは、行動をモデルの裁量に委ねるのではなく、エージェントのワークフロー上の定められた地点で何かを自動的に実行する設定である。Anthropic の Claude Code のドキュメントは、この仕組みの価値を決定性として枠づける。コンテキストファイル内の指示は助言的であるのに対し、フックは決定論的で、その行動が確実に起こることを保証する——これが、例外なく毎回必ず起こらなければならない行動にフックを使う理由として示されている。具体的な実装は、何をきっかけに発火するのか、そして何が実行されるのかにおいて大きく異なる。

## 用法

**Claude Code** はフックを、エージェントのライフサイクル上の特定の地点で実行されるユーザー定義のコマンドとして実装している。そのドキュメントはフックを `CLAUDE.md` の指示と直接対比する。後者は助言的だが、フックは決定論的でその行動が起こることを保証する。フックは `.claude/settings.json` で設定し、`/hooks` で一覧でき、エージェント自身に書かせることもできる——ドキュメントの例は「ファイル編集のたびに eslint を実行するフックを書いて」あるいは「migrations フォルダへの書き込みをブロックするフックを書いて」といったプロンプトである。Stop フックはこれとは別に、チェックをスクリプトとして実行し、それが通るまでターンの終了をブロックする方法として説明されている。ただし Claude Code は8回連続でブロックされるとフックを上書きしてターンを終了させる、という但し書きがある。

**Kiro** はフックを、ファイルの保存・作成・削除、あるいは手動トリガーによって、*エージェント* にバックグラウンドでタスクを実行させるイベント駆動の自動化として実装している。その発表記事はフックを「あなたが見落としたものを捉える経験豊富な開発者のように」振る舞うものと説明し、例として React コンポーネントが保存されたときにテストファイルを更新すること、API エンドポイントが変わったときに README ファイルを更新すること、コミット前に漏洩した認証情報をスキャンすることを挙げる。セットアップは平易な言葉によるプロンプトから行い、そこから Kiro が最適化されたシステムプロンプトを生成し、監視対象のリポジトリフォルダを選択する。そのフックを Git にコミットすれば、その基準がチーム全体に適用される。

この違いは押さえておく価値がある。Claude Code のフックはスクリプトを決定論的に実行するのに対し、Kiro のフックはタスクを実行するためにエージェントを派遣する。したがってフックの *発火* は決定論的だが、その *行動* はそうではない。Kiro の発表記事はさらに、フックを個人的な設定ではなくチームレベルの設定として位置づけ——Git にコミットして全員が同じチェックを受けられるようにする——注意深い開発者がコードを提出する前に頭の中で走らせるチェックリストになぞらえている。Claude Code のドキュメントは、フックの設定が組織的にどこに置かれるべきかについて同等の主張をしていない。

### フックの解剖：Claude Code のモデル

Anthropic の専用のフックガイドは、この考え方の成熟した実装が何を伴うのかが分かる程度に詳しく仕組みを記している。フックの登録は3つの部分からなる。待ち受ける **イベント**、そのイベントのどの発生を発火対象にするかを絞り込む省略可能な **マッチャー**、そして実際に実行される1つ以上の **ハンドラ** である。

イベントの一覧は長く、ファイル編集だけでなくセッションのライフサイクル全体にわたる。セッションの境界（`SessionStart`、`SessionEnd`、`Setup`）、プロンプトの処理（`UserPromptSubmit`、`UserPromptExpansion`）、ツール呼び出しのサイクル（`PreToolUse`、`PermissionRequest`、`PermissionDenied`、`PostToolUse`、`PostToolUseFailure`、`PostToolBatch`）、委譲（`SubagentStart`、`SubagentStop`）、ターンの境界（`Stop`、`StopFailure`）、コンテキスト管理（`PreCompact`、`PostCompact`）、設定とファイルシステムの変更（`ConfigChange`、`CwdChanged`、`DirectoryAdded`、`FileChanged`、`InstructionsLoaded`、`WorktreeCreate`、`WorktreeRemove`）、そして MCP サーバーとのやり取り（`Elicitation`、`ElicitationResult`）を網羅する。マッチャーが何をフィルタするかはイベントごとに異なる。ツール呼び出し系のイベントではツール名、`SessionStart` ではセッションの開始のされ方、`Notification` では通知の種類、`SubagentStart`/`SubagentStop` ではエージェントの種類、といった具合であり、マッチャーをまったくサポートしないイベントもいくつかある。個々のハンドラに付く別個の `if` フィールドは、パーミッションルールの構文を用いてツール名 *と引数* を組み合わせてフィルタするため、フックをすべての Bash 呼び出しではなく `Bash(git *)` に限定できる——もっともドキュメントは、このフィルタはベストエフォートであり、コマンドをパースできない場合はフェイルオープンになるため、厳格な許可や拒否の強制に使うべきではないと注記している。

ハンドラはシェルコマンドに限られない。5つのハンドラ型が文書化されている。`command`（シェルコマンド。一般的なケース）、`http`（イベントデータをエンドポイントに POST し、エンドポイントは command フックが出力するのと同じ JSON を返す）、`mcp_tool`（接続済みの MCP サーバー上のツールを呼び出す）、`prompt`（単一ターンの LLM による評価。既定では Haiku で実行される）、そして `agent`（実験的な複数ターンのハンドラで、ファイルを読みコマンドを実行してから判定を返すサブエージェントを生成する）である。後ろの2つは、決定論的なルールではなく判断を要する意思決定に対するドキュメントの答えであり、両者の役割分担も明快に示されている。イベントの入力データだけで判断できるなら prompt フックを、判断をコードベースの実際の状態に照らして検証する必要があるなら agent フックを使う、というものだ。どちらも `{"ok": ..., "reason": ...}` を返す。prompt フックはさらに `Stop` イベントにおいて `"impossible": true` を設定でき、決して満たされえない条件であることを示してターンを終了させられる。

command フックとのやり取りは stdin、stdout、stderr、および終了コードを通じて行われる。イベントのデータは JSON として stdin に届く。終了コード 0 は異議なしを報告し（いくつかのイベントについては、stdout をプレーンテキストとしてモデルのコンテキストに注入する）、終了コード 2 は stderr のメッセージを理由として行動をブロックし、それ以外の終了コードは、stdout が有効な JSON オブジェクトを載せていない限り、ブロックしないエラーとして扱われる。終了コードに頼る代わりに構造化された JSON を出力すれば、より細かい制御が得られる。`PreToolUse` フックは `permissionDecision` として `allow`、`deny`、`ask` を理由とともに返してモデルにフィードバックでき、`UserPromptSubmit` フックは `hookSpecificOutput.additionalContext` を通じてテキストを注入できる。ドキュメントは、1つのフックの中でこの2つのスタイルを混ぜるべきではないと明言している。

同じイベントに複数のフックがマッチした場合、それらはすべて並列に実行され、すべて最後まで実行される——あるフックが `deny` を返しても、兄弟フックの副作用が抑制されるわけではない。その後、出力が統合される。パーミッションの判断は `deny`、`defer`、`ask`、`allow` の順で最も制限の強いものが勝ち、注入されたコンテキストはすべてのフックのものが保持される。

フックがどこに登録されるかがそのスコープを決める。文書化されている登録場所は、個人設定、プロジェクト設定、gitignore されたローカル設定、組織全体の管理ポリシー、プラグイン、そして——注目すべきことに——個々の [[DefinedTerm/agent-skills]] 定義や [[DefinedTerm/subagents]] 定義のフロントマターにまで及ぶ。この2つは登録の有効期間が異なる。スキルのフロントマターで宣言されたフックは、そのスキルが呼び出されると以後そのセッションの間ずっと有効であり続けるのに対し、サブエージェントのフロントマターで宣言されたフックは、そのサブエージェントが動作している間だけ適用される。

ドキュメントはこの仕組みの限界についても率直である。`PostToolUse` フックは何も取り消せない。ツールはすでに実行されてしまっているからである。command フックは stdout、stderr、終了コードを通じてしか語れず、スラッシュコマンドやツール呼び出しを引き起こすことはできない。またタイムアウトはハンドラの型によって異なり、`command`、`http`、`mcp_tool` のフックは既定で10分、`prompt` フックは30秒、`agent` フックは60秒である。

## 関連用語

フックは [[DefinedTerm/context-files]] の下で概観され、[[SoftwareApplication/claude-code]] と [[SoftwareApplication/kiro]] について整理されている、リポジトリレベルの設定機構の一つである。チェックを強制的に実行させる手段として [[DefinedTerm/backpressure]] と重なる。チェック自体がスクリプトではなく別のモデル呼び出しである場合は [[DefinedTerm/llm-as-judge]] を参照——`prompt` と `agent` のハンドラ型は、まさにそのパターンをフックの仕組みの内側に直接実装したものである。
