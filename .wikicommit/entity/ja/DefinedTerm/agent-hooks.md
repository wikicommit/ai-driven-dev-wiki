エージェントフックは、AI エージェントのツール呼び出しを開発者が横取りできるようにするものであり、呼び出しが実行される
直前または直後に独自のロジックを走らせることで、その呼び出しを承認したり、ブロックしたり、事後処理を行ったりできる
ようにする。この機構は、ランタイムが読み込む外部設定としても、エージェントフレームワークが公開するプロセス内の
コールバック API としても現れる。Google の Gemini API は前者を、名前付きルールの下にイベント定義をまとめ、標準の RE2
正規表現でツール名に照合する `hooks.json` 設定として実装しており、[[SoftwareApplication/strands-agents]] は後者を、
フレームワークのライフサイクルイベントに対して登録されるコールバックとして実装している。

この機構が*何のためのもの*かを最も直截に述べているのは
[[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] である。フックを走らせるかどうかを決めるのはモデルでは
なくランタイムなので、フックに実装されたルールは毎回必ず効く。同じルールをプロンプトやコンテキストファイルに書いた
場合、それはモデルがそのターンで従うかもしれないし従わないかもしれない提案にすぎない。この記事はフックを、エージェント
の確率的な指示追従に対する決定論的な釣り合いとして提示し、モデルがコンテキストをどう読むかに依存してはならない少数の
ルールのために取っておくべきだとしている。

## 用法

Google の Gemini API では、フックは 2 つのライフサイクルイベントのいずれかで発火する。`pre_tool_execution` はツール
呼び出しの前に走り、実行前にそれを承認（`allow`）またはブロック（`deny`）できる — ブロックされた場合、モデルには拒否
理由が見えるので適応できる。`post_tool_execution` は呼び出しの完了後に走り、コードの整形、テストの実行、テレメトリの
記録といった事後処理しか行えない。すでに起きてしまったアクションを取り消すこともブロックすることもできないからである。
各ルールグループは `matcher`（`code_execution`、`read_file`、`write_file` のようなツール名に照合される正規表現）と、
それが一致したときに走らせる `hooks` の順序付きリストを指定する。フックは `command`（サンドボックス内で走り、イベントを
JSON として標準入力から読み、判断を標準出力へ書く）か `http` ハンドラ（サンドボックスの送信プロキシを通してイベントを
外部の HTTPS エンドポイントへ POST する。このプロキシは送信リクエストに認証ヘッダーを差し込めるので、フックの設定その
ものに秘密情報を保存する必要がない）のいずれかである。コマンドスクリプトがクラッシュした場合、HTTP フックが 2xx 以外の
ステータスを返した場合、あるいはフックがタイムアウトしたり認識できない出力を返した場合、ランタイムはそれを呼び出しの
ブロックではなく承認として扱う。したがって壊れたフックがエージェントをデッドロックさせることはない。Gemini API の実装
では、フックの適用範囲はサンドボックス自身の組み込みツール（コード実行とファイルシステム操作）に限られ、カスタムの
関数呼び出しツールや、コンテナの外で処理される外部 MCP サーバーのツールに対しては発火しない。

同じ実行前の横取りは、[[SoftwareApplication/strands-agents]] ではプロセス内の API として現れる。ここでは
`HookProvider` が `HookRegistry` を通じて `BeforeToolCallEvent` にコールバックを登録する。コールバックは保留中の呼び出しの
名前と入力を受け取り、`event.cancel_tool` にメッセージを代入することでそれをブロックする。フレームワークはツールの結果の
代わりにそのメッセージをモデルへ返す。この仕組みからその記事が引き出しているのは、強制がどこに属するかについての議論で
ある。コールバックはモデルの外側で走るので、そこで評価されるルールは、同じルールをプロンプトやツールの docstring に書い
た場合と違い、モデルが解釈し直せるものではない。この用法は [[DefinedTerm/neurosymbolic-validation]] の下で展開されて
いる。

[[SoftwareApplication/claude-code]] は [[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] において、競合に
先んじてフックを出荷し、AI コーディングエージェントの中でいまなお最も踏み込んだ実装を持つものとして述べられている。その
リファレンスは合計 30 のイベントを文書化しており、権限リクエスト、サブエージェントのライフサイクル、コンテキストの圧縮、
設定の変更、ファイル監視までを網羅する。この記事はそれらを発火の頻度で分類している。セッションごとに一度発火するもの
（`SessionStart`、`SessionEnd`）、会話のターンごとに一度発火するもの（`UserPromptSubmit`、`Stop`）、そして記事が最も
有用とみなす、エージェントループ内のツール呼び出しごとに発火するもの — ツール実行前の `PreToolUse` と、成功後の
`PostToolUse` である。`PreToolUse` フックはツール呼び出しを JSON として `stdin` から受け取り、そこにはこれから触れられる
正確なコマンドやファイルパスが含まれる。そしてその呼び出しを許可するか、理由をモデルへ返しつつ拒否するか、権限プロンプト
へエスカレートするか、実行前にツールの入力を書き換えるかができる。

Claude Code の 2 つの判断機構は、その記事では逆方向に失敗する代替手段として文書化されている。フックは終了コードで合図を
送ることができる — `exit 2` は呼び出しをブロックし、`stderr` を理由としてモデルへ返す。`exit 0` は判断なしを報告する。
あるいは `exit 0` して、`allow`、`deny`、`ask` のいずれかの `permissionDecision` を載せた `hookSpecificOutput` ブロックを
出力することもできる。JSON はスクリプトが `0` で終了したときにしか読まれないので、不正な形式の拒否はパースされず呼び出しは
進行する。つまり JSON の経路はフェイルオープンであり、一方 `exit 2` は `stdout` の中身が何であれブロックするのでフェイル
クローズである。記事自身の実践は、コマンドが決して走ってはならない場合には `exit 2` を使い、明確なメッセージやより穏やかな
結果のほうが重要な場合には JSON 形式を使うというものである。また `exit 2` がイベントによって異なる意味を持つことにも注意を
促している。

Anthropic 自身の Claude Code のドキュメントは、同じ強制に関する議論を一行で述べている — CLAUDE.md の指示は助言的であり、
フックは決定論的でアクションが起きることを保証する — そのうえで、上記の説明が扱っていない用途を加えている。ターンの*終了*
が許されるタイミングをゲートすることである。`Stop` フックはチェックをスクリプトとして走らせ、そのドキュメントの言葉では、
それが通るまでターンの終了をブロックする — エージェントと「完了した」という宣言との間に、テストスイートやビルドを挟むので
ある。それがどれほど強固かは、このページのどの出典に尋ねるかによる。
[[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] は、ブロックされた `Stop` は理由をモデルへ返して継続を
求めるものだと注意を促し、絶対的な保証というよりは強い後押しだとしている。ドキュメントは上限も記録している。連続 8 回
ブロックされると、Claude Code はフックを上書きしてターンを終了する。同じドキュメントは、フックは求めればエージェント自身に
書かせられるとも述べている。

何も判断せず何もブロックしない用法は [[BlogPosting/making-ai-follow-team-rules]] で述べられている。そこではフックは、
ツール呼び出しを取り締まるのではなく、チームのコーディング規約をエージェントへ運び込むものである。その記事が述べる
プラグイン [[SoftwareApplication/pfmls-stylepack]] は、エージェントループ内の 2 つの瞬間にフックを掛ける。エージェントが
ファイルを書いた直後には、そのファイルの本文を読んで、該当する規約ルールを最大 2 件テキストとして注入する。そして
エージェントが終了しようとするときには、変更全体を `git diff` として読み、最大 4 件を注入する。セッション開始にもフックを
掛けるが、こちらは別の仕事のためである — リポジトリの言語環境によって選ばれたチーム全体のコンテキストを注入し、さらに中央
リポジトリから現在のルールをバックグラウンドで取得する。2 つめの地点で注入されるテキストは、それ自身について、ハードな
失敗ではなくレビューを促すリマインダーであると述べており、それをどう扱うかはエージェントが決める。この配置についての
記事の論拠は、強制についてではなく位置についてのものである。セッションの開始時に一度与えられたルールは、セッションが長く
なるにつれて適用されなくなる。記事はこれを [[DefinedTerm/lost-in-the-middle]] に帰しており、だからこそルールはそれが適用
されるコードのすぐ隣で再度与えられる。また、すべてのファイル書き込みにフックを掛けることから生じる制約も報告されている —
フックは即座に返らなければならないので、ルールの選択はファイル名パターンと正規表現で行われる。以前のモデルベースの関連性
判定はリクエストあたり約 10 秒を要したという。

## 適用される場面

フックは、ある結果が単に推奨されないのではなく不可能でなければならない場面で適用される。
[[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] は繰り返し現れるケースとして、破壊的なシェルコマンド、
`.env` ファイル・秘密情報・本番設定へのアクセス、そして組織が依存する 1 つか 2 つの CI/CD 標準を挙げている。実際に最も
よく使われるフックは、最も地味なものだと記事は報告している — ファイル編集のたびに走る `PostToolUse` のフォーマッタと
リンタである。これはランタイムがそもそもこの機構をサポートしているエージェントを前提とし、またルールがツール呼び出しだけ
からコードで判定できることを前提としている。

配置はポリシーのスコープそのものである。個人用・マシン全体のセーフティネットにはユーザー設定、チーム標準にはプロジェクト
にコミットされた `.claude/settings.json`、組織のガードレールには管理者が制御するマネージドポリシー設定を使う。その配置は
同時に、この機構の主たる失敗モードでもある。フックはランタイムがユーザーの権限で自動的に実行するコードであり、
`SessionStart` フックはプロジェクトを開いた瞬間、何かを入力する前に走る — つまり設定ファイルに書き込めるものなら何でも、
走るコードを仕込める。記事は、リポジトリ設定に悪意ある `SessionStart` フックを仕込んだ 2026 年 4 月の PyPI ワームを挙げ、
設定ファイルは CI 設定と同じように扱うべきだと助言している。すべての変更をレビューし、クローンしたリポジトリの `.claude`
フォルダは開く前にレビューせよ、と。

記事はまたコストの観点から使いすぎにも反対している — フックはエージェントループの内側で走るので、一致するツール呼び出しの
たびにスクリプト起動のコストを払う — そして、その決定的に重要な少数以外はすべてプロンプトとスキルに属するとしている。
そこでは取りこぼしが起きても、危険ではなく煩わしいだけで済むからである。この実践がどれほど確立しているかは、その広がりから
読み取れる。記事によれば、Cursor はバージョン 1.7 で同じ終了コードの意味論を保ったままフックを出荷し、Gemini CLI と
GitHub Copilot CLI はそれぞれ独自のフック機構を出荷し、OpenAI Codex は Claude Code の命名を映した 5 つのイベントを持つ
実験的なフックをフィーチャーフラグの背後に追加した — Claude Code の「JSON を `stdin` で渡し `exit 2` でブロックする」設計が
事実上の慣行となりつつある。
