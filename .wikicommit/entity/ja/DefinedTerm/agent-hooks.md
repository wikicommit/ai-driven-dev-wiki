エージェントフックは、開発者が AI エージェントのツール呼び出しに割り込み、呼び出しが実行される直前または直後にカスタムロジックを実行できるようにするものであり、これによって呼び出しを承認、ブロック、または事後対応できる。この仕組みは、ランタイムが読み込む外部設定としても、エージェントフレームワークが公開するプロセス内のコールバック API としても現れる。Google の Gemini API は前者を、名前付きのルールのもとにイベント定義をまとめ、標準の RE2 正規表現でツール名と照合する `hooks.json` 設定として実装している。一方、[[SoftwareApplication/strands-agents]] は後者を、フレームワークのライフサイクルイベントに対して登録されるコールバックとして実装している。

この仕組みが*何のために*あるのかを最も直接的に述べているのは [[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] である。フックを実行するかどうかを決めるのはモデルではなくランタイムであるため、フックで強制されるルールは毎回確実に守られる。これに対し、同じルールをプロンプトやコンテキストファイルに書いた場合、それはモデルがあるターンで従うかもしれないし従わないかもしれない提案にすぎない。この投稿はフックを、エージェントの確率的な指示追従に対する決定論的な対抗手段として提示し、モデルがコンテキストをどう読むかに左右されてはならない少数のルールのためにフックを取っておく。

## 用法

Google の Gemini API では、フックは 2 つのライフサイクルイベントのいずれかで発火する。`pre_tool_execution` はツール呼び出しの前に実行され、実行前にその呼び出しを承認（`allow`）またはブロック（`deny`）できる — ブロックされた場合、モデルは却下の理由を受け取り、それに適応できる。`post_tool_execution` は呼び出しの完了後に実行され、すでに起きた行動を取り消したりブロックしたりはできないため、コードの整形、テストの実行、テレメトリの記録といった事後作業のみを行える。各ルールグループは、`matcher`（`code_execution`、`view_file`、`write_to_file` などのツール名と照合される正規表現）と、一致したときに実行する `hooks` の順序付きリストを指定する。フックは `command`（サンドボックス内で実行され、イベントを JSON として stdin から読み取り、判定を stdout に書き出す）か `http` ハンドラー（サンドボックスの送信プロキシを経由して外部の HTTPS エンドポイントにイベントを POST する。このプロキシは送信リクエストに認証ヘッダーを注入できるため、シークレットをフック設定そのものに保存する必要がない）のいずれかである。コマンドスクリプトがクラッシュした場合、HTTP フックが 2xx 以外のステータスを返した場合、あるいはフックがタイムアウトしたり認識できない出力を返したりした場合、ランタイムはそれを呼び出しのブロックではなく承認として扱うため、壊れたフックがエージェントをデッドロックさせることはない。Gemini API の実装では、フックの対象はサンドボックス自身の組み込みツール（コード実行とファイルシステム操作）に限られ、コンテナの外で処理されるカスタムの関数呼び出しツールや外部の MCP サーバーのツールに対しては発火しない。

同じ実行前の割り込みは、[[SoftwareApplication/strands-agents]] ではプロセス内の API として現れる。そこでは `HookProvider` が `HookRegistry` を通じて `BeforeToolCallEvent` にコールバックを登録する。コールバックは保留中の呼び出しの名前と入力を受け取り、`event.cancel_tool` にメッセージを代入することでそれをブロックする。フレームワークはそのメッセージを、ツールの結果の代わりにモデルへ返す。これを説明する投稿がこの仕組みから導き出すのは、強制をどこに置くべきかについての主張である。コールバックはモデルの外側で実行されるため、そこで評価されるルールは、プロンプトやツールの docstring に書かれた同じルールとは異なり、モデルが解釈し直せるものではない。この使い方は [[DefinedTerm/neurosymbolic-validation]] で詳しく扱われている。

[[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] では、[[SoftwareApplication/claude-code]] は競合に先駆けてフックを搭載し、現在も AI コーディングエージェントの中で最も深い実装を持つと説明されている。そのリファレンスには合計 30 のイベントが記載されており、パーミッション要求、サブエージェントのライフサイクル、コンテキストのコンパクション、設定の変更、ファイル監視をカバーしている。投稿はそれらを発火の頻度でグループ分けしている。セッションごとに 1 回発火するもの（`SessionStart`、`SessionEnd`）、会話のターンごとに 1 回発火するもの（`UserPromptSubmit`、`Stop`）、そして投稿が最も有用とみなす、エージェント的ループ内のツール呼び出しのたびに発火するもの — ツールの実行前の `PreToolUse` と、成功後の `PostToolUse` — である。`PreToolUse` フックは、これから触れられる正確なコマンドやファイルパスを含むツール呼び出しを JSON として `stdin` から受け取り、その呼び出しを許可する、理由をモデルにフィードバックしたうえで拒否する、パーミッションプロンプトにエスカレーションする、あるいは実行前にツールの入力を書き換えることができる。

Claude Code の 2 つの判定の仕組みは、この投稿では、互いに逆方向に失敗する代替手段として説明されている。フックは終了コードで合図することができる — `exit 2` は呼び出しをブロックして `stderr` を理由としてモデルにフィードバックし、`exit 0` は判定なしを報告する。あるいは、`exit 0` で終了したうえで、`allow`、`deny`、`ask` のいずれかの `permissionDecision` を持つ `hookSpecificOutput` ブロックを出力することもできる。JSON はスクリプトが `0` で終了した場合にのみ読み取られるため、不正な形式の deny は決して解析されず、呼び出しはそのまま進む。つまり JSON の経路はフェイルオープンであり、一方 `exit 2` は `stdout` の内容にかかわらずブロックするためフェイルクローズである。投稿自身の実践は、絶対に実行されてはならないコマンドには `exit 2` を使い、明確なメッセージやより穏やかな結果のほうが重要な場合には JSON の形式を使うというものである。投稿はまた、`exit 2` はイベントによって意味が異なると注意を促している。

Anthropic 自身の Claude Code のドキュメントは、同じ強制の議論を 1 行で述べている — CLAUDE.md の指示は助言的なものであり、フックは決定論的でアクションが確実に実行されることを保証する — そして、フックを使ってターンがいつ*終了*してよいかを制御する方法を説明している。`Stop` フックはチェックをスクリプトとして実行し、そのドキュメントの言葉では、それが通るまでターンの終了をブロックする — テストスイートやビルドを、エージェントと、エージェント自身による完了宣言との間に置くのである。それがどれほど確実かは、このページのどの情報源に尋ねるかによって異なる。[[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] は、ブロックされた `Stop` は理由をモデルにフィードバックして作業の継続を求めるものであり、絶対的な保証ではなく強い後押しだと注意を促している。ドキュメントには上限も記載されている。Claude Code は 8 回連続でブロックされると、フックを無視してターンを終了する。同じドキュメントは、フックは依頼に応じてエージェント自身が書くこともできると述べている。

2026 年 6 月 18 日付の Anthropic の投稿 [[BlogPosting/steering-claude-code]] は、フックを Claude Code に指示を与える 7 つの方法の 1 つに位置づけ、その位置づけを強制だけでなくコンテキストのコストによって説明している。投稿はフックを、`settings.json`、管理ポリシー設定、あるいはスキルやサブエージェントのフロントマターに登録される、ユーザー定義のコマンド、HTTP エンドポイント、または LLM プロンプトとして説明し、command、HTTP、`mcp_tool`、prompt、agent の 5 つの種類を挙げている。いずれも決定論的にトリガーされる。最初の 3 つは実行も決定論的であるのに対し、prompt フックと agent フックは一連のルールではなく Claude の判断によって出力を決める。フックの設定はメインのコンテキストウィンドウの外にある — command、HTTP、`mcp_tool` フックについてはハーネスがハンドラーを実行し、prompt フックと agent フックについては別のウィンドウでモデル呼び出しを行う — ため、投稿はフックをコンテキストのコストが低く、[[DefinedTerm/compaction]] を完全に迂回するものとみなしている。そこから投稿が引き出す帰結は、設定がそれを返さない限り、フックの出力の大半はメインのコンテキストに届かないということである。ブロックするフックの標準エラー出力は、Claude が呼び出しの拒否された理由を知るために保持されるが、`PreCompact` フックがチャット履歴をファイルにバックアップしても、Claude はどのファイルにそれが保存されているかを知らない。

何も判定せず何もブロックしない使い方が [[BlogPosting/making-ai-follow-team-rules]] で説明されている。そこではフックは、エージェントのツール呼び出しを取り締まるのではなく、チームのコーディング規約をエージェントに届けるために使われる。この投稿が説明するプラグイン [[SoftwareApplication/pfmls-stylepack]] は、エージェントループ内の 2 つの時点にフックする。1 つはエージェントがファイルを書き込んだ直後で、そのファイルの本文を読み取り、一致する規約ルールを最大 2 つまでテキストとして注入する。もう 1 つはエージェントが作業を終えようとする時点で、変更全体を `git diff` として読み取り、最大 4 つまで注入する。セッション開始時にもフックするが、これは別の目的のためである — リポジトリの言語環境に応じて選ばれたチーム全体のコンテキストを注入し、中央リポジトリから最新のルールをバックグラウンドで取得する。2 つ目の時点で注入されるテキストは、自らを致命的な失敗ではなくレビューのためのリマインダーであると述べており、それをどう扱うかはエージェントが決める。この配置についての投稿の主張は、強制に関するものではなく位置に関するものである。セッションの開始時に一度だけ与えられたルールは、セッションが長くなるにつれて適用されなくなる。投稿はこれを [[DefinedTerm/lost-in-the-middle]] によるものとし、そのためルールを、それが適用されるコードのすぐ隣で改めて与える。投稿はまた、ファイル書き込みのたびにフックすることから生じる制約も報告している — フックは即座に応答を返さなければならないため、ルールの選択はファイル名のパターンと正規表現で行われる。以前のモデルベースの関連性チェックでは、リクエストごとに約 10 秒かかっていたという。

実践者による Claude Code のフックのリファレンスガイド [[BlogPosting/claude-code-hooks-complete-guide]] は、この仕組みをプロンプトとの対比だけでなく、パーミッションシステムとの対比の中に位置づけている。その説明では、`PreToolUse` の `deny` はあらゆるパーミッションモードのチェックより前に評価されるため、`bypassPermissions` のもとでも呼び出しをブロックする。一方、フックの `allow` は対話的なプロンプトを省略するだけであり、設定内の一致する `deny` や `ask` のルールを上書きはしない — フックはパーミッションシステムが許可する範囲を狭めることはできても、広げることは決してできない。同じガイドは、判定の 2 つの形式を記録し、それがフックのバグの最もよくある原因だとしている。`PreToolUse` は `hookSpecificOutput.permissionDecision` を通じて応答するのに対し、判定が可能な他のイベントの大半はトップレベルの `decision: "block"` を使い、誤った形式を返すと何も起こらないまま黙って無視される。ガイドはまた、英字、数字、`_`、`|` のみからなる matcher は完全一致の文字列として扱われるため、`mcp__memory` のようなサーバーの接頭辞は、`mcp__memory__.*` のような正規表現として書かない限り、そのサーバーのツールには決して一致しないと述べている。

## 適用される場面

フックが適用されるのは、ある結果を単に抑止するのではなく、起こりえないものにしなければならない場面である。[[BlogPosting/agentic-coding-hooks-deterministic-ai-guardrails]] は、繰り返し現れるケースとして、破壊的なシェルコマンド、`.env` ファイル・シークレット・本番設定へのアクセス、そして組織が依存している 1 つか 2 つの CI/CD 標準を挙げている。実際に最もよく使われるフックは、最も地味なもの — ファイルの編集のたびに実行される `PostToolUse` のフォーマッターとリンター — だと投稿は報告している。

同じ投稿では、配置の場所がそのままポリシーの適用範囲となる。個人的なマシン全体のセーフティネットにはユーザー設定、チームの標準にはプロジェクトにコミットされた `.claude/settings.json`、組織のガードレールには管理者が管理する管理ポリシー設定である。投稿は、この配置はセキュリティの問題でもあると論じる。フックはランタイムがユーザーの権限で自動的に実行するコードであり、`SessionStart` フックはプロジェクトが開かれた瞬間、何かが入力される前に実行される — したがって、設定ファイルに書き込めるものは何であれ、実行されるコードを仕込むことができる。投稿は、リポジトリの設定に悪意のある `SessionStart` フックを仕込んだ 2026 年 4 月の PyPI ワームを挙げ、設定ファイルを CI 設定と同じように扱うこと、すなわちすべての変更をレビューし、クローンしたリポジトリの `.claude` フォルダーを開く前にレビューすることを勧めている。

投稿はまた、コストの観点から過剰な使用に反対している — フックはエージェントループの内部で実行されるため、一致するツール呼び出しのたびにスクリプトを起動するコストがかかる — そして、決定的に重要な少数のもの以外はすべて、ときおりの見落としが危険ではなく煩わしい程度で済むプロンプトやスキルに属すると考えている。この実践がどれほど定着しているかは、その広がりから読み取れる。投稿によれば、Cursor はバージョン 1.7 で同じ終了コードの意味論を保ったままフックを搭載し、Gemini CLI と GitHub Copilot CLI はそれぞれ独自のフックシステムを搭載し、OpenAI Codex は Claude Code の命名を踏襲した 5 つのイベントを持つ実験的なフックをフィーチャーフラグの背後に追加した — そして、Claude Code の JSON を `stdin` で受け取り `exit 2` でブロックする設計が事実上の標準になりつつある。

Claude Code の指示をどこに置くべきかについての Anthropic の投稿 [[BlogPosting/steering-claude-code]] は、強制の議論を配置のルールへと落とし込んでいる。[[DefinedTerm/claude-md]] に書かれた「X のたびに、必ず Y をする」という形の指示は、代わりにフックに置くべきである。モデルがフォーマッターを実行することを選ぶのと、フォーマッターが自動的に実行されるのとは別物だからである。そして「これは決してしてはならない」は、そもそも指示の役割ではない。プレッシャーのもとで、長いセッションの中で、曖昧な状況で、あるいは読み込んだファイル内のプロンプトインジェクションによって、モデルはプロンプトで与えられたルールに従えなくなることがあるからである。この投稿は、強制の方法としてフックとパーミッションを挙げ、組織全体の決定論的なガードレールを強制する唯一の方法として、管理者が配布し、ユーザーのローカル設定では上書きできない管理設定を挙げている。

[[BlogPosting/claude-code-hooks-complete-guide]] は、この役割分担を一言でまとめている — 「`CLAUDE.md` は説得し、パーミッションはフィルタリングし、フックは強制し反応する」 — そして、堅牢化された構成では同じ要件に対してこの 3 つすべてを動かし、それぞれが他の 2 つの取りこぼしを捕捉するようにしている。ガイドはさらに、設定レイヤー間の解決順序は Managed > Local > Project > Plugin > User であり、`allowManagedHooksOnly: true` を指定するとユーザー、プロジェクト、プラグインのフックがすべてブロックされ、組織が承認したフックのみが実行されると付け加えている。
