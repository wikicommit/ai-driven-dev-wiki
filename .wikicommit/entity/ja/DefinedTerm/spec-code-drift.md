仕様とコードの乖離とは、仕様が主張することとコードが実際にすることのあいだの食い違いであり、仕様が別個の文書として維持され、開発者がコードを更新しながら仕様の更新を後回しにするたびに蓄積していく。[[ScholarlyArticle/the-spec-growth-engine]] はこれを AI 支援開発の2つの構造的な失敗モードのうちの一つとして扱い、それを定義づける性質を不可視性だと特徴づける。リンターはこれを指摘せず、CI も指摘せず、システムは乖離を焼き付けたまま出荷される。仕様は「生きた契約ではなく歴史的な遺物となり、その後のエージェントの実行は嘘に導かれる」。

論文は、この観察自体が古いものであることを明示している——同じパターンを指摘した Reflexion Model の仕事と、同時代における「アーキテクチャの侵食」という造語を引用する——そして、新しいのはその速度のほうだと位置づける。AI コーディングエージェントが古びた仕様に導かれて毎分数百行を生成するとき、乖離した仕様による損害は従来の開発よりはるかに速く蓄積するのだ。

## 用法

同論文が提案する対抗策は、2つの導出されたグラフの上に構築された**ドリフトゲート**である。*インテントグラフ*は仕様ファイルから導出され、契約、不変条件、受け入れ基準を担う。*エビデンスグラフ*は静的コード解析から導出され、インポートとエクスポート、ルートとイベント、そしてテストを担う。両者が食い違うコミットはブロックされる。

無条件にマージをブロックするハードエラーとして4つの条件が挙げられている。孤立したコード、すなわち仕様上の所有者を持たないソースファイル。宣言されていない依存、すなわちコードが宣言されたエッジなしに仕様の境界をまたいでインポートしている状態。契約を迂回する依存、すなわちコードが別のノードの内部ファイルをインポートしている状態。そして依存先の契約の欠落、すなわち対象のノードがそもそも契約を持たない状態である。

さらに3つの条件が、ブロックを伴わない警告として報告される。コードの証跡がない宣言された依存、契約に言及のない公開エクスポート、そしてテストの証跡がない契約上の振る舞いである。

このゲートを実用的にしている仕組みは、勤勉さではなく結合である。AI エージェントが、コードの変更と*同じコミット*の中で影響を受ける仕様を更新し、エンジンがその差分を証跡と突き合わせて検査し、人間は契約レベルの行だけをレビューする。この配置について論文が掲げる主張は、それが「乖離を社会的／プロセス上の問題から構造的な不可能事へと変える」というものだ——仕様とコードを同期させ続けることが規律任せにされない、ということである。
