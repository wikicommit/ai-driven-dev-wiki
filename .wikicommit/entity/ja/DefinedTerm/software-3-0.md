Software 3.0 は、コンピュータがどのようにプログラムされるかについて Andrej Karpathy が示す系列の 3 番目の段階である。その前には、人間が明示的なコードを書く Software 1.0 と、人間がデータセット、目的関数、ニューラルネットワークのアーキテクチャを組み立て、プログラムが重みへと学習される Software 2.0 がある。Software 3.0 では、プログラムはプロンプト、コンテキスト、ツール、例、メモリ、指示として表現され、大規模言語モデルがインタプリタとなる。コンテキストウィンドウに置かれたものがそのレバーであり、モデルが行う計算はデジタル情報を対象とする。これが可能になった経緯についての彼の説明は、十分に大きなタスク集合（インターネットには多くのタスクが含まれている）で訓練されたモデルは、暗黙のうちにプログラム可能なコンピュータになる、というものである。

## 用法

Karpathy がこの転換を具体的に示すために用いる例はインストールである。彼の主張によれば、多くのプラットフォームやマシン構成をシェルスクリプトで対象にしようとすると、Software 1.0 の世界ではあらゆる細部を正確なコードで書き出す必要があるため、スクリプトは条件分岐で膨れ上がらざるをえない。彼が示す代替案は、エージェントに貼り付けるテキストのブロックとして配布されるインストール手順である。エージェントはローカル環境を読み取り、知的な行動をとり、ループの中でエラーをデバッグし、セットアップを完了させる。彼はこれを、精度は劣るがより適応的な、別種のプログラムだと述べ、「エージェントにコピー&ペーストするテキストは何か」ということ自体がいまやプログラミングの問いになっている、という実際的な帰結を導いている。

2 つ目の例は、議論をさらに推し進め、ソフトウェアが存在しなくなるところまで至る。彼が普通のやり方で作ったメニュー写真アプリには、OCR、画像生成器、フロントエンド、デプロイ、認証、決済、シークレット、インフラが必要だった。Software 3.0 版では、写真をマルチモーダルモデルに渡し、料理の画像をメニューの画像の上に直接描画するよう頼むだけである。彼の読みでは、古いスタックはモデルがいまや自ら実行できる変換のまわりに組まれた足場であり、創業者にとっての帰結は、一部のアプリケーションはそもそもアプリケーションとして存在すべきではないということである。彼は同じ論理を思弁的にハードウェアにまで広げ、ニューラルネットワークがホストプロセスとなり CPU がコプロセッサとなる姿を思い描きつつ、そこへの道のりは断片的なものになるだろうと述べている。

この枠組みはコードの外にも及ぶ。Karpathy は、古典的なプログラムは構造化データを対象としていたのに対し、新たに自動化可能になったのは、以前はまったくプログラム可能でなかった情報処理だと論じる。彼の例は、雑多なドキュメントを、要約、エンティティページ、概念ページ、矛盾、相互リンクからなる永続的な Markdown の知識ベースへと段階的にコンパイルしていくエージェントである。したがって彼が勧める問いは、AI がどの既存のワークフローを高速化できるかだけではなく、以前は不可能だったがいまや自然になった情報変換はどれか、というものである。

この枠組みは、Karpathy の具体的なプログラミング論としてではなく、時代を示すラベルとして他者に用いられることもある。[[BlogPosting/raising-productivity-floor-with-harness]] は「Software 3.0 の時代」を舞台設定とし、その中で組織的な問いを立てる。プログラムがいまやプロンプト、コンテキスト、指示であるなら、チームがかつて共有ライブラリを配布していたのと同じように互いに配布すべきなのはそうした成果物である、というものである。その記事の提案は、チームの知識をエージェントプラグインとして保持し（記事はそれが [[DefinedTerm/executable-ssot]] になる可能性をもつと述べる）、マーケットプレイスを通じて公開するというものであり、モジュールの中身はコードからプロンプトとエージェントのロジックへと変わったが、その周囲のエンジニアリング実践は引き継がれるものとして扱っている。共有モジュールをワークフロープラグインに、ライブラリの公開をマーケットプレイスへのアップロードに対応づけ、共有モジュールに適用されてきたコードレビューと品質管理は AI ワークフローにも適用されるべきだと論じている。その記事の著者は、そのすべてを成果ではなく方向性と仮説として提示している。このように読むと、この用語はモデルをプログラミングする行為だけでなく、組織が扱う素材そのものを名指すことになる。

## 適用される場面

このパラダイムのトレードオフは、その発案者自身によって率直に述べられている。精度を代償に適応性を得るものであり、したがって環境が変化し、正確な仕様では脆くなるような作業に適しており、ループの中で行動しデバッグできるだけの能力をもつモデルを前提とする。これは業界で合意された用語ではなく一個人の枠組みであり、ここでの説明は、講演のレポート記事に基づいている。その記事の文章はイベントの書き起こしからモデルによって生成され、その後に彼自身が確認したものである。
