適応的コンテキストコンパクション（Adaptive Context Compaction、ACC）は、[[ScholarlyArticle/building-effective-ai-coding-agents-for-the-terminal]] で説明されているコンテキスト管理フレームワークであり、推論の各イテレーション開始時に監視を行いながら、段階的に強度を増す削減戦略のパイプラインによってコンテキストの圧迫を管理する。これは、当該レポートが標準的手法として特徴づけるもの——典型的には容量の 95〜99% で発火する二値の緊急しきい値によって会話履歴の非可逆な要約を行うやり方であり、その結果として発動が遅れ、深刻な情報損失を招き、以後のコンパクションで誤りが累積していく——に対する代替案として提示されている。

## 用法

出発点となる観察は、ファイルの内容やコマンドの出力といったツールの観測結果が急速に蓄積し、利用可能なトークン予算の 70〜80% をしばしば占めてしまうというものである。そこで ACC は、API が報告するプロンプトトークン数を較正の基準点として用いながらトークン使用量を逐次的に監視し、5つの段階的なステージを適用する。

| ステージ | 発火条件 | 動作 |
| --- | --- | --- |
| 警告 | 70% | 監視のためにコンテキストの圧迫が記録される。データの削減は行われない |
| 観測結果のマスキング | 80% | 古いツール結果メッセージがその場でコンパクトな参照ポインタに置き換えられる。直近の出力は完全な忠実度で保持される |
| 高速プルーニング | 85% | 軽量なパスがツール結果を逆順にたどり、保護された直近性の予算を超えたものをプルーニング済みのマーカーに置き換える |
| 積極的マスキング | 90% | 保持のウィンドウが直近のツール出力だけに縮小され、その他の観測結果はすべてマスクされる |
| 完全コンパクション | 99% | 会話履歴全体がスクラッチファイルにシリアライズされ、LLM ベースの要約器が中間部分を圧縮する一方、直近のメッセージは逐語的に保持される |

レポートはマスキングとプルーニングを区別する。マスキングは内容を、外部に退避させたファイルへの参照ポインタで置き換えるものであり、プルーニングは内容を破棄する削除系の操作だが、対象は直近性のウィンドウを十分に超えた出力に限られる。より安価な戦略だけで、より破壊的なステージを完全に回避できるだけの領域を確保できることが多いとされ、とりわけ高速プルーニングのパスは LLM ベースのコンパクションよりも大幅に安価だと説明されている。

コンパクションを実質的に非損失なものにする仕組みとして、2つが挙げられている。パイプラインは *アーティファクトインデックス*——セッション中に触れたすべてのファイルと実行したすべての操作の構造化されたレジストリ——を維持し、これがコンパクションの要約にシリアライズされる。そのため、コンテキストが圧縮された後もエージェントはどのファイルを扱っていたかを記憶している。また履歴アーカイブのパスも要約に注入されるため、エージェントはアーカイブを読むことで任意の詳細を復元できる。

レポートによれば、定量的な評価では ACC によって観測結果によるコンテキスト消費のピークが約 54% 削減され、典型的な 30 ターンのセッションでは緊急コンパクションの必要性が完全になくなることも多いという。

著者はこの設計を教訓として一般化している。コンテキストの削減は二値の操作ではなく、段階的なアプローチ——利用率を継続的に監視し、古くなったツール出力が無関係になる前にプルーニングし、古い観測結果をマスクし、LLM ベースの要約は真のオーバーフローのために取っておく——のほうが、ハードリミットに達してからすべてをコンパクションするやり方を圧倒的に上回る、というものである。また、個々のしきい値の数値は第一原理から算出することが難しく、解析的な導出ではなく反復的な失敗分析から得られたものだとも述べている。

## 関連用語

ACC は [[DefinedTerm/context-engineering]] の下にまとめられる仕組みの一つであり、[[DefinedTerm/agent-harness]] が実行時に調整する関心事の一つでもある。レポートはこれを、取り込み時点でのツール結果の要約と補完的な関係にあるとしている。結果は会話に入る時点ですでに圧縮されているため、完全コンパクションの際に要約モデルへ渡される入力自体が大幅に小さくなるからである。
