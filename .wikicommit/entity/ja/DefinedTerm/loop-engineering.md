ループエンジニアリング（loop engineering）とは、コーディングエージェントに 1 ターンずつ直接プロンプトを与えるのではなく、自分に代わってエージェントにプロンプトを与えるシステムを設計する実践である。通常のエージェント利用では、人が指示を入力し、結果を読み、次の指示を入力する。これに対してループとは、作業を見つけ、それをエージェントに渡し、返ってきたものを確認し、行ったことを記録し、次の一手を決める小さなシステムであり、人はそのシステムを継続的に操作するのではなく、一度設計するだけである。これは [[DefinedTerm/harness-engineering|ハーネスエンジニアリング]]の 1 つ上の階層に位置するものとして説明される。ハーネスは単一のエージェントが動作する環境を形づくり、ループはそのハーネスをスケジュールに従って実行し、補助エージェントを生成し、自らに新たな作業を供給する。別の記述は同じ関係をハーネスそのものの観点から述べている。ハーネスとはモデルを取り巻くモデル以外のすべて、すなわちシステムプロンプト、ツール、パーミッション、コンテキスト管理、検証ループ、ログを指し、ループエンジニアリングはその 1 つ上の階層にあるコントロールプレーンとして、ハーネスが停止条件やスケジューラに照らして自律的に動き続けるよう設計するものだとされる。いずれの記述においても、この用語が指す転換は同じである。すなわち、自分でモデルにプロンプトを与えるのをやめ、モデルにプロンプトを与えるループを設計し始めるということである。

## 使われ方

ループは、繰り返し登場する 5 つの要素と、状態を記憶する場所とから構築される。スケジュールに従って実行され、作業を発見・トリアージする自動化。並行して動くエージェントが同じファイルを編集しないようにするためのワークツリー（それぞれ独自のブランチを持つ分離された作業ディレクトリ）。エージェントが毎セッションそれを導き出し直さなくて済むよう、プロジェクト固有の知識を記録するスキル。一般に MCP の上に構築され、課題トラッカーやチャットチャンネルといった実際のツールにループが到達できるようにするプラグインとコネクタ。そして、自分の出力を採点するモデルは甘くなりがちであるため、作業を書く者とそれを確認する者が同一にならないよう分けられたサブエージェントである。6 つ目の要素は外部メモリ — 個々の会話の外に存在する markdown ファイルや Linear のボード — である。基盤となるモデルは実行と実行の間ですべてを忘れるため、この状態は代わりにディスク上に置かれなければならない。Codex アプリと Anthropic の Claude Code はいずれも、名称こそ異なるものの、現在ではこの 5 つの要素をすべて備えて提供されているとされ、これはループエンジニアリングが各チームで手作りしなければならないものではなく、製品そのものの特性になったことの証拠として提示されている。

コーディング作業以外での実例が [[BlogPosting/loop-engineering-prompt-tuning]] で報告されており、そこで自動化されているループは視覚言語モデルのためのプロンプトチューニングである。その構築方法は、人が手作業ですでに行っていたことを分解し、各ステップにそれぞれ専用のコンポーネントを割り当てることだと述べられている — 失敗例を見る、原因を診断する、プロンプトを書き直す、再評価する、効果があったことを記録する、という各ステップであり、再評価のステップは単純なスクリプトが担い、残りはサブエージェントが担う。加えて、純粋にオーケストレーターとして働くスキルファイル、改善の優先順位・採否のルール・停止条件を保持し、すべてのサブエージェントが従う単一のポリシーファイル、そして人間のチューニング担当者が蓄積していく記憶に意図的に相当するものとして、各イテレーション後にループが追記していく教訓ファイルが用いられる。同記事は、比較が可能だった唯一のタスクにおいて自動化されたループが手作業によるチューニングに匹敵するか、わずかに上回ったこと、そして周辺の評価サイクルを約 3.5 週間から約 1 週間に短縮したことを報告しているが、これは繰り返し測定したものではなく単一の実行によるものである。

## 適用される場面

これが適用されるのは、さもなければ人がサイクルごとにエージェントへプロンプトを与え直し続けなければならない、反復的または長時間にわたる作業 — トリアージ、スケジュールされた発見作業、あるいは無人のまま続く作業 — である。実際に確認可能な停止条件（たとえば検証用のモデルによって）と、ループが実行と実行の間に読み書きできる永続的な外部状態とを前提とする。基盤となるモデル自体は、実行をまたいで何も保持しないからである。ループがうまく回るようになった後でも、検証は人間の責任であり続けるとされる。無人のループは無人のまま誤りを犯すのであり、この実践は他の 2 つの問題を解決するのではなく、むしろ先鋭化させるとされる。すなわち、ループが生み出すものを読むのをやめれば、出荷されたコードに対する人の理解はより速く劣化しうること、そしてうまく回っているループは、その出力を無批判に受け入れる誘惑を生みうることである。これは他の実践者たちが独立に述べてきた実践の統合として提示されている（Peter Steinberger と Boris Cherny はいずれも、エージェントに直接プロンプトを与えるのではなくループを設計する方向への同じ転換を述べたものとして引用されている）。上記の 5 要素の列挙は Steinberger によるリストであり、著者自身の貢献は、それを Codex アプリと Claude Code の両方に対応づけ、各要素を順に検討した点にある。

プロンプトチューニングの記述は、独自の注意点を 2 つ加えており、いずれも無人のループが動作しているときに何をするかに関わるものである。1 つ目として、各イテレーションでデータセット全体に対して推論を再実行したため API 料金が積み上がった。同記事は、設計の悪いループはバックグラウンドで推論を続け、予想外にコストを押し上げかねないと指摘し、変更はまず小さなサンプルで試し、その実行が有望に見えた場合にのみデータセット全体で評価することを推奨している。2 つ目として、ループは自らが採点される指標に対して最適化を行うため、編集対象の成果物は精度の向上とともに着実に長くなっていった。同記事は、最も注意深く監視したものとして過学習を挙げ、その理由として、文言が訓練データに寄れば寄るほど過学習のリスクが高まると述べ、最低限テスト用の分割を取り分けておくことを推奨している。
