Agent Teams は、複数のコーディングエージェントを真に並列に走らせるための [[SoftwareApplication/claude-code]] の実験的機能であり、[[BlogPosting/the-code-agent-orchestra]] で説明されている。素の [[DefinedTerm/subagents]] との違いは協調にある。サブエージェントの構成では依存関係のグラフの管理が親の手作業に委ねられ、子同士が会話する手段もないのに対し、Agent Teams は依存関係の追跡とファイルロックを備えた共有タスクリスト、チームメイト間のピアツーピアのメッセージング、そしてファイルロックを提供する。環境変数 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` を設定することで有効になる。

## 用法

説明されているアーキテクチャは3層からなる。**チームリード**が作業を分解し、タスクリストを作成し、結果を統合する。中間に位置する**共有タスクリスト**が、pending・in_progress・completed・blocked というステータスを持つタスクを、依存関係の追跡とファイルロックとともに保持する。最下層の**チームメイト**は独立した Claude Code のインスタンスであり、それぞれが独自のコンテキストウィンドウを持ち、tmux の分割ペインで動作する。

協調を担う仕組みは2つある。チームメイトは共有リストからタスクを自ら取得し、あるチームメイトがタスクを完了とマークすると、それに依存してブロックされていたタスクは自動的に pending に変わり、別のチームメイトが取れるようになる。ファイルロックは2人のチームメイトが同時に同じファイルを編集することを防ぐ。これとは別に、チームメイトはリードを経由せず互いに直接メッセージを送る——具体例は、バックエンドのエージェントがたった今確定させた API 契約をフロントエンドのエージェントに送るというものだ——これによってリードが協調のボトルネックになることを防いでいる、と説明されている。チームメイトがアイドルになるとリードには自動的に通知が届き、`Ctrl+T` でタスクリストの視覚的なオーバーレイを切り替えられる。

Osmani が示す運用上の指針は、チームメイトは3〜5人がスイートスポットであり、トークンコストはチームの規模に比例して増えること、そして焦点の定まった3人は散漫な5人に勝ることである。彼はその上に2つの信頼性向上策を加えたと述べている。チームメイトごとの厳格な `MAX_ITERATIONS=8` と、リトライのたびに強制される内省のプロンプト（「何が失敗したか？　それを直す具体的な変更は何か？　同じアプローチを繰り返していないか？」）であり、これによって行き詰まるエージェントが大幅に減ったと報告している。もう一つは、専任の読み取り専用の `@reviewer` チームメイトで、ビルダー3〜4人につきおよそ1人の比率で置かれ、リント・テスト・セキュリティスキャンのツールに制限され、タスク完了のたびに自動的に起動される。こうしてリードが目にするのは常にレビュー済みのコードだけになる。実装前にチームメイトに計画を書かせ、リードがそれを承認するよう求めることは、リスクの高いタスクのためのゲートとして提示されている。悪い計画を直すほうが悪いコードを直すより安上がりだ、という理由による。

### 同じ名前で呼ばれる、別の作りの二つめのもの

この名前は、目標は共有するが仕組みはほとんど共有しない研究プロトタイプにも使われている。[[BlogPosting/building-a-c-compiler-with-parallel-claudes]] において [[Person/nicholas-carlini]] は、「我々が『agent teams』と呼んでいる、言語モデルを監督する新しいアプローチ」を説明しており、そこでは複数の Claude インスタンスが人間の能動的な介入なしに共有のコードベース上で並列に作業する。この2つの構成を、一つのシステムについての記述として読むべきではない。

Claude Code の機能がチームリード、依存関係の追跡を備えた共有タスクリスト、ピアツーピアのメッセージング、ファイルロックを提供するのに対し、そのプロトタイプは意図的にそのいずれも提供しない。各エージェントは bare の git リポジトリに対して自分の Docker コンテナ内で動作する。タスクの取得は `current_tasks/` ディレクトリにロックファイルを書き込むことで行われ、衝突は git 自身の同期によって、2番目の主張者を別のタスクへ追いやることで解決される。レポートは、他のエージェント間通信の手段は一切実装されていないこと、上位の目標を管理するプロセスは強制されていないこと、そしてオーケストレーションエージェントは使われていないことを率直に述べている。各エージェントが自分で何に取り組むかを決め、一般には次に最も明白な問題を取る。著者はこれをごく初期の研究プロトタイプだと呼んでいる。

両者は、人間に何を期待するかという点でも異なる。機能としての構成は、計画の承認とレビューのゲートに操作者がいることを前提とする。プロトタイプは、既存のスキャフォールドが長い問題では停止して入力を待つという観察に基づき、まさに操作者を取り除くために存在する。そのレポート自身がこのトレードオフについて出した結論は、協調の機構が不要だというものではなく、代わりにその協調の負担を担わなければならないのは環境——テスト、フィードバック、ログ——である、というものだ。

## 関連用語

Agent Teams は [[DefinedTerm/subagents]] と同じ軸の協調された側の端にあたる。サブエージェントはコンテキストの隔離と並列実行を提供するが、共有状態やピア間の通信は提供しない。また Agent Teams は [[DefinedTerm/multi-agent-orchestration]] の具体的な実装の一つである。それと対に置かれる品質ゲート——フックと、複利的な学習のための [[DefinedTerm/agents-md]] ファイル——は、[[DefinedTerm/verification-bottleneck]] に応える手立てと同じものである。
