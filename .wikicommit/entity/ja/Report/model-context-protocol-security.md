「Model Context Protocol (MCP) Security」は Coalition for Secure AI のワークストリーム4——エージェント的システムのセキュアな設計パターン——が作成し、2026年1月8日に CoSAI プロジェクト運営委員会が承認したレポートである。**Status: Draft** と記されている。その主題は抽象的な仕様のセキュリティではなく、[[DefinedTerm/model-context-protocol]] の実装のセキュリティである。2025年6月版（`2025-06-18`）およびそれ以降の改訂仕様のトランスポート層とプロトコル層、MCP ベースのエージェント的システムに対する脅威モデリングの戦略、サーバとツールのサプライチェーンに関する考慮、エージェント的アーキテクチャにおける ID とアクセス管理、導入と運用の実践、そしてプロトコル拡張のための推奨事項を分析している。レポートは、著者たちが推奨事項を実装可能なものに保つために [[Organization/anthropic]] および MCP のメンテナコミュニティと協働していること、そしてこの作業が CoSAI のソフトウェアサプライチェーンセキュリティのワークストリームと連携していることを述べている。

スコープからの除外は、スコープと同じくらい明示的に述べられている。セキュリティと無関係なコンテンツ安全性、誤情報、AI 倫理は扱わない。セキュリティ上の含意を超えた一般的なモデルの安全性やアラインメントも扱わない。個別のセキュリティツールの詳細な実装は後続の論文に譲る。MCP の性能、スケーラビリティ、機能的能力のうちセキュリティ以外の側面も扱わない。そして法務・規制順守は CoSAI のワークストリーム3「AI リスクガバナンス」へ回す。主たる読者は、MCP サーバをセキュアにし、作成し、あるいはそれに接続するセキュリティ専門職と開発者であり、より長期の読者として MCP のメンテナとコアプロトコル開発者が挙げられている。

## 主な知見

- **12のカテゴリにわたる40近い脅威。** MCP-T1 不適切な認証と ID 管理、T2 アクセス制御の欠如または不適切、T3 入力の検証とサニタイズの失敗、T4 入力／指示——別の箇所ではデータ／制御——の境界の区別の失敗、T5 不十分なデータ保護と機密性の制御、T6 完全性と検証の制御の欠如、T7 セッションとトランスポートのセキュリティの失敗、T8 ネットワークのバインドと隔離の失敗、T9 信頼境界と権限設計の失敗、T10 リソース管理とレート制限の不在、T11 サプライチェーンとライフサイクルのセキュリティの失敗、T12 不十分なログ・監視・監査可能性。
- **3つの特異性の階層。** ティア1は MCP のアーキテクチャと設計上の決定に固有の新規の脅威7件を扱う。ティア2は MCP の文脈で異なる現れ方をする、あるいは増幅される既知の脅威8件を扱う。ティア3は広く一般に当てはまる、あるいはレガシー・インフラ・トランスポートの決定に由来する従来型の脅威19件を扱う。
- **ティア1として名指されている脅威**には、ID のなりすまし、[[DefinedTerm/tool-poisoning]]、完全なスキーマポイズニング、リソースコンテンツポイズニング、タイポスクワッティングと混同攻撃、シャドー MCP サーバ、そして LLM への過度の依存が含まれる。レポートはポイズニングの変種を注意深く区別している。完全なスキーマポイズニングは個々のメタデータではなくツールの構造定義と型システム全体を侵害するものであり、リソースコンテンツポイズニングはツール定義ではなく、サーバが取得するバックエンドのデータソースの中に指示を隠すものである。
- **MCP には固有の脅威モデルが必要である。** MITRE ATLAS、NIST AI RMF、MAESTRO といった既存の枠組みは質の高いものとして認められているが、レポートはそれらが「コンポーネントがあらかじめ定義されたロジックに従って予測可能に振る舞うことを前提にしている」のに対し、MCP は「自然言語の入力によって振る舞いが形づくられるエージェントである LLM を、セキュリティ上決定的な判断の中心に据える」と論じる。新しいものとして挙げられている4つの考慮点は、クライアントとツールサーバのあいだのプロトコルレベルの認証、AI がどのツールに到達できるかを決定する動的な能力ネゴシエーション、独立したツール提供者にまたがる分散した信頼、そして長寿命の AI 対話に固有のセッション管理の複雑さである。
- **導入パターンが脅威モデルを決める。** 3つのパターン——全ローカル、シングルテナントのハイブリッド、マルチテナントのクラウド——が提示され、レポートはセキュリティ態勢がサーバのコードの出所（ファーストパーティ、オープンソース、サードパーティ）、それが実行される場所、そして何にアクセスできるかに依存すると論じる。ローカルの stdio による導入はプロセスレベルの隔離をもたらすが、ファイルシステムへのアクセスを管理する必要がある。内部の Streamable HTTP による導入は横方向の移動と認証を考慮しなければならない。外部のクラウド導入はインターネットに面した攻撃面とマルチテナンシーの懸念を持ち込む。
- **11の制御ファミリ**が脅威カテゴリへ対応づけられている。エージェント ID、セキュアな委譲とアクセス制御、入力とデータのサニタイズおよびフィルタリング、暗号学的完全性とリモートアテステーション、サンドボックス化と隔離、リソースの暗号学的検証、トランスポート層のセキュリティ、セキュアなツールと UX の設計、ヒューマンインザループ、ログ、そしてライフサイクルとガバナンスである。
- **同意疲れが仕様自身の防御を掘り崩す。** レポートは、MCP がツールの出所と入力を可視化することについての指針を提供し、ヒューマンインザループによる承認を推奨していると指摘しつつ、ユーザーが注意深いレビューなしに反射的にプロンプトを承認することが「これらの保護を著しく損ないうる」と述べている。そして安全でないヒューマンインザループと、同意／ユーザー承認の疲れを、それ自体独立した脅威として挙げている。

## 根拠と留保

証拠の基盤は独自の測定ではなく、文書化されたインシデントと構築された分類である。レポートは、複数の重大な CVE が報告されており、データ漏洩といったインシデントが MCP およびエージェント的な導入においてすでに発生していると述べ、3件を名指している。2025年5月の Asana AI のインシデントでは、テナント隔離の欠陥により組織をまたぐデータ汚染が起き、最大1,000社の企業に影響した。WordPress プラグインの脆弱性では、AI Engine プラグインにおける MCP 経由の権限昇格により10万を超えるサイトが影響を受け、2025年6月18日に修正された。そして Supabase の MCP の問題では、研究者がサポートチケットのデータを介したプロンプトインジェクションを実証し、データベースへ直接アクセスできる接続済みサーバを通じて AI ツールにプライベートなテーブルを露出させた。過剰なツールと過剰な権限を突いたものである。これらについてのレポート自身のまとめは、脅威が「理論上の懸念ではなく、現に活動している脅威である」ことを示している、というものだ。

知見とともに携えておくべき限界が2つある。この文書は「Status: Draft」と記されており、番号の付いたリリースではなく `7ec1306f2f55563f6eeef9d36a6bb2b531491ceb` という不透明なバージョン文字列を持つ。また CoSAI の寄稿者リストは、この領域に商業的な利害を持つベンダーから大きく構成されている——名前の挙がったワークストリームのリード、編集者、寄稿者には IBM、Intel、NVIDIA、Anthropic、Google、Cisco、Red Hat、Wiz、Amazon、Dell、PayPal、ServiceNow、Trend Micro、Adversa AI の人々が含まれる——。レポート自身はこれを、業界をリードする組織の AI およびセキュリティ専門家によるオープンなエコシステムとして肯定的に枠づけている。レポートはまた、AI 支援による起草についての方針も開示しており、最終的な出力は人間によるレビューまたは編集を経ること、実質的な AI の利用を開示することを義務づけている。

結論で推奨されている態勢は多層防御である。ゼロトラストアーキテクチャ、Trusted Execution Environment によるハードウェアベースの隔離、厳格なサプライチェーンの審査、そして継続的な監視であり、MCP をセキュアにするには開発者、組織、プロトコルのメンテナにまたがる協調した努力が必要だという指摘が添えられている。
