「Beyond Code-Centric: Agents Code but the Problem of Clear Specification Remains」は、[[Organization/specstory]] の共同創業者 [[Person/greg-ceccarelli]] が2025年6月15日に公開したホワイトペーパーである。その主張は、ソフトウェアのボトルネックが移動した——「もはや問題はどれだけ速くタイプするかではなく、どれだけ明晰に考えるかである」——というものであり、そしてソフトウェアの仕事を組み立てる確立されたやり方はいずれも、エージェントが破ってしまう前提のうえに築かれていた、というものである。

## 主な知見

同論文はこの移動を**抽象度の移行（abstraction shift）**と呼ぶ。エージェントは高レベルのプロンプトから求めに応じてコードを生み出せるため、いまや進捗は、何を作るべきかの仕様の背後にある思考の明晰さにかかっている。同論文はこれを、*Clean Code* における Robert C. Martin の議論——「機械が実行できるほど詳細に要件を規定することはプログラミングである。そのような仕様はコードである」——に基礎づけ、Martin の指摘をこの移行への反駁としてではなく、新たに字義どおりのものとして読んでいる。

同論文が特定する中心的な機構は、人間はエージェントが素通りしていく隙間を埋める、というものである。「もっとユーザーフレンドリーにして」と言われた人間の開発者は打ち合わせを設定して質問をする。同じ一行を与えられたエージェントは解決策をでっち上げるのであって、その中間はない。同論文は、これはエージェントがプロンプトを実行する仕方そのものに焼き込まれているために設計で取り除くことはできないと論じ、その帰結が最も強く出るのはチームワークにおいてであるとする。仕様がプロダクトビジョン、ビジネス上の現実、デザインの制約、ユーザーの制約、技術アーキテクチャを一度に担わねばならないところでは、いかなる曖昧さもバグ、思い込み、あるいはブロッカーになる。

そこから同論文は、確立された各パラダイムがそれぞれの理由で破綻すると論じる。**ウォーターフォール**は本一冊分の文書を生み出し、それが「LLM を窒息させる」——長大で、AI の観点からは不正確で、反復的な構成要素ではなく最終製品を志向しており、単一の権威が仕様を所有することを前提としている。**アジャイル**が文書よりも動くソフトウェアを選好することは、設計意図を廊下での雑談、スタンドアップ、暗黙知のうちに留めてしまう。同論文はこれをパラドックスと呼ぶ。エージェントは「レトロに出席することも行間を読むこともできない」からである。**GitFlow** の長寿命ブランチは、エージェントが辻褄を合わせねばならないコンテキストを増殖させる。`main`、`dev`、フィーチャーブランチ、ホットフィックスブランチにまたがって機能を実装するよう求められたとき、人間は会話と暗黙知から正しいものを推測するが、「AI エージェントは互いに矛盾する4つの現実を、辻褄を合わせる手立てもないまま目にする」。

その答えは、各役割が単一の共有リポジトリへ仕様を寄せるトランクベース開発である——プロダクトマネージャーはテスト可能なユーザー挙動を機能的意図として書き、デザイナーは間隔、コンポーネント、インタラクションといった制約をデザイン意図としてコード化し、アーキテクトはインターフェース、契約、依存関係を技術的意図として宣言する。掲げられた理由は選好ではなく強制である。「未完了の作業がブランチのなかに隠れることはできない。1つのブランチが1つの真実を強制する。」その上に重ねられるワークフローが [[DefinedTerm/specflow]] である。

同論文は、このアプローチがなお痛みを伴う箇所について異例なほど率直であり、複雑さを取り除くのではなく再配分するにすぎないと述べる難点を列挙している——コンテキストのロード問題、モデル選択のミクロな意思決定、精緻さのオーバーヘッド、介入とバージョニングのトレードオフ、そしてエージェントが「砂上の楼閣のようなコード」——完成しているように見えて現実の圧力のもとで崩れるコード——を生み出すこととして要約される保守負担である。その一覧から同論文自身が引き出す結論は留保つきのものである。意図を中心に据えたより良いツールがこれらのミクロな意思決定を減らすまでは、「エージェントによる仕様駆動開発は理論上は強力だが実務上は不十分なままである」。

テストについては、Diwank Singh を引きながら神聖と呼ぶ規則を述べている——「絶対に。AI に。テストを。書かせるな。」——が、力点はずらされている。同論文自身の立場は、重要なのは*仕様*なのであって、AI がテストを仕様化するのなら統制を明け渡したことになる、というものである。その論拠は、テストとは正しい振る舞いについての共有された理解を捉える実行可能な仕様であり、ビジネスルール、ユーザーのニーズ、そしてドメインを知る人々の洞察を反映していなければならない、というものである。

## 背景

同論文の枠づけは全篇を通じて、*Clean Code* の原則を置き換えることを提案しているのではなく、実装が安価で調整が高価な世界に向けてそれを進化させることを提案している、というものである。Clean Code がコードを第一の仕様としたのに対し、同論文は3層のスタックを提案する。プロダクト、デザイン、アーキテクチャの声を反映した第一級の仕様としての**宣言された意図**。唯一の真実の源ではなく、その意図の1つの妥当な実行としての**コード**。そして意図とその実装の双方を検証する**テスト**である。結びの節では「仕様は依然としてコードである。種類が違うだけだ」と述べ、ノーコードあるいはローコードの未来を明示的に退けて、高レバレッジなコードと呼ぶものを支持している。

ベンダーのホワイトペーパーである以上、自らの手法についての主張は著者自身のものである。報告された成果——3人が4週間で SpecStory の Studio 製品の完全なエンドツーエンドの macOS アルファ版を届けたというもの——は、同社が自社の実践について述べたものであり、独立した検証はない。同論文の Specflow についての記述も同様に、そのワークフローの公刊者自身による記述である。
