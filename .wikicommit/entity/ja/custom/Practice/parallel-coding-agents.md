コーディングエージェントを並列に走らせるとは、1人のエージェントに作業を逐次的にこなさせるのではなく、リードエージェントによって調整されたうえで、1つの問題の異なる部分に複数のエージェントを同時に取り組ませることである。これを記述する各種の説明のなかで2つの動機が述べられており、両者は切り離せる。**コンテキストの隔離**——どの単一のコンテキストウィンドウにもすべてが積み上がらないようにすること——と、**並列性そのもの**——別々のエージェントが問題の異なる部分を同時に探索できるようにすること——である。この実践は、コンテキストウィンドウが有限の資源であることに対する標準的な答えの一つであり、[[DefinedTerm/compaction]] や [[DefinedTerm/agentic-memory]] と並ぶ。そして [[DefinedTerm/multi-agent-orchestration]] が、その協調を逐次的にではなく同時並行に行うときに姿を現すものでもある。

## 適用する場面

この実践とタスクの形との最も明快な対応づけは、[[DefinedTerm/multi-agent-orchestration]] の背後にあるコンテキストエンジニアリングの記述から来ている。並列のサブエージェントは、**並行的な探索が報われる複雑な調査と分析**に向いており、これは会話的なやり取りにはコンパクションを、明確なマイルストーンを伴う反復的な開発にはノートテイキングを、という対比のなかに置かれる。実装の側では、[[DefinedTerm/subagents]] における議論はより狭く、より運用寄りである。主エージェントが同一の応答のなかで複数の生成呼び出しを出したとき、複数のサブエージェントが同時に走りうるのであり、これは**スレッドのオーバーヘッドを、独立した操作におけるレイテンシの削減と引き換えにすること**として枠づけられている。ここでは限定条件が効いている。この取引が割に合うためには、操作が独立していなければならない。

同じ資料は、これに手を伸ばす*べきでない*場面についても明示的である。Anthropic のサブエージェントのドキュメントは、タスクが頻繁なやり取りを要するとき、複数のフェーズが大きな文脈を共有するとき、あるいはレイテンシが重要なときには、代わりに主たる会話を用いることを推奨している。フォークではないサブエージェントは本当にまっさらな状態から始まるため、何かを行える状態になるまでに文脈を集める時間が必要になりうるからだ。新しいエージェントは会話の履歴も、すでに呼び出されたスキルも、親がすでに読んだファイルも見ることができない。

2つの説明は、タスクの形ではなく*分割*の前提条件を付け加える。[[DefinedTerm/spec-driven-development]] の背後にあるレポートは、仕様が複雑な問題をエージェントのコンテキストウィンドウに合ったモジュール的な構成要素へ分解する「スーパープロンプト」として働くと論じ、仕様のレベルで作業を分割することこそが、複数のエージェントに干渉なしに異なるコンポーネントを同時に実装させるものだとする——その干渉こそ、仕様が防ぐために存在するものである。[[SoftwareApplication/spec-kit]] は並行した実装の探索をそれ自体1つのフェーズとして扱っている（「Creative Exploration」——複数の技術スタックとアーキテクチャにまたがって多様な解を探索する）。これはスループットのためではなく*ばらつき*のために用いられる並列性である。

すべての実践者がこれをプロセスのレベルで採用しているわけではない。[[Person/geoffrey-huntley]] は [[BlogPosting/ralph-wiggum-as-a-software-engineer]] において、当時エージェント間の通信や多重化は必要なかったと論じ、非決定的なエージェントをマイクロサービスに見立てることを単一のモノリシックなプロセスより不利なものとして対比している——その一方で、その単一のプロセスの*内側*では [[DefinedTerm/subagents]] を大いに使っている。これは有用な境界線である。彼は並列エージェントをアーキテクチャとしては退け、ディスパッチの仕組みとしては保っている。

## 仕組み

**リードエージェントが計画を保持し、並列のエージェントが細部を保持する。** 1つのエージェントがプロジェクト全体にわたって状態を維持するのではなく、専門特化したサブエージェントがきれいなコンテキストウィンドウで焦点の定まったタスクを扱い、主エージェントは高レベルの計画で調整する。各サブエージェントは広く探索してよく——数万トークン以上に及ぶこともある——、返すのは凝縮された要約だけであり、およそ 1,000〜2,000 トークンとされる。関心の分離が要点である。詳細な検索の文脈はサブエージェントの内側に隔離されたまま、リードエージェントは統合と分析を行う。

**ファンアウトは意図的に上限が設けられ、その上限は作業の種類によって異なる。** Huntley のプロンプトは検索とファイル書き込みには多数の並列サブエージェントを許すが、ビルドとテストには*1つ*だけを許す。数百のサブエージェントを展開してすべてにビルドとテストを走らせると、彼が「悪い形のバックプレッシャー」と呼ぶものが生じるからである。彼の説明では、並列度を制御することは実装上の細部ではなく、この仕組みを使うことの一部である。Claude Code は同じ懸念をハードな上限として符号化している。デフォルトでは、サブエージェントは主たる会話から3層下までは自分のサブエージェントを生成でき、それを超えると委譲のツールが与えられなくなり、サブエージェントは自ら作業して1つの要約を返さなければならない。また21番目の*実行中*のサブエージェントを生成しようとすると `Concurrent subagent limit reached` のエラーで失敗し、モデルには再試行しないよう指示される。セッションを通じて生成される総数に上限はない。いずれの上限も環境変数で設定できる。

**ツールの集合はエージェントごとに絞られ、共有されない。** [[DefinedTerm/subagents]] のもとで記述されている OpenDev の実装では、各サブエージェント種別がフィルタされたツールの集合に制限されており、それは実行時の権限チェックではなくスキーマのレベルで強制される。したがって読み取り専用のエージェントは、書き込みのツールを試みることも、例外を主張することも、迂回の条件を探ることもできない。3つの理由が挙げられており、うち2つはまさに並列性に関わるものだ。タスク管理のツールを除外して、タスクリストを調整するのが主エージェントだけになるようにし、**競合状態を防ぐ**こと。コンテキストのサイズを減らし、各エージェントを自分の役割に集中させること。そして誤りの影響範囲を限ることである。

**エージェントが書き込むところでは、別々の地面が要る。** [[SoftwareApplication/claude-code]] のドキュメントは並行作業の選択肢として worktree、デスクトップアプリ、ウェブ版の Claude Code、エージェントチームを挙げており、`isolation: worktree` はサブエージェントに自分のコンテキストだけでなくリポジトリの自分のコピーを与える。その境界は能動的に強制される。各コマンドの作業ディレクトリを確認し、git を主チェックアウトへ向け直すコマンドをブロックし、worktree の内側にとどまることを確認できない形のコマンドを拒否する。

**並列性は分業のためだけでなく競争のためにも使われる。** [[DefinedTerm/subagent-driven-development]] は、コンテキストの隔離を伴って同じタスクを複数の独立した対象にわたって実行する `/do-in-parallel` と、競争的な生成に続いて複数の判定者による評価と証拠に基づく統合を行う `/do-competitively` を同梱している。そのメンテナたちはまた、完全な仕様をあらかじめ書くのではなく、実装*と並行して*その場で仕様を生成することも記述している。Claude Code の**フォーク**（`/subtask`）は同じ形を反対側から満たす。これはそれまでの会話全体を引き継ぎ、サブエージェントが本来提供する入力の隔離を意図的に手放しつつ出力の隔離は保つもので、同じ出発点から複数のアプローチを並行して試すのに推奨されている。

**検証もたいていは並列のエージェントである。** 作業を完了と見なす前に新しいサブエージェントのコンテキストで敵対的なレビューの段階を加えることが推奨される実践であり、その論拠は、作業を行ったエージェントがそれを採点する者であってはならない、というものである——[[DefinedTerm/llm-as-judge]] を参照。

## 失敗モード

- **際限のない探索。** 明確な停止条件を欠いた初期の OpenDev のプロンプトは、探索役のサブエージェントに同じファイルを繰り返し読ませる結果を招いた。明示的な終了条件とループ防止の指示を加えることで解決した。同じパターンは Anthropic のベストプラクティスのガイドにも「無限の探索」として収録されており、スコープの定まらない調査が何百ものファイルを読むというもので、対処としてスコープを定めた委譲が挙げられている。
- **コンテキストの汚染と役割の混乱。** OpenDev の初期版はサブエージェントに主エージェントと同じツールを与えており、それがコンテキストの汚染、役割の混乱、そして両方のエージェントが同時にタスクリストを更新しようとしたときの衝突を招いた。これはエージェントごとのツールのフィルタリングを動機づける競合状態の具体的な現れである。
- **広いファンアウトにおけるバックプレッシャー。** Huntley がビルドとテストのサブエージェントを1つに限っているのは、その種の作業では広いファンアウトが加速ではなく劣化をもたらすからである。
- **見えない結果。** サブエージェントの結果はユーザーには見えないため、親エージェントはそれらが見られているものと想定するのではなく、その知見を自ら提示しなければならない。
- **境界を越えないルール。** Claude Code の組み込みの Explore と Plan のエージェントは、速く安価であり続けるために CLAUDE.md の階層と親セッションの git ステータスを飛ばしており、それを変える設定は存在しない。エージェント自身に届かなければならないルールは、委譲のプロンプトのなかで述べ直す必要がある。
- **コスト。** チャットの最大 15 倍のトークンが報告されており、あわせてサブエージェントの作業を計画するための入念なプロンプトエンジニアリングと、協調そのもののオーバーヘッドも必要になる。

## 証拠

この実践を支える資料は、ほぼ全面的に**ベンダーのドキュメント、実装報告、実践者の記述**である。並列エージェント実行についての統制された研究はそこに現れない。

Anthropic のエンジニアリング記事とその Claude Code のドキュメントがアーキテクチャと運用上の上限を供給しているが、いずれもベンダー自身の製品についての記述である。OpenDev のレポートは単一の実装の記録であり、完成した設計だけでなく、うまくいく前に何がうまくいかなかったか（同じツールを与えた誤り、欠けていた停止条件）を記録している点で価値がある。LangChain のコンテキストエンジニアリングの記事はコストの数字——15 倍という数字は Anthropic に帰されている——と、OpenAI の Swarm ライブラリの背後にある関心の分離という動機を供給している。Huntley の記述は一人の実践者による自身のループの経験であり、そこにある並列性の上限は測定されたものではなく彼のものである。

[[Report/2026-agentic-coding-trends-report]] は、単一のエージェントから協調するチームへの移行を、2026年について*予測される*8つのトレンドの一つとして扱い、その採用が何を要求するかを述べている。タスク分解、エージェントの専門化、協調プロトコルにおける新しいスキル。複数の同時並行のエージェントセッションの状態を示す開発環境。そしてエージェントが生成した同時並行の寄与を扱えるバージョン管理のワークフローである。そこでの Fountain の例はある顧客の階層的なオーケストレーションであり、ベンダーによって報告されたものである。

[[DefinedTerm/subagent-driven-development]] の数字——`/do-and-judge` は 1〜3 ファイルにまたがる変更について 1.5〜3 倍のトークンのオーバーヘッドで完全に正確な結果が得られる確率 90%、`/do-in-steps` は 3〜5 倍で 92%、対してワンショットのプロンプトはオーバーヘッドなしで 60〜80%——は、公開されたベンチマークの結果ではなく、メンテナたちの実運用における自前の数字である。人間が洗練させた仕様が LLM 生成コードの品質を改善し、統制された研究で最大 50% のエラー削減が示されているという仕様駆動のレポートの主張は、並列性そのものではなく仕様の品質についてのものである。

[[ScholarlyArticle/agentic-software-engineering-foundational-pillars]] はビジョン論文であり、著者らは自らの枠組みについて経験的な評価を提示していないと明言している。

## 注記

これらの説明を通じて、この実践の2つの動機——コンテキストの隔離と並列による速度——は常に一緒に述べられるが、両者は異なる方向へ引っ張っている。そして資料がそれを可視にするのは、複数の出典を並べて置いたときだけである。Anthropic 自身の指針は、レイテンシが重要なときには委譲に*反対*する。新しいエージェントはまず文脈を集めなければならないからだ。OpenDev のレポートは、まさにレイテンシの削減として同時並行に*賛成*する。両方が成り立ちうるが、それは隔離のコストが、その文脈集めもまた並行して起きるほど独立した作業の上で支払われる場合に限られる。これは仕様駆動の説明が別の角度から——どのエージェントも始める前に作業を分割することによって——扱っている条件でもある。

第2の緊張は、資料の実践者側と枠組み側のあいだにある。[[ScholarlyArticle/agentic-software-engineering-foundational-pillars]] は「大規模な並列性」のために作られた [[DefinedTerm/agent-execution-environment]] を提案し、SE のカリキュラムは学生にエージェントの*艦隊*を管理するよう訓練すべきだと論じる。一方で運用の記録は、ビルドとテストの作業についてファンアウトが意図的に1桁に抑えられていること、そしてある出荷済み製品ではデフォルトで20の同時エージェントに抑えられていることを記述している。ビジョンは、広い並列性を安価にするインフラを前提としている。出荷されているツールは、それが存在するようになる前に現に存在するバックプレッシャーを記述している。

この根拠資料のなかに、同じコードベースに対して並列に作業したエージェントの出力をどう統合あるいは調停するかを記述した出典はない。動向レポートは、エージェントが生成した同時並行の寄与を扱えるバージョン管理のワークフローを採用の要件として名指し、worktree は作業中のエージェントごとの隔離を供給する——しかしマージの地点で何が起きるのかは、これらのいずれの説明も扱っていない。
