「Spec-Driven Development Using Coding Agents」は [[Person/arun-gupta]] によるカンファレンスのスライドデッキであり、JetBrains の VP, Developer Experience としての立場で発表されたものである。[[DefinedTerm/vibe-coding]] はその出力を安全に拡張したり変更したりできないワンショットのアプローチだと論じ、意図優先の代替として [[DefinedTerm/spec-driven-development]] を——コードではなく仕様を信頼できる唯一の情報源として——提示する。

デッキは長いアナロジーとして構成されている。冒頭では、裏庭を「バイブコーディング」するとどうなるかが語られる。「バーベキューできるかっこいい何かを作ってよ」といったプロンプトは、施主の意図の推測を施工業者に委ねることになり、その結果バーベキュー台は届いたのに石材にそれ用の切り欠きがなく、表面上は見栄えのする「バイブ」が出来上がるが、配管とガス管が一度も接続されていないために最初の「本番」ディナーで破綻する。次いで同じプロジェクトを設計図から回し直し、その建設プロセスの各要素をソフトウェア開発ライフサイクルへ対応づけたうえで、実務的な仕組み——`AGENTS.md`、Agent Skills、実装計画、そしてドリフトの問題——へと進む。

## 要点

- **バイブコーディングはワンショットのアプローチである。** デッキが挙げる帰結は、構造がないこと、計画がないこと、幻覚されたファイルが大量に出ること、コードベースの誤解、企業標準の無視、拡張しづらく、当初のメンタルモデルが失われた後には安全に変更することがほぼ不可能なコード、そしてレビューしづらいコードである。問題のまとめは、バイブコーディングはあなたのバイブに基づいてコードを生成するものであり、代わりに必要なのは「意図が先、コードが後のアプローチ」だ、というものである。DORA のレポートを引きつつ、AI は既存の組織的な強みや弱みを増幅する傾向があると付け加える。良いチームはより良くなり、苦しんでいるチームはより悪くなりうる。

- **裏庭からコードベースへの対応づけ。** 設計図は仕様（API、DB スキーマ）に、資材の確保は インターフェース定義に、ユーティリティの依存は認証・DB・API ゲートウェイといったインフラに、下請け業者はテスト生成・セキュリティ・ドキュメントのための専門特化エージェントに、施工業者の検証ループや許認可はリンタやテストスイートといった自己修正ループに、そして2つ目の裏庭を作ることは同じ仕様を Java、Go、Python にまたがって再利用することに対応する。設計図に添えられた標語は「設計図が信頼できる唯一の情報源である」であり、先行投資の議論に添えられた標語は「速く走るためにゆっくり走れ」である。

- **デッキの言葉による仕様駆動開発とは何か。** 何を、なぜ作るのかを定義する自然言語の仕様を書くこと。すなわち、意図（望ましい振る舞い）、インターフェース（コンポーネント間の契約）、要件（機能要件と非機能要件）、そして Gherkin 形式の受け入れ基準である。それらの仕様を実装から独立にレビューし洗練させ、AI エージェントにそれらに照らしてコードを生成させ検証させる。そして人間の判断が「何を」を定義し、AI の効率が「どのように」を届ける。

- **4段階の仕様駆動 SDLC。** Research（既存のコードベースとパターン、技術論文とベストプラクティス、エージェントが生成した調査レポート、ステークホルダーへのインタビュー、依存関係と統合ポイント）。Standardize（リント、ADR、スタイルガイドといったルール、スキル、MCP と統合、プロジェクト構造と規約）。Define（スコープの境界、要件、契約、UI/UX、テスト戦略と受け入れゲート）。そして Loop（仕様からの AI 駆動のコード生成、仕様に照らした継続的な検証、コードと仕様のあいだの反復的な洗練、トレーサビリティと変更管理）。

- **仕様を再利用可能かつテスト可能にする。** デッキは再利用可能な仕様の7つの性質を挙げている。明確なスコープの境界（機能の膨張を防ぐための「スコープ内」対「スコープ外」）、根拠を伴う文書化された ADR、言語およびフレームワークからの独立、機能要件と非機能要件を分けた構造化された要件、JSON スキーマをあらかじめ定義する契約優先のアプローチ、テスト可能な WHEN/THEN 条件としての受け入れ基準、そして規定ではなく指針として提示される技術スタックの推奨である。仕様を曖昧でないものにするために、要件ごとの Given-When-Then の受け入れ基準を推奨し、「typically」「expected」「strategic」「best」といった柔らかい語を命令形と測定可能な値へ置き換えることを勧める——実例では「Prioritizes moves」「Recommends」「Considers」を「MUST select moves in this priority order」と正確な数値の優先度へ置き換えている——、そしてあらゆる失敗ケースについてエラーコード、スキーマ、明示的なデータ型と制約を定義することを勧めている。

- **実装計画と検証ゲート。** デッキは実装計画を、プロンプトを通して仕様を変換した出力として記述し、それが備えるべき性質を挙げている。仕様の要件への直接のトレーサビリティ、段階的な漸進的デリバリ、AI の効率に向けた最適化（小さくスコープの明確な単位はコンテキストウィンドウに収まり、意図からのドリフトも小さい）、フェーズ間の「完了の定義」を伴う検証ゲート、後付けではなく計画された包括的なテスト、定量化された成功指標、組み込まれたリスク緩和、そして依存関係とリソースの追跡である。

- **エージェントのドリフトと UI/UX。** デザイン作業についてのデッキの推奨は、既存のツールを MCP 経由でエージェントへ橋渡しすることである。Figma の選択範囲のリンクをエージェントへコピーして `ui-spec.md` を生成させ、次に UI 作業のために `AGENTS.md` からその仕様を参照する。同時に、デザインが変わったときにデザインチームと開発者のあいだのコミュニケーションが長期的には必要になることも指摘している。

- **3つの分離と3つの実践。** 締めくくりのまとめは、SDD の3つの分離を次のように述べる。考えることと行うことを分離すること（仕様が「何を」を定義し、エージェントが「どのように」を定義する）。戦略と戦術を分離すること（コードの行ではなく仕様をレビューする）。そしてパターンとプロジェクトを分離すること（使い捨てのプロンプトではなく持ち運べるスキルを作る）。重要な3つの実践は、デリバリを加速するために先行投資すること、ゲートを伴うフェーズで構築すること、そしてより良い仕様にたどり着くために AI に自分をインタビューさせることである。最後の一行は、AI はあなたがすでに持っているものを増幅するのだから、正しいものを増幅しているかを確かめる価値がある、というものである。

## 背景

この実践についてのデッキ自身による一文の定義は、その立場のまとめとして記録しておく価値がある。仕様駆動開発とは、「AI が何を知るべきか（AGENTS.md）、何をすべきか（skills）、そしてあなたが何を作っているのか（実装計画）を書き下しておくことで、説明するのをやめて作り始められるようにすること」である。この枠づけは、デッキの2つの実務的な仕組み——[[DefinedTerm/agents-md]] と [[DefinedTerm/agent-skills]]——を付随的なものではなく荷重を支えるものにしている。

デッキはまた、確定した手法を提示するのではなく、この分野の現状を概観している。「仕様駆動開発の領域で何が起きているか」のもとに Spec-kit、AgentOS、Kiro、AntiGravity、Tessl を新興のツールとして名指し、グリーンフィールドとブラウンフィールドの双方で採用が広がっていると報告したうえで、自らは答えない未解決の問いを列挙している。SDD が TDD、BDD、DDD とどう統合されるのか。コードが進化するなかで誰が仕様を保守するのか。そして複数のエージェントが並行作業をどう調整するのか。ドリフト防止の戦略とマルチエージェントオーケストレーションのパターンが次の課題として挙げられている。
