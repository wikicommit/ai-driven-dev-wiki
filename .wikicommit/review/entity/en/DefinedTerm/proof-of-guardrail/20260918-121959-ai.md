Body says the wrapper 'mediates all of the agent's inputs, outputs and tool calls'; the source (Sec. 3.2) writes 'mediates all agent inputs/outputs (and tool calls, if applicable)'. The page drops the 'if applicable' qualifier, so it reads as though tool-call mediation is unconditional.
Body says the attestation 'carries the enclave measurement together with a commitment to the input and the response'. The source states d = Hash(x,r) 'or Hash(r), if binding of x is not required' (Sec. 3.2), and Appendix A notes that in the agent-skill-based implementation actually demonstrated, the input x is omitted from the application data field d. The page states the input-binding case as the only one.
'Proof-of-guardrail is intended for that setting rather than for agents a user runs themselves' - the first half tracks the paper's threat model (remote agents owned by other developers), but the contrast with self-run agents is the page's own framing; the source never discusses locally-run agents.
The page's WikiLink [[DefinedTerm/guardrails]] points to an existing page that defines guardrails as an organizational framework of policies, access controls and audit trails for AI agents in a DevSecOps setting, while this page uses 'guardrail' in the paper's narrower sense of an executable content-safety / fact-checking filter (LlamaGuard3, Loki). The two do not state the same fact differently, so this is not a cross-page contradiction, but the link sends a reader to a materially different sense of the word.
The source states latency overhead twice - '34% on average' (abstract and Sec. 1) and '25% to 38%' (Sec. 4.3). The page reports only the range; both are in the source, so this is not a defect, only a note that the paper's headline figure differs in form from the one quoted.
