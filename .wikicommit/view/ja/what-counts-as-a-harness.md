このウィキで「ハーネス」という語を使うページは、それが何を含むのかについて意見が一致していない。各ページが異なる答えを出している問いは、述べるだけなら簡単である。ハーネスとは正確には何なのか。モデルの周りにあるすべてなのか、エージェント構築ソフトウェアの積み重ねの中の 1 つの層なのか、エージェントを構成するいくつかのコンポーネントの 1 つなのか、それともさらに上に別のレベルを持つオーケストレーションの 1 つのレベルなのか。このページでは、それぞれの答えを、その拠り所とともに並べて示す。どれか 1 つを選ぶことはしない。

## 広い答え: モデルでないものすべて

最も広い定義は、「Agent = Model + Harness」と「モデルでないなら、それはハーネスだ（if you're not the model, you're the harness）」という言葉に凝縮されている。Vivek Trivedy による LangChain の投稿 [[BlogPosting/the-anatomy-of-an-agent-harness]] は、モデルそのものではないコード、設定、実行ロジックのすべてをハーネスに数える。すなわち、システムプロンプト、説明付きのツール、スキル、MCP サーバー、ファイルシステム、サンドボックス、ブラウザのような同梱のインフラストラクチャ、サブエージェントの生成、ハンドオフ、モデルのルーティングのようなオーケストレーションロジック、そして決定論的な実行のためのフックやミドルウェアである。この説明では、生のモデルは、ハーネスが状態、ツールの実行、フィードバックループ、強制可能な制約を与えるまではエージェントではない。Trivedy はこれを、境界を引く多くの可能な方法のうち、彼の意見では最もすっきりしたものとして提示している。

[[DefinedTerm/agent-harness]] に関する他のいくつかの情報源も、この語をこの広い意味で用いている。Anthropic のドキュメントは [[SoftwareApplication/claude-code]] を、ツールを提供し、モデルが見るコンテキストを管理する、モデルの周りの層として説明し、その層こそが「エージェント型ハーネス（agentic harness）」の指すものだとしている。[[SoftwareApplication/openharness]] の README は、ハーネスを、LLM を包んで機能するエージェントにする完全なインフラストラクチャと呼び、「The model is the agent. The code is the harness.」という言葉で締めくくっている。[[DefinedTerm/harness-engineering]] は、「agent = model + harness」という定式化を Trivedy に帰する Addy Osmani の投稿と、コーディングエージェントとは言語モデルのためのハーネス*そのもの*であり、ユーザーが目にしないプロンプトと呼び出し可能なツールでモデルを拡張するソフトウェアであると述べる [[CreativeWorkSeries/agentic-engineering-patterns]] の 1 章を記録している。

Trivedy の投稿は、学習についての観察を付け加えている。Claude Code や Codex のような製品は、ハーネスをループに入れた状態で事後学習されるため、モデルがそのハーネスに過適合することがありうる。投稿は、Terminal Bench 2.0 のリーダーボードで、Claude Code 上の Opus 4.6 のスコアが他のハーネス上の Opus 4.6 よりはるかに低いことを指摘している。投稿はここから、あるタスクにとって最良のハーネスは、必ずしもモデルがともに学習されたハーネスではないと論じている。

## 広い答えの形式化されたバージョン

3 つの研究レビューは、広い範囲を保ちつつ、それに一覧ではなく内部構造を与えている。

[[DefinedTerm/execution-harness]] は、[[ScholarlyArticle/survey-on-agent-system-and-harness-design]] がエージェントを、実行ハーネスと結合したモデル層として記述し、それを観察インターフェース、コンテキストマネージャー、制御ループ、アクションインターフェース、状態と成果物のストア、検証とガバナンスという 6 つの部分からなるタプルとして形式化していることを記録している。このサーベイは、これが個々のツール、メモリモジュール、プロンプトテンプレート、ワークフロースクリプトのいずれよりも広いと述べ、6 つの部分を独立に最適化できるものではなく互いに結合したものとして扱っている。

[[DefinedTerm/agent-harness]] は、2 つ目のサーベイ [[ScholarlyArticle/code-as-agent-harness]] を記録している。このサーベイは、ハーネスを、モデルの周りにあるポリシーに統治されたシステムとして捉える。そしてハーネスを、その中で実行されるコードから切り離す。コードはハーネスの*内部*にある実行可能な媒体であり、ハーネスはどのコードを実行し、信頼し、永続化し、再利用し、昇格させてよいかを決める。このサーベイはまた、ハーネスを、提案されたアクションをリスクによって分類し、権限の階層を強制する安全のためのガバナーとして扱っている。

[[DefinedTerm/harness-engineering]] は、この概念をさらに押し広げるレビュー [[ScholarlyArticle/externalization-in-llm-agents]] を記録している。そこでは、ハーネスは、外部化されたモジュールがともに効果を発揮するようになる**設計された認知環境**であり、エージェンシーはモデルだけに宿るのではなく、モデルと環境の結合から立ち現れるとされる。このレビューは、この概念はまだ固まりつつある段階であると述べ、その特徴付けを閉じた定義ではなく、繰り返し現れるパターンの統合として提示している。そして、ハーネス設計の 6 つの分析次元を、実装のチェックリストとしてではなく、ハーネスのアーキテクチャを比較するための枠組みとして示している。

## より狭い答え: フレームワークの上の層

Harrison Chase の投稿 [[BlogPosting/agent-frameworks-runtimes-and-harnesses]] は、「ハーネス」を、モデルの周りのシステム一般ではなく、エージェント構築パッケージの階層の中の 1 つの位置を指すものとして用いている。[[DefinedTerm/agent-framework]] は抽象化を提供する。その下にあるエージェントランタイムは、永続的な実行のような本番運用のインフラストラクチャを提供する。そしてエージェントハーネスはフレームワークの上に位置し、デフォルトのプロンプト、ツール呼び出しの独自の方針に基づく処理、計画用ツール、ファイルシステムへのアクセスを加える。いわゆる「バッテリー同梱（batteries included）」である。彼の例は、LangChain の上に構築された LangChain 自身の [[SoftwareApplication/deep-agents]] である。

このように読むと、ハーネスはモデルの補集合ではなく、3 つのカテゴリーの 1 つである、ある種のパッケージということになる。Chase は、あらゆるコーディング CLI がある種のエージェントハーネスだと主張することもできると認めている。彼は、この用語を作ったのは自分ではないこと、その定義はまだ明確ではないこと、そして 3 つの層の間の境界は曖昧であることを述べている。たとえば LangGraph は、「おそらくランタイムでもありフレームワークでもあると説明するのが最もよい」。この分類は全体を通じて著者自身の会社のパッケージで例示されており、投稿は自らを確立された分類ではなく最初の試みと称している。

したがって、2 つの LangChain の投稿は互いに食い違っている。[[DefinedTerm/agent-harness]] は、Trivedy の後の定義が Chase の階層よりはるかに広いことを指摘している。

## 分割された答え: 4 つのうちの 1 つのコンポーネント

[[DefinedTerm/harness-engineering]] に記録されている、エージェントのガバナンスに関する Anthropic の投稿は、エージェントを 4 つに分ける。**モデル**、モデルが従って動作する指示とガードレールとして定義される**ハーネス**、モデルが使えるサービスとアプリケーションである**ツール**、そしてエージェントが動作し、何にアクセスできるかを決める**環境**である。それぞれが、能力の源泉であると同時に、監督の潜在的なポイントでもあると説明されている。

この読み方では、ツールと環境はハーネスの一部*ではない*。「モデルでないならハーネス」という定義の下では、それらはハーネスの一部である。[[DefinedTerm/harness-engineering]] は、この 4 分割を「agent = model + harness」の第 2 項を分解したものとして提示しており、それと競合するものとはしていない。それでも境界の問題は見えている。一方の説明がハーネスの一部と呼ぶものを、もう一方はその横にある別のコンポーネントとして名指ししている。

## レベル分けされた答え: エージェントハーネスとシステムハーネス

Gorinova らの論文 [[ScholarlyArticle/coding-benchmarks-are-misaligned-with-agentic-software-engineering]] は、「エージェントハーネス」を、2 つのオーケストレーションのレベルのうちの 1 つに用いている。[[DefinedTerm/system-harness]] に記録されているとおり、エージェントハーネスとは、単一のタスクに向けてツールとやり取りする言語モデルであり、モデル、プロンプト、ツール、ループを設定可能な実行器として扱われる。「コーディングエージェント」と呼ばれる成果物の大半は、この意味でのエージェントハーネスであり、論文は Claude Code、Codex、Cursor Agent、SWE-Agent、OpenHands をその例として挙げている。**システムハーネス**はそれらの外側に位置する。上位の目標をタスクに変え、各タスクを 1 つ以上のエージェントハーネスに振り分け、環境を管理し、範囲、レイテンシー、信頼度によって分けた 3 段階のフィードバックを通じて出力を回す。

ここでは「ハーネス」は入れ子にできるものを指している。内側のレベルは、広い答えにおけるハーネスと同じものではない。Gorinova らのエージェントハーネスはモデルを含むのに対し、Trivedy のハーネスはモデル以外のすべてである。そして論文は、大規模な実用的なエージェント型コーディングは外側のレベルで行われているのに、ベンチマークは内側のレベルを測定していると論じている。[[DefinedTerm/agent-harness]] は、同じ著者らが、単一の固定したモデルについて複数のエージェントハーネスで Terminal-Bench のエントリーを再現し、精度がおよそ 58% からおよそ 80% までばらついたこと、そしてモデルだけを名指ししたリーダーボードのエントリーは指定が不十分だと論じていることを記録している。

## 1 つのエージェントを超えて: 方法論的ハーネス

[[DefinedTerm/methodological-harness]] は、この語をソフトウェアの外にまで広げる、[[ScholarlyArticle/spec-driven-development-for-agentic-software-engineering]] の提案を記録している。この論文は、モデルの周りにあるソフトウェア、すなわちオーケストレーションループ、ツール、コンテキスト管理、メモリ、ガードレール、検証ループを、1 つのセッションの 1 つのエージェントを統治する*技術的*ハーネスと呼ぶ。そして、再現性、監査可能性、移転可能性、レビュー能力、協調のようなチームレベルの性質には、2 つ目の*方法論的*ハーネス、すなわち仕様を中心とした、チームが所有する実践と成果物が必要だと論じている。

この答えは、ハーネスがどれだけ長く存続するかについても意見を異にする。論文は、技術的ハーネスを、モデルが改善し、能力がモデルにネイティブに備わるにつれて価値が下がっていく一時的なものとし、方法論的ハーネスを時間とともに価値が上がるものとしている。著者らは自らの枠組みを、検証済みのモデルではなく反証可能な仮説として説明している。

## 隣接する語

ウィキにある他の 2 つの用語は、「ハーネス」によって定義されてはいないものの、同じ領域の多くをカバーしている。

[[DefinedTerm/agent-scaffold]] は、13 のオープンソースのコーディングエージェントのソースコードに基づく分類である [[ScholarlyArticle/inside-the-scaffold]] を記録している。これは、コーディングエージェントにおいてモデルを取り巻くコード、すなわち制御ループ、ツール定義、状態管理、コンテキスト戦略をその**スキャフォールド**と呼び、それを制御アーキテクチャ、ツールと環境のインターフェース、リソース管理に整理している。スキャフォールドとハーネスのページは互いにリンクしているが、「スキャフォールド」と「ハーネス」が同じものを指すかどうかは、どのページも述べていない。

[[DefinedTerm/harness-as-a-service]] は、この語を、その*上に*構築するものに対して用いている。これは Viv Trivedy に帰される枠組みで、補完を返す LLM API の上に構築することから、ランタイムを返すハーネス API の上に構築することへの移行を指す。Claude Agent SDK、Codex SDK、OpenAI Agents SDK が、この方向を指し示すものとして挙げられている。Chase と同様に、これはハーネスを構築者が書くものではなく入手するものとして扱っているが、例は一致していない。harness-as-a-service のページは OpenAI Agents SDK をハーネス API を指し示すものとして挙げているのに対し、[[DefinedTerm/agent-framework]] は Chase が OpenAI Agents SDK をエージェントフレームワークに分類していることを記録している。同じページはこの枠組みを Viv Trivedy に帰しているが、これは [[DefinedTerm/harness-engineering]] が「agent = model + harness」の発案者としても挙げている名前である。

## 答えが分かれるところ

並べてみると、各説明はいくつかの別々の線に沿って異なっている。

- **境界。** ツールと実行環境がハーネスの一部なのか、その横にある別のコンポーネントなのか。Trivedy の一覧はその両方を含み、ツールを、ファイルシステム、サンドボックス、ブラウザのような同梱のインフラストラクチャと並べて挙げている。Anthropic の Claude Code のドキュメントと OpenHarness の README はツールをハーネスの内側に置いている。Anthropic のガバナンスに関する 4 分割は、ツールと環境をそれ自体のコンポーネントとして名指ししている。
- **ものの種類。** ハーネスが、あらゆるエージェントにおけるモデルの補集合なのか（広い答え）、フレームワークやランタイムと並ぶパッケージのカテゴリーなのか（Chase）、それとも構築者がサービスとして入手するものなのか（Harness-as-a-Service）。
- **範囲。** 「ハーネス」が、単一のタスクに取り組む単一のエージェントを指すのか、その上にあって多数のエージェントに振り分けるシステムを指すのか（Gorinova ら）、それとも両者を取り巻くチームの実践を指すのか（方法論的ハーネスの提案）。
- **持続性。** [[DefinedTerm/harness-engineering]] は、モデルが改善するにつれてハーネスのコンポーネントが取り除かれたという Anthropic の報告と、その投稿が、興味深いハーネスの組み合わせの空間はモデルが改善しても縮小するのではなく移動するという立場で締めくくられていることを記録している。Trivedy の投稿は、ハーネスの機能の一部はモデルに吸収されるが、ハーネスエンジニアリングは引き続き有用であると見込んでいる。方法論的ハーネスの提案は、技術的ハーネスを価値が下がっていくもの、方法論的ハーネスを価値が上がっていくものとしている。

情報源のいくつかは、自らの定義を暫定的なものと明示している。Chase は明確な定義はまだ存在しないと言い、Trivedy は自分の境界を彼の意見では最もすっきりしたものと呼び、外部化のレビューはこの概念がまだ固まりつつある段階だとしている。
