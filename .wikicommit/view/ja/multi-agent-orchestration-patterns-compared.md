このウィキは、複数の LLM エージェントの間で作業を分担する方法をいくつか記録しており、それぞれ異なる出典に基づいて書かれている。ベンダーのガイド、ベンダーのエンジニアリング記事、実務者の講演、あるチームの本番システム、そして研究文献のレビューである。語彙は重なっており、「オーケストレーター」「プランナー」「ワーカー」「レビュアー」が繰り返し現れるが、制御がどこにあるか、エージェント間で何が受け渡されるか、そもそもなぜ作業を分割するのか、各記述の背後にどのような証拠があるかは異なる。本ページはそうした違いが見えるように各パターンを並べて示すものであり、パターンを順位付けしたり、いずれかを推奨したりはしない。

## パターンの比較

| パターン | このウィキの記述の出典 | 役割 | エージェント間での作業の受け渡し方 |
|---|---|---|---|
| [[DefinedTerm/manager-pattern]] | OpenAI のエージェント構築ガイド | 中央のマネージャーと専門エージェント | マネージャーが各専門エージェントをツールとして呼び出し、結果はマネージャーに戻る。ユーザーとの対話はマネージャーが続ける |
| [[DefinedTerm/decentralized-pattern]] | 同じ OpenAI のガイド | 対等なエージェント群。多くの場合トリアージエージェントから始まる | 一方向のハンドオフで実行と会話状態を移し、受け取ったエージェントがやり取りを引き継ぐ |
| [[DefinedTerm/sub-agent-architecture]] | Anthropic のエンジニアリング記事とドキュメント、および採用チームとハンドブックの章 | メイン（またはリード）エージェントとサブエージェント | 各サブエージェントは新しいコンテキストで作業し、凝縮した要約をリードに返す |
| [[DefinedTerm/agent-teams]] | 2 つの記事が記述する Claude Code の実験的機能 | チームリード、共有タスクリスト、チームメイト | チームメイトは共有リストからタスクを自ら引き受け、互いに直接メッセージを送り合う |
| [[DefinedTerm/planner-worker-model]] | 2 つの記事が報告する Cursor のエンジニアリング実験 | Planner、Worker、Judge | Planner がタスクを生成し（再帰的にサブプランナーとして）、Worker がそれを実装し、Judge が目標が達成されたかを評価する |
| [[DefinedTerm/planner-executor-reviewer]] | エージェント型 AI 文献のレビューと、1 つの教育用実装 | Planner、Executor、Reviewer。一般に Orchestrator の下に置かれる | 逐次的またはグラフベースのパイプライン。自由記述のテキストではなく型付きの状態遷移を用いることが多い |
| [[DefinedTerm/three-layer-agent-orchestration]] | OpenWork における 1 人のエンジニアのコードレビューシステム | 親エージェント、収集エージェントと精査エージェント、観点ごとのレビューエージェント | 親がサブエージェントを並列に起動し、精査エージェントは 2 つ以上のレビュアーが独立に挙げた指摘だけを残す |

さらに 2 つのページは、この一覧に項目を加えるのではなく、一覧の枠組みを与えている。[[DefinedTerm/llm-based-multi-agent-system]] は、総称と、あらゆるそのようなシステムを記述するためのサーベイの軸を示す。協調モデル（協力的、競争的、階層的、混合）と通信チャネル（中央集権型、分散型、階層型）である。[[BlogPosting/code-agent-orchestra]] は、コーディングのための段階的に拡大する 3 つのパターン、すなわちサブエージェント、エージェントチーム、大規模なオーケストレーションプラットフォームを示している。

## 違いのあるところ

### 制御がどこにあるか

OpenAI のガイドは、まさにこの点で 2 つのパターンを区別している。マネージャーパターンでは、マネージャーが制御を手放すことはなく、ガイドはそれをコンテキストを失わない理由として挙げている。そのエッジは戻ってくるツール呼び出しである。分散型パターンでは、エッジは戻ってこないハンドオフである。受け取ったエージェントが実行を引き継ぎ、自らユーザーに対応する。ガイドはこれを、単一のエージェントが中央で制御を保ったり結果を統合したりする必要がない場合に最適なものとして示している。

サブエージェントアーキテクチャは、マネージャーパターンと同じようにリードに制御を残すが、その記述はこの構成をツール呼び出しではなくコンテキストの分離という観点で説明している。Agent Teams は作業を分解し結果を統合するチームリードを残すが、タスク間の調整をリードから切り離している。あるチームメイトがタスクを完了とマークすると、リードが仲介しなくても依存するタスクのブロックが解除される。Planner-Worker モデルは制御を階層全体に分散させ、Planner はサブプランナーを生成でき、Judge はイテレーションをいつ終えていつやり直すかを決める。3 層オーケストレーションは親エージェントを最上位に置くが、どのレビュアーを動かすかは、変更されたファイルの拡張子から機械的に決める。

### ワーカー同士が対話するかどうか

サブエージェントを記述する各記述は、ワーカー同士は対話しないと述べている。[[DefinedTerm/agent-teams]] はこの線を明示的に引いている。サブエージェントは単一の親に報告を返すだけで互いに対話できないのに対し、チームメイトは発見を共有し、互いのアプローチに異議を唱え、メールボックスを通じて調整する。サブエージェントのページは、Anthropic のリサーチシステムにおける同じ制約を記録している。そこではリードがサブエージェントの各組が終わるのを待ち、途中でそれらを誘導することはできず、遅いサブエージェントが 1 つあるだけでシステム全体が止まる。

ワーカーが対話しない場合、必要なものは別の何かが運ぶ。サブエージェントのページにある採用チームの 1 つは、各タスクファイルを自己完結的に書き、会話ではなくファイルがエージェント間のインターフェースになるようにしている。Planner–Executor–Reviewer のレビューは、型付きの JSON ペイロードや LangGraph の状態グラフが自由記述のハンドオフに取って代わっていることを報告している。[[DefinedTerm/llm-based-multi-agent-system]] にあるマルチエージェントによるコード生成のレビューは、オーケストレーションの失敗への対策として、構造化されたスキーマベースのプロトコルを報告している。分散型パターンは、会話状態をハンドオフそのものと一緒に移す。

### そもそもなぜ作業を分割するのか

各記述は、複数のエージェントを持つ理由として異なるものを挙げている。

- **コンテキスト。** サブエージェントアーキテクチャは Anthropic によって、長期にわたるタスクでのコンテキストウィンドウの制限を回避する方法として示されている。サブエージェントは数万トークンを探索し、多くの場合 1,000〜2,000 トークンの要約を返す。[[BlogPosting/code-agent-orchestra]] は、単一エージェントの 3 つの制約の 1 つ目としてコンテキストの過負荷を挙げている。
- **より狭い範囲。** Planner–Executor–Reviewer は認知負荷を根拠に挙げる。範囲を絞ることで、計画、統合、検証を一度に行う 1 つの汎用エージェントよりも予測しやすくなることが意図されている。3 層オーケストレーションはレビューの観点について同じ議論をしている。小さく範囲の限られたタスクの方が、より正確な出力が得られるというものである。
- **調整。** Planner-Worker モデルは、同格のエージェントが共有ファイルロックを通じて調整するよりフラットな設計で、エージェントが互いを待って行き詰まったりリスク回避的になったりしたことへの答えとして報告されている。[[BlogPosting/code-agent-orchestra]] では、Agent Teams はサブエージェントが解決しないまま残す調整の問題を解決するものとされている。
- **処理能力。** Anthropic のリサーチシステムに関する記事は、BrowseComp において性能の分散の 80% がトークン使用量で説明されることを、作業を別々のコンテキストウィンドウに分散させるアーキテクチャの妥当性を裏付けるものと読んでいる。
- **プロンプトとツールの肥大化。** OpenAI のガイドは、多くの条件分岐が積み重なったプロンプトや、選択を混乱させるほど重複したツールを、分割のきっかけとして挙げている。
- **復旧。** サブエージェントのページにある採用チームの 1 つは、失敗したフェーズを実行全体ではなくそれ単独でやり直せることを付け加えている。

### レビューをどこに置くか

ほとんどのパターンはどこかに検査の役割を置いているが、その置き方は異なる。

- Planner–Executor–Reviewer では、Reviewer は単なる 3 番目の段階ではなく、このパターンの検証可能性を担う仕組みとして記述されている。このページは、パターンの適合性を、Reviewer が照らし合わせるべき客観的な基準を持っているかどうかに依存させている。正解となるシグナルのないフェーズにいる Reviewer は、自らの判断しか適用できない。
- Planner-Worker モデルは、各イテレーションの最後に Judge が全体の目標が達成されたかを評価する。
- Agent Teams には、lint、テスト、セキュリティスキャンのツールに限定され、タスクが完了するたびに起動される、読み取り専用の「@reviewer」チームメイトという実践例が報告されている。
- Claude Code のドキュメントにおけるサブエージェントアーキテクチャの 2 つ目の用途は、差分と基準だけを見る新しいコンテキストからの敵対的レビューである。同じドキュメントは、そうしたレビュアーは作業が健全であっても通常何らかの不足を報告すると警告し、正しさと明示された要件に限定することを推奨している。
- 3 層オーケストレーションは、判定するレビュアーを合意に置き換えている。2 つのモデルファミリーの 4 つのエージェントが各観点をレビューし、1 つだけが挙げた指摘は破棄される。

### コストと、適さない場合

コストを論じるすべての記述は、分割を正当化が必要なものとして扱っている。

- OpenAI のガイドは、複数のエージェントを導入する前に、まず単一エージェントの能力を最大限に引き出すことを推奨している。
- Anthropic のリサーチシステムに関する記事は、マルチエージェントシステムがチャットでのやり取りの約 15 倍のトークンを使用すると報告し、現時点ではほとんどのコーディングタスクは適さないとしている。同じページにある採用チームは、このパターンをコーディングのパイプライン全体で運用している。このページは両者を合わせて、限界はタスクの切り分け方に依存することを示すものと読んでいるが、どちらの側も測定はされていない。
- Agent Teams は、各チームメイトが別個の Claude インスタンスであるため、より多くのトークンを消費する。[[BlogPosting/code-agent-orchestra]] は 3〜5 人のチームメイトが最適だと報告している。
- Planner-Worker の出典は、この規模はまだ一般的ではなく、ほとんどのユーザーにとっては大規模な群れよりも、有能な長時間稼働エージェント 1 つの方が実用的であることが多いと記している。
- 3 層オーケストレーションは、多数のサブエージェントを起動しても個別に課金されない料金体系を前提としており、呼び出しごとの課金にはそのままでは移せない。
- [[DefinedTerm/llm-based-multi-agent-system]] にあるハンドブックの章は、調整のオーバーヘッドが専門化による利得を打ち消しうること、そして逐次的で密結合のタスクには複雑なフレームワークは要らないことを警告している。

## 各記述の背後にあるもの

各パターンは異なる種類の証拠に基づいており、各ページはそのことを明記している。

- **マネージャーパターンと分散型パターン**：独立に確立された分類ではなく、1 つのベンダーが自社の顧客経験を特徴づけたものであり、コード例もそのベンダーの SDK によるものである。
- **サブエージェントアーキテクチャ**：ベンダーが報告した結果。設計が記述されていない社内のリサーチ評価で、リードとサブエージェントからなるシステムが単一エージェントを 90.2% 上回ったというものを含む。これに採用チームによる測定されていない報告が加わる。
- **Agent Teams**：実験的機能であり、セッション再開時にチームメイトが復元されないことや、タスクの状態の反映が遅れうることなどの制限事項が列挙されている。
- **Planner-Worker モデル**：1 社が報告した実験とその本番設計であり、2 つの記事を通じて伝えられたものである。
- **Planner–Executor–Reviewer**：レビューの 92 件の一次研究全体で支配的なアーキテクチャと報告されており、そのうち 13 件は産業の文脈で評価されたものである。教育用実装は、このパターンがどう教えられているかの証拠であって、どう機能するかの証拠ではない。
- **3 層エージェントオーケストレーション**：本番運用されている 1 人のエンジニアのシステムであり、定性的なフィードバックがある。著者が示した評価基準が満たされたとは報告されていない。
