このウィキにあるいくつかのツールは、[[DefinedTerm/spec-driven-development]] を実践に移している。すなわち、開発者の依頼とコーディングエージェントによる実装の間に、書かれた仕様が挟まる。ただし、その仕様の位置付け方はツールごとに異なる。このページでは、そのうち 8 つ、すなわち
[[SoftwareApplication/github-spec-kit]]、[[SoftwareApplication/kiro]]、[[SoftwareApplication/tessl]]、
[[SoftwareApplication/openspec]]、[[SoftwareApplication/spec-kitty]]、[[SoftwareApplication/bmad]]、
[[SoftwareApplication/get-shit-done]]、[[SoftwareApplication/cc-sdd]] を並べて比較する。比較には、この分野についてウィキが持つ 2 つの比較の枠組みを用いる。このページはツール同士がどこで異なるかを記録するものであり、どれを使うべきかは述べない。

## ウィキがすでに持つ 2 つの枠組み

ウィキには、これらのツールを比較する 2 つの道具があり、それぞれ異なるツールの部分集合に適用されている。

- **Böckeler の実装レベル**は [[DefinedTerm/spec-driven-development-levels]] で説明されており、タスクの後で仕様がどうなるかを問う。*スペックファースト*では、仕様は目の前のタスクのために書かれる。*スペックアンカード*では、仕様は保持され、機能とともに進化していく。*スペック・アズ・ソース*では、人間は仕様だけを編集し、コードには決して手を触れない。彼女はこのレベルを、2025 年後半時点の Kiro、Spec Kit、Tessl に適用した。
- **[[DefinedTerm/six-dimension-process-taxonomy]]** は、支援フレームワークを 6 つの次元、すなわち仕様・コンテキスト・役割・実行・検証・可搬性について 0 から 2 で採点する。その研究である [[ScholarlyArticle/from-prompt-to-process]] は、これを 6 つのフレームワークに適用した。そのうち 5 つ、すなわち Spec Kit、OpenSpec、Spec Kitty、BMAD、GSD がこのページに登場する。各フレームワークは、単一の評価者が公式ドキュメントに基づいて採点した。研究は、スコアが独立した経験的測定ではなく著者の判断であると述べている。

根拠となるページには、Kiro、Tessl、cc-sdd の 6 次元スコアは記録されておらず、Böckeler のレベルも cc-sdd には適用されていない。

## 仕様はコードにとって何か

この軸で、ツール同士の違いは最もはっきりと表れる。

- **Tessl** はスペック・アズ・ソースの端に位置する。そこでは仕様が開発者の編集する唯一の成果物であり、コードは仕様から再生成される。生成されたコードには
  `// GENERATED FROM SPEC – DO NOT EDIT` というマーカーが付く。ドキュメント化されたコマンドには逆方向に働くものもあり、既存のコードから仕様を導き出す。Böckeler は Tessl を、彼女が調べた 3 つのツールのうち、明示的にスペックアンカードを目指し、スペック・アズ・ソースを探っている唯一のツールと読んでいる。
- **Spec Kit** は、GitHub によって「コードが信頼できる唯一の情報源である」から「意図が信頼できる唯一の情報源である」への転換として提示されている。それでも Böckeler は、仕様ごとにブランチを作ることから、Spec Kit はまだスペックファーストにとどまると読んでいる。
- **Kiro** は、Böckeler によっておおむねスペックファーストと読まれている。
- **cc-sdd** は、バージョン 3.0 の README で明確に異なる立場を取る。仕様はシステムの各部分の間の契約であり、コードが引き続き信頼できる唯一の情報源であって、仕様は人間とエージェントが並行して作業できるように境界を明示するものだとする。一方で、その入門ガイドは依然として仕様を、実装後に削除するのではなくコミットして残す生きたドキュメントとして扱っている。

## プロセスの形

| ツール | ドキュメント化されたフロー |
|---|---|
| Kiro | コード生成の前に、要件 → 設計 → タスク |
| Spec Kit | Specify → Plan → Tasks → Implement → Converge。implement と converge は「Converged」になるまで繰り返される。バグ修正とアイデアの評価は、別個のオプトインの入口になっている |
| Spec Kitty | spec、plan、tasks、next、review、accept、merge |
| cc-sdd | ステアリング、EARS 形式の要件、設計、タスク分割、実装（コマンド形式）。バージョン 3.0 では、ディスカバリーの入口と長時間の自律的な実装が加わる |
| BMAD | 任意の分析、計画、ソリューション、実装の各フェーズと、小さなタスク向けのクイックフロー。README は、Clarify、Plan、Build and verify のいずれかから入れると説明している |
| OpenSpec | 別々のドキュメントを段階的に作るのではなく、1 つの統合された仕様と、追跡可能な変更提案 |
| GSD | 大まかな依頼を仕様と実行可能なステップに変換する、コマンドと規約の層 |
| Tessl | 仕様を編集し、コードはそこから生成・再生成される |

これらのフローの間には、1 つの系譜が記録されている。cc-sdd は、その設計を Kiro の仕様駆動開発に着想を得たものとしており、Kiro の仕様と互換性がある。cc-sdd は、3 つのステアリングドキュメント用のものを含むテンプレートを `.kiro/settings/` ツリーの下にインストールする。Kiro 自身は、Steering ファイルを `.kiro/steering/` の下に置いている。

## 役割、コンテキスト、検証

研究が評価した 5 つのフレームワークの 6 次元スコアは次のとおりである。

| フレームワーク | 仕様 | コンテキスト | 役割 | 実行 | 検証 | 可搬性 | 合計 |
|---|---|---|---|---|---|---|---|
| BMAD | 2 | 2 | 2 | 1 | 2 | 1 | 10 |
| GSD | 1 | 2 | 0 | 1 | 0 | 0 | 4 |
| OpenSpec | 2 | 1 | 0 | 1 | 0 | 2 | 6 |
| Spec Kit | 2 | 1 | 1 | 1 | 1 | 2 | 8 |
| Spec Kitty | 2 | 1 | 1 | 2 | 2 | 1 | 9 |

研究は、この表からプロセスの深さと可搬性の間の構造的な対立を読み取っている。可搬性で 2 を得たフレームワーク、すなわち Spec Kit と OpenSpec は、役割と検証を犠牲にしている。最も深いプロセスを持つ BMAD は、可搬性と実行を犠牲にしている。コンテキストに最も焦点を当てたフレームワークである GSD は、役割、検証、可搬性で 0 となっている。仕様はほぼすべてのフレームワークで 2 となるため、研究はこれを最も識別力の低い次元として扱う。役割と検証は最も二極化しており、したがって最も識別力が高い。

各ツールは、それぞれ異なる手段でこれらのスコアに至っている。

- **役割。** BMAD はチームという比喩を文字どおりに受け取る。デフォルトのエージェントは、アナリスト、プロダクトマネージャー、アーキテクト、開発者、UX デザイナー、テクニカルライターであり、各役割が次のフェーズへとつながるワークフローを起動する。OpenSpec と GSD はここで 0 となる。
- **実行と隔離。** Spec Kitty は各作業パッケージを [[DefinedTerm/git-worktrees|Git ワークツリー]] に隔離し、マージの前にレビューと受け入れを求める。評価されたフレームワークの中で、実行で 2 を得たのは Spec Kitty だけである。cc-sdd v3.0 は、ホストエージェントがネイティブなサブエージェントを持つ場合、各タスクに新しいテストファーストの実装担当と独立したレビュー担当を割り当てる。
- **コンテキスト。** GSD は、コンテキストの組み立て、すなわちエージェントが何を、どの順序で、どのような枠付けの下で読むかを、明示的なエンジニアリング作業として扱う。Kiro の Steering ファイルと cc-sdd の steering コマンドは、別の形、すなわちプロダクト、技術、構造を記述するファイルとして、エージェントに常設のプロジェクトコンテキストを与える。
- **人間によるゲート。** Spec Kit は、各フェーズを次のフェーズが始まる前に人間がレビューするものとして提示しており、そのリポジトリはスキルを一度に 1 つずつ呼び出すよう強く求めている。cc-sdd 自身の要約は、エージェントが仕様を書き、人間がフェーズゲートで契約を承認するというものである。そのガイドは、ツールを学んでいる間は前のフェーズを自動承認するフラグを使わないよう勧めている。

## 可搬性とパッケージング

ツールは、それぞれ異なる方法でエージェントに結び付く。

- **Spec Kit** は、`specify init --integration` によってプロジェクトごとに 1 つのエージェントに結び付けられる。そのプロセスは `/speckit-*` エージェントスキルとして実行され、一覧にないエージェント向けに `generic` 統合も用意されている。
- **OpenSpec** は、スラッシュコマンドを通じて数十のコードアシスタントをサポートすると表明している。研究はこれを、OpenSpec をエージェントの上の薄い層として位置付けるものと読んでいる。
- **cc-sdd** は、8 つのサポート対象エージェントを挙げており、2 つが安定版、6 つがベータ版である。スキルをインストールしても、ホストが完全な自律ループを実行できることは検証されないと注意を促している。
- **BMAD** は [[DefinedTerm/agent-skills]] として、あるいは Claude Code や Codex のプラグインとしてインストールでき、さらに選ばれたワークフローを、コーディングツールの外での計画用に Gemini Gems や ChatGPT のカスタム GPT としてパッケージ化している。
- **Spec Kitty** は複数のエージェントで動作するが、独自のリポジトリ規約と Git ワークツリーに依存する。
- **GSD** は [[SoftwareApplication/claude-code]] 向けに作られており、研究はその可搬性を Spec Kit や OpenSpec より限定的だと述べている。
- **Kiro** は、他のエージェントの上の層ではなく、単体の AI IDE である。

## 情報源が挙げる注意点

根拠となるページでは、各ツールにそれぞれの注意点が付いている。これらは情報源が提起する懸念であり、評決ではない。

- **Spec Kit:** 検証が弱いところでの、成果物と実装の間のずれ。
- **OpenSpec:** オーバーヘッドの低さは、プロジェクトがより精緻な役割、アーキテクチャ、検証を必要とする場合には不十分かもしれない。
- **Spec Kitty:** 牽引力がまだ控えめであり、成熟度と普及は未知数である。
- **BMAD:** プロセスのコストと、それを使うのに必要な規律。
- **GSD:** チームのプロンプト規約への依存と、新しい組織への移行を示唆したリポジトリの不安定さ。
- **Kiro:** あるハンドブックは、測定に基づかない判断として、直感的だが扱いにくく、単発のタスクに向いていると評している。
- **Tessl:** スペック・アズ・ソースには、成熟した信頼できるコード生成ツールが必要である。Böckeler は、スペック・アズ・ソースがモデル駆動開発と LLM の双方の欠点を抱え込むことになるのではないかと疑問を呈している。
- **cc-sdd:** そのガイドは、小さな修正、1 回のやり取りで済むタスク、探索的な作業を、cc-sdd に向かないものとして挙げている。

分類法の研究は、この分類法が対象としたフレームワークの大半が独立した学術的評価を経ていないと指摘している。Spec Kit、OpenSpec、BMAD の各ページも、それぞれのフレームワークについてこの点を記録している。これらのフレームワークは活発に開発が続いているため、どちらの分類もスナップショットである。
